## 一、对齐规则

### 1.1 两条规则，全部内容

> **规则一**：每个成员的偏移，必须是「该成员自身对齐值」的整数倍。
> **规则二**：结构体总大小，必须是「所有成员中最大对齐值」的整数倍。

对齐值（alignment）通常等于成员的 `sizeof`，但有例外（`long double`、SIMD 类型、加了 `aligned` 属性的类型）。

### 1.2 为什么要有对齐

硬件总线的物理限制。32 位 CPU 读内存是按 4 字节一组读的：

```
地址 0x1000: [byte0][byte1][byte2][byte3]  ← 一次读完
地址 0x1004: [byte4][byte5][byte6][byte7]
```

如果一个 `uint32_t` 从 `0x1002` 开始，它就横跨了两次总线读。有些架构（Cortex-M0）**直接拒绝**这种访问（HardFault）；有些（x86）能处理但慢一倍；Cortex-M3/M4 支持但同样有性能损失。

### 1.3 每个基础类型的典型对齐值

| 类型 | 大小 | 对齐值（ARM 32 位） | 对齐值（x86-64） |
|:--|:--|:--|:--|
| `char` / `uint8_t` | 1 | 1 | 1 |
| `short` / `uint16_t` | 2 | 2 | 2 |
| `int` / `uint32_t` | 4 | 4 | 4 |
| `float` | 4 | 4 | 4 |
| `double` | 8 | **8**（AAPCS）或 4 | 8 |
| 指针 | 4 / 8 | 4 | 8 |
| `long long` | 8 | 8 | 8 |

⚠️ **`double` 在 ARM 上是 8 字节，但 32 位 ARM 的对齐要求可能是 4**。这导致同一个结构体在 PC 和 MCU 上大小不同 —— 跨平台协议千万别直接 `memcpy` 结构体。

## 二、结构体大小的计算公式

### 2.1 手算流程

给定：

```c
struct bad {
    uint8_t  a;   // 1 字节, 对齐 1
    uint32_t b;   // 4 字节, 对齐 4
    uint8_t  c;   // 1 字节, 对齐 1
};
```

**逐成员算偏移**：

| 成员 | 大小 | 对齐 | 当前偏移 | 需要填充 | 实际偏移 |
|:--|:--|:--|:--|:--|:--|
| `a` | 1 | 1 | 0 | 0（0 是 1 的倍数） | 0 |
| `b` | 4 | 4 | 1 | **3**（补到 4） | 4 |
| `c` | 1 | 1 | 8 | 0 | 8 |
| — | — | — | 结束于 9 | **补到 4 的倍数** → **12** | |

**`sizeof = 12`**，成员合计只有 6 字节，**浪费 6 字节（50%）**。

实测验证：

```
bad=12  offsets: a=0 b=4 c=8
```

### 2.2 重排省一半

```c
struct good {
    uint32_t b;   // offset 0
    uint8_t  a;   // offset 4
    uint8_t  c;   // offset 5
};                // 6 字节 → 补到 8
```

实测 `good=8`。**省了 4 字节（33%）**，功能完全一样。

**重排原则**：**按对齐值从大到小排列**。同对齐值的成员放在一起。

```c
// 优化前：24 字节
struct s1 {
    uint8_t  a;   // 0
    uint32_t b;   // 4  (填充 3)
    uint8_t  c;   // 8
    uint64_t d;   // 16 (填充 7)
    uint8_t  e;   // 24
};                // 25 → 32

// 优化后：16 字节
struct s2 {
    uint64_t d;   // 0
    uint32_t b;   // 8
    uint8_t  a;   // 12
    uint8_t  c;   // 13
    uint8_t  e;   // 14
};                // 15 → 16（填充 1）
```

**从 32 字节降到 16 字节**，省 50%。在 RAM 只有几 KB 的 MCU 上，这种优化经常是必须的。

### 2.3 用工具验证，别靠猜

```c
#include <stddef.h>
#include <stdio.h>

printf("sizeof = %zu\n", sizeof(struct s2));
printf("offsetof a = %zu\n", offsetof(struct s2, a));
printf("offsetof b = %zu\n", offsetof(struct s2, b));
```

**编译期断言更好**（不占运行时）：

```c
// C11
_Static_assert(sizeof(struct wire) == 6, "wire 必须是 6 字节");

// 老编译器
typedef char wire_size_check[(sizeof(struct wire) == 6) ? 1 : -1];
```

协议结构体**必须**加这个断言 —— 换编译器、换目标架构、加个 `-fpack-struct`，大小都可能变。

## 三、成员顺序决定大小

### 3.1 三个"一样"的结构体

```c
struct a { uint8_t x; uint16_t y; uint8_t z; };   // 6 字节
struct b { uint8_t x; uint8_t z; uint16_t y; };   // 4 字节
struct c { uint16_t y; uint8_t x; uint8_t z; };   // 4 字节
```

`b` 和 `c` 都是 4 字节，`a` 是 6 字节。**同样的三个字段，差 2 字节**。

### 3.2 真实的取舍

```c
// 版本 1：按逻辑顺序写（好读，但浪费）
typedef struct {
    uint8_t  version;      // 0
    uint32_t timestamp;    // 4  ← 填充 3
    uint16_t length;       // 8
    uint8_t  flags;        // 10
} header_t;                // 12 字节

// 版本 2：按对齐排（省 25%，但字段顺序和协议文档不一致）
typedef struct {
    uint32_t timestamp;    // 0
    uint16_t length;       // 4
    uint8_t  version;      // 6
    uint8_t  flags;        // 7
} header_t;                // 8 字节
```

**内存储结构体（只在 RAM 里用）→ 重排**。**协议结构体 → 用 `#pragma pack`，保持字段顺序**。

## 四、嵌套结构体与联合体

### 4.1 嵌套的对齐值是「内层最大值」

```c
struct in {
    uint16_t x;   // 对齐 2
    uint8_t  y;   // 对齐 1
};                // sizeof = 4（填充 1）

struct nested {
    uint8_t   a;      // offset 0
    struct in i;      // offset 2（in 的对齐是 2，所以不能放 1）
    uint8_t   z;      // offset 6
};                    // 7 → 补到 4 的倍数 = 8
```

实测：

```
nested=8  offsets: a=0 i=2 i.x=2 z=6
```

⚠️ **注意 `i` 的偏移是 2，不是 1** —— 因为 `struct in` 的对齐值继承自它最大的成员（`uint16_t` = 2）。`a` 占 1 字节，后面补 1 字节，`i` 才能从 2 开始。

### 4.2 联合体：所有成员共享同一块内存

```c
union u {
    uint32_t w;      // 4 字节
    uint8_t  b[4];   // 4 字节
};                   // sizeof = 4
```

实测 `u=4`。

**联合体大小 = 最大成员的大小**，且要按最大对齐值补齐。

```c
union weird {
    uint32_t w;      // 4, 对齐 4
    uint8_t  b[6];   // 6, 对齐 1
};                   // 6 → 补到 4 的倍数 = 8
```

### 4.3 联合体的两个真实用途

**① 按字节访问一个多字节值（端序检测）**

```c
union {
    uint32_t u32;
    uint8_t  u8[4];
} test = { .u32 = 0x11223344 };

if (test.u8[0] == 0x44) {
    // 小端
}
```

⚠️ 这个做法在某些编译器上有 type-punning 争议。**更稳的方式**：

```c
uint32_t v = 0x11223344;
uint8_t first;
memcpy(&first, &v, 1);   // memcpy 是标准保证的，不算 UB
```

**② 协议报文的多种解释（同一份数据，不同视角）**

```c
typedef union {
    struct {
        uint8_t type;
        uint8_t len;
        uint8_t data[6];
    } fields;
    uint8_t raw[8];
} frame_t;

// 收：先填 raw，再读 fields
memcpy(frame.raw, rx_buf, 8);
process(frame.fields.type);
```

**这样做的好处**：解析时不用手工算偏移，编译器和结构体定义帮你算。**坏处**：`fields` 内部仍有对齐填充，所以**必须 `#pragma pack(1)`**，否则 `data` 的偏移会错。

## 五、位域

### 5.1 基本语法

```c
struct flags {
    unsigned enable : 1;   // 1 位
    unsigned mode   : 3;   // 3 位
    unsigned rsvd   : 4;   // 4 位
};
```

`sizeof(struct flags) == 4`（实测 `bf1=4`），不是 1 —— 因为成员类型 `unsigned` 的对齐是 4。

**换成 `uint8_t` 就紧凑了**：

```c
struct flags8 {
    uint8_t enable : 1;
    uint8_t mode   : 3;
    uint8_t rsvd   : 4;
};                       // sizeof = 1（实测 bf4=1）
```

### 5.2 位域的四个致命问题

**① 布局由编译器决定**

```c
struct bf4 { uint8_t a:4, b:4; };
struct bf4 v;
v.a = 0xF;
v.b = 0x3;
```

实测内存里的第一个字节是 **`0x3F`** —— 说明 GCC 在 x86 上把**先声明的 `a` 放在低位**。

但**标准没规定这一点**。换编译器/换架构，`a` 可能在**高位**（变成 `0xF3`）。所以：

> **位域绝对不能用于跨设备协议**。发出去的字节序会随编译器变。

**② 不能取地址**

```c
struct flags f;
&f.mode;      // ❌ 编译错误：cannot take address of bit-field
```

原因：位域不占完整的可寻址单元。这直接导致不能用 `scanf("%d", &f.mode)`、不能传给任何接受指针的函数。

**③ 读写是「读-改-写」，非原子**

```c
f.mode = 3;
// 编译成：
//   load  byte
//   and   0xF1        (清掉 bit1-3)
//   or    0x06        (写入 3<<1)
//   store byte
```

如果中断里也在改同一个字节的**其他位域**，就会互相覆盖：

```c
// 主循环
f.mode = 3;       // 读-改-写之间被中断打断

// 中断
f.enable = 1;     // 改了同一字节，主循环的 store 会把 enable 覆盖回 0
```

**④ 跨存储单元的行为未定义**

```c
struct bad {
    uint8_t a : 7;
    uint8_t b : 7;    // 第 8 位放不下，怎么办？
};
```

标准说这是 implementation-defined（由实现决定）。GCC 默认会开一个新的存储单元，但这不保证所有编译器一样。

### 5.3 那什么时候能用位域

**可以用的场景**：
- 纯粹 RAM 内部状态标志（不跨设备、不跨编译器）
- 单线程或全程在临界区内操作
- 团队统一编译器版本

**不能用**：
- 协议报文（必须用 `#pragma pack` + 手动位操作）
- 硬件寄存器（必须用位掩码，见 04 位操作）
- 多线程/中断共享

### 5.4 真实工程的替代方案

很多 UDS / ISO-TP 协议栈里全部用**掩码宏**，没有一个位域：

```c
// ISO-TP 帧类型在首字节高 4 位
#define IsSF(x) ((((x) >> 4u) == SF) ? TRUE : FALSE)
#define IsFF(x) ((((x) >> 4u) == FF) ? TRUE : FALSE)
#define IsCF(x) ((((x) >> 4u) == CF) ? TRUE : FALSE)

// 设置流控状态：保留低 4 位，只改高 4 位
#define SetFS(buf, fs)  (*(buf) = (*(buf) & 0xF0u) | (uint8_t)(fs))
#define GetFS(fs, buf)  (*(buf) = (fs) & 0x0Fu)

// 序号只占低 4 位
#define IsRxSNValid(sn) (gs_stCanTPRxDataInfo.ucSN == ((sn) & 0x0Fu))
```

**为什么这样更好**：
1. 布局由代码明确表达，不依赖编译器
2. 可以单独对某几位做「读-改-写」，也能一次性操作
3. 汇编层面的指令可预测
4. `& 0xF0 | x` 这种写法在任何平台上结果相同

## 六、`#pragma pack`：协议报文的必需品与陷阱

### 6.1 用法

```c
#pragma pack(push, 1)
struct wire {
    uint8_t  a;   // offset 0
    uint32_t b;   // offset 1  ← 不再填充
    uint8_t  c;   // offset 5
};                // sizeof = 6
#pragma pack(pop)
```

实测 `wire=6`（对比默认的 `bad=12`）。

⚠️ **必须用 `push` / `pop` 成对**。如果只写 `#pragma pack(1)`，它会**影响后面所有结构体**，包括标准库头文件里的 —— 那是灾难。

```c
// ❌ 危险写法
#pragma pack(1)
struct a { ... };
// 后面整个文件的所有 struct 都是紧凑的

// ✅ 安全写法
#pragma pack(push, 1)
struct a { ... };
#pragma pack(pop)
```

### 6.2 代价：未对齐访问

```c
#pragma pack(push, 1)
struct wire { uint8_t a; uint32_t b; };
#pragma pack(pop)

struct wire w;
uint32_t v = w.b;   // b 的地址可能是 0x...001，未对齐 4
```

⚠️ 在 **Cortex-M0/M0+ 上这会直接 HardFault**（这些核不支持非对齐访问）。Cortex-M3/M4 支持但慢。

**正确用法：紧凑结构体只当「缓冲区视图」，用完立刻拷进对齐结构体**：

```c
#pragma pack(push, 1)
typedef struct { uint8_t a; uint32_t b; uint8_t c; } wire_t;
#pragma pack(pop)

typedef struct { uint8_t a; uint32_t b; uint8_t c; } aligned_t;   // 无 pack，12 字节

void parse(const uint8_t *raw) {
    wire_t w;
    memcpy(&w, raw, sizeof(w));      // 从缓冲区拷进紧凑结构体（memcpy 允许未对齐源）
    aligned_t a;                     // 目标是对齐的
    a.a = w.a;
    a.b = w.b;                       // 从紧凑结构体读，编译器会生成安全的字节访问
    a.c = w.c;
    use(&a);                         // 后续都用对齐版本
}
```

**更彻底的做法**：不定义紧凑结构体，直接用 `BE32(p)` 之类的宏从字节数组里读（见 01 文档 2.4 节）。这样连 `memcpy` 都省了，而且端序显式。

### 6.3 `-fpack-struct` 是核弹

gcc 有个全局开关 `-fpack-struct[=n]`，让**所有**结构体紧凑。**永远不要用它** —— 它会打破 libc、HAL、任何第三方库的 ABI 假设。

## 七、柔性数组

### 7.1 语法

```c
typedef struct {
    uint16_t len;
    uint8_t  data[];    // 柔性数组成员，必须是最后一个
} msg_t;
```

`sizeof(msg_t) == 2`（实测 `flex=2`）—— **柔性数组本身不占空间**。

### 7.2 为什么比「指针 + 单独分配」好

```c
// ❌ 方案 A：指针 + 两次分配
typedef struct { uint16_t len; uint8_t *data; } msg_a;
msg_a *m = malloc(sizeof(*m));
m->data = malloc(len);
// 释放要两次，而且 data 和结构体不连续（缓存不友好）

// ✅ 方案 B：柔性数组 + 一次分配
msg_t *m = malloc(sizeof(msg_t) + len);
m->len = len;
memcpy(m->data, src, len);
// 一次分配一次释放，内存连续
```

**关键优势**：`data` 紧跟在 `len` 后面，**整个消息是一块连续内存**。这对 DMA、网络收发、环形缓冲都很重要。

### 7.3 资源受限环境里的用法

没有操作系统时一般不用 `malloc`，但柔性数组可以用在**静态缓冲区视图**上：

```c
#define MSG_BUF_SIZE 256
static uint8_t g_msg_buf[MSG_BUF_SIZE];

void build_msg(void) {
    msg_t *m = (msg_t *)g_msg_buf;   // 用静态缓冲区当柔性数组结构体
    m->len = 10;
    memcpy(m->data, "0123456789", 10);
    send(g_msg_buf, sizeof(msg_t) + m->len);
}
```

⚠️ **对齐风险**：`g_msg_buf` 是 `uint8_t` 数组，转成 `msg_t *` 时如果地址不是 2 的倍数，`m->len` 就是未对齐访问。必须加对齐：

```c
static uint8_t g_msg_buf[MSG_BUF_SIZE] __attribute__((aligned(4)));
```

### 7.4 柔性数组的两个限制

1. **必须是最后一个成员**（否则编译器不知道结构体多大）
2. **结构体不能作为数组元素**（`msg_t arr[10]` 非法）—— 因为每个元素的大小不确定

C99 之前的「struct hack」写法是 `uint8_t data[1]`，那个**会占 1 字节**（有时 4 字节，因为对齐），且是 UB。**用 `[]`，不要用 `[1]`**。

## 八、`container_of`：从成员反推结构体

### 8.1 原理

给定「成员地址」和「成员在结构体里的偏移」，反推「结构体本身的地址」：

```c
#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))
```

### 8.2 一个可运行的例子

```c
struct list {
    struct list *next;   // offset 0
    int val;             // offset 8（64位）
};

struct list a = {0, 10}, b = {0, 20};
a.next = &b;

struct list *p = a.next;   // p 指向 b
// 现在只知道 &p->next，怎么拿到 b 本身？
printf("%d\n", container_of(&p->next, struct list, next)->val);   // 20 ✅
```

实测输出 `val via container_of: 20`。

### 8.3 为什么内核和驱动都用它

```c
// Linux 内核：链表节点嵌在任意结构体里
struct my_device {
    struct list_head list;   // 链表节点（嵌在里面，不是指针）
    int id;
    char name[32];
};

// 遍历链表时只拿到 list_head 的地址，用 container_of 反推
struct my_device *dev = container_of(node, struct my_device, list);
```

**优势**：
- 不用额外分配链表节点（省内存）
- 一个结构体可以同时在多个链表里（多个 `list_head` 成员）
- 不像「指针链表」那样有额外的指针开销

### 8.4 简化版

```c
typedef struct {
    uint32_t magic;
    uint8_t  data[64];
} packet_t;

void on_rx(const uint8_t *raw) {
    packet_t *p = container_of(raw, packet_t, data);   // 从 data 反推 packet
    if (p->magic != 0x5041434B) {   // "PACK"
        return;
    }
    // ...
}
```

⚠️ **前提是 `raw` 确实来自某个 `packet_t` 的 `data`**。如果传进来的是独立缓冲区，减掉偏移后得到的就是野地址。**这个宏不做任何检查**，用错的后果是直接崩。

## 九、工程实践

### 9.1 结构体对齐属性

```c
// 强制 32 字节对齐（DMA 缓冲区常用）
typedef struct {
    uint8_t buf[512];
} dma_buf_t __attribute__((aligned(32)));

// 或者单独给变量加
static uint8_t dma_buf[512] __attribute__((aligned(32)));
```

### 9.2 用结构体映射寄存器

```c
struct systimer {
    volatile uint32_t CONF, UNIT0_OP, /* ... */ INT_ENA, INT_RAW, INT_CLR, INT_ST,
        RESERVED0[34], DATE;
};
#define SYSTIMER ((struct systimer *) 0x6000F000)
```

**这里的 `RESERVED0[34]` 是必须的** —— 它对应手册里真实存在的空档。少写一个，后面所有寄存器偏移全错。

### 9.3 结构体版本兼容（协议演进）

```c
typedef struct {
    uint8_t  version;
    uint8_t  length;        // 本结构体实际长度
    uint16_t flags;
    // v1 字段到此为止
} msg_v1_t;

typedef struct {
    uint8_t  version;
    uint8_t  length;
    uint16_t flags;
    uint32_t extra;         // v2 新增
} msg_v2_t;
```

**解析时先读 `length`，再决定怎么解释后面的字节**。这是协议向前兼容的标准做法。

### 9.4 `.bss` 里的结构体不自动清零？

其实**会**清零（`.bss` 段整个被启动代码 memset），但**只有「零初始化」和「未初始化」的全局变量才在 `.bss`**：

```c
static my_struct_t g_a;                    // .bss，清零
static my_struct_t g_b = {0};              // .bss，清零
static my_struct_t g_c = {.x = 1};         // .data，从 Flash 拷
my_struct_t local;                          // 栈上，**脏值**！
```

⚠️ **局部结构体不清零**：

```c
void f(void) {
    my_struct_t m;       // 栈上，内容是上一个函数留下的垃圾
    if (m.flag) { ... }  // 随机行为
}
```

**修法**：`my_struct_t m = {0};` 或 `memset(&m, 0, sizeof m)`。

## 十、错误清单

| 症状 | 原因 | 修法 |
|:--|:--|:--|
| 结构体比预想大 | 对齐填充 | 按对齐值从大到小重排；用 `offsetof` 核对 |
| 协议解析错位 | 缺 `#pragma pack(1)` | 加 pack + 编译期断言 `sizeof` |
| 加了 pack 后 HardFault | 未对齐访问 | 只当缓冲区视图，`memcpy` 到对齐结构体 |
| 位域发出去对端解析错 | 布局实现相关 | 改用手动位操作宏 |
| 位域改一个字段，另一个也变了 | 非原子读-改-写 | 进临界区，或改普通变量 |
| `&s.bitfield` 报错 | 位域不可寻址 | 用普通变量或抽到临时变量 |
| 柔性数组 `sizeof` 是 0 | 正常，柔性数组不占空间 | 分配时 `sizeof(T) + n` |
| `msg_t arr[10]` 报错 | 含柔性数组的结构体不能做数组元素 | 改用指针数组 |
| 局部结构体行为诡异 | 栈上未初始化 | `= {0}` |
| `container_of` 得到野指针 | 传入的不是该结构体的成员 | 只在明确的链表/嵌入场景用 |
