## 一、数组名到底是什么

### 1.1 三个看起来一样的地址

```c
int a[5] = {1, 2, 3, 4, 5};

&a        // 数组的地址
a         // 数组首元素的地址
&a[0]     // 首元素的地址
```

实测（本机）：

```
&a    = 0x7fffa7e35310
a     = 0x7fffa7e35310
&a[0] = 0x7fffa7e35310
```

**三个值完全一样**，但类型不同：

| 表达式 | 类型 | `+1` 走多远 |
|:--|:--|:--|
| `&a` | `int (*)[5]` | **20 字节**（整个数组） |
| `a` | `int *`（退化后） | 4 字节 |
| `&a[0]` | `int *` | 4 字节 |

实测验证：

```c
printf("%p\n", (void *)(a + 1));    // 0x...314  ← +4
printf("%p\n", (void *)(&a + 1));   // 0x...324  ← +20
```

**这就是「数组名不是指针」的第一个证据**：`&a` 和 `a` 打印出来一样，但做算术时步长差 5 倍。

### 1.2 数组名的两个例外

数组名在**大多数表达式**里会退化成「指向首元素的指针」，但有两个例外：

```c
int a[5];

sizeof(a);      // 20 —— 不是 8！数组名在这里没退化
sizeof(&a);     // 8  —— 这是指针的大小

// 第二个例外：& 取地址
int (*p)[5] = &a;   // 合法，类型是「指向 5 个 int 的数组的指针」
```

⚠️ 注意 `sizeof(&a)` = **8**（64 位环境）。`&a` 是**指针**，不是数组。这个区别在 `memcpy` 里会致命：

```c
memcpy(dst, &a, sizeof(a));    // ✅ 20 字节
memcpy(dst, &a, sizeof(&a));   // ❌ 只拷 8 字节
```

### 1.3 数组名不能被赋值

```c
int a[5], b[5];
a = b;        // ❌ 编译错误：数组名不是左值
a++;          // ❌ 编译错误
```

数组名不是变量，它是「编译器给这块内存起的名字」。一旦定义，地址就固定了。想「复制数组」只能用 `memcpy` 或循环。

## 二、`sizeof` 的三种命运

同一个 `sizeof`，在三个位置给出三个答案。这是 C 里最常见的静默 bug。

```c
int a[5] = {1,2,3,4,5};

// ① 定义所在的作用域：数组就是数组
sizeof(a);                        // 20

// ② 作为形参：已退化成指针
void f(int arr[5]) {              // 注意：写 5 也没用，编译器直接忽略
    sizeof(arr);                   // 8（64 位）—— 不是 20，也不是 20/4
}

// ③ 指向数组的指针：解引用后是数组
int (*p)[5] = &a;
sizeof(*p);                       // 20  ← 这个能拿到真实大小
sizeof(p);                        // 8   ← 指针本身
```

实测全部吻合：

```
sizeof a=20  p(指针)=8  pa(数组指针)=8  ap(指针数组)=40
```

### 2.1 `void f(int arr[5])` 里的 5 是个谎

```c
void f(int arr[5]) {
    printf("%zu\n", sizeof(arr));   // 8
    arr[7] = 1;                     // 编译器不拦，运行时越界
}
```

**方括号里的数字对编译器毫无约束力**，它只是给人看的注释。想真正约束，用 C99 的 `static` 数组语法：

```c
void f(int arr[static 5]);   // 告诉编译器：调用时至少给 5 个元素
                             // 传更短的数组 = 编译告警（不是强制错误）
```

⚠️ 这个语法用的人不多，但在 `-Warray-bounds` 和 LTO 下能抓住一些越界调用。资源受限环境更常见的做法是**长度显式传参**。

### 2.2 真实工程的写法

```c
void bad(uint8_t buf[]) {
    memset(buf, 0, sizeof(buf));        // ❌ 只清 8 字节
}

void good(uint8_t *buf, size_t len) {
    memset(buf, 0, len);                // ✅ 长度由调用方决定
}
```

`multi_cyc_fifo.c` 里所有对外 API 都是 `(buf, len)` 成对出现：

```c
void WriteDataInFifo(tId i_xFifoId,
                     unsigned char *i_pucWriteDataBuf,
                     tLen i_xWriteDatalen,      // ← 长度必须显式
                     tErroCode *o_peWriteStatus);
```

**这条规则值得写进团队规范**：任何接受数组的函数，签名里必须有 `len`，且 `len` 的类型和数组元素类型分开（不要用 `sizeof` 推）。

## 三、二维数组的真实布局

### 3.1 二维数组不是「指针的指针」

```c
int m[3][4];
```

内存里是**一块连续的 12 个 int**（48 字节），只是编译器帮你按行切开：

```
m[0][0] m[0][1] m[0][2] m[0][3] | m[1][0] ... | m[2][3]
 ←────── 第 0 行 16 字节 ──────→
```

实测：

```
sizeof m   = 48     ← 整块
sizeof m[0] = 16    ← 一行
(m+1) - m       = 16   ← m 的类型是 int(*)[4]
(m[0]+1) - m[0] = 4    ← m[0] 的类型是 int*
&pm[1][2] offset = 24  ← 1*16 + 2*4
```

### 3.2 `m` 的类型是「指向 4 个 int 的数组」的指针

```c
int m[3][4];
// m 的类型：int (*)[4]   ← 不是 int **！
```

这就是为什么下面这种写法编译警告或直接错：

```c
int **p = m;         // ❌ 类型不兼容（有些编译器只给 warning）
int (*p)[4] = m;     // ✅ 正确
p[1][2] = 5;         // 等价于 m[1][2]
```

### 3.3 用指针遍历二维数组

```c
int m[3][4];

// 方式一：行指针（最自然）
for (int (*row)[4] = m; row < m + 3; row++) {
    for (int *p = *row; p < *row + 4; p++) {
        printf("%d ", *p);
    }
}

// 方式二：当成一维铺平（只有连续存储时才成立）
int *flat = &m[0][0];
for (int i = 0; i < 3 * 4; i++) {
    printf("%d ", flat[i]);
}
```

⚠️ **方式二依赖「数组连续存储」这一 C 标准保证**（多维数组确实是连续的），但**不能用在「动态分配的指针数组」上**：

```c
int **rows = malloc(3 * sizeof(int *));
for (int i = 0; i < 3; i++) rows[i] = malloc(4 * sizeof(int));
// 此时 rows[0] 和 rows[1] 之间没有任何保证，不能铺平访问
```

## 四、数组指针 vs 指针数组

两个名字只差一个字，含义完全反。

### 4.1 读法：从内向外，从右向左

```c
int (*p)[5];    // p 是 指针，指向「5 个 int 的数组」
int *p[5];      // p 是 数组，5 个元素，每个是 int *
```

**技巧**：先看括号内的 `*p`，再看外面。

| 写法 | 名字 | `sizeof`（64位） | 用途 |
|:--|:--|:--|:--|
| `int (*p)[5]` | 数组指针 | 8 | 指向二维数组的「一行」 |
| `int *p[5]` | 指针数组 | 40 | 5 个独立指针，常用来存字符串 |
| `int p[5]` | 数组 | 20 | 普通数组 |

实测 `sizeof ap=40`（`int *ap[5]`），正是 5 × 8。

### 4.2 指针数组的典型用法

```c
// 字符串表 —— 系统编程里极常见
static const char *const g_error_msg[] = {
    "OK",
    "Timeout",
    "CRC error",
    "Buffer full",
};
// 4 个指针 = 32 字节（64位）/ 16 字节（32位 MCU），
// 字符串本体在 .rodata，不占 RAM
```

注意 `const char *const` 两个 `const`：

- 第一个：**指向的内容**不可改（`g_error_msg[0][0] = 'x'` 报错）
- 第二个：**指针本身**不可改（`g_error_msg[0] = "other"` 报错）

少写第二个 `const`，整个数组会从 `.rodata` 掉进 `.data`，**多占 RAM**。这一点在第 8 节展开。

### 4.3 函数指针数组（状态机/命令表）

```c
typedef void (*cmd_fn)(void);

static const cmd_fn g_cmd_table[] = {
    cmd_reset, cmd_start, cmd_stop, cmd_query,
};

// 派发
if (idx < sizeof(g_cmd_table) / sizeof(g_cmd_table[0])) {
    g_cmd_table[idx]();
}
```

这里 `sizeof(g_cmd_table) / sizeof(g_cmd_table[0])` 是**唯一安全的求长度写法** —— 因为 `g_cmd_table` 在定义作用域内，没退化。

**封装成宏**：

```c
#define ARRAY_LEN(a) (sizeof(a) / sizeof((a)[0]))
```

⚠️ 这个宏**只能用在真正的数组上**。传给指针会得到垃圾值（指针大小/元素大小）。防御写法：

```c
// GCC/Clang 扩展：编译期断言，传指针直接报错
#define ARRAY_LEN(a) \
    (sizeof(a) / sizeof((a)[0]) + \
     0 * sizeof(char[1 - 2 * __builtin_types_compatible_p(typeof(a), typeof(&(a)[0]))]))
```

## 五、`const` 与指针的三种组合

### 5.1 三种写法，三种含义

```c
const int *p;        // ① 指向常量的指针：*p 不能改，p 可以改
int *const p = &x;   // ② 常量指针：p 不能改，*p 可以改
const int *const p = &x;  // ③ 都不能改
```

**读法技巧**：`const` 在 `*` **左边** → 修饰指向的内容；`const` 在 `*` **右边** → 修饰指针本身。

```c
const int *p;      // const 在 * 左边 → *p 只读
int const *p;      // 同上（const 和 int 顺序无关）

int *const p;      // const 在 * 右边 → p 只读
```

### 5.2 常见用途

```c
// ① 函数参数：承诺不改调用方的数据
size_t my_strlen(const char *s);

// ② 返回值：指向只读区
const char *get_version(void);

// ③ 查表：表和指针都只读，全进 Flash
static const uint16_t *const g_lut = ...;
```

### 5.3 一个真实的坑：`const` 数组传给非 `const` 形参

```c
void process(uint8_t *buf, size_t len);   // 形参没有 const

const uint8_t table[16] = {...};
process(table, 16);      // ⚠️ 编译器警告：丢弃 const 限定符
                         // 强转能过，但函数如果真写了就是 UB
```

**正确做法**：函数不改数据就加 `const`。这不是「洁癖」，是让它能接受 `const` 数据源（Flash 里的表、字符串字面量）。

## 六、字符串、字符数组、字符指针

### 6.1 三种写法的内存归属

```c
char *s1 = "hello";          // ① 指针指向 .rodata，只读，写它 = UB
char s2[] = "hello";         // ② 栈上（或 .data）6 字节副本，可写
const char *s3 = "hello";    // ③ 同 ①，但「明确声明只读」
```

| 写法 | 存哪 | 可写 | `sizeof` |
|:--|:--|:--|:--|
| `char *s1 = "hello"` | 指针在栈/.data，内容在 `.rodata` | ❌ | 8（指针） |
| `char s2[] = "hello"` | 数组本体在栈（局部）或 .data（全局） | ✅ | 6 |
| `const char *s3` | 同 s1 | ❌ | 8 |

```c
s1[0] = 'H';    // ❌ 段错误 / HardFault —— 改的是 .rodata
s2[0] = 'H';    // ✅
```

⚠️ **`char *s1 = "hello"` 在 C 里合法但危险**，C++ 里直接编译错误。现代实践一律写 `const char *`。

### 6.2 `sizeof` vs `strlen`

```c
char s2[] = "hello";
sizeof(s2);    // 6  ← 含结尾 '\0'
strlen(s2);    // 5  ← 不含

char *s1 = "hello";
sizeof(s1);    // 8  ← 指针大小，不是 6！
strlen(s1);    // 5
```

**`sizeof` 是编译期算子，`strlen` 是运行期函数。** 一个数内存，一个数字符。

### 6.3 字符串在资源受限环境的用法

```c
// 固件版本号：全进 .rodata，不占 RAM
static const char FW_VERSION[] = "1.2.3";

// 运行时拼字符串：必须有固定缓冲区
char buf[32];
snprintf(buf, sizeof(buf), "v%s-%lu", FW_VERSION, (unsigned long)build_id);
```

⚠️ **不要用 `sprintf`**，它不知道缓冲区多大。`snprintf` 至少会截断而不是溢出。但 `snprintf` 的返回值是「**本应写入的长度**」，不是实际写入的：

```c
int n = snprintf(buf, 4, "hello");   // n = 5，但 buf 里只有 "hel"
if (n >= (int)sizeof(buf)) {
    // 被截断了
}
```

## 七、传参：长度为什么必须单独传

### 7.1 C 没有「数组引用」这个概念

C 没有「数组引用」这种自带长度的类型；C 传数组时**只剩一个地址**，长度信息在退化那一刻就丢了。

```c
void f(int a[10]);    // 编译器看到的：void f(int *a)
void g(int a[]);      // 同上
void h(int *a);       // 同上 —— 三种写法完全等价
```

用 `nm` 或 `objdump` 看符号，三者生成的符号一模一样。

### 7.2 三种传长度的方法

```c
// ① 显式长度（最常用）
void f1(const uint8_t *buf, size_t len);

// ② 结束标记（类似 C 字符串）
void f2(const char *s);            // 靠 '\0' 判断
void f3(const uint8_t *buf, uint8_t end_marker);  // 自定义结束符

// ③ 带长度字段的结构体（协议报文常用）
typedef struct {
    uint16_t len;
    uint8_t  data[];    // 柔性数组，见 03 文档
} msg_t;
void f4(const msg_t *m);
```

**推荐 ① 和 ③**：结束标记法（②）遇到数据里正好有结束符就提前截断，必须转义，得不偿失。

### 7.3 真实工程：一次传参的完整链路

```c
// 最底层：HAL 收发
bool uart_read(uint8_t *buf, uint16_t max_len, uint16_t *actual_len);

// 中间层：环形缓冲
bool rb_get(ringbuf_t *rb, uint8_t *byte);

// 上层：协议解析
void parser_feed(parser_t *p, uint8_t byte, uint32_t now_ms);
```

每一层都**自己声明能接受多少**，不依赖上一层猜。这是系统编程的通行做法。

## 八、系统编程里的数组

### 8.1 Flash 查表：`const` 决定它占哪块内存

```c
// ✅ 全进 Flash（.rodata），不占 RAM
static const uint16_t g_crc16_tab[256] = { ... };   // 512 字节

// ❌ 少了 const → 进 .data，启动时从 Flash 拷到 RAM
static uint16_t g_crc16_tab[256] = { ... };         // 512 字节 RAM 没了
```

一个 512 字节的表，在只有 20 KB RAM 的 MCU 上是 2.5%。**256 项的 uint32 表（CRC32）就是 1 KB**。

**检查方法**：

```bash
nm --size-sort -S firmware.elf | tail -10
```

如果 `g_crc32_tab` 出现在这里，说明它进了 RAM（`.data` 或 `.bss`）。应该只有 `.rodata` 里才对 —— 而 `.rodata` 的符号 `nm` 也会列出来，所以更准确的是看段：

```bash
readelf -s firmware.elf | grep g_crc32_tab
# 输出里 Ndx 列 = 段索引，对照 readelf -S 看是 .rodata 还是 .data
```

### 8.2 对齐：DMA 和硬件外设的硬要求

```c
// DMA 缓冲区必须按 4 字节对齐（有些外设要求 32 字节甚至缓存行对齐）
static uint8_t dma_buf[512] __attribute__((aligned(32)));
```

为什么：DMA 控制器按字/块搬运，起始地址不对齐会导致搬运错位，或者某些架构直接报总线错误。

### 8.3 数组越界在资源受限环境的表现

```c
uint8_t buf[8];
buf[8] = 0;    // 越界（合法下标是 0..7）
```

后果取决于 `buf` 后面是什么：

- 后面是另一个全局变量 → **静默改写它**，找 bug 找一天
- 后面是栈上的返回地址 → 函数返回时跳到野地址
- 后面是 `.bss` 边界外的非法地址 → HardFault

**没有下标检查**是 C 的固有特性。防御手段只有三个：

1. 所有数组访问都过 `if (i < len)` 检查
2. 编译期用 `-Warray-bounds`、`-fsanitize=bounds`（主机侧测试时）
3. 关键缓冲区前后放哨兵值，定期检查

```c
// 哨兵法
static uint32_t g_guard_before = 0xDEADBEEF;
static uint8_t  g_buf[256];
static uint32_t g_guard_after  = 0xCAFEBABE;

void check_guard(void) {
    if (g_guard_before != 0xDEADBEEF || g_guard_after != 0xCAFEBABE) {
        // 有越界写
    }
}
```

## 九、错误清单

| 症状 | 原因 | 修法 |
|:--|:--|:--|
| `sizeof` 在函数里变小了 | 数组形参退化成指针 | 长度显式传参 |
| `memcpy` 只拷了一半 | 用了 `sizeof(&a)` 而不是 `sizeof(a)` | 检查有没有多余的 `&` |
| `int **p = m`（二维数组） | 类型不匹配 | `int (*p)[4] = m` |
| 写字符串字面量崩了 | `char *s = "..."` 后写它 | 用 `char s[]` 或加 `const` |
| 查表占了大量 RAM | 忘了 `const` | `static const ...` |
| `ARRAY_LEN` 算出垃圾 | 传了指针不是数组 | 只在定义作用域用，或加编译期断言 |
| `sprintf` 溢出 | 不知道目标缓冲区大小 | 换 `snprintf` + 检查返回值 |
| 循环少跑一次 | `for (i=0; i<=len; i++)` | 用 `i < len`，把长度语义写进变量名 |
| 二维数组遍历顺序反了 | `m[i][j]` 写成 `m[j][i]` | 内层循环用最后一维（缓存友好） |
