## 一、认知转换：语法之外的那一层

| 高层语言的直觉 | C 的真相 | 你在哪里会撞上 |
|:--|:--|:--|
| 变量是名字，绑定到对象 | 变量是**一块有地址的内存**，类型决定这块内存怎么解释 | 修改 `memcpy` 后的 `struct` |
| 对象自动管理内存 | 内存位置由**链接脚本**决定，谁清零、谁搬运由**启动代码**决定 | 全局变量没初始化却是脏值 |
| 整数是任意精度 | `int` 是固定宽度，溢出是**未定义行为**，不是回绕 | `-Wconversion` 一堆告警 |
| 异常会往上抛 | 出错只能**返回错误码**，或者直接触发硬件异常 | 指针空解引用 → 系统复位 |
| 代码跑在解释器里 | 代码跑在**你配的时钟频率**上，中断随时打断你 | ISR 里改的变量被优化器删掉 |

一句话：**高层语言让你只管逻辑，C 让你管逻辑 + 管它落在哪块内存、由谁在什么时候动它。**

## 二、类型与内存布局

### 2.1 位宽不是「大概」

C 标准只保证 `char ≤ short ≤ int ≤ long`，**不保证具体位宽**。跨平台代码必须按真实宽度写：

```c
#include <stdint.h>

uint8_t  a;   // 永远是 8 位
uint16_t b;   // 永远是 16 位
uint32_t c;   // 永远是 32 位
int32_t  d;   // 有符号 32 位

// 不要这样写跨平台的协议结构体
unsigned long len;   // 32 位 MCU 上是 4 字节，64 位 PC 上是 8 字节
```

一个真实的坑：`int` 在 32 位平台上是 4 字节，在部分 16 位平台上是 2 字节。协议字段、CRC 中间量、长度变量，**一律用 `stdint.h`**。

### 2.2 结构体大小 ≠ 成员大小之和

对齐规则：**每个成员的偏移必须是它自身对齐值的整数倍**；结构体的总大小必须是**最大成员对齐值**的整数倍。

```c
struct bad {
    uint8_t  a;   // offset 0
    uint32_t b;   // offset 4  ← 中间塞了 3 字节填充
    uint8_t  c;   // offset 8
};                // sizeof = 12（末尾再补 3 字节，凑到 4 的倍数）
```

把这个 `struct` 直接 `memcpy` 到协议报文里，你会多发 3 个字节的垃圾。两种处理：

```c
// 方案 A：重排成员，大对齐的放前面（省内存，但字段顺序变了）
struct good {
    uint32_t b;
    uint8_t  a;
    uint8_t  c;
};                // sizeof = 8

// 方案 B：显式指定紧凑布局（协议报文必须用这个）
#pragma pack(push, 1)
struct wire {
    uint8_t  a;
    uint32_t b;
    uint8_t  c;
};                // sizeof = 6
#pragma pack(pop)
```

⚠️ `#pragma pack(1)` 的代价：**未对齐访问**。有些处理器访问 `wire.b` 会直接触发硬件异常；另一些支持非对齐访问但要走两条总线、性能打折。所以紧凑结构体只用于**收发缓冲区**，解出来后立刻拷贝到对齐的正常结构体里用。

### 2.3 位域：能不用就不用

```c
struct flags {
    uint8_t enable  : 1;
    uint8_t mode    : 3;
    uint8_t rsvd    : 4;
};
```

位域的问题：
- **布局由编译器决定**（先放低位还是高位、跨不跨存储单元，标准没规定）
- 不能取地址（`&s.mode` 编译不过）
- 读写是「读-改-写」，**非原子**

用寄存器和协议报文时，老老实实写 `x & 0x07` / `x |= BIT(3)`，比位域可靠。实际项目的寄存器定义几乎清一色用位掩码宏，很少用位域。

### 2.4 端序：只在跨设备时才痛

x86 和 ARM 默认都是**小端**（低字节在低地址）。但 CAN / UDS 这类协议的多字节字段是**大端**。所以代码里到处是这种手工拼接：

```c
// ISO-TP 首帧：高 4 位是类型，低 12 位是长度（大端）
frameLen = (uint32)((msg[0] & 0x0F) << 8) | msg[1];
```

这类手工拼接在协议实现里几乎无处不在。写错一个 `<< 8` 就是长度差 256 倍。

**自查方法**：定义一对宏，别到处手写位移。

```c
#define BE16(p)  ((uint16_t)(((uint16_t)((const uint8_t *)(p))[0] << 8) | \
                             ((const uint8_t *)(p))[1]))
#define BE32(p)  (((uint32_t)BE16(p) << 16) | BE16((const uint8_t *)(p) + 2))
```

## 三、内存段与启动代码

### 3.1 五个段，各自谁负责

| 段 | 内容 | 存在 Flash 还是 RAM | 谁初始化 |
|:--|:--|:--|:--|
| `.text` | 代码、字符串常量 | Flash | 不需要 |
| `.rodata` | `const` 全局、查表 | Flash | 不需要 |
| `.data` | **有初值**的全局/静态变量 | Flash 里有初值副本，运行时在 RAM | **启动代码 memcpy** |
| `.bss` | **无初值**或初值为 0 的全局/静态变量 | 只在 RAM | **启动代码 memset 0** |
| stack / heap | 局部变量 / `malloc` | RAM | 栈指针由硬件或启动代码设 |

这就是「全局变量默认是 0」的来源 —— 不是编译器保证的，是**启动代码把 `.bss` 整段清成 0**。

### 3.2 一个「不用搬 `.data`」的反例

下面是一个无操作系统环境的链接脚本（`.data` 和 `.rodata` 都直接落在 RAM 区）：

```ld
MEMORY {
  CODE : ORIGIN = 0x40000000, LENGTH = 32K
  DATA : ORIGIN = 0x3FC80000, LENGTH = 128K
}

SECTIONS {
  .text : { *(.text) *(.text*) } > CODE

  .data : {
    _sdata = .;
    *(.data) *(.data*) *(.rodata) *(.rodata*)
    _edata = .;
  } > DATA          /* 注意：.rodata 也被放进 DATA（RAM） */

  .bss (NOLOAD) : {
    _sbss = .;
    *(.bss) *(.bss*) *(COMMON)
    _ebss = .;
  } > DATA
}
```

启动代码只做了两件事：

```c
void Reset_Handler(void) {
  s_heap_start = s_brk = &_end, s_heap_end = &_eram;
  for (char *p = &_sbss; p < &_ebss;) *p++ = '\0';   // 只清 .bss
  // 没有 .data 搬运！
  clock_init();          // 配时钟
  timer_init();          // 系统节拍
  interrupts_enable();   // 开全局中断
  main();
}
```

**为什么可以不搬？** 因为镜像生成工具产出的固件自带分段信息，片内 ROM 的引导程序会按段把内容直接写到目标地址 —— 相当于 ROM 帮你做了搬运。这是「谁搬 `.data`」的另一种答案：**不一定是你自己的启动代码**。

对比另一种常见做法：镜像里只存一份 `.data` 初值，运行时由 `Reset_Handler` 用 `memcpy` 从 Flash 搬到 RAM。**同一个概念，两种落地方式，取决于芯片的引导流程。**

### 3.3 把变量钉在特定内存上

有些芯片有不止一块 RAM，能力并不对等。例如某些 Cortex-M4 芯片除主 SRAM 外还有一块约 64 KB 的 CCM：`0x20000000` 的主 SRAM 是 CPU 和 DMA 都能用的，`0x10000000` 的 CCM **只有 CPU 能访问，DMA 不可达**。

链接脚本里分两行声明：

```ld
MEMORY {
  RAM    (xrw) : ORIGIN = 0x20000000, LENGTH = 128K
  CCMRAM (rw)  : ORIGIN = 0x10000000, LENGTH = 64K
}
```

想手动把某个变量放进 CCM，用段属性：

```c
// 方式一：__attribute__
static uint8_t big_buffer[32 * 1024] __attribute__((section(".ccmram")));

// 方式二：链接脚本里定义专门的段
// .ccmram (NOLOAD) : { *(.ccmram) *(.ccmram*) } > CCMRAM
```

⚠️ **踩坑提醒**：把缓冲区放进 CCM 再用 DMA 搬运，DMA 会读到全 0 或者直接报总线错误 —— 因为 DMA 控制器根本看不到 `0x10000000` 这块地址。这是「地址空间不通」而不是「代码写错」，从代码上完全看不出来。

### 3.4 栈溢出怎么发现

资源受限环境下栈通常只有 1~4 KB。递归、大局部数组、`printf` 的浮点格式化，都能吃掉几百字节。

三种手段：

```c
// 1. 启动时用魔数填满整个栈区
#define STACK_PATTERN 0xDEADBEEFu
extern uint32_t _sstack, _estack;
void stack_paint(void) {
    for (uint32_t *p = &_sstack; p < &_estack; p++) *p = STACK_PATTERN;
}
// 之后检查「还有多少 0xDEADBEEF」= 还有多少没用过

// 2. 栈末尾放一个哨兵，被改写就说明溢出
// 3. 用 MPU 把栈底下一块设成不可访问，溢出立刻 MemManage Fault
```

## 四、指针与函数指针

### 4.1 指针就是「一个装地址的整数」

```c
uint32_t x = 0x11223344;
uint32_t *p = &x;      // p 的值是 x 的地址
*p = 0x55667788;       // 往那个地址写

// 指针自己的类型决定「读几个字节、怎么解释」
uint8_t *bp = (uint8_t *)&x;
// 小端机器上 bp[0] == 0x88, bp[3] == 0x55
```

关键认知：**指针的值是一个数，指针的类型决定解引用时干几件事**。这解释了为什么 `(uint8_t *)&x` 能按字节访问一个 32 位变量。

### 4.2 数组名会退化成指针，但不是指针

```c
uint8_t buf[16];
sizeof(buf);       // 16  ← 在定义所在的作用域里，数组就是数组
void f(uint8_t b[]) {
    sizeof(b);     // 4 或 8  ← 形参里 b 已经退化成指针
}
```

**这是最常见的 bug 来源**：

```c
void bad(uint8_t buf[]) {
    memset(buf, 0, sizeof(buf));   // ❌ 只清了 4 字节
}
void good(uint8_t *buf, size_t len) {
    memset(buf, 0, len);           // ✅ 长度必须显式传
}
```

真实工程里 `multi_cyc_fifo.c` 的所有 API 都是 `(buf, len)` 成对出现，从不依赖 `sizeof`。

### 4.3 函数指针：C 里唯一的多态

```c
// 定义类型
typedef void (*irq_fn_t)(void *arg);

// 结构体里存回调
struct irq_data {
    void (*fn)(void *);    // 用户处理函数
    void *arg;             // 传给它的参数
    void (*clr)(void *);   // 清中断标志
    void *clr_arg;
};

// 注册
g_irq_data[no].fn  = (void (*)(void *)) SysTick_Handler;
g_irq_data[no].clr = systimer_clear_interrupt;

// 中断里统一分发 —— 32 个中断源共用一段代码
if (d->clr) d->clr(d->clr_arg);
if (d->fn)  d->fn(d->arg);
```

一个真实细节：`SysTick_Handler` 的原型是 `void SysTick_Handler(void)`，但 `fn` 期望 `void (*)(void *)`。**C 允许这种强制转换，但调用时传参是未定义行为**（在 ARM 上多余参数放寄存器里，被调用者不读就没事；换成别的 ABI 就可能崩）。

这也是为什么中断表用统一签名 + 参数结构体，比给每个中断写一个 handler 好维护。

### 4.4 `void *`：唯一能装任何指针的类型

```c
void *p = &x;              // 任何指针都能隐式转成 void *
uint32_t *q = p;           // C 里 void* 能隐式转回去（C++ 不行）
```

`memcpy` / `memset` / `qsort` 的签名都用 `void *`，就是为了通用。代价是**丢了类型信息**，编译器不再帮你检查。

### 4.5 指针算术按「元素大小」走

```c
uint32_t arr[4];
uint32_t *p = arr;
p + 1;              // 地址 +4，不是 +1
(uint8_t *)p + 1;   // 地址 +1
```

这就是为什么 `for (char *p = &_sbss; p < &_ebss;) *p++ = '\0';` 能正确逐字节清零 —— `p` 是 `char *`，每次 +1 就是 +1 字节。

## 五、`const` / `static` / `extern`

三个词分别管**不同的期**，别混。

### 5.1 `const`：只读承诺，不是常量

```c
const uint32_t SIZE = 100;
// SIZE 不是编译期常量！在 C 里它仍是一个「只读变量」，
// 不能用作数组维度、不能用在 case 标签里

uint8_t buf[SIZE];        // ❌ C90/C99 编译不过（C11 的 VLA 另说）
// 正确做法：
#define SIZE 100
enum { SIZE = 100 };
```

`const` 真正的作用是**放进 `.rodata` 段**（Flash 里，不占 RAM），以及给编译器优化提示。

```c
// 这两个差别很大
char *p1 = "hello";              // 指向只读区，写它 = 未定义行为
const char *p2 = "hello";        // 明确告诉编译器：不许通过 p2 写
char buf[] = "hello";            // 拷贝到栈上，可写
```

### 5.2 `static`：三个不同的意思

```c
// ① 修饰全局变量/函数 → 链接属性变成「内部」，别的 .c 文件看不到
static uint8_t gs_ucFifo[800];       // 只有本文件可见
static void AddInList(...);          // 只有本文件可调用

// ② 修饰局部变量 → 生命周期变成整个程序，值跨调用保留
static uint64_t timer = 0;           // 只初始化一次，下次进来还是上次的值
void led_task(void) {
    if (timer_expired(&timer, 500, s_ticks)) { ... }
}

// ③ 修饰函数参数 → 无意义（别写）
```

`static` 局部变量在无操作系统环境里极其常见：**它就是「模块私有状态」的载体，不用 malloc**。

⚠️ 注意：`static` 局部变量在 `.bss`（无初值）或 `.data`（有初值）里，不在栈上。所以它**不是线程/中断安全的** —— 多个中断源调用同一个带 `static` 局部变量的函数会打架。

### 5.3 `extern`：声明，不定义

```c
// startup.c
extern char _sbss, _ebss;      // 这两个符号在链接脚本里定义
for (char *p = &_sbss; p < &_ebss;) *p++ = '\0';
```

```ld
/* link.ld 里 */
_sbss = .;
```

`extern` 告诉编译器「这个东西在别处定义，先按这个类型用，链接时去找」。链接器找不到就报 `undefined reference`。

**`extern` 修饰数组时要注意**：`extern char _sbss` 声明的是一个 `char`，取地址 `&_sbss` 才拿到符号地址。如果写成 `extern char _sbss[]`，`sizeof` 就不对了。

## 六、`volatile` 的作用与边界

### 6.1 它到底让编译器不做什么

编译器会做「把变量缓存在寄存器里」这种优化。对普通变量这是对的（没人能从外部改它）。但有两种情况编译器判断错了：

1. **中断服务程序（ISR）会改它**
2. **它是硬件寄存器**（读一下就有副作用，比如读走 RX FIFO）

```c
// 没有 volatile：编译器可能把 s_ticks 缓存在寄存器里，
// while (!s_ticks) {} 变成死循环
uint64_t s_ticks;

// 有 volatile：每次循环都从内存重新读
static volatile uint64_t s_ticks;
void SysTick_Handler(void) { s_ticks++; }
```

`volatile` 的准确语义是：**每次访问都必须真正发生一次（不能不访问、不能合并、不能重排到别的 volatile 访问之间）**。

### 6.2 它不保证什么（这是最常被误解的）

```c
volatile uint32_t counter;

// ❌ 这不是原子操作！是「读、加、写」三条指令
counter++;

// 中断里也可能执行 counter++，主循环和中断可能交错：
// 主循环读 counter=5 → 中断读 counter=5 → 中断写 6 → 主循环写 6
// 结果少加一次
```

**`volatile` ≠ 原子性，`volatile` ≠ 内存屏障。**

### 6.3 复合数据要进临界区

```c
// 32 位及以下的读写通常是单指令，天然原子（要确认架构）
// 但下面这些都不是原子的：
//   - uint64_t 的读写在 32 位 MCU 上是两条指令
//   - 结构体的读改写
//   - 多个变量的「一致性」组合

// 正确做法：进临界区
uint64_t now;
__disable_irq();          // 或者 __get_PRIMASK / __set_PRIMASK
now = s_ticks;
__enable_irq();
```

### 6.4 临界区必须能嵌套（保存-恢复，而不是盲开盲关）

```c
// ❌ 错的：内层 enable 会把外层的保护提前解开
void inner(void) { __disable_irq(); ...; __enable_irq(); }
void outer(void) { __disable_irq(); inner(); ...; }  // outer 后面的代码失去保护

// ✅ 对的：保存进来时的状态，出去时恢复
static inline uint32_t critical_enter(void) {
    uint32_t primask = __get_PRIMASK();
    __disable_irq();
    return primask;      // 返回进入前的状态
}
static inline void critical_exit(uint32_t primask) {
    __set_PRIMASK(primask);   // 原来开着就开，原来关着就保持关
}

void outer(void) {
    uint32_t s = critical_enter();
    inner();                  // inner 里再 enter/exit 也不会破坏外层
    critical_exit(s);
}
```

### 6.5 编译屏障 vs 内存屏障

```c
// 编译屏障：只阻止编译器重排，不产生任何指令
asm volatile("" ::: "memory");

// 内存屏障：产生真实指令，阻止 CPU 乱序
__DMB();   // Data Memory Barrier（ARM 架构）
__DSB();   // Data Synchronization Barrier
__ISB();   // Instruction Synchronization Barrier

// 其他架构有对应指令，例如 RISC-V
asm volatile("fence" ::: "memory");
```

**场景区分**：单核 MCU 上，中断不会真正「并发执行」，需要的多半是编译屏障 + `volatile`。多核或者 DMA 场景才需要真内存屏障。

## 七、整数提升与未定义行为

### 7.1 你写的拼接可能悄悄错了

```c
uint8_t hi = 0x12, lo = 0x34;

// ❌ 危险：uint8_t 会先被提升成 int（有符号），
//    如果 hi 的高位是 1（如 0x80），<< 8 会得到 0x8000，
//    但如果是 0xFF << 8 = 0xFF00，赋给 uint16_t 还好
//    真正危险的是 << 16 或 << 24，会溢出到符号位 → 未定义行为
uint32_t v = (hi << 24) | (lo << 16) | ...;

// ✅ 先转成目标宽度再移位
uint32_t v = ((uint32_t)hi << 24) | ((uint32_t)lo << 16) | ...;
```

真实工程里的写法（CAN TP 收数据长度）：

```c
*(pxDataLen) = ((uint16)(pucRxData[0] & 0x0fu) << 8u) | (uint16)pucRxData[1u];
```

**每一步都显式 `(uint16)` 转换**，就是为了避开整型提升。看着啰嗦，但这是 MISRA 规范要求的。

### 7.2 有符号 vs 无符号，谁赢

```c
int      a = -1;
unsigned b = 1;

a < b;    // ❌ true 还是 false？—— 结果是 false
// 因为 a 被转换成 unsigned，-1 变成 0xFFFFFFFF，比 1 大
```

**规则**：有符号和无符号混合运算时，有符号转成无符号。所以：

```c
// 经典 bug
for (unsigned i = n - 1; i >= 0; i--) { ... }   // 死循环，i 永远 >= 0

// 正确
for (int i = (int)n - 1; i >= 0; i--) { ... }
// 或者
for (unsigned i = n; i-- > 0; ) { ... }
```

### 7.3 未定义行为不是「结果不确定」，是「编译器可以做任何事」

```c
int x = INT_MAX;
x + 1;              // UB，编译器可以假设这不会发生，把整个分支优化掉

uint8_t buf[4];
buf[5] = 0;         // UB

int *p = NULL;
*p = 1;             // UB（在 MCU 上通常就是 HardFault）

// 最阴险的：
int f(int x) { return x + 1 > x; }   // 编译器可以优化成 return 1
                                      // 因为「假设 x+1 不会溢出」
```

所以工具链里 `-Wconversion`、`-Wsign-compare` 这些不是啰嗦，是**帮你提前发现 UB**。下面是一份真实项目的告警配置，直接把告警当错误：

```makefile
CFLAGS ?= -W -Wall -Wextra -Werror -Wundef -Wshadow \
          -Wdouble-promotion -fno-common -Wconversion
```

`-Wconversion` 会揪出所有隐式窄化转换 —— 一开始会觉得噪音大，写多了就习惯显式转换了。

## 八、位运算与寄存器访问

### 8.1 三种基本操作

```c
#define BIT(n)  (1UL << (n))

x |=  BIT(3);      // 置位
x &= ~BIT(3);      // 清位
x ^=  BIT(3);      // 翻转
if (x & BIT(3))    // 测位
```

### 8.2 用结构体映射寄存器（真实工程的做法）

```c
struct systimer {  // 按 TRM 第 10.6 节的手册顺序排
    volatile uint32_t CONF, UNIT0_OP, UNIT1_OP, UNIT0_LOAD_HI, UNIT0_LOAD_LO,
        UNIT1_LOAD_HI, UNIT1_LOAD_LO, TARGET0_HI, TARGET0_LO,
        TARGET1_HI, TARGET1_LO, TARGET2_HI, TARGET2_LO,
        TARGET0_CONF, TARGET1_CONF, TARGET2_CONF,
        UNIT0_VALUE_HI, UNIT0_VALUE_LO, UNIT1_VALUE_HI, UNIT1_VALUE_LO,
        COMP0_LOAD, COMP1_LOAD, COMP2_LOAD, UNIT0_LOAD, UNIT1_LOAD,
        INT_ENA, INT_RAW, INT_CLR, INT_ST, RESERVED0[34], DATE;
};
#define SYSTIMER ((struct systimer *) 0x6000F000)

SYSTIMER->INT_ENA |= 7U;
```

**为什么必须 `volatile`**：这些地址背后是硬件，不是内存。不加 `volatile`，编译器可能把两次读合并成一次，或者把「读-改-写」优化掉。

**为什么顺序必须和手册一致**：结构体布局是编译器按偏移排的。少写一个保留字段、多写一个，后面所有寄存器全部错位 —— 而且编译器不会报错，你只会在跑起来时看到「写 A 结果 B 变了」。

真实工程里的做法（用结构体逐字映射寄存器）：

```c
// 有保留字段的地方显式留数组
struct gpio {
    volatile uint32_t BT_SELECT, OUT, OUT_W1TS, OUT_W1TC, RESERVED0[4],
        ENABLE, ENABLE_W1TS, ENABLE_W1TC, RESERVED1[3],
        STRAP, IN, RESERVED2[1], STATUS, STATUS_W1TS, STATUS_W1TC,
        RESERVED3[3], PCPU_INT, PCPU_NMI_INT,
        STATUS_NEXT, PIN[22], FUNC_IN[128], FUNC_OUT[22], DATE, CLOCK_GATE;
};
```

`RESERVED0[4]` 不是装饰 —— 它是**真实存在的空档**。删掉它，后面所有寄存器偏移全部前移 16 字节。

### 8.3 另一种写法：直接用偏移量

```c
#define REG(x) ((volatile uint32_t *) (x))
REG(C3_RTCCNTL)[42] = 0x50d83aa1;   // 第 42 个 32 位字 = 偏移 0xA8
```

优点是不用关心结构体对齐，缺点是**完全不可读** —— 42 是什么？半年后你自己都不记得。两种写法在真实工程里混用：结构体定义在头文件里，需要时用 `REG()` 偷懒访问。

### 8.4 对齐陷阱

```c
// ❌ 危险：buf 可能不按 4 字节对齐
uint8_t buf[64];
uint32_t *p = (uint32_t *)&buf[1];   // 未对齐指针
*p = 0x12345678;                     // 不支持非对齐访问的芯片上直接触发硬件异常
```

修正：
```c
// ① 保证数组本身对齐
uint32_t buf[16] __attribute__((aligned(4)));

// ② 或者用 memcpy（编译器会展开成正确指令）
uint32_t v;
memcpy(&v, &buf[1], sizeof(v));
```

## 九、禁用 malloc 的静态分配风格

### 9.1 为什么资源受限环境不用 malloc

1. **堆碎片**：长时间运行后会出现「总共还有 5 KB 空闲，但申请不到 100 字节」
2. **不确定性**：`malloc` 耗时取决于当前堆状态，实时性无法保证
3. **失败处理**：`malloc` 返回 NULL 时你几乎没有好的退路
4. **栈/堆相撞**：很多资源受限的工程栈和堆在 RAM 两端对着长，撞上就是随机崩溃，且极难定位

真实工程的做法：**所有内存静态分配，编译期就确定**。

### 9.2 静态内存池

```c
#define POOL_BLOCK_SIZE  64
#define POOL_BLOCK_NUM   16

typedef struct {
    uint8_t data[POOL_BLOCK_SIZE];
    bool    used;
} block_t;

static block_t g_pool[POOL_BLOCK_NUM];   // .bss 里，编译期就有
static uint32_t g_pool_used;

void *pool_alloc(void) {
    for (int i = 0; i < POOL_BLOCK_NUM; i++) {
        if (!g_pool[i].used) {
            g_pool[i].used = true;
            g_pool_used++;
            return g_pool[i].data;
        }
    }
    return NULL;   // 明确失败，调用方必须处理
}

void pool_free(void *p) {
    if (!p) return;
    block_t *b = (block_t *)p;   // ⚠️ 这里依赖 data 是第一个成员
    b->used = false;
    g_pool_used--;
}
```

⚠️ `(block_t *)p` 这个转换只在 `data` 是结构体第一个成员时成立。更稳的做法是让调用方传回索引。

### 9.3 真实工程实例：一处固定大小的 FIFO 池

一个静态内存池的实例：用一个固定大小的数组管理 4 个 FIFO：

```c
typedef struct {
    tId            xOwnerId;
    tLen           xFifoLen;
    tLen           xReadAddr;
    tLen           xWriteAddr;
    tFifoStatus    eFifoStatus;
    unsigned char *pStartFifoAddr;
    void          *pvNextFifoList;
} tFifoInfo;

#define STRUCT_LEN   (20u)     /* Every FIFO struct used space */
#define TOTAL_BYTES  ((STRUCT_LEN) * (FIFO_NUM) + TOTAL_FIFO_BYTES)

static unsigned char gs_ucFifo[TOTAL_BYTES] = {0};   // 全部在 .bss
static tFifoInfo    *gs_pstListHeader = NULL;
static tLen          gs_xCleanFifoLen = TOTAL_BYTES;
```

**关键设计**：所有 FIFO 的**元数据**（头部结构体）和**数据区**都在同一块静态数组里，从前向后分配（元数据区往下长，数据区从 `TOTAL_BYTES` 往上长）。不用 `malloc`，不用链表节点，一共 800 + 20×4 = 880 字节，编译期就定死在 `.bss`。

这个设计还解决了一个隐性问题：`gs_ucFifo` 是 `unsigned char` 数组，任何位置都可能不对齐。所以 `ApplyFifo` 里有这么一段：

```c
/* Confirm apply FIFO header start align as 4Bytes */
CleanFIFOLenTmp = (uint32)(&gs_ucFifo[TOTAL_BYTES - gs_xCleanFifoLen]) & 0x03u;
if (CleanFIFOLenTmp) {
    gs_xCleanFifoLen -= CleanFIFOLenTmp;   // 手动对齐，丢掉几个字节
}
```

**这是 C 里最典型的「对齐要靠手动补」的场景**。高层语言里根本不会碰到。

### 9.4 环形缓冲（ring buffer）

比内存池更常用。单生产者单消费者时**可以做到无锁**：

```c
#define RB_SIZE 256   // 必须是 2 的幂

typedef struct {
    volatile uint16_t head;   // 写指针（只由生产者改）
    volatile uint16_t tail;   // 读指针（只由消费者改）
    uint8_t buf[RB_SIZE];
} ringbuf_t;

// 生产者（可能是 ISR）
bool rb_put(ringbuf_t *rb, uint8_t byte) {
    uint16_t next = (uint16_t)((rb->head + 1) & (RB_SIZE - 1));
    if (next == rb->tail) return false;   // 满
    rb->buf[rb->head] = byte;
    rb->head = next;                       // ⚠️ 顺序不能反
    return true;
}

// 消费者（主循环）
bool rb_get(ringbuf_t *rb, uint8_t *byte) {
    if (rb->head == rb->tail) return false;  // 空
    *byte = rb->buf[rb->tail];
    rb->tail = (rb->tail + 1) & (RB_SIZE - 1);
    return true;
}
```

四个关键点：

1. **`RB_SIZE` 必须 2 的幂** —— 这样 `% RB_SIZE` 可以优化成 `& (RB_SIZE-1)`
2. **`head` / `tail` 必须是 `volatile`** —— 一个在 ISR 改、一个在主循环改
3. **先写数据再移指针** —— 反了就会读到一个还没写好的槽
4. **留一个空槽区分「满」和「空」** —— 所以实际容量是 `RB_SIZE - 1`

**为什么单生产者单消费者能无锁**：`head` 只有生产者写、`tail` 只有消费者写，两个变量不共享写权，就不会有「读-改-写」的交错。这是系统编程里最常见的无锁结构。

⚠️ 但如果 `head` / `tail` 是 `uint32_t` 且超过 16 位（比如计数器），32 位 MCU 上读写是单指令所以安全；64 位计数器就不是了，必须进临界区。

### 9.5 队列满了怎么办（这是需求问题，不是代码问题）

上面的 `rb_put` 满了直接返回 `false`。但「返回 false 之后」有三种策略，**选哪个取决于业务语义**，写错会导致「数据看起来都在，但全是旧的」：

| 策略 | 行为 | 适合 | 不适合 |
|:--|:--|:--|:--|
| **丢新**（drop newest） | 满了丢弃刚来的字节 | 日志、统计（旧数据更有价值） | 控制命令（新的才是关键） |
| **丢旧**（drop oldest） | 满了覆盖最老的，`tail` 前进一格 | 实时传感、状态同步 | 协议报文（丢一帧就全乱） |
| **背压**（backpressure） | 生产者阻塞或关流控 | 有硬件流控的串口 | 中断里（绝对不能阻塞） |

```c
// 丢旧：生产者在满时推着 tail 前进
bool rb_put_overwrite(ringbuf_t *rb, uint8_t byte) {
    uint16_t next = (uint16_t)((rb->head + 1) & (RB_SIZE - 1));
    if (next == rb->tail) {
        rb->tail = (uint16_t)((rb->tail + 1) & (RB_SIZE - 1));  // 丢弃最老的一个
        // 这里应该置一个 overflow 标志，让上层知道「数据有洞」
        rb->overflow = true;
    }
    rb->buf[rb->head] = byte;
    rb->head = next;
    return true;
}
```

⚠️ **丢旧的致命细节**：`tail` 本来只由消费者写，现在生产者也要写它 —— **破坏了「单写者」前提**。如果消费者正在读 `rb->buf[rb->tail]` 而生产者刚把 `tail` 推走，读到的就是一个即将被覆盖的槽。所以：

- 单核 MCU 上，如果消费者在临界区里读，可以接受
- 多核 / DMA 场景下，**丢旧策略必须加锁**，不能再叫「无锁环形缓冲」

**更好的做法：不清数据，只记 overflow 计数。**

```c
volatile uint32_t rb_overflow_cnt;   // 溢出次数，只增不减
// 满了就 ++，让上层隔一段时间读一次，非 0 就说明数据链路已经跟不上
```

比「静默丢数据」强得多 —— 现场排障时，「有没有丢」比「丢了什么」重要。

### 9.6 中断里写、主循环里读：内存序要自己保证

```c
rb->buf[rb->head] = byte;   // ① 写数据
rb->head = next;            // ② 再发布指针
```

这两行的顺序**语义上不能换**，但编译器不知道 `head` 是「发布信号」，可能重排。`volatile` 只保证「每次都真实访问」，**不保证两行之间的顺序**。

C11 的解法是 `atomic_store_explicit(..., memory_order_release)`；不能使用 C11 原子时，用编译屏障：

```c
rb->buf[rb->head] = byte;
__asm volatile("" ::: "memory");   // 告诉编译器：这之前的写不能往后挪
rb->head = next;
```

单核 MCU 上这就够了（中断不会真正并行执行）。**多核才需要 `__DMB()`。**

## 十、状态机

### 10.1 为什么不用一长串 switch

```c
// ❌ 这种代码三个月后没人敢改
void handle(uint8_t ev) {
    switch (state) {
        case S_IDLE:
            if (ev == EV_START) state = S_RUN;
            else if (ev == EV_RESET) state = S_IDLE;
            else if (ev == EV_ABORT) state = S_ERROR;
            // ... 20 行以后
            break;
        case S_RUN:
            // ... 又是 20 行
    }
}
```

问题：**状态和事件的组合是 n×m，代码量爆炸，且不容易看出「缺了哪个转移」**。

### 10.2 表驱动状态机

```c
typedef enum { S_IDLE, S_RUN, S_ERROR, S_COUNT } state_t;
typedef enum { EV_START, EV_STOP, EV_ABORT, EV_COUNT } event_t;

typedef struct {
    state_t next;
    void  (*action)(void *ctx);
} transition_t;

static const transition_t g_table[S_COUNT][EV_COUNT] = {
    /*                 EV_START              EV_STOP             EV_ABORT        */
    /* S_IDLE  */ {{S_RUN,   on_start}, {S_IDLE,  NULL    }, {S_ERROR, on_abort}},
    /* S_RUN   */ {{S_RUN,   NULL    }, {S_IDLE,  on_stop }, {S_ERROR, on_abort}},
    /* S_ERROR */ {{S_IDLE,  on_reset}, {S_ERROR, NULL    }, {S_ERROR, NULL    }},
};

static state_t g_state = S_IDLE;

void fsm_dispatch(event_t ev, void *ctx) {
    const transition_t *t = &g_table[g_state][ev];
    if (t->action) t->action(ctx);
    g_state = t->next;
}
```

**好处**：
- 转移表在 Flash 里（`const`），不占 RAM
- 一眼能看出所有转移，包括「未定义」的格子
- 加新状态只改表，不改逻辑

### 10.3 表驱动的隐患

1. **非法转移要显式处理**：上表里 `S_ERROR + EV_ABORT` 回到自己，这是「忽略」，不是「没写」。空指针 action 就是「什么都不做」。
2. **一个事件触发多个动作**：表驱动只支持「一个转移一个动作」。需要多动作时，action 里再调多个函数。
3. **状态机的「进入/退出动作」**：上表不支持。需要的话加两张表 `on_enter[]` / `on_exit[]`，或者用更重的框架。

### 10.4 真实场景：UDS 会话状态

Bootloader 里的 UDS 会话管理就是典型状态机：`Default → Programming → Extended → Default`。每个服务只在特定会话下可用（比如 `0x34 RequestDownload` 只能在 Programming 会话下）。

如果用 `switch (session)` 判断，代码会散落到每个服务处理函数里；用表驱动，一张「服务 × 会话」的许可表就搞定了。

## 十一、协议解析器

> 验收标准里写着「能写简单协议解析器」。这一章讲的就是它 —— **比环形缓冲难，因为它是唯一一个「输入不可信」的模块**。

### 11.1 解析器要解决的三个问题

串口给你的是**没有边界的字节流**。你必须自己回答：

1. **帧从哪里开始？** —— 帧头同步
2. **这一帧有多长？** —— 长度字段（而且**不能信它**）
3. **这一帧对不对？** —— 校验 + 超时

三个问题任何一个处理不好，表现都是「跑一会儿就乱了」。

### 11.2 最简单的帧格式（也是大多数工业协议的样子）

```
┌──────┬──────┬──────┬─────────────┬───────┐
│ HEAD │ LEN  │ CMD  │    DATA     │ CRC16 │
│ 2 B  │ 1 B  │ 1 B  │ LEN-2 字节  │ 2 B   │
└──────┴──────┴──────┴─────────────┴───────┘
```

- `HEAD`：固定字节（如 `0xAA 0x55`），用来找帧边界
- `LEN`：`CMD + DATA` 的长度，**不包含 HEAD/LEN/CRC**
- `CRC16`：覆盖 `LEN + CMD + DATA`，**不覆盖 HEAD**（HEAD 只用于同步）

### 11.3 ❌ 错误写法：`read()` 一次就当一帧

```c
// 这段代码在实验室能跑，在现场必崩
void on_rx(uint8_t *buf, uint32_t len) {
    if (len < 4) return;
    if (buf[0] != 0xAA || buf[1] != 0x55) return;
    uint8_t payload_len = buf[2];
    uint16_t crc = crc16(buf + 2, payload_len);
    if (crc != BE16(buf + 2 + payload_len)) return;
    dispatch(buf[3], buf + 4, payload_len - 2);
}
```

三处错误，每一处都真实发生过：

1. **`len` 是一次的读取量，不是一帧的长度** —— 串口一次可能给你半帧，也可能给你两帧半
2. **`payload_len` 没有上限检查** —— 距离 `buf[2]` 读出的值如果是 0xFF，`crc16` 会读 255 字节，越界
3. **CRC 覆盖范围搞错** —— `crc16(buf+2, ...)` 覆盖了 LEN，但发送端可能没算 LEN

### 11.4 ✅ 正确结构：状态机 + 累积缓冲

```c
typedef enum {
    RX_WAIT_HEAD1,   // 等 0xAA
    RX_WAIT_HEAD2,   // 等 0x55
    RX_WAIT_LEN,     // 等长度
    RX_WAIT_BODY,    // 收 CMD+DATA+CRC
} rx_state_t;

#define FRAME_MAX_LEN  64   // CMD + DATA 的上限，必须写死

typedef struct {
    rx_state_t state;
    uint8_t    buf[FRAME_MAX_LEN + 4];  // LEN + CMD+DATA + CRC16
    uint16_t   pos;                     // 已收字节数
    uint16_t   need;                    // 本帧总共要收多少
    uint32_t   last_ms;                 // 最后一次收到字节的时刻
} parser_t;

void parser_feed(parser_t *p, uint8_t byte, uint32_t now_ms) {
    p->last_ms = now_ms;

    switch (p->state) {
    case RX_WAIT_HEAD1:
        if (byte == 0xAA) p->state = RX_WAIT_HEAD2;
        /* 其他字节直接丢弃 —— 这就是「帧同步」的成本：重新对齐 */
        break;

    case RX_WAIT_HEAD2:
        if (byte == 0x55) { p->state = RX_WAIT_LEN; p->pos = 0; }
        else if (byte == 0xAA) { /* 连续 0xAA，留在本状态 */ }
        else p->state = RX_WAIT_HEAD1;
        break;

    case RX_WAIT_LEN:
        if (byte < 2 || byte > FRAME_MAX_LEN) {   // ⚠️ 关键：不信长度字段
            p->state = RX_WAIT_HEAD1;             // 长度非法 → 重新同步
            break;
        }
        p->buf[0] = byte;    // 存 LEN
        p->need = (uint16_t)(byte + 2);  // LEN + CRC16
        p->pos = 1;
        p->state = RX_WAIT_BODY;
        break;

    case RX_WAIT_BODY:
        p->buf[p->pos++] = byte;
        if (p->pos >= p->need) {
            parser_try_dispatch(p);          // 校验后分发
            p->state = RX_WAIT_HEAD1;        // 无论成败，回同步态
        }
        break;
    }
}
```

**四个关键设计**：

1. **长度字段做范围检查**（`byte < 2 || byte > FRAME_MAX_LEN`）。长度字段来自对端，**它可能撒谎** —— 恶意或故障设备发一个 `LEN=0xFF` 就能让你的解析器越界读。这是所有协议实现的第一个安全边界。
2. **缓冲区大小由 `FRAME_MAX_LEN` 决定，不由长度字段决定**。这是防止栈溢出的根本。
3. **解析永远在 `RX_WAIT_HEAD1` 状态可以重启**。任何异常都回同步态，不接受「半恢复」。
4. **逐字节喂**，不要「先找帧头再切片」—— 逐字节状态机的内存占用是常数，切片方案要额外的搬运。

### 11.5 超时：最容易被忘的一环

```c
// 主循环里定期调用，比如每 10 ms
typedef enum { PARSER_IDLE, PARSER_TIMEOUT } parser_result_t;

parser_result_t parser_tick(parser_t *p, uint32_t now_ms) {
    if (p->state == RX_WAIT_HEAD1) return PARSER_IDLE;
    if ((now_ms - p->last_ms) > 50) {        // 50 ms 没收到下一个字节
        p->state = RX_WAIT_HEAD1;            // 丢弃半帧，重新同步
        p->pos = 0;
        return PARSER_TIMEOUT;
    }
    return PARSER_IDLE;
}
```

**为什么必须有超时**：如果对端发到第 3 个字节就断线了，你的状态机永远停在 `RX_WAIT_BODY`，`pos` 卡在中间。此时即使对端重连、重新发一帧，你的解析器也会把新帧的头当成老帧的body —— **会连续错到超时为止**。

真实事故：CAN TP / LIN TP 里都有这个「N_Cr 超时」参数（通常 1000 ms），本质是同一件事，超时处理占了协议栈不小篇幅。

### 11.6 校验失败之后做什么

```c
static void parser_try_dispatch(parser_t *p) {
    uint8_t  len = p->buf[0];
    uint16_t calc = crc16(&p->buf[0], (uint32_t)(len + 1));  // LEN + CMD+DATA
    uint16_t recv = BE16(&p->buf[len + 1]);                  // 末尾 2 字节

    if (calc != recv) {
        g_rx_crc_err_cnt++;      // 只统计，不重传（重传是对端的事）
        return;
    }
    dispatch_frame(p->buf[1], &p->buf[2], (uint16_t)(len - 2));
}
```

**三个原则**：

1. **CRC 错就丢，别尝试修复** —— 校验就是为了让你能安全丢弃
2. **计数，别打印** —— 中断 / 高频路径里 `printf` 会让下一帧也丢失
3. **不要自动请求重传** —— 重传逻辑属于应用层协议，解析器不该有这个职责

### 11.7 测试这个解析器（这才是重点）

解析器是**最适合单元测试**的模块 —— 纯逻辑、无硬件、输入是字节流。至少测这些：

```c
void test_parser_half_frame(void) {
    // 只喂半帧，然后超时，再喂完整帧 —— 必须正确解析
}
void test_parser_garbage_prefix(void) {
    // 喂一堆随机字节，再喂合法帧 —— 必须能同步上
}
void test_parser_len_too_large(void) {
    // LEN = 0xFF —— 必须丢弃并重新同步，不能越界
}
void test_parser_len_zero(void) {
    // LEN = 0 —— 必须丢弃
}
void test_parser_bad_crc(void) {
    // CRC 错 —— 必须不分发，计数 +1
}
void test_parser_back_to_back(void) {
    // 两帧连在一起喂 —— 必须都能解析出来
}
void test_parser_aa_aa_55(void) {
    // 帧头前有干扰的 0xAA —— 必须能处理连续 0xAA
}
```

**`test_parser_aa_aa_55` 这条最能暴露实现问题**：如果你的 `RX_WAIT_HEAD1` 收到 `0xAA` 就跳到 `HEAD2`，而 `HEAD2` 收到第二个 `0xAA` 时回到 `HEAD1`（而不是留在 `HEAD2`），那你就会漏掉「`0xAA 0xAA 0x55` 里的真实帧头」。上面代码里的 `else if (byte == 0xAA) { /* 留在本状态 */ }` 就是为这个写的。

## 十二、CRC

### 12.1 CRC 是什么（一句话）

**把任意长度的数据压成一个固定长度的校验值，使得任何一位错误都以极高概率被检出。**

不是加密、不是哈希 —— 它是**为检测传输/存储错误设计的**，不是为防篡改。

### 12.2 三种实现，选哪个

```c
// ① 逐位计算：最慢，但代码最小（可放 Bootloader）
uint16_t crc16_bitwise(const uint8_t *data, uint32_t len) {
    uint16_t crc = 0xFFFF;
    for (uint32_t i = 0; i < len; i++) {
        crc ^= (uint16_t)data[i] << 8;
        for (int b = 0; b < 8; b++) {
            crc = (crc & 0x8000) ? (uint16_t)((crc << 1) ^ 0x1021) : (uint16_t)(crc << 1);
        }
    }
    return crc;
}

// ② 查表：256 项 × 2 字节 = 512 字节，速度快 8 倍
static const uint16_t g_crc16_tab[256] = { /* ... */ };

uint16_t crc16_table(const uint8_t *data, uint32_t len) {
    uint16_t crc = 0xFFFF;
    for (uint32_t i = 0; i < len; i++) {
        crc = (uint16_t)((crc << 8) ^ g_crc16_tab[((crc >> 8) ^ data[i]) & 0xFF]);
    }
    return crc;
}

// ③ 硬件 CRC 外设：很多 MCU 自带 CRC 模块，一个寄存器写数据、读结果
```

真实工程的取舍：**Bootloader 用逐位（省 Flash），App 用查表（省时间），有硬件就用硬件**。

同一份代码里两种实现都保留，靠宏切换：

```c
#ifdef EN_CRC_HARDWARE
#include "crc_cfg.h"
#endif
#ifdef EN_CRC_SOFTWARE
static const uint16 g_dnpCrcTable[256u] = { ... };   // 512 字节放 Flash
#endif
```

### 12.3 三个必须对齐的参数

同一个多项式，参数不同结果就不同。CRC 的完整定义需要五个参数：

| 参数 | 含义 | CRC-16/CCITT-FALSE | CRC-16/DNP |
|:--|:--|:--|:--|
| Poly | 多项式 | 0x1021 | 0x3D65 |
| Init | 初值 | 0xFFFF | 0x0000 |
| RefIn | 输入是否按位翻转 | false | **true** |
| RefOut | 输出是否按位翻转 | false | **true** |
| XorOut | 最后异或的值 | 0x0000 | **0xFFFF** |

**这是最容易出错的地方**：两个人都说「我用 CRC-16」，结果一个用 CCITT 一个用 DNP，算出来的值完全对不上，还都认为自己没错。

真实工程里的注释（CRC_hal.c）：

```c
/*
 * CRC-16/DNP
 * Poly:        0x3D65
 * Init:        0x0000
 * Reverse In:  true      ← 这一行救过命
 * Reverse Out: true
 * XOR Out:     0xFFFF
 */
```

**把这五个参数写在表格注释里，比记住算出来的值重要得多。**

### 12.4 位翻转（RefIn）怎么实现

```c
static uint8_t reverse8(uint8_t b) {
    b = (uint8_t)((b & 0xF0) >> 4 | (b & 0x0F) << 4);
    b = (uint8_t)((b & 0xCC) >> 2 | (b & 0x33) << 2);
    b = (uint8_t)((b & 0xAA) >> 1 | (b & 0x55) << 1);
    return b;
}
```

三次「对半交换」—— 这是位操作里最经典的套路，值得记住。

### 12.5 用它校验什么

真实工程里 CRC 的两个用途：

```c
// ① 校验整块 Flash 区域（App 完整性）
CRC_HAL_CreatSoftwareCrc((const uint8 *)pAppInfo, sizeof(tAppFlashStatus) - 4u, &crc);
if (crc == pAppInfo->crc) { /* 完整 */ }

// ② UDS 服务 0x31 (RoutineControl) 校验下载的数据
ReceivedCrc = (ReceivedCrc << 8u) | msg->aDataBuf[5u];
ReceivedCrc = (ReceivedCrc << 8u) | msg->aDataBuf[6u];
ReceivedCrc = (ReceivedCrc << 8u) | msg->aDataBuf[7u];
```

注意第一处的 `sizeof(tAppFlashStatus) - 4u` —— **CRC 字段自己不能参与计算**，否则鸡生蛋。这是 CRC 应用里最常见的 off-by-4。

### 12.6 CRC32：和 CRC16 就差几个参数

验收标准里写的是「CRC16/CRC32」。**两者代码结构完全一样**，只是宽度、多项式和参数不同：

| 参数 | CRC-16/CCITT-FALSE | CRC-16/DNP | **CRC-32 (ISO-HDLC)** |
|:--|:--|:--|:--|
| Width | 16 | 16 | **32** |
| Poly | 0x1021 | 0x3D65 | **0x04C11DB7** |
| Init | 0xFFFF | 0x0000 | **0xFFFFFFFF** |
| RefIn | false | true | **true** |
| RefOut | false | true | **true** |
| XorOut | 0x0000 | 0xFFFF | **0xFFFFFFFF** |
| 用在哪 | 串口协议、XMODEM | 工业总线 | **ZIP / PNG / 以太网 / UDS 刷写** |

```c
// ⚠️ CRC-32/ISO-HDLC 的 RefIn/RefOut 都是 true，所以是「反射式」实现：
//    右移、异或反转多项式 0xEDB88320（不是 0x04C11DB7）
//    写成左移版会得到 0xFC891918（错），不是标准值 0xCBF43926
uint32_t crc32_bitwise(const uint8_t *data, uint32_t len) {
    uint32_t crc = 0xFFFFFFFFu;
    for (uint32_t i = 0; i < len; i++) {
        crc ^= data[i];
        for (int b = 0; b < 8; b++) {
            crc = (crc & 1u) ? (crc >> 1) ^ 0xEDB88320u : (crc >> 1);
        }
    }
    return crc ^ 0xFFFFFFFFu;   // ⚠️ 别忘了 XorOut
}

// 查表版：256 × 4 字节 = 1 KB，放 Flash（必须加 const）
static const uint32_t g_crc32_tab[256] = { /* ... */ };

uint32_t crc32_table(const uint8_t *data, uint32_t len) {
    uint32_t crc = 0xFFFFFFFFu;
    for (uint32_t i = 0; i < len; i++) {
        crc = (crc >> 8) ^ g_crc32_tab[(crc ^ data[i]) & 0xFFu];
    }
    return crc ^ 0xFFFFFFFFu;
}
```

**为什么这里是右移、`0xEDB88320`，而 CRC16 那段是左移、`0x1021`**：

CRC16/CCITT-FALSE 的 RefIn/RefOut 是 **false** → 左移、用原始多项式。
CRC-32/ISO-HDLC 的 RefIn/RefOut 是 **true** → 右移、用**反转后的多项式**。

`0xEDB88320` 就是 `0x04C11DB7` 的 32 位反转结果（把二进制从右往左读）。**这两个数字必须配套**：左移配 0x04C11DB7，右移配 0xEDB88320。混用就是最常见的「算出来对不上」。

**三个最容易错的点**：

1. **忘了最后的 `^ 0xFFFFFFFF`（XorOut）** —— 算出来的值和对端对不上，而且差得毫无规律
2. **左移/右移和多项式不配套** —— 上面说的那个坑，比忘 XorOut 更隐蔽
3. **查表没加 `const`** —— 1 KB 的表跑进 RAM。在只有 128 KB SRAM 的 MCU 上，一张表就吃掉 1/128

### 12.7 用标准测试向量验证（必做）

CRC 的参数写错后，代码能跑、结果稳定、就是**和别人的对不上**。唯一可靠的验证方式是标准测试向量：

```c
// "123456789"（9 个 ASCII 字节）的标准结果
// CRC-16/CCITT-FALSE → 0x29B1
// CRC-16/DNP         → 0xEA82
// CRC-32/ISO-HDLC    → 0xCBF43926

void test_crc_vectors(void) {
    const uint8_t v[] = "123456789";
    assert(crc16_ccitt_false(v, 9) == 0x29B1);
    assert(crc16_dnp(v, 9)         == 0xEA82);
    assert(crc32(v, 9)             == 0xCBF43926u);
}
```

**这三个数字背下来都不亏** —— 它们是 CRC 界的「Hello World」，也是排查「为什么对端校验不过」最快的一步。如果本地算 `0xCBF43926` 是对的，那问题一定在覆盖范围（多算/少算了哪几个字节）或端序（发出去是不是大端），而不在算法本身。

### 12.8 硬件 CRC 的三个坑

很多 MCU 都有硬件 CRC 外设，但用之前确认：

1. **硬件支持的多项式是不是你要的** —— 很多 MCU 的硬件 CRC 只支持固定多项式（如某些型号固定 0x04C11DB7），换个协议就用不了
2. **输入/输出是否按字节翻转** —— 硬件通常有个「反转」配置位，配错了结果完全不对
3. **初值能不能改** —— 有些硬件初值固定为 0xFFFFFFFF，要改成别的得自己预处理

真实工程里 `CRC_hal.c` 用宏 `EN_CRC_HARDWARE` / `EN_CRC_SOFTWARE` 切换，**两个实现必须比特级一致**，靠上面的标准向量测出来。

### 13.1 别当语法背，绑着事故学

### 13.2 三个真实的用法示例

**① 查「为什么 RAM 不够了」**

```bash
arm-none-eabi-nm --size-sort -S --radix=d firmware.elf | tail -20
```

输出按大小排序，一眼看出哪个变量最大。常见元凶：
- 忘记加 `const` 的大查表（8 KB 的表本该在 Flash，结果进了 RAM）
- `static` 的缓冲区开太大
- 某个库内部藏了个大 `.bss`

**② 查「函数是不是被 gc-sections 删了」**

```bash
arm-none-eabi-nm firmware.elf | grep my_function
# 没输出 = 不在符号表里 = 被链接器删了或根本没编进来
```

如果确实需要保留（比如中断向量表引用的函数、`__attribute__((constructor))`），用 `KEEP()`：

```ld
.text : {
    KEEP(*(.isr_vector))
    *(.text) *(.text*)
}
```

**③ 查「为什么跳到了野地址」**

```bash
arm-none-eabi-objdump -d firmware.elf | grep -B2 -A2 "bl.*0x00000000"
```

跳到 0 通常是：函数指针没初始化、虚表（C++）没构造、或者 `PROVIDE` 的符号地址写错了。

### 13.3 一个 map 文件的读法

链接时加 `-Wl,-Map=firmware.map`，产出物里能看到：

```
Memory Configuration
Name             Origin             Length             Attributes
FLASH            0x0000000008000000 0x0000000000100000 xr
RAM              0x0000000020000000 0x0000000000020000 xrw
CCMRAM           0x0000000010000000 0x0000000000010000 rw

Linker script and memory map
.text           0x0000000008000000     0x1a4c
 *(.isr_vector)
 .isr_vector    0x0000000008000000      0x188 startup.o
 *(.text*)
 .text.main     0x0000000008000188      0x2c  main.o
```

读法：
1. **先看 Memory Configuration** —— 确认链接脚本里的区域都识别了
2. **再看每个段的总大小** —— 对比 Flash/RAM 容量，还剩多少
3. **怀疑某个符号时 grep 它** —— 能看到它被哪个 `.o` 贡献、放在哪个地址

### 13.4 ⚠️ 一件事 map **看不了**：栈有多大

截图里说「能看 map 文件说出 `.text`/`.data`/`.bss` 在哪里、**栈大概多大**」。前半句对，后半句要纠正：

> **map 文件能告诉你栈的「起址」（即 `_estack` 或 `__StackTop`），但告诉不了你「栈实际用了多少」。**

原因很简单：栈是**运行时**才往下长的。链接时编译器只知道「栈底地址是 `0x20020000`」，不知道你的递归、`printf` 的浮点格式化、局部大数组会吃掉多少。所以：

| 想知道 | map 能不能答 | 怎么办 |
|:--|:--|:--|
| 栈的起址（栈顶地址） | ✅ 能 —— `_estack` 符号 | `grep _estack firmware.map` |
| 链接时预留给栈的大小 | ⚠️ 部分能 —— 如果你在链接脚本里写 `_Min_Stack_Size`，它是个常量 | `grep _Min_Stack_Size firmware.map` |
| **栈实际峰値用量** | ❌ **不能** | 栈填充魔数 + 事后扫描（见 3.4） |
| 堆用了多少 | ❌ 不能 | 自己包一层 `malloc` 计数 |

```ld
/* 链接脚本里通常这样写：*/ 
_Min_Stack_Size = 0x400;   /* 只声明“至少留 1KB”，不是“只用了 1KB” */ 
. _estack = ORIGIN(RAM) + LENGTH(RAM);   /* 栈顶 = RAM 末尾 */ 
```

**真正量栈峰値的做法**（也是验收标准里「栈大概多大」该有的答案）：

```c
// 1. 启动时把整个栈区填成 0xCD
#define STACK_PAINT 0xCDCDCDCDu
extern uint32_t _sstack, _estack;
void stack_paint(void) {
    for (uint32_t *p = &_sstack; p < &_estack; p++) *p = STACK_PAINT;
}

// 2. 跑一段时间（覆盖所有业务路径）后，从栈顶往下扫描
uint32_t stack_peak_bytes(void) {
    uint32_t *p = &_sstack;
    while (p < &_estack && *p == STACK_PAINT) p++;
    return (uint32_t)((uint8_t *)&_estack - (uint8_t *)p);   // 被改写的字节数 ≈ 峰値用量
}
```

这个值比链接脚本留的 `_Min_Stack_Size` 有意义得多：**留 1 KB 实际只用 200 字节，说明你浪费了 800；留 1 KB 用掉 990，说明快撑了。**

**一句话总结**：map 回答「空间被谁占了」（静态占用），栈填充回答「运行时到底用了多少」（动态占用）。两者都不能省。

## 十四、可测性：主机侧单元测试

### 14.1 为什么硬件相关代码也要写单元测试

硬件相关的逻辑在真实硬件上测太慢：每改一次要重新下载、复位、接仪器观察，一轮下来几分钟。而**纯逻辑部分（协议解析、状态机、CRC、环形缓冲）完全可以在主机上跑**，几十毫秒出结果。

### 14.2 关键设计：把硬件抽象成接口

```c
// 不要在业务代码里直接调硬件驱动
// ❌ 这样在主机上编译不过，也没法 mock
void handle(void) {
    uint8_t b;
    uart_receive(&g_uart, &b, 1, 100);
    process(b);
}

// ✅ 依赖注入：业务代码只依赖函数指针
typedef struct {
    bool    (*read)(uint8_t *byte);
    bool    (*write)(const uint8_t *data, uint32_t len);
    uint32_t (*now_ms)(void);
} platform_t;

void handle(const platform_t *p) {
    uint8_t b;
    if (p->read(&b)) process(b);
}
```

主机上给它一个假的：

```c
static uint8_t g_fake_rx[64];
static uint32_t g_fake_rx_len = 0, g_fake_rx_pos = 0;
static uint8_t g_fake_tx[256];
static uint32_t g_fake_tx_len = 0;

static bool fake_read(uint8_t *b) {
    if (g_fake_rx_pos >= g_fake_rx_len) return false;
    *b = g_fake_rx[g_fake_rx_pos++];
    return true;
}
static bool fake_write(const uint8_t *d, uint32_t n) {
    memcpy(&g_fake_tx[g_fake_tx_len], d, n);
    g_fake_tx_len += n;
    return true;
}
static uint32_t fake_now(void) { return 0; }

static const platform_t fake_platform = { fake_read, fake_write, fake_now };
```

### 14.3 测试框架选型

| 框架 | 特点 | 适合 |
|:--|:--|:--|
| **Unity** | 单文件 `unity.c`，几十 KB，无依赖 | 资源受限环境 / Bootloader |
| **Ceedling** | Unity + CMock + Rake，自动生成 mock | 有一定规模的项目 |
| **cmocka** | 支持 mock 和 fixture | Linux 上跑的协议栈 |
| **GoogleTest** | C++，功能全 | 只测 C 代码也可以（用 `extern "C"`） |

**推荐路径**：先上 **Unity**（就两个文件，加进 CMake 的 `add_executable` 就能跑），跑通之后再考虑 Ceedling。

### 14.4 在现有 CMake 工程里加测试

```cmake
# tests/CMakeLists.txt
add_executable(test_ringbuf
    test_ringbuf.c
    ${PROJECT_SOURCE_DIR}/src/ringbuf.c      # 直接编源码，不链硬件驱动库
)
target_include_directories(test_ringbuf PRIVATE ${PROJECT_SOURCE_DIR}/src)
target_link_libraries(test_ringbuf PRIVATE unity)

add_test(NAME ringbuf COMMAND test_ringbuf)
```

关键：**测试目标只编「纯逻辑 .c」，绝不链硬件驱动 / 芯片头文件 / 启动文件**。这样 GCC 用主机的，不需要交叉工具链，CI 里 `cmake -B build-test && ctest` 就能跑。

### 14.5 该测什么，不该测什么

**该测**（纯逻辑，无硬件依赖）：
- 协议帧解析（正常帧、超长帧、CRC 错、长度字段撒谎）
- 状态机所有转移（包括非法转移）
- 环形缓冲边界（空、满、只差一个、wrap around）
- CRC 对已知向量（标准测试向量最容易抓出参数写错）

**不该测**（在主机上测不了）：
- 寄存器访问（需要真实硬件或仿真）
- 时序（`delay_ms` 到底延迟了多久）
- 中断优先级、实际抢占行为

**中间地带**（用 mock 测）：
- 「发送失败时是否重试 3 次」→ mock `write` 返回 false
- 「超时后是否回错误码」→ mock `now_ms` 递增

### 14.6 一个能立刻做的练习

拿一段你自己写的协议处理代码来试：

```c
// 把 0x22 服务的 DID 解析抽成纯函数
uds_result_t handle_read_did(const uint8_t *req, uint32_t len,
                             uint8_t *resp, uint32_t *resp_len);

// 然后测：
// - 请求长度不足 → NRC 0x13 (incorrectMessageLength)
// - DID 不支持 → NRC 0x31 (requestOutOfRange)
// - 正常 DID → 返回数据 + 正响应
// - 大端解析是否正确（DID 0x0102 不能被解析成 0x0201）
```

这些测试在 x86 上跑，几十毫秒出结果，可以挂到 Jenkins 的每个 PR 上。

## 十五、学习计划与验收标准

### 15.1 四周分段

| 周 | 主题 | 产出 |
|:--|:--|:--|
| **第 1 周** | 内存与类型 | 能手工算出任意 `struct` 的 `sizeof`；能画出 `.text/.data/.bss/stack/heap` 布局图 |
| **第 2 周** | 指针与 const/static/extern | 能说清一个变量「在哪、谁改、什么时候初始化」；能写函数指针回调表 |
| **第 3 周** | volatile + 位运算 + 未定义行为 | 能在一段有 bug 的 ISR 代码里指出 3 处问题；能把协议解析改成 `stdint.h` + 显式转换 |
| **第 4 周** | 静态分配 + 环形缓冲 + 状态机 + 解析器 + CRC + 工具链 | 写一个无 `malloc` 的通信模块，用 `nm/size` 验证内存占用，用标准向量验证 CRC |

### 15.2 验收标准（对照你的大纲逐条展开）

大纲的四条验收标准，拆成可检验的子项：

**① 能写一个无动态分配的 UART 环形缓冲，并说明满/空/溢出处理**

- [ ] `RB_SIZE` 是 2 的幂，用 `& (RB_SIZE-1)` 而不是 `%`
- [ ] `head` / `tail` 都标 `volatile`，且**只有单一写者**
- [ ] 能解释为什么实际容量是 `RB_SIZE - 1`（留一个空槽区分满/空）
- [ ] 能说出「丢新 / 丢旧 / 背压」三种策略分别适合什么场景（9.5）
- [ ] 能指出「丢旧」策略为什么破坏单写者前提
- [ ] 溢出时有计数器（`rb_overflow_cnt`），不是静默丢数据

**② 能写 CRC16/CRC32、简单协议解析器、协作式状态机**

- [ ] CRC16 能算出 `"123456789"` → `0x29B1`（CCITT-FALSE）
- [ ] CRC32 能算出 `"123456789"` → `0xCBF43926`
- [ ] 能说出五个参数里哪个最容易写错（RefIn / XorOut）
- [ ] 查表版加了 `const`，能说出表占多少 Flash
- [ ] 解析器对 `LEN=0xFF` 不越界，回同步态（11.4）
- [ ] 解析器有 50 ms 超时，半帧能丢掉重来（11.5）
- [ ] 能处理 `0xAA 0xAA 0x55` 这种连续帧头干扰（11.7）
- [ ] 状态机用表驱动，非法转移有显式定义
- [ ] 状态机是**协作式**的 —— 每次调用只推进一步，不在里面死等

**③ 能解释一个变量为什么必须 volatile，以及什么情况下仍会出错**

- [ ] 说出 `volatile` 的准确语义（每次访问必须真实发生）
- [ ] 指出 `counter++` 不是原子操作，三种交错
- [ ] 临界区用保存-恢复 `PRIMASK`，可嵌套
- [ ] 区分编译屏障 `asm volatile("" ::: "memory")` 和内存屏障 `__DMB()`
- [ ] **能说出 `volatile` 挡不住的两种情况**：多字节原子性、跨变量的顺序

**④ 能看 map 文件说出 `.text`/`.data`/`.bss` 在哪里、栈大概多大**

- [ ] 能读出每个段的起址和大小，算出 Flash / RAM 剩余
- [ ] 能用 `nm --size-sort` 找出最大的 5 个符号
- [ ] **能指出「map 只给栈的起址，给不了峰值」**，并说出怎么真量（3.4 / 13.4）
- [ ] 能用 `size -A` 和 map 互相验证

**额外必须能独立完成的**：

- [ ] 给定 `struct`，算出 `sizeof` 和每个成员的 `offsetof`
- [ ] 解释 `.bss` 为什么不需要存在 Flash 里，谁清零
- [ ] 用 `(uint32_t)` 显式转换修好一处 `<< 24` 的 UB
- [ ] 把直连 HAL 的业务代码改成依赖注入，主机上跑通单元测试

### 15.3 🎯 达标信号：300–500 行、`-Wall -Wextra -Werror`

大纲最后的「达标信号」是**不靠教程写出 300–500 行可编译、可测试的系统编程风格 C，并通过严格告警**。这个目标具体化成下面这个题目：

**题目：一个串口命令服务**（约 400 行）

| 模块 | 行数 | 要求 |
|:--|:--|:--|
| `ringbuf.[ch]` | ~80 | 无锁 SPSC，256 字节，溢出计数 |
| `crc.[ch]` | ~60 | CRC16 + CRC32 各一份查表实现，带标准向量自测 |
| `parser.[ch]` | ~120 | 状态机解析器，帧头 `AA 55`，长度上限检查，50 ms 超时 |
| `fsm.[ch]` | ~80 | 3 状态 × 4 事件表驱动，含错误态 |
| `main.c` | ~60 | 主循环 + 依赖注入的平台接口 |
| `test_*.c` | ~100 | 最少 12 个用例（见 11.7） |

**编译要求**（差一个都不算过）：

```bash
# 主机侧（单元测试）
gcc -std=c11 -Wall -Wextra -Werror -Wconversion -Wsign-conversion \
    -Wshadow -Wundef -Wdouble-promotion -Wcast-qual -Wstrict-prototypes \
    -fno-common -O2 -c ringbuf.c crc.c parser.c fsm.c

# 交叉编译（真实固件）
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=c11 \
    -Wall -Wextra -Werror -Os -ffunction-sections -fdata-sections -c *.c
```

**自检清单**：

- [ ] `grep -n "malloc\|calloc\|realloc\|free" *.c` 无输出
- [ ] `grep -n "printf" *.c` 在中断 / 解析路径上无输出
- [ ] `size firmware.elf` 的 `.bss` 和你手算的一致
- [ ] `nm --size-sort` 里最大符号是你预期的那个缓冲区
- [ ] 12 个单元测试全绿，`ctest` 0 失败

**为什么是 300–500 行而不是 2000 行**：规模到 500 行左右，你会自然碰到所有核心问题（静态分配边界、中断与主循环共享、协议容错、内存占用核算），但还没大到需要拆分模块、引入构建系统复杂度。**这是「一个人一周能完整写完并讲清楚」的极限尺寸。**
