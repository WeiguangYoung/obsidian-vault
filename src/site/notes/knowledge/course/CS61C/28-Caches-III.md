## 一、完整走查：16 KB 直接映射缓存、16 B 块

### 1.1 缓存结构（回顾 L27）

| 字段 | 位数 |

| **Index** | **10** |

### 1.2 ⭐ 第 1 次读：`0x00000014`

**拆分：**

```
000000000000000000  0000000001  0100
       Tag             Index      Offset
        = 0             = 1        = 4
```

**过程：**

| 步骤 | 结果 |
|---|---|
| **① 查索引 1** | Valid = **0** |
| **② 未命中（Compulsory Miss）** | |
| **③ 从内存载入块（0x10–0x1F）** | 值 = a, b, c, d |
| **④ 设置 Valid = 1, Tag = 0** | |
| **⑤ 用 offset=4 取字** | **返回 `b`** |

**更新后：**

| Index | Valid | Tag | 0x0-3 | 0x4-7 | 0x8-b | 0xc-f |
|---|---|---|---|---|---|---|
| **1** | **1** | **0** | **a** | **b** | **c** | **d** |

> ⚠️ **offset=4 表示「块内第 4 字节」→ 第 2 个字（`b`）。**

---

### 1.3 ⭐ 第 2 次读：`0x0000001C`

**拆分：**

```
...0000 0000 0000000001 1100
       Tag=0    Index=1   Offset=0xC(12)
```

**过程：**

| 步骤 | 结果 |
|---|---|
| **① 查索引 1** | **Valid = 1** ✅ |
| **② Tag = 0，匹配** ✅ | **命中（HIT）** |
| **③ 用 offset = 0xC 取字** | 第 4 个字 |

**返回：`d`** ✅

---

### 1.4 ⭐ 第 3 次读：`0x00000034`

**拆分：**

```
...0000 0000 0000000011 0100
       Tag=0    Index=3   Offset=4
```

**过程：**

| 步骤 | 结果 |
|---|---|
| **① 查索引 3** | Valid = **0** |
| **② 未命中（Compulsory Miss）** | |
| **③ 载入块 0x30–0x3F** | 值 = e, f, g, h |
| **④ 设置 Valid = 1, Tag = 0** | |
| **⑤ offset=4** | **返回 `f`** |

---

### 1.5 ⭐⭐ 第 4 次读：`0x00008014`

**拆分：**

```
...0000 0010 0000000001 0100
    Tag=2       Index=1   Offset=4
```

**过程：**

| 步骤 | 结果 |
|---|---|
| **① 查索引 1** | **Valid = 1** ✅ |
| **② Tag 检查：缓存里是 0，请求的是 2** | **❌ 不匹配** |
| **③ 未命中（Conflict Miss）** | |
| **④ 替换块 1** | **把 a,b,c,d 踢掉，载入 i,j,k,l** |
| **⑤ 设置 Tag = 2** | |
| **⑥ offset=4** | **返回 `j`** |

**更新后：**

| Index | Valid | Tag | 0x0-3 | 0x4-7 | 0x8-b | 0xc-f |
|---|---|---|---|---|---|---|
| **1** | 1 | **2** | **i** | **j** | **k** | **l** |
| 3 | 1 | 0 | e | f | g | h |

> ⭐ **这就是「冲突未命中（Conflict Miss）」的教科书例子：**
> **`0x14` 和 `0x8014` 都映射到索引 1，互相踢出。**

> ⚠️ **注意：此时 `0x14` 的数据（a,b,c,d）已经没了 —— 如果再次读 `0x14`，又要 miss 一次。**

### 1.6 🎯 课堂练习（自己算）

**当前状态：**

| Index | Valid | Tag | 数据 |
|---|---|---|---|
| 0 | 0 | — | |
| 1 | **1** | **2** | **i, j, k, l** |
| 2 | 0 | — | |
| **3** | **1** | **0** | **e, f, g, h** |

#### 练习 A：读 `0x00000030`

```
Tag=0  Index=3  Offset=0
```

| 步骤 | 结果 |
|---|---|
| 查索引 3 | Valid = 1 ✅ |
| Tag 0 == 0 | **匹配** ✅ |
| **命中（HIT）** | |
| offset = 0 | 第 1 个字 |

> **答案：`e`（命中，无需替换）**

#### 练习 B：读 `0x0000001c`

```
Tag=0  Index=1  Offset=0xC
```

| 步骤 | 结果 |
|---|---|
| 查索引 1 | Valid = 1 ✅ |
| Tag 缓存是 **2**，请求是 **0** | **❌ 不匹配** |
| **未命中（Conflict Miss）** | |
| 替换 | 载入 a,b,c,d，Tag 改回 0 |
| offset = 0xC | 第 4 个字 |

> **答案：`d`（未命中+替换）**

### 1.7 ⭐ 关键观察

> **「因为都是「读」，返回的值必然等于「内存值」—— 无论有没有缓存。」**

```
0x00000030 = e
0x0000001c = d
```

> **缓存只影响「速度」，不影响「正确性」—— 这是缓存设计的第一原则。**

## 二、⭐ 多字块直接映射缓存（4K 字、4 字/块）

### 2.1 结构

```
31 30           15 14 13          4 3 2 1 0
┌───────────────┬──────┬─────────┬───────────┐
│  Tag (18)     │Index │  Block  │Byte offset│
│               │  10  │ offset 2│    (2)    │
└───────────────┴──────┴─────────┴───────────┘
```

| 字段 | 位数 | 作用 |
|---|---|---|
| **Tag** | **18** | 区分同索引的块 |
| **Index** | **10** | 选择 1024 行之一 |
| **Block offset** | **2** | **块内选哪个字（4 字 → 2 位）** |
| **Byte offset** | **2** | **字内选哪个字节（4 字节 → 2 位）** |

> ⭐ **「Block offset + Byte offset = 总共 4 位 offset」—— 和 L27 的 16 B 块一致。**

### 2.2 硬件结构

```
   Tag(18)  Index(10)
       │        │
       ▼        ▼
  ┌────────┬────────┐
  │"=="比较│        │
  └───┬────┴───┬────┘
      │        ▼
      │    ┌────────┐
      │    │  Data  │  1024 行 × 4 字
      │    └───┬────┘
      │        │ 4 字
      │        ▼
      │   ┌──────────┐
      │   │4→1 MUX   │◄── Block offset(2)
      │   └────┬─────┘
      │        │ 32 位字
      │        ▼
      └──►  Hit  ──► 输出
```

> **「4→1 多路选择器」由 Block offset 控制，从 4 个字里选 1 个。**

### 2.3 ⭐ 问题：利用的是什么局部性？

> **「我们利用的是什么局部性？」**

**答案：空间局部性（Spatial Locality）。**

> **一次 miss 取来 4 个字，后续访问邻近地址就能命中。**

## 三、⭐⭐ 写命中怎么办（Write Policy）

> **「写命中时该怎么做？」**

### 3.1 Write-through（写直达）

> **「同时更新缓存和内存。」**

| 步骤 | 说明 |
|---|---|
| **① 写缓存** | |
| **② 同时写内存** | |

**优点：**

| 优点 | 说明 |
|---|---|
| **简单** | 无需额外状态 |
| **内存永远是最新的** | 缓存是「纯副本」|
| **I/O 安全** | DMA 读内存能拿到新值 |

**缺点：**

| 缺点 | 说明 |
|---|---|
| **每次写都要访问内存** | ⚠️ **非常慢（100 ns vs 1 ns）** |
| **写频繁的程序性能暴跌** | |

> **缓解：加「写缓冲（write buffer）」—— 写内存异步进行。**

### 3.2 Write-back（写回）

> **「只更新缓存块里的字。**
> **允许内存里的字「陈旧（stale）」→ 给块加一个「脏位（dirty bit）」。**
> **内存和缓存不一致，需要在块被替换时更新。**
> **……OS 在 I/O 前 flush 缓存……」**

| 步骤 | 说明 |
|---|---|
| **① 只写缓存** | **不碰内存** |
| **② 设置 dirty = 1** | 标记「内存里的旧了」 |
| **③ 替换时** | **若 dirty，写回内存** |

**优点：**

| 优点 | 说明 |
|---|---|
| **写快（只有 1 ns）** | ✅ |
| **同一块反复写只写回一次** | ✅ 大幅减少内存流量 |

**缺点：**

| 缺点 | 说明 |
|---|---|
| **需要 dirty 位** | 每个块多 1 位 |
| **替换时可能「突变慢」** | 要写内存 |
| **内存可能不一致** | ⚠️ **需要 OS 在 I/O 前 flush** |

### 3.3 ⭐ 性能权衡

| 场景 | Write-through | Write-back |
|---|---|---|
| **写少读多** | 差不多 | 差不多 |
| **写密集（如 `memset`）** | ❌ 极慢 | ✅ 快 |
| **单线程正确性** | ✅ 简单 | 需要 flush |
| **多核/多设备一致性** | ✅ 简单 | ❌ 复杂 |

> ⭐ **「现代 CPU 用 write-back + 写缓冲；某些嵌入式/安全场景用 write-through。」**

**还有一个「写未命中」的问题：**

| 策略 | 说明 |
|---|---|
| **Write-allocate** | 未命中时先载入块，再写（配合 write-back）|
| **No-write-allocate** | 直接写内存，不载入块（配合 write-through）|

## 四、⭐⭐ 块大小的权衡

### 4.1 大块的好处

> **「空间局部性：如果访问某个字，很可能很快访问邻近的字。」**

| 好处 | 说明 |
|---|---|
| **✅ 对「存储程序概念」非常适用** | 指令是顺序的 |
| **✅ 对「顺序数组访问」效果很好** | `for (i) a[i]` |

### 4.2 大块的坏处

> **「块越大 → miss penalty 越大（一次 miss 要从下层加载更久）。」**
> **「如果块相对缓存太大 → 块数太少 → miss rate 上升。」**

| 坏处 | 机制 |
|---|---|
| **⚠️ Miss penalty ↑** | 载入更多字节 |
| **⚠️ Miss rate ↑（块过大时）** | 块数少 → 冲突多 |

### 4.3 ⚠️ 极端例子：一个大块

> **「缓存大小 = 4 字节，块大小 = 4 字节 → 缓存只有「一行」！」**

```
┌───────┬──────┬─────────────────────────┐
│ Valid │ Tag  │ Data: B3 B2 B1 B0       │
└───────┴──────┴─────────────────────────┘
```

**灾难：**

> **「如果某项被访问，很可能很快再被访问。**
> **但不太可能「立刻」再被访问！**
> **下一次访问很可能又是 miss。**
> **不断加载数据，但在再次使用前就被丢弃。」**

> ⭐ **「缓存设计师的噩梦：「乒乓效应（Ping Pong Effect）」」**

### 4.4 三条曲线

```
Miss Rate              Miss Penalty         Average Access Time
    │                      │                     │
    │╲                     │        ╱            │╲
    │ ╲___                 │      ╱              │ ╲___
    │     ╲___             │    ╱                │     ╲___
    └────────── Block      └────────── Block     └────────── Block
      (先降后升)              (单调上升)            (U 形)
```

| 曲线 | 趋势 |
|---|---|
| **Miss Rate** | **先降（空间局部性）→ 后升（块数少）** |
| **Miss Penalty** | **单调上升** |
| **Average Access Time** | **U 形 → 有最优点** |

### 4.5 ⭐ 结论

> **三条曲线共同解释：**
> **「块大小有「甜点区」—— 通常 16–64 字节。」**

| 影响因素 | 方向 |
|---|---|
| **利用空间局部性** | 块越大越好 |
| **块数太少（伤时间局部性）** | 块越大越糟 |
| **载入代价** | 块越大越糟 |

## 五、⭐⭐ 三种 Miss（Three Cs Model）

### 5.1 第一个 C：Compulsory Miss（强制未命中）

> **「程序刚启动时发生。缓存里还没有该程序的任何数据，所以 miss 必然发生。」**

| 特性 | 说明 |
|---|---|
| **无法轻易避免** | 本课不重点讨论 |
| **「每个内存块」都会有一次** | ⚠️ **注意：不是「每个缓存块」** |

> ⚠️ **「每个内存块都有一次 compulsory miss —— 不只是「缓存的每个块」。」**

**含义：**

```
如果内存有 1 GB（2^30 字节），块 64 B（2^6）
→ 2^24 个块
→ 总共 2^24 次 compulsory miss（无论缓存多大）
```

> ⭐ **「compulsory miss 是「程序的数据量」决定的，不是「缓存大小」决定的。」**

**别名：** **Cold miss（冷未命中）**

### 5.2 第二个 C：Conflict Miss（冲突未命中）

> **「两个「不同的内存地址」映射到「同一个缓存位置」导致的 miss。」**
> **「两个块（碰巧映射到同一位置）会不断地互相覆盖。」**
> **「在直接映射缓存里是「大问题」。」**

**怎么缓解：**

| 方案 | 说明 | 效果 |
|---|---|---|
| **① 把缓存做大** | **到某个点就失效了** | ⚠️ 不能根治 |
| **② 让「多个不同的块」能放进「同一个缓存索引」** | **→ 组相联/全相联** | ✅ **正解** |

### 5.3 第三个 C：Capacity Miss（容量未命中）

> **「缓存大小有限导致的 miss。」**
> **「如果增大缓存大小就不会发生的 miss。」**
> **「定义有点模糊，理解大意即可。」**

> ⭐ **「这是全相联缓存的主要 miss 类型。」**

> **因为全相联没有冲突 —— 剩下的 miss 只能是「装不下」。**

## 六、⭐⭐ 全相联缓存（Fully Associative）

### 6.1 地址字段

| 字段 | 说明 |
|---|---|
| **Tag** | **和之前一样** |
| **Offset** | **和之前一样** |
| **Index** | ❌ **不存在！** |

### 6.2 这意味着什么

> **「没有「行」—— 任何块可以去缓存的「任何地方」。」**
> **「必须和「整个缓存里的所有 tag」比较，才能知道数据在不在。」**

### 6.3 结构

```
      Tag (27 位)              Byte Offset (4/5 位)
           │
    ┌──────┴───────┬─────────┬─────────┬─────┐
    ▼              ▼         ▼         ▼     ▼
  ┌───┐         ┌───┐     ┌───┐     ┌───┐
  │ ==│         │ ==│     │ ==│ ... │ ==│   ← 32 个比较器并行
  └─┬─┘         └─┬─┘     └─┬─┘     └─┬─┘
    │             │         │         │
  ┌─▼─┐         ┌─▼─┐     ┌─▼─┐     ┌─▼─┐
  │V,T│         │V,T│     │V,T│ ... │V,T│   ← Tag 存储
  └─┬─┘         └─┬─┘     └─┬─┘     └─┬─┘
    │             │         │         │
  ┌─▼─────────────▼─────────▼─────────▼─┐
  │        数据块（B0…B31）              │
  └───────────────┬──────────────────────┘
                  ▼
              ┌───────┐
              │  MUX  │◄── 命中信号（选择）
              └───┬───┘
                  ▼
               32 位字
```

### 6.4 优点

> **「✅ 没有冲突未命中（数据可以去任何地方）。」**

### 6.5 ⚠️ 缺点（致命）

> **「需要「每个条目一个硬件比较器」：**
> **如果缓存有 64 KB 数据、4 B 条目，我们需要 16K 个比较器：不可行（infeasible）！」**

**对比：**

| 类型 | 比较器数 |
|---|---|
| **直接映射（1024 行）** | **1 个** |
| **全相联（16384 行）** | **16,384 个** ❌ |

> ⭐ **「比较器的面积 + 延迟，让全相联只适用于「小缓存」（如 TLB、L1 的某些部分）。」**

> **这就是为什么需要「折中方案：组相联（set-associative）」—— L29 的主题。**

## 七、⭐⭐ 如何「分类」miss（Kubiatowicz 算法）

> **「拿一个地址 trace，跑在一组缓存上：」**

| 步骤 | 做法 |
|---|---|
| **①** | **先考虑「无限大小、全相联」的缓存** |
| | **此时发生的每个 miss → 算作 Compulsory Miss** |
| **②** | **再考虑「有限大小（你要考察的大小）、全相联」的缓存** |
| | **不在 #1 里的 miss → 算作 Capacity Miss** |
| **③** | **最后考虑「有限大小、有限相联」的缓存** |
| | **剩下的（不在 #1 也不在 #2）→ 算作 Conflict Miss** |

> ⭐ **「（感谢 Kubiatowicz 教授提供这个算法）」**

**这个算法为什么有效：**

```
① 去掉「容量」和「冲突」的限制 → 只剩「必然要 miss 的」
② 加回「容量」限制 → 新增的 miss 都是「装不下」
③ 加回「关联度」限制 → 新增的 miss 都是「位置冲突」
```

> **层层剥离，把「miss 的成因」分离出来。**

## 八、课程结论（原话）

> **「结论：**
> **分成 T I O 位，跳到 Index = I，检查 Valid。**
> **1. 若 Valid = 0，载入块、设置 valid 和 tag（COMPULSORY MISS），用 offset 返回正确的块（1/2/4 字节）**
> **2. 若 Valid = 1，检查 tag**
> **   1. 若匹配（HIT），用 offset 返回正确的块**
> **   2. 若不匹配（CONFLICT MISS），载入块、设置 valid 和 tag，用 offset 返回正确的块」**

## 九、我的笔记与理解

### 9.1 走查例子里的「一个陷阱」

> **第 4 次读 `0x8014` 之后，索引 1 里装的是 `i,j,k,l`。**
> **此时如果你再读 `0x14` —— 又要 miss 一次。**

```
0x14   → 索引 1 → Tag 0，缓存是 2 → miss，载入 a,b,c,d
0x8014 → 索引 1 → Tag 2，缓存是 0 → miss，载入 i,j,k,l
0x14   → 索引 1 → Tag 0，缓存是 2 → miss，载入 a,b,c,d
0x8014 → ...
```

> ⭐ **「这是「乒乓效应」的直接表现 —— 命中率 0%，尽管缓存有 16 KB 而只需要 32 字节。」**

> **L29 的组相联就是为了破这个局。**

### 9.2 为什么 write-through 慢得不合比例

> **写一次内存 = 100 ns，写一次缓存 = 1 ns。**

**在 5 级流水线里：**

```
写直达：STORE 指令要等 100 ns → 相当于 100 个流水线周期
       → 流水线完全停住！
```

> ⭐ **这就是为什么真实 CPU 必须有「写缓冲（write buffer）」：**
> **写入缓冲后立即继续，硬件后台慢慢写内存。**

**写缓冲的陷阱：**

> **如果连续写很多次，缓冲区满了 → 还是要停。**
> **这就是为什么 `memset` 大数组仍然慢。**

### 9.3 Dirty bit 与「一致性问题」

> **Write-back 的核心风险：内存里的数据是「陈旧的」。**

**谁会被这个坑到？**

| 场景 | 问题 |
|---|---|
| **DMA（设备直接读内存）** | **读到旧数据** ❌ |
| **多核共享** | **别的核读到旧数据** ❌ |
| **断电/崩溃** | **丢失最后几次写** ❌ |

**解法：**

| 场景 | 解法 |
|---|---|
| **I/O 前的软件** | **`flush`、`mb()`（memory barrier）** |
| **多核** | **缓存一致性协议（MESI）** |
| **断电** | **写日志（journaling）/ `fsync`** |

> ⭐ **「dirty bit 是「性能优化」，代价是「一致性复杂化」—— 典型的工程权衡。」**

### 9.4 「块太大 → 块数少」的量化

**例：16 KB 缓存**

| 块大小 | 块数 | 每块的「数据占比」 |
|---|---|---|
| **4 B** | **4096** | 32/(18+32+1) = **63%** ❌ |
| **16 B** | **1024** | 128/147 = **87%** ✅ |
| **64 B** | **256** | 512/531 = **96%** ✅✅ |
| **256 B** | **64** | 2048/2067 = **99%** |
| **4 KB** | **4** | 32768/32787 ≈ **100%** |

> ⭐ **「块越大，「tag 开销」越低 —— 但「块数」也越少。」**

**块数的影响（冲突）：**

```
4 块：4 个「不同的索引」→ 4 路并行，冲突概率高
256 块：256 个索引 → 冲突少得多
```

> **所以「开销」和「冲突」是拉锯战 —— 64 B 左右是平衡点。**

### 9.5 「三个 C」与「优化方向」

| Miss 类型 | 谁负责 | 优化手段 |
|---|---|---|
| **Compulsory** | 无法避免（除非预取）| **预取（prefetching）** |
| **Capacity** | 缓存总容量 | **加大缓存 / 更好的替换策略** |
| **Conflict** | 关联度 | **组相联** |

> ⭐ **「诊断 miss 类型，才能对症下药 ——**
> **这就是为什么 Kubiatowicz 算法有实用价值。」**

**实际例子：**

| 现象 | 诊断 | 处方 |
|---|---|---|
| **换大缓存也没用** | Compulsory | 预取（程序局部性差异大）|
| **换大缓存明显改善** | Capacity | 加大 L2/L3 |
| **加大关联度明显改善** | Conflict | 直接映射 → 组相联 |

### 9.6 为什么「全相联不可行」

> **「16K 个比较器」听起来只是面积问题 —— 但延迟更致命。**

```
单个比较器延迟：~0.5 ns
32 个并行比较：仍是 ~0.5 ns（并行）
16K 个并行比较：需要「大扇入 OR 树」→ 延迟增大 + 功耗剧增
```

> ⭐ **「这就是为什么全相联只用在「小结构」：**
> - **TLB（32–512 项）** ✅
> - **L1 的某些部分** ⚠️
> - **L3 的一部分** ⚠️
> - **整个 L2/L3 全相联** ❌ 不可行"
