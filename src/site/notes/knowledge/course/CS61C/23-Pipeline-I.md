## 一、单周期 CPU 留下的问题

| 已有 | 问题 |
|---|---|
| ✅ 能执行全部 RISC-V 指令（每条一周期）| ❌ **不是所有硬件被所有指令使用** |
| ✅ 五个阶段 IF/ID/EX/MEM/WB | ❌ **不是所有指令在所有阶段活跃** |
| ✅ 控制器（ROM 或逻辑）| ❌ **关键路径随指令变化** |

**核心矛盾（数字回顾）：**

```
f_max = 1/800 ps = 1.25 GHz    ← 按 lw 的完整路径定
每阶段只需 200 ps              ← 理论上能跑 5 GHz
```

> ⭐ **「很多块在大多数时间是闲置的！」**
> **「反过来，每个阶段只要 200 ps → 为什么不能 5 GHz？」**

## 二、⭐ Latency vs Throughput

### 2.1 两个定义

| 术语 | 通俗说法 |
|---|---|
| **Latency（延迟）** | **端到端完成一个任务要多久** |
| **Throughput（吞吐量）** | **开始跑起来之后，执行任务有多高效** |

> **两者不是一回事，不能混为一谈。**

### 2.2 ⭐ 交通类比（本讲最经典）

> **任务：送 100 名乘客，往返 50 英里。**

| 车型 | 载客 | 速度 |
|---|---|---|
| **跑车（Sports Car）** | 2 人 | **200 mph** |
| **大巴（Bus）** | 50 人 | **50 mph** |

**哪辆车「更好」？取决于你用什么指标！**

#### 指标 1：单程时间（Latency）

| 车 | 计算 | 结果 |
|---|---|---|
| **跑车** | `50 mi / 200 mph = 0.25 h` | **15 分钟** ✅ |
| **大巴** | `50 mi / 50 mph = 1 h` | 60 分钟 |

#### 指标 2：送完 100 人总时间

| 车 | 计算 | 结果 |
|---|---|---|
| **跑车** | `50 趟 × 15 min` | **750 分钟** |
| **大巴** | `2 趟 × 60 min` | **120 分钟** ✅ |

#### 指标 3：每小时送多少人（Throughput）

| 车 | 计算 | 结果 |
|---|---|---|
| **跑车** | `2 人 / 15 min` | **8 人/小时** |
| **大巴** | `50 人 / 60 min` | **50 人/小时** ✅ |

> ⭐ **结论：跑车「单车更快」，大巴「总吞吐更高」。**
> **选哪个，看你要什么。**

### 2.3 映射到计算机

| 交通指标 | 处理器指标 |
|---|---|
| **单程时间** | **指令延迟（instruction latency）** |
| **送完 100 人总时间** | **程序执行时间** |
| **每小时人数** | **指令吞吐量（instructions/cycle）** |

> ⭐ **流水线提升的是「吞吐量」，不是「单条指令的延迟」。**

### 2.4 其他指标（课件补充）

> - **能效（energy efficiency）**
> - **油耗（gas mileage）**
> - **全生命周期成本（cost over car lifetime）**

> **同理，CPU 也不能只看一个数字。**

## 三、⭐ 洗衣房的类比

### 3.1 场景

> **4 位顾客（1、2、3、4），每人有一批衣服要洗、烘、叠、收。**

| 阶段 | 耗时 |
|---|---|
| **洗衣机（Washer）** | **30 分钟** |
| **烘干机（Dryer）** | **30 分钟** |
| **折叠（Folder）** | **30 分钟** |
| **收纳（Stasher）** | **30 分钟** |

### 3.2 ❌ 顺序洗（Sequential）

> **一个人用完全部四个阶段，下一个人再开始。**

```
6PM  7    8    9    10   11   12   1AM  2
 │
客1  ████ ████ ████ ████
客2                 ████ ████ ████ ████
客3                                 ████ ████ ████ ████
客4                                                 ████ ████ ████ ████
```

| 指标 | 数值 |
|---|---|
| **4 批衣服总时间** | **8 小时** |
| **单批时间** | **2 小时** |
| **每 30 分钟完成批数** | **0.25** |

### 3.3 ✅ 流水线洗（Pipelined）

> **每 30 分钟启动一个新阶段，不同顾客同时处于不同阶段。**

```
6PM  7    8    9    10
 │
客1  W¹  D²  F³  S⁴
客2      W¹  D²  F³  S⁴
客3          W¹  D²  F³  S⁴
客4              W¹  D²  F³  S⁴
     └──── 30 分钟一格 ────┘
```

| 指标 | 顺序 | 流水线 | 变化 |
|---|---|---|---|
| **4 批总时间** | 8 小时 | **3.5 小时** | ✅ **2.3×** |
| **单批时间（延迟）** | 2 小时 | **2 小时** | ⚠️ **不变** |
| **每 30 分钟批数（吞吐）** | 0.25 | **1** | ✅ **4×** |

> ⭐ **「流水线提高的是「指令吞吐量」，不是「指令延迟」。」**

### 3.4 稳态（Steady State）

> **「不是平均而言…… 而是一旦流水线「填满」，恰好每 30 分钟完成 1 批。」**

| 时期 | 行为 |
|---|---|
| **填充期（fill）** | 前 3 个 30 分钟没有输出 |
| **稳态（steady）** | 每 30 分钟输出 1 批 |
| **排空期（drain）** | 最后 3 个 30 分钟还在干活 |

```
吞吐量 = 1 批 / 30 分钟   （稳态下）
```

> **这就是为什么「指令数越多，流水线越划算」—— 填充和排空的成本被摊薄。**

## 四、从洗衣房到 CPU

### 4.1 顺序 vs 流水线

**顺序（Sequential）**

```
t_instruction
add t0 t1 t2  ████████████████
or  t3 t4 t5                   ████████████████
lw  t6 8(t7)                                      ████████████████
              └──── t_cycle ────┘
```

> **「单周期 CPU 里，同一时钟周期只能有一条指令按顺序访问资源。」**

**流水线（Pipelined）**

```
t_instruction
add t0 t1 t2  IF │ ID │ EX │ MEM│ WB
or  t3 t4 t5     │ IF │ ID │ EX │ MEM│ WB
lw  t6 8(t7)     │    │ IF │ ID │ EX │ MEM│ WB
                 └── t_cycle ──┘
```

> **「流水线 CPU 里，多条指令在同一时钟周期访问不同资源。」**

### 4.2 ⭐ 性能对比（关键数字）

| 指标 | 单周期 | 流水线 |
|---|---|---|
| **阶段耗时** | 200, 100, 200, 200, 100 ps | **全部 200 ps** |
| **指令延迟** | **800 ps** | **5 × 200 = 1000 ps** |
| **时钟频率** | **1/800 ps = 1.25 GHz** | **1/200 ps = 5 GHz** |
| **吞吐增益** | — | **×4** |

> ⚠️ **注意两个反直觉之处：**
> 1. **流水线让「单条指令」变慢了**（800 → 1000 ps）—— 因为要过 5 个流水线寄存器
> 2. **但吞吐量涨了 4 倍**（1.25 → 5 GHz）

### 4.3 为什么只有 ×4 而不是 ×5

> **单周期 800 ps → 流水线 200 ps = 4 倍。**

**原因：**

```
单周期每周期完成 1 条 → 800 ps/条
流水线每周期完成 1 条 → 200 ps/条
```

```
增益 = 800/200 = 4
```

> **不是因为 5 阶就 ×5 —— 而是「最慢阶段」决定的。**

> ⭐ **「流水线 CPU 仍然所有阶段共用一个时钟！时钟周期由最慢的阶段决定。」**

**如果五阶段完全均匀（都 160 ps）：**

```
增益 = 800/160 = 5 倍（理论上限）
```

## 五、⭐ 流水线的两条公式

### 5.1 非流水线 Adder + Shifter

```
输入 ──►[ Adder ]──►[ Shifter ]──► 输出
```

| 量 | 公式 |
|---|---|
| **关键路径** | `t_clk-q + t_Add + t_Shift + t_setup` |
| **吞吐** | **每周期 1 个结果** |

> **时钟周期受「Adder + Shifter 的传播延迟」限制。**

### 5.2 流水线 Adder + Shifter

```
输入 ──►[ Adder ]──►[REG]──►[ Shifter ]──► 输出
```

| 量 | 公式 |
|---|---|
| **关键路径** | `max{ t_clk-q + t_Add + t_setup,` |
| |  `t_clk-q + t_Shift + t_setup }` |
| **延迟** | `(t_clk-q + t_Add + t_setup)` |
| | `+ (t_clk-q + t_Shift + t_setup)` |

> ⭐ **关键洞察：延迟「相加变长」，但关键路径「取最大变短」。**

| 指标 | 变化 |
|---|---|
| **吞吐量** | ✅ **更高（每秒更多输出）** |
| **延迟** | ⚠️ **更高（单个结果更慢）** |

## 六、⭐ 五级流水线 datapath

### 6.1 核心思想

> **「流水线 datapath 需要把 RV32I datapath 的五个阶段「分开」。**
> **每个阶段要处理「不同指令」的数据。」**

```
IF │ ID │ EX │ MEM │ WB
```

### 6.2 四个流水线寄存器

> **在阶段之间插寄存器，每个上升沿把「数据 + 控制信号」传给下一阶段。**

| 流水线寄存器 | 位于 | 携带内容 |
|---|---|---|
| **IF/ID** | IF → ID | **`inst`、`PC`**（两个寄存器）|
| **ID/EX** | ID → EX | **`RegReadData1`、`RegReadData2`、`imm`、`inst`** |
| **EX/MEM** | EX → MEM | **`ALUOut`、`RegReadData2`（store 用）、`inst`** |
| **MEM/WB** | MEM → WB | **`rdata`、`ALUOut`、`inst`** |

### 6.3 各寄存器的要点

#### IF/ID（1/4）

| 要点 | 说明 |
|---|---|
| **有两个流水线寄存器** | **`inst` + `PC`** |
| **`PC+4` 存进 IF/ID** | **为下一周期的 IF 阶段准备好 PC** |

**为什么存 PC 而不只存指令？**

> **因为后面的 jal/jalr 需要 `PC+4` 写回 rd。**

#### ID/EX（2/4）

> **「把指令和它需要的数据一起传下去，以便每个阶段能正确操作控制。」**

| 携带 | 用途 |
|---|---|
| **`RegReadData1`** | ALU 的 A 输入 |
| **`RegReadData2`** | ALU 的 B 输入 / store 的 dataW |
| **`imm`** | ALU 的 B 输入（BSel=1 时）|
| **`inst`** | **控制信号来源**（rg: rd 字段、分支判定等）|

#### EX/MEM（3/4）

> ⚠️ **「`rs2`（要存的数据）需要被 pipeline 到 MEM 阶段。」**

> **因为 `sw` 的 dataW 来自 `R[rs2]`，而 MEM 阶段才需要它。**

#### MEM/WB（4/4）

> ⭐ **「为了避免同时把 `PC` 和 `PC+4` 都送下流水线，在这里重新计算 `PC+4`。」**

> **节省一条 32 位数据通路。**

### 6.4 ⭐ 控制信号也要流水线化

> **「控制信号从指令派生。后续阶段的控制信息也存储在流水线寄存器里。」**

**策略：**

| 步骤 | 说明 |
|---|---|
| **①** | **在 ID 阶段「尽可能多地」计算控制信号** |
| **②** | **把控制「字」（control words）在阶段之间流水线化** |

**控制字的流动：**

```
ID:   算出全部控制信号 → 存进 ID/EX 寄存器
       ↓
EX:   用 ALUSel、ASel、BSel；把 MemRW、RegWEn、WBSel 继续往下传
       ↓
MEM:  用 MemRW；把 RegWEn、WBSel 继续往下传
       ↓
WB:   用 RegWEn、WBSel
```

> ⭐ **`RegWEn`、`WBSel` 要一路传到 WB 阶段 —— 因为它们控制的是最后一步。**

## 七、🎯 课堂练习：谁在哪个阶段

### 7.1 题目

> **在给定的时钟周期里，所有同时在执行的指令是如何使用流水线各阶段的？**

```asm
add t0, t1, t2
or  t3, t4, t5
lw  t6, 8(t7)
```

| 选项 | |
|---|---|
| A | `add` 或 `lw` |
| **B** | **`lw` 或 `add`** ✅ |
| C | 其他 |

### 7.2 答案

```
        IF    ID    EX    MEM   WB
```

**稳态下（最老的在最后阶段）：**

| 阶段 | 指令 | 说明 |
|---|---|---|
| **WB** | **`lw`** | **最老的指令**，在最后阶段 |
| **MEM** | — | |
| **EX** | — | |
| **ID** | — | |
| **IF** | — | |

**如果三条都同时在：**

| 阶段 | 指令 |
|---|---|
| **IF** | **`add`**（最年轻的）|
| **ID** | — |
| **EX** | — |
| **MEM** | — |
| **WB** | **`lw`**（最老的）|

> ⭐ **课件答案 B：`lw` 或 `add` ——**
> **`lw` 在最靠后的阶段，`add` 在最靠前的阶段。**

### 7.3 ⭐ 核心规律（呼应洗衣房）

> **「更早的顾客在更靠后的流水线阶段（他们更接近完成洗衣）。」**

```
程序顺序：  add → or → lw
流水线位置：最前        最后
```

> ⭐ **「最老的指令在最后的阶段」—— 这是理解流水线时序的第一原则。**

## 八、我的笔记与理解

### 8.1 为什么「延迟变差」是可接受的

> **单条指令从 800 ps 变 1000 ps，慢了 25%。**

**但：**

| 场景 | 影响 |
|---|---|
| **跑 1 条指令** | 慢 25% ❌ |
| **跑 100 万条指令** | **快 4 倍** ✅ |
| **填充+排空成本** | 只有 4 个周期 ≈ 800 ps，可摊薄 |

**数学：**

```
顺序跑 N 条：N × 800 ps
流水线跑 N 条：(N + 4) × 200 ps

N = 4:     3200 vs 1600    → 2×
N = 100:   80000 vs 20800  → 3.85×
N → ∞:        → 4× （趋近）
```

> ⭐ **「流水线是「摊销」的艺术：把固定成本分摊到海量指令上。」**

### 8.2 为什么不能切 10 段 / 20 段

> **理论上切得越细，频率越高。**

**但现实有代价：**

| 代价 | 说明 |
|---|---|
| **流水线寄存器延迟（`t_clk-q + t_setup`）** | **固定开销，切得越细占比越大** |
| **冒险增多** | 数据冒险、控制冒险（L24）|
| **硅面积** | 每级都要存大量状态 |
| **功耗** | 更多寄存器翻转 |

**数学：**

```
切 N 段：周期 = t_reg + t_stage ≈ 30 + 160/N ps
N = 5:  30 + 32 = 62 ps   → 16 GHz（理想）
N = 20: 30 + 8  = 38 ps   → 26 GHz（理想）
```

> **但实际 CPU 停在 5–20 级 —— 因为冒险的代价超过收益。**

> ⭐ **这就是为什么 Pentium 4 的 31 级流水线失败了，而 Apple M 系列的 ~10 级成功了。**

### 8.3 为什么要把「控制信号」也流水线

> **控制信号是从指令派生的 —— 而指令只在 ID 阶段存在。**

**问题：**

```
EX 阶段需要 ALUSel
MEM 阶段需要 MemRW
WB 阶段需要 RegWEn、WBSel
```

> **但 EX/MEM/WB 阶段手里没有「指令」了（只有流水线寄存器里的数据）。**

**两种解法：**

| 解法 | 说明 | 代价 |
|---|---|---|
| **① 把指令传下去，每阶段重新解码** | 只传 `inst` | 每阶段都要解码器 |
| **✅ ② 在 ID 全解码，把控制字传下去** | 传多个 1 位控制信号 | 需要更多流水线位 |

> ⭐ **本课选方案 ②：解码一次，控制字随数据流动。**

**控制字位宽估算：**

```
PCSel(1) + ImmSel(3) + BrUn(1) + ASel(1) + BSel(1)
+ ALUSel(4) + MemRW(1) + RegWEn(1) + WBSel(2)
= 15 位
```

> **每个流水线寄存器多 15 位 —— 5 级流水线多 60 位状态。**
> **相比 32 位数据通路，这个开销可以接受。**

### 8.4 MEM/WB 重算 PC+4 的精妙

> **朴素做法：**

```
IF/ID 存 PC
ID/EX 存 PC
EX/MEM 存 PC
MEM/WB 存 PC
       ↓
WB 阶段算 PC+4 → 写 rd
```

> **同时还要存 `PC+4`（给分支算目标）→ 两条 32 位通路。**

**本课做法：**

```
只用一条 32 位通路传 PC
MEM/WB 阶段：从 PC 重新算 PC+4（一个 32 位加法器）
```

> ⭐ **「用计算代替存储」—— 省 32 位 × 4 级 = 128 位寄存器。**

**代价：多一个加法器。**

> **这是硬件设计的经典权衡：**空间 vs 时间**、**存储 vs 计算**。**

### 8.5 「填满」和「排空」的工程意义

> **流水线的性能公式（理想化）：**

```
CPI = 1 + (fill + drain) / N
    = 1 + 4/N
```

| N（指令数）| CPI | 效率 |
|---|---|---|
| **4** | **2.0** | 50% |
| **100** | **1.04** | 96% |
| **1000** | **1.004** | 99.6% |

> ⭐ **这就是为什么「循环体里的短程序」最需要优化 ——**
> **分支越频繁，流水线越容易排空（L24 的控制冒险）。**

### 8.6 为什么是「五个阶段」而不是四个或六个

**这个划分来自 RV32I 的资源结构：**

| 阶段 | 用的资源 | 不能合并的原因 |
|---|---|---|
| **IF** | IMEM | 只有 1 个 IMEM |
| **ID** | RegFile | 只有 1 个 RegFile 读口组 |
| **EX** | ALU | 只有 1 个 ALU |
| **MEM** | DMEM | 只有 1 个 DMEM |
| **WB** | RegFile 写口 | 与 ID 的读分开 |

> ⭐ **「每个阶段一个独占资源」—— 这就是五级划分的物理依据。**

> **如果资源更丰富（双端口内存、多 ALU），可以合并或拆得更细。**

### 8.7 与后续的衔接

| 讲次 | 关系 |
|---|---|
| **L24 Pipeline II** | **数据冒险（forwarding）和 load-use 冒险** |
| **L25 Pipeline III** | **控制冒险、分支预测、性能计算** |
| **L26–L29** | 缓存：让 IF/MEM 阶段不那么慢 |
