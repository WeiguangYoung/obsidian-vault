## 二、🎯 课堂练习：哪些冒险能用转发解决

### 2.1 题目

```asm
add s0, t1, t2
lw  s1, 8(s0)
or  t3, s1, t5
and t4, s1, t2
sll t0, t1, t2
```

> **哪些数据冒险能靠 forwarding 解决？（多选）**

| 选项 | 内容 |
|---|---|
| **A** | **`add` 的 EX 输出被 `lw` 的 MEM 输入需要** |
| **B** | **`lw` 的 MEM 输出被 `or` 的 EX 输入需要（同一周期）** |
| **C** | **`lw` 的 MEM 输出被 `and` 的 EX 输入需要** |
| **D** | 以上都不是 |

### 2.2 瀑布图

| 指令 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| **add** | IF | ID | EX | MEM | WB | | |
| **lw** | | IF | ID | EX | MEM | WB | |
| **or** | | | IF | ID | EX | MEM | WB |
| **and** | | | | IF | ID | EX | MEM |
| **sll** | | | | | IF | ID | EX |

### 2.3 ⭐ 答案

> **✅ A 和 C 可以，❌ B 不行。**

#### ✅ A：MEM→EX（相隔 1 条）

```
add 的 EX 输出（t=3）
        ↓ 存进 EX/MEM 寄存器
lw 的 MEM 阶段（t=4）需要它
```

> **「把 EX 阶段的输出转发到「下一个时钟周期」的 EX 阶段输入。」**

> ⚠️ **课件标注为「MEM→EX」，实际含义是「EX/MEM 寄存器 → EX 阶段」。**
> **`lw` 的 MEM 阶段（t=4）实际上不需要 `s0` —— 它在 EX 阶段（t=3）就用完了。**
> **课件这条选项描述的是「通用情况：相隔一条指令」。**

#### ✅ C：WB→EX（相隔 2 条）

```
lw 的 MEM 输出（t=5）
        ↓ 存进 MEM/WB 寄存器
and 的 EX 阶段（t=6）需要它
```

> **「把 MEM 阶段的输出转发到「下一个时钟周期」的 EX 阶段输入。」**

> **`and` 在 t=6 的 EX 阶段，`lw` 的结果在 t=5 结束时就进了 MEM/WB 寄存器 → 可以转发。**

#### ❌ B：同周期不可能

```
lw 的 MEM 输出（t=5）
or 的 EX 阶段（t=5）
     ↑ 同一周期！
```

> ⭐ **「MEM 阶段（`lw`）的输出，需要在「同一时钟周期」作为 EX 阶段（`or`）的输入。」**
> **这做不到 —— 数据在同一周期内还没有稳定地「出来」。**

> ⭐⭐ **「不能时光倒流（Cannot go backwards in time!）」—— 课件原话。**

## 三、⭐ Load 冒险（load-use hazard）

### 3.1 术语

> **「紧跟在 load 之后的那个指令位置，叫做「load 延迟槽（load delay slot）」。」**

### 3.2 问题

> **如果延迟槽里的指令「使用了 load 的结果」：**

| 情况 | 结果 |
|---|---|
| **硬件必须停一个周期** | **（停完再用 forwarding）** |
| **后果** | ⚠️ **性能损失！** |

### 3.3 时序分析

```asm
add s0, t1, t2
lw  s1, 8(s0)
or  t3, s1, t5     ← 用 s1，用不了！
and t4, s1, t2
sll t0, t1, t2
```

**原始（有 stall）：**

| 指令 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| **add** | IF | ID | EX | MEM | WB | | |
| **lw** | | IF | ID | EX | **MEM** | WB | |
| **or**（→ nop）| | | IF | ID | **—** | — | |
| **or**（真实）| | | | | **IF** | ID | EX |
| **and** | | | | | | IF | ID |
| **sll** | | | | | | | IF |

> ⚠️ **`lw` 在 t=5 的 MEM 阶段才拿到数据。**
> **`or` 在 t=5 就要用 —— 同一周期，来不及！**

### 3.4 ⭐ 为什么 forwarding 到此为止

> **「Forwarding 在「下一个时钟周期」送数据。」**
> **「不能时光倒流！」**

**对比两种情况：**

| 情况 | 间隔 | forwarding |
|---|---|---|
| **ALU 指令 → 下一条** | **相隔 1 条（差 2 周期）** | ✅ 可转发 |
| **ALU 指令 → 下下条** | 相隔 2 条 | ✅ 可转发 |
| **load → 紧随其后** | **数据在 MEM 才出（t+3）** | ❌ **来不及** |
| **load → 隔一条** | `load` 的 MEM 在 t+3，后者 EX 在 t+4 | ✅ **可转发** |

> ⭐ **根本原因：`lw` 的数据「出现得晚」—— 要到第 4 个阶段（MEM）才有。**

### 3.5 解法一：停一拍

```
t=5: or 停住（发 nop）
t=6: lw 的结果进了 MEM/WB，or 进入 EX → 转发 ✅
```

> **代价：1 个周期的损失。**

## 四、⭐ 解法二：Code Scheduling（代码调度）

### 4.1 示例程序

```c
A[3] = A[0] + A[1];
A[4] = A[0] + A[2];
```

**内存布局：**

```
&a → A[0] A[1] A[2] A[3] A[4]
      a0   t0   t1   t2   t3   t4
              ↑    ↑    ↑    ↑    ↑
              偏移 0、4、8、12、16
```

### 4.2 ❌ 简单编译（7 条指令，9 周期）

```asm
lw  t0, 0(a0)
lw  t1, 4(a0)      ← 需要 stall+forward（+1 周期）
add t3, t0, t1
sw  t3, 12(a0)
lw  t2, 8(a0)
add t4, t0, t2     ← 需要 stall（+1 周期）
sw  t4, 16(a0)
```

| 指标 | 数值 |
|---|---|
| **指令数** | 7 |
| **周期数** | **9**（7 + 2 次停顿）|

### 4.3 ✅ 代码调度后（7 周期）

```asm
lw  t0, 0(a0)       ← A[0]
lw  t1, 4(a0)       ← A[1]（在 t0 的延迟槽里！）
lw  t3, 8(a0)       ← A[2]（在 t1 的延迟槽里！）
add t2, t0, t1      ← A[0] + A[1]
sw  t2, 12(a0)      ← 写 A[3]
add t4, t0, t3      ← A[0] + A[2]
sw  t4, 16(a0)      ← 写 A[4]
```

| 指标 | 数值 |
|---|---|
| **指令数** | 7 |
| **周期数** | **7** ✅ |
| **停顿** | **0** |

### 4.4 ⭐ 为什么能省下来

> **「在延迟槽里，放一条「与 load 结果无关」的指令。」**

**关键操作：把三条 `lw` 连在一起！**

```
原始顺序：  lw → (stall) → lw → (stall) → add → sw → ...
调度之后：  lw → lw → lw → add → sw → add → sw
                  ↑    ↑
            填进延迟槽，无需 stall
```

> ⭐ **第二条 `lw` 不依赖第一条的结果 → 可以填进延迟槽。**

### 4.5 ⭐ 课程定义

> **「代码调度（Code scheduling）：**
> **凭借对底层 CPU 流水线的了解，编译器重排代码以提高性能。」**

> ⚠️ **「这需要了解流水线结构」—— 编译器必须知道「几条指令后数据才可用」。**

## 五、⭐ 控制冒险（Control Hazard）

### 5.1 定义

> **「执行流取决于前一条指令。」**

### 5.2 具体场景：条件分支

```asm
0x40  beq t0, t1, Label
0x44  sub t2, s0, t0      ← 已开始执行
0x48  or  t6, a0, t0      ← 已开始执行
0x4c  xor t5, t1, s0      ← 已开始执行
...
0x70  sw  s0, 8(t3)       ← Label 处的正确指令
```

> **「如果 `beq` 跳转，那么「在分支结果未知之前」，这三条指令已经开始执行了。」**

### 5.3 ⭐ 根因：分支结果在 MEM 阶段才知道

> **「分支结果在 MEM 阶段才准备好。」**

```
IF   ID   EX   MEM   WB
          │    │
          │    └─ Branch Comp 出结果，PCSel 决定
          └────── ALU 算 PC + imm（目标地址）
```

**所以：**

| 时刻 | 已取入的指令 |
|---|---|
| **t=1** | `beq`（IF）|
| **t=2** | `sub`（IF）—— **不知道 beq 会不会跳** |
| **t=3** | `or`（IF）|
| **t=4** | `xor`（IF）|

> ⭐ **总共「3 条指令」被「错误地取入」。**

### 5.4 解法：Flush（冲刷）

> **「如果分支成立，把 3 条「不正确的指令」转换成 nop。」**

```
0x40  beq  → 正常执行
0x44  sub  → 改成 nop
0x48  or   → 改成 nop
0x4c  xor  → 改成 nop
...
0x70  sw   → 从正确地址取指
```

> **「在下一个时钟周期，PC 更新，正确的指令被取入。」**

### 5.5 ⭐ 分支代价

> **「在简单的 RV32I 流水线里，每一个「成立的分支」都要付出 3 个时钟周期。」**

| 情况 | 代价 |
|---|---|
| **分支成立（taken）** | **3 个周期** ❌ |
| **分支不成立（not taken）** | **0 个周期** ✅ |

> **「注意：如果分支不成立，流水线不停顿，分支后面顺序取入的指令就是正确指令。」**

### 5.6 ⚠️ 一个被忽略的事实

> ⭐ **「简单的 RV32I 流水线，实际上「总是预测「分支不成立」」。**

**为什么？**

```
t=1: beq 进 IF
t=2: PC = PC + 4（默认行为），sub 进 IF
     ↑ 这时分支结果还不知道
```

> **硬件「懒得等」，直接走 PC+4 —— 这就是「不成立」的预测。**

### 5.7 ⭐ 分支预测（Branch Prediction）

> **「分支预测可以提升「平均」CPU 性能。」**

**两个步骤：**

| 步骤 | 说明 |
|---|---|
| **① 在流水线「早期」猜** | **猜分支往哪边走** |
| **② 猜错了就 flush** | 冲刷掉错误指令 |

**朴素预测器：**

> **「Don't Take Branch（不跳转）」—— 猜 `PC = PC + 4`。**

| 情况 | 结果 |
|---|---|
| **猜对了（不成立）** | ✅ 无需停顿 |
| **猜错了（成立）** | ❌ **仍然付 3 个周期** |

> ⭐ **「对「错误预测」的惩罚仍然是 3 个时钟周期！分支预测只是想提升「平均」性能。」**

### 5.8 ⭐ 分支预测的价值

> **假设分支成立率 20%：**

| 策略 | 平均惩罚 |
|---|---|
| **不做预测（等于总猜不成立）** | `0.2 × 3 = 0.6` 周期/分支 |
| **总是猜不成立** | 同上 |
| **猜「上次的方向」（1 位预测器）** | 循环里命中率极高 → 接近 0 |

> **课件提到：「教科书里有「超出本课范围」的硬件代价改进。」**

**真实 CPU 用的预测器：**

| 类型 | 说明 |
|---|---|
| **1 位（last outcome）** | 记住上次方向 |
| **2 位（saturating counter）** | 连续两次错才改主意 |
| **BTB（Branch Target Buffer）** | 缓存分支目标地址 |
| **TAGE / 神经网络** | 现代 CPU 的复杂预测器，命中率 > 95% |

## 六、⭐ 结论：RISC-V 为什么「天生适合流水线」

> **这是本讲的「总结陈词」—— 也回答了「为什么 RISC-V 是这么设计的」。**

### 6.1 ① 所有指令都是 32 位宽

| 好处 | 说明 |
|---|---|
| **容易取指（IF）** | **一个周期取得完整指令** |
| **容易译码（ID）** | **一个周期完成译码** |

> ⚠️ **「对比 CISC（复杂）x86：指令宽 1 到 15 字节！」**

> ⭐ **x86 的变长指令让「取指+译码」必须多周期，这是它流水线的天然负担。**

### 6.2 ② 少量标准指令格式

| 好处 | 说明 |
|---|---|
| **能在「一个阶段」（第 2 个，ID）完成「译码 + 读寄存器」** |

> **对比：变长指令需要先「找出指令边界」，才能译码。**

### 6.3 ③ Load/Store 寻址概念清晰

| 步骤 | 说明 |
|---|---|
| **① 第 3 阶段（EX）用 ALU 算地址** | |
| **② 第 4 阶段（MEM）访存** | |

> **「内存操作数全部「对齐（aligned）」」**
> **「访存只需一个周期。」**

> ⭐ **对齐是「能用一周期」的前提 —— 否则可能跨 cache line，需要多周期。**

### 6.4 ④ 五级流水线「无处不在」

> **「我们学的五级流水线，在很多设备里都很常见：汽车、家电等等。」**

> **不是只有高性能 CPU 才用流水线 —— 它是「数字系统设计的通用技术」。**

## 七、我的笔记与理解

### 7.1 Load 冒险的「不可救药」在哪里

> **其他数据冒险都能转发，唯独 load 不行。**

**根本原因：`lw` 的数据「出现得最晚」。**

```
ALU 指令：  EX 阶段出结果（第 3 阶段）
load 指令： MEM 阶段出结果（第 4 阶段）  ← 晚一拍
```

**指令序列：**

```
        t1    t2    t3    t4    t5
lw     IF    ID    EX    MEM   WB
                      ↑
                  数据在这里才出来
or           IF    ID    EX    MEM
                            ↑
                        同一时刻要用了！
```

> ⭐ **「差 1 个周期就够，但硬件「不能时光倒流」。」**

**解法只有三个：**

| 解法 | 说明 |
|---|---|
| **① Stall（停顿）** | 硬件发 nop |
| **② Code scheduling** | 编译器填延迟槽 |
| **③ 更好的 ISA 设计** | MIPS 有「延迟槽」，RISC-V **取消了** |

> ⭐ **RISC-V 取消延迟槽是个重要决定：**
> **代码更简单（无隐藏语义），代价是硬件必须自己 stall。**

### 7.2 为什么 RISC-V 能取消延迟槽

**MIPS 时代（1980s）：**

> **「延迟槽」暴露了硬件细节给程序员 —— 你必须手动填 nop 或有用指令。**

**RISC-V（2010s）：**

> **硬件能高效 stall（1 周期），编译器也能调度。**
> **没必要再让 ISA 背这个包袱。**

| 对比 | MIPS | RISC-V |
|---|---|---|
| **load 延迟槽** | ✅ 有（可见）| ❌ 无 |
| **分支延迟槽** | ✅ 有 | ❌ 无 |
| **代码复杂度** | 高 | **低** |
| **硬件复杂度** | 低 | 略高 |

> ⭐ **「把复杂度从「程序员」转移到「硬件」」—— 这是现代 ISA 的趋势。**

### 7.3 分支的 3 周期代价从哪来

```
t=1  IF  beq
t=2  IF  sub（已取，但可能错）
t=3  IF  or （已取，但可能错）
t=4  IF  xor（已取，但可能错）
     ↑ 此时 MEM 阶段才知道分支结果
t=5  IF  正确指令（重新取）
```

**所以：**

| 阶段 | 已经「浪费」了几条 |
|---|---|
| **分支结果在 EX 知道** | 浪费 1 条 |
| **分支结果在 MEM 知道** | **浪费 3 条** ← 本课 |
| **分支结果在 ID 知道** | 浪费 0 条（但需要额外硬件）|

> ⭐ **「越早知道分支结果，代价越小。」**
> **这就是为什么真实 CPU 要「提前算分支」：
> - 专门的比较器在 ID 阶段就比
> - 分支预测器在 IF 阶段就猜**

### 7.4 分支预测的「悖论」

> **「预测错了还是罚 3 个周期 —— 那预测有什么意义？」**

**意义在「平均值」：**

| 策略 | 假设分支 t% |
|---|---|
| **不预测（总猜不成立）** | **惩罚 = t% × 3** |
| **完美预测** | 惩罚 = 0 |
| **1 位预测器（循环）** | 循环里只有「最后一次」错 |

**例子：for 循环 100 次**

| 策略 | 错误次数 | 惩罚 |
|---|---|---|
| **总猜不成立** | 100 次（每次都跳） | **300 周期** |
| **1 位预测器** | 2 次（进/出）| **6 周期** |

> ⭐ **「预测器不需要「总是对」—— 只要「大多数对」就够了。」**

### 7.5 `lw → lw → lw` 为什么能连发

> **三条 load 互不依赖 → 每条各自走自己的流水线阶段。**

**但注意：它们都要访问 DMEM！**

| 时刻 | IF | ID | EX | MEM |
|---|---|---|---|---|
| **t=3** | lw₃ | lw₂ | lw₁ | |
| **t=4** | | lw₃ | lw₂ | **lw₁** |
| **t=5** | | | lw₃ | **lw₂** |
| **t=6** | | | | **lw₃** |

> **同一时刻只有一条在 MEM 阶段 → DMEM 不冲突 ✅**

> ⭐ **这就是「结构冒险」不会出现的原因：五级流水线保证「每级每周期只有一条指令」。**

### 7.6 代码调度的「边界」

> **编译器能做的有限：**

| 能做 | 不能做 |
|---|---|
| **重排独立指令** | 跨越函数调用 |
| **填延迟槽** | 跨越分支（依赖分析难）|
| **展开循环（unroll）** | 跨越内存别名（alias）|

> ⭐ **「A[0] 和 A[3] 会不会是同一块内存？」—— 指针别名是编译器调度的最大障碍。**
> **这就是 C 的 `restrict` 关键字存在的原因。**

### 7.7 RISC-V 设计的「四原则」在这里全部兑现

| L25 结论 | 对应 L13–L15 的设计决策 |
|---|---|
| **① 32 位定长** | **I/R/S/B/U/J 六种格式，全部 4 字节** |
| **② 少量格式** | **六种格式，寄存器字段位置固定** |
| **③ load/store 简单寻址** | **只有 `rs1 + imm` 一种模式** |
| **④ 对齐访存** | **`lw` 要求 4 字节对齐** |

> ⭐ **「ISA 是为流水线设计的」—— 这不是巧合，是「刻意为之」。**

### 7.8 与后续的衔接

| 讲次 | 关系 |
|---|---|
