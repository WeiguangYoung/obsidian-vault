# CS61C FA26 · L24 Pipeline II: Hazards

> UC Berkeley · Great Ideas in Computer Architecture

## 一、⭐ Hazard 的定义

> **Hazard（冒险）：一种「计划中的指令无法在「正确的」时钟周期执行」的情况。**

### 1.1 三种类型的冒险

| # | 类型 | 定义 |
|---|---|---|
| **1** | **Structural hazard（结构冒险）** | **硬件不支持「同一周期内跨多条指令访问」** |
| **2** | **Data hazard（数据冒险）** | **指令间有数据依赖** |
| | | **需要等前一条指令完成读写** |
| **3** | **Control hazard（控制冒险）** | **执行流取决于前一条指令** |

> ⭐ **本讲：结构冒险 + 数据冒险（含 forwarding）**
> **L25：load 冒险 + 控制冒险**

## 二、⭐ 瀑布图（Waterfall Diagram）

> **流水线可视化工具：横轴时间（周期数），纵轴指令，每行画出 IF/ID/EX/MEM/WB。**

### 2.1 示例程序

```asm
add t0, t1, t2
lw  t0, 8(t3)
or  t3, t4, t5
sw  t0, 4(t3)
sll t6, t0, t3
```

**瀑布图：**

| 指令 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| **add** | IF | ID | EX | MEM | WB | | | | |
| **lw** | | IF | ID | EX | MEM | WB | | | |
| **or** | | | IF | ID | EX | MEM | WB | | |
| **sw** | | | | IF | ID | EX | MEM | WB | |
| **sll** | | | | | IF | ID | EX | MEM | WB |

### 2.2 ⭐ 这张图上暴露的三个问题

> **课件在瀑布图旁边直接标注：**

| 问题 | 对应冒险 |
|---|---|
| **「同一时钟周期能读两次内存吗？」** | **结构冒险** |
| **「如果 `or` 的 WB 还没执行，`sw` 的 EX 怎么拿到正确的 `t3` 值？？？」** | **数据冒险** |
| **「分支怎么工作？？？」** | **控制冒险** |

> ⭐ **三个问题 = 三种冒险。这就是本讲和 L25 的全部内容。**

## 三、⭐ 结构冒险（Structural Hazard）

### 3.1 定义再强调

> **「结构冒险是关于「硬件」的，不是关于「指令」的。」**

### 3.2 潜在结构冒险 A：RegFile 同时读写

> **如果 RegFile 硬件不支持「同时读写」：**

```
        ┌─────────┐
wdata ──┤         ├── rdata
  rs  ──┤  Reg[]  │        ⚠️ Hazard!!
RegWEn ─┤         │
        └─────────┘
         ↑ 同时发生
   inst4 写 / inst1 读
```

❌ **冲突！**

### 3.3 ✅ RV32I 的 RegFile 设计避免了它

> **「RV32I 要求的 RegFile 设计防止了这个结构冒险。」**

| 特性 | 说明 |
|---|---|
| **独立的端口（separate ports）** | 读口和写口物理分开 |
| **三路访问可同周期** | **2 读 + 1 写** |

```
        ┌─────────┐
wdata ──┤         │
  rd  ──┤         ├── rdata1
 rs1  ──┤  Reg[]  ├── rdata2
 rs2  ──┤         │
RegWEn ─┤         │
        └─────────┘
   全部可同时！
```

### 3.4 潜在结构冒险 B：IMEM 与 DMEM 共用

> **如果 IMEM 和 DMEM 是同一块硬件：**

```
        ┌─────────┐
addr ───┤         ├── inst
        │  MEM    │
        │         ├── rdata
wdata ──┤         │
MemRW ──┤         │
        └─────────┘
     ↑ inst2 要取指，inst5 要读数据 → 冲突！
```

> **「没有独立内存的话，`inst2` 或 `inst5` 之一必须停一个周期。」**

### 3.5 ✅ RV32I 的两块独立内存

> **「RV32I 要求 IMEM、DMEM 作为独立内存，这防止了结构冒险。」**

> ⭐ **「记住：IMEM、DMEM 是两块 L1 缓存！」**

```
   ┌──────┐        ┌──────┐
   │IMEM  │        │DMEM  │
   │(L1i) │        │(L1d) │
   └──────┘        └──────┘
    取指独立        访存独立
```

### 3.6 ⭐ 结论

> **「在我们当前的 CPU 里，结构冒险不是问题。**
> **我们对 RegFile 和 Memory 的硬件要求已经满足：**
> - **RegFile 支持同时读写**
> - **IMEM、DMEM 是独立（缓存）的」**

**两种潜在结构冒险：**

| 冒险 | 何时发生 | RV32I 的解法 |
|---|---|---|
| **RegFile 同时访问** | `inst4`（写）+ `inst1`（读）| **独立端口** |
| **内存同时访问** | `inst5`（读数据）+ `inst2`（取指）| **IMEM/DMEM 分离** |

## 四、⭐ 四类解决方案（本讲总纲）

> **课件用 🌟 标出的四条路：**

| # | 方案 | 效率 |
|---|---|---|
| **1** | **规定硬件要求（specifying HW requirements）** | ✅ 最好（如果可行）|
| **2** | **Stalling（停顿）** | ❌ **低效 —— 指令被延迟，性能受损** |
| **3** | **Forwarding（转发/旁路）** | ✅ **高效：用「算出来但还没写回」的值** |
| **4** | **Code scheduling（代码调度）** | ✅ **编译器重排指令** |

> ⭐ **「我们想尽可能避免 stalling……！」**

## 五、⭐ 数据冒险 #1：需要等三拍

### 5.1 示例

```asm
add s0, t0, t1
sub t2, s0, t0
```

**瀑布图：**

| 指令 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| **add** | IF | ID | EX | MEM | **WB** | | |
| **sub** | | IF | **ID** | EX | MEM | WB | |
| | | | **↑ 读 s0 时** | **↑ add 才写 s0** | | | |

### 5.2 ⭐ 问题

> **`t=3`：`sub` 在 ID 阶段读 `s0`。**
> **`t=5`：`add` 才在 WB 阶段写 `s0`。**

> **「读到的是「陈旧的值（stale value）」！」**

### 5.3 时间线

```
t=3  sub 读 s0  →  旧值 ❌
...
t=5  add 写 s0  →  新值（太晚了）
```

## 六、⭐ 数据冒险 #2：RegFile 的「写后读」

### 6.1 示例

```asm
add t0, t1, t2
lw  t7, 8(t3)
or  t3, t4, t5
sw  t0, 4(t6)      ← 读 t0
sll t6, t0, t3     ← 读 t0
```

### 6.2 时序

| 指令 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| **add** | IF | ID | EX | MEM | **WB** |
| **lw** | | IF | ID | EX | MEM |
| **or** | | | IF | ID | EX |
| **sw** | | | | IF | **ID** |
| **sll** | | | | | IF |

> **`t=5`：`add` 写 `t0`（WB），同时 `sw` 读 `t0`（ID）。**

### 6.3 ⭐ 关键问题：同一周期能「先写后读」吗？

> **「如果 RegFile 写在「下一个周期」发生（t=6），那就有数据冒险！（这是我们当前的实现）」**

> **「但如果我们要求 RegFile 硬件「同周期内先写后读（write-then-read）」呢？」**

---

## 七、⭐ 提高 RegFile 硬件要求

### 7.1 要求：同周期内 write-then-read

> **「要求 RegFile 硬件在同一周期内「先写后读（write-then-read）」。**
> **这利用了 RegFile 的高速（100 ps + 100 ps 而非 100 ps + 100 ps 的两个独立周期）。」**

| 机制 | 说明 |
|---|---|
| **写** | 在周期前半段完成 |
| **读** | 是组合逻辑（CL），写稳定后立刻拿到数据 |
| **总时间** | **写 + 读 ≤ 一个周期** |

> **瀑布图里用「阴影（shading）」标记这种情况。**

### 7.2 ⚠️ 重要警告

> **「在某些设计中，例如「高频率」设计，这种 RegFile 设计可能做不到。」**

> ⭐ **「永远检查题目的假设！！！」**

### 7.3 ✅ 如果满足 write-then-read

**案例 #2：**

```
t=5 前半：add 写 t0
t=5 后半：sw 读 t0
→ 拿到新值 ✅ 无冒险
```

**案例 #1：**

```
t=5 前半：add 写 s0
t=5 后半：sub 读 s0
→ 拿到新值 ✅
```

> **但等等 —— 案例 #1 的 `sub` 在 `t=3` 就读了，不是 `t=5`！**
> **所以案例 #1 仍然需要 stall。**

### 7.4 ⭐ 两个案例的对比

| 案例 | 情况 | write-then-read 能解决吗 |
|---|---|---|
| **#2** | **`add` WB 和 `sw` ID 都是 `t=5`** | ✅ **能！** |
| **#1** | **`sub` 在 `t=3` 读，`add` 在 `t=5` 写** | ❌ **差 2 个周期，必须 stall** |

## 八、⭐ Stalling（停顿）

### 8.1 案例 #1 的 stalled 版本

```asm
add s0, t0, t1
nop               ← 插入
nop               ← 插入
sub t2, s0, t0
```

**瀑布图：**

| 指令 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| **add** | IF | ID | EX | MEM | WB | | | | |
| **nop** | | IF | ID | EX | MEM | WB | | | |
| **nop** | | | IF | ID | EX | MEM | WB | | |
| **sub** | | | | IF | ID | EX | MEM | WB | |

> **现在 `sub` 在 `t=5` 读 `s0`，正好赶上 `add` 的 WB（write-then-read）→ ✅**

### 8.2 三拍还是两拍？

> **课件：「对于 #1，停三个周期」**
> **但 write-then-read 版本只要停两个周期。**

**对照：**

| 前提 | 需要 stall | 说明 |
|---|---|---|
| **写发生在「下一周期」** | **3 个** | 最保守 |
| **write-then-read** | **2 个** | ✅ 本课实现 |
| **+ forwarding** | **0 个** | ✅✅ 后面讲 |

> ⚠️ **课件第 14 页展示「stall three cycles」，第 18 页展示「stall two cycles」（带 write-then-read 假设）。**
> **这就是「永远检查题目假设」的含义。**

### 8.3 ⚠️ Stalling 的代价

> **「需要额外的流水线状态，来防止被停住的阶段发生「非预期的状态改变」（例如寄存器/内存写）。」**

**必须做的事：**

| 动作 | 说明 |
|---|---|
| **① 冻结 PC** | 不能继续取新指令 |
| **② 冻结 IF/ID 寄存器** | 重复执行同一条指令 |
| **③ 插入气泡（bubble）** | 往下游发 nop |
| **④ 阻止写** | `RegWEn=0`、`MemRW=Read` |

### 8.4 编译器也能做这件事

> **「编译器可以重排代码/插入 nop 来避免冒险（从而避免停顿），但这需要了解流水线结构。」**

> ⭐ **这是 §十「代码调度」的伏笔。**

## 九、⭐ Forwarding（转发/旁路）

### 9.1 ⭐ 核心洞察

> **「我们真的需要在「WB 阶段」才有正确的值吗？」**

```asm
add s0, t0, t1
sub t2, s0, t0
or  t6, s0, t3
```

**瀑布图：**

| 指令 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| **add** | IF | ID | EX | **MEM** | WB | | |
| **sub** | | IF | ID | **EX** | MEM | WB | |
| **or** | | | IF | ID | **EX** | MEM | WB |

### 9.2 ⭐ 关键观察

> **「停顿时我们的假设是：`sub`、`or` 在 ID 阶段读到旧的 `s0`，在 EX 算错。」**
> **「但我们真正需要的正确值，只在 `sub`、`or` 的「EX 阶段」（给 ALU 用）……」**

**时间点：**

```
t=4: add 的结果在 MEM 阶段（已经算出来了！）
t=4: sub 进入 EX 阶段（正要算）
     ↑ 这两个是同一个周期！
```

> ⭐ **「不用等值写进 RegFile。直接从流水线阶段「抓」操作数。」**

### 9.3 实现

> **「在 datapath 里加额外连线。同时加 forwarding 控制逻辑。」**

```
        EX/MEM 寄存器
            │ ALUOut
            ▼
       ┌────────┐
   ┌──►│  0 1 2 │──► ALU 的 A 输入
   │   └────────┘
   │      ▲
   │      │ 转发自 EX/MEM 或 MEM/WB
   │
RegRead
Data1
```

> **「在阶段开始时，把 EX/MEM 流水线寄存器（`ALUOut`）接到 ALU mux 的输入。」**

### 9.4 ⭐ 名称：MEM→EX forwarding

> **课件用了这个容易混淆的标题：**
> **「EX → EX..? 不，实际上是 MEM → EX」**

**为什么？**

| 视角 | 说法 |
|---|---|
| **按「数据流经的阶段」** | **EX/MEM 寄存器 → EX 阶段**（所以叫 MEM→EX）|
| **按「产生/消费的指令」** | 前一条的 MEM 阶段 → 后一条的 EX 阶段 |

> ⭐ **记住：数据从「EX/MEM 流水线寄存器」流向「ALU 输入 MUX」。**
> **因为 `add` 在 `t=4` 时，结果已经在 EX/MEM 寄存器里了（MEM 阶段的开始）。**

### 9.5 两条转发路径

> **「两条转发路径」：**

| 路径 | 从 | 到 | 覆盖的间隔 |
|---|---|---|---|
| **① EX/MEM → EX** | **前一条的 `ALUOut`** | **当前条 ALU 输入** | **相隔 1 条** |
| **② MEM/WB → EX** | **前两条的 `ALUOut`/`rdata`** | **当前条 ALU 输入** | **相隔 2 条** |

```
指令序列：  add  →  sub  →  or
             │       │       │
             │       │       └─ 从 MEM/WB 转发
             │       └────────── 从 EX/MEM 转发
             └───────────────────（自己的 EX）
```

> ⭐ **两条路径覆盖「相隔 1 条」和「相隔 2 条」两种情况。**
> **相隔 3 条以上就由 RegFile 的正常读解决了。**

### 9.6 转发需要什么

| 需求 | 说明 |
|---|---|
| **额外连线** | EX/MEM 和 MEM/WB 的 ALUOut 引到 EX 的 MUX |
| **ALU 输入扩成 3 路 MUX** | 0 = RegReadData1；1 = EX/MEM；2 = MEM/WB |
| **Forwarding Control Logic** | **判断「当前指令的 rs1/rs2」是否等于「前 1~2 条的 rd」** |
| **比较寄存器号** | `EX/MEM.rd == ID/EX.rs1` 等 |

**控制逻辑的核心判定：**

```
if (EX/MEM.RegWEn && EX/MEM.rd == ID/EX.rs1)  → A 选 EX/MEM
if (MEM/WB.RegWEn && MEM/WB.rd == ID/EX.rs1)  → A 选 MEM/WB
（rs2 同理，控制 B）
```

> ⚠️ **必须检查 `RegWEn`！否则 `sw`/`beq` 的 `rd` 字段（无意义）会造成误转发。**

## 十、我的笔记与理解

### 10.1 三种冒险的「责任归属」

| 冒险 | 谁的问题 | 谁来解决 |
|---|---|---|
| **结构冒险** | **硬件设计** | **ISA 规定硬件要求** |
| **数据冒险** | **指令序列** | **硬件（forwarding）+ 编译器（调度）** |
| **控制冒险** | **指令序列** | **硬件（预测）+ 编译器（延迟槽）** |

> ⭐ **「结构冒险是关于硬件的，不是关于指令的」（课件原话）——**
> **这句话划清了「架构设计」与「程序正确性」的边界。**

### 10.2 「write-then-read」是一个「免费的午餐」吗

> **表面看：同一个周期内先写后读，不需要额外周期。**

**但代价是：**

| 代价 | 说明 |
|---|---|
| **周期必须 ≥ 写延迟 + 读延迟** | 不能无限提高频率 |
| **寄存器文件设计复杂** | 需要特殊时序控制 |
| **高频 CPU 做不到** | 课件明确警告 |

> ⭐ **「永远检查题目的假设」—— 这句话是硬件题的第一原则。**
> **同一个瀑布图，假设不同，答案完全不同。**

### 10.3 Forwarding 的本质：**把「存储」变成「传递」**

```
无转发：EX → MEM → WB → RegFile → ID → EX     （绕一大圈）
有转发：EX → (EX/MEM) ──────────────→ EX      （抄近路）
```

> ⭐ **数据在「寄存器堆」里「存一下」是为了让后续任意指令能读。**
> **但如果紧接着就有指令要用，那「存」这一步是浪费 —— 直接递过去更快。**

**类比：**
> **你在厨房做好菜，先放冰箱（RegFile），再拿出来吃。**
> **如果客人就在旁边等，直接从锅里盛给他 —— 这就是 forwarding。**

### 10.4 为什么只需要两条转发路径

> **关键：RegFile 的读在 ID 阶段，而写在前一条的 WB。**

```
指令 i   : ... EX  MEM  WB
指令 i+1 :        ID   EX  MEM  WB
指令 i+2 :             ID   EX   MEM  WB
指令 i+3 :                  ID   EX    ...
```

**分析指令 i+3 的 EX 阶段（`t`）：**

| 前序指令 | 在 `t` 时刻的位置 | 能否转发 |
|---|---|---|
| **i+2** | **MEM 阶段（结果在 EX/MEM 寄存器）** | ✅ 路径 ① |
| **i+1** | **WB 阶段（结果在 MEM/WB 寄存器）** | ✅ 路径 ② |
| **i** | **已完成 WB（结果已在 RegFile）** | ✅ RegFile 正常读 |

> ⭐ **「相隔 3 条以上，值已经写进 RegFile —— ID 阶段读到的就是新值。」**

### 10.5 Forwarding 的代价

| 代价 | 说明 |
|---|---|
| **更多连线** | 长距离布线，可能影响时序 |
| **更大的 MUX** | ALU 输入从 2 路变 3 路 |
| **控制逻辑复杂** | 需要比较寄存器号 |
| **可能的时序问题** | 转发路径可能成为关键路径 |

> **但相比「停顿 2 个周期」，这个代价小得多。**

### 10.6 Stalling 的「隐藏成本」

> **课件提到：「需要额外的流水线状态，来防止被停住的阶段发生非预期的状态改变。」**

**这点很容易被忽略！**

```
停顿期间：
  - PC 必须冻结（否则取下一条）
  - IF/ID 必须冻结（否则指令丢失）
  - ID/EX 必须清空（发气泡，否则重复执行）
  - RegWEn 必须强制 0（否则重复写）
  - MemRW 必须强制 Read（否则重复写内存）
```

> ⭐ **「停顿不是「什么都不做」—— 而是「精确地做一部分、冻结一部分、清空一部分」。**
> **这是流水线控制最复杂的部分。**

### 10.7 数据冒险 #2 是「假冒险」

> **`add` 在 `t=5` 的 WB 写 `t0`，`sw` 在 `t=5` 的 ID 读 `t0`。**

> **如果硬件支持 write-then-read，这根本不是冒险。**

> ⭐ **这提醒我们：冒险的判定「依赖于硬件实现」 ——**
> **同一个指令序列，在不同 CPU 上可能有也可能没有冒险。**
