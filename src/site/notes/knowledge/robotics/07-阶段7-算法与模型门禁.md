# 🧠 阶段 7 实战：算法与模型性能门禁

## 摘要

车载 CI 的门禁只管**代码质量**——编译过没过、MISRA 有没有违规、覆盖率够不够。

机器人 CI 多一层：**模型本身会退化**。代码一行没改，换个模型文件精度就掉了；或者新模型精度涨了但延迟翻倍，实时性崩了。

本文实现了一套**相对基线的模型性能门禁**：固定测试集跑推理 → 采集延迟/吞吐/签名 → 与 baseline 比对 → 退化超阈值则阻断。**实测通过，两条路径（通过/阻断）都验证过。**

**2026-11-08 补充**：初版只有性能门禁，缺精度维度。补齐后门禁从 6 项扩展到 9 项：
性能 6 项（延迟 / P95 / 吞吐 / 体积 / 输入签名 / 输出签名）+ 精度 3 项（整体准确率 / 每类召回 / 混淆矩阵）。
实测基线 **98.3%**，CI 跑出 **98.5%**。

**核心认知**：算法门禁与代码门禁的本质区别是——

| | 代码门禁 | 模型门禁 |
|---|---|---|
| 判据 | **绝对**（0 违规） | **相对**（不比基线差 X%） |
| 基准 | 静态规则集 | 历史最好成绩 |
| 失败含义 | 新代码有问题 | **模型变差了** |

## 一、为什么模型需要单独的门禁

### 场景 1：精度退化

```
周二：yolov8n.onnx  mAP=0.42    ← baseline
周三：yolov8s.onnx  mAP=0.38    ← 换了个"更大"的模型，反而掉了
```

代码 diff 里只有一个二进制文件变化，**代码审查看不出来**。

### 场景 2：性能退化（更隐蔽）

```
周二：2.1ms   ← baseline
周三：5.8ms   ← 精度涨了 3%，延迟涨了 176%
```

**精度指标看起来更好，但实时性已经崩了**。机器人 20Hz 控制循环撑不住。

### 场景 3：接口破坏

```
输入 [1,3,224,224] → [1,3,640,640]
```

模型换了输入尺寸，下游预处理代码没改，**运行时才崩**。

**这三种，代码门禁一个都拦不住。**

## 三、评测脚本

### 3.1 采集哪些指标

| 指标 | 为什么重要 |
|---|---|
| **mean 延迟** | 平均性能 |
| **p95 / p99 延迟** | 长尾——机器人最怕偶发卡顿 |
| **吞吐 fps** | 能不能撑住控制频率 |
| **模型体积** | 端侧部署的 Flash / 内存约束 |
| **输入/输出签名** | 接口兼容性 |

**为什么 p95 比 mean 更重要**：平均 2ms 但 p99 是 50ms 的模型，在实时系统里是灾难——100 帧里有 1 帧卡死就够让控制环丢拍。

### 3.2 实现要点

```python
def evaluate(model_path, iterations=100, warmup=10):
    sess = ort.InferenceSession(model_path, providers=['CPUExecutionProvider'])
    input_name, x = build_input(sess)
    output_names = [o.name for o in sess.get_outputs()]

    # 预热（第一次推理会加载/优化，不预热数据会失真）
    for _ in range(warmup):
        sess.run(output_names, {input_name: x})

    latencies = []
    for _ in range(iterations):
        t0 = time.perf_counter()
        sess.run(output_names, {input_name: x})
        latencies.append((time.perf_counter() - t0) * 1000.0)

    arr = np.array(latencies)
    return {
        'latency_ms': {
            'mean': round(float(arr.mean()), 3),
            'p50':  round(float(np.percentile(arr, 50)), 3),
            'p95':  round(float(np.percentile(arr, 95)), 3),
            'p99':  round(float(np.percentile(arr, 99)), 3),
        },
        'throughput_fps': round(1000.0 / float(arr.mean()), 1),
        'input_shape': list(x.shape),
        'model_size_bytes': Path(model_path).stat().st_size,
    }
```

**warmup 不能省**：第一次推理包含 ONNX Runtime 的图优化，比后续慢 10 倍，混进去会污染 mean。

### 3.3 实测数据

| 模型 | 大小 | mean | p95 | 吞吐 |
|---|---|---|---|---|
| **MNIST**（小型 CNN） | 25.5 KB | **0.045 ms** | 0.051 ms | **22308 fps** |
| **SqueezeNet**（中型 CNN） | 4836 KB | **2.080 ms** | 2.085 ms | **481 fps** |

环境：x86_64, ONNX Runtime 1.23.2, CPU ExecutionProvider

## 四、门禁脚本

### 4.1 六项检查

```python
checks = [
    ('平均延迟',  cur <= base * 1.20),   # 涨幅上限 20%
    ('P95 延迟',  cur <= base * 1.30),   # 长尾上限 30%
    ('吞吐量',    cur >= base * 0.80),   # 保留至少 80%
    ('模型体积',  cur <= base * 1.50),   # 涨幅上限 50%
    ('输入签名',  cur == base),           # 必须完全一致
    ('输出签名',  cur == base),           # 必须完全一致
]
```

### 4.2 为什么阈值是"相对"的

**不能要求绝对指标**，因为：
- 不同机器性能差异巨大（开发机 vs CI runner vs 目标板）
- 框架版本升级会带来整体性能漂移
- 只有"相对自己历史"才有意义

```python
# 错：绑定绝对数值
assert latency < 3.0    # 换了台弱一点的机器就全挂

# 对：相对基线
assert latency <= baseline * 1.20
```

### 4.3 输出格式

```
============================================================
模型性能门禁
============================================================
基线: baseline_squeezenet.json
当前: baseline_squeezenet.json
------------------------------------------------------------
[PASS] 平均延迟: 2.080ms vs 基线 2.080ms (1.00x, 上限 1.2x)
[PASS] P95 延迟: 2.085ms vs 基线 2.085ms (1.00x, 上限 1.3x)
[PASS] 吞吐量: 480.9 fps vs 基线 480.9 fps (1.00x, 下限 0.8x)
[PASS] 模型体积: 4836.9KB vs 基线 4836.9KB (1.00x, 上限 1.5x)
[PASS] 输入签名: [1, 3, 224, 224] vs [1, 3, 224, 224]
[PASS] 输出签名: [1, 1000, 1, 1] vs [1, 1000, 1, 1]
------------------------------------------------------------
结果: 通过
```

## 四·补、精度门禁（2026-11-08 补充）

> **背景**：本文初版（11:16）只做了性能门禁——延迟、吞吐、体积、签名。**没有精度维度**。
> 性能好不等于模型对：一个 100% 输出同一类的模型，延迟可以极低。11:59 补齐了精度门禁。

### 4.1 为什么必须补精度

| 门禁 | 能发现什么 | 漏掉什么 |
|---|---|---|
| 性能（初版） | 变慢、变大、接口变了 | **判错了却很快** |
| 精度（补充） | 判错、某类退化 | 变慢、变大 |

**极端例子**：把模型换成「永远输出 0」，延迟 0.001ms、体积 1KB、签名完全一致——**性能门禁全过，但它什么都不会认**。

### 4.2 评测脚本

```python
def evaluate(model_path, testdir):
    sess = ort.InferenceSession(model_path, providers=['CPUExecutionProvider'])
    labels = json.loads((Path(testdir) / "labels.json").read_text())

    y_true, y_pred = [], []
    for item in labels:
        img = np.load(Path(testdir) / item["file"])
        x = normalize_to_model(img, spec.shape)
        out = sess.run(out_names, {spec.name: x})[0]
        y_pred.append(int(np.array(out).reshape(-1).argmax()))
        y_true.append(int(item["label"]))

    acc = (y_true == y_pred).mean()
    return {
        "accuracy": round(acc, 4),
        "per_class": {...},        # 每类召回率
        "confusion_matrix": cm.tolist(),
    }
```

**产出三个维度**：整体准确率、每类召回率、混淆矩阵。

### 4.3 数据集：从哪来

实测下载源对比：

| 源 | 结果 |
|---|---|
| **`ossci-datasets.s3.amazonaws.com/mnist/`** | ✅ **可用**，1.6MB，国内直连 |
| `github.com/onnx/models` | ✅ 可用（模型文件） |
| `huggingface.co` | ❌ 超时 |
| `hf-mirror.com` | ❌ 404 |
| GitHub ultralytics releases | ❌ 404 |

**MNIST idx 格式转换**：

```python
def read_images(path):
    with gzip.open(path, "rb") as f:
        magic, n, rows, cols = struct.unpack(">IIII", f.read(16))
        assert magic == 2051
        data = np.frombuffer(f.read(), dtype=np.uint8)
    return data.reshape(n, rows, cols)
```

**采样策略**：每类均匀取 N 张，保证类别平衡（不平衡会让准确率失真）。

### 4.4 两组数据

| 用途 | 样本数 | 每类 | 准确率 |
|---|---|---|---|
| **基线** | 1000 | 100 | **98.3%** |
| **CI 测试** | 200 | 20 | **98.5%** |

**基线每类召回率**：

```
0: 100.0%   1: 99.0%   2: 99.0%   3: 99.0%   4: 98.0%
5: 100.0%   6: 98.0%   7: 98.0%   8: 95.0%   9: 97.0%
```

> 类别 8 最差（95%），是 MNIST 的经典难点。

### 4.5 阈值设计（这里踩过坑）

#### 坑：单类阈值拍脑袋

**现象**：
```
[PASS] 准确率: 98.5% vs 基线 98.3% (下降 -0.2pp, 允许 2.0pp)
[FAIL] 单类退化过大: 类别 9 97.0% -> 90.0%
结果: 阻断
```

整体准确率完全正常，却被单类检查阻断。

**根因**：CI 测试集每类只有 **20 张**。掉 2 张 = 10% 的召回率下降。原阈值固定 6pp，但 20 张样本的 ±10% 波动是纯噪声。

**修正**：阈值与样本量挂钩。

```python
support = max(d.get("support", 1), 1)
min_tol = 2.0 / support          # 20 张 -> 10%
if drop_c > max(max_drop * 3, min_tol):
    fail()
```

> **教训**：**任何比率阈值都要问「分母多大」**。1/5 和 1/1000 都是 20%，但意义完全不同。

## 七、CI 集成

```yaml
model_eval:
  stage: test
  image: ros2-ci:humble-base
  rules:
    - changes: ["models/**", "eval/**"]     # 模型变了才跑
  script:
    - pip3 install onnxruntime

      - current.json
```

### 关键点

| 项 | 说明 |
|---|---|
| **`rules: changes`** | 只在模型/评测代码变更时触发，避免每次提交都跑 |
| **`when: always` 归档** | 失败时的指标 JSON 最有价值 |
| **baseline 要进仓库** | 它是版本的一部分，不能只存在本地 |
| **更新 baseline 要评审** | 否则有人"悄悄放宽标准" |

## 八、坑点

### 8.1 不预热会污染数据

第一次推理比后续慢 **10 倍**（ONNX Runtime 要做图优化）。必须 warmup。

```python
for _ in range(10):   # 这 10 次不计入
    sess.run(...)
```

### 8.2 `exit=0` 可能是 grep 的退出码

```bash
# 错：这样测不出节点真实退出码
ros2 run hello_robot model_gate ... | grep PASS
echo $?     # 这 $? 是 grep 的！

# 对：用 PIPESTATUS
ros2 run hello_robot model_gate ... | grep PASS
echo ${PIPESTATUS[0]}    # 这才是节点退出码
```

**CI 里尤其要小心**——用错会导致门禁"假绿"。

### 8.3 模型源不可用

实测发现：

| 源 | 结果 |
|---|---|
| GitHub ultralytics releases | 404 |
| huggingface.co | 超时 |
| hf-mirror.com | 404 |
| **github.com/onnx/models** | **可用** |

**备选策略**：用 ONNX 官方模型库，里面有 MNIST、SqueezeNet、ResNet 等。

### 8.4 不同机器的绝对值不可比

开发机 2.08ms，CI runner 可能 3.5ms，目标板可能 15ms。

**所以 baseline 必须在同一环境下采集**。跨环境比对只能看相对变化，或者用归一化指标。

---

### 坑 5：单类阈值拍脑袋（补精度时踩的）

**现象**：整体准确率 98.5%（通过），但单类召回检查阻断。

**根因**：CI 测试集每类 20 张，掉 2 张 = 10%。原阈值固定 6pp，20 张样本的 ±10% 是纯噪声。

**解法**：`min_tol = 2.0 / support`，至少允许 2 个样本的偏差。

> **教训**：比率类阈值必须问「分母多大」。

### 坑 6：精度门禁需要模型文件进仓库

**现象**：CI 里报 `NoSuchFile: Load model ... failed`。

**根因**：`.gitignore` 里 `*.onnx` 把 CI 需要的模型也忽略了。

**解法**：
```gitignore
*.onnx
!models/*.onnx
```

> **教训**：本地能跑不代表 CI 能找到——gitignore 的错误本地完全复现不出来。

## 九、扩展方向

| 方向 | 做法 |
|---|---|
| **精度门禁** | 固定测试集 + 标注，算 mAP / 准确率，不只看延迟 |
| **GPU 评测** | `providers=['CUDAExecutionProvider']`，对比 CPU vs GPU |
| **量化对比** | FP32 vs INT8 的精度-速度权衡 |
| **端侧评测** | 在 Jetson/RK3588 上跑，指标更真实 |
| **模型版本追踪** | 每次评测结果存档，画出趋势曲线 |

## 十、面试可以怎么讲

> "车载 CI 的门禁只管代码质量——编译、MISRA、覆盖率。但机器人的模型是二进制文件，代码没改、模型换了，性能可能就崩了。
>
> 我做了个模型性能门禁：固定输入跑 ONNX 推理，采集平均延迟、P95 延迟、吞吐、模型体积、输入输出签名，和 baseline 比对。延迟涨幅超 20%、P95 超 30%、吞吐掉到 80% 以下，或者签名不一致，就阻断合并。
>
> 关键是**判据必须是相对的**——不能要求绝对 3ms，因为开发机、CI runner、目标板性能差好几倍。只有'不比历史基线差太多'才有意义。
>
> 我还特意测了失败路径：构造一个延迟涨 40% 的模型，门禁正确阻断；再拿一个完全不同的小模型对比，性能全面'变好'但签名不匹配，也被拦住。**性能变好不等于模型对**，签名是最后一道防线。"
>
> 后来我发现只有性能门禁不够——一个永远输出同一类的模型，延迟可以极低。所以补了精度门禁：真实 MNIST 1000 张做基线 98.3%，CI 跑 200 张实测 98.5%。这里踩了个坑：单类召回率用固定 6pp 阈值会误判，因为每类只有 20 张，掉 2 张就是 10%。改成阈值随样本量动态才对。"
