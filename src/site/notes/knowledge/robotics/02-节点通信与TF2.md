# # 🤖 ROS 2 阶段一实战：节点通信、参数、launch 与 TF2

## 摘要

按 [00-机器人入门路线](00-机器人入门路线.md) 阶段 1 完成第一个可运行的工作区：一个 `hello_robot` 包，内含 talker/listener 双向通信 + 参数化 + launch 编排 + 差速车 URDF + TF2 变换树。所有验证均在本机实测通过。

**关键认知**：ROS 2 的学习不是背 API，而是建立一个可验证的数据流闭环。本文每个小节都配「怎么证明它真的通了」。

## 一、工作区结构

```
~/ros2_ws/
├── src/hello_robot/
│   ├── hello_robot/
│   │   ├── status_talker.py      # 发布 /robot_status（JSON）
│   │   └── status_listener.py    # 订阅 + 发布 /robot_alert
│   ├── launch/
│   │   ├── status.launch.py      # 双节点编排 + 参数
│   │   ├── display.launch.py     # URDF + RViz 可视化
│   │   └── verify_tf.launch.py   # 无 GUI 环境验证 TF
│   ├── urdf/diffbot.urdf         # 差速车模型
│   ├── rviz/diffbot.rviz         # RViz 配置
│   ├── setup.py
│   └── package.xml
├── build/  install/  log/
```

**四目录职责**：

| 目录 | 内容 | 能否删 |
|---|---|---|
| `src/` | 源码（唯一需要版本控制的） | ❌ |
| `build/` | CMake/中间产物 | ✅ 删了重编 |
| `install/` | 安装后的可运行产物 + setup.bash | ✅ 删了重编 |
| `log/` | colcon 构建日志 | ✅ 随时删 |

## 二、节点通信（Topic）

### 2.1 设计：两级数据流

```
status_talker ──/robot_status(JSON)──> status_listener ──/robot_alert──> (告警消费者)
```

**为什么这样设计**：不是为了演示 API，而是模拟真实机器人的「状态上报 → 业务判断 → 告警」链路。这是 CI 里仿真回归最常断的一环。

### 2.2 talker 要点

```python
self.declare_parameter('rate_hz', 1.0)
rate = self.get_parameter('rate_hz').value
self.pub = self.create_publisher(String, 'robot_status', 10)
self.timer = self.create_timer(1.0 / rate, self.tick)
```

- **参数优先于硬编码**：频率必须可被 launch 覆盖，否则进 CI 改不动
- **`create_timer` 而非 `while + sleep`**：ROS 2 的 timer 由 executor 调度，不会阻塞回调
- **队列深度 10**：订阅者处理慢时会丢旧消息，这是有意的（状态类数据要新不要全）

### 2.3 listener 要点

```python
if d['battery'] < self.threshold:
    alert = String()
    alert.data = f"LOW_BATTERY seq={d['seq']} {d['battery']}V"
    self.alert_pub.publish(alert)
```

**实测输出**：

```
[talker]: publish #1: {"seq": 1, "robot": "demo_bot", "battery": 3.52, "x": 0.1}
[listener]: #1 demo_bot x=0.1m batt=3.52V
[listener]: [WARN] LOW_BATTERY seq=1 3.52V
```

双向通信 + 业务判断 + 二次发布，一条链路全打通。

## 三、参数（Parameter）

```bash
# 运行时查看
ros2 param list /talker
# 运行时改（立即生效，不重启）
ros2 param set /talker rate_hz 5.0
# 从 launch 传入（推荐，进 CI 只改 launch 参数）
ros2 launch hello_robot status.launch.py rate_hz:=5.0 robot_name:=agv_01
```

**三种传参方式对比**：

| 方式 | 场景 | 优先级 |
|---|---|---|
| 代码 `declare_parameter` 默认值 | 兜底 | 最低 |
| launch `parameters=[{...}]` | 部署/CI | 中 |
| launch `LaunchConfiguration` + 命令行 `:=` | 临时覆盖 | 最高 |

> **坑**：use `declare_parameter` 而不是 `get_parameter` 直接读，否则找不到键会抛异常。

## 四、Launch 编排

```python
DeclareLaunchArgument('rate_hz', default_value='2.0'),
Node(package='hello_robot', executable='status_talker',
     parameters=[{'rate_hz': 2.0, 'robot_name': robot}]),
```

**实测**：`ros2 node list` 显示 `/talker` `/listener`，`ros2 topic hz /robot_status` 显示稳定 2 Hz。

**坑**：改完 launch 文件必须 `colcon build` 才生效——launch 目录是**安装**过去的，不是符号链接。报错形式：

```
file 'xxx.launch.py' was not found in the share directory of package
```

## 五、URDF 与 TF2

### 5.1 差速车模型结构

```
base_footprint            ← 地面投影（TF 树的根，代表"车在地面的位置"）
  └── base_joint (fixed, z=0.06)
        └── base_link     ← 车体中心
              ├── wheel_left_joint  (continuous, 绕 y 轴)
              ├── wheel_right_joint (continuous, 绕 y 轴)
              ├── caster_joint      (fixed, 万向轮)
              └── laser_joint       (fixed, 雷达)
```

**为什么必须有 `base_footprint`**：`base_link` 在车体中心（离地 6cm），但导航/建图算法需要"车在地面的投影点"。没有 `base_footprint`，SLAM 和 Nav2 的坐标系链条会断。这是新手最常漏的一个 link。

### 5.2 关键参数

```xml
<joint name="wheel_left_joint" type="continuous">
  <origin xyz="0 0.16 0.0"/>      <!-- 左右轮各偏 16cm -->
  <axis xyz="0 1 0"/>              <!-- 绕 y 轴转（ROS 约定 y 向左） -->
  <limit effort="10" velocity="20"/>
</joint>
```

**`continuous` 与 `revolute` 的区别**：revolute 有角度上下限（机械臂关节），continuous 无限制（车轮）。用错会导致 Gazebo 里车轮转到某个角度就卡住。

### 5.3 验证方法（三个层次）

```bash
# 层次 1：XML 合法性（不启动任何节点）
check_urdf diffbot.urdf
# → Successfully Parsed XML / root Link: base_footprint has 1 child(ren)

# 层次 2：TF 树是否真的发布出来
ros2 launch hello_robot verify_tf.launch.py
ros2 run tf2_ros tf2_echo base_footprint laser

# 层次 3：可视化（有 GUI 时）
ros2 launch hello_robot display.launch.py
ros2 run tf2_tools view_frames   # 生成 frames.pdf
```

**实测（层次 2）**：`robot_state_publisher` 日志输出 6 个 segment：

```
got segment base_footprint
got segment base_link
got segment caster
got segment laser
got segment wheel_left
got segment wheel_right
```

说明 URDF 被正确解析成 TF 变换树。

## 六、坑点记录

### 6.1 命令行传 URDF 会被截断

```bash
# ❌ 失败
ros2 run robot_state_publisher robot_state_publisher \
  --ros-args -p robot_description:"$(cat diffbot.urdf)"
# → [ERROR] argument parsing failed, at ./src/rcl/arguments.c:343
```

**原因**：URDF 里的 `"`、`<`、换行在命令行参数解析阶段被处理，超长单参数也会超限。

**正确做法**：在 launch 文件里 `open()` 读文件内容塞进 parameters，绕开命令行解析。

### 6.2 `joint_state_publisher_gui` 不在 desktop 里

`ros-humble-desktop` 不含 GUI 版。要单独装：

```bash
sudo apt install -y ros-humble-joint-state-publisher-gui
```

无 GUI 环境（CI）用 `joint_state_publisher`（不带 `_gui`）。

### 6.3 launch 文件不重建不生效

见第四章。**CI 里尤其容易踩**：改了 launch 但构建缓存命中，跑的永远是旧版本。

## 七、给 CI 的启示

这一阶段看似只是"学 API"，但已经有三个点直接影响后续 CI 设计：

| 现象 | CI 影响 | 对策 |
|---|---|---|
| 参数硬编码 | 无法在同一流水线跑多配置 | 所有可变项必须 `declare_parameter` |
| launch 不重建不生效 | 假绿（跑了旧版本还以为通了） | CI 里强制 `--cmake-clean-cache` 或校验产物 hash |
| 没有 `base_footprint` | SLAM/Nav2 后续全断 | URDF 静态检查加进 CI 门禁 |

**第三条是你后续要给机器人 CI 加的独特门禁**：普通 CI 只查编译过没过，机器人 CI 必须查**坐标系链条是否完整**，因为那是"能编译但跑不起来"的典型。
