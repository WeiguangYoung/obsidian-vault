# 🤖 环境搭建：ROS 2 Humble + Gazebo + NVIDIA 驱动

## 摘要

在 Ubuntu 22.04（jammy）上从零搭建 ROS 2 Humble + Gazebo Fortress 桌面学习环境，用于机器人 CI 构建方向的能力补齐。**核心坑位不是安装步骤，而是三个国内网络问题**：① `packages.ros.org` 官方源在本机被限速到接近 0（curl 20 秒拿不到 1MB），必须换清华 TUNA 镜像；② `rosdep` 的 sources list 走 GitHub raw；③ **更隐蔽的**：`rosdistro` 的 `index-v4.yaml` URL 硬编码在 Python 源码里，`rosdep update` 没有 CLI 参数可改，只能用 `ROSDISTRO_INDEX_URL` 环境变量覆盖。三者全部换源后，安装约 15 分钟完成。

> 本文只记录**可复现的步骤与坑点定位方法**，不写流水帐。

---

## 一、目标与结果

| 项 | 值 |
|---|---|
| 系统 | Ubuntu 22.04.5 LTS（jammy），内核 6.8.0-40 |
| ROS 发行版 | ROS 2 Humble（支持至 2027-05） |
| 仿真器 | Gazebo Sim 6.18.0（Fortress） |
| 构建工具 | colcon（`python3-colcon-common-extensions`） |
| 安装位置 | `/opt/ros/humble` |
| ROS 包数量 | 288 个（`ros2 pkg list`） |
| 磁盘占用 | 约 3.3 GB |

**版本对应关系（必须遵守）**：

```
Ubuntu 22.04 (jammy)  →  ROS 2 Humble  →  Gazebo Fortress
Ubuntu 24.04 (noble)  →  ROS 2 Jazzy   →  Gazebo Harmonic
```

Gazebo 与 ROS distro 是强绑定关系，混装非官方组合会出现插件加载失败、`gz` 命令找不到等诡异问题。

## 二、安装步骤

### 2.1 添加 ROS 2 APT 源（用 TUNA 镜像）

```bash
sudo apt install -y software-properties-common curl gnupg lsb-release

# ROS 官方签名密钥
curl -sSL https://raw.githubusercontent.com/ros/rosdistro/master/ros.key -o /tmp/ros.key
sudo gpg --dearmor --yes -o /usr/share/keyrings/ros-archive-keyring.gpg /tmp/ros.key

# 关键：用清华镜像，不要用 packages.ros.org
sudo tee /etc/apt/sources.list.d/ros2.list > /dev/null << 'EOF'
deb [arch=amd64 signed-by=/usr/share/keyrings/ros-archive-keyring.gpg] https://mirrors.tuna.tsinghua.edu.cn/ros2/ubuntu jammy main
EOF

sudo apt update
```

### 2.2 安装桌面版 + Gazebo 集成

```bash
sudo apt install -y \
  ros-humble-desktop \
  ros-humble-ros-gz \
  python3-colcon-common-extensions \
  python3-rosdep
```

**包说明**：

| 包 | 作用 |
|---|---|
| `ros-humble-desktop` | 桌面完整版（RViz2、demo、rqt 等） |
| `ros-humble-ros-gz` | ROS 2 ↔ Gazebo Fortress 桥接（`ros_gz_bridge`、`ros_gz_sim`） |
| `python3-colcon-common-extensions` | colcon 构建工具全集（含 `--packages-select` 等扩展） |
| `python3-rosdep` | 依赖自动解析 |

> 只跑 CI 的话 `ros-humble-ros-base` 就够（体积小很多）；本地学习建议 desktop。

### 2.3 环境变量

```bash
echo "source /opt/ros/humble/setup.bash" >> ~/.bashrc
source ~/.bashrc
```

### 2.4 rosdep 初始化（有两层网络要换）

```bash
sudo rosdep init
```

### 坑位一：sources list 走 GitHub

```bash
sudo tee /etc/ros/rosdep/sources.list.d/20-default.list > /dev/null << 'EOF'
yaml https://mirrors.tuna.tsinghua.edu.cn/rosdistro/rosdep/osx-homebrew.yaml osx
yaml https://mirrors.tuna.tsinghua.edu.cn/rosdistro/rosdep/base.yaml
yaml https://mirrors.tuna.tsinghua.edu.cn/rosdistro/rosdep/python.yaml
yaml https://mirrors.tuna.tsinghua.edu.cn/rosdistro/rosdep/ruby.yaml
EOF
```

### 坑位二（更隐蔽）：rosdistro index 硬编码 GitHub

即使 sources list 全换成镜像，`rosdep update` 最后还是会去拉 `index-v4.yaml`，而这个 URL **硬编码在 `rosdistro/__init__.py` 里**：

```python
# /usr/lib/python3/dist-packages/rosdistro/__init__.py:80
DEFAULT_INDEX_URL = 'https://raw.githubusercontent.com/ros/rosdistro/master/index-v4.yaml'
```

`rosdep update` 没有暴露改这个 URL 的 CLI 参数（`--rosdistro-index-url` 不存在），必须用**环境变量**覆盖：

```bash
export ROSDISTRO_INDEX_URL=https://mirrors.tuna.tsinghua.edu.cn/rosdistro/index-v4.yaml
rosdep update
```

写入 `~/.bashrc` 让它持久化（**CI 镜像里也必须设这个变量**，否则 `rosdep install` 会卡住）。

**成功标志**：

```
Add distro "humble"
updated cache in /home/yang/.ros/rosdep/sources.cache
```

> **另一个坑**：默认 sources list 里的 `gbpdistro .../releases/fuerte.yaml fuerte` 指向 2014 年就废弃的 fuerte 仓库，可以整行删掉，减少一个超时点。

## 四、坑点定位方法（比结论更重要）

### 4.1 怎么判断是"包太大"还是"网络被限速"

症状：`apt-get install` 卡在某个 `Get:` 行十几分钟不动。

**别猜，直接测单包下载速度**：

```bash
curl -o /dev/null -s -w 'http=%{http_code} size=%{size_download} speed=%{speed_download}\n' \
  --max-time 20 '<deb 完整 URL>'
```

实测对比（同一个包 `libignition-gazebo6_6.18.0-1~jammy_amd64.deb`，7 MB）：

| 源 | 结果 |
|---|---|
| `http://packages.ros.org` | 20 秒内几乎无数据（speed ≈ 0） |
| `https://mirrors.tuna.tsinghua.edu.cn/ros2` | **13.7 MB/s**，秒下 |

**结论**：不是包大，是源被限速。换镜像即可。

### 4.2 apt 卡住后怎么安全重来

```bash
# 1. 杀掉卡住的进程
sudo pkill -f 'apt-get install'

# 2. 清锁（只在确认无 apt 进程运行时做）
sudo rm -f /var/lib/apt/lists/lock /var/cache/apt/archives/lock /var/lib/dpkg/lock-frontend

# 3. 修复可能的半安装状态
sudo dpkg --configure -a

# 4. 重装（已下载的包在 /var/cache/apt/archives，会复用不重下）
sudo apt-get -o Acquire::http::Timeout=30 -o Acquire::Retries=5 install -y ...
```

> **`-o Acquire::http::Timeout=30 -o Acquire::Retries=5`** 这两个参数很重要，能把"无限挂起"变成"30 秒失败后重试"，避免整晚卡在一个连接上。

### 4.3 被 kill 的 apt 会不会留下半装状态

会，但可修复。判断方法：

```bash
dpkg -l | grep -E '^i[^i]|^.[^i]' | head    # 看状态列不是 ii 的包
sudo dpkg --configure -a                       # 重新配置
sudo apt-get install -f                        # 修复依赖
```

本次实测：被杀后直接重跑 apt，APT 自动丢弃半下载文件重新拉取，无残留问题。

## 五、给 CI 用的关键认知

### 5.1 装什么、不装什么

| 场景 | 推荐包 | 体积 |
|---|---|---|
| 本地学习 | `ros-humble-desktop` | 大 |
| CI 构建 | `ros-humble-ros-base` + 按需的 `ros-humble-<pkg>` | 小 |
| CI 仿真回归 | 加上 `ros-humble-ros-gz` | 中 |

`desktop` 里有大量 GUI 依赖（Qt、RViz2、rqt），CI 镜像里全是浪费。

### 5.2 DDS 中间件必须固定

ROS 2 Humble 默认用 FastDDS，但环境里可能有 CycloneDDS。多机/多容器通信时会因中间件不一致而"看不见对方"。

```bash
# 显式固定（写进 Dockerfile 或 CI 环境变量）
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp   # 或 rmw_cyclonedds_cpp
```

**这类问题在本地单机看不出来，一进 CI 容器就暴露**，所以要提前固定。

### 5.3 headless 仿真的三个必要条件

```bash
export DISPLAY=            # 或完全不设
ign gazebo -s -r --headless-rendering
# 若传感器（相机）仍报错，检查：
export LIBGL_ALWAYS_SOFTWARE=1    # 无 GPU 时强制软渲染
```

### 5.4 构建缓存

colcon 本身支持增量（`build/` 目录保留即可）。挂 ccache 需要额外配置：

```bash
export CCACHE_DIR=/ccache
colcon build --cmake-args -DCMAKE_CXX_COMPILER_LAUNCHER=ccache
```

实测 1 包增量构建 0.7 秒，包多了之后 ccache 才有明显收益。

## 附录：NVIDIA 驱动安装与传感器启用

### 背景

前一阶段（[[knowledge/robotics/04-Gazebo仿真与SIL\|04-Gazebo仿真与SIL]]）遇到了一个**无法在软件层解决**的问题：headless 下 Gazebo 的 `Sensors` 插件永久卡死。当时判断根因是「无 GPU 渲染能力」，只能禁用传感器跑纯物理仿真。

**2026-11-08 装完 NVIDIA 595 驱动后，问题彻底消失。** 激光雷达和相机都正常出数据。本文记录驱动安装的完整流程、踩的坑，以及传感器验证的实测结果。

**结论先行**：RTX/GTX 显卡机器上做机器人仿真，**必须先装好 NVIDIA 驱动**，否则 Gazebo 的 GPU 传感器会静默卡死，而且报错信息完全指不到根因。


### 一、安装前状态排查

```bash
nvidia-smi              # → command not found（未装驱动）
lspci -nn | grep -i vga # → NVIDIA Corporation TU116 [GeForce GTX 1660 SUPER]
lsmod | grep nvidia     # → 只有 i2c_nvidia_gpu（I2C 辅助模块，不是显卡驱动）
lsmod | grep nouveau    # → nouveau 3100672 10（开源驱动在跑）
```

**判断方法**：`lspci` 能看到显卡说明硬件在，`lsmod` 看到 `nouveau` 说明用的是开源驱动，`nvidia-smi` 报 command not found 说明专有驱动没装。

### 环境确认（决定要不要担心安全启动）

```bash
mokutil --sb-state      # → SecureBoot disabled  ← 关键
uname -r                # → 6.8.0-40-generic
dpkg -l | grep linux-headers-$(uname -r)   # → 已安装 ← DKMS 前提
```

安全启动关闭 + 内核头文件齐全 = DKMS 能顺利编译，不会有签名问题。


### 二、选驱动版本

```bash
ubuntu-drivers devices
```

**本机输出（节选）**：

```
model    : TU116 [GeForce GTX 1660 SUPER]
driver   : nvidia-driver-545 - distro non-free
driver   : nvidia-driver-580 - distro non-free
driver   : nvidia-driver-595 - distro non-free recommended    ← 推荐
driver   : nvidia-driver-595-open - distro non-free
driver   : nvidia-driver-595-server - distro non-free
driver   : xserver-xorg-video-nouveau - distro free builtin
```

### 版本类型说明

| 类型 | 含义 | 适用 |
|---|---|---|
| `nvidia-driver-NNN` | 标准闭源驱动 | 桌面 + 计算，**通用首选** |
| `nvidia-driver-NNN-open` | 开源内核模块（用户态仍闭源） | Turing 及更新架构可用 |
| `nvidia-driver-NNN-server` | 服务器版，无桌面组件 | 纯计算节点 |

**GTX 1660 Super 是 Turing（TU116）架构**，`open` 版本理论上支持，但**标准版最稳**。本次装标准版。


### 三、安装

```bash
sudo apt install -y nvidia-driver-595
```

### 实际安装了什么

```
nvidia-compute-utils-595    595.99.02   计算工具（nvidia-smi 等）
nvidia-dkms-595             595.99.02   DKMS 内核模块构建框架
nvidia-driver-595           595.99.02   驱动元包
nvidia-firmware-595         595.99.02   固件
nvidia-kernel-common-595    595.99.02   内核公共模块
nvidia-kernel-source-595    595.99.02   内核模块源码
nvidia-prime                0.8.17.1    双显卡切换（本机无用但无害）
nvidia-settings             510.47.03   GUI 配置工具
nvidia-utils-595            595.99.02   用户态工具
```

### 安装过程中会做什么

1. 解压内核模块源码到 `/usr/src/nvidia-595.99.02/`
2. DKMS 针对当前内核编译（**约 3-5 分钟**）
3. 产出 `/lib/modules/$(uname -r)/updates/dkms/nvidia*.ko`
4. 写黑名单 `/lib/modprobe.d/nvidia-graphics-drivers.conf`（`blacklist nouveau`）
5. 重建 initramfs

**验证模块已编译**：

```bash
ls /lib/modules/$(uname -r)/updates/dkms/nvidia*.ko
# → nvidia.ko  nvidia-drm.ko  nvidia-modeset.ko  nvidia-uvm.ko  nvidia-peermem.ko
```


### 四、坑：装完不能立即用

### 现象

```bash
$ nvidia-smi
NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver.

$ sudo modprobe nvidia
modprobe: ERROR: could not insert 'nvidia': No such device
```

### 根因

**nouveau 还占着显卡**。检查：

```bash
lsmod | grep nouveau
# → nouveau  3100672  10    ← 引用计数 10，说明正在被使用
```

引用计数 10 来自 X/Wayland 合成器 + 浏览器等图形程序。

### 尝试卸载（失败）

```bash
sudo modprobe -r nouveau
# → rmmod: ERROR: Module nouveau is in use
```

**这是死锁**：要卸载 nouveau 必须停图形界面，要停图形界面得先有替代驱动。

### 唯一解：重启

> 除非你是纯文本服务器（无图形界面），或者愿意 `systemctl stop gdm3` 后手动跑 `modprobe`，否则**装完驱动必须重启**。


### 五、重启前的安全加固（避免黑屏）

这几步很关键，能大幅降低黑屏概率：

### 5.1 确认 nouveau 已加入黑名单

```bash
grep -rn 'blacklist nouveau' /lib/modprobe.d/ /etc/modprobe.d/
# → /lib/modprobe.d/nvidia-graphics-drivers.conf:1:blacklist nouveau
```

### 5.2 确认 DRM modeset 开启

```bash
cat /etc/modprobe.d/nvidia-graphics-drivers-kms.conf
# → options nvidia_drm modeset=1
```

**`modeset=1` 很重要**：没有它，内核早期可能用不了 KMS，导致纯控制台黑屏。

### 5.3 把 NVIDIA 模块加进 initramfs

**这一步默认不会做，但建议手动加**（防止启动早期无显示）：

```bash
sudo tee -a /etc/initramfs-tools/modules << 'EOF'
nvidia
nvidia_drm
nvidia_modeset
nvidia_uvm
EOF

sudo update-initramfs -u
```

**验证**：

```bash
lsinitramfs /boot/initrd.img-$(uname -r) | grep 'dkms/nvidia'
# → usr/lib/modules/.../updates/dkms/nvidia.ko 等 4 个
```

### 5.4 检查 Xorg 配置

```bash
ls /etc/X11/xorg.conf /etc/X11/xorg.conf.d/
```

**如果是空的，最好** —— 让系统自动检测。如果之前手动配过 `xorg.conf` 指向 nouveau，要删掉。

### 七、关键验证：Gazebo 传感器复活

这是本文的核心价值 —— 证明「昨晚卡死」确实是驱动问题。

### 7.1 重新启用 Sensors 插件

```xml
<!-- 前文注释掉的这段，现在取消注释 -->
<plugin filename="ignition-gazebo-sensors-system" name="ignition::gazebo::systems::Sensors">
  <render_engine>ogre2</render_engine>
</plugin>
```

### 7.2 启动 Gazebo（带传感器）

```bash
ign gazebo -s -r -v 3 --headless-rendering robot_world.sdf
```

**对比结果**：

| | 装驱动前（nouveau） | 装驱动后（NVIDIA 595） |
|---|---|---|
| Gazebo 启动 | 僵尸状态，`/gazebo/worlds` 永久超时 | ✅ 立即响应 |
| `ign model --list` | 超时 | ✅ 返回模型列表 |
| Sensors 插件 | 卡在 `SensorsPrivate::WaitForInit()` | ✅ 正常初始化 |

### 八、坑点汇总

### 8.1 `modprobe nvidia` 报 `No such device`

**不是驱动装坏了**，是 nouveau 占着设备。必须重启。

### 8.2 `nvidia-smi` 报无法通信

同理，模块没加载。重启后自动解决。

### 8.3 initramfs 没有 nvidia 模块

默认安装脚本可能不把 nvidia 加进 initramfs。如果启动早期需要显示（如 LUKS 解锁密码界面），会黑屏。**手动加更保险**（见 §5.3）。

### 8.4 传感器数据里大量 `.inf`

**这是正常的**。激光雷达在无障碍物方向的返回值是无穷大（远超 `range_max` 时也可能是 inf）。解析时必须过滤：

```python
valid = [r for r in msg.ranges if msg.range_min < r < msg.range_max]
```

### 8.5 ROS 2 消息里 `frame_id` 的位置

```python
# ❌ 错：LaserScan 没有 frame_id 属性
msg.frame_id

# ✅ 对：在 header 里
msg.header.frame_id   # → 'laser'
```

这是 ROS 2 所有带 header 的消息的统一规则。


### 九、对机器人 CI 的启示

这次经历直接印证了一条 CI 设计原则：

### 仿真环境必须有能力探测门禁

```bash
# CI 前置检查
nvidia-smi > /dev/null 2>&1 || {
  echo "❌ 无 NVIDIA 驱动，GPU 传感器仿真不可用"
  echo "   降级方案：禁用 Sensors 插件，只跑物理 + 里程计"
  export SENSORS_ENABLED=false
}
```

**为什么重要**：昨晚的现象是「进程还在、日志正常、但服务永久超时」。这种失败模式在 CI 里会表现为 **job 挂到超时**，浪费 runner 时间且日志毫无线索。

**更好的做法**：在流水线最前面花 2 秒做能力探测，明确降级或失败，而不是等到 30 分钟后超时。
