# 第一部分 · 构建环境（容器镜像）




### 摘要

把前几阶段的 ROS 2 + Gazebo 仿真环境完整容器化，产出一个**可复现、带 GPU 直通、能在 CI 里跑 SIL 回归**的镜像 `ros2-ci:humble-base`（4.7GB）。

**最终验证结果**（容器内实测）：

```
colcon build  → 3 packages finished [5.85s]
Gazebo        → 世界 5 秒就绪
spawn         → OK creation of entity
sensors_count = 4
  /scan              ← 激光雷达
  /camera/image_raw  ← 相机
GPU           → NVIDIA GeForce GTX 1660 SUPER
```

**核心结论**：构建能做成，但要趟过**五个国内环境特有的坑**——其中三个是「看起来在跑，其实是死的」这种最难排查的类型。

### 一、五大致命坑（按排查难度排序）

#### 坑 1：buildkit 构建「假死」（最难）

**现象**：
```
Step 19/19 : CMD ["bash"]
#15 exporting to image
#15 exporting layers          ← 卡在这里，无限期
```

所有步骤都 `CACHED`，只在最后导出层时卡住。同时 `/var/lib/docker` 从 7.9GB 骤降到 **416K**——之前的构建成果全部被 GC 回收。

**根因**（dockerd 日志）：
```
level=error msg="healthcheck failed fatally"
  error="session healthcheck failed: only one connection allowed"
```

**Docker 29 的 buildkitd 会话健康检查有 bug**，会在长时间构建后误判会话死亡。

**解法**：
```bash
# 方法一：全局关闭 buildkit
# /etc/docker/daemon.json
{
  "features": { "buildkit": false }
}
sudo systemctl restart docker

# 方法二：单次构建禁用
DOCKER_BUILDKIT=0 docker build -t xxx .
```

**验证**：传统构建器日志是 `Step N/M : RUN ...` 格式，能清楚看到每步执行。

> **教训**：Docker 29 + buildkit 在长构建（>30 分钟）时不稳。**构建大镜像一律用 `DOCKER_BUILDKIT=0`**。

#### 坑 2：ROS 密钥下载卡住

**现象**：
```
Step 9/22 : RUN curl -sSL https://raw.githubusercontent.com/ros/rosdistro/master/ros.key
 ---> Running in 59527a8aa253     ← 卡 30 分钟不动
```

**根因**：`raw.githubusercontent.com` 国内访问不稳定。

**解法**：换国内镜像的密钥副本
```dockerfile
RUN curl -sSL --retry 3 --max-time 60 https://mirrors.ustc.edu.cn/rosdistro/ros.key \
        -o /tmp/ros.key \
    && gpg --dearmor --yes -o /usr/share/keyrings/ros-archive-keyring.gpg /tmp/ros.key
```

**可用的密钥源**：
| 源 | 可用性 |
|---|---|
| `mirrors.ustc.edu.cn/rosdistro/ros.key` | ✅ 可用 |
| `raw.githubusercontent.com/ros/rosdistro/master/ros.key` | ⚠️ 不稳定 |
| `mirrors.tuna.tsinghua.edu.cn/ros/ros.asc` | ❌ 404 |

#### 坑 3：Docker Hub 拉不动镜像

**现象**：`docker pull` 任何镜像都卡住，包括 `hello-world`。

**诊断过程**：
```bash
# 1. 测 registry
curl -s -o /dev/null -w '%{http_code}' https://registry-1.docker.io/v2/
# → 000（超时）

# 2. 测认证服务（关键）
curl -s -o /dev/null -w '%{http_code}' 'https://auth.docker.io/token?service=registry.docker.io&scope=repository:library/hello-world:pull'
# → 000（超时）

# 3. 测镜像加速器
curl -s -o /dev/null -w '%{http_code}' https://docker.m.daocloud.io/v2/
# → 401（正常，需认证）
```

**根因**：**镜像加速器只代理 registry，不代理 auth.docker.io**。拉取的认证阶段必然失败。

**测试过的加速器**：

| 加速器 | /v2/ | token 端点 | 结论 |
|---|---|---|---|
| docker.m.daocloud.io | 401 | 401 | ❌ 不代理认证 |
| docker.nju.edu.cn | 403 | — | ❌ |
| dockerproxy.com | 000 | — | ❌ |
| docker.1ms.run | 401 | 404 | ❌ |
| docker.xuanyuan.me | 401 | 返回 HTML | ❌ |

**最终方案**：
- **不要依赖 Docker Hub**。用 `apt` 里的系统包、或已经缓存的基础镜像
- 本次用了 `nvidia/cuda:12.0.0-base-ubuntu22.04`（338MB，已缓存）
- 生产环境建议：**自建 registry（Harbor）**，镜像从本地推

#### 坑 4：容器内 colcon 找不到 ament_cmake

**现象**：
```
CMake Error at CMakeLists.txt:8 (find_package):
  Could not find a package configuration file provided by "ament_cmake"
```

**根因**：用 `--entrypoint /bin/bash` 覆盖了 ENTRYPOINT，导致 `ros_entrypoint.sh` 没执行，ROS 环境没 source。

**解法**：
```bash
# ❌ 错：entrypoint 被覆盖，ROS 环境丢失
docker run --rm --entrypoint /bin/bash myimage -c 'colcon build'

# ✅ 对：显式 source
docker run --rm --entrypoint /bin/bash myimage -lc 'source /opt/ros/humble/setup.bash && colcon build'

# ✅ 或：用 login shell（-l）让 .bashrc 生效
docker run --rm --entrypoint /bin/bash myimage -lc 'colcon build'
```

#### 坑 5：容器里 Gazebo 传感器话题不出现

**现象**：Gazebo 正常启动、机器人 spawn 成功、`/world/default/*` 话题都在，**但 `/scan` 和 `/camera/*` 没有**。

**验证 GPU 是好的**：
```bash
docker run --rm --gpus all myimage nvidia-smi
# → 正常输出 GTX 1660 SUPER    ← GPU 没问题
```

**根因**：**Ignition Transport 的进程间发现机制**。当 Gazebo 服务和查询进程不在同一容器/进程树时，或者 `IGN_PARTITION` 不一致，就互相看不见。

**解法**：所有组件（Gazebo + spawn + bridge + 测试）**必须在同一个容器内**运行。

**错误做法**：
```bash
# 容器 A 起 Gazebo
docker run -d --name gz myimage ign gazebo ...
# 容器 B 查话题 → 看不到
docker run --rm myimage ign topic -l
```

**正确做法**：
```bash
# 一个容器内跑完整流程
docker run --rm --gpus all myimage bash -c '
  ign gazebo -s -r --headless-rendering world.sdf &
  sleep 20
  ros2 run ros_gz_sim create -name bot -file model &
  sleep 10
  ign topic -l | grep scan
'
```

或者显式统一分区：
```bash
docker run -e IGN_PARTITION=sim ...
```

### 二、可用的 Dockerfile

```dockerfile
FROM nvidia/cuda:12.0.0-base-ubuntu22.04

ENV DEBIAN_FRONTEND=noninteractive
ENV LANG=C.UTF-8
ENV LC_ALL=C.UTF-8
ENV TZ=Asia/Shanghai

# 国内 apt 镜像
RUN sed -i 's|http://archive.ubuntu.com/ubuntu|http://mirrors.tuna.tsinghua.edu.cn/ubuntu|g; \
           s|http://security.ubuntu.com/ubuntu|http://mirrors.tuna.tsinghua.edu.cn/ubuntu|g' \
    /etc/apt/sources.list

# 基础工具
RUN apt-get update && apt-get install -y --no-install-recommends \
        ca-certificates curl gnupg lsb-release software-properties-common \
        build-essential cmake git \
        python3 python3-pip python3-dev \
        locales tzdata vim less procps iputils-ping net-tools \
    && locale-gen C.UTF-8 \
    && rm -rf /var/lib/apt/lists/*

# ROS 2 源（密钥走 USTC 镜像）
RUN curl -sSL --retry 3 --max-time 60 https://mirrors.ustc.edu.cn/rosdistro/ros.key -o /tmp/ros.key \
    && gpg --dearmor --yes -o /usr/share/keyrings/ros-archive-keyring.gpg /tmp/ros.key \
    && echo "deb [arch=amd64 signed-by=/usr/share/keyrings/ros-archive-keyring.gpg] https://mirrors.tuna.tsinghua.edu.cn/ros2/ubuntu jammy main" \
        > /etc/apt/sources.list.d/ros2.list \
    && rm -f /tmp/ros.key

# ROS 2 Humble + Gazebo
RUN apt-get update && apt-get install -y --no-install-recommends \
        ros-humble-ros-base \
        ros-humble-ros-gz \
        ros-humble-xacro \
        ros-humble-robot-state-publisher \
        ros-humble-joint-state-publisher \
        python3-colcon-common-extensions \
        python3-rosdep \
    && rm -rf /var/lib/apt/lists/*

ENV ROSDISTRO_INDEX_URL=https://mirrors.tuna.tsinghua.edu.cn/rosdistro/index-v4.yaml
ENV RMW_IMPLEMENTATION=rmw_fastrtps_cpp

RUN rosdep init 2>/dev/null || true
RUN printf 'yaml https://mirrors.tuna.tsinghua.edu.cn/rosdistro/rosdep/base.yaml\n\
yaml https://mirrors.tuna.tsinghua.edu.cn/rosdistro/rosdep/python.yaml\n' \
        > /etc/ros/rosdep/sources.list.d/20-default.list

RUN echo 'source /opt/ros/humble/setup.bash' >> /root/.bashrc \
    && echo '[ -f /ws/install/setup.bash ] && source /ws/install/setup.bash' >> /root/.bashrc

COPY docker/ros_entrypoint.sh /ros_entrypoint.sh
RUN chmod +x /ros_entrypoint.sh

WORKDIR /ws
ENTRYPOINT ["/ros_entrypoint.sh"]
CMD ["bash"]
```

**构建命令**：
```bash
DOCKER_BUILDKIT=0 docker build -f docker/Dockerfile -t ros2-ci:humble-base .
```

**耗时**：约 40-50 分钟（下载 1418 个包）

### 四、镜像重建（不落盘备份）

**决策**：镜像**不导出成 tar 包长期存放**，靠 Dockerfile + 构建脚本重建。

**为什么这样取舍**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **导出 tar 包** | 恢复快（`docker load` 几十秒） | 占 1GB 存储；Dockerfile 改了要重新导出；容易忘记更新导致版本不一致 |
| **靠 Dockerfile 重建** | 镜像内容永远和 Dockerfile 一致；体积只占一次 | 重建约 40 分钟（下载 1418 个包） |

**结论**：Dockerfile 才是唯一可信源。tar 包会随时间漂移，反而制造「以为有备份，其实是旧版」的风险。

**重建方式**：
```bash
cd ~/ros2_ws
DOCKER_BUILDKIT=0 docker build -f docker/Dockerfile -t ros2-ci:humble-base .
```

**前提条件**：
- 国内 apt/ROS 镜像可用（见 §1 坑 2 / 坑 3）
- 约 6GB 空闲磁盘（构建中间层）
- 40 分钟时间

> **什么时候才值得导出**：需要把镜像搬到**离线环境**或**另一台机器**时，才临时 `docker save`，用完即删。日常不保留。

### 五、磁盘清理

多次失败构建会留下大量中间层：

```bash
# 查看
docker system df

# 输出示例（构建前）
# Images          5    1    9.889GB   9.497GB (96%)   ← 9.5GB 可回收
# Build Cache    17    0    4.677GB   24.58kB         ← 4.6GB 可回收
```

**清理命令**：
```bash
docker container prune -f    # 删停止的容器
docker image prune -f        # 删无 tag 镜像（保留有 tag 的）
docker builder prune -f      # 删 build cache
```

**本次清理效果**：回收 **8.5GB**（4.2GB 镜像 + 4.3GB 缓存）

> ⚠️ 不要用 `docker image prune -a`，会连正在用的镜像一起删。

### 六、CI 集成建议

#### 6.1 流水线骨架

```yaml
build_and_test:
  image: ros2-ci:humble-base
  script:
    - source /opt/ros/humble/setup.bash
    - colcon build --merge-install
    - source install/setup.bash
    - colcon test
    - ros2 run hello_robot sil_test --ros-args -p target_distance:=1.0
  artifacts:
    when: always
    paths: ["log/", "*.json"]
```

#### 6.2 必须做的三件事

| 项 | 原因 |
|---|---|
| **环境能力探测** | 先查 GPU，没有就降级（禁传感器只跑物理） |
| **轮询代替 sleep** | 固定 `sleep 20` 在慢机器上会失败，轮询才稳 |
| **失败也归档日志** | `when: always`，失败日志才最有价值 |

#### 6.3 能力探测脚本

```bash
if nvidia-smi >/dev/null 2>&1; then
  export SENSORS_ENABLED=true
  echo "✅ GPU 可用，启用传感器仿真"
else
  export SENSORS_ENABLED=false
  echo "⚠️ 无 GPU，降级为纯物理仿真"
fi
```

# 第二部分 · 流水线（Jenkins 接入）




### 摘要

把 ROS 2 技术栈接入已有的企业级 Jenkins Shared Library，与 `c-embedded`、`java-gradle` 并列成为第三种 profile。

**最终结果**：构建 #13 **SUCCESS**，耗时 **34.2 秒**，**8 项门禁全部通过**，完整跑通六个阶段：

~~~
Gitea 推送 → 检出 → colcon 构建（3 包 / 5.99s）
  → 静态门禁（colcon test + URDF + TF 树）
  → Gazebo 启动（10s 就绪）→ spawn → 桥接
  → 传感器 4 话题就绪 → SIL 用例 → 到达 1.0072m
  → 模型门禁（性能 6 项 + 精度 1 项）
  → SUCCESS 回写 Gitea
~~~

**SIL 实测**：目标 1.0m，实际 **1.0072m**，误差 **7.2mm（0.72%）**，用时 3.53s，`passed: true`。

**核心结论**：难点不在 ROS 2，而在**把 ROS 2 塞进 Jenkins 的执行模型里**——11 个坑，其中 4 个是「日志只有一行，但根因在别处」。

---

### 一、目标与设计

#### 1.1 与已有技术栈的关系

| 技术栈 | 构建工具 | 门禁 | 制品 |
|---|---|---|---|
| `c-embedded` | CMake / make / ninja | cppcheck + MISRA + 覆盖率 | `.a` `.h` `hex` |
| `java-gradle` | Gradle | checkstyle + jacoco | `.jar` `APK` |
| **`ros2-humble`（新增）** | **colcon** | **colcon test + URDF + TF + SIL + 模型** | **ROS 包 / 镜像** |

#### 1.2 设计原则（沿用现有 shared library 的架构）

| 原则 | ROS 2 场景的体现 |
|---|---|
| **仓库侧只声明** | Jenkinsfile 只留 `@Library` + 一行调用 |
| **差异即配置** | colcon 参数、SIL 阈值、门禁规则全进 profile |
| **逻辑唯一源** | 30 个 ROS 包复用同一条流水线 |

#### 1.3 分工

~~~
standardPipeline  → 通用骨架配置解析（profile 加载 + 环境校验 + 横幅）
ros2Pipeline      → ROS 2 特有的构建 / 测试 / 仿真 / 模型门禁
~~~

**为什么拆成两个**：`standardPipeline` 处理跨技术栈的共性（超时、保留策略、归档 glob），`ros2Pipeline` 处理 ROS 2 特有的阶段。这样以后加 `isaac-sim` 或 `autoware` 栈时，只需再写一个 pipeline 步骤。

### 三、profile 设计

~~~groovy
[
    stack            : 'ros2-humble',
    nodeLabel        : 'agent-01',
    dockerImage      : 'ros2-ci:humble-base',
    rosDistro        : 'humble',
    rmwImplementation: 'rmw_fastrtps_cpp',   // DDS 必须固定

    buildTool        : ['colcon'],
    colconArgs       : ['build', '--merge-install', ...],

    incremental      : [
        enabled       : true,
        interfaceGlobs: ['**/msg/**', '**/srv/**', '**/action/**'],
        implGlobs     : ['**/src/**', '**/include/**'],
    ],

    staticChecks     : [
        [id: 'colcon-test', name: 'colcon test',              enabled: true],
        [id: 'urdf-check',  name: 'URDF 合法性',               enabled: true],
        [id: 'tf-tree',     name: 'TF 树完整性',               enabled: true],
    ],

    sil              : [
        enabled        : true,
        world          : 'robot_world.sdf',
        targetDistance : 1.0,
        tolerance      : 0.15,
        maxDurationSec : 15.0,
    ],

    modelGate        : [enabled: false, baseline: 'models/baseline.json', ...],
    crossCompile     : [enabled: false, targetArch: 'aarch64', sysroot: '/opt/ros-aarch64-sysroot'],
]
~~~

**关键设计点**：

1. **`nodeLabel: 'agent-01'`** —— 明确要求 ROS 2 环境，避免路由到没有 ROS 2 的构建机
2. **`rmwImplementation` 显式声明** —— 容器内外 DDS 不一致会导致「看不见对方」
3. **`incremental.interfaceGlobs`** —— 把「改接口跑全下游」的规则写进配置，而不是代码
4. **门禁可开关** —— `modelGate` 和 `crossCompile` 默认 `false`，按需启用

##### 单类阈值为什么要动态

CI 测试集只有 200 张，**每类 20 张**。掉 2 张就是 10% 的召回率下降——用固定的 6pp 阈值会频繁误判。

```python

support = max(d.get("support", 1), 1)
min_tol = 2.0 / support        # 20 张样本 -> 10%
if drop_c > max(max_drop * 3, min_tol):
    fail()
```

> **教训**：小样本集上的单类指标噪声极大，阈值必须与样本量挂钩。

### 六、十一个坑

#### 坑 1-2：Java 版本（两连击）

**现象**：
~~~
java.lang.UnsupportedClassVersionError:
  hudson/remoting/Launcher has been compiled by a more recent
  version of the Java Runtime (class file version 61.0)
~~~

**解法**：装 JDK 17。

**结果**：还是失败。
~~~
java.lang.UnsupportedClassVersionError:
  Failed to load hudson.slaves.SlaveComputer$SlaveVersion
~~~

**真正原因**：Jenkins 2.555.3 **用 Java 21 编译**（class 65），agent.jar 是 17，但 master 回传的类需要 21。

**解法**：装 JDK 21。

~~~bash
sudo apt install -y openjdk-21-jre-headless
/usr/lib/jvm/java-21-openjdk-amd64/bin/java -jar agent.jar ...
~~~

> **教训**：agent 的 Java 版本必须 **≥ master 的编译版本**，不是 ≥ agent.jar 的版本。查 master 版本：`curl <jenkins>/api/json | jq .version` 然后对照 Jenkins 的 Java 要求表。

#### 坑 3：systemd 用户服务 216/GROUP

**现象**：
~~~
Process: ... (code=exited, status=216/GROUP)
~~~

**原因**：用户级 systemd 服务里写了 `User=` / `Group=`，但用户级服务不需要（也不能）指定。

**解法**：删掉这两行。

#### 坑 4：/home/jenkins 权限拒绝

**现象**：
~~~
java.nio.file.AccessDeniedException: /home/jenkins
~~~

**原因**：节点配置的 `remoteFS` 是 `/home/jenkins/agent`，但该目录不存在或属主不对。

**解法**：
~~~bash
sudo mkdir -p /home/jenkins/agent
sudo chown -R yang:yang /home/jenkins
~~~

> 因为 agent 以 `yang` 用户运行，必须让 yang 能写这个目录。

#### 坑 5：`sh` 用 dash，`source` 不认识（最隐蔽）

**现象**：
~~~
+ . /opt/ros/humble/setup.bash
/opt/ros/humble/setup.bash: Bad substitution
+ builtin cd
/opt/ros/humble/setup.bash: builtin: not found
~~~

**原因**：Jenkins 的 `sh` 默认用 `/bin/sh`（Ubuntu 上是 dash），而 ROS 的 `setup.bash` 是 bash 专用语法（用了 `${BASH_SOURCE}`、`builtin`）。

**试过但失败的方案**：
~~~groovy
sh(script: '...', shell: '/bin/bash')
// WARNING: Unknown parameter(s) found for class type ShellStep: shell
~~~

**Jenkins 2.555.3 移除了 `shell` 参数。**

**正确解法**：在 Groovy 字符串里用 bash heredoc

~~~groovy
sh(script: """
    bash <<'JSH_EOF'
    set -e
    source /opt/ros/humble/setup.bash
    colcon build
    JSH_EOF
""")
~~~

> `<<'EOF'`（带引号）防止变量在 heredoc 展开，这是关键。

#### 坑 6：Groovy 变量插值吃掉 shell 变量

**现象**：
~~~
groovy.lang.MissingPropertyException: No such property: f for class: ros2Pipeline
~~~

**原因**：Groovy 的 `"""` 双引号字符串会做变量插值。这段代码：

~~~groovy
sh(script: """
    find . -name '*.urdf' | while read f; do
        check_urdf "$f"        // ← Groovy 把 $f 当成自己的属性
    done
""")
~~~

**解法**：转义为 `\$f`

~~~groovy
case "\$f" in
    *.urdf) check_urdf "\$f" || exit 1 ;;
esac
~~~

**转义规则**：

| 场景 | 写法 |
|---|---|
| Groovy 变量 | `${var}` |
| Shell 变量 | `\$var` |
| 字面量 $ | `\$\$` |

#### 坑 7：工具校验跑在 master 上

**现象**：
~~~
ERROR: standardPipeline: 缺少必需工具: colcon, ros2
~~~

**原因**：`standardPipeline(requiredTools: [...], ...)` 的校验在流水线开始前执行，此时**还没进入 `agent { }` 块**，跑在 master（容器里没有 ROS 2）。

**解法**：不在 Jenkinsfile 传 `requiredTools`，改由 `ros2Pipeline` 在 agent 上校验（阶段 1 已内置）。

#### 坑 8：colcon test 缺 --merge-install

**现象**：

```
[0.108s] colcon ERROR colcon test: The install directory
'install' was created with the layout 'merged'.
Please remove the install directory, pick a different one
or add the '--merge-install' option.
```

**原因**：构建阶段用了 `--merge-install`，测试阶段没带，colcon 认为两者布局不一致。

**解法**：test 命令也加该参数。

```bash
colcon test --merge-install --packages-select hello_robot
```

> **教训**：colcon 的 `install/` 布局是全局约定，所有子命令（build/test/install）必须一致。

#### 坑 9：.gitignore 把模型排除了

**现象**：

```
onnxruntime...NoSuchFile: Load model from models/squeezenet1.0-12.onnx
failed: File doesn't exist
```

**原因**：`.gitignore` 里写了 `*.onnx`（本意排除临时模型），但 CI 需要的模型也在 `models/` 下。

**解法**：加例外规则。

```gitignore
*.onnx
!models/*.onnx
```

> **教训**：`*.xx` 通配会连"该进仓库的"一起排除。这类问题本地完全复现不出来。

#### 坑 10：heredoc 结束符必须顶格（最隐蔽）

**现象**：

```
所有门禁全部 PASS，"结果: 通过"
bash: line 13: JSH_EOF: command not found
Finished: FAILURE
```

**最坑的地方**：门禁输出全绿，但构建是红的。

**原因**：bash heredoc 的结束符**必须顶格**，前面有任何空格都不认。

```groovy
sh(script: """bash <<JSH_EOF
    set -e
    python3 gate.py ...
            JSH_EOF"""     // 有缩进 -> bash 不认
```

**解法**：结束符顶格。

> 想保留缩进可用 `<<-`，但它只去掉**制表符**，不去空格。最稳的还是顶格。
>
> **教训**：**"日志全绿但构建红"** 是 CI 里最难排查的一类——大脑会本能相信日志内容。定位方法是**只看最后 5 行**。

#### 坑 11：单类召回率阈值拍脑袋

**现象**：

```
[PASS] 准确率: 98.5% vs 基线 98.3% (下降 -0.2pp, 允许 2.0pp)
[FAIL] 单类退化过大: 类别 9 97.0% -> 90.0%
结果: 阻断
```

**问题**：整体准确率完全正常，却被单类检查阻断。

**原因**：CI 测试集每类只有 20 张，掉 2 张 = 10%。原阈值固定 6pp，而 20 张样本 ±10% 是正常噪声。

**解法**：阈值与样本量挂钩。

```python
support = max(d.get("support", 1), 1)
min_tol = 2.0 / support         # 20 张 -> 10%
if drop_c > max(max_drop * 3, min_tol):
    fail()
```

> **教训**：小样本集上比率类指标噪声极大。**任何比率阈值都要问"分母多大"**——1/5 和 1/1000 都是 20%，意义完全不同。

| | **模型精度回归** | 准确率 + 每类召回 vs baseline | 7 |
| | 模型接口签名 | 输入输出 shape | 7 |
| **仿真** | SIL 闭环回归 | 到达精度 + 耗时 | 3 / 5 |
| | 传感器话题存活 | /scan /camera 是否存在 | 3 / 5 |
| **环境** | GPU 可用性探测 | nvidia-smi | 1 |
| | 世界就绪轮询 | 不用固定 sleep | 3 / 5 |
| **多架构** | readelf 架构校验 | 产物是 ARM 还是 x86 | 6 |

**前 6 项普通 CI 也有；后 6 项是机器人 CI 独有。**

### 十一、面试话术

> "我把 ROS 2 接进了已有的 Jenkins Shared Library，新增 ros2-humble 技术栈档案和 ros2Pipeline 步骤，和 c-embedded、java-gradle 并列。仓库侧 Jenkinsfile 只留 @Library 加一行调用。
>
> 流水线跑五个阶段：环境准备、影响面计算、colcon 构建、静态门禁、SIL 仿真回归。整个构建 33 秒，Gitea 状态自动回写。
>
> 影响面用了 colcon 的 --packages-above：改 msg 接口就跑所有下游，改实现只跑那个包。这是车载部件粒度增量构建在 ROS 2 里的对应做法。
>
> 静态门禁除了 colcon test，我加了两个机器人独有的检查：URDF 合法性、TF 树里有没有 base_footprint。后者很关键——缺了它编译完全正常，但跑到 SLAM 就断链。
>
> SIL 这块用轮询等 Gazebo 世界就绪，不用固定 sleep。传感器话题数要 ≥ 2 才继续。最后跑闭环用例断言到达精度，实测误差 7 毫米。
>
> 印象最深的坑是 Jenkins 的 sh 默认走 dash，ROS 的 setup.bash 直接报 Bad substitution，得用 bash heredoc 包裹；还有 Groovy 双引号字符串会把 shell 的变量当成自己的属性。这些文档里都没写，只能一行行看日志。"
