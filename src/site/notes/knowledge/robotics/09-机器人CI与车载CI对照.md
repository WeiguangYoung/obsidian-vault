# 🔄 机器人 CI 与车载 CI 差异对照表

## 为什么写这份表

两边都做过：

- **车载 CI**：华为 OD，2024.05 至今。C 嵌入式（10+ MCU / 10+ 编译器） + C++ AI 算法 + Java 车机应用三栈，250+ 部件，ISO 26262 ASIL-B(D) 取证链
- **机器人 CI**：2026.11，个人项目。ROS 2 Humble + Gazebo SIL + 模型门禁 + 多架构交叉编译，跑在真实 Jenkins Shared Library 上

**核心判断**：两者是**同一类问题的不同变体**——都是「多架构交叉编译 + 硬件在环 + 迭代快」，但约束条件和失败模式差异很大。

---

## 一、一张表看懂

| 维度 | 车载 CI | 机器人 CI | 迁移难度 |
|---|---|---|---|
| **构建体系** | CMake / Make / Ninja，多编译器矩阵 | **colcon + ament**，包依赖图 | 🟡 中 |
| **多平台** | 10+ MCU 架构（Cortex-M/RH850/TriCore/S32/ARC/RISC-V） | **x86 + aarch64**（Jetson/RK3588/树莓派） | 🟢 低 |
| **交叉编译** | arm-none-eabi 等嵌入式工具链 | aarch64-linux-gnu + sysroot | 🟡 中（机器人 sysroot 更复杂） |
| **增量策略** | 部件清单（manifest）驱动 | **package.xml 依赖图** + `--packages-above` | 🟢 低（思路相同） |
| **单元测试** | CUnit / GTest / JUnit | `colcon test`（pytest / gtest / lint） | 🟢 低 |
| **静态检查** | MISRA / CodeCheck / Coverity | cppcheck / flake8 / pep257 | 🟢 低 |
| **覆盖率** | gcov → lcov，按 ASIL 拉线（MC/DC） | gcov / pytest-cov | 🟡 中（ASIL 要求更严） |
| **集成测试** | **HIL 台架**（CANoe / ECU 实机） | **SIL 仿真**（Gazebo）+ HIL（真机） | 🟠 高（机器人 SIL 是全新的） |
| **门禁粒度** | 代码质量为主 | **代码 + 模型 + 仿真** 三层 | 🟠 高（多两层） |
| **制品形态** | `.a/.h`、`.so`、`APK`、`jar`、`hex/s19` | ROS 包（`.deb`）、容器镜像 | 🟢 低 |
| **部署目标** | ECU 刷写（UDS / OTA） | 板子（Docker 镜像 / deb） | 🟡 中 |
| **实时性约束** | 硬实时（ms 级，AUTOSAR） | 软实时（ROS 2，10-100Hz） | 🟢 低（机器人宽容） |
| **功能安全** | ISO 26262 ASIL-B(D)，强制 | 无强制标准（部分公司自建） | 🟢 低（车载更严） |
| **构建耗时** | 30-60 分钟（多编译器矩阵） | **34 秒**（3 包增量） | 🟢 低 |

## 二、四个关键差异（面试重点）

### 差异 1：依赖图是动态的，不是静态清单

**车载**：部件清单（manifest）是人写的静态文件。CI 读清单，知道要编哪些部件。

```
# 车载：静态 manifest
parts:
  - name: BootSDK
    deps: [CommonLib, CryptoLib]
  - name: AppSDK
    deps: [BootSDK, CommonLib]
```

**机器人**：依赖图从 `package.xml` **自动解析**，colcon 建 DAG。

```xml
<!-- 机器人：自动解析 -->
<depend>rclcpp</depend>
<depend>robot_interfaces</depend>
```

**影响**：

| 场景 | 车载 | 机器人 |
|---|---|---|
| 加一个新部件 | 改 manifest | 只加 `package.xml`，DAG 自动更新 |
| 依赖关系错了 | manifest 写错就编错 | CMake 直接报找不到 |
| 影响面计算 | 读 manifest 反查 | `colcon list --packages-above` |

**面试说法**：
> 车载的部件依赖是人维护的清单，机器人的包依赖是工具自动解析的。这意味着车载 CI 要额外做「清单一致性校验」，而机器人 CI 天然不会有这个问题——但代价是 colcon 的依赖解析本身就慢，且容易出现循环依赖。

### 差异 2：SIL 是机器人独有的第三层门禁

**车载的集成测试**：HIL 台架，真 ECU + CANoe 发报文。**硬件成本高**（一个台架几十万），所以只有关键项目才做。

**机器人的集成测试**：SIL 仿真，Gazebo 纯软件。**硬件成本为零**（有 GPU 就行），所以**每个 PR 都能跑**。

```
车载：代码 → 编译 → 单测 → [HIL 台架（贵，稀疏）] → 交付
机器人：代码 → 编译 → 单测 → [SIL 仿真（免费，密集）] → HIL（真机） → 交付
```

**这就是为什么机器人 CI 能做「每个 PR 都跑仿真回归」** ——车载做不到，成本不允许。

**代价**：仿真不等于现实。SIL 过了不代表真机能跑。所以机器人公司还要做 HIL 兜底。

### 差异 3：模型是二进制，代码审查看不见

**车载**：AI 算法模型是 C++ 代码的一部分，模型参数存在代码里或配置文件里，diff 能看到变化。

**机器人**：模型是独立的 `.onnx` / `.pt` 文件，几 MB 到几百 MB。**换一个模型，diff 里只有一个二进制文件的 hash 变化**。

**这导致**：

| 问题 | 车载有吗 | 机器人有吗 |
|---|---|---|
| 代码看不出来模型变差了 | 较少 | **必然** |
| 需要精度回归门禁 | 少 | **必须** |
| 需要性能回归门禁（延迟/吞吐） | 少 | **必须** |

**所以机器人 CI 多了两层门禁**：模型性能 + 模型精度。这是车载 CI 没有的。

### 差异 4：构建速度差两个数量级

| | 车载 | 机器人 |
|---|---|---|
| 全量构建 | 30-60 分钟 | 5-10 分钟 |
| 增量构建 | 5-15 分钟 | **6 秒** |
| 集成测试 | HIL 台架（小时级，稀缺资源） | SIL 仿真（23 秒） |
| 端到端 | **小时级** | **34 秒** |

**为什么差这么多**：

1. **代码量**：车载 250+ 部件 vs 机器人 3 个包
2. **编译器数量**：车载 10+ 编译器矩阵 vs 机器人 1 个 GCC
3. **平台数量**：车载 10+ MCU vs 机器人 1 个 x86
4. **测试成本**：HIL 台架是物理资源 vs SIL 是软件

**这不是坏事**：机器人构建快 = 反馈快 = 迭代快。但代价是**测试深度浅**——车载的 ASIL-D 取证链在机器人里不存在。

## 三、可以直接搬的（80% 复用）

| 能力 | 车载做法 | 机器人照样用 |
|---|---|---|
| **Jenkins Shared Library** | 多技术栈 profile + 可复用步骤 | ✅ 直接复用，加一个 profile |
| **多分支流水线** | Multibranch + PR 回写 | ✅ 完全一样 |
| **质量门禁框架** | 双轨（MR 增量 / 分支总量） | ✅ 逻辑相同，换检查工具 |
| **制品管理** | Harbor 生命周期 + 不可变 tag | ✅ 直接用 |
| **容器化构建** | Docker 固化工具链 | ✅ 直接用，且更重要（ROS 2 依赖多） |
| **多架构交叉编译** | arm-none-eabi 工具链 | ✅ 思路相同，换工具链 |
| **可观测** | Prometheus + Grafana + 告警 | ✅ 直接用 |

**一句话**：**CI 骨架不用重学，只需换「检查什么」和「怎么构建」**。

## 四、必须新增的（20% 差异）

| 能力 | 为什么车载没有 | 机器人怎么做 |
|---|---|---|
| **colcon 构建体系** | 车载用 CMake/Make 直调 | colcon + ament，包依赖自动解析 |
| **SIL 仿真回归** | HIL 太贵，做不到每 PR 跑 | Gazebo headless + 自动化用例 |
| **URDF / TF 树门禁** | 车载无此概念 | `check_urdf` + `base_footprint` 检查 |
| **模型性能门禁** | 模型嵌在代码里，diff 可见 | 相对基线比对延迟/吞吐/签名 |
| **模型精度门禁** | 同上 | 固定测试集 + 准确率/mAP |
| **传感器话题存活检查** | 车载无 ROS topic | `/scan` `/camera` 频率探测 |
| **仿真环境能力探测** | HIL 台架是固定的 | GPU/EGL 可用性预检（防静默卡死） |

## 六、面试怎么讲这段

**开场定位**：

> 我在华为做车载软件 CI，覆盖 C 嵌入式、C++ 算法、Java 应用三栈，10+ 编译器、250+ 部件的构建体系。这套东西的难点不在写流水线，在于**多目标平台 × 多编译器 × 多部件的构建矩阵路由和增量触发**。

**迁移逻辑**：

> 机器人和车载的构建体系是同一类问题的两个变体：都是**多架构交叉编译 + 硬件在环 + 算法迭代快**。车载是 MCU 平台碎片化，机器人是 Jetson/RK3588 + ROS2 colcon。

**具体差异（这段最能体现深度）**：

> 但两边有三处本质差异：
>
> 第一，**依赖图是动态的**。车载的部件清单是人维护的 manifest，机器人的依赖图从 package.xml 自动解析。所以车载要多做「清单一致性校验」，机器人不会错但会有循环依赖问题。
>
> 第二，**集成测试成本差一个数量级**。车载的 HIL 台架几十万一台，只给关键项目用；机器人的 SIL 仿真纯软件，每个 PR 都能跑。这就是为什么机器人能做到「每 PR 跑仿真回归」，车载做不到。
>
> 第三，**模型是二进制**。车载的算法模型嵌在代码里，diff 看得见；机器人的模型是独立 onnx 文件，换一个 diff 里只有 hash 变了。所以机器人 CI 必须加模型性能和精度两层门禁——这是车载没有的。

**收尾**：

> 所以我不是从零学机器人 CI，是把已有的 CI 骨架搬过来，换掉「检查什么」和「怎么构建」这两块。骨架部分复用 67%，剩下 33% 是机器人独有的——URDF/TF 门禁、SIL 回归、模型门禁。

## 七、如果被问「车载经验对机器人有什么用」

**三条硬通货**：

1. **构建矩阵思维**：10+ 编译器 × 10+ MCU 的矩阵路由，直接映射到「ROS 包 × 目标架构」。我做的「部件粒度增量构建」在 ROS 2 里就是 `--packages-above`。
2. **质量门禁设计**：分级门禁（MR 增量 vs 分支总量）、双轨门禁（新增 vs 总量），这套逻辑完全通用。我把它套到模型门禁上就是「相对基线不退化」。
3. **功能安全取证**：ISO 26262 的「证据链」思维——每个门禁都要留下可审计的证据。机器人虽然没强制标准，但机器人公司的安全关键路径（急停、看门狗）正在补这块。

**一句总结**：

> 车载 CI 教我的不是某个工具，是**「如何在一个充满异构约束的系统里，让构建和验证可控」**。这个能力在机器人赛道同样稀缺。
