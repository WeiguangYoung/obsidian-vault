## 一、编译器扩展

### 1. 宏的三个固有缺陷，以及一个解法

#### 缺陷一：参数多次求值

```c
#define MAX(a, b)  ((a) > (b) ? (a) : (b))

int i = 1;
int r = MAX(i++, 10);     // 展开成 ((i++) > (10) ? (i++) : (10))
```

**实测**：`i` 从 1 变成 **2**，`r = 10`。看似正常，但如果 `i` 是 5：

```c
int i = 5;
int r = MAX(i++, 10);     // (5 > 10? ...) → 假，但 i++ 已经执行了
                          // 结果 i=6, r=10 —— 意外的是 i 也变了
```

加括号解决不了，这是**文本替换**的固有限制。

#### 缺陷二：宏没有类型

```c
MAX("abc", "def");        // 能编译通过（比较指针），语义是垃圾
```

#### 解法：语句表达式 `({ })`

GCC/Clang 扩展，把「一个代码块」变成一个**有值的表达式**：

```c
#define MAX_SAFE(a, b) ({        \
    __typeof__(a) _a = (a);      \
    __typeof__(b) _b = (b);      \
    _a > _b ? _a : _b;           \
})

int i = 1;
int r = MAX_SAFE(i++, 10);
```

**实测输出**：`i=2  r=10` —— `i` 只加了**一次**。

关键点：
- 变量名带下划线前缀（`_a` / `_b`），减少和调用方变量重名的概率
- `__typeof__` 保证临时变量类型和入参一致（避免隐式转换）
- 代码块最后一行是表达式，它的值就是整个块的值

⚠️ **这是 GCC 扩展，不是标准 C**，MSVC 不支持。嵌入式用 GCC/Clang 所以没问题，但移植到 IAR/Keil 时要确认。

#### 对比三种写法

| 写法 | 类型安全 | 副作用安全 | 可调试 |
|:--|:--:|:--:|:--:|
| `#define MAX(a,b) ((a)>(b)?(a):(b))` | ❌ | ❌ | ❌ |
| `#define` + `typeof` 语句表达式 | ✅ | ✅ | ⚠️ |
| `static inline int max_int(int,int)` | ✅ | ✅ | ✅ |

**结论：能用 `static inline` 就别用宏。** 宏只在这三种情况下不可替代：

1. 需要编译期常量（数组维度、`case` 标签、`_Static_assert`）
2. 需要接受任意类型（`ARRAY_LEN`、`container_of`）
3. 需要字符串化/拼接（`#`、`##`）

### 2. `__attribute__` 家族：驱动代码里的高频词

`__attribute__` 是 GNU 扩展，用来给编译器「额外指令」。嵌入式里常用的有九种。

#### 2.1 `section`：把变量钉到指定段

```c
// 放进 CCM RAM（F407 的 0x10000000，DMA 不可达）
static uint8_t buf[4096] __attribute__((section(".ccmram")));

// 放进一个自定义段，供后续遍历
struct cmd { const char *name; void (*fn)(void); };
__attribute__((section(".cmd_table")))
static const struct cmd g_cmds[] = { ... };
```

**用途**：内存分区、链接期收集（把散落各处的表项聚到一段）、把 Flash 擦写代码放到 RAM 执行。

⚠️ 自定义段如果要靠 `__start_XXX` / `__stop_XXX` 遍历，**需要链接脚本配合**。默认链接脚本下这两个符号不自动生成 —— 我实测编译会报 `undefined reference to __start_mysec`。要么在 `link.ld` 里加：

```ld
.cmd_table : {
    __start_cmd_table = .;
    KEEP(*(.cmd_table))
    __stop_cmd_table = .;
} > flash
```

要么就别用符号遍历，改用「显式注册 + 表」。

#### 2.2 `aligned` / `packed`：对齐的双向开关

```c
// 强制 32 字节对齐（DMA 缓冲区、缓存行）
static uint8_t dma_buf[512] __attribute__((aligned(32)));

// 取消填充（协议报文）
struct __attribute__((packed)) wire {
    uint8_t  a;
    uint32_t b;
};
```

**实测**：

```
sizeof(struct packed{a;u32 b;}) = 5
sizeof(struct normal{a;u32 b;}) = 8
```

`packed` 的代价是**未对齐访问**：Cortex-M0 直接触发异常，M3/M4 能处理但慢，RISC-V 看实现。

**实践**：`packed` 只用于「缓冲区视图」，解析时立刻 `memcpy` 到对齐结构体里用。

⚠️ 一个常见误解：`aligned` 只是**提高**对齐要求，不能降低。想让结构体按 1 字节排，必须用 `packed`。

#### 2.3 `weak`：可被覆盖的默认实现

这是理解 HAL 库的关键。

```c
// 库里的默认实现
__attribute__((weak)) void HAL_UART_RxCpltCallback(UART_HandleTypeDef *h) {
    // 空实现
}

// 你的代码（同签名，不带 weak）
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *h) {
    // 你的处理
}
```

**链接器规则**：
- 强符号 + 强符号 → **重复定义错误**
- 强符号 + 弱符号 → **选强符号**
- 弱符号 + 弱符号 → 选任意一个
- 只有弱符号 → 用弱符号（未被引用的弱符号可能被丢弃）

**实测**：只定义 `__attribute__((weak)) void hook(void)` 时，调用走默认实现，输出 `[weak] 默认实现被调用`。

**真实用途**：
- 库提供空回调，用户按需覆盖
- 启动文件里 `SysTick_Handler` 等中断向量用 `weak`，用户实现即覆盖 —— 你在 `esp32c3/startup.c` 里见过 `__attribute__((weak)) void SysTick_Handler(void) {}`
- 同一份代码支持多种芯片，用弱符号给「默认实现」

#### 2.4 `alias`：给函数起别名

```c
static int real_func(int x) { return x * 2; }
int alias_func(int x) __attribute__((alias("real_func")));
```

**实测**：`alias_func(21)` = **42**。

**用途**：ABI 兼容（保留旧函数名指向新实现）、给同一个函数起多个语义化名字。

⚠️ 别名函数的**签名必须和原函数完全一致**，否则是未定义行为。`alias` 只能用于**同一编译单元内**的函数。

#### 2.5 `format`：让自定义日志函数也能被检查

```c
__attribute__((format(printf, 1, 2)))
void my_log(const char *fmt, ...);
//                  ↑1=格式串位置  ↑2=第一个可变参数位置
```

有了它，编译器会对 `my_log("%d", "abc")` 报 `-Wformat` 警告 —— 否则自定义的变参函数是完全不做格式检查的。

**这是写日志宏的必备属性**。参数位置要数准：如果是成员函数风格 `void log(obj_t *o, const char *fmt, ...)`，那就是 `format(printf, 2, 3)`。

#### 2.6 `used`：防止被链接器删掉

```c
__attribute__((used)) static void never_called_directly(void) {
    // 只被汇编或链接脚本引用，C 层面从没调用
}
```

`-ffunction-sections -Wl,--gc-sections` 会删掉「没被引用」的函数。如果你的函数只被**向量表**或**汇编代码**调用，编译器看不见引用关系，就会误删。

**同类还有 `retain`（ARMCC）和 `KEEP()`（链接脚本）**。

#### 2.7 `noreturn`：告诉编译器「这函数不返回」

```c
__attribute__((noreturn)) void panic(const char *msg);
```

好处：编译器知道调用后不会继续执行，**后续代码不会被当成死代码生成**，也不会在调用点保存不该保存的寄存器。

**典型用途**：`panic()`、`reboot()`、`__libc_init_array` 之后的 `abort()`。

#### 2.8 `interrupt`：中断函数

```c
// RISC-V
__attribute__((interrupt)) void irq_handler(void) { ... }

// Cortex-M（GCC）
__attribute__((interrupt("IRQ"))) void TIM2_IRQHandler(void) { ... }
```

**它做了什么**：
- 用专门的返回指令（RISC-V 的 `mret`、ARM 的 `bx lr` 配合 EXC_RETURN）
- 保存/恢复所有被用到的寄存器（而不是只保存 AAPCS 规定的 callee-saved）

⚠️ **RISC-V 上漏了这个属性 = 中断返回后随机崩**。因为普通 `ret` 走的是 `jalr x0, 0(ra)`，不是 `mret`，特权级和中断使能状态恢复都不对。

#### 2.9 `constructor` / `destructor`

```c
__attribute__((constructor)) void early_init(void) {
    // main 之前自动执行
}
```

启动代码里的 `__libc_init_array()` 会遍历 `.init_array` 段，逐个调用。**嵌入式的「自动注册」机制就靠它** —— 比如 `LOG_MODULE_REGISTER()` 这类宏。

### 3. `typeof` 与 `container_of`：从成员反推结构体

#### 原理

```c
#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))
```

给定「成员地址」和「成员在结构体里的字节偏移」，做减法就是结构体首地址。

#### 实测

```c
struct list {
    struct list *next;   // offset 0
    int val;             // offset 8（64 位）
};

struct list a = {0, 10}, b = {0, 20};
a.next = &b;

// 只知道 &a.next->next（= &b.next），怎么拿到 b？
printf("%d\n", container_of(&a.next->next, struct list, next)->val);
```

**输出**：`20` ✅

#### 为什么内核和驱动都用它

```c
// 链表节点嵌在业务结构体里，而不是用独立节点
struct my_dev {
    struct list_head list;   // 链条穿在身上
    int id;
    char name[32];
};

// 遍历时只拿到 list_head 地址，反推出整个 dev
struct my_dev *d = container_of(node, struct my_dev, list);
```

**好处**：
- 不用为每个节点额外分配内存
- 一个结构体可以同时挂在多个链表上（多个 `list_head` 成员）
- 遍历时不关心业务类型，通用性强

#### ⚠️ 用错就是野指针

这个宏**不做任何检查**。传进去的 `ptr` 如果不是 `type` 的 `member`，减完偏移得到的就是野地址，解引用直接 HardFault。

### 4. 零长度数组 vs 柔性数组

```c
struct z { uint16_t len; uint8_t data[0]; };   // GNU 扩展：零长度
struct f { uint16_t len; uint8_t data[]; };    // C99 标准：柔性数组
```

**实测**：`sizeof(struct z) = 2`，`sizeof(struct f) = 2` —— **两者都不占空间**，行为等价。

#### 为什么需要它

```c
// 一次分配，数据结构连续
struct f *m = malloc(sizeof(struct f) + payload_len);
m->len = payload_len;
memcpy(m->data, src, payload_len);
```

对比「指针 + 两次分配」：

| | 连续分配 | 指针 + 两次分配 |
|:--|:--:|:--:|
| 分配次数 | 1 | 2 |
| 释放次数 | 1 | 2 |
| 内存连续性 | ✅ | ❌ |
| 适合 DMA | ✅ | ❌ |
| 缓存友好 | ✅ | ❌ |

#### 嵌入式的用法：静态缓冲区视图

```c
#define MSG_BUF_SIZE 256
static uint8_t g_msg_buf[MSG_BUF_SIZE] __attribute__((aligned(4)));

void build(void) {
    struct f *m = (struct f *)g_msg_buf;   // 把静态缓冲区当柔性结构体
    m->len = 10;
    memcpy(m->data, "0123456789", 10);
    send(g_msg_buf, sizeof(struct f) + m->len);
}
```

⚠️ **`aligned(4)` 不能省**。`g_msg_buf` 是 `uint8_t` 数组，如果地址不是 2 的倍数，`m->len` 就是未对齐访问。

#### 限制

1. 必须是**最后一个成员**
2. 含柔性数组的结构体**不能作为数组元素**（`struct f arr[10]` 非法 —— 每个元素大小不定）

### 5. 指定初始化：驱动表的标准写法

```c
struct cfg {
    int a, b, c;
    const char *name;
};

static struct cfg g = { .c = 3, .name = "hi", .a = 1 };
```

**实测**：`a=1  b=0  c=3  name=hi` —— 没指定的成员自动清零。

#### 为什么驱动代码爱用它

```c
// 传统写法：位置依赖，一改顺序全错
static struct ops g_ops = { 0, 0, 0, my_open, my_close };

// 指定初始化：名字对上就行，顺序无关，还能跨编译器
static struct ops g_ops = {
    .open  = my_open,
    .close = my_close,
};
```

**三个好处**：
1. **抗改动**：结构体加字段时，老代码不用动
2. **可读**：一眼看出赋了哪些字段，哪些留空
3. **部分初始化**：没写的自动是 0，不用手写一堆 `NULL`

⚠️ C 里 `.field = value` 是 C99 特性，C++ 也支持但规则略有不同（C++20 才要求按声明顺序）。

### 6. 变参宏与日志

#### 基础写法

```c
#define LOG(fmt, ...)  printf("[LOG] " fmt "\n", ##__VA_ARGS__)
```

`##__VA_ARGS__` 是 GNU 扩展：**可变参数为空时，把前面的逗号一起去掉**。

**实测**：

```
LOG("无额外参数")            → [LOG] 无额外参数
LOG("带参数 x=%d y=%s", 7, "ok") → [LOG] 带参数 x=7 y=ok
```

不加 `##` 会展开成 `printf("...", )` —— 尾随逗号，编译错误。

#### C23 的标准写法

```c
#define LOG(fmt, ...)  printf("[LOG] " fmt "\n" __VA_OPT__(,) __VA_ARGS__)
```

`__VA_OPT__(,)` 意思是「如果有可变参数，就展开这个逗号」。

#### 嵌入式日志宏的完整形态

```c
#ifdef EN_DEBUG_PRINT
  #define DBG(fmt, ...)                                    \
      do {                                                 \
          printf("[%s:%d] " fmt "\r\n",                    \
                 __FILE__, __LINE__, ##__VA_ARGS__);       \
      } while (0)
#else
  #define DBG(fmt, ...)  do { } while (0)
#endif
```

三个关键点：
1. **`do { } while (0)`** —— 保证 `if (x) DBG(...); else ...` 能正确配对
2. **Release 版本编译成空语句** —— 零代码、零开销
3. **`__FILE__` / `__LINE__`** —— 定位到具体行

⚠️ **中断里不能用 `printf`**。原因见第四部分。

### 7. 内建函数：`likely` / `unlikely`

```c
#define likely(x)    __builtin_expect(!!(x), 1)
#define unlikely(x)  __builtin_expect(!!(x), 0)
```

**作用**：告诉编译器「这个分支大概率/小概率成立」，影响**代码布局**（热路径放直线上，冷路径跳出去）。

```c
if (unlikely(p == NULL)) {
    return -EINVAL;      // 错误处理放远处，不占 I-cache
}
// 正常路径直线执行
```

**实测**：`if (likely(g.a == 1))` 走热路径，输出正常。

⚠️ **它只影响性能，不改变语义**。别指望它「保证执行」或「跳过检查」。仅在确实有明确概率分布时才用，乱用反而降低性能。

#### 其他常用内建

| 内建 | 作用 |
|:--|:--|
| `__builtin_popcount(x)` | 数 1 的个数 |
| `__builtin_clz(x)` / `ctz(x)` | 前导零 / 尾随零个数 |
| `__builtin_constant_p(x)` | 编译期判断是否常量 |
| `__builtin_unreachable()` | 告诉编译器「这里不可能到达」 |
| `__builtin_offsetof(t, m)` | 同 `offsetof` |

⚠️ `__builtin_ctz(0)` 是**未定义行为**，必须先判非零。

## 二、函数调用与栈帧

### 1. 一次函数调用，栈上发生了什么

以 ARM AAPCS（Cortex-M 用的调用约定）为例，寄存器分工：

| 寄存器 | 用途 | 调用前后 |
|:--|:--|:--|
| `r0-r3` | 参数 1-4、返回值 | **调用者保存**（caller-saved） |
| `r4-r11` | 局部变量 | **被调用者保存**（callee-saved） |
| `r12` (IP) | 过程间临时 | 调用者保存 |
| `r13` (SP) | 栈指针 | 由双方共同维护 |
| `r14` (LR) | 返回地址 | 被调用者保存（或压栈） |
| `r15` (PC) | 程序计数器 | — |

**关键规则**：
- 前 4 个参数走寄存器 `r0-r3`，**第 5 个开始才压栈**
- 栈在任何「公开接口」处必须 **8 字节对齐**
- `r4-r11` 如果被调用者用了，**必须**先压栈保存，返回前恢复

#### 典型函数序言/尾声

```asm
my_func:
    push    {r4, r5, lr}      ; 保存要用的 callee-saved + 返回地址
    sub     sp, sp, #16       ; 为局部变量开空间
    ...
    add     sp, sp, #16       ; 归还局部空间
    pop     {r4, r5, pc}      ; 恢复寄存器，pc 直接取返回地址
```

**注意最后是 `pop {..., pc}` 不是 `pop {..., lr}; bx lr`** —— 直接把返回地址弹进 PC 更省一条指令。这是编译器的小优化。

#### 为什么这决定了 HardFault 能不能定位

出异常时，你拿到的只有「出错地址」。要知道**哪个函数、哪一行**，必须能读出栈上的返回地址链 —— 而返回地址在栈的哪个位置，取决于上面这套约定。

### 2. Cortex-M 的异常栈帧（和普通函数调用不同）

**这是关键区别**：普通函数调用由编译器按 AAPCS 压栈；**异常发生时由 NVIC 硬件自动压栈**。

硬件压入 8 个字（32 字节）：

| 偏移 | 内容 |
|:--|:--|
| `SP+0x00` | R0 |
| `SP+0x04` | R1 |
| `SP+0x08` | R2 |
| `SP+0x0C` | R3 |
| `SP+0x10` | R12 |
| `SP+0x14` | LR（R14） |
| **`SP+0x18`** | **PC（R15）← 出错指令地址** |
| `SP+0x1C` | xPSR |

**`SP+0x18` 就是你要的答案** —— 出问题的那条指令的地址。

#### 如果开了 FPU

Cortex-M4F 有「懒加载」机制：如果中断发生时浮点上下文在用，会额外压入 `S0-S15` + `FPSCR`（共 17 个字，68 字节）。

判断方法：看 `EXC_RETURN`（异常返回时 LR 的值）的 **bit 4**：
- `bit4 = 0` → 有 FPU 帧
- `bit4 = 1` → 无 FPU 帧

#### 用哪个栈？

异常可能发生在**线程模式**（用 PSP）或**已经在一个中断里**（用 MSP）：

```c
// 看 EXC_RETURN 的 bit 2
// bit2 = 0 → 用的是 MSP
// bit2 = 1 → 用的是 PSP
```

这就是 HardFault handler 里必须先判断用哪个栈的原因。

### 3. 实战：一个能打印现场的 HardFault handler

```c
// 用 naked 确保编译器不插入序言/尾声，原始 SP 才有效
__attribute__((naked)) void HardFault_Handler(void) {
    __asm volatile(
        "tst   lr, #4          \n"   // 测 EXC_RETURN bit2
        "ite   eq              \n"
        "mrseq r0, msp         \n"   // 相等 → 用的 MSP
        "mrsne r0, psp         \n"   // 不等 → 用的 PSP
        "b     hardfault_report\n"   // r0 = 栈帧指针，作为参数传入
    );
}

void hardfault_report(uint32_t *frame) {
    uint32_t cfsr  = *(volatile uint32_t *)0xE000ED28;
    uint32_t hfsr  = *(volatile uint32_t *)0xE000ED2C;
    uint32_t mmfar = *(volatile uint32_t *)0xE000ED34;
    uint32_t bfar  = *(volatile uint32_t *)0xE000ED38;

    uart_printf("\r\n===== HARD FAULT =====\r\n");
    uart_printf("R0  = 0x%08lX   R1  = 0x%08lX\r\n", frame[0], frame[1]);
    uart_printf("R2  = 0x%08lX   R3  = 0x%08lX\r\n", frame[2], frame[3]);
    uart_printf("R12 = 0x%08lX   LR  = 0x%08lX\r\n", frame[4], frame[5]);
    uart_printf("PC  = 0x%08lX  <- 出错指令\r\n",    frame[6]);
    uart_printf("xPSR= 0x%08lX\r\n",                  frame[7]);
    uart_printf("CFSR= 0x%08lX  HFSR= 0x%08lX\r\n", cfsr, hfsr);
    uart_printf("MMFAR=0x%08lX  BFAR=0x%08lX\r\n", mmfar, bfar);
    for (;;) (void)0;   // 停机，等复位
}
```

#### CFSR 怎么读（最有用的一组位）

| 位 | 名称 | 含义 |
|:--:|:--|:--|
| 0 | IACCVIOL | 取指访问违例（MPU） |
| 1 | DACCVIOL | 数据访问违例（MPU） |
| 3 | MUNSTKERR | 出栈时出错 |
| 4 | MSTKERR | 入栈时出错（**栈溢出典型**） |
| 9 | **PRECISERR** | 精确总线错误（`BFAR` 里有出错地址） |
| 10 | IMPRECISERR | 不精确总线错误（写缓冲导致，难定位） |
| 11 | UNSTKERR | 异常返回时出栈出错 |
| 12 | **STKERR** | 异常入栈出错（**栈溢出**） |
| 15 | BFARVALID | `BFAR` 有效 |
| 16 | UNDEFINSTR | 未定义指令 |
| 17 | INVSTATE | 非法状态（常见于跳转到 Thumb 位没设的地址） |
| 18 | INVPC | 非法 PC（常见于函数指针为 0） |
| 24 | **UNALIGNED** | 未对齐访问（M0 常见） |
| 25 | DIVBYZERO | 除零 |

#### 最快定位流程

```
1. 读 PC (frame[6]) → 用 addr2line 或 objdump 定位到函数/行
2. 读 CFSR → 判断是哪类错误
3. 如果 BFARVALID 置位 → 读 BFAR，那是非法访问的地址
4. 如果 STKERR/MSTKERR 置位 → 查栈溢出
5. 如果 INVPC 置位 → 查函数指针是不是 0 或没初始化
```

**定位命令**：

```bash
arm-none-eabi-addr2line -e firmware.elf -f -C 0x08001234
arm-none-eabi-objdump -d firmware.elf | grep -B5 -A5 "8001234:"
```

## 三、C 与汇编的边界

### 1. 什么时候必须写汇编

| 场景 | 为什么 C 写不了 |
|:--|:--|
| 读写特殊寄存器 | `mrs`/`msr`（ARM）、`csrr`/`csrw`（RISC-V）没有 C 语法 |
| 内存屏障 | `dmb`/`dsb`/`isb`、`fence` |
| 精确控制指令序列 | 上下文切换、启动代码 |
| 调用无 C 原型的 ROM 函数 | 需要手工设寄存器 |
| 访问 C 看不到的硬件特性 | 缓存操作、TLB、MPU 配置序列 |

### 2. 内联汇编的语法结构

```c
__asm__ volatile (
    "指令模板"                        // 汇编代码
    : 输出操作数                       // "=r"(var)
    : 输入操作数                       // "r"(var)
    : clobber 列表                     // 告诉编译器「我改了这些」
);
```

四部分，只有第一个必填。

#### 约束符速查

| 约束 | 含义 |
|:--|:--|
| `"r"` | 任意通用寄存器 |
| `"=r"` | 只写（输出）寄存器 |
| `"+r"` | 读写（既输入又输出） |
| `"=&r"` | 只写，且**不能和输入共用**寄存器（early clobber） |
| `"m"` | 内存操作数 |
| `"i"` | 立即数 |
| `"I"` / `"J"` / `"K"` | 特定范围的立即数（架构相关） |

**实测**：

```c
uint32_t out, in = 0x1234;
__asm__ volatile("movl %1, %0" : "=r"(out) : "r"(in));
// out = 0x1234  ✅

uint32_t a, b;
__asm__ volatile("movl $1, %0\n\t movl $2, %1" : "=&r"(a), "=&r"(b));
// a=1, b=2  ✅
```

#### `volatile` 在汇编里的作用

```c
__asm__ volatile("nop");
```

`volatile` 告诉编译器：**不要优化掉、不要移到别处、不要合并**。

不加的话，如果这段汇编没有输出操作数，编译器会认为它「没有副作用」，直接删掉。

#### clobber：告诉编译器「我动了什么」

```c
// 改了内存
__asm__ volatile("..." ::: "memory");

// 改了 r0 和条件码
__asm__ volatile("..." ::: "r0", "cc");
```

**`"memory"` 是最重要的一个**：它告诉编译器「这段汇编可能读写任意内存」，于是编译器会把内存访问重新排序到这段汇编前后 —— 这就是**编译屏障**。

### 3. 编译屏障 vs 内存屏障

这是最容易混淆的一对概念。

#### 编译屏障：`asm volatile("" ::: "memory")`

```c
buf[i] = data;
__asm__ volatile("" ::: "memory");   // 编译器不许把上面的写挪到下面
flag = 1;
```

**它不产生任何机器指令**，纯粹是给编译器的约束。

**解决什么**：编译器重排。比如它可能觉得「先写 flag 再写 buf 更快」，但你需要「数据先就位，再发信号」。

#### 内存屏障：`__DMB()` / `fence`

```c
__DMB();                      // ARM: Data Memory Barrier
asm volatile("fence" ::: "memory");   // RISC-V
```

**它产生真实指令**，让 CPU 的乱序执行/写缓冲同步。

**解决什么**：CPU 硬件层面的重排。

#### 什么时候用哪个

| 场景 | 用什么 |
|:--|:--|
| 单核 MCU，中断与主循环共享变量 | **编译屏障** + `volatile` 就够了 |
| 多核之间共享数据 | 内存屏障 |
| DMA 与外设 | 内存屏障（+ 缓存操作） |
| 编译器把循环优化掉了 | `volatile` |

**关键认知**：Cortex-M 单核上，「中断」并不会真正和主循环**并行执行** —— 中断只是打断，恢复后继续。所以硬件不需要内存屏障，只有编译器重排需要防。

## 四、中断与并发

### 1. 可重入函数：中断里能调什么

**可重入** = 函数执行到一半被打断，另一处又调用它，仍然正确。

#### 不可重入的四个原因

| 原因 | 例子 |
|:--|:--|
| 用了静态/全局可变数据 | `static int counter; counter++;` |
| 调用了不可重入函数 | `printf`、`malloc` |
| 返回指向静态区的指针 | `char *itoa(int)` 内部 static buffer |
| 用了非原子操作保护共享资源 | 没进临界区的链表操作 |

#### 为什么中断里不能用 `printf`

三个叠加的原因：

1. **不可重入**：`printf` 内部有 `FILE *stdout` 的缓冲区状态。主循环正在写一半被中断，中断里又写 → 缓冲区错乱
2. **阻塞**：串口 FIFO 满了会等，中断里等 = 其他中断全被延迟
3. **慢**：一次格式化输出可能几千个周期，中断应该几十个周期内返回

**替代方案**：中断里只把数据塞进环形缓冲，主循环再打印。

```c
// 中断里：只入队，不做任何格式化
void UART_IRQHandler(void) {
    uint8_t byte = read_data_register();
    rb_put(&g_rx_rb, byte);       // 环形缓冲，O(1)
    clear_interrupt_flag();
}

// 主循环：格式化 + 输出
void main_loop(void) {
    uint8_t b;
    while (rb_get(&g_rx_rb, &b)) {
        parser_feed(&g_parser, b, now_ms());
    }
}
```

#### 为什么中断里不能用 `malloc`

堆管理器要维护空闲链表。`malloc` 执行到一半被打断，中断里再 `malloc` → **空闲链表被破坏，后续所有分配都可能返回重叠的内存**。

而且 `malloc` 耗时取决于堆的碎片程度，**没有时间上界** —— 违反中断的实时要求。

#### 为什么中断里不能延时

```c
void IRQHandler(void) {
    delay_ms(10);        // ❌ 灾难
}
```

- 同级和低级中断全被阻塞 10ms
- 如果中断频率高于 10ms/次，**中断会堆积**，最终丢中断
- 看门狗可能因为主循环得不到执行而复位

### 2. 临界区：保护共享数据

#### 基本形式

```c
// ❌ 错的：直接开/关
__disable_irq();
shared++;
__enable_irq();
```

问题：如果这段代码本身在中断里被调用，或者外层已经关了中断 —— `__enable_irq()` 会把**外层**的保护也解开。

#### 正确形式：保存-恢复

```c
static inline uint32_t critical_enter(void) {
    uint32_t primask = __get_PRIMASK();   // 读当前状态
    __disable_irq();
    return primask;
}

static inline void critical_exit(uint32_t primask) {
    __set_PRIMASK(primask);               // 恢复进入前的状态
}
```

**这样才可嵌套**：原来开着 → 出去时开；原来关着 → 出去时保持关。

#### `PRIMASK` vs `BASEPRI`

| 机制 | 效果 | 适用 |
|:--|:--|:--|
| `PRIMASK` | 屏蔽**所有**可配置优先级中断 | 极短的临界区 |
| `BASEPRI` | 只屏蔽**优先级低于阈值**的中断 | 需要保留高优先级中断响应 |

```c
// BASEPRI 用法：只屏蔽优先级数值 >= 5 的中断
// （Cortex-M 里数值越大优先级越低）
__set_BASEPRI(5 << (8 - __NVIC_PRIO_BITS));
```

**实践**：临界区越短越好，通常只保护几条指令。长时间关中断会破坏实时性。

#### 什么时候不需要临界区

| 情况 | 原因 |
|:--|:--|
| 单字节/单字的读或写 | 32 位 MCU 上 `uint32_t` 的读写是单指令，天然原子 |
| 只被一个上下文写 | 单写者原则（见下文环形缓冲） |
| 用原子指令 | `LDREX/STREX`（ARM）、`AMO`（RISC-V） |

⚠️ **`uint64_t` 的读写不是原子的**（32 位 MCU 上是两条指令），必须进临界区。

---

### 3. 单写者原则：无锁环形缓冲的基础

```c
typedef struct {
    volatile uint16_t head;   // 只由生产者写
    volatile uint16_t tail;   // 只由消费者写
    uint8_t buf[256];
} rb_t;
```

**为什么可以无锁**：`head` 和 `tail` **不共享写权**。

- 生产者只写 `head`，只读 `tail`
- 消费者只写 `tail`，只读 `head`

没有「两个上下文同时写同一个变量」的情况，就不需要互斥。

#### 但顺序不能反

```c
bool rb_put(rb_t *rb, uint8_t byte) {
    uint16_t next = (rb->head + 1) & 255;
    if (next == rb->tail) return false;   // 满
    rb->buf[rb->head] = byte;             // ① 先写数据
    __asm__ volatile("" ::: "memory");    // 编译屏障
    rb->head = next;                      // ② 再发布指针
    return true;
}
```

**②必须晚于①**，否则消费者可能看到「指针已前进但数据还没写」的空槽。

`volatile` 保证每次真实访问，但**不保证两行之间的顺序** —— 所以要加编译屏障。

#### 一旦破坏单写者，就必须加锁

「丢弃最旧数据」这个策略需要生产者去推 `tail`：

```c
if (next == rb->tail) {
    rb->tail = (rb->tail + 1) & 255;   // ❌ 生产者动了 tail
}
```

**此时 `tail` 有两个写者，无锁前提被破坏**，必须进临界区。

### 4. 中断栈与栈预算

#### 栈的分工

| 栈 | 谁用 | 大小 |
|:--|:--|:--|
| **MSP**（主栈） | 复位后、所有异常/中断 | 通常几 KB |
| **PSP**（进程栈） | 线程模式（如果用 RTOS） | 每个任务一份 |

**裸机**：只用 MSP，中断和主循环共用同一个栈。
**RTOS**：每个任务有独立 PSP，中断仍用 MSP。

#### 栈预算怎么算

```
总栈需求 = 主线最大调用深度 + 中断嵌套 × 每层异常帧
```

**举例**：
- 主线最坏路径用 800 字节
- 中断嵌套最深 3 层
- 每层异常帧 32 字节（无 FPU）

```
最坏情况 ≈ 800 + 3 × 32 = 896 字节
```

留 30~50% 余量 → **配 1.5 KB**。

⚠️ 别忘了：
- FPU 上下文 + 68 字节/层
- `printf` 的浮点格式化可能吃 300+ 字节
- 局部大数组直接占满

#### 怎么量实际用量

```c
// 启动时把整段栈填成魔数
#define STACK_PAINT  0xCDCDCDCDu
extern uint32_t _sstack, _estack;

void stack_paint(void) {
    for (uint32_t *p = &_sstack; p < &_estack; p++) *p = STACK_PAINT;
}

// 跑完所有业务路径后，从栈顶往下找第一个被改写的字
uint32_t stack_peak(void) {
    uint32_t *p = &_sstack;
    while (p < &_estack && *p == STACK_PAINT) p++;
    return (uint32_t)((uint8_t *)&_estack - (uint8_t *)p);
}
```

**`stack_peak()` 的返回值才是真实用量** —— 链接脚本里写的 `_Min_Stack_Size` 只是「预留多少」，不是「用了多少」。

#### 编译期估算每个函数的栈用量

```bash
arm-none-eabi-gcc -fstack-usage -c foo.c
# 生成 foo.su 文件，每行：函数名:字节数:类型
```

```
parser_feed:    48      static
uart_printf:    312     static
```

把这些按调用链累加，就是粗略的栈深估算。**`printf` 这类函数通常是大头。**

### 5. 中断里能做什么、不能做什么（速查）

| 能做 | 不能做 |
|:--|:--|
| 读/写单字变量（32 位原子） | 调 `printf` / `sprintf` |
| 环形缓冲入队/出队 | 调 `malloc` / `free` |
| 置标志位，主循环处理 | 长时间阻塞等待 |
| 短临界区操作共享数据 | 调不可重入的库函数 |
| 清中断标志（注意 W1C） | 浮点运算（除非明确保存了 FPU 上下文） |
| 启动 DMA 传输 | 递归 |
| 记录时间戳 | 复杂的状态机推进（放主循环） |
