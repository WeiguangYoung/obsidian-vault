三栏各自的角色：

| 栏 | 内容 | 谁提供 | 干什么 |
|:--|:--|:--|:--|
| **左** | `startup_stm32f10x_xx.s` | ST（随芯片型号） | 向量表 + 复位入口 + 默认中断处理 |
| **中** | `main.c` / `system_xx.c` / `stm32f10x_it.c` | 你写 | 业务逻辑、时钟初始化、中断服务 |
| **右** | `stm32f10x.h` / `core_cm3.h` / 库函数 | ARM + ST | 寄存器定义与操作封装 |

**中间栏的箭头指向右边**，意思是：C 文件通过 `#include` 拿头文件里的类型和函数声明。

### 1.2 左栏：启动文件到底做了什么

`startup_stm32f10x_hd.s`（`hd` = high density，大容量型号；中容量是 `md`，小容量是 `ld`）是**整个工程第一个执行的东西**。

#### ① 向量表

文件开头是一张表，本质就是**一串函数地址**，放在 Flash 最前面（`0x08000000`）：

```asm
__Vectors       DCD     __initial_sp          ; 第 0 项：栈顶地址
                DCD     Reset_Handler         ; 第 1 项：复位入口
                DCD     NMI_Handler           ; 第 2 项
                DCD     HardFault_Handler     ; 第 3 项
                ...
                DCD     WWDG_IRQHandler       ; 外设中断从这里开始
                DCD     PVD_IRQHandler
                ...
```

**上电那一刻发生了什么**（这是 Cortex-M 的硬件行为，不是软件）：

1. 内核从 `0x08000000` 读第 0 项，**写进 MSP**（主栈指针）
2. 读第 1 项，**跳过去**执行

所以 `Reset_Handler` 是硬件的「复位中断服务函数」。你在 `03-嵌入式C语言的自我修养` 里看到的「异常自动压栈 8 个字」，同一套机制。

⚠️ 向量表第 0 项是**栈顶地址**不是函数，这是 Cortex-M 和很多其他架构的区别。

#### ② Reset_Handler：三行关键代码

```asm
Reset_Handler   PROC
                EXPORT  Reset_Handler             [WEAK]
                IMPORT  __main
                IMPORT  SystemInit

                LDR     R0, =SystemInit
                BLX     R0                  ; ① 配时钟
                LDR     R0, =__main
                BX      R0                  ; ② 进 C 运行时，最终调 main
                ENDP
```

只有两步：`SystemInit()` → `__main()`。

#### ③ `__main` 不是 `main`（最容易忽略的细节）

差两个下划线，完全是两个东西：

| 名字 | 谁提供 | 干什么 |
|:--|:--|:--|
| `main` | **你**写在 `main.c` | 业务逻辑 |
| `__main` | ARM 编译器运行时库 | 拷贝 `.data`、清零 `.bss`、初始化堆栈、**然后才调 `main`** |

两者的执行顺序：

1. 上电 —— 硬件从 `0x08000000` 取 MSP，从 `0x08000004` 取 `Reset_Handler` 地址并跳转
2. `Reset_Handler`（汇编）
3. `SystemInit()` —— 配时钟（RCC、Flash 等待周期）
4. `__main`（ARM C 库）—— 拷贝 `.data`、清零 `.bss`、初始化堆
5. `main()` —— 你的代码

图示见 [1.5 启动链路](#一工程架构三栏结构与启动链路)。

**这正好解释了为什么「全局变量默认是 0」** —— 是 `__main` 清的 `.bss`，不是编译器保证的。

> 你在 [[knowledge/embedded/01-裸机编程指南\|裸机编程指南]] 里手写的 `_reset`，做的就是 `__main` 这一层的活：
> ```c
> for (long *dst = &_sbss; dst < &_ebss; dst++) *dst = 0;              // 清 .bss
> for (long *dst = &_sdata, *src = &_sidata; dst < &_edata;) *dst++ = *src++;  // 拷 .data
> main();
> ```
> 裸机路线是「自己干」，标准库路线是「交给 `__main` 干」。

#### ④ 其他中断：全是 `[WEAK]` 符号

启动文件里每个中断处理函数的写法都长这样：

```asm
WWDG_IRQHandler PROC
                EXPORT  WWDG_IRQHandler   [WEAK]
                B       .                 ; 原地死循环
                ENDP
```

`B .` 是一条跳到自己身上的指令 —— **一旦触发未实现的中断，程序就卡死在这里**。这是故意设计的：让问题立刻暴露，而不是跳到随机地址。

**`[WEAK]` 是核心**：你在 `stm32f10x_it.c` 里定义一个同名函数（不带 weak），链接器就会用你的版本替换掉它。

> 这和第 [[knowledge/embedded/03-嵌入式C语言的自我修养\|四层硬功夫]] 里讲的 `__attribute__((weak))` 是同一个机制，只是汇编里的写法不同：
> - 汇编（Keil/armasm）：`EXPORT  foo  [WEAK]`
> - C（GCC）：`__attribute__((weak)) void foo(void) {}`

**没有一个中断是「必须实现」的**，你实现哪个，哪个才生效。

### 1.3 中间栏：三个 C 文件

#### `system_stm32f10x.c` —— 只有一个正经函数

```c
void SystemInit(void)
{
    /* 1. 复位 RCC 到默认状态 */
    RCC->CR |= 0x00000001;        // 打开 HSI
    RCC->CFGR = 0x00000000;       // 时钟源切回 HSI，不分频
    ...
    /* 2. 配置 Flash 等待周期 */
    /* 3. 配置 PLL（如果定义了 SYSCLK_FREQ_72MHz） */
    SetSysClock();
    
    /* 4. 向量表基址（重定位时用） */
    SCB->VTOR = FLASH_BASE | VECT_TAB_OFFSET;
}
```

同时定义了全局变量 `SystemCoreClock`（默认 72 MHz），供 `SysTick_Config()` 和串口波特率计算使用。

**关键点**：`SystemInit` 在 `main` **之前**执行。你在 `main` 里做的任何时钟相关配置，都是「在默认 72 MHz 的基础上再改」。

⚠️ `SystemInit` 里没有开任何外设时钟（GPIO/USART 的 `RCC->APB2ENR` 位）。**每个外设用之前必须自己开时钟** —— 这是新手最常见的第一类 bug：代码全对，就是没反应，因为外设没通电。

#### `main.c` —— 你的地盘

```c
int main(void)
{
    /* 1. 外设时钟（RCC_APB2PeriphClockCmd ...） */
    /* 2. 外设初始化（GPIO_Init / USART_Init ...） */
    /* 3. 中断配置（NVIC_Init） */
    
    while (1)
    {
        /* 主循环 */
    }
}
```

#### `stm32f10x_it.c` —— 中断服务函数

```c
void TIM2_IRQHandler(void)
{
    if (TIM_GetITStatus(TIM2, TIM_IT_Update) != RESET)
    {
        TIM_ClearITPendingBit(TIM2, TIM_IT_Update);   // ⚠️ 必须清标志
        /* 你的处理 */
    }
}
```

**两条铁律**：

1. **函数名必须和启动文件的向量表完全一致**。名字错了不会报错，只会静默走默认的 `B .` 死循环
2. **必须清中断标志**。不清就会反复进中断，主循环饿死（详见 [[knowledge/embedded/03-嵌入式C语言的自我修养\|四层硬功夫]] 里「写 1 清零」那节）

### 1.4 右栏：头文件的四层结构

从下往上，一层包一层：

| 层 | 文件 | 内容 | 谁提供 |
|:--|:--|:--|:--|
| ④ 配置 | `stm32f10x_conf.h` | 决定哪些外设头文件被包含 | 你改 |
| ③ 库函数 | `stm32f10x_ppp.c/.h`、`misc.c/.h` | 操作寄存器的 C 函数封装 | ST |
| ② 外设寄存器 | `stm32f10x.h` | 外设结构体、基址、中断号 | ST |
| ① 内核寄存器 | `core_cm3.c/.h` | NVIC / SCB / SysTick / DWT | ARM |

#### ① `core_cm3.h`：Cortex-M3 内核

定义的是**内核**里的东西，和具体芯片无关（F103/F407 只要是 Cortex-M3 都一样）：

```c
typedef struct {
    __IO uint32_t ISER[8];      // 中断使能
    __IO uint32_t ICER[8];      // 中断清除
    ...
} NVIC_Type;

typedef struct {
    __IO uint32_t CTRL;
    __IO uint32_t LOAD;
    __IO uint32_t VAL;
    __I  uint32_t CALIB;
} SysTick_Type;

#define NVIC    ((NVIC_Type *) 0xE000E100)
#define SysTick ((SysTick_Type *) 0xE000E010)
```

`__IO` 展开就是 `volatile` —— 这是寄存器定义必须加 `volatile` 的由来。

#### ② `stm32f10x.h`：外设寄存器

```c
typedef struct {
    __IO uint32_t CRL, CRH, IDR, ODR, BSRR, BRR, LCKR;
} GPIO_TypeDef;

#define GPIOA  ((GPIO_TypeDef *) 0x40010800UL)
#define RCC    ((RCC_TypeDef *)  0x40021000UL)
```

同时定义了中断编号：

```c
typedef enum {
    WWDG_IRQn = 0,
    PVD_IRQn  = 1,
    ...
    TIM2_IRQn = 28,
} IRQn_Type;
```

#### ③ 库函数层

`stm32f10x_gpio.c` 这类文件，本质是把寄存器操作包成函数：

```c
void GPIO_SetBits(GPIO_TypeDef* GPIOx, uint16_t GPIO_Pin)
{
    GPIOx->BSRR = GPIO_Pin;      // 底层就这一行
}
```

`misc.c` 比较特殊，它管的是**内核**外设（NVIC 优先级分组、SysTick 时钟源），不是 STM32 外设：

```c
void NVIC_PriorityGroupConfig(uint32_t NVIC_PriorityGroup);   // 优先级分组
void NVIC_Init(NVIC_InitTypeDef* NVIC_InitStruct);           // 中断使能
void SysTick_CLKSourceConfig(uint32_t SysTick_CLKSource);    // SysTick 时钟源
```

#### ④ `stm32f10x_conf.h`：总开关

```c
/* 用哪个外设就取消注释哪一行 */
#include "stm32f10x_gpio.h"
#include "stm32f10x_rcc.h"
#include "stm32f10x_usart.h"
//#include "stm32f10x_adc.h"
//#include "stm32f10x_spi.h"
```

**作用**：`stm32f10x.h` 末尾会 `#include "stm32f10x_conf.h"`（前提是定义了 `USE_STDPERIPH_DRIVER` 宏），于是所有你启用的外设头文件被一次性包含进来。

**好处**：编译快（不用的不编译）、依赖清晰（看这一个文件就知道工程用了哪些外设）。

### 1.6 为什么这样分层

| 分层 | 为什么独立出来 |
|:--|:--|
| 启动文件用汇编 | 上电那一刻 C 环境还不存在（栈都没设），只能用汇编 |
| `SystemInit` 单独一个文件 | 时钟配置和业务无关，换晶振/换频率只改这一处 |
| 中断处理单独一个文件 | 中断是「被动触发」的，和主流程分离，便于审阅 |
| 寄存器定义和库函数分开 | 寄存器是芯片事实（不可改），库函数是封装（可替换成 HAL/LL/裸机） |
| `conf.h` 做总开关 | 用「配置」而非「裁剪文件」来控制编译范围 |

**核心思想**：**把「芯片事实」「厂商封装」「你的业务」三层彻底分开**。所以后来 ST 能推出 HAL 库替换标准库，而不动启动文件和你的业务代码。

### 1.7 和你现有裸机路线的对应

你现在走的是 cpq 裸机路线（GCC + Makefile + 直接操作寄存器），标准库是另一条路。两者的对应关系：

| 标准库 | 裸机（cpq） | 本质 |
|:--|:--|:--|
| `startup_stm32f10x_hd.s` | `main.c` 里的 `_reset` + 向量表数组 | 同一件事，一个用汇编一个用 C |
| `__main`（库提供） | `_reset` 里的两个 for 循环 | 拷 `.data` + 清 `.bss` |
| `SystemInit()` | `clock_init()` / `sysinit.c` | 配时钟树 |
| `GPIO_Init()` | `gpio_init()` | 写 MODER/OTYPER/OSPEEDR/PUPDR |
| `stm32f10x.h` 的 `GPIO_TypeDef` | `hal.h` 的 `struct gpio` | 结构体映射寄存器 |
| `stm32f10x_it.c` | `TIM2_IRQHandler` 直接写在 `main.c` | 同名函数覆盖弱符号 |

**两条路的优劣**：

| | 标准库 + Keil | 裸机 + GCC |
|:--|:--|:--|
| 上手速度 | 快（模板一建就能跑） | 慢（链接脚本、启动代码都要自己写） |
| 理解深度 | 容易停在「调库」 | 必须理解每个寄存器 |
| 可移植性 | 绑 Keil / 绑 ST 库 | 换编译器只改 Makefile |
| 适合 | 项目起步、快速验证 | 学习原理、面试讲得清 |

**建议**：入门用标准库跑通（建立整体认知），然后**用裸机路线重做一遍**（这正是你 STAGE 2 在做的事）。两条路都走过，面试时「标准库背后做了什么」才答得出来。

### 2.2 Cortex-M3 的四条总线：为什么不是一条

图上 Cortex-M3 右边伸出四根线，标着 `ICode` / `DCode` / `System` / `DMA`。这是理解整个结构的关键。

| 总线 | 走什么 | 连到哪 |
|:--|:--|:--|
| **ICode** | 取**指令** | Flash 接口 |
| **DCode** | 取**常量数据**（`const` 数组、字面量） | Flash 接口 |
| **System** | 访问**外设和 SRAM** | 总线矩阵 → AHB |
| **DMA** | DMA 控制器访问存储器 | 总线矩阵 |

前两条分开，就是著名的**哈佛架构**（指令和数据走不同的路）。为什么？

```c
const uint8_t font[] = {...};   // 放 Flash
int main(void) {
    for (int i = 0; i < 100; i++)
        lcd_write(font[i]);     // 一边取指令，一边读 font
}
```

这个循环里，CPU **同时**要取指令（`ICode`）和读 `font`（`DCode`）。如果只有一条总线，两者就要排队，速度直接减半。分成两条就能并行。

> 这叫「改进的哈佛架构」——对 Flash 是哈佛（指令/数据分开），对 SRAM 和外设是冯·诺依曼（共用地址空间）。所以你在 C 里能用指针指向任何地址，但 Flash 的取指和数据读在硬件上是两条路。

**DMA 总线单独一条**也很关键：DMA 搬运数据时不占用 CPU 的总线，两者可以同时跑。这就是 DMA 能「不占用 CPU」的硬件原因，不是软件魔法。

---

### 2.3 总线矩阵：解决「抢路」问题

四根主总线（CPU 三条 + DMA 一条）最后都汇到中间那个竖着的「**总线矩阵**」框里。

矩阵的作用是**仲裁**：它决定这一拍谁用哪条从设备（Flash / SRAM / FSMC / AHB 桥）。

| 场景 | 矩阵怎么处理 |
|:--|:--|
| CPU 取指 + CPU 读 SRAM | 不冲突，并行（不同从设备） |
| CPU 读 SRAM + DMA 写 SRAM | **冲突**，矩阵仲裁，一方等一拍 |
| CPU 和 DMA 都在访问**同一个**外设 | 冲突，仲裁 |

所以「用了 DMA 就完全不影响 CPU」这个说法是**不准确的**。准确说法是：**访问不同目标时并行，访问同一个目标时排队**。做高速采集时如果发现 CPU 变慢，就要查是不是和 DMA 抢同一个 SRAM 区。

---

### 2.4 存储器侧：四个方块

矩阵往右伸出四路：

| 方块 | 是什么 | 备注 |
|:--|:--|:--|
| **Flash 接口** → **Flash** | 片上程序存储器 | 取指走这里；F103 通常 64 KB~512 KB |
| **SRAM** | 片上运行内存 | 变量、栈、堆；F103 常见 20 KB / 48 KB / 64 KB |
| **FSMC** | 灵活的静态存储器控制器 | 接**外部** SRAM / NOR / LCD 屏 |
| **SDIO** | SD 卡接口 | 读 SD 卡 |

**Flash 接口这个框容易被忽略，但很重要**：它不是简单的「一根线连到 Flash」。CPU 跑 72 MHz，而 Flash 的读取速度跟不上，所以中间有等待周期（Latency）。F103 在 48 MHz 以上要配 2 个等待周期，这行代码在标准库里是：

```c
FLASH_SetLatency(FLASH_Latency_2);   // 48~72 MHz 要 2 个 wait state
```

F407 更狠：168 MHz 下要 **5 个等待周期**，所以 ST 加了 **ART Accelerator**（自适应实时加速器）来抵消等待时间，做成「等效 0 等待」。这也是为什么 F407 的 Flash 那一段和 F103 长得不一样。

> 这条正是 `04-ZLG-CAN库与UDS刷写详解` 里 9.8 节第 9 条提到的「Flash 驱动要配等待周期」。

---

### 2.5 AHB 与 APB：为什么要分快慢两条

总线矩阵往下，是 **AHB 系统总线**，再往下经过两个桥接分成 **APB1** 和 **APB2**。

| 总线 | 全称 | F103 最高频率 | 挂什么 |
|:--|:--|:--:|:--|
| **AHB** | Advanced High-performance Bus | 72 MHz | 总线矩阵、DMA、RCC、Flash 接口 |
| **APB2** | Advanced Peripheral Bus 2（高速） | 72 MHz | GPIO、USART1、SPI1、ADC、TIM1/TIM8、AFIO、EXTI |
| **APB1** | Advanced Peripheral Bus 1（低速） | 36 MHz | TIM2~7、USART2~5、I2C、SPI2/3、CAN、USB、DAC、RTC、看门狗 |

**为什么分两条？** 因为不是所有外设都需要跑满速：

- GPIO 翻转、串口这些**要快**，放 APB2
- I2C、CAN、USB 这些**本身协议就慢**，放 APB1，跑 36 MHz 够用
- 分两条还能**省功耗**、**简化时序收敛**

**这是最容易踩的坑来源**——`RCC_APB1PeriphClockCmd()` 和 `RCC_APB2PeriphClockCmd()` 是两个不同函数，传错枚举值后果是「时钟没开，外设写寄存器无效，但程序不报错」：

```c
// 对：GPIO 在 APB2
RCC_APB2PeriphClockCmd(RCC_APB2Periph_GPIOA, ENABLE);

// 错：用 APB1 开 GPIOA —— 编译通过，运行无效
RCC_APB1PeriphClockCmd(RCC_APB2Periph_GPIOA, ENABLE);
```

更隐蔽的是**定时器时钟不等于总线时钟**：APB1 上的定时器，如果 APB1 分频系数 ≠ 1，定时器时钟 = APB1 × 2 = 72 MHz。所以 `TIM2` 挂在 36 MHz 的 APB1 上，但它的计数时钟其实是 72 MHz。算波特率/定时周期时搞错这一点，出来的时间会差一倍。

---

### 2.6 DMA：那两根虚线在说什么

图左下方 DMA1、DMA2 各有若干「通道」，右边伸出**棕色虚线**指向外设，标着「DMA 请求」。

```
外设（比如 ADC、USART）--DMA 请求--> DMA 控制器 --DMA 总线--> SRAM
```

**流程**：外设准备好数据 → 拉一根「DMA 请求」线 → DMA 控制器接管 → 通过自己的总线把数据搬进 SRAM → 搬完发中断通知 CPU。

| DMA | 通道数（F103） | 典型用途 |
|:--|:--:|:--|
| **DMA1** | 7 | ADC、SPI/I2C、USART、TIM |
| **DMA2** | 5（仅大容量型号有） | SDIO、TIM1/8、ADC3、DAC |

**通道是硬连线的，不能随便选**。哪个外设能触发哪个通道，在参考手册的「DMA 请求映射表」里写死。比如 F103 的 `USART1_TX` 只能用 `DMA1 通道 4`——选错了就是「配好了但永远不触发」。

> F407 从「通道」改成了「**流（Stream）+ 通道（Channel）**」两级：DMA1/DMA2 各 8 个流，每个流可选 8 个通道之一。灵活了，但配错的机会也更多。

---

### 2.7 这张图和你手上的 F407 差在哪

你现在的主线是 F407，不能照搬 F103 的结论。逐项对照：

| 项 | F103（本图） | F407 |
|:--|:--|:--|
| 内核 | Cortex-M3 | **Cortex-M4F**（带 FPU + DSP 指令） |
| 主频 | 72 MHz | **168 MHz** |
| 内核总线 | ICode / DCode / System / DMA | 同样四条，名称一致 |
| 总线矩阵 | 单层矩阵 | **多层矩阵**，主从设备更多 |
| AHB | 一条 | **AHB1 + AHB2** 两条 |
| APB1 上限 | 36 MHz | **42 MHz** |
| APB2 上限 | 72 MHz | **84 MHz** |
| Flash 加速 | 等待周期 | **ART Accelerator**（等效 0 等待） |
| DMA | 通道（7 + 5） | **流 + 通道**（8 + 8） |
| 外设 | 少 | 多（以太网、摄像头接口、加密…） |

**必须记住的三条差异**：

1. **F407 的 APB1/APB2 上限变了**（42/84，不是 36/72）。移植时若沿用 36/72 的假设，算出来的波特率会错。
2. **ART Accelerator 不是 Cache**。它做的是「预取 + 指令/数据缓冲」，语义上等价于 0 等待 Flash，但你不用手动清它。（真正需要手动清 Cache 的是 S32K312 的 Cortex-M7，这是你 STAGE 6 要处理的事。）
3. **DMA 是流+通道两级**。从 F103 抄 DMA 配置代码到 F407 一定编不过，因为结构体都不一样。

> 顺带说明：这张图的**结构逻辑**（哈佛总线 / 矩阵仲裁 / AHB+APB 分层 / DMA 独立总线）在 F407 上完全成立，变的只是数量和频率。所以先看懂 F103 这张图，再看 F407 的图会快很多——这也是江科大这套教程仍然值得看的原因。

---

### 2.8 这张图对写代码的实际影响

不是「知道了就行」，这四条会直接影响你写对代码：

| 现象 | 根因在图上的哪里 | 怎么查 |
|:--|:--|:--|
| 外设配了没反应，不报错 | 时钟没开（RCC 挂在 AHB，但要手动使能到具体外设） | 查 `RCC_APBxPeriphClockCmd` 用的是 1 还是 2 |
| 定时器时间差一倍 | APB1 分频 ≠ 1 时定时器时钟 ×2 | 查 `RCC_CFGR` 的 PPRE1 |
| DMA 配好不触发 | 通道（流）选错 | 查参考手册的 DMA 请求映射表 |
| 程序跑着突然 HardFault | 访问了未使能时钟的外设（总线错误） | 查是不是漏了 RCC 使能 |

**最后一条值得展开**：在 STM32 上访问一个**时钟没开**的外设寄存器，不是「读到 0」这么温和，而是触发**总线错误 → HardFault**。所以你调试时如果发现「一进某个函数就进 HardFault」，先看那个外设的时钟使能了没有。图上「RCC 挂在 AHB 上、控制所有外设的时钟」这个位置，就是这条规则的来源。

### 2.9 和第一章的关系

两章合起来是一条完整的链：

| 看什么 | 第一章（工程架构） | 第二章（系统结构） |
|:--|:--|:--|
| 层次 | 软件文件怎么组织 | 硬件模块怎么连接 |
| 起点 | `startup_xx.s` 的向量表 | 上电后内核从 Flash 取第一条指令 |
| 中间 | `SystemInit()` 配时钟 | RCC 通过 AHB 分发时钟到 APB1/APB2 |
| 终点 | `main()` 里调 `GPIO_Init()` | 写 APB2 上的 GPIO 寄存器 → 引脚电平变化 |

**一句话串起来**：`SystemInit()` 干的事，就是按第二章这张图把时钟树配好（PLL → AHB → APB1/APB2 分频），让后面所有外设都能被访问。第一章的 1.3 节说「`SystemInit` 里配时钟」，第二章的 2.5 节说「配的是哪条总线、上限多少」——是同一件事的两个视角。

### 3.2 命名规则：GPIOA / GPIOB / PA0

底下的字幕说的就是这条：

> GPIO 外设的名称是按照 GPIOA、GPIOB、GPIOC 等等这样来命名的

规则很机械：

| 写法 | 含义 | 举例 |
|:--|:--|:--|
| `GPIOx` | 第 x 个端口（外设名字） | `GPIOA`、`GPIOB`、`GPIOC` |
| `Pxnn` | 第 x 个端口的第 nn 号引脚 | `PA0`、`PB7`、`PC13` |
| `GPIO_Pin_n` | 库函数里的引脚掩码 | `GPIO_Pin_0` → `0x0001`，`GPIO_Pin_13` → `0x2000` |

一个端口固定 **16 个引脚**（`0`~`15`），所以：

- `GPIO_Pin_n` 的 n 只能是 0~15
- 掩码是 `1 << n`，最大 `1 << 15 = 0x8000`
- 一个 16 位寄存器刚好能装下一个端口的全部引脚状态 —— 这不是巧合，是设计

**这条规则为什么重要**：`P` 后面那个字母是**端口**，后面数字是**引脚号**。`PB7` 是 GPIOB 的第 7 脚，不是「第 B7 脚」。新手常把 `PA13` 写成 `GPIOA_Pin13`（对）和 `GPIO_Pin_13`（也对），但**跨端口就错**——`GPIO_Pin_13` 不带端口信息，必须配合 `GPIOx` 一起用。

---

### 3.3 寄存器：图里那个绿块拆开是什么

图上「寄存器」只是一块绿方块，实际是**一组**寄存器。F103 的每个 GPIOx 有 7 个：

| 寄存器 | 全称 | 干什么 | 位宽 |
|:--|:--|:--|:--|
| `CRL` | Configuration Register Low | 配置 **Px0~Px7** 的模式 | 32 |
| `CRH` | Configuration Register High | 配置 **Px8~Px15** 的模式 | 32 |
| `IDR` | Input Data Register | 读引脚**当前电平** | 32（只用低 16） |
| `ODR` | Output Data Register | 写输出电平 / 读回上次写的值 | 32（只用低 16） |
| `BSRR` | Bit Set/Reset Register | **原子**置位/复位单个引脚 | 32 |
| `BRR` | Bit Reset Register | 只复位（F1 独有，F4 合并进 BSRR） | 32 |
| `LCKR` | Configuration Lock Register | 锁定配置，防止误改 | 32 |

**为什么配置要分 CRL / CRH 两个**：每个引脚要 4 位（2 位 MODE + 2 位 CNF），16 个引脚就是 64 位，一个 32 位寄存器装不下。所以低 8 脚一个、高 8 脚一个。

```c
// 配置 PA0 为推挽输出、50MHz（标准库帮你算好了，裸机要自己移位）
// CRL 里 PA0 占 bit[3:0]：MODE=11(50MHz) CNF=00(推挽输出) → 0x3
GPIOA->CRL &= ~(0xF << 0);   // 先清 4 位
GPIOA->CRL |=  (0x3 << 0);   // 再写
```

**`ODR` 和 `BSRR` 的区别是这一章最实用的一条**：

```c
// 写法 A：读-改-写，有竞态
GPIOA->ODR |= (1 << 5);      // 编译成 LDR / ORR / STR 三条指令

// 写法 B：原子操作，一条指令
GPIOA->BSRR = (1 << 5);      // 置位 PA5，写 1 生效
GPIOA->BSRR = (1 << (5 + 16)); // 复位 PA5（高 16 位是复位）
```

如果中断里也在改同一个 `ODR`，写法 A 会出现「主循环读到的旧值覆盖了中断的修改」。写法 B 是硬件原子操作，没有这个问题。**这就是为什么中断和主循环共用一个端口时，必须用 `BSRR` 而不是 `|=`。**

---

### 3.4 驱动器：绿块到引脚之间的那一层

图上右侧的「驱动器」是**电气层**，寄存器里的 `0/1` 到这里才变成真正的电压。它决定三件事：

| 项 | 选项 | 什么时候用 |
|:--|:--|:--|
| **方向** | 输入 / 输出 | 由 `CRL/CRH` 的 MODE 位定 |
| **输出类型** | 推挽（Push-Pull）/ 开漏（Open-Drain） | 推挽能主动输出高低；开漏只能拉低，高电平靠外部上拉 |
| **上下拉** | 浮空 / 上拉 / 下拉 | 输入时决定「没接东西」读到什么 |

**推挽 vs 开漏**这一对最常考：

| | 推挽 | 开漏 |
|:--|:--|:--|
| 高电平 | 内部主动拉到 VDD | **高阻**，靠外部上拉电阻 |
| 低电平 | 内部主动拉到 GND | 内部拉到 GND |
| 能否线与 | ❌ 两个推挽对接会短路 | ✅ 多个开漏可以接一起（I2C 就是这样） |
| 典型用途 | LED、普通数字输出 | **I2C 的 SDA/SCL、多机共享信号** |

I2C 必须用开漏，因为总线上挂多个设备，任何一个拉低都应该是低电平——推挽做不到这一点，两个推挽一个输出高一个输出低会直接短路烧引脚。

**上拉/下拉**决定「悬空时读到什么」：

```c
// 按键接法：一端接引脚，一端接 GND
// 不按下 = 悬空 = 读数随机 → 必须开内部上拉
GPIO_InitStructure.GPIO_Mode = GPIO_Mode_IPU;   // IPU = Input Pull-Up
```

这条正是 `06-ESP32C3烧录与裸机固件实战` 里按键抖动/误触发的根源之一：输入没配上拉，悬空时读到的是天线拾取的噪声。

### 3.5 为什么按端口分组，而不是按功能

图上把 16 个引脚打包成一个 `GPIOA`，而不是「LED 一组、串口一组」。原因是**物理和电气**：

1. **引脚是物理实体**，一个封装脚固定连到某个端口某一位，不能软件重排
2. **16 位刚好一个寄存器**，读一次 `IDR` 就拿到整个端口的电平，效率最高
3. **端口时钟独立**，`RCC_APB2Periph_GPIOA` 单独使能，不用的端口可以不供电（省功耗）

代价是：**同一个功能可能散落在不同端口**。比如 USART1 的 TX/RX 在 PA9/PA10，USART2 在 PA2/PA3，TIM2 的四个通道在 PA0/PA1/PA2/PA3。所以配外设时总要查「这个功能能映射到哪些引脚」——这就是**复用功能（AF）**要解决的问题，留到后面章节讲。

### 3.6 这张图和你手上的 F407 差在哪

和第二章程一样，F103 的结论不能全照搬：

| 项 | F103（本图） | F407 |
|:--|:--|:--|
| 挂在哪条总线 | **APB2** | **AHB1**（注意！不是 APB2） |
| 配置寄存器 | `CRL` / `CRH`（4 位/引脚） | `MODER` / `OTYPER` / `OSPEEDR` / `PUPDR`（**每个属性一个寄存器，2 位/引脚**） |
| 复位寄存器 | `BRR` + `BSRR` | 只有 `BSRR`（`BRR` 被删了） |
| 复用功能 | 靠 `AFIO` 重映射 | `AFR[0]` / `AFR[1]`，每个引脚 4 位可选 16 种 AF |
| 输出速度 | 2 / 10 / 50 MHz 三档 | 4 / 25 / 50 / 100 MHz 四档 |
| 时钟使能函数 | `RCC_APB2PeriphClockCmd` | `RCC_AHB1PeriphClockCmd` |

**第一条最容易踩**：从 F103 抄过来的代码写

```c
RCC_APB2PeriphClockCmd(RCC_APB2Periph_GPIOA, ENABLE);   // F103 对
```

搬到 F407 上，这行**编译能过**（宏还在），但 GPIOA **永远不会有时钟**，接着所有 GPIO 操作全部无效，甚至 HardFault。F407 上必须是：

```c
RCC_AHB1PeriphClockCmd(RCC_AHB1Periph_GPIOA, ENABLE);   // F407 对
```

> 回看第二章 2.5 节那张 APB1/APB2 表——F103 的 GPIO 在 APB2，F407 移到了 AHB1。这就是为什么那张表必须按型号分别记，不能混。

### 3.7 对写代码的实际影响

| 现象 | 根因 | 怎么查 |
|:--|:--|:--|
| 输出电平不变 | 端口时钟没使能，或引脚被配成输入 | 查 RCC 使能 + `CRL/CRH`（F4 查 `MODER`） |
| 中断里改引脚，主循环改丢了 | 用了 `ODR \|=` 而不是 `BSRR` | 全局搜 `ODR \|=` |
| 输入读数乱跳 | 浮空输入没配上拉/下拉 | 查 `GPIO_Mode_IPU/IPD` |
| I2C 通信失败 | SDA/SCL 配成推挽 | 必须开漏（`GPIO_Mode_AF_OD`） |
| 同一个引脚功能不对 | 复用功能没配对 | F1 查 AFIO 重映射，F4 查 `AFR[]` |
| 上电瞬间引脚有毛刺 | 配置前引脚是默认状态（浮空输入） | 先配电平再配方向，或外部加上下拉 |

**最后一条值得展开**：引脚复位后的默认状态是**浮空输入**。如果你要驱动一个继电器/LED，从复位到 `GPIO_Init()` 执行之间有一小段时间引脚是悬空的。对时间敏感的外设，正确顺序是**先把 `ODR` 设成期望电平，再配成输出模式**，这样切换瞬间不会产生毛刺。

### 3.8 三章串起来

| 章 | 视角 | 一句话 |
|:--|:--|:--|
| 一 | 软件工程 | 哪个文件放什么、启动怎么走 |
| 二 | 芯片级硬件 | 内核怎么通过总线矩阵连到 APB2 |
| 三 | 外设级硬件 | APB2 上的 GPIO 内部怎么组织 |

**一条完整的路径**：`main()` 里调 `GPIO_Init()` → 写 APB2（F4 是 AHB1）上的 `CRL/CRH` → 驱动器按配置切换推挽/开漏 → 引脚电平变化 → LED 亮。

第二章告诉你「GPIO 挂在 APB2 上，要先开时钟」；这一章告诉你「开了时钟之后，具体写哪几个寄存器、为什么输入要上拉、为什么中断里要用 BSRR」。两章合起来，`GPIO_Init()` 这个函数就不再是黑盒了。
