# 05 · 单元测试篇（unit-testing）

> 路径：`05-unit-testing/`
> 目标：把单元测试接进构建系统，让 `ctest` 成为一条命令。

返回 [[knowledge/embedded/cmake-examples/index\|📘 cmake-examples 总览]]

## 📑 本节示例

| 示例 | 测试框架 | 引入方式 |
|:--|:--|:--|
| `boost` | Boost.Test | `find_package(Boost COMPONENTS unit_test_framework)` |
| `catch2-vendored` | Catch2 | 源码 vendor + `add_subdirectory` |
| `google-test-download` | GoogleTest | 配置阶段下载 + `add_subdirectory` |

三个示例的骨架完全一致，差别只在**框架怎么来**。

---

## 一、公共骨架：CTest 三步

无论用哪个框架，接入都是这三步：

```cmake
# 1) 开启测试
enable_testing()

# 2) 编译出测试可执行文件，并链接被测库 + 测试框架
add_executable(unit_tests unit_tests.cpp)
target_link_libraries(unit_tests PRIVATE example_lib test_framework)

# 3) 注册测试用例
add_test(test_all unit_tests)
```

然后：

```bash
cd build
cmake .. && make
ctest                        # 跑全部
ctest -V                     # 显示输出
ctest -R test_all            # 按名字过滤
ctest --output-on-failure    # 只显示失败的详细输出
```

> `enable_testing()` 必须写在**顶层 CMakeLists.txt**，写在子目录里会导致 `ctest` 找不到测试。

## 二、boost —— 系统安装的框架

### 2.1 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.5)
project(boost_unit_test)

find_package(Boost 1.46.1 REQUIRED COMPONENTS unit_test_framework)

# 被测库
add_library(example_boost_unit_test
    Reverse.cpp
    Palindrome.cpp
)

target_include_directories(example_boost_unit_test
    PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}
)

target_link_libraries(example_boost_unit_test
    PUBLIC Boost::boost
)

#############################################
# 单元测试

enable_testing()

add_executable(unit_tests unit_tests.cpp)

target_link_libraries(unit_tests
    example_boost_unit_test
    Boost::unit_test_framework
)

target_compile_definitions(unit_tests
    PRIVATE BOOST_TEST_DYN_LINK
)

add_test(test_all unit_tests)
```

### 2.2 三个要点

**1. `Boost::boost` 是 header-only 接口 target**

Boost 大部分组件是纯头文件，`Boost::boost` 只提供 include 路径，不链接任何二进制。

**2. `unit_test_framework` 是编译好的库**

需要 `libboost_unit_test_framework.so`，所以 `find_package` 时要 `COMPONENTS unit_test_framework`。

**3. `BOOST_TEST_DYN_LINK` 不能漏**

```cmake
target_compile_definitions(unit_tests PRIVATE BOOST_TEST_DYN_LINK)
```

Boost.Test 有静态链接和动态链接两种模式。用动态库（`.so`）时必须定义这个宏，否则会出现 `undefined reference to main` 或重复符号 —— 因为 Boost.Test 自带 `main()`，动态链接模式下要靠宏来正确启用。

### 2.3 依赖安装

```bash
sudo apt-get install libboost-all-dev
# 或只装需要的
sudo apt-get install libboost-test-dev
```

## 三、catch2-vendored —— 源码内嵌

### 3.1 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.5)
project(catch2_unit_test)

set(CMAKE_CXX_STANDARD 11)

# 引入 vendored 的 catch2
add_subdirectory(3rd_party/catch2)

add_library(example_unit_test
    Reverse.cpp
    Palindrome.cpp
)

#############################################
# 单元测试

enable_testing()

add_executable(unit_tests unit_tests.cpp)

target_link_libraries(unit_tests
    example_unit_test
    Catch2::Test
)

add_test(test_all unit_tests)
```

### 3.2 vendored 的 Catch2 怎么写的

```cmake
# 3rd_party/catch2/CMakeLists.txt
cmake_minimum_required(VERSION 3.0)
project(catch2)

# 纯头文件库 → 用 INTERFACE
add_library(Catch2 INTERFACE)
add_library(Catch2::Test ALIAS Catch2)
target_include_directories(Catch2 INTERFACE ${CMAKE_CURRENT_SOURCE_DIR})
```

只用三行就造出一个「能被 `target_link_libraries` 消费的 target」。这就是 `INTERFACE` 库最典型的用途 —— **给纯头文件第三方库套一层 CMake 外壳**（俗称 shim）。

### 3.3 Vendoring 的优缺点

| 优点 | 缺点 |
|:--|:--|
| 离线可构建，不依赖网络 | 仓库变大 |
| 版本完全锁定 | 升级要手动替换文件 |
| 改第三方代码很方便（打补丁） | 代码审计范围扩大 |

引入方式：

```bash
# git submodule
git submodule add https://github.com/catchorg/Catch2.git 3rd_party/catch2

# 或直接复制（catch2 单头文件版本只要一个 catch.hpp）
```

### 3.4 Catch2 v2 与 v3 的差异

| | Catch2 v2 | Catch2 v3 |
|:--|:--|:--|
| 形态 | 单头文件 `catch.hpp` | 编译成库 |
| CMake target | `Catch2::Catch2` | `Catch2::Catch2WithMain` |
| 依赖 | 无 | 需要编译 |

> 现代要配 `catch_discover_tests()`：
> ```cmake
> include(Catch)
> catch_discover_tests(unit_tests)
> ```
> 这会把测试可执行文件里**每个 `TEST_CASE` 都注册成独立 CTest 用例**，而不是整个可执行文件算一个。

## 四、google-test-download —— 配置阶段下载

### 4.1 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.5)
project(google_test_example)

add_library(example_google_test
    Reverse.cpp
    Palindrome.cpp
)

#############################################
# 单元测试

add_subdirectory(3rd_party/google-test)

enable_testing()

add_executable(unit_tests unit_tests.cpp)

target_link_libraries(unit_tests
    example_google_test
    GTest::GTest
    GTest::Main
)

add_test(test_all unit_tests)
```

### 4.2 下载逻辑写在 `3rd_party/google-test/CMakeLists.txt`

```cmake
# 1) 用 configure_file 生成一个独立的小工程
configure_file(CMakeLists.txt.in googletest-download/CMakeLists.txt)

# 2) 配置这个小工程（配置阶段就会触发下载）
execute_process(COMMAND ${CMAKE_COMMAND} -G "${CMAKE_GENERATOR}" .
    RESULT_VARIABLE result
    WORKING_DIRECTORY ${CMAKE_CURRENT_BINARY_DIR}/googletest-download)
if(result)
    message(FATAL_ERROR "CMake step for googletest failed: ${result}")
endif()

# 3) 构建（实际执行 download 步骤）
execute_process(COMMAND ${CMAKE_COMMAND} --build .
    RESULT_VARIABLE result
    WORKING_DIRECTORY ${CMAKE_CURRENT_BINARY_DIR}/googletest-download)
if(result)
    message(FATAL_ERROR "Build step for googletest failed: ${result}")
endif()

# 4) 防止污染父工程的编译选项
set(gtest_force_shared_crt ON CACHE BOOL "" FORCE)
set(INSTALL_GTEST OFF CACHE BOOL "" FORCE)
set(INSTALL_GMOCK OFF CACHE BOOL "" FORCE)

# 5) 把下载下来的源码加进本工程
add_subdirectory(${CMAKE_CURRENT_BINARY_DIR}/googletest-src
                 ${CMAKE_CURRENT_BINARY_DIR}/googletest-build)

# 6) 补上命名空间别名
if(NOT TARGET GTest::GTest)
    add_library(GTest::GTest ALIAS gtest)
    add_library(GTest::Main  ALIAS gtest_main)
endif()
```

`CMakeLists.txt.in` 是一个只包含 `ExternalProject_Add` 的迷你工程：

```cmake
cmake_minimum_required(VERSION 3.5)
project(googletest-download NONE)

include(ExternalProject)
ExternalProject_Add(googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        release-1.12.1
    SOURCE_DIR     "${CMAKE_CURRENT_BINARY_DIR}/googletest-src"
    BINARY_DIR     "${CMAKE_CURRENT_BINARY_DIR}/googletest-build"
    CONFIGURE_COMMAND ""
    BUILD_COMMAND     ""
    INSTALL_COMMAND   ""
    TEST_COMMAND      ""
)
```

### 4.3 为什么这套操作这么绕

这是 **`FetchContent` 出现之前（CMake < 3.11）** 的标准做法：

1. **配置阶段就要有源码** —— 因为后面要 `add_subdirectory` 它
2. `ExternalProject_Add` 默认是**构建阶段**动作，所以要 `execute_process` 手动驱动（配置 + 构建两个阶段）
3. `CONFIGURE_COMMAND ""` 等空命令是为了**只下载不构建**，构建交给外层 `add_subdirectory`

### 4.4 现代替代：`FetchContent`（强烈推荐）

```cmake
include(FetchContent)

FetchContent_Declare(
    googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        release-1.12.1
)
FetchContent_MakeAvailable(googletest)

target_link_libraries(unit_tests PRIVATE
    example_lib
    GTest::gtest_main
)
```

**4 行 vs 40 行**。`FetchContent` 还支持：

| 能力 | 说明 |
|:--|:--|
| `FETCHCONTENT_SOURCE_DIR_<NAME>` | 指定本地已有源码，离线构建 |
| `FETCHCONTENT_FULLY_DISCONNECTED` | 完全禁网模式 |
| `FETCHCONTENT_UPDATES_DISCONNECTED` | 只在首次下载 |
| 自动缓存 | 同一份源码多个工程共用 |

> 本示例的价值在于「理解老项目为什么这么写」，**新项目直接用 `FetchContent`。**

### 4.5 `GTest::GTest` 与 `GTest::Main`

| target | 内容 |
|:--|:--|
| `GTest::GTest` | gtest 库本身，需要你自己写 `main()` |
| `GTest::Main` | gtest + 自带 `main()`，测试文件里只写 `TEST()` 即可 |
| `GTest::GMock` / `GMock::Main` | 加 gmock 支持 |

一般链 `GTest::Main` 最省事。

## 五、三种引入方式对比

| 方式 | 示例 | 是否需要网络 | 版本控制 | 推荐度 |
|:--|:--|:--|:--|:--:|
| 系统包 `find_package` | boost | 装包时 | 由发行版决定 | ✅✅ 团队内网常用 |
| 源码 vendoring | catch2-vendored | 首次 | 完全锁定 | ✅ 嵌入式常用 |
| 配置阶段下载 | google-test-download | 每次干净构建 | 由 URL 决定 | ⚠️ 老做法 |
| **`FetchContent`** | — | 首次 | 完全锁定 | ✅✅✅ **现代首选** |
| Conan / vcpkg | 07 章 | 首次 | 完全锁定 | ✅✅ 大工程 |

### 嵌入式场景建议

| 约束 | 选择 |
|:--|:--|
| 产线/离线构建 | vendoring 或 `FetchContent` + 本地 source dir |
| CI 有网 | `FetchContent` |
| 要求可审计、版本冻结 | vendoring（源码进仓库） |
| 团队统一依赖 | Conan / vcpkg |

## 六、测试进阶

### 6.1 每个用例独立注册

```cmake
# Catch2
include(Catch)
catch_discover_tests(unit_tests)

# GoogleTest（3.10+ 内置）
include(GoogleTest)
gtest_discover_tests(unit_tests)
```

效果：`ctest -R "Reverse.*Empty"` 能精确跑单个 case，CI 报告也更细。

### 6.2 给测试传参数

```cmake
add_test(NAME test_filter
         COMMAND unit_tests --gtest_filter=ReverseTest.*)
```

### 6.3 属性设置

```cmake
set_tests_properties(test_all PROPERTIES
    TIMEOUT 30              # 超时秒数
    ENVIRONMENT "LD_LIBRARY_PATH=${CMAKE_BINARY_DIR}/lib"
    LABELS "unit"           # 分类，ctest -L unit
    WILL_FAIL TRUE          # 期望失败（负向测试）
)
```

### 6.4 覆盖率

```bash
cmake .. -DCMAKE_CXX_FLAGS="--coverage" -DCMAKE_EXE_LINKER_FLAGS="--coverage"
make && ctest
gcovr -r . --html-details coverage.html
```

### 6.5 嵌入式怎么办

单元测试跑在主机上（`-DCMAKE_TOOLCHAIN_FILE` 换成宿主编译器），被测的**纯逻辑代码**剥离硬件依赖；硬件相关用 mock 或 HAL 桩。

```
src/          ← 产品代码（交叉编译）
src/logic/    ← 纯逻辑，无硬件依赖
test/         ← 宿主机构建，测 src/logic
hal/          ← 硬件抽象，测试时替换成 mock
```

## 七、本章要点小结

### CTest 命令速查

| 命令 | 作用 |
|:--|:--|
| `enable_testing()` | 开启测试（顶层） |
| `add_test(NAME n COMMAND cmd)` | 注册用例 |
| `set_tests_properties(n PROPERTIES ...)` | 设超时/环境/标签 |
| `ctest` / `ctest -V` / `ctest -R` / `-L` / `--output-on-failure` | 运行 |
| `ctest -N` | 只列出，不跑 |

### 常见坑

| 现象 | 原因 | 解决 |
|:--|:--|:--|
| `ctest` 显示 `No tests were found` | `enable_testing()` 写在子目录 | 移到顶层 |
| Boost.Test 链接失败 | 漏 `BOOST_TEST_DYN_LINK` | 补 `target_compile_definitions` |
| `GTest::Main` 找不到 | 旧版本只有 `gtest` target | 手动 `add_library(GTest::Main ALIAS gtest_main)` |
| 每次构建都重新下载 GTest | `execute_process` 无条件执行 | 换 `FetchContent` |
| 测试跑不起来找不到 `.so` | 动态库路径 | `set_tests_properties(... ENVIRONMENT ...)` |
| 测试代码混进产品二进制 | 测试源文件加进产品 target | 测试独立 target |
