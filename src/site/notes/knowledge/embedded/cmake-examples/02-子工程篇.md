# 02 · 子工程篇（sub-projects）

> 路径：`02-sub-projects/A-basic/`
> 目标：把「一个可执行文件」拆成「多个库 + 一个可执行文件」的多目录工程。

返回 [[knowledge/embedded/cmake-examples/index\|📘 cmake-examples 总览]]

## 一、目录结构

```
02-sub-projects/A-basic/
├── CMakeLists.txt          顶层
├── sublibrary1/            静态库
│   ├── CMakeLists.txt
│   ├── include/sublib1.h
│   └── src/sublib1.cpp
├── sublibrary2/            纯头文件库（INTERFACE）
│   ├── CMakeLists.txt
│   └── include/sublib2.h
└── subbinary/              可执行文件
    ├── CMakeLists.txt
    └── main.cpp
```

依赖关系：

```
subbinary ──▶ sub::lib1 (静态库)
          └─▶ sub::lib2 (接口库，只有头文件)
```

## 二、顶层 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.5)

project(subprojects)

add_subdirectory(sublibrary1)
add_subdirectory(sublibrary2)
add_subdirectory(subbinary)
```

顶层只做两件事：**声明工程 + 挂子目录**。不写任何 `add_library` / `add_executable`。

`add_subdirectory()` 会：

1. 进入指定子目录，读取其中的 `CMakeLists.txt` 并立即执行
2. 该子目录的 target 自动加入本工程，可被后续目录引用
3. **顺序有意义**：被依赖的目录必须写在依赖者之前（`sublibrary1` 在 `subbinary` 之前）

## 三、sub library1 —— 静态库

```cmake
project(sublibrary1)

add_library(${PROJECT_NAME} src/sublib1.cpp)
add_library(sub::lib1 ALIAS ${PROJECT_NAME})

target_include_directories(${PROJECT_NAME}
    PUBLIC ${PROJECT_SOURCE_DIR}/include
)
```

### 两个技巧

**1. 用 `${PROJECT_NAME}` 代替硬编码名字**

`project(sublibrary1)` 之后，`PROJECT_NAME` 就是 `sublibrary1`。改名时只需改 `project()` 一行，后续所有 `add_library` / `target_*` 自动跟随。

> ⚠️ 注意 `PROJECT_NAME` 在**子目录中被 `project()` 重新定义**后，指的是子工程名而非顶层工程名。想跨层引用顶层建议用 `CMAKE_PROJECT_NAME`。

**2. `ALIAS` 加命名空间前缀**

```cmake
add_library(sub::lib1 ALIAS sublibrary1)
```

约定用 `<前缀>::<名字>` 形式，和 `Boost::filesystem`、`Qt5::Core` 风格统一。好处是**依赖者不关心它是本地库还是外部包**。

## 四、sublibrary2 —— 接口库（纯头文件）

```cmake
project(sublibrary2)

add_library(${PROJECT_NAME} INTERFACE)
add_library(sub::lib2 ALIAS ${PROJECT_NAME})

target_include_directories(${PROJECT_NAME}
    INTERFACE
        ${PROJECT_SOURCE_DIR}/include
)
```

### `INTERFACE` 库是什么

| 特点 | 说明 |
|:--|:--|
| 无源文件 | `add_library(x INTERFACE)` 后面**不能**跟源文件 |
| 不产生产物 | 没有 `.a`、没有 `.so`，构建时不编译任何东西 |
| 只传属性 | 作用就是把 include 路径、宏、依赖「打包」给使用者 |
| 属性必须用 `INTERFACE` | 写 `PUBLIC` / `PRIVATE` 会报错，因为它自己不编译 |

### 为什么 header-only 库要用 INTERFACE 而不是直接 `include_directories`

`include_directories(sub library2/include)` 是全局的：整个目录树的所有 target 都能看到这个路径，**依赖关系完全隐形**。而：

```cmake
target_link_libraries(subbinary sub::lib2)
```

明确表达了「subbinary 依赖 sublib2」，依赖图可追踪、可传递、可移植。

## 五、subbinary —— 最终可执行文件

```cmake
project(subbinary)

add_executable(${PROJECT_NAME} main.cpp)

target_link_libraries(${PROJECT_NAME}
    sub::lib1
    sub::lib2
)
```

注意这里**没有写任何 `target_include_directories`** —— 因为 `sub::lib1` 是 `PUBLIC` 传出的 include，`sub::lib2` 是 `INTERFACE` 传出的 include，链接它们就自动获得头文件路径。

> 这就是 CMake 传递性依赖的实际效果：**消费者只需要说「我要谁」，不需要知道「它在哪」。**

注意 `target_link_libraries` 这里没写 `PRIVATE` / `PUBLIC` —— 老式写法会默认按 `PUBLIC` 处理（由 `CMP0022` 策略控制）。**新代码务必显式写作用域。**

## 七、本章要点小结

### `add_subdirectory` vs 其他组织方式

| 方式 | 用途 | 特点 |
|:--|:--|:--|
| `add_subdirectory(dir)` | **子目录子工程** | 同一次配置，target 共享，最常用 |
| `add_subdirectory(dir out)` | 指定输出目录 | 可把子工程产物放别处 |
| `include(xxx.cmake)` | 引入脚本片段 | 不创建新目录作用域，只执行命令 |
| `add_library(x IMPORTED)` | 引用外部已编译库 | 不参与构建，见 01 章 K 例 |

### 三条实践建议

1. **每个目录一个 `CMakeLists.txt`**，责任单一：一个库 / 一个可执行文件
2. **顶层只负责组织和全局策略**，不写具体 target
3. **一律用 `Namespace::Target` 别名跨目录链接**，杜绝硬编码路径和全局 `include_directories`

### 常见坑

| 现象 | 原因 |
|:--|:--|
| `Cannot find source file` | `add_subdirectory` 顺序错了，依赖者在前 |
| `Target "sub::lib1" not found` | 别名所在的子目录还没被 `add_subdirectory` |
| 子工程产物跑到源码目录 | 没指定 `add_subdirectory(dir out)`，或用了 in-source 构建 |
| `PROJECT_NAME` 值不对 | 子目录 `project()` 覆盖了，跨层请用 `CMAKE_PROJECT_NAME` |

### 现代替代：`target_sources` 与对象库

需要把多个子目录的源文件编成一个 target 时：

```cmake
# 顶层
add_executable(app app/main.c)
add_subdirectory(core)      # core 里写 target_sources(app PRIVATE ...)
```

```cmake
# core/CMakeLists.txt
target_sources(app PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/crc.c
)
target_include_directories(app PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/inc
)
```

`OBJECT` 库则是另一条路：先编成 `.o` 集合，再整体塞进多个 target，避免重复编译：

```cmake
add_library(common_objs OBJECT a.c b.c)
target_link_libraries(app1 PRIVATE common_objs)
target_link_libraries(app2 PRIVATE common_objs)
```
