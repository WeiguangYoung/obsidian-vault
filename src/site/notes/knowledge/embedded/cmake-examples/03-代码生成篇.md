## 一、configure-files —— 模板 → 头文件

### 1.1 文件构成

```
configure-files/
├── CMakeLists.txt
├── main.cpp
├── ver.h.in
└── path.h.in
```

### 1.2 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.5)
project(cf_example)

# 设置工程版本
set(cf_example_VERSION_MAJOR 0)
set(cf_example_VERSION_MINOR 2)
set(cf_example_VERSION_PATCH 1)
set(cf_example_VERSION
    "${cf_example_VERSION_MAJOR}.${cf_example_VERSION_MINOR}.${cf_example_VERSION_PATCH}")

# ${VARIABLE} 语法
configure_file(ver.h.in ${PROJECT_BINARY_DIR}/ver.h)

# @VARIABLE@ 语法（@ONLY 限定）
configure_file(path.h.in ${PROJECT_BINARY_DIR}/path.h @ONLY)

add_executable(cf_example main.cpp)

target_include_directories(cf_example
    PUBLIC ${CMAKE_BINARY_DIR}
)
```

### 1.3 两个模板

`ver.h.in` —— 用 `${}` 语法：

```c
#ifndef __VER_H__
#define __VER_H__

// 会被 cmake 替换
const char* ver = "${cf_example_VERSION}";

#endif
```

`path.h.in` —— 用 `@...@` 语法：

```c
#ifndef __PATH_H__
#define __PATH_H__

// @ONLY 模式下只替换这种
const char* path = "@CMAKE_SOURCE_DIR@";

#endif
```

### 1.4 main.cpp

```cpp
#include <iostream>
#include "ver.h"
#include "path.h"

int main() {
    std::cout << "Hello Version " << ver << "!" << std::endl;
    std::cout << "Path is " << path << std::endl;
    return 0;
}
```

### 1.5 输出示例

```bash
$ ./cf_example
Hello Version 0.2.1!
Path is /home/user/cmake-examples/03-code-generation/configure-files
```

## 二、`configure_file` 深入

### 2.1 语法

```cmake
configure_file(<input> <output>
    [COPYONLY] [ESCAPE_QUOTES] [@ONLY]
    [NEWLINE_STYLE [UNIX|DOS|WIN32|LF|CRLF]]
)
```

| 参数 | 作用 |
|:--|:--|
| `@ONLY` | **只替换 `@VAR@`，不替换 `${VAR}`** —— 处理 `.c` / `.h` / `.sh` 模板时几乎必加 |
| `COPYONLY` | 纯复制，不做任何替换 |
| `ESCAPE_QUOTES` | 用 C 风格转义引号 |
| `NEWLINE_STYLE` | 强制换行符，跨平台生成脚本时用 |

### 2.2 为什么要 `@ONLY`

C/C++ 源码里有大量 `${...}` 形式的字符串、shell 脚本里有 `${VAR}` 变量。如果不加 `@ONLY`，CMake 会把这些**全部当成自己需要替换的变量**，替换成空字符串，生成的文件直接损坏。

```cmake
# ❌ 危险：脚本里的 ${PATH} 会被 CMake 吃掉
configure_file(run.sh.in ${CMAKE_BINARY_DIR}/run.sh)

# ✅ 安全：只替换 @CMAKE_BINARY_DIR@ 这类
configure_file(run.sh.in ${CMAKE_BINARY_DIR}/run.sh @ONLY)
```

> **实践准则：模板内容不是「纯给 CMake 用」的，一律加 `@ONLY`。**

### 2.3 生成的时机

`configure_file` 在**配置阶段（cmake 那一步）**执行，不在编译阶段。这意味着：

- 改 CMakeLists.txt 里的版本号 → 重新 `cmake` 后才更新
- **改了 `.in` 模板文件** → CMake 会自动检测到并重新配置（3.x 有依赖跟踪）
- 生成物默认**不覆盖**已存在的输出文件，除非 `COPYONLY` 或内容变化

### 2.4 典型用途清单

| 场景 | 模板内容 | 好处 |
|:--|:--|:--|
| 版本头文件 | `#define FW_VERSION "@PROJECT_VERSION@"` | 版本号只维护一处 |
| 配置头文件 | `#cmakedefine USE_FEATURE_X` | 用 `option()` 控制功能开关 |
| 链接脚本 | `ORIGIN = @FLASH_ORIGIN@` | 内存布局参数化 |
| pkg-config 的 `.pc` | `prefix=@CMAKE_INSTALL_PREFIX@` | 安装路径自动适配 |
| 启动脚本 | `exec @CMAKE_INSTALL_PREFIX@/bin/app` | 免手工改路径 |

### 2.5 进阶：`#cmakedefine`

```c
// config.h.in
#cmakedefine USE_CAN
#cmakedefine01 USE_LIN
#cmakedefine MAX_TASKS @MAX_TASKS@
```

配合 CMake：

```cmake
option(USE_CAN "Enable CAN" ON)
option(USE_LIN "Enable LIN" OFF)
set(MAX_TASKS 8)
configure_file(config.h.in ${CMAKE_BINARY_DIR}/config.h @ONLY)
```

生成结果：

```c
#define USE_CAN          // 开 = 定义
/* #undef USE_LIN */     // 关 = 注释掉
#define USE_LIN 0        // #cmakedefine01 总是 0/1

#define MAX_TASKS 8
```

> `#cmakedefine01` 比 `#cmakedefine` 好用在：生成的宏**总是存在**，可以直接 `#if USE_LIN`，不用担心未定义宏在 `-Wundef` 下报警。

## 三、protobuf —— 协议代码生成

### 3.1 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.5)
project(protobuf_example)

find_package(Protobuf REQUIRED)

if(PROTOBUF_FOUND)
    message("protobuf found")
else()
    message(FATAL_ERROR "Cannot find Protobuf")
endif()

# 从 .proto 生成 .pb.h / .pb.cc
PROTOBUF_GENERATE_CPP(PROTO_SRCS PROTO_HDRS AddressBook.proto)

message("PROTO_SRCS = ${PROTO_SRCS}")
message("PROTO_HDRS = ${PROTO_HDRS}")

add_executable(protobuf_example
    main.cpp
    ${PROTO_SRCS}
    ${PROTO_HDRS})

target_include_directories(protobuf_example
    PUBLIC
    ${PROTOBUF_INCLUDE_DIRS}
    ${CMAKE_CURRENT_BINARY_DIR}
)

target_link_libraries(protobuf_example
    PUBLIC
    ${PROTOBUF_LIBRARIES}
)
```

### 3.2 依赖安装

```bash
sudo apt-get install libprotobuf-dev protobuf-compiler
```

## 四、`PROTOBUF_GENERATE_CPP` 深入

### 4.1 它做了什么

```cmake
PROTOBUF_GENERATE_CPP(<SRCS_VAR> <HDRS_VAR> <proto files...>)
```

展开后等价于：

1. 找到 `protoc` 可执行文件路径
2. 为每个 `.proto` 注册 `add_custom_command`：
   - `OUTPUT`：`${CMAKE_CURRENT_BINARY_DIR}/<name>.pb.cc` 和 `.pb.h`
   - `COMMAND`：`protoc --cpp_out=<bindir> <file>.proto`
   - `DEPENDS`：`.proto` 文件本身
3. 把生成的源文件路径填入 `<SRCS_VAR>` 和 `<HDRS_VAR>` 两个变量

因为用的是 `add_custom_command`，**只有 `.proto` 变了才会重新生成**，增量构建友好。

### 4.2 三个必须注意的点

**1. 生成的 `.pb.h` 在构建目录，不在源码目录**

```cmake
target_include_directories(protobuf_example PUBLIC ${CMAKE_CURRENT_BINARY_DIR})
```

不写这条，`main.cpp` 里 `#include "AddressBook.pb.h"` 会找不到。

**2. `.pb.h` 也要加进 `add_executable`**

```cmake
add_executable(protobuf_example main.cpp ${PROTO_SRCS} ${PROTO_HDRS})
```

这不是必需的，但加上头文件能让 IDE 正确索引，某些生成器也能更好地跟踪依赖。

**3. `PROTOBUF_GENERATE_CPP` 是「模块函数」，不是命令**

它定义在 `FindProtobuf.cmake` 里，必须先 `find_package(Protobuf)` 才能调用。如果 `protoc` 版本和 `libprotobuf` 版本不一致，运行时会报 `This program was compiled against version X, which does not match the installed version Y`。

### 4.3 多 proto 文件与 include 路径

```cmake
PROTOBUF_GENERATE_CPP(PROTO_SRCS PROTO_HDRS
    proto/user.proto
    proto/order.proto
)
```

如果 `.proto` 之间有 `import`，需要保证 proto 搜索路径正确：

```cmake
# 方式一：给 protoc 加 -I（老版本模块不够灵活）
# 方式二（推荐）：protoc 从 .proto 所在目录向上推导，保持目录结构一致
```

## 五、其他代码生成方式

`PROTOBUF_GENERATE_CPP` 只是把 `add_custom_command` 包装了一层。**任何代码生成器都能用同一套手法接进 CMake**：

### 5.1 通用模式

```cmake
add_custom_command(
    OUTPUT
        ${CMAKE_CURRENT_BINARY_DIR}/generated/parser.c
        ${CMAKE_CURRENT_BINARY_DIR}/generated/parser.h
    COMMAND bison -d -o ${CMAKE_CURRENT_BINARY_DIR}/generated/parser.c
            ${CMAKE_CURRENT_SOURCE_DIR}/grammar.y
    DEPENDS ${CMAKE_CURRENT_SOURCE_DIR}/grammar.y
    COMMENT "Generating parser from bison grammar"
    VERBATIM
)

add_custom_target(generated_parser DEPENDS
    ${CMAKE_CURRENT_BINARY_DIR}/generated/parser.c)

add_executable(myapp main.c
    ${CMAKE_CURRENT_BINARY_DIR}/generated/parser.c)
add_dependencies(myapp generated_parser)

target_include_directories(myapp PRIVATE
    ${CMAKE_CURRENT_BINARY_DIR}/generated)
```

### 5.2 常见生成器对照

| 工具 | 输入 | 输出 | CMake 接入方式 |
|:--|:--|:--|:--|
| `protoc` | `.proto` | `.pb.h` / `.pb.cc` | `PROTOBUF_GENERATE_CPP` |
| `bison` / `flex` | `.y` / `.l` | `parser.c` / `lexer.c` | `add_custom_command` |
| `qt5_wrap_cpp` | `.ui` / `.qrc` | `ui_*.h` | Qt 官方模块 |
| AUTOSAR 生成器 | `.arxml` | `Rte.c` / `Rte.h` | `add_custom_command` |
| 脚本自研 | 任意模板 | 任意 | `add_custom_command` + python |

### 5.3 三个反模式

| ❌ 不要 | 原因 |
|:--|:--|
| 用 `execute_process` 在配置阶段调生成器 | 每次改 CMakeLists 都重跑，且构建阶段无法增量 |
| 生成物写进源码目录 | 污染源码树，`git status` 永远脏 |
| 用 `file(GLOB)` 收集生成物 | 生成物在配置阶段还不存在，GLOB 拿到空列表 |

## 六、本章要点小结

### configure_file 一览

```cmake
# 基本用法
configure_file(<in> <out> @ONLY)

# 关键参数
@ONLY                                # 只替换 @VAR@，推荐必加
COPYONLY                             # 纯复制不替换
NEWLINE_STYLE UNIX|DOS               # 统一换行符
```

### 模板语法速查

| 写法 | 触发条件 | 生成结果 |
|:--|:--|:--|
| `@VAR@` | 默认 + `@ONLY` 都有 | 变量值 |
| `${VAR}` | 仅默认模式（无 `@ONLY`） | 变量值 |
| `#cmakedefine VAR` | — | `#define VAR` 或 `/* #undef VAR */` |
| `#cmakedefine01 VAR` | — | `#define VAR 1` 或 `#define VAR 0` |

### 代码生成三条原则

1. **生成物一律放 `CMAKE_BINARY_DIR`**，绝不写源码目录
2. **用 `add_custom_command(OUTPUT ...)` + `DEPENDS`**，让 CMake 管增量
3. **`target_include_directories` 要包含生成目录**，否则头文件找不到

### 常见坑

| 现象 | 原因 | 解决 |
|:--|:--|:--|
| 生成的头文件内容被清空 | 没加 `@ONLY`，`${...}` 被误替换 | 加 `@ONLY` |
| `AddressBook.pb.h: No such file` | 没把 `${CMAKE_CURRENT_BINARY_DIR}` 加进 include | 补 `target_include_directories` |
| 改 `.proto` 后没重新生成 | `add_custom_command` 的 `DEPENDS` 漏了 | 补 `.proto` 到 `DEPENDS` |
| protobuf 运行时版本不匹配 | `protoc` 与 `libprotobuf` 版本不同 | 统一 apt 安装或同源编译 |
| `configure_file` 不生效 | 生成物已存在且内容一致 | 正常行为，动模板或删输出 |
