# 07 · 包管理篇（package-management）

> 路径：`07-package-management/`
> 解决的问题：**第三方依赖从哪来，怎么锁版本，怎么让 CMake 认出来**。

返回 [[knowledge/embedded/cmake-examples/index\|📘 cmake-examples 总览]]

## 📑 先看这张表：什么场景选哪条路

五条路线，从上到下依次是「从省事到可控」：

| 路线 | 一句话 | 版本锁定 | 离线可用 | 上手成本 | 什么时候选它 |
|:--|:--|:--:|:--:|:--:|:--|
| **A · 系统包管理器** | `apt install` + `find_package` | ❌ | ✅ | 极低 | 系统基础库（zlib/openssl/boost）；内网离线机器 |
| **B · 源码内嵌 vendoring** | 代码进仓库 + `add_subdirectory` | ✅✅ | ✅✅ | 低 | 嵌入式/产线；要给库打补丁；安全审计要求源码可查 |
| **C · ExternalProject_Add** | 构建期下载并构建 | ✅ | ❌ | **高** | 老项目历史包袱；需要给非 CMake 工程套壳 |
| **D · FetchContent** | 配置期下载 + 直接链接 | ✅ | ⚠️ 首次需网络 | 低 | **绝大多数情况的首选** |
| **E · Conan / vcpkg** | 包管理器接管依赖图 | ✅✅ | ⚠️ 需缓存 | 中 | 大型 C++ 项目；依赖几十个包；要二进制缓存复用 |

### 一句话决策

```
依赖是系统基础库？          → A（apt + find_package）
必须离线 / 要打补丁？       → B（vendoring + submodule）
依赖多、要跨团队复用构建？  → E（Conan 2.x / vcpkg）
其他（含 90% 的日常场景）   → D（FetchContent）
只有对接 autotools 老项目  → C（ExternalProject）
```

> **仓库的 A/B/C 三个目录只有 README、没有代码**，它们是概念说明，实际示例分别指向 `01-basic/H`、`05-unit-testing/catch2-vendored`、`05-unit-testing/google-test-download`。
> `D-conan` 是唯一带完整代码的示例 —— 但它写的是 **Conan 1.x 语法，在 Conan 2.x 上直接报错**，本文第四节给出 2.x 的正确写法并实测通过。

## 一、路线 A · 系统包管理器

### 1.1 做法

```bash
sudo apt-get install libboost-all-dev
```

```cmake
find_package(Boost 1.46.1 REQUIRED COMPONENTS filesystem system)
target_link_libraries(app PRIVATE Boost::filesystem)
```

系统包管理器把库和头文件装到标准位置（`/usr/lib`、`/usr/include`），`find_package` 能在默认搜索路径里找到。

### 1.2 优缺点

| 优点 | 缺点 |
|:--|:--|
| 零配置，最省事 | **版本由发行版决定**，不能自由选 |
| 系统统一管理升级 / 安全补丁 | 不同发行版路径、包名不同 |
| 不需要联网（已装好） | 同一台机器不能并存多个版本 |
| | 项目不能锁定依赖版本，**不可复现** |

### 1.3 适用

- 团队内网 / 产线机器（离线环境）
- 依赖是系统基础库（zlib、openssl、boost）
- 不要求版本精确复现的场景

**实测环境中遇到的真实问题**：Ubuntu 20.04 自带 Boost 1.71，而示例 `01-basic/H` 用 `Boost::filesystem` imported target 时，CMake 3.16 的 `FindBoost.cmake` 会警告 `New Boost version may have incorrect or missing dependencies`。版本越新越容易碰上，这是系统包路线的天然摩擦。

## 二、路线 B · 源码内嵌（vendoring）

### 2.1 做法

```
project/
├── 3rd_party/
│   └── catch2/
│       ├── catch.hpp
│       └── CMakeLists.txt       ← 库自带或自己写
├── CMakeLists.txt
└── src/
```

```cmake
add_subdirectory(3rd_party/catch2)
target_link_libraries(app PRIVATE Catch2::Test)
```

### 2.2 两种引入手段

```bash
# git submodule（推荐：只存指针，可追踪版本）
git submodule add https://github.com/catchorg/Catch2.git 3rd_party/catch2
git submodule update --init --recursive

# git subtree（代码真的进仓库，克隆者无需 --recursive）
git subtree add --prefix 3rd_party/catch2 https://github.com/catchorg/Catch2.git v3.4.0 --squash
```

| | submodule | subtree |
|:--|:--|:--|
| 仓库体积 | 小（只存指针） | 大（存全量） |
| 克隆体验 | 需 `--recursive` | 直接完整 |
| 打补丁 | 麻烦 | 方便 |
| 版本记录 | `.gitmodules` | 融合进提交历史 |

### 2.3 不支持 CMake 的库：写 shim

```cmake
# 3rd_party/mylib/CMakeLists.txt —— 自己造的外壳
add_library(mylib STATIC
    src/foo.c
    src/bar.c
)
add_library(MyLib::mylib ALIAS mylib)

target_include_directories(mylib PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include)
target_compile_options(mylib PRIVATE -w)      # 关掉第三方代码的告警
```

### 2.4 优缺点

| 优点 | 缺点 |
|:--|:--|
| **完全离线可构建** | 仓库变大 |
| 版本 100% 锁定 | 升级需手动替换 |
| 可改第三方代码（打补丁） | 代码审计范围扩大 |
| 构建确定性最强 | 多项目重复 vendor 同一库 |

### 2.5 适用

- **嵌入式 / 产线 / 离线 CI**（最常用）
- 需要给第三方库打补丁
- 安全审计要求源码可查

## 三、路线 C · ExternalProject_Add

> 这一节是**历史教训**。新项目请直接跳到第四节 `FetchContent`。

### 3.1 基本用法

```cmake
include(ExternalProject)
ExternalProject_Add(googletest
    URL https://github.com/google/googletest/archive/release-1.12.1.tar.gz
    INSTALL_COMMAND ""        # 不装系统，避免权限问题
)
```

`configure` 阶段只是**生成一个 target**，真正执行是**构建时**：下载 → 更新 → 配置 → 构建 → 安装。

### 3.2 各阶段可定制

```cmake
ExternalProject_Add(myext
    GIT_REPOSITORY https://github.com/foo/bar.git
    GIT_TAG        v1.2.3
    SOURCE_DIR     ${CMAKE_BINARY_DIR}/myext-src
    BINARY_DIR     ${CMAKE_BINARY_DIR}/myext-build
    CONFIGURE_COMMAND <自定义>
    BUILD_COMMAND     <自定义>
    INSTALL_COMMAND   ""
    TEST_COMMAND      ""
)
```

对非 CMake 工程（autotools、裸 Makefile）也能接 —— 这是它**至今仍不可替代**的唯一场景。

### 3.3 致命限制：不能直接链接

**`ExternalProject_Add` 的 target 不能直接 `target_link_libraries`。**

因为它构建阶段才被编译，而 `target_link_libraries` 在配置阶段就要知道库文件在哪，此时文件还不存在。

只能绕：

```cmake
# 用 IMPORTED 库 + 依赖关系（经典手法）
add_library(ext_lib STATIC IMPORTED GLOBAL)
set_target_properties(ext_lib PROPERTIES
    IMPORTED_LOCATION ${CMAKE_BINARY_DIR}/myext-build/libmyext.a
    INTERFACE_INCLUDE_DIRECTORIES ${CMAKE_BINARY_DIR}/myext-src/include
)
add_dependencies(ext_lib myext)      # 保证先构建它
target_link_libraries(app PRIVATE ext_lib)
```

或者用 `BUILD_BYPRODUCTS`（3.2+）让 ninja 知道产物路径。**两条路都很啰嗦** —— 这就是它被 `FetchContent` 取代的根本原因。

### 3.4 仓库里的 hack：配置阶段手动驱动下载

`05-unit-testing/google-test-download` 用了另一招：

```cmake
configure_file(CMakeLists.txt.in googletest-download/CMakeLists.txt)
execute_process(COMMAND ${CMAKE_COMMAND} -G "${CMAKE_GENERATOR}" .
    WORKING_DIRECTORY ${CMAKE_CURRENT_BINARY_DIR}/googletest-download)
execute_process(COMMAND ${CMAKE_COMMAND} --build .
    WORKING_DIRECTORY ${CMAKE_CURRENT_BINARY_DIR}/googletest-download)
```

在**配置阶段**用 `execute_process` 手动跑一遍「只下载」的 ExternalProject，之后就能正常 `add_subdirectory` 了。

> 这是 `FetchContent` 出现前的标准 workaround。**新项目别这么写。**

### 3.5 这个示例的实测翻车记录

本机验证时 `05-unit-testing/google-test-download` **首次编译失败**：

```
gmock-matchers.h:432:67: error: implicitly-declared ... is deprecated [-Werror=deprecated-copy]
```

原因：示例拉的是 2017 年的 gtest 提交 `bfc0ffc8`，它自己的 `googletest/cmake/internal_utils.cmake:101` 硬编码：

```cmake
set(cxx_base_flags "-Wall -Wshadow -Werror")
```

而 GCC 9 会为这份老代码报 `-Wdeprecated-copy`，被 `-Werror` 升级成错误。

解决：

```bash
cmake .. -DCMAKE_CXX_FLAGS="-Wno-error=deprecated-copy -Wno-deprecated-copy"
```

**这不是环境问题，是仓库自身的老代码问题** —— 任何 GCC 9+ 环境复现这个示例都会撞上。GCC 9+ 都受影响。

## 四、路线 D · FetchContent（现代首选）

> **3.11 引入，3.14 起 `FetchContent_MakeAvailable` 大幅简化。这是 90% 场景的正确选择。**

### 4.1 最小可用示例

```cmake
cmake_minimum_required(VERSION 3.20)
project(fetchcontent_demo CXX)

include(FetchContent)

FetchContent_Declare(fmt
    GIT_REPOSITORY https://github.com/fmtlib/fmt.git
    GIT_TAG        10.2.1
    GIT_SHALLOW    TRUE
)
FetchContent_MakeAvailable(fmt)

add_executable(fc_demo main.cpp)
target_link_libraries(fc_demo PRIVATE fmt::fmt)
```

`FetchContent_MakeAvailable` 一步做完三件事：拉取源码 → `add_subdirectory` → 暴露 target。**之后就能像普通子目录一样直接链接。**

### 4.2 实测输出（本机验证）

```bash
$ cmake -S . -B build
-- Version: 10.2.1
-- Configuring done (140.7s)     ← 首次要 clone fmt 全量历史，慢
-- Build files have been written to: /tmp/fc7/build

$ cmake --build build -j8
$ ./build/fc_demo
Hello FetchContent!
```

首次配置 140 秒是**下载 + 配置 fmt 全项目**的耗时。二次配置约 0.1 秒（源码已在 `build/_deps/fmt-src`）。

### 4.3 它为什么能取代 ExternalProject

| 对比 | `ExternalProject_Add` | `FetchContent` |
|:--|:--|:--|
| 拉取时机 | **构建阶段** | **配置阶段** |
| 能否直接 `target_link_libraries` | ❌ 要 IMPORTED 绕一圈 | ✅ 直接链接 |
| 配置复杂度 | 高 | 低 |
| 生成器并行友好度 | 差（`BUILD_BYPRODUCTS` 才勉强） | 好（就是普通 target） |
| 引入版本 | 3.0 | 3.11（3.14 起 `MakeAvailable`） |
| 能否对接非 CMake 工程 | ✅ | ❌ |

**结论**：CMake 工程用 `FetchContent`；非 CMake 工程（autotools）才用 `ExternalProject`。

### 4.4 必须知道的四个变量

| 变量 | 作用 | 典型用法 |
|:--|:--|:--|
| `FETCHCONTENT_BASE_DIR` | 下载目录根 | 固定缓存目录，避免删 `build/` 就重下 |
| `FETCHCONTENT_SOURCE_DIR_<NAME>` | 指定本地源码，跳过下载 | **离线 CI 的关键**；`<NAME>` 是大写 |
| `FETCHCONTENT_FULLY_DISCONNECTED` | 完全禁止联网 | 断网环境强制用本地缓存 |
| `FETCHCONTENT_UPDATES_DISCONNECTED` | 配置时不执行 git update | 加速二次配置 |

```bash
# 离线构建：把依赖预置到本地，完全不联网
cmake -B build \
  -DFETCHCONTENT_SOURCE_DIR_FMT=/opt/deps/fmt \
  -DFETCHCONTENT_FULLY_DISCONNECTED=ON
```

> ⚠️ **变量名里的 `<NAME>` 必须与 `FetchContent_Declare` 的第一个参数完全一致并转大写**。写错不报错，只是静默重新下载 —— 离线环境下表现为「卡住」。

### 4.5 三个真实的坑

**坑 1：删 `build/` 就重下**

`_deps/` 在构建目录里。解决办法：

```cmake
set(FETCHCONTENT_BASE_DIR ${CMAKE_SOURCE_DIR}/.cache/fetchcontent)
```

**坑 2：`GIT_TAG` 用分支名不可复现**

```cmake
GIT_TAG main            # ❌ 每天内容可能不同
GIT_TAG 10.2.1          # ✅ tag
GIT_TAG a1b2c3d4        # ✅ commit hash 最稳
```

分支名 + `GIT_SHALLOW TRUE` 还有个副作用：shallow clone 拿不到完整历史，后续想 `git describe` 定位版本会失败。

**坑 3：上下游都 FetchContent 同一个库**

A 依赖 fmt/10.2.1，B 依赖 fmt/9.1.0，两个都用 `FetchContent_Declare(fmt ...)` —— 结果**后声明的那份被忽略**，只有第一份生效（3.24 起会给出 `OVERRIDE_FIND_PACKAGE` 相关提示）。跨项目冲突要靠 `FetchContent_Declare(... OVERRIDE_FIND_PACKAGE)` + `find_package` 统一入口来管。

### 4.6 什么时候**不**用 FetchContent

- 依赖超过 20~30 个 → 换 Conan / vcpkg（否则配置阶段变成串行等待）
- 需要二进制缓存跨团队复用的重型库（LLVM、Qt）→ 包管理器更划算
- 依赖有复杂传递依赖图（版本冲突需统一求解）→ 包管理器的依赖求解器不可替代

## 五、路线 E · Conan

### 5.1 仓库示例的现状（**已过时，别照抄**）

`D-conan/` 两个子目录：

| 目录 | 写法 |
|:--|:--|
| `i-basic` | `include(conanbuildinfo.cmake)` + `conan_basic_setup()` + `${CONAN_LIBS}` |
| `ii-basic-targets` | `conan_basic_setup(TARGETS)` + `CONAN_PKG::fmt` |

`conanfile.txt` 用的是 `fmt/5.3.0@bincrafters/stable`。

**这些在 Conan 2.x 上全部不可用**：`conanbuildinfo.cmake` 不再生成，`conan_basic_setup` 不存在，`bincrafters` 仓库早已停止维护，`CONAN_PKG::` 也不存在了。

### 5.2 Conan 1.x vs 2.x 对照

| 项 | Conan 1.x（仓库写法） | **Conan 2.x（正确写法）** |
|:--|:--|:--|
| 生成器 | `cmake` | **`CMakeDeps` + `CMakeToolchain`** |
| CMake 接入 | `include(conanbuildinfo.cmake)` | `-DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake` |
| 链接 | `${CONAN_LIBS}` / `CONAN_PKG::fmt` | `find_package(fmt)` + `fmt::fmt` |
| 包引用 | `fmt/5.3.0@bincrafters/stable` | `fmt/10.2.1` |
| 命令 | `conan install ..` | `conan install . --output-folder=build` |
| 最低 CMake | 3.5 | **3.20**（toolchain 生成的文件要求） |

### 5.3 Conan 2.x 完整流程（**实测通过**）

**`conanfile.txt`**

```ini
[requires]
fmt/10.2.1

[generators]
CMakeDeps
CMakeToolchain
```

**`CMakeLists.txt` —— 和不用 Conan 时一模一样**

```cmake
cmake_minimum_required(VERSION 3.20)
project(conan_third_party_include CXX)

set(CMAKE_CXX_STANDARD 11)

find_package(fmt REQUIRED)

add_executable(third_party_include main.cpp)
target_link_libraries(third_party_include PRIVATE fmt::fmt)
```

**`main.cpp`（仓库原文件，未改）**

```cpp
#include <iostream>
#include <fmt/format.h>

int main(int argc, char *argv[])
{
    fmt::print("Hello, {}. This is {}!\n", "conan", "fmtlib");
    return 0;
}
```

**构建命令**

```bash
conan profile detect --force          # 首次：自动探测编译器
conan install . --output-folder=build --build=missing
cmake -S . -B build \
      -DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake \
      -DCMAKE_POLICY_DEFAULT_CMP0091=NEW \
      -DCMAKE_BUILD_TYPE=Release
cmake --build build
./build/third_party_include
```

**实测输出**

```
conan install  → Install finished successfully
cmake configure → cfg exit=0
cmake --build   → build exit=0
运行            → Hello, conan. This is fmtlib!
```

### 5.4 `conan install` 生成了什么

```
build/
├── conan_toolchain.cmake        ← CMake 入口，必须 -DCMAKE_TOOLCHAIN_FILE 指它
├── CMakePresets.json            ← conan-release preset（CMake 3.23+ 可直接 --preset）
├── CMakeUserPresets.json
├── fmt-config.cmake             ← CMakeDeps 生成：让 find_package(fmt) 能找到
├── fmt-config-version.cmake
├── fmtTargets.cmake             ← 定义 fmt::fmt target
├── fmt-release-x86_64-data.cmake
├── conanbuild.sh / conanrun.sh  ← 环境变量脚本（需要时 source）
└── conandeps_legacy.cmake       ← 兼容 1.x 的遗留文件
```

**核心机制**：`CMakeDeps` 负责生成 `find_package` 能消费的 config 文件，`CMakeToolchain` 负责把编译器、标准库、构建类型统一进一个 toolchain 文件。**你的 CMakeLists.txt 里看不到 Conan 的任何痕迹** —— 这才是包管理器该有的形态。

### 5.5 关键细节

**1. 必须用 `--output-folder` 指定输出目录**

```bash
conan install . --output-folder=build --build=missing
```

不指定会生成在**当前目录**，污染源码树。

**2. `-DCMAKE_POLICY_DEFAULT_CMP0091=NEW` 不能省**

CMP0091 管 MSVC 运行库的选择方式。Conan 2 的 toolchain 依赖 NEW 行为，漏了会在某些配置下报错。CMake 3.15+ 默认就是 NEW，但显式写不会错。

**3. `--build=missing` 是必需的**

不加这个参数，本地没有预编译包时**直接失败**，不会自动从源码构建。ConanCenter 上很多包有二进制，但特定编译器版本（比如本机 GCC 9）不一定有。

**4. 用 `CMakePresets.json` 更省事（CMake 3.23+）**

```bash
conan install . --output-folder=build --build=missing
cmake --preset conan-release
cmake --build --preset conan-release
```

`conan install` 会自动生成 preset，不用手敲那一串 `-D`。

**5. 二进制定位缓存**

```bash
~/.conan2/p/          # 包二进制缓存
conan cache clean     # 清理
conan list "fmt/*"    # 查看本地已有的版本
```

`--build=missing` 编出来的包会进缓存，下次同配置直接复用。

## 六、五条路线横向对比

| 维度 | A 系统包 | B vendoring | C ExternalProject | **D FetchContent** | E Conan/vcpkg |
|:--|:--|:--|:--|:--|:--|
| 版本锁定 | ❌ | ✅✅ | ✅ | ✅ | ✅✅ |
| 离线构建 | ✅（预装） | ✅✅ | ❌ 首次 | ⚠️ 需 `FETCHCONTENT_SOURCE_DIR_*` | ⚠️ 需缓存 |
| 仓库体积 | 无 | 大 | 无 | 无 | 无 |
| 配置复杂度 | 极低 | 低 | **高** | 低 | 中 |
| 多版本并存 | ❌ | ✅ | ✅ | ✅ | ✅ |
| 传递依赖 | 靠系统 | 手动 | 手动 | 靠库自己的 CMake | ✅ 自动求解 |
| 代码可审计 | 部分 | ✅ | 部分 | ✅ | ❌ 二进制 |
| 打补丁 | 难 | ✅ | 难 | 中（改 `_deps` 会被覆盖） | 需 recipe / overlay |
| 首次构建耗时 | 秒 | 秒 | 长 | **长（140s 级）** | 中（有二进制则秒级） |
| 最适合 | 基础库 | 嵌入式 | 老项目 | **日常项目** | 大型 C++ |

## 七、选型决策树

```
需要第三方依赖
│
├─ 是系统基础库（zlib / openssl / boost）？
│    └─▶ A：apt install + find_package
│
├─ 要求离线 / 产线 / 需要打补丁 / 安全审计？
│    └─▶ B：vendoring（git submodule）
│
├─ 依赖几十个包，且团队内要复用构建产物？
│    └─▶ E：Conan 2.x 或 vcpkg
│
├─ 要对接 autotools / 裸 Makefile 工程？
│    └─▶ C：ExternalProject_Add
│
└─ 其他（绝大多数情况）
     └─▶ D：FetchContent
```

### 嵌入式实际选择

| 层级 | 建议 |
|:--|:--|
| MCAL / HAL（厂商提供） | vendoring + 写 shim 包成 INTERFACE / STATIC target |
| RTOS | vendoring（版本必须锁死） |
| 单元测试框架 | vendoring，或 FetchContent + `FETCHCONTENT_SOURCE_DIR_*` 指本地 |
| 宿主端工具链依赖 | 系统包（A） |
| 内部公共 C++ 库 | FetchContent 指向内网 Git，或 Conan 私有仓库 |

## 八、本章要点小结

### 五种「让 CMake 认得一个外部库」的手法

| 手法 | 代码 |
|:--|:--|
| `find_package` | `find_package(X REQUIRED); target_link_libraries(a X::x)` |
| `add_subdirectory` | `add_subdirectory(vendor/X); target_link_libraries(a X::x)` |
| `IMPORTED` | `add_library(X::x STATIC IMPORTED); set_target_properties(...)` |
| **`FetchContent`** | `FetchContent_MakeAvailable(x); target_link_libraries(a X::x)` |
| **Conan `CMakeDeps`** | `conan install` + `find_package(X)` —— 表面看和第一种完全一样 |

**消费者看到的永远是 `X::x`** —— 这就是现代 CMake 用 target 封装依赖的价值：换供应商，改的是「怎么提供」，不是「怎么用」。

### 常见坑速查

| 现象 | 原因 | 解决 |
|:--|:--|:--|
| `ExternalProject` 的库链接报找不到文件 | 配置阶段文件还不存在 | 改 `FetchContent`；或 IMPORTED + `BUILD_BYPRODUCTS` |
| Conan 2.x 报 `conan_basic_setup` 未定义 | 1.x 语法已废弃 | `CMakeDeps` + `CMakeToolchain` + `find_package` |
| Conan toolchain 报 CMake 版本不足 | 要求 ≥ 3.20 | 升级 CMake；或装到 `~/.local/opt` 不动系统 |
| `conan install` 找不到 fmt/5.3.0 | bincrafters 仓库已停维护 | 换 ConanCenter 版本号，如 `fmt/10.2.1` |
| 干净构建 `FetchContent` 重新下载 | `_deps` 在构建目录里 | 设 `FETCHCONTENT_BASE_DIR` 到源码外 |
| 离线 CI 卡在下载 | 无网络 | `FETCHCONTENT_SOURCE_DIR_<NAME>`（大写！）|
| `fetchcontent SOURCE_DIR` 写了不生效 | 变量名没全大写 / 和 Declare 名不匹配 | 逐字核对 |
| submodule 拉下来是空目录 | 没加 `--recursive` | `git submodule update --init --recursive` |
| vendoring 的库告警刷屏 | 第三方代码开了 `-Wall` | `target_compile_options(x PRIVATE -w)` |
| 老 gtest 在 GCC 9+ 编译失败 | 它自己写死 `-Werror` | `-DCMAKE_CXX_FLAGS="-Wno-error=deprecated-copy -Wno-deprecated-copy"` |

### 三条守则

1. **默认 `FetchContent`** —— 除非有明确理由（离线、打补丁、依赖爆炸、非 CMake 工程）
2. **版本用 tag 或 commit，不用分支名** —— 分支等于放弃可复现性
3. **工程文件里只写 `X::x`** —— 依赖的获取方式属于构建配置，不该污染源码
