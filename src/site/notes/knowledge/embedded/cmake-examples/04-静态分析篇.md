# 04 · 静态分析篇（static-analysis）

> 路径：`04-static-analysis/`
> 目标：把代码检查工具接进构建系统，让「`make analysis`」成为 CI 门禁的一环。

返回 [[knowledge/embedded/cmake-examples/index\|📘 cmake-examples 总览]]

## 📑 本节示例

| 示例 | 工具 | 接入方式 |
|:--|:--|:--|
| `clang-analyzer` | Clang Static Analyzer | `CMAKE_EXPORT_COMPILE_COMMANDS` + `scan-build` |
| `clang-format` | clang-format | 自定义 `FindClangFormat.cmake` + format 目标 |
| `cppcheck` | cppcheck | 自定义 `FindCppCheck.cmake` + `analysis` 目标 |
| `cppcheck-compile-commands` | cppcheck | 直接消费 `compile_commands.json` |

## 一、公共基石：`compile_commands.json`

四个示例都绕不开这个东西，先说清它。

### 1.1 开启

```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```

配置后在 `build/` 目录生成 `compile_commands.json`：

```json
[
  {
    "directory": "/path/to/build/subproject1",
    "command": "/usr/bin/c++ -I/path/include -std=c++11 -o CMakeFiles/subproject1.dir/main1.cpp.o -c /path/main1.cpp",
    "file": "/path/subproject1/main1.cpp"
  }
]
```

### 1.2 它为什么重要

| 消费者 | 用途 |
|:--|:--|
| clangd / CLion / VS Code | 精确补全、跳转、诊断（不用自己猜 include 路径） |
| clang-tidy / cppcheck | 拿到**真实的编译命令**，包括所有 `-I` / `-D` |
| `scan-build` | 知道每个文件该怎么编 |
| CI 工具 | 分析范围与构建范围严格一致 |

**没有它，静态分析工具只能靠猜 include 路径**，大量误报（missingInclude）和漏报。

### 1.3 常用技巧

```bash
# 软链到源码根目录，让 IDE 直接找到
ln -sf build/compile_commands.json .

# 多个构建目录时（Debug / Release / cross），用 CMAKE_EXPORT_COMPILE_COMMANDS 各自生成
```

> 现代写法还有 `CMAKE_EXPORT_COMPILE_COMMANDS` 的配套：`CMAKE_COMPILE_COMMANDS_PATH`（3.20+）可自定义输出位置。

## 二、clang-analyzer —— 扫描构建

### 2.1 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.5)
project(cppcheck_analysis)

# 分析建议用 Debug 构建
set(CMAKE_BUILD_TYPE Debug)

# 生成编译数据库
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

add_subdirectory(subproject1)
add_subdirectory(subproject2)
```

### 2.2 用法

`clang-analyzer` 不需要写自定义 target —— 它直接**包装构建命令**：

```bash
mkdir build && cd build
cmake ..
scan-build make          # 或 scan-build -o report make
```

`scan-build` 会拦截 `compile_commands.json` 里每条编译命令，插入分析器，产物是 HTML 报告：

```bash
scan-view report/2026-11-14-001
```

### 2.3 特点

| 优点 | 缺点 |
|:--|:--|
| **路径敏感分析**，能查出空指针解引用、内存泄漏、dead store | 编译时间大幅增加（3~10 倍） |
| 不需要额外配置 | 跨编译单元分析能力弱 |
| 报告可视化好 | 老版本对 C++17 支持不佳 |

> 现代替代：`clang-tidy` 现在能力更全，且能直接在 CMake 里用 `CMAKE_CXX_CLANG_TIDY` 一行接入：

```cmake
set(CMAKE_CXX_CLANG_TIDY "clang-tidy;-checks=bugprone-*,-modernize-use-trailing-return-type")
```

## 三、clang-format —— 格式检查

### 3.1 文件构成

```
clang-format/
├── .clang-format                          风格配置
├── CMakeLists.txt
├── cmake/
│   ├── modules/
│   │   ├── FindClangFormat.cmake          查找二进制
│   │   └── clang-format.cmake             注册 format 目标
│   └── scripts/
│       └── clang-format-check-changed     只检查 git 变更文件
├── subproject1/
└── subproject2/
```

### 3.2 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.5)
project(cppcheck_analysis)

# 把自定义模块目录加进搜索路径
set(CMAKE_MODULE_PATH ${CMAKE_SOURCE_DIR}/cmake/modules
                      ${CMAKE_MODULE_PATH})

add_subdirectory(subproject1)
add_subdirectory(subproject2)

set(CLANG_FORMAT_BIN_NAME clang-format-3.6)
set(CLANG_FORMAT_EXCLUDE_PATTERNS "build/" ${CMAKE_BINARY_DIR})

find_package(ClangFormat)
```

> 现在直接删掉 `set(CLANG_FORMAT_BIN_NAME clang-format-3.6)` 那行，用系统默认的 `clang-format` 即可。

### 3.3 `FindClangFormat.cmake` 的核心模式

```cmake
if(NOT CLANG_FORMAT_BIN_NAME)
    set(CLANG_FORMAT_BIN_NAME clang-format)
endif()

# 支持自定义根目录优先查找
if(CLANG_FORMAT_ROOT_DIR)
    find_program(CLANG_FORMAT_BIN
        NAMES ${CLANG_FORMAT_BIN_NAME}
        PATHS "${CLANG_FORMAT_ROOT_DIR}"
        NO_DEFAULT_PATH)
endif()

# 再从系统默认路径找
find_program(CLANG_FORMAT_BIN NAMES ${CLANG_FORMAT_BIN_NAME})

include(FindPackageHandleStandardArgs)
FIND_PACKAGE_HANDLE_STANDARD_ARGS(
    CLANG_FORMAT
    DEFAULT_MSG
    CLANG_FORMAT_BIN)

mark_as_advanced(CLANG_FORMAT_BIN)
```

这是写 `FindXXX.cmake` 的**标准模板**：

```cmake
find_program()                        # 找二进制
include(FindPackageHandleStandardArgs)  # 处理 FOUND / REQUIRED / QUIET
FIND_PACKAGE_HANDLE_STANDARD_ARGS()     # 定义 XXX_FOUND
mark_as_advanced()                      # 让 ccmake 不显示内部变量
```

### 3.4 用法

```bash
make format          # 就地格式化
make format-check    # 只检查，有差异则非 0 退出（CI 用）
```

`clang-format-check-changed` 脚本只处理 `git diff` 出来的文件，适合 pre-commit hook。

### 3.5 `.clang-format` 最小示例

```yaml
BasedOnStyle: Google
Language: Cpp
ColumnLimit: 100
IndentWidth: 4
SortIncludes: CaseSensitive
```

> 团队统一格式的最佳做法：`.clang-format` 进仓库 + CI 里跑 `format-check`，**不通过就 fail**。

## 四、cppcheck —— 自定义 analysis 目标

### 4.1 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.5)
project(cppcheck_analysis)

set(CMAKE_MODULE_PATH ${CMAKE_SOURCE_DIR}/cmake/modules
                      ${CMAKE_MODULE_PATH})

find_package(CppCheck)

# 必须在 add_subdirectory 之前初始化，子目录会往里 APPEND
set(ALL_ANALYSIS_TARGETS)

add_subdirectory(subproject1)
add_subdirectory(subproject2)

if(CPPCHECK_FOUND)
    add_custom_target(analysis)
    ADD_DEPENDENCIES(analysis ${ALL_ANALYSIS_TARGETS})
    set_target_properties(analysis PROPERTIES EXCLUDE_FROM_ALL TRUE)
    message("analysis targets are ${ALL_ANALYSIS_TARGETS}")
endif()
```

### 4.2 子目录写法

```cmake
project(subproject1)

set(SOURCES main1.cpp)

# 引入宏并注册分析目标
include(${CMAKE_SOURCE_DIR}/cmake/analysis.cmake)
add_analysis(${PROJECT_NAME} SOURCES)

add_executable(${PROJECT_NAME} ${SOURCES})
```

### 4.3 `analysis.cmake` 宏的精妙之处

```cmake
macro(add_analysis _target _sources)
    if(CPPCHECK_FOUND)
        # 1) 收集 include 目录，转成 cppcheck 的 -I 参数
        get_property(dirs DIRECTORY ${CMAKE_CURRENT_SOURCE_DIR}
                     PROPERTY INCLUDE_DIRECTORIES)
        foreach(dir ${dirs})
            LIST(APPEND cppcheck_includes "-I${dir}")
        endforeach()

        # 2) 把本目标的分析任务登记到全局列表（PARENT_SCOPE 上抛）
        LIST(APPEND ALL_ANALYSIS_TARGETS "${_target}_analysis")
        set(ALL_ANALYSIS_TARGETS "${ALL_ANALYSIS_TARGETS}" PARENT_SCOPE)

        # 3) 把 "‑j 4 --quiet ..." 这类参数串拆成列表
        separate_arguments(tmp_args UNIX_COMMAND ${CPPCHECK_ARG})

        # 4) 建独立目标，默认不构建
        add_custom_target(${_target}_analysis)
        set_target_properties(${_target}_analysis PROPERTIES EXCLUDE_FROM_ALL TRUE)

        add_custom_command(TARGET ${_target}_analysis PRE_BUILD
            WORKING_DIRECTORY "${CMAKE_CURRENT_SOURCE_DIR}"
            COMMAND ${CPPCHECK_BIN} ${tmp_args} ${cppcheck_includes} ${${_sources}}
            DEPENDS ${${_sources}}
            COMMENT "Running cppcheck: ${_target}"
            VERBATIM)
    endif()
endmacro()
```

### 4.4 三个设计要点

**1. 用 `macro` 而非 `function`**

`function` 会创建新的变量作用域，`PARENT_SCOPE` 只能往上跳一级，多层嵌套时会丢。`macro` 是文本就地展开，`ALL_ANALYSIS_TARGETS` 累积最省事。

**2. `EXCLUDE_FROM_ALL TRUE`**

分析目标**不参与 `make`**，只有显式 `make analysis` 才跑。否则每次构建都跑一遍 cppcheck，开发体验灾难。

**3. 二级目标聚合**

每个子工程一个 `<name>_analysis`，顶层 `analysis` 依赖它们全部。这样既能单独分析某个模块（`make subproject1_analysis`），也能整体分析（`make analysis`）。

### 4.5 `FindCppCheck.cmake` 关键点

```cmake
find_program(CPPCHECK_BIN NAMES cppcheck)

set(CPPCHECK_THREADS "-j 4" CACHE STRING "cppcheck 并行线程数")
set(CPPCHECK_ARG "${CPPCHECK_THREADS}" CACHE STRING "cppcheck 完整参数")

include(FindPackageHandleStandardArgs)
FIND_PACKAGE_HANDLE_STANDARD_ARGS(CPPCHECK DEFAULT_MSG
    CPPCHECK_BIN CPPCHECK_THREADS CPPCHECK_ARG)
```

用 `CACHE STRING` 让参数可配置：

```bash
cmake .. -DCPPCHECK_ARG="--enable=all --inconclusive --error-exitcode=1 -j 8"
```

> `--error-exitcode=1` 是 CI 门禁的关键：发现问题就返回非零，流水线才会红。

## 五、cppcheck-compile-commands —— 现代做法

### 5.1 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.5)
project(cppcheck_analysis)

set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

set(CMAKE_MODULE_PATH ${CMAKE_SOURCE_DIR}/cmake/modules
                      ${CMAKE_MODULE_PATH})

find_package(CppCheck)

add_subdirectory(subproject1)
add_subdirectory(subproject2)
```

### 5.2 差异

`cppcheck` 示例是**逐个 target 手动收集源文件和 include 路径**；这个示例改成让 cppcheck 直接读 `compile_commands.json`：

```bash
cppcheck --project=build/compile_commands.json --enable=all
```

| 方式 | 优点 | 缺点 |
|:--|:--|:--|
| 手动 `add_analysis` | 可按 target 精确控制 | 要维护宏，include 路径靠 `get_property` 抓 |
| `--project=compile_commands.json` | 零配置，与真实编译完全一致 | 只能整体分析，粒度粗 |

> **推荐现代方案**：`cppcheck --project=build/compile_commands.json` 一行搞定。如果需要按模块分批，再套 `--file-filter`。

## 六、四种工具横向对比

| 工具 | 分析类型 | 速度 | 误报率 | 接入成本 | 适合场景 |
|:--|:--|:--|:--|:--|:--|
| **cppcheck** | 语义 / 数据流 | 中 | 低 | 中 | 嵌入式 C，MISRA 检查 |
| **clang-tidy** | AST 级 + 现代化建议 | 中 | 低 | 低（一行变量） | C++ 项目 |
| **clang-analyzer** | 路径敏感 | 慢 | 中 | 低 | 深度 bug 挖掘 |
| **clang-format** | 纯格式 | 极快 | — | 低 | 团队风格统一 |

### 组合建议

```cmake
# CI 里的推荐组合：格式 + 快速检查 + 深度分析分阶段
# 1) 格式门禁（秒级）
clang-format --dry-run --Werror $(git ls-files '*.c' '*.h')

# 2) 快速检查（分钟级）
clang-tidy -p build $(git ls-files '*.c')

# 3) 深度分析（夜间任务）
scan-build -o report cmake --build build
```

## 七、本章要点小结

### 静态分析接入 CMake 的三层模式

| 层级 | 方式 | 示例 |
|:--|:--|:--|
| **工具变量** | `CMAKE_CXX_CLANG_TIDY` / `CMAKE_CXX_CPPCHECK` | 最简单，一行生效 |
| **自定义目标** | `add_custom_target(xxx_analysis)` | 可控、可按模块 |
| **外部包装** | `scan-build make` | 不改工程，CI 侧插入 |

### CMake 内置的工具变量（很多人不知道）

```cmake
# 直接指定，构建时自动调用
set(CMAKE_CXX_CLANG_TIDY "clang-tidy")
set(CMAKE_CXX_CPPCHECK "cppcheck;--enable=all")
set(CMAKE_CXX_INCLUDE_WHAT_YOU_USE "include-what-you-use")
```

这是**接入成本最低的方式**，比示例里的自定义脚本简单得多。缺点是只能整体启用，不能精细控制。

### 写 `FindXXX.cmake` 的标准套路

```cmake
find_program(XXX_BIN NAMES xxx)
set(XXX_ARG "默认参数" CACHE STRING "说明")
include(FindPackageHandleStandardArgs)
FIND_PACKAGE_HANDLE_STANDARD_ARGS(XXX DEFAULT_MSG XXX_BIN)
mark_as_advanced(XXX_BIN XXX_ARG)
```

### 常见坑

| 现象 | 原因 | 解决 |
|:--|:--|:--|
| cppcheck 报一堆 missingInclude | 没拿到 `-I` 路径 | 用 `compile_commands.json` |
| `make` 每次都跑分析，特别慢 | 忘写 `EXCLUDE_FROM_ALL` | 补上 |
| `ALL_ANALYSIS_TARGETS` 在顶层为空 | 用了 `function` 而非 `macro` | 改用 `macro` |
| clang-format 格式化范围太大 | 没设 `CLANG_FORMAT_EXCLUDE_PATTERNS` | 排除 `build/` |
| CI 没因分析失败而红 | 缺 `--error-exitcode=1` | 补参数 |
| `compile_commands.json` 没生成 | 忘开 `CMAKE_EXPORT_COMPILE_COMMANDS` | 补 `set(... ON)` |
