## 一、环境准备

```bash
sudo apt-get install build-essential cmake

sudo apt-get install libboost-all-dev   # H, K
sudo apt-get install -y ninja-build     # J
sudo apt-get install clang              # I
```

通用构建流程：

```bash
cd 01-basic/A-hello-cmake
mkdir build && cd build
cmake ..
make          # 或 cmake --build .
```

> **为什么要 out-of-source（外部构建）**：直接在源码目录跑 `cmake .` 会生成 `CMakeCache.txt` / `CMakeFiles/` / `Makefile` 污染源码树，且无法同时保留 Debug 和 Release 两套配置。一个配置一个 build 目录是铁律。

## 二、A · hello-cmake — 最小骨架

```cmake
cmake_minimum_required(VERSION 3.5)
project(hello_cmake)
add_executable(hello_cmake main.cpp)
```

| 命令 | 作用 |
|:--|:--|
| `cmake_minimum_required(VERSION 3.5)` | 声明最低 CMake 版本，低于此版本直接报错 |
| `project(hello_cmake)` | 声明工程名，定义 `PROJECT_NAME` / `PROJECT_SOURCE_DIR` / `PROJECT_BINARY_DIR`，并隐式启用 C/C++ |
| `add_executable(<name> <sources...>)` | 由源文件生成可执行目标 |

### 关键认知：Target 是 CMake 的核心

现代 CMake 一切围绕 **target** 展开 —— 可执行文件、库、自定义命令都是 target。后续 `target_include_directories` / `target_link_libraries` / `target_compile_definitions` 全是「给某个 target 加属性」。

> **忘掉 `include_directories()` 这类全局命令** —— 它们无法区分目标、无法传递依赖。

`cmake_minimum_required` 建议写实际用到的特性版本。仓库写 3.5 是 2017 年的语境，**新项目建议 `VERSION 3.20` 起步**。

## 三、B · hello-headers — 引入头文件

```cmake
cmake_minimum_required(VERSION 3.5)
project(hello_headers)

set(SOURCES
    src/Hello.cpp
    src/main.cpp
)

add_executable(hello_headers ${SOURCES})

target_include_directories(hello_headers
    PRIVATE
        ${PROJECT_SOURCE_DIR}/include
)
```

### 要点 1：`set` 收集源文件

```cmake
set(SOURCES src/Hello.cpp src/main.cpp)
add_executable(hello_headers ${SOURCES})
```

`${SOURCES}` 是变量展开。**不要用 `file(GLOB ...)`** —— 新增文件不会自动触发重新配置，会出现「明明加了文件却没编译」的诡异现象。

### 要点 2：`target_include_directories` 替代 `include_directories`

等价于给这个 target 的编译命令加 `-I<dir>`。`PRIVATE` 表示「只用于我自己编译，不传给任何人」。

老写法 `include_directories(include)` 是全局的，影响当前目录及所有子目录下**所有** target，且无法传递依赖。新项目一律用 `target_*`。

## 四、C · static-library — 静态库与作用域

```cmake
add_library(hello_library STATIC
    src/Hello.cpp
)

target_include_directories(hello_library
    PUBLIC
        ${PROJECT_SOURCE_DIR}/include
)

add_executable(hello_binary src/main.cpp)

target_link_libraries(hello_binary
    PRIVATE
        hello_library
)
```

产物：`libhello_library.a`（静态库，链接时整个归档进可执行文件）。可执行体积大，但不依赖运行时环境。

### 本节最重要的一课：`PUBLIC` 为什么不能换成 `PRIVATE`

`Hello.cpp` 里 `#include "static/Hello.h"`，`main.cpp` 也要 `#include "static/Hello.h"`。

如果写成 `PRIVATE`，`hello_binary` 编译时会**找不到头文件** —— 因为 `main.cpp` 需要 `include/` 这个路径，但它自己没声明，只能靠 `hello_library` 通过 `PUBLIC` 传递过来。

```
hello_library ── PUBLIC include/ ──▶ hello_binary 自动获得 -Iinclude/
```

### 作用域速查

| 关键字 | 自己编译需要 | 传给依赖者（链接我的 target） |
|:--|:--:|:--:|
| `PRIVATE` | ✅ | ❌ |
| `PUBLIC` | ✅ | ✅ |
| `INTERFACE` | ❌ | ✅ |

**`INTERFACE` 用在哪**：纯头文件库（header-only）—— `add_library(x INTERFACE)` + `target_include_directories(x INTERFACE include)`，自己不编译任何东西，只负责把头文件路径传出去。

### `target_link_libraries` 的作用域

- `PRIVATE`：自己用，不往下传
- `PUBLIC`：自己用 + 传给链接我的 target
- 可执行文件一般用 `PRIVATE`（没人链接一个可执行文件）

## 五、D · shared-library — 动态库与 ALIAS

```cmake
add_library(hello_library SHARED
    src/Hello.cpp
)
add_library(hello::library ALIAS hello_library)

target_include_directories(hello_library
    PUBLIC
        ${PROJECT_SOURCE_DIR}/include
)

add_executable(hello_binary src/main.cpp)

target_link_libraries(hello_binary
    PRIVATE
        hello::library
)
```

### 静态库 vs 动态库

| | `STATIC` | `SHARED` |
|:--|:--|:--|
| 产物 | `.a` | `.so`（Windows `.dll`） |
| 链接时机 | 编译期 | 编译期记录符号，运行期加载 |
| 可执行体积 | 大 | 小 |
| 运行时依赖 | 无 | 需 `.so` 在搜索路径中 |
| 更新库 | 需重编可执行文件 | 替换 `.so` 即可（**前提是 ABI 兼容**） |

> ABI 兼容的意思是：不改类成员布局、不改函数签名、不删导出符号。改了这些还只换 `.so`，程序会在运行期崩（轻则 `symbol lookup error`，重则内存错乱静默出错）。

### `ALIAS` 别名

```cmake
add_library(hello::library ALIAS hello_library)
```

- 读起来是**命名空间形式**，和 `find_package` 导出的 target 风格统一
- 日后把本地库换成外部包，只改 target 名字，链接代码不用动
- 别名是**只读**的，不能用于 `install()` / `add_custom_command` 的目标参数

### 运行时找不到 `.so` 的坑

```bash
./hello_binary
# error while loading shared libraries: libhello_library.so
```

三种解法：

```bash
LD_LIBRARY_PATH=./build ./hello_binary            # 临时
cmake .. -DCMAKE_INSTALL_PREFIX=/usr/local        # 装到系统路径
```

```cmake
# 或给 target 加 rpath，$ORIGIN = 可执行文件所在目录
set_target_properties(hello_binary PROPERTIES
    BUILD_RPATH   "\\$ORIGIN"
    INSTALL_RPATH "\\$ORIGIN/../lib"
)
```

> ⚠️ **`$` 必须转义成 `\$`**。CMake 里 `$ORIGIN` 会被当成变量/生成器表达式解析，展开成空串，rpath 就变成 `/origin` 这种垃圾路径，`.so` 依然找不到。正确写法是 `"\\$ORIGIN"`（见上方代码块）。也可以用 `$<TARGET_FILE_DIR:hello_library>` 让 CMake 自己算路径。

## 六、E · installing — 安装规则

```cmake
# 可执行文件
install(TARGETS cmake_examples_inst_bin
    DESTINATION bin)

# 动态库
install(TARGETS cmake_examples_inst
    LIBRARY DESTINATION lib)

# 头文件目录
install(DIRECTORY ${PROJECT_SOURCE_DIR}/include/
    DESTINATION include)

# 普通文件
install(FILES cmake-examples.conf
    DESTINATION etc)
```

### `CMAKE_INSTALL_PREFIX`

所有 `DESTINATION` 都是相对路径，拼在安装前缀后，默认 `/usr/local`：

```bash
cmake .. -DCMAKE_INSTALL_PREFIX=/opt/myapp
make install
# → /opt/myapp/bin/...  /opt/myapp/lib/...  /opt/myapp/include/...
```

### 三个容易踩的细节

**1. `install(DIRECTORY ...)` 末尾的斜杠**

```cmake
install(DIRECTORY include/  DESTINATION include)   # ✅ prefix/include/
install(DIRECTORY include   DESTINATION include)   # ❌ prefix/include/include/
```

**2. 为什么要写 `LIBRARY DESTINATION`**

`install(TARGETS)` 支持多种产物类型：`RUNTIME`（可执行、Windows DLL）、`LIBRARY`（Unix 动态库）、`ARCHIVE`（静态库）、`PUBLIC_HEADER`。Windows 的 DLL 属于 RUNTIME 而非 LIBRARY，所以原注释写「may not work on windows」。

**3. 安装清单**

`make install` 会在构建目录生成 `install_manifest.txt`，记录所有装出去的文件。CMake 本身**没有 `uninstall` 目标**，卸载得按这份清单手工删。

> 现代写法推荐 `cmake --install build --prefix /opt/myapp`，生成器无关，比 `make install` 更中性。

## 七、F · build-type — 构建类型

CMake 内置四种构建配置，直接决定优化级别与调试信息：

| 类型 | 编译器标志 | 用途 |
|:--|:--|:--|
| `Debug` | `-g` | 调试，无优化 |
| `Release` | `-O3 -DNDEBUG` | 发布，最高优化 |
| `MinSizeRel` | `-Os -DNDEBUG` | 追求最小体积 |
| `RelWithDebInfo` | `-O2 -g -DNDEBUG` | 发布 + 可调试 |

### 设置方式

```bash
cmake .. -DCMAKE_BUILD_TYPE=Release
```

### 给项目设默认值

```cmake
if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
  message("Setting build type to 'RelWithDebInfo' as none was specified.")
  set(CMAKE_BUILD_TYPE RelWithDebInfo CACHE STRING "Choose the type of build." FORCE)
  set_property(CACHE CMAKE_BUILD_TYPE PROPERTY STRINGS
    "Debug" "Release" "MinSizeRel" "RelWithDebInfo")
endif()
```

逐句拆解：

- `NOT CMAKE_BUILD_TYPE`：用户没指定
- `NOT CMAKE_CONFIGURATION_TYPES`：排除多配置生成器（VS、Xcode 本身就是多配置，`CMAKE_BUILD_TYPE` 对它们无意义）
- `CACHE STRING "..." FORCE`：写进 `CMakeCache.txt` 并强制覆盖，用户后续仍可改
- `set_property(CACHE ...)`：给 `cmake-gui` / `ccmake` 提供下拉选项，避免手打错

> ⚠️ **多配置生成器陷阱**：用 `-G "Ninja Multi-Config"` / VS / Xcode 时，`CMAKE_CONFIGURATION_TYPES` 非空，整块 `if` 会被跳过 —— 此时构建类型由 `cmake --build . --config Release` 决定，`CMAKE_BUILD_TYPE` 完全不生效。`ninja`（单配置）和 `Ninja Multi-Config` 名字很像，别混。

> ⚠️ 不设构建类型时，CMake 默认**不加任何优化标志**（既非 Debug 也非 Release），性能可能比预期低一个数量级。这是新手最常见的「为什么我的程序这么慢」原因之一。

## 八、G · compile-flags — 编译选项

示例用宏定义直观展示两种方式的差异：`main.cpp` 里 `#ifdef EX2` / `#ifdef EX3` 分别控制两行输出。

### 方式一：全局标志（不推荐）

```cmake
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -DEX2" CACHE STRING "Set C++ Compiler Flags" FORCE)
```

- 影响当前目录及所有 `add_subdirectory` 进来的子目录中的**全部 target**
- 无法按 target 区分，也无法向依赖者传递
- 新代码别用

相关变量：`CMAKE_C_FLAGS`（C）、`CMAKE_CXX_FLAGS`（C++）、`CMAKE_EXE_LINKER_FLAGS`、`CMAKE_SHARED_LINKER_FLAGS`

### 方式二：目标级（推荐）

```cmake
target_compile_definitions(cmake_examples_compile_flags
    PRIVATE EX3
)
```

等价于编译时加 `-DEX3`。`PRIVATE` 不传递；换成 `PUBLIC` / `INTERFACE` 时，链接本 target 的其他目标也会带上这个定义。

### 三兄弟函数对照

| 函数 | 用途 | 生成的标志 |
|:--|:--|:--|
| `target_compile_definitions(t PRIVATE FOO)` | 宏定义 | `-DFOO` |
| `target_compile_options(t PRIVATE -Wall)` | 任意编译选项 | `-Wall` |
| `target_include_directories(t PRIVATE dir)` | 头文件路径 | `-Idir` |

### 实测输出

```bash
cmake .. && make && ./cmake_examples_compile_flags
Hello Compile Flags!
Hello Compile Flag EX2!   # 来自全局 CMAKE_CXX_FLAGS
Hello Compile Flag EX3!   # 来自 target_compile_definitions
```

两者共存，说明全局与目标级选项是**叠加**关系。

## 九、H · third-party-library — 引入第三方库

```cmake
find_package(Boost 1.46.1 REQUIRED COMPONENTS filesystem system)

if(Boost_FOUND)
    message("boost found")
else()
    message(FATAL_ERROR "Cannot find Boost")
endif()

add_executable(third_party_include main.cpp)

target_link_libraries(third_party_include
    PRIVATE
        Boost::filesystem
)
```

### `find_package` 做了什么

按顺序搜索：

1. `CMAKE_MODULE_PATH` 里的 `FindXXX.cmake`（模块模式）
2. CMake 自带模块目录
3. 各包自己安装的 `<Package>Config.cmake`（配置模式，现代库优先走这条）

找到后导出两样东西：

- **变量**：`Boost_FOUND`、`Boost_INCLUDE_DIRS`、`Boost_LIBRARIES`（老式）
- **IMPORTED target**：`Boost::filesystem`（现代，✅ 推荐）

### 参数说明

| 参数 | 含义 |
|:--|:--|
| `1.46.1` | 最低版本需求 |
| `REQUIRED` | 找不到就 `FATAL_ERROR`；不设则只警告，结果 `Boost_FOUND=FALSE` |
| `COMPONENTS filesystem system` | 只找这两个组件，不必装全量 Boost |

### 为什么链 `Boost::filesystem` 而不是 `${Boost_LIBRARIES}`

`Boost::filesystem` 这个 imported target 自带**头文件路径 + 库路径 + 依赖的 system 组件**，一站式带全。用 `${Boost_LIBRARIES}` 还得自己 `include_directories(${Boost_INCLUDE_DIRS})`，容易漏。

> `main.cpp` 里 `#include <boost/shared_ptr.hpp>` 能编过，正说明头文件路径是从 imported target 自动传过来的 —— 这就是「依赖即 target」思想。

## 十、I · compiling-with-clang — 换编译器

`CMakeLists.txt` 与 A 完全一样，差异只在构建命令：

```bash
mkdir build.clang && cd build.clang
cmake .. -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++
make
```

### 要点

- CMake 只是元构建系统，本身不编译，真正的编译交给你指定的工具链
- **编译器路径会写进 `CMakeCache.txt`**，所以必须在**首次配置时**指定；已配置过的目录要删掉重建（或另开 `build.clang/`）
- 支持取值：`gcc`、`clang`、`icc`、交叉编译的 `arm-none-eabi-gcc` 等

### 相关变量

```bash
cmake .. -DCMAKE_C_COMPILER=gcc-13 -DCMAKE_CXX_COMPILER=g++-13
cmake .. -DCMAKE_TOOLCHAIN_FILE=toolchains/arm-none-eabi.cmake   # 交叉编译
```

> 原示例写的是 `clang-3.6`，现在直接写 `clang` / `clang++` 即可。

## 十一、J · building-with-ninja — 换构建工具

同样 `CMakeLists.txt` 不变，只换生成器：

```bash
mkdir build.ninja && cd build.ninja
cmake .. -G Ninja
ninja
```

### Generator 是什么

CMake 输出的是**给底层构建工具用的输入文件**，`-G` 选择输出哪种：

| Generator | 产物 | 特点 |
|:--|:--|:--|
| `Unix Makefiles`（默认） | `Makefile` | 通用，串行依赖解析慢 |
| `Ninja` | `build.ninja` | 快，依赖图紧凑，大工程明显 |
| `Ninja Multi-Config` | `build-*.ninja` | 一个构建目录支持多配置 |
| `Visual Studio 17 2022` | `.sln` / `.vcxproj` | Windows |
| `Xcode` | `.xcodeproj` | macOS |

查看本机支持的生成器：

```bash
cmake --help
```

### Ninja 为什么快

- Ninja 文件是**极简的依赖 DAG**，不做复杂逻辑，启动开销极小
- Make 需要递归解析 Makefile，增量构建时依赖扫描成本高
- 大工程上 Ninja 通常比 Make 快 20%~50%

### 现代推荐：用预设而非手敲 `-G`

```json
// CMakePresets.json
{
  "version": 3,
  "configurePresets": [
    {
      "name": "default",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build",
      "cacheVariables": { "CMAKE_BUILD_TYPE": "RelWithDebInfo" }
    }
  ]
}
```

```bash
cmake --preset default && cmake --build --preset default
```

> `CMakePresets.json` 是 3.19+ 的特性，仓库时代还没有，但**这是现在项目管理构建配置的标准做法**。

## 十二、K · imported-targets — 导入目标

`CMakeLists.txt` 与 H 几乎一致，核心在于理解 **IMPORTED target** 这个概念本身。

### 什么是 Imported Target

`IMPORTED` 是 target 的一种属性，表示「这个 target **不在本工程内构建**，而是外部已存在的二进制/库，由 `FindXXX.cmake` 或 `XXXConfig.cmake` 声明进来」。

```cmake
# 一个 Config 文件里典型的样子
add_library(Boost::filesystem SHARED IMPORTED)
set_target_properties(Boost::filesystem PROPERTIES
    IMPORTED_LOCATION "/usr/lib/x86_64-linux-gnu/libboost_filesystem.so"
    INTERFACE_INCLUDE_DIRECTORIES "/usr/include"
)
```

消费者只需：

```cmake
target_link_libraries(imported_targets PRIVATE Boost::filesystem)
```

### 三种 target 形态对比

| 形态 | 定义方式 | 是否参与构建 |
|:--|:--|:--|
| 普通 target | `add_library(x STATIC ...)` | ✅ 会编译 |
| ALIAS target | `add_library(ns::x ALIAS x)` | 指向已有 target，只读 |
| IMPORTED target | `add_library(ns::x IMPORTED)` | ❌ 外部已存在，只管用 |

### 为什么这是「现代 CMake」的分水岭

- **老风格**：`include_directories(${Boost_INCLUDE_DIRS})` + `target_link_libraries(app ${Boost_LIBRARIES})` —— 依赖信息散落在变量里，传递性靠人脑记
- **新风格**：`target_link_libraries(app PRIVATE Boost::filesystem)` —— 路径、宏、依赖链全封装在 target 里，自动传递

原则：**`find_package` 结果里有 `Namespace::Target` 形式就优先用它，别用 `${XXX_LIBRARIES}`。**

### 命名空间约定的意义

`Boost::`、`Qt5::`、`Threads::`、`ZLIB::` 双冒号前缀不是随意的 —— 明确标识「这是 imported/alias target，不是本工程的普通 target」，避免命名冲突，也让错误信息更清楚。

## 十三、L · cpp-standard — 设置 C++ 标准

`L-cpp-standard/` 下有三个子示例，正好代表 C++ 标准设置的三代做法。

### 13.1 上古写法（`i-common-method`）

```cmake
cmake_minimum_required(VERSION 2.8)

include(CheckCXXCompilerFlag)
CHECK_CXX_COMPILER_FLAG("-std=c++11" COMPILER_SUPPORTS_CXX11)
CHECK_CXX_COMPILER_FLAG("-std=c++0x" COMPILER_SUPPORTS_CXX0X)

if(COMPILER_SUPPORTS_CXX11)
    set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -std=c++11")
elseif(COMPILER_SUPPORTS_CXX0X)
    set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -std=c++0x")
else()
    message(STATUS "The compiler ${CMAKE_CXX_COMPILER} has no C++11 support.")
endif()
```

> ⚠️ 这段 `cmake_minimum_required(VERSION 2.8)` **在 CMake 3.27+ 上会直接配置失败**，报 `Compatibility with CMake < 3.5 has been removed from CMake`。本机 CMake 3.16 能跑，但新环境想复现需加 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` 或改成 `VERSION 3.5`。这里保留 2.8 只为展示历史写法。

CMake 3.1 之前的唯一办法：**手工探测编译器是否支持某个 flag，再手动拼到全局变量**。

问题：冗长易错、全局生效、编译器差异靠人肉分支处理。

### 13.2 全局标准变量（`ii-cxx-standard`）

```cmake
cmake_minimum_required(VERSION 3.1)
set(CMAKE_CXX_STANDARD 11)
```

CMake 3.1 引入的标准做法。三个配套变量：

| 变量 | 含义 | 默认 |
|:--|:--|:--|
| `CMAKE_CXX_STANDARD` | 目标标准版本号 | 无 |
| `CMAKE_CXX_STANDARD_REQUIRED` | 编译器不支持时是否报错 | `OFF`（降级到支持的最高标准） |
| `CMAKE_CXX_EXTENSIONS` | 是否允许 GNU 扩展（`gnu++11` vs `c++11`） | `ON` |

**推荐组合**（写进顶层 CMakeLists.txt）：

```cmake
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)     # 可移植性优先
```

### 13.3 目标级特性（`iii-compile-features`）

```cmake
cmake_minimum_required(VERSION 3.1)
add_executable(hello_cpp11 main.cpp)
target_compile_features(hello_cpp11 PUBLIC cxx_auto_type)
message("List of compile features: ${CMAKE_CXX_COMPILE_FEATURES}")
```

不指定「用 C++11」这种版本号，而是声明「我**需要 `auto` 这个特性**」，CMake 自动选一个支持的编译器标准。

- `main.cpp` 里用了 `auto message = "Hello C++11";`，所以声明 `cxx_auto_type`
- 特性名列表见 `${CMAKE_CXX_COMPILE_FEATURES}`
- **优点**：精确、可组合、能传递（`PUBLIC` 时依赖者也继承标准要求）
- **缺点**：特性名需要查文档，不如 `CMAKE_CXX_STANDARD` 直观

### 三种方式对比

| 方式 | CMake 版本 | 推荐度 | 适用 |
|:--|:--|:--:|:--|
| `CHECK_CXX_COMPILER_FLAG` + `CMAKE_CXX_FLAGS` | 2.8+ | ❌ | 维护古董项目 |
| `CMAKE_CXX_STANDARD` | 3.1+ | ✅✅ | **日常项目首选** |
| `target_compile_features` | 3.1+ | ✅ | 库/框架作者，需精确表达依赖 |

## 十四、本章命令总览

```cmake
# 必备三件套
cmake_minimum_required(VERSION 3.x)
project(name)
add_executable(name src...)

# 库
add_library(name STATIC|SHARED|INTERFACE|OBJECT src...)
add_library(ns::name ALIAS name)

# 依赖与属性（全部 target 级）
target_include_directories(t PRIVATE|PUBLIC|INTERFACE dir...)
target_link_libraries(t PRIVATE|PUBLIC|INTERFACE target...)
target_compile_definitions(t PRIVATE|PUBLIC|INTERFACE MACRO)
target_compile_options(t PRIVATE|PUBLIC|INTERFACE -Wall)
target_compile_features(t PUBLIC cxx_std_17)

# 外部依赖
find_package(Pkg VERSION x.y REQUIRED COMPONENTS a b)

# 安装
install(TARGETS t RUNTIME DESTINATION bin LIBRARY DESTINATION lib)
install(DIRECTORY include/ DESTINATION include)
```

### 「现代 CMake」三条守则

1. **一切围绕 target** —— 不用 `include_directories()` / `link_directories()` / `add_definitions()` 这类全局命令
2. **依赖用 `Namespace::Target`** —— 能拿到传递性，别手动拼变量
3. **作用域想清楚** —— `PRIVATE` 自己用、`PUBLIC` 一起用、`INTERFACE` 只给别人用

## 十五、动手练习

## 十六、踩坑速查

| 现象 | 原因 | 解决 |
|:--|:--|:--|
| 找不到头文件 | 依赖用 `PRIVATE` 声明了 include | 改 `PUBLIC` / `INTERFACE` |
| 运行时找不到 `.so` | 动态库不在默认搜索路径 | `LD_LIBRARY_PATH` 或 `INSTALL_RPATH` |
| 程序性能异常低 | 没设 `CMAKE_BUILD_TYPE` | 显式 `-DCMAKE_BUILD_TYPE=Release` |
| 换了编译器没生效 | 编译器路径已缓存 | 删 `build/` 重建 |
| `make install` 装到了 `/usr/local` | 忘了改 `CMAKE_INSTALL_PREFIX` | 配置时显式指定 |
| `install(DIRECTORY)` 多了一层目录 | 源路径末尾少了 `/` | 写 `include/` 而非 `include` |
| 新增源文件没被编译 | 用了 `file(GLOB ...)` | 显式列源文件，或重新 `cmake ..` |
| `ALIAS` target 报错 | 别名是只读的 | 别名不能用于 `install()` 等命令 |
