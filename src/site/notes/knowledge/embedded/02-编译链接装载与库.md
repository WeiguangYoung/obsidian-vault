## 一、全景：从源码到可执行体

```
源码 (.c/.cpp)
    │
    ▼  预处理  ── cpp        → .i    展开宏、包含头文件、去注释
    │
    ▼  编译    ── cc1        → .s    词法/语法/语义分析 → 汇编代码
    │
    ▼  汇编    ── as         → .o    汇编代码 → 机器码（此时还不能运行）
    │
    ▼  链接    ── ld         → .elf  符号解析 + 重定位，把多个 .o 拼成一个
    │                          ↑ 链接脚本在这里决定每个段落在哪个地址
    ▼  装载    ── 启动代码    → 运行时  把 .data 从 Flash 搬到 RAM、清 .bss、设栈
    │
    ▼  格式转换 ── objcopy    → .bin/.hex/.s19
    │
    ▼  烧录    ── 刷写器/UDS → Flash
```

**关键区分**（这是本书的核心视角）：

| 环节 | 干什么 | 谁负责 |
|:--|:--|:--|
| 编译 | **单个源文件** → 目标文件，产出「未定址」的机器码 | 编译器 `cc1` + 汇编器 `as` |
| 链接 | **多个目标文件** → 一个可执行体，解决「符号在哪、指令里该填什么地址」 | 链接器 `ld` |
| 装载 | 可执行体 → **内存里的运行态**，段落到该去的地址、初始化数据到位 | 启动代码 + 芯片 boot ROM |
| 库 | 把一堆 `.o` 打包复用 | `ar`（静态）/ `ld -shared`（动态） |

> ⚠️ **最容易混的一点**：编译阶段产出 `.o` 里**没有任何绝对地址**。所有「跳到某个函数」的指令位置都是空的，等着链接器来填。这就是「重定位」存在的理由，详见第四章。

## 二、编译（Compilation）

### 2.1 四个步骤

很多人把「编译」笼统当成一个动作，实际是四个程序接力：

| 步骤 | 命令 | 输出 | 典型错误 |
|:--|:--|:--|:--|
| 预处理 | `gcc -E` | `.i` | 头文件找不到、宏展开不符预期 |
| 编译 | `gcc -S` | `.s` | 语法错误、类型不匹配 |
| 汇编 | `as`（`gcc` 隐式调用） | `.o` | 内联汇编语法错 |
| 链接 | `ld`（`gcc` 隐式调用） | `.elf` | `undefined reference`、多次定义 |

只跑前三个（不链接）用 `-c`：

```bash
arm-none-eabi-gcc -c main.c -o main.o     # 预处理 + 编译 + 汇编，停在这里
```

想留存中间产物排查问题：

```bash
arm-none-eabi-gcc -E main.c -o main.i        # 看宏展开后的代码
arm-none-eabi-gcc -S main.c -o main.s        # 看生成的汇编
arm-none-eabi-gcc -c main.c -o main.o
```

### 2.2 GCC 工具链全家桶

| 工具 | 作用 | 典型用法 |
|:--|:--|:--|
| `arm-none-eabi-gcc` | C 编译器驱动程序 | `-c main.c -o main.o` |
| `arm-none-eabi-g++` | C++ 编译器 | 同上，C++ 源码 |
| `arm-none-eabi-cpp` | 独立预处理器 | 少见，通常由 gcc 调用 |
| `arm-none-eabi-as` | 汇编器 | 通常由 gcc 隐式调用 |
| `arm-none-eabi-ld` | 链接器 | 通常由 gcc 隐式调用 |
| `arm-none-eabi-ar` | 静态库打包 | `ar rcs libdrivers.a *.o` |
| `arm-none-eabi-objcopy` | 格式转换 | `.elf` → `.bin`/`.hex` |
| `arm-none-eabi-objdump` | 反汇编 | 排查崩溃、看优化结果 |
| `arm-none-eabi-readelf` | ELF 结构查看 | 看段布局、符号表、重定位表 |
| `arm-none-eabi-nm` | 符号列表 | 查某个函数是否被链接进来 |
| `arm-none-eabi-size` | 段大小统计 | 检查 Flash/RAM 占用 |
| `arm-none-eabi-strings` | 提取字符串 | 查固件里残留的调试信息 |

> 💡 `gcc` 是**驱动程序**（driver），它本身不编译，只负责按顺序调 `cpp → cc1 → as → ld`。加 `-v` 可以看到它实际执行了哪些命令。

### 2.3 工具链命名解读

```
arm - none - eabi - gcc
 │     │      │      └── 编译器前端
 │     │      └───────── ABI：Embedded Application Binary Interface
 │     │                 （裸机/RTOS，没有操作系统）
 │     └──────────────── 无操作系统
 └────────────────────── 目标架构
```

对比其他常见前缀：

| 前缀 | 目标环境 | 典型芯片 |
|:--|:--|:--|
| `arm-none-eabi-` | 裸机 / RTOS | Cortex-M0/M3/M4/M7 |
| `arm-linux-gnueabihf-` | 嵌入式 Linux，硬浮点 | Cortex-A7/A53 |
| `aarch64-linux-gnu-` | 64 位 Linux | Cortex-A53/A72 |
| `riscv64-unknown-elf-` | RISC-V 裸机 | RV32/RV64 |

> **`none` 和 `linux` 的区别很关键**：`none-eabi` 不链接 glibc，用 `--specs=nosys.specs` 提供空实现的系统调用桩；`linux-gnu` 会链接完整 glibc，产物是能在 Linux 上跑的 ELF 可执行文件。

### 2.4 常用编译选项

```bash
# 最简编译
arm-none-eabi-gcc -c main.c -o main.o

# 常用选项组合（Cortex-M4）
arm-none-eabi-gcc \
    -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16 \
    -O2 -g3 -Wall -Wextra \
    -ffunction-sections -fdata-sections \
    -DSTM32F407xx -DUSE_HAL_DRIVER \
    -I./inc -I./drivers \
    -c main.c -o main.o
```

| 选项 | 含义 | 嵌入式要点 |
|:--|:--|:--|
| `-mcpu=xxx` | 目标 CPU | **必须与芯片一致**，否则指令非法 |
| `-mthumb` | Thumb 指令集 | Cortex-M 只支持 Thumb |
| `-mfloat-abi=hard` | 硬件浮点 | 芯片有 FPU 才开，否则用 `soft` |
| `-mfpu=fpv4-sp-d16` | FPU 型号 | 必须与 `-mcpu` 匹配 |
| `-O0/-O2/-Os` | 优化级别 | 嵌入式常用 `-Os`（省 Flash） |
| `-g3` | 调试信息 | 不影响运行，占 Flash 空间 |
| `-ffunction-sections` | 每个函数单独成段 | 配合 `--gc-sections` 剔除未用代码 |
| `-fdata-sections` | 每个变量单独成段 | 同上 |
| `-ffreestanding` | 无宿主环境 | 裸机应加 |
| `-nostdlib` | 不链接标准库 | 用 `--specs=nosys.specs` 替代 |
| `-fPIC` | 位置无关代码 | 做动态库时必需 |
| `-fno-common` | 不允许同名符号合并 | 避免「多个 `.o` 定义了同名全局变量」的隐式合并 |

> **`-fno-common` 值得单独说**：老版 GCC 默认把多个 `.o` 里的同名未初始化全局变量**合并成一个**（common 符号），这在链接时悄悄掩盖了「重复定义」。新版 GCC（≥10）默认改成 `-fno-common`，于是原本能过的工程会突然报 `multiple definition`。这是升级工具链后最常见的「怎么突然编译不过」。

### 2.5 交叉编译

> **在 PC（x86）上编译出给 MCU（ARM）用的代码**

之所以需要，是因为 MCU 性能太弱，跑不动编译器。

```
开发机 (x86 Linux)                         目标 ECU (ARM Cortex-M4)
┌────────────────────┐                    ┌──────────────────────┐
│ arm-none-eabi-gcc  │                    │                      │
│ arm-none-eabi-as   │  ─── .elf ───►     │  Flash → 执行        │
│ arm-none-eabi-ld   │  ─── .bin ───►     │                      │
└────────────────────┘                    └──────────────────────┘
  "我帮你编译"                               "我直接运行"
```

三种编译形态：

| 形态 | 编译器 | 运行平台 | 用途 |
|:--|:--|:--|:--|
| 本地编译 | `gcc` | 同架构 | 主机侧单元测试、工具 |
| 交叉编译 | `arm-none-eabi-gcc` | 不同架构 | 固件 |
| 自举编译 | 自带编译器 | 同架构 | 大型系统（少见） |

完整手工流程：

```bash
# 1. 安装工具链
sudo apt install gcc-arm-none-eabi binutils-arm-none-eabi
# 或用 ARM 官方预编译包，解压后加 PATH

# 2. 编译（逐个 .c → .o）
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -O2 -c main.c    -o main.o
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -O2 -c startup.s -o startup.o

# 3. 链接（含链接脚本）
arm-none-eabi-gcc -T link.ld main.o startup.o -o firmware.elf \
    -Wl,-Map=output.map -Wl,--gc-sections

# 4. 转格式
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin

# 5. 查看结构
arm-none-eabi-size firmware.elf
arm-none-eabi-readelf -a firmware.elf
```

> 手工敲这一串能跑通一次就够。真实工程不会这么干 —— 参数重复、新增文件要手改、头文件依赖不跟踪。这些**工程编排**问题由构建系统解决，见 [[knowledge/devops/practices/05-构建系统实战-CMake\|CMake 工程实战]]。本文只管「命令本身为什么这么写」。

### 2.6 编译期的可移植性约束

跨平台代码在嵌入式上常见的坑：

| 问题 | 后果 | 做法 |
|:--|:--|:--|
| `int` 假定 32 位 | 换平台后溢出 | 用 `<stdint.h>` 的 `int32_t` |
| 结构体直接 memcpy 落盘/发网络 | 编译器插入 padding，长度随平台变 | `__attribute__((packed))` 或显式序列化 |
| 字节序假定小端 | ARM 多数小端，但通信协议可能大端 | `htons/ntohl` 或手写转换 |
| 位域布局依赖编译器 | `struct { int a:3; }` 在不同编译器上天差地别 | 用位掩码手写，别用位域描述硬件寄存器 |
| 未定义行为（有符号溢出、越界） | `-O2` 下被优化成完全不同的逻辑 | 开 `-fsanitize=undefined` 在主机侧先跑一遍 |

## 三、目标文件与段（ELF 视角）

### 3.1 编译器把代码和数据分到不同段

理解链接脚本和启动代码的前提 —— `.o` 里不是一坨字节，而是**按属性分好的若干段**：

| 段 | 内容 | 初始值在哪 | 可写 |
|:--|:--|:--|:--:|
| `.text` | 机器码 | Flash | ❌ |
| `.rodata` | 常量、字符串字面量、`const` 数组 | Flash | ❌ |
| `.data` | 已初始化的全局/静态变量 | **Flash 存初值，运行在 RAM** | ✅ |
| `.bss` | 未初始化（或初始化为 0）的全局/静态变量 | 仅 RAM，启动清零 | ✅ |
| `.init_array` | C++ 全局对象构造表 | Flash | ❌ |
| `.isr_vector` | 中断向量表 | Flash 首地址 | ❌ |
| `.comment` | 编译器版本信息 | — | — |
| `.ARM.exidx` | 异常展开表（C++ 异常/栈回溯） | Flash | ❌ |

**为什么必须分段**：不同段属性不同（只读/可写/可执行），要落到物理上不同的存储介质（Flash / RAM），且权限要能被硬件区分（MPU）。

### 3.2 `.data` 为什么占两份

```c
int g_init = 0x1234;   // .data —— 有初值
int g_zero;            // .bss  —— 初值为 0
const int g_const = 5; // .rodata
```

- `g_init` 的初值 `0x1234` 必须**存在 Flash 里**（掉电不丢），但变量运行时必须**在 RAM 里**才能被读写 → 所以 Flash 和 RAM 各有一份
- `g_zero` 的初值就是 0，没必要占 Flash 空间存一堆 0 → 只占 RAM，启动时清零

这解释了 `size` 报告的一个常见困惑：**`data` 段同时算进 Flash 和 RAM**。详见第八章。

### 3.3 段在 `.o` 里的样子

用 `readelf` 看一个目标文件：

```bash
arm-none-eabi-readelf -S main.o
```

```
[Nr] Name              Type            Address  Off    Size   ES Flg Lk Inf Al
[ 1] .text             PROGBITS        00000000 000034 0000a4 00  AX  0   0  4
[ 2] .data             PROGBITS        00000000 0000d8 000008 00  WA  0   0  4
[ 3] .bss              NOBITS          00000000 0000e0 000004 00  WA  0   0  4
[ 4] .rodata           PROGBITS        00000000 0000e0 000010 00   A  0   0  4
```

**注意 `Address` 全是 `00000000`** —— 这就是「目标文件未定址」的直接证据。链接器的工作之一就是给这些段分配真实地址。

| Flg | 含义 |
|:--|:--|
| `A` | Alloc，运行时占用内存 |
| `W` | Write，可写 |
| `X` | eXecute，可执行 |

`NOBITS` 表示这个段**在文件里不占空间**（`.bss` 就是这样，只有大小没有内容）。

### 3.4 常用查看工具

| 目的 | 命令 |
|:--|:--|
| 看段表 | `readelf -S file.o` |
| 看符号表 | `readelf -s file.o` 或 `nm file.o` |
| 看重定位表 | `readelf -r file.o` |
| 看 ELF 头 | `readelf -h file.o` |
| 反汇编 | `objdump -d file.elf` |
| 看段大小 | `size file.elf` |
| 查某个符号在哪个文件定义 | `nm -A *.o \| grep symbol` |
| 查固件里有没有残留路径 | `strings file.bin \| grep -i home` |

> **`nm` 的符号类型字母**是最实用的速查：`T` = `.text`（已定义函数）、`D` = `.data`、`B` = `.bss`、`U` = undefined（**该文件用了但没定义，等着链接器去找**）、`W` = weak、`R` = `.rodata`。

## 四、链接（Linking）

链接器做的全部工作可以概括成两件事：**符号解析** 和 **重定位**。

### 4.1 符号解析

每个 `.o` 都带一张符号表，记录：

- **定义的符号**（我提供了 `uart_init`）
- **引用的符号**（我需要 `memcpy`，但我没有它）

链接器把所有 `.o` 的符号表汇总，建立一张全局符号表，然后回答：「每个 `U`（undefined）符号，在哪个 `.o` 或哪个库里定义？」

**回答不出来就是 `undefined reference to 'xxx'`** —— 这是嵌入式最常见的链接错误，占实际排障时间的一半以上。

| 报错 | 真实原因（按概率排序） |
|:--|:--|
| `undefined reference to 'uart_init'` | ① 忘了把 `uart.o` 加进链接命令 ② 链接顺序不对 ③ 函数名拼错 ④ C/C++ 混编没加 `extern "C"` |
| `undefined reference to '__aeabi_uidiv'` | 没链接 libgcc（除法辅助函数），通常是加了 `-nostdlib` 但没补 `-lgcc` |
| `undefined reference to '_sbrk'` | 用了 `malloc` 但没提供堆实现，加 `--specs=nosys.specs` 或自己写桩 |
| `multiple definition of 'g_flag'` | 同一个全局变量在头文件里**定义**（而非 `extern` 声明），被多个 `.o` 各定义一份 |

> **C/C++ 混编的关键**：C++ 编译器会对函数名做 **name mangling**（`uart_init` 变成 `_Z9uart_initv`），C 编译器不会。所以 C++ 调 C 函数必须用 `extern "C" { }` 包住声明，否则链接器认为这是两个不同的符号。

### 4.2 重定位

符号解析只解决了「这个符号定义在哪」。真正难的是：**调用这个函数的那条指令，机器码里该填什么？**

编译阶段生成 `bl uart_init` 时，编译器根本不知道 `uart_init` 最终在哪个地址，于是：

1. 在 `.text` 里留下一条**占位指令**（地址填 0 或填偏移）
2. 同时在 `.rel.text`（重定位表）里记一条：「偏移 0x1c 处的指令，引用了符号 `uart_init`，等你算出真实地址后按 R_ARM_CALL 规则回填」

链接器分配完所有段的地址后，遍历重定位表，逐条把真实地址填回指令里。**这才让 `.o` 变成可执行体。**

```bash
arm-none-eabi-readelf -r main.o
```

```
Relocation section '.rel.text' at offset 0x1a4 contains 3 entries:
 Offset     Info    Type            Sym.Value  Sym. Name
00000018  00000b02 R_ARM_CALL        00000000   uart_init
0000001c  00000c02 R_ARM_CALL        00000000   delay_ms
00000020  00000d02 R_ARM_ABS32       00000000   g_init
```

| 重定位类型 | 含义 |
|:--|:--|
| `R_ARM_CALL` / `R_ARM_JUMP24` | 函数调用，填 PC 相对偏移 |
| `R_ARM_ABS32` | 绝对地址，填 32 位地址（如取全局变量地址） |
| `R_ARM_MOVW_ABS_NC` / `MOVT_ABS` | ARM 的 movw/movt 两条指令各填一半地址 |

**在 ARM 上尤其要注意 `movw/movt` 成对出现** —— 一条 32 位 ARM 指令装不下完整 32 位地址，所以用两条指令各装低 16 位和高 16 位。这两条必须一起重定位，漏一个就跳到错误地址。

### 4.3 链接顺序

`ld` 对 `.o` 和 `.a` 的扫描是**单次、从左到右**的：

```bash
# ✅ 正确：main.o 引用了 drivers 里的符号，drivers 在后面
arm-none-eabi-gcc main.o -L. -ldrivers -o firmware.elf

# ❌ 错误：链接器扫描 -ldrivers 时还没遇到引用的地方，直接跳过
arm-none-eabi-gcc -ldrivers main.o -L. -o firmware.elf
```

**为什么是单次**：这是 `ld` 的设计选择（为了处理大型工程的性能），不是 bug。修法有三种：

| 方法 | 说明 |
|:--|:--|
| 调整顺序 | 被依赖的放后面：`-lA -lB` 中 A 依赖 B 就写 `-lA -lB` |
| `--start-group` | 循环依赖时用：`-Wl,--start-group -lA -lB -Wl,--end-group`，链接器反复扫描直到收敛 |
| `--whole-archive` | 强制整个库都链进来，不管有没有被引用（常用于需要注册构造函数的库） |

### 4.4 化解未用代码

嵌入式里 Flash 就那么大，绝不能把没用到的函数链进来。三步配合：

| 步骤 | 标志 | 作用 |
|:--|:--|:--|
| 编译期分段 | `-ffunction-sections -fdata-sections` | 每个函数/变量独立成段，而不是全塞进一个大 `.text` |
| 链接期回收 | `-Wl,--gc-sections` | 从入口点出发做可达性分析，没被引用到的段直接丢弃 |
| 保护必要段 | `KEEP(*(.isr_vector))` | 中断向量表虽然没被代码「调用」，但必须保留 |

> ⚠️ `--gc-sections` 把中断向量表当成「没人引用」删掉，是嵌入式最经典的翻车现场之一 —— 表现为「烧进去完全不跑」或「一进中断就 HardFault」。链接脚本里必须 `KEEP`。

## 五、链接脚本：嵌入式装载控制

### 5.1 为什么需要链接脚本

`.o` 里的段只说「我有多大」，不说「我该放哪」。链接脚本告诉链接器：

- 目标芯片的 Flash/RAM **起始地址和大小**
- 每个段放到哪个区域的什么位置
- 哪些符号（`_sdata`/`_etext` 等）**暴露出地址给启动代码用**

格式通常是 `.ld` 或 `.lds`（GNU LD），也有 `.icf`（IAR）或 `.scf`（ARMCC）。本文以 GNU LD 为准。

### 5.2 嵌入式芯片的存储布局

```text
STM32F407VGT6:
┌────────────── 0x08000000 ──────────────────┐
│              Flash (1 MB)                   │
│   ┌──────────────────────────────┐          │
│   │ .isr_vector（中断向量表）      │ ← 必须在最前 │
│   │ .text（代码段）                │          │
│   │ .rodata（常量、字符串）         │          │
│   │ .init_array（C++ 构造表）      │          │
│   │ _etext ── .data 初值副本从这里开始       │
│   └──────────────────────────────┘          │
├──────── 0x20000000 ────────────────────────┤
│              SRAM (128 KB，CPU+DMA 可访问)   │
│   ┌──────────────────────────────┐          │
│   │ .data（已初始化的全局变量）     │          │
│   │ .bss（未初始化的全局变量）      │          │
│   │ .heap（malloc）               │          │
│   │ .stack（栈，向下生长）          │          │
│   └──────────────────────────────┘          │
├──────── 0x10000000 ────────────────────────┤
│              CCM RAM (64 KB，仅 CPU 可访问)  │
│   ┌──────────────────────────────┐          │
│   │ 可选：热点数据 / 不用           │          │
│   └──────────────────────────────┘          │
└────────────────────────────────────────────┘
```

> **CCM 的取舍**：`0x10000000` 的 64 KB **只有 CPU 能访问，DMA 到不了**。放栈和局部变量没问题，放 DMA 缓冲区会静默失败。所以很多工程干脆不用它，只声明 `RAM = 128K`；用的话要在链接脚本里单列 `CCMRAM` 区并指定哪些段进去。

### 5.3 完整链接脚本示例

```ld
/* ===== link.ld — STM32F407 链接脚本 ===== */

MEMORY
{
    FLASH  (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K  /* 1MB Flash */
    RAM    (rwx) : ORIGIN = 0x20000000, LENGTH = 128K   /* 128KB 主 SRAM */
    CCMRAM (rw)  : ORIGIN = 0x10000000, LENGTH = 64K    /* 64KB CCM（仅 CPU）*/
}

ENTRY(Reset_Handler)

SECTIONS
{
    /* ===== Flash 区 ===== */
    .text :
    {
        . = ALIGN(4);
        KEEP(*(.isr_vector))      /* 向量表必须在最前，且不能被 gc 掉 */
        *(.text*)
        *(.rodata*)
        KEEP(*(.init_array))      /* C++ 全局构造 */
        KEEP(*(.fini_array))
        . = ALIGN(4);
        _etext = .;               /* 代码结束地址：.data 初值在此之后 */
    } > FLASH

    /* ===== RAM 区 ===== */
    .data : AT(_etext)            /* 装载地址在 Flash，运行地址在 RAM */
    {
        . = ALIGN(4);
        _sdata = .;
        *(.data*)
        . = ALIGN(4);
        _edata = .;
    } > RAM

    .bss (NOLOAD) :               /* NOLOAD：不占 Flash，运行期清零 */
    {
        . = ALIGN(4);
        _sbss = .;
        *(.bss*)
        *(COMMON)
        . = ALIGN(4);
        _ebss = .;
    } > RAM

    /* ===== 堆栈 ===== */
    .heap (COPY) :
    {
        . = ALIGN(8);
        _heap_start = .;
        . = . + 0x4000;           /* 16 KB heap */
        _heap_end = .;
    } > RAM

    .stack (COPY) :
    {
        . = ALIGN(8);
        . = . + 0x2000;           /* 8 KB stack */
        _stack_top = .;           /* 启动代码把它写进 SP */
    } > RAM

    /* ===== 链接期检查：溢出直接报错，别等烧进去跑飞 ===== */
    ASSERT(_stack_top <= ORIGIN(RAM) + LENGTH(RAM), "RAM 溢出！")
    ASSERT(_etext <= ORIGIN(FLASH) + LENGTH(FLASH), "Flash 溢出！")
}
```

**两个关键语法**：

| 写法 | 含义 |
|:--|:--|
| `.data : AT(_etext) { ... } > RAM` | **VMA（运行地址）= RAM，LMA（装载地址）= Flash 的 `_etext`**。这就是「Flash 存初值、RAM 运行」在链接脚本里的表达 |
| `.bss (NOLOAD)` | 该段不从文件加载，只有 VMA。启动时清零即可 |

### 5.4 内存布局参数化

换芯片就要改 `.ld` 里的地址，容易漏改。工程做法是把 `.ld` 变成模板（`.ld.in`），构建时替换占位符：

```ld
/* stm32f407.ld.in */
MEMORY
{
    FLASH (rx) : ORIGIN = @FLASH_ORIGIN@, LENGTH = @FLASH_LENGTH@
    RAM   (rwx): ORIGIN = @RAM_ORIGIN@,   LENGTH = @RAM_LENGTH@
}
```

替换由构建系统完成（Make 用 `sed`，CMake 用 `configure_file(... @ONLY)`）。具体写法见 [[knowledge/devops/practices/05-构建系统实战-CMake\|CMake 工程实战]] 的链接脚本模板化一节。

> ⚠️ **双镜像（Bootloader + APP）时必须给每个镜像独立变量名**。用同一个 `FLASH_ORIGIN` 反复覆盖，覆盖顺序一变两份镜像地址就静默互换 —— 现象是 APP 烧进去不跑、BL 却能启动。

### 5.5 进阶技巧

```ld
/* 把热点函数放到 RAM 里跑（Flash 取指有等待周期，RAM 无）*/
.fast_code :
{
    *(.ramfunc*)
} > RAM AT > FLASH              /* 运行在 RAM，装载在 Flash，启动时搬过去 */

/* 版本信息嵌入固件 */
.version_info :
{
    KEEP(*(.version_info))
} > FLASH

/* 强制符号对齐——某些外设要求 DMA 缓冲区地址对齐 */
.dma_buffer (NOLOAD) :
{
    . = ALIGN(32);
    *(.dma_buffer*)
    . = ALIGN(32);
} > RAM
```

> RAM 里跑代码的前提是**启动代码把 `.fast_code` 也从 Flash 搬到 RAM** —— 链接脚本只描述了布局，搬运要自己写。这类「VMA ≠ LMA」的段，启动代码必须逐个处理，漏一个就是取到未初始化的垃圾指令。

## 六、装载（Loading）

链接完成后 `.elf` 只是一份**静态描述**。真正让它跑起来的是「装载」——把各段放到该去的地址、把有初值的数据搬到位、设好栈。

### 6.1 启动代码为什么必须搬 `.data`

链接脚本定义的符号（`_sdata`/`_edata`/`_etext`/`_sbss`/`_ebss`）在启动代码里被消费：

```c
/* startup_stm32f407xx.c（简化版） */
extern uint32_t _sdata, _edata, _etext;   /* 符号地址，不是变量 */
extern uint32_t _sbss, _ebss, _stack_top;

void Reset_Handler(void)
{
    /* 1. 把 .data 初值从 Flash(_etext) 复制到 RAM(_sdata) */
    uint32_t *src = &_etext;
    uint32_t *dst = &_sdata;
    while (dst < &_edata) *dst++ = *src++;

    /* 2. 清零 .bss */
    for (dst = &_sbss; dst < &_ebss; ) *dst++ = 0;

    /* 3. 设置栈指针（有些芯片上电时 SP 未初始化） */
    __asm volatile ("msr msp, %0" :: "r" (&_stack_top));

    /* 4. 调 SystemInit（时钟等），再跳 main */
    main();
    for (;;);   /* main 不该返回 */
}
```

**三个必须理解的点**：

| 现象 | 原因 |
|:--|:--|
| 不搬 `.data` 会怎样 | `.data` 里的全局变量拿到的是**垃圾值或 0**（RAM 上电内容随机），而不是代码里写的初值。表现是「明明初始化成 100，读出来是随机数」 |
| 不清 `.bss` 会怎样 | 未初始化变量拿到上电随机值，`if (flag)` 可能一开始就为真 |
| `extern uint32_t _sdata` 为什么能当地址用 | 链接脚本里 `_sdata = .` 定义的是一个**符号**（symbol），它没有存储空间，**符号的值就是地址**。所以 `&_sdata` 取的是符号值（地址），不是「读一个变量的地址」 |

> 📌 这也是为什么 `extern void _estack(void)` 这种「声明成函数」的写法常见 —— 数组/函数名会退化成地址，而 `extern uint32_t _estack` 直接用会被理解成读变量内容。两种都能编过，但语义要清楚。

### 6.2 中断向量表

向量表是**放在 Flash 最前面的一张地址表**，CPU 复位后硬件直接从这里取 SP 和 PC：

| 偏移 | 内容 |
|:--|:--|
| `0x00` | 初始 SP 值（通常是 `_stack_top`） |
| `0x04` | Reset_Handler 地址 |
| `0x08` | NMI_Handler |
| `0x0C` | HardFault_Handler |
| ... | 其余异常/中断 |

```c
/* 典型写法 */
typedef void (*vector_t)(void);

__attribute__((section(".isr_vector"), used))
const vector_t g_vectors[] = {
    (vector_t)&_stack_top,     /* 0x00 初始 SP */
    Reset_Handler,             /* 0x04 复位入口 */
    NMI_Handler,
    HardFault_Handler,
    /* ... */
};
```

**两个约束**：

1. **必须在 Flash 首地址** —— 链接脚本里 `KEEP(*(.isr_vector))` 放在 `.text` 段的最前，且 `.text` 落在 `ORIGIN(FLASH)`
2. **不能被 `--gc-sections` 删掉** —— 向量表没有被任何代码「引用」，全靠 `KEEP` 保命

### 6.3 Bootloader + APP 的装载切换

双镜像场景下，装载多一层：Bootloader 决定跳不跳 APP，跳之前要改向量表位置：

```c
/* 跳转前必须做两件事 */
SCB->VTOR = APP_BASE;              /* 1. 向量表重定位到 APP 起始 */
__set_MSP(*(uint32_t *)APP_BASE);  /* 2. 用 APP 的第一个字初始化 SP */
((void (*)(void))(*(uint32_t *)(APP_BASE + 4)))();  /* 3. 跳到 APP 的 Reset_Handler */
```

> `SCB->VTOR` 这条**在 RM0090（参考手册）里找不到**，只在 PM0214（编程手册）的内核章节。这是「两本手册分工」的典型例子 —— 外设看 RM，内核看 PM。

## 七、库（Library）

### 7.1 静态库 vs 动态库

| 特性 | 静态库 (`.a`) | 动态库 (`.so` / `.dll`) |
|:--|:--|:--|
| **链接时机** | 链接时把用到的 `.o` **复制**进可执行体 | 运行时加载，符号在运行时才解析 |
| **最终体积** | 大（每个可执行文件各存一份） | 小（多进程共享同一份） |
| **部署** | 单文件，省心 | 依赖 `.so` 路径配置 |
| **更新** | 要重新链接 | 替换 `.so` 即可（**要求 ABI 兼容**） |
| **嵌入式使用** | ✅ **常用** | ❌ 裸机/RTOS 基本不用 |
| **性能** | 无额外开销 | 有 PLT/GOT 间接跳转开销 |
| **工具** | `ar` 打包 | `gcc -shared` 生成 |

> ABI 兼容指：不改结构体布局、不改函数签名、不删导出符号。改了还只换 `.so`，运行期会崩（`symbol lookup error`）或静默内存错乱。

### 7.2 嵌入式场景：99% 用静态库

原因：

- 裸机/RTOS 通常**没有动态加载器**
- 代码放 Flash，RAM 宝贵，没法给动态链接留页表和 GOT
- 版本管控要求确定性（不能依赖外部 `.so` 的版本）
- 单文件固件便于烧录和 OTA 校验

### 7.3 手工制作静态库

```bash
# 1. 编译目标文件
arm-none-eabi-gcc -c uart.c -o uart.o
arm-none-eabi-gcc -c gpio.c -o gpio.o

# 2. 打包成静态库（r=替换 c=创建 s=写索引）
arm-none-eabi-ar rcs libdrivers.a uart.o gpio.o

# 3. 查看库内容
arm-none-eabi-ar t libdrivers.a
arm-none-eabi-nm libdrivers.a

# 4. 使用静态库链接
arm-none-eabi-gcc main.o -L. -ldrivers -o firmware.elf
```

**静态库的「按需拉取」语义**：链接器只从 `.a` 里拉出**被引用到的那几个 `.o`**，不是整包链进去。这是它和 `--whole-archive` 的区别，也是理解「为什么库里的函数没进固件」的关键。

### 7.4 库相关的三个坑

| 坑 | 现象 | 原因 / 解决 |
|:--|:--|:--|
| **链接顺序** | `undefined reference` | `ld` 单次从左到右扫描，被依赖的库必须放在后面。循环依赖用 `--start-group ... --end-group` |
| **库里的弱符号被覆盖** | 自己的 `malloc` 没生效 / 或者重定义冲突 | 库里的实现若标 `weak`，你定义的强符号会胜出；反之则冲突 |
| **.a 里的构造函数没跑** | 库里的 C++ 全局对象没初始化 | `.init_array` 所在 `.o` 没被拉进来 → 用 `--whole-archive` 或显式引用一个符号 |

### 7.5 动态库（嵌入式 Linux 场景）

在跑 Linux 的 Cortex-A 上动态库是常态：

```bash
# 交叉编译动态库（-fPIC 不能省）
arm-linux-gnueabihf-gcc -fPIC -shared algorithm.c -o libalgorithm.so

# 使用
arm-linux-gnueabihf-gcc main.c -L. -lalgorithm -o app

# 运行时找不到 .so 的三种解法
export LD_LIBRARY_PATH=/usr/lib:$LD_LIBRARY_PATH    # 临时
# 或装到系统库路径 /etc/ld.so.conf.d/ 后 ldconfig
# 或用 rpath 把搜索路径写进 ELF（$ORIGIN = 可执行文件所在目录）
arm-linux-gnueabihf-gcc main.c -Wl,-rpath,'$ORIGIN/lib' -lalgorithm -o app
```

**`-fPIC` 为什么不能省**：位置无关代码。动态库加载到任意地址都要能工作，所以不能有绝对地址引用，必须走 GOT/PLT 间接寻址。

**`-shared` 和 `-fPIC` 的关系**：可以只 `-shared` 不加 `-fPIC`（会生成「TEXTREL」重定位），在部分平台上能加载但性能差且限制多。规范做法是两个都加。

## 八、产物格式（bin / hex / s19 / map）

### 8.1 为什么还需要这一步

链接产出的是 `.elf` —— 带符号表、调试信息、段头的完整容器，**烧录器不认识它**（或者说，只有支持 ELF 的高级烧录器认识）。要转成裸二进制或带地址记录的文本格式。

| 格式 | 命令 | 特点 | 用在哪 |
|:--|:--|:--|:--|
| `.elf` | 链接器直接产出 | 含符号/调试信息/段头 | 调试、存档、size 分析 |
| `.bin` | `objcopy -O binary` | 纯字节流，**无地址信息** | 烧录（地址由写入命令指定） |
| `.hex` | `objcopy -O ihex` | Intel HEX，每行带地址和校验 | 多数烧录器、OTA |
| `.s19` | `objcopy -O srec` | Motorola S-record，带地址和校验 | 部分车厂刷写工具 |
| `.map` | `-Wl,-Map=xxx.map` | 符号地址与段布局清单 | 排查溢出、分析内存占用 |

### 8.2 三种格式的本质区别

```
.bin   ← 只有字节流，烧录地址靠外部指定
        [ 0x00 0x01 0x02 ... ]
        ↑ 从哪个地址开始写？烧录命令里告诉它

.hex   ← 每行带地址和校验
        :10010000214601360121470136007EFE09D21901 40
         ↑字节数 ↑地址↑类型  ↑数据              ↑校验和

.s19   ← 类似的记录格式，Motorola 风格
        S00600004844521B
        ↑类型 ↑长度 ↑地址  ↑数据       ↑校验
```

`.bin` 最省空间但**必须有配套的地址信息**；`.hex`/`.s19` 自带地址，烧录器能自己解析，适合多段镜像（比如 Bootloader 和 APP 分段烧）。

### 8.3 `.map` 文件怎么用

```bash
arm-none-eabi-gcc ... -Wl,-Map=output.map
```

`.map` 是**链接器的账本**，三块内容最有用：

| 区块 | 用途 |
|:--|:--|
| `Memory Configuration` | 各 MEMORY 区的起止地址，确认链接脚本生效 |
| `Linker script and memory map` | 每个段落到哪个地址、多大 |
| `Archive member included` | 从哪些 `.a` 里拉出了哪些 `.o`（查「库函数为什么进了固件」） |

**排查 Flash 溢出**：在 map 里按大小排序找大块，看是哪个库/模块占的。**排查符号冲突**：搜符号名，看它最终绑到了哪个定义。

### 8.4 把 size 报告当成硬指标

```bash
arm-none-eabi-size --format=berkeley firmware.elf
```

```
   text    data     bss     dec     hex filename
  24576    1024    8192   33792    8400 firmware.elf
```

| 段 | 含义 | 实际占用 |
|:--|:--|:--|
| `text` | 代码 + 只读数据 + 向量表 + `.data` 初值副本 | Flash |
| `data` | 有初值的全局变量 | **Flash + RAM 双份** |
| `bss` | 无初值的全局变量 | 仅 RAM |

**Flash 占用 = text + data，RAM 占用 = data + bss + heap + stack**。

> 注意 `size` 报的 `text` **已经包含了 `.data` 的初值副本**（因为它算的是文件里的实际内容）。所以：
> **Flash = text**（已含 .data 初值），**RAM = data + bss**。
> 两种写法在实际工程里都能见到，差别在于是否把 `.data` 的 Flash 副本算进 text —— 拿不准就以 `readelf -S` 的实际段大小为准。

这两个数应该在每次构建后直接检查，超限就报错 —— 比烧到板上才发现便宜得多。

### 8.5 反汇编排查

固件跑飞时，反汇编是最直接的证据链：

```bash
# 反汇编整个固件
arm-none-eabi-objdump -d firmware.elf > firmware.dis

# 只看某个函数
arm-none-eabi-objdump -d --disassemble=HardFault_Handler firmware.elf

# 带源码行号（需要 -g 编译）
arm-none-eabi-objdump -S firmware.elf

# 看具体地址落在哪个函数
arm-none-eabi-addr2line -e firmware.elf -f -C 0x08001a2c
```

> **HardFault 定位套路**：从栈里取出出错时的 PC（`mepc`/栈帧里的 PC），`addr2line` 反查是哪一行。这条链路正是「链接器把地址填进指令」的逆向应用 —— 有符号表才能反查，所以**发布固件要保留对应的 `.elf`**。
