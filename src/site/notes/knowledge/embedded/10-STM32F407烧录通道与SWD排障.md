# 🔧 STM32F407 烧录通道与 SWD 排障

> 芯路城 STM32F407VGT6-Mini 的实战记录：SWD 曾可用，之后永久失效；DFU 能用但不适合长期；
> 串口是当前主力通道。
> **最后更新：2026-11-27 23:15 UTC**

---

## 一、现状快照

| 项 | 状态 | 证据 |
|:--|:--|:--|
| 芯片 | ✅ 健康 | Flash 里有有效向量表（SP `0x20020000`、Reset `0x08004415`）|
| 固件 | ✅ 还在 | 串口例程，`dfu-util` 回读可见 |
| SWD | ❌ **不可用** | `chipid: 0x0000`，`jtag status contains invalid mode value` |
| DFU | ✅ 可用 | BOOT0 拉高 + 复位即出现 `0483:df11` |
| 串口 bootloader | ✅ 可用（未实测）| `stm32flash` 已装，PA9/PA10 在 P3 |
| **RDP** | ⚠️ **`0xBB`（非标准值）** | 我用 `dfu-util` 写入只成功一半，**待修正为 `0xAA`** |
| 原固件备份 | ✅ | `~/backups/f407/orig_20261127.bin`（1 MB）|

**当前 USB**：只剩 ST-Link（`0483:374b`）。`/dev/ttyACM0` 是 ST-Link 的虚拟串口，**不是** F407 的串口。
CH343（`1a86:55d3`）当前未插入。

### 那个 `0xBB` 是我弄出来的

```
原始: ff aa 00 55   (RDP=0xFF，Level 1)
我请求写入: aa aa 55 55   (RDP=0xAA，Level 0)
实际写入:   bb aa 44 55   (RDP=0xBB)
```

`dfu-util` 写 Option Bytes 时返回 `Error during download get_status`，**只改对了一部分位**。
`0xBB` 不是 ST 定义的标准值，属中间态。

> **教训：不要用 `dfu-util` 写 Option Bytes。** 它不是为此设计的工具。
> 正确工具是 `stm32flash -k`（原生支持）或 STM32CubeProgrammer。

## 二、时间线：SWD 是怎么坏的

```
12:08  SWD 正常，成功读出整片 1 MB → 备份落盘
       ↓
       openocd 只下了 shutdown，没有 reset run
       芯片停在 debug halt
       ↓
       st-flash 报 "Failed to unlock flash!"
       但仍发出擦除命令
       ↓
之后   SWD 报 init mode failed → 后来变成 jtag status invalid mode
       再也连不上
```

**直接触发点是 `st-flash` 的解锁动作**（它改写 Option Bytes）。
但**不能证明是它单独造成的**——同一时段还发生了：debug halt 未复位、mass erase、后续多次插拔。

诚实结论：**时间上关联明确，机理上没有闭环。**

## 三、已排除的原因（附证据）

逐条实测，不是推断：

| 怀疑点 | 实测结果 | 结论 |
|:--|:--|:--|
| **RDP 读保护** | 读 Option Bytes 得 `RDP=0xBB/0xFF`（Level 1）| ❌ **不是 chipid=0 的原因**（见下）|
| 固件禁用了 SWD 脚 | 芯片跑在 DFU（ROM bootloader）时测，仍失败 | ❌ ROM 代码不会禁 SWD |
| 板子没电 | 万用表 / TVCC 读数 | ⚠️ **读数不可信，见 3.1** |
| 杜邦线断芯 | 换过线，症状不变 | ❌ 不是线材 |
| 速度太快 / 时序容差 | 试到 **50 kHz**（比正常慢 30 倍）仍失败 | ❌ 不是速度 |
| 接线插错格 | 用户确认接在 P1 的 3/4/5 脚 | 待万用表复核 |
| 全片擦除后残留状态 | mass erase 后空白片测，仍失败 | ❌ 不是残留 |
| 芯片损坏 | DFU 烧录 / 擦除 / 运行 / 串口全部正常 | ❌ 芯片健康 |

### 3.1 关键陷阱：3.32V 不代表板子有电

我一度把 `Target voltage: 3.32V` 当作「板子供电正常、TVCC 通」的证据。**这是错的。**

实测：**板子完全没插电时，读数照样是 3.32V。**

```
12:08 通电    3.329452
13:17         3.346939
14:28         3.323327
16:10 未通电  3.324949   ← 板子没电，照样 3.3V
16:14 通电    3.326572
```

六次读数全在 3.32V 附近，通断电之间**没有台阶**。

**原因**：ST-Link 板载自己的 3.3V LDO（USB 5V 供电），TVCC 引脚给的是它自己的输出。
OpenOCD 读的「Target voltage」测得的是这根线，**不是目标板的电源**。

> **这条要记住**：ST-Link 的 TVCC 读数无法用来判断目标板是否上电。
> 要判断板子有没有电，只能用万用表量板子的 3V3 脚，或看板载电源 LED。

### 3.2 为什么 RDP Level 1 解释不了 chipid=0

这是本轮排障最重要的技术判断：

```
RDP Level 1 的典型表现：
  ✅ SWD 的 DP 握手仍能完成
  ✅ IDCODE 仍可读（chipid 正常）
  ❌ Flash 内容读取被拦截

我们实测到的：
  ❌ chipid: 0x0000        ← 连 DP 握手都没完成
  ❌ pyocd: No device connected
```

**`chipid = 0x0000` 说明 SWD 链路根本没建立**，比 RDP 保护所在层级低得多。
所以：**即使 RDP 完美修回 `0xAA`，SWD 大概率仍不通。**

> 判断口诀：**chipid 有值但读 Flash 报错 → 查 RDP；chipid = 0 → 查物理层。**

## 四、为什么 DFU 不能当长期方案

| 问题 | 具体表现 |
|:--|:--|
| **每次都要手动跳线** | BOOT0 → 3V3、按 S2、拔线，三步缺一不可 |
| **USB 枚举不稳** | 实测 `error -110`（超时）/ `error -62`（地址分配失败）反复出现 |
| **不能可靠写 Option Bytes** | dfu-util 把 `0xAA` 写成 `0xBB`，还报错 |
| **零调试能力** | 无断点、无单步、无寄存器查看、无实时变量 |
| **无法处理启动早期问题** | bootloader 在 app 之前，app 的 bug 看不到 |
| **依赖 BOOT0 硬件** | 没有按键、没有跳线帽，全靠杜邦线 |

**结论：DFU 只适合「救砖」和「一次性烧写」，不适合日常开发迭代。**

日常开发需要的是：改一行 → 编译 → 烧录 → 看现象，一分钟内完成。DFU 做不到。

## 五、怎么定死是哪个环境的问题

「环境」有三个独立部分：**调试器（ST-Link）**、**目标板（F407）**、**连接线**。
只有一个方法能真正分开它们：**交叉替换**。

### 5.1 2×2 交叉矩阵（唯一能定性的方法）

| | 这块 F407 | 另一块 STM32 板 |
|:--|:--|:--|
| **这个 ST-Link** | ❌ 已测：失败 | **B：未测** |
| **另一个调试器** | **C：未测** | D：对照组 |

- **B 成功** → 说明这个 ST-Link 没问题，问题在这块 F407
- **C 成功** → 说明这块 F407 没问题，问题是这个 ST-Link
- B、C 都失败 → 两个都有问题，或方法本身有系统性错误

**没有 B 或 C，就无法定死。** 这是为什么我一直在「猜」——缺对照实验。

可用的「另一个调试器」：正品 Nucleo/Discovery 板载的 ST-Link（最省钱的方案）、DAP-Link（CMSIS-DAP）、J-Link。

### 5.2 没有第二套硬件时的替代验证（万用表，无需对照）

**测点 A：目标板侧的引脚电平**（板子通电，DCV 20V 档，黑笔压 GND）

| 测点 | 正常值 | 异常含义 |
|:--|:--:|:--|
| P1 **脚4（SWDIO / PA13）** | **≈3.3V** | 0V → 引脚未接通 / 插错格 / 排针虚焊 |
| P1 **脚5（SWSCLK / PA14）** | **≈0V** | 3.3V → 两根线接反 |
| P1 **脚3（GND）** | 0V | 与板子 3V3 之间应有 3.3V |

原理：STM32 复位后 **PA13 内部上拉、PA14 内部下拉**。这个特征电压同时证明：
**引脚映射正确 + 芯片活着 + 排针焊通**。

**测点 B：ST-Link 侧空载电压**（不接板子）

| 测点 | 正常值 | 异常含义 |
|:--|:--:|:--|
| ST-Link 的 **SWDIO** | ≈3.3V | 0V → **适配器损坏** |
| ST-Link 的 **SWCLK** | 通常 0V 或 3.3V（各家不同）| — |

**测点 C：通断（断电，蜂鸣档）**

从 P1 排针直达 MCU 引脚，验证走线：

| 起点 | 终点 | 应通 |
|:--|:--|:--:|
| P1 脚4 | MCU **pin 72**（PA13）| ✅ |
| P1 脚5 | MCU **pin 76**（PA14）| ✅ |
| P1 脚3 | GND | ✅ |

原理图上这两根网络上**没有串联电阻**，应该是直通。

> 表笔太粗会同时碰到相邻针。针距 2.54 mm，建议用缝衣针绑在表笔上，或斜 45° 只点针尖。

### 5.3 判决表

| 组合 | 结论 |
|:--|:--|
| 测点A 全部正常 + 测点B 正常 + 测点C 全通 | 三者都好 → **ST-Link 固件/协议层问题或主板 SWD 走线** → 换调试器验证 |
| 测点A 的 SWDIO = 0V | 板子侧断路（插错/虚焊/走线）|
| 测点B 的 SWDIO = 0V | **ST-Link 坏了** |
| 测点C 任一条不通 | 板子走线或排针焊接问题 |

### 5.4 顺带一个可疑点

```
ST-Link 序列号: AE5A5BB50000000000078880
固件版本:       V2J28M18
```

原厂 ST-Link V2.1 序列号是唯一 ID；后段全 0 是**山寨方案**（常见 CS32F103 + 改写固件）的特征。
山寨 ST-Link 在 F4 上有已知的 SWD 时序兼容问题——这是当前最大的嫌疑，但**未经验证前只是假设**。

## 六、串口烧录：每次都要短接吗

### 6.1 先说结论

| 接线程度 | 每次烧录要做什么 | 能否自动化 |
|:--|:--|:--:|
| **只接 TX/RX/GND**（现状）| 跳线 BOOT0→3V3、按 S2、拔线 | ❌ 全手动 |
| **加接 DTR→BOOT0、RTS→NRST** | 一条命令 | ✅ 全自动 |
| **应用层软件跳转** | 一条命令（app 健康时）| ✅ 但 app 坏了就失效 |

**默认答案是：是的，每次都要短接复位。** 除非补上 DTR/RTS 那两根线。

### 6.2 为什么默认要手动

STM32 的 bootloader 是否启动，只看**复位那一刻 BOOT0 的电平**：

```
复位时 BOOT0 = 高  →  ROM bootloader（可烧录）
复位时 BOOT0 = 低  →  从 0x08000000 跑 app
```

这块板的 BOOT0 没有按键、没有跳线帽，只有 P1 的脚1（丝印 `B70`）带 10K 下拉。
所以每次都得人工制造「BOOT0 高 + 复位」这个组合。

### 6.3 方案一：自动复位（推荐，一次性改造）

`stm32flash` 原生支持 `-i` 参数驱动 GPIO 时序（**仅 Linux**）：

```bash
# 语法
-i GPIO_string       # 格式: [entry_seq][:exit_seq]
                     # sequence: [-]n[,sequence]
```

它能用**宿主机 GPIO** 或 **UART 的 modem 信号（DTR/RTS）** 当作 GPIO，在烧录前后自动拉电平。

需要焊两根线：

| 信号 | 接哪里 | 作用 |
|:--|:--|:--|
| **DTR** | P1 **脚1 (B70 / BOOT0)** | 拉高进 bootloader，拉低回 app |
| **RTS** | **S2 按键的 NRST 焊盘** | 产生复位脉冲 |

> ⚠️ **NRST 没有引到任何排针**，只在芯片 pin 14 和 S2 按键上。
> 所以 RTS 这一根**必须焊到 S2 的焊盘**，不能插排针。这是本方案唯一的动手门槛。
>
> 具体 `-i` 的 DTR/RTS 语法在本机 `man` 里说明较简略，**首次使用需实测确认**
> （备选：用 `-i` 配合 `gpioset`，或改用 pyserial 自己控制 DTR/RTS + `stm32flash -c`）。

改造后：

```bash
stm32flash -i <序列> -w app.bin -v -g 0x08000000 /dev/ttyUSB0
```

一条命令完成：进 bootloader → 擦 → 写 → 校验 → 跳 app。**不用碰板子。**

### 6.4 方案二：应用层跳转（不焊线，但有前提）

在 app 里加一段「收到特定命令就跳 ROM bootloader」：

```c
// F407 系统存储器 bootloader 入口
#define BOOTLOADER_ADDR  0x1FFF0000

void jump_to_bootloader(void)
{
    uint32_t sp = *(volatile uint32_t *)BOOTLOADER_ADDR;
    uint32_t pc = *(volatile uint32_t *)(BOOTLOADER_ADDR + 4);

    __disable_irq();
    SysTick->CTRL = 0;
    HAL_RCC_DeInit();
    HAL_DeInit();
    __set_MSP(sp);
    ((void (*)(void))pc)();
}
```

触发方式任选：串口收到 `"boot"`、长按 PA0、或上电 3 秒内按键。

**优点**：不用焊线、不用跳线，`stm32flash -w ... -g 0x08000000` 直接烧。
**致命缺点**：**app 跑飞或烧坏时，这段代码也没了**，还是得回到跳线。
所以它只能加速日常迭代，**不能替代物理恢复手段**。

### 6.5 三种方案对比

| | 手动跳线（现状）| DTR/RTS 自动 | 应用层跳转 |
|:--|:--:|:--:|:--:|
| 每次动手 | 3 步 | 0 | 0 |
| 需要焊接 | 无 | **2 根** | 无 |
| app 坏了能救 | ✅ | ✅ | ❌ |
| 实现成本 | 0 | 中 | 低 |
| 适合场景 | 偶发烧写 | **长期主力** | 快速迭代 |

**建议组合**：先做应用层跳转（马上见效），再补 DTR/RTS（彻底免手）。

## 七、操作手册

### 7.1 串口接线（CH343 → F407）

```
CH343          STM32 (P3 排针)
RXD    ←────  脚20  PA9   (板子 TX)
TXD    ────→  脚19  PA10  (板子 RX)
GND    ─────  GND
DTR    ────→  P1 脚1 B70      （可选，自动复位用）
RTS    ────→  S2 的 NRST 焊盘  （可选，自动复位用）
```

- **交叉接**：模块 RX 接板子 TX，模块 TX 接板子 RX
- **不要接 VCC/3V3**：板子已由 Type-C 供电
- CH343 若有 5V/3.3V 跳线，**必须拨到 3.3V**

### 7.2 修 RDP（当前 `0xBB` → `0xAA`）

```bash
# 1. 手动进 bootloader：B70 → 3V3，按 S2，拔线
# 2. 解除读保护（会触发全片擦除）
stm32flash -k /dev/ttyUSB0
# 3. 读回验证
stm32flash -r /tmp/ob.bin -S 0x1FFFC000:16 /dev/ttyUSB0
xxd /tmp/ob.bin     # byte0 应为 aa
```

### 7.3 烧固件

```bash
# 手动跳线后
stm32flash -w firmware.bin -v -g 0x08000000 /dev/ttyUSB0

# -w 写入  -v 校验  -g 烧完从 flash 启动
```

### 7.4 DFU 烧录（救砖用）

```bash
# 1. B70 → 3V3，按 S2，拔线
# 2. 确认出现 0483:df11
lsusb | grep df11
# 3. 烧
dfu-util -a 0 -s 0x08000000:leave -D firmware.bin
```

### 7.5 全片擦除

```bash
# DFU 方式
dfu-util -a 0 -s 0x08000000:mass-erase:force
# 出现 "Last page not writeable" 是长度计算的警告，擦除已生效
# 验证：读回应为全 FF
```

## 八、待办与决策树

### 现在该做什么（优先级排序）

```
① 万用表测三组点（5.2 节）
   → 这一步不需要任何新硬件，能排除一大半可能
   
② 若有第二块 STM32 板/调试器 → 做 2×2 交叉（5.1 节）
   → 唯一能"定死"的方法
   
③ 接 CH343，用 stm32flash -k 把 RDP 修回 0xAA
   → 清理我留下的 0xBB 中间态
   
④ 建立串口烧录流程（7.2/7.3）
   → 摆脱 DFU
   
⑤ 长期：换正品 ST-Link 或 DAP-Link
   → 恢复 SWD，拿回调试能力
```

### 决策树

```
SWD 不通
├─ 万用表测点A（目标板 SWDIO）？
│  ├─ 0V ────────────────→ 板子侧断：查插针/虚焊/走线
│  └─ 3.3V
│     ├─ 测点B（ST-Link 空载 SWDIO）？
│     │  ├─ 0V ──────────→ 换调试器
│     │  └─ 3.3V
│     │     └─ 2×2 交叉
│     │        ├─ 换调试器 OK ──→ 原 ST-Link 问题（山寨兼容性）
│     │        └─ 换板子 OK ────→ 本板 SWD 走线问题
└─ 修 RDP 后仍 chipid=0 ──→ 与 RDP 无关，回到上面的物理层排查
```

### 明确不该再做的

- ❌ 继续改 OpenOCD 速度参数（50 kHz 都试过了）
- ❌ 继续换杜邦线（已换过）
- ❌ 继续用 `dfu-util` 写 Option Bytes（会写出 `0xBB` 这类中间态）
- ❌ 反复「再试一次」而不加新变量

## 九、一句话总结

> **芯片是好的，固件是好的，坏的是 SWD 这条通道。**
> 判据：`chipid=0x0000` 指向物理层，不是 RDP 保护。
> 定死原因只能靠 2×2 交叉或万用表测点，靠猜没有出路。
> 在此之前，串口 + `stm32flash` 是可靠的日常通道；DFU 只作救砖。
