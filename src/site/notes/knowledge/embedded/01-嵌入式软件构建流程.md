## 一、构建链路总览

```
源码 (.c/.cpp)
    │
    ▼
  预处理 (Preprocessing)     ── gcc -E          → .i
    │
    ▼
  编译 (Compilation)         ── gcc -S          → 汇编文件 (.s)
    │
    ▼
  汇编 (Assembly)            ── as              → 目标文件 (.o)
    │
    ▼
  链接 (Linking)             ── ld              → 可执行文件 (.elf)
    │                                             ↑ 链接脚本在这里起作用
    ▼
  格式转换                   ── objcopy         → .bin / .hex / .s19
    │
    ▼
  固件签名 / 打包            ── 脚本             → signed.bin
    │
    ▼
  ECU Flash 写入             ── UDS / 刷写器     → 烧录到 Flash
```

**四个环节对应四类工具**：

| 环节 | 工具 | 本文位置 |
|:--|:--|:--|
| 编译 | `gcc`/`g++`/`as` | 第二章 |
| 构建编排 | `make` 或 `cmake` | 第三、四章 |
| 链接 | `ld` + 链接脚本 | 第五章 |
| 产物处理 | `objcopy`/`size`/`objdump` | 第二、七、八章 |

> **一个容易混淆的点**：构建系统（Make/CMake）不参与编译，它只负责「按什么顺序、用什么参数调用编译器和链接器」。链路本身由编译器驱动，构建系统只是编排者。

## 二、编译器与工具链（Compiler）

### 2.1 GCC 工具链全家桶

以 ARM GCC 为例，一套完整的交叉编译工具链包含：

| 工具 | 作用 | 典型用法 |
|:--|:--|:--|
| `arm-none-eabi-gcc` | C 编译器驱动程序 | `-c main.c -o main.o` |
| `arm-none-eabi-g++` | C++ 编译器 | 同上，C++ 源码 |
| `arm-none-eabi-as` | 汇编器 | 通常由 gcc 隐式调用 |
| `arm-none-eabi-ld` | 链接器 | 通常由 gcc 隐式调用 |
| `arm-none-eabi-ar` | 静态库打包 | `ar rcs libdrivers.a *.o` |
| `arm-none-eabi-objcopy` | 格式转换 | `.elf` → `.bin`/`.hex` |
| `arm-none-eabi-objdump` | 反汇编 | 排查崩溃、看优化结果 |
| `arm-none-eabi-size` | 段大小统计 | 检查 Flash/RAM 占用 |
| `arm-none-eabi-readelf` | ELF 结构查看 | 看段布局、符号表 |
| `arm-none-eabi-nm` | 符号列表 | 查某个函数是否被链接进来 |

### 2.2 工具链命名解读

```
arm - none - eabi - gcc
 │     │      │      └── 编译器前端
 │     │      └───────── ABI：Embedded Application Binary Interface
 │     │                 （裸机/RTOS，没有操作系统）
 │     └──────────────── 无操作系统
 └────────────────────── 目标架构
```

对比其他常见前缀：

| 前缀 | 目标环境 | 典型芯片 |
|:--|:--|:--|
| `arm-none-eabi-` | 裸机 / RTOS | Cortex-M0/M3/M4/M7 |
| `arm-linux-gnueabihf-` | 嵌入式 Linux，硬浮点 | Cortex-A7/A53 |
| `aarch64-linux-gnu-` | 64 位 Linux | Cortex-A53/A72 |
| `riscv64-unknown-elf-` | RISC-V 裸机 | RV32/RV64 |

> **`none` 和 `linux` 的区别很关键**：`none-eabi` 不链接 glibc，`--specs=nosys.specs` 提供空实现的系统调用桩；`linux-gnu` 会链接完整 glibc，产物是能在 Linux 上跑的 ELF 可执行文件。

### 2.3 常用编译选项

```bash
# 最简编译
arm-none-eabi-gcc -c main.c -o main.o

# 常用选项组合（Cortex-M4）
arm-none-eabi-gcc \
    -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16 \
    -O2 -g3 -Wall -Wextra \
    -ffunction-sections -fdata-sections \
    -DSTM32F407xx -DUSE_HAL_DRIVER \
    -I./inc -I./drivers \
    -c main.c -o main.o
```

| 选项 | 含义 | 嵌入式要点 |
|:--|:--|:--|
| `-mcpu=xxx` | 目标 CPU | **必须与芯片一致**，否则指令非法 |
| `-mthumb` | Thumb 指令集 | Cortex-M 只支持 Thumb |
| `-mfloat-abi=hard` | 硬件浮点 | 芯片有 FPU 才开，否则用 `soft` |
| `-mfpu=fpv4-sp-d16` | FPU 型号 | 必须与 `-mcpu` 匹配 |
| `-O0/-O2/-Os` | 优化级别 | 嵌入式常用 `-Os`（省 Flash） |
| `-g3` | 调试信息 | 不影响运行，占 Flash 空间 |
| `-ffunction-sections` | 每个函数单独成段 | 配合 `--gc-sections` 剔除未用代码 |
| `-fdata-sections` | 每个变量单独成段 | 同上 |
| `-ffreestanding` | 无宿主环境 | 裸机应加 |
| `-nostdlib` | 不链接标准库 | 用 `--specs=nosys.specs` 替代 |

### 2.4 编译产物的段布局

理解后面链接脚本的前提 —— 编译器把代码和数据分到不同段：

| 段 | 内容 | 初始值在哪 |
|:--|:--|:--|
| `.text` | 机器码 | Flash |
| `.rodata` | 常量、字符串字面量 | Flash |
| `.data` | 已初始化的全局/静态变量 | **Flash 存初值，运行在 RAM** |
| `.bss` | 未初始化（或初始化为 0）的全局/静态变量 | 仅 RAM，启动清零 |
| `.init_array` | C++ 全局对象构造表 | Flash |
| `.isr_vector` | 中断向量表 | Flash 首地址 |

> `.data` 的「双份」是理解启动代码的关键，详见第五章。

## 三、Make / Makefile

### 3.1 为什么嵌入式还要学 Make

即使主力用 CMake，Make 仍然重要：

- **大量存量工程是 Make**（MCU 厂商 SDK 常默认生成 Makefile）
- 老 Bootloader、第三方协议栈（lwIP、FreeRTOS demo）常自带 Makefile
- 理解 Make 才能真正理解 CMake 生成的东西
- 极简单的工程，Make 比 CMake 更直接

### 3.2 Makefile 核心三要素

```make
# 目标(target): 依赖(prerequisites)
#     命令(recipe)      ← 必须 Tab 开头，不是空格
```

### 3.3 实战 Makefile

```make
# ===== 变量定义 =====
CC      = arm-none-eabi-gcc
CFLAGS  = -mcpu=cortex-m4 -mthumb -O2 -Wall -I./inc
LDFLAGS = -T link.ld -Wl,-Map=output.map -Wl,--gc-sections
TARGET  = firmware.elf
OBJS    = main.o uart.o gpio.o startup.o

# ===== 默认目标 =====
all: $(TARGET)

# ===== 模式规则：.c → .o =====
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

# ===== 链接 =====
$(TARGET): $(OBJS)
	$(CC) $(OBJS) $(LDFLAGS) -o $@
	arm-none-eabi-objcopy -O binary $@ firmware.bin
	arm-none-eabi-size $@

# ===== 伪目标 =====
.PHONY: all clean flash

clean:
	rm -f $(OBJS) $(TARGET) firmware.bin output.map

flash: $(TARGET)
	st-flash write firmware.bin 0x08000000
```

### 3.4 Make 的进阶能力

```make
# 条件编译
ifeq ($(DEBUG),1)
    CFLAGS += -Og -g3 -DDEBUG_ENABLE
else
    CFLAGS += -Os -DNDEBUG
endif

# include 其他 makefile
include config.mk
-include $(DEPS)      # 前缀 - 表示文件不存在也不报错

# 递归调用子目录 make
SUBDIRS = drivers hal app
all:
	for dir in $(SUBDIRS); do $(MAKE) -C $$dir; done

# 自动生成依赖（头文件变化触发重编）
DEPS = $(OBJS:.o=.d)
%.d: %.c
	$(CC) $(CFLAGS) -MM -MT $(@:.d=.o) $< > $@
```

### 3.5 Make 的局限性

| 局限 | 后果 |
|:--|:--|
| 不跨平台 | Linux/macOS/Windows 的 shell 命令不同 |
| 语法晦涩 | Tab/空格混用直接报错，错误信息难懂 |
| 依赖管理靠手写 | 头文件依赖要自己生成，漏了就出诡异 bug |
| 无内置包管理 | 第三方库全靠手工 vendor 或写下载规则 |
| 大型工程难维护 | 几十个子目录的递归 make 极难调试 |
| 增量构建靠时间戳 | 时钟回拨、文件复制会误判 |

> **所以有了 CMake** 👇

## 四、构建系统：为什么需要 CMake

### 4.1 CMake 在链路里的位置

CMake **不是编译器**，它只做一件事：把一份平台无关的 `CMakeLists.txt` 翻译成某个构建工具能执行的输入文件，之后的编译链接仍然由 `make`/`ninja` 调用编译器完成。

```
CMakeLists.txt ──cmake──▶ Makefile / build.ninja ──make/ninja──▶ gcc/ld ──▶ .elf
                          ↑ 生成阶段              ↑ 构建阶段
```

一句话：**CMake 替代的是手写 Makefile，不是替代编译器**。

### 4.2 两个阶段

| 阶段 | 做什么 | 典型命令 |
|:--|:--|:--|
| Configure | 读 CMakeLists、探测编译器、生成构建文件、缓存到 `CMakeCache.txt` | `cmake -S . -B build` |
| Build | 调用底层工具，真正编译链接 | `cmake --build build` |

配置阶段能跑任意脚本（探测编译器能力、生成头文件、下载依赖），构建阶段只做编译链接。很多「为什么我的变量是空的」问题，都源于没搞清某个值在哪个阶段求值。

### 4.3 最小示例（够看懂，不展开）

```cmake
cmake_minimum_required(VERSION 3.20)
project(Firmware VERSION 1.0.0 LANGUAGES C ASM)

add_executable(firmware main.c startup.s)
target_include_directories(firmware PRIVATE inc)
target_link_options(firmware PRIVATE -T link.ld -Wl,--gc-sections)
```

三行就够表达「用哪些源码、头文件在哪、链接脚本在哪」。完整的语法、target 模型、作用域传导、生成器表达式见 [[knowledge/embedded/02-CMake工程实战-嵌入式固件七能力\|02-CMake 工程实战]]。

### 4.4 与 Make 的分工

| | Makefile | CMake |
|:--|:--|:--|
| 抽象层级 | 直接描述编译命令 | 描述目标与依赖，命令由它生成 |
| 跨平台 | 手写各平台分支 | 一套文件，切换生成器 |
| 依赖传导 | 手写变量 | target 的 `PUBLIC`/`PRIVATE` |
| 适用规模 | 几十个文件 | 几百个文件以上 |

## 五、链接脚本 (Linker Script)

### 5.1 为什么需要链接脚本

编译器产出的 `.o` 里，每个段只有「大小」和「相对偏移」，**不知道要放到芯片的哪个地址**。链接脚本告诉链接器：

- 目标芯片的 Flash/RAM 起始地址和大小
- 每个段放到哪个区域的什么位置
- 哪些符号（`_sdata`/`_etext` 等）暴露出地址给启动代码用

格式通常是 `.ld` 或 `.lds`（GNU LD），也有 `.icf`（IAR）或 `.scf`（ARMCC）。

### 5.2 嵌入式芯片的存储布局

```text
STM32F407VGT6:
┌────────────────── 0x00000000 ──────────────────┐
│                  Flash (1MB)                     │
│  0x08000000  ┌──────────────────────────────┐    │
│              │  .isr_vector（中断向量表）      │    │
│              │  .text（代码段）               │    │
│              │  .rodata（常量、字符串）        │    │
│              │  .init_array（初始化函数表）    │    │
│              └──────────────────────────────┘    │
├────────────────── 0x10000000 ──────────────────┤
│                  RAM (128KB)                     │
│  0x20000000  ┌──────────────────────────────┐    │
│              │  .data（初始化的全局变量）       │    │
│              │  .bss（未初始化的全局变量）       │    │
│              │  .heap（堆，malloc）             │    │
│              │  .stack（栈）                    │    │
│              └──────────────────────────────┘    │
└──────────────────────────────────────────────────┘
```

### 5.3 完整链接脚本示例

```ld
/* ===== link.ld — STM32F407 链接脚本 ===== */

/* 芯片内存布局定义 */
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K  /* 1MB Flash，只读+执行 */
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K   /* 128KB RAM，读写+执行 */
    CCMRAM (rw) : ORIGIN = 0x10000000, LENGTH = 64K    /* 64KB CCM RAM（内核专用）*/
}

/* 入口点（Reset 中断向量） */
ENTRY(Reset_Handler)

/* 段定义 */
SECTIONS
{
    /* ===== Flash 区域 ===== */
    .text :
    {
        . = ALIGN(4);
        KEEP(*(.isr_vector))         /* 中断向量表 — 必须放在最前面 */
        *(.text*)                     /* 代码段 */
        *(.rodata*)                   /* 只读数据（常量） */
        KEEP(*(.init_array))          /* C++ 构造函数表 */
        . = ALIGN(4);
        _etext = .;                   /* 代码结束地址（用于 Copy .data）*/
    } > FLASH

    /* ===== RAM 区域 ===== */
    /* 初始化的全局变量（启动时从 Flash 复制到 RAM）*/
    .data : AT(_etext)
    {
        . = ALIGN(4);
        _sdata = .;                   /* data 起始地址 */
        *(.data*)
        . = ALIGN(4);
        _edata = .;                   /* data 结束地址 */
    } > RAM

    /* 未初始化的全局变量（启动时清零）*/
    .bss :
    {
        . = ALIGN(4);
        _sbss = .;                    /* bss 起始地址 */
        *(.bss*)
        *(COMMON)
        . = ALIGN(4);
        _ebss = .;                    /* bss 结束地址 */
    } > RAM

    /* ===== Heap & Stack ===== */
    .heap (COPY) :
    {
        _heap_start = .;
        . = . + 0x8000;               /* 32KB heap */
        _heap_end = .;
    } > RAM

    .stack (COPY) :
    {
        _stack_end = .;
        . = . + 0x4000;               /* 16KB stack */
        _stack_top = .;
    } > RAM
}
```

### 5.4 启动时数据搬运

链接脚本定义的符号（`_sdata`、`_edata`、`_etext` 等）在启动代码里被用到：

```c
// startup_stm32f407xx.c（简化版）
extern uint32_t _sdata, _edata, _etext;
extern uint32_t _sbss, _ebss;

void Reset_Handler(void)
{
    // 1. 复制 .data 从 Flash → RAM
    uint32_t *src = &_etext;
    uint32_t *dst = &_sdata;
    while (dst < &_edata) *dst++ = *src++;

    // 2. 清零 .bss
    for (dst = &_sbss; dst < &_ebss; ) *dst++ = 0;

    // 3. 跳转到 main
    main();
}
```

**为什么 `.data` 要搬**：初始化值存在 Flash（掉电不丢），但变量运行时必须在 RAM 里读写。所以启动时从 Flash 复制一份到 RAM。`.bss` 全是 0，不需要存初值，只占 RAM 不占 Flash。

这解释了一个常见困惑：**为什么 `size` 报告里 `data` 段同时占 Flash 和 RAM** —— 因为它在两边各有一份。

### 5.5 进阶技巧

```ld
/* 版本号嵌入固件 */
. = ALIGN(4);
.version_info :
{
    KEEP(*(.version_info))
    LONG(1)          /* 主版本 */
    LONG(2)          /* 次版本 */
    LONG(3456)       /* Build number */
    LONG(0x20260706) /* 日期 */
} > FLASH

/* 自定义段——把关键函数放到 RAM 里跑（加快速度）*/
.fast_ram :
{
    *(.ramfunc*)
} > RAM AT > FLASH

/* 检查溢出（链接期就报错，比烧进去跑飞好得多）*/
ASSERT(SIZEOF(.text) < 1024K - 4K, "Flash 溢出！")
ASSERT(ORIGIN(RAM) + LENGTH(RAM) - _stack_top > 0x200, "RAM 溢出！")
```

### 5.6 内存布局参数化

换芯片就要改 `.ld` 里的地址，容易漏改。工程上的做法是把 `.ld` 变成模板（`.ld.in`），构建时由构建系统替换占位符：

```ld
/* stm32f407.ld.in */
MEMORY
{
    FLASH (rx) : ORIGIN = @FLASH_ORIGIN@, LENGTH = @FLASH_LENGTH@
    RAM   (rwx): ORIGIN = @RAM_ORIGIN@,   LENGTH = @RAM_LENGTH@
}
```

替换动作由构建系统完成：Make 里用 `sed`，CMake 里用 `configure_file(... @ONLY)`。具体写法见 [[knowledge/embedded/02-CMake工程实战-嵌入式固件七能力\|02]] 第四节（链接脚本模板化）。

> 双镜像（Bootloader + APP）时**必须给每个镜像一套独立变量名**。用同一个 `FLASH_ORIGIN` 反复覆盖，覆盖顺序一变两份镜像的地址就会静默互换 —— 现象是 APP 烧进去不跑、BL 却能启动。

## 六、静态库 vs 动态库

### 6.1 对比

| 特性 | 静态库 (`.a`) | 动态库 (`.so` / `.dll`) |
|:--|:--|:--|
| **链接时机** | 编译时直接打入可执行文件 | 运行时加载 |
| **最终体积** | 大（每个可执行文件各存一份） | 小（多进程共享） |
| **部署** | 单文件，省心 | 依赖 `.so` 路径配置 |
| **更新** | 要重新链接 | 替换 `.so` 即可（**要求 ABI 兼容**） |
| **嵌入式使用** | ✅ **常用** | ❌ 裸机/RTOS 基本不用 |
| **性能** | 无额外开销 | 动态链接有少量开销 |
| **工具** | `ar` 打包 | `gcc -shared` 生成 |

> ABI 兼容指：不改类成员布局、不改函数签名、不删导出符号。改了这些还只换 `.so`，会在运行期崩（`symbol lookup error` 或静默内存错乱）。

### 6.2 嵌入式场景：99% 用静态库

原因：

- 裸机/RTOS 通常**没有动态加载器**
- 代码放 Flash，RAM 宝贵，没法给动态链接留空间
- 版本管控要求确定性（不能依赖外部 `.so` 的版本）
- 单文件固件便于烧录和 OTA 校验

### 6.3 手工制作静态库

```bash
# 1. 编译目标文件
arm-none-eabi-gcc -c uart.c -o uart.o
arm-none-eabi-gcc -c gpio.c -o gpio.o

# 2. 打包成静态库
arm-none-eabi-ar rcs libdrivers.a uart.o gpio.o

# 3. 使用静态库链接
arm-none-eabi-gcc main.o -L. -ldrivers -o firmware.elf
```

**链接顺序的坑**：`ld` 对静态库是**单次从左到右扫描**。库 A 依赖库 B，`-lA -lB` 正确，`-lB -lA` 报 `undefined reference`。循环依赖用 `-Wl,--start-group ... -Wl,--end-group` 包起来。

### 6.4 动态库（嵌入式 Linux 场景）

在嵌入式 Linux（Cortex-A 跑 Linux）中动态库是常态：

```bash
# 交叉编译动态库
arm-linux-gnueabihf-gcc -fPIC -shared algorithm.c -o libalgorithm.so

# 使用
arm-linux-gnueabihf-gcc main.c -L. -lalgorithm -o app

# 运行时找不到 .so 的三种解法
export LD_LIBRARY_PATH=/usr/lib:$LD_LIBRARY_PATH    # 临时
# 或装到系统路径
# 或用 rpath 把搜索路径写进 ELF（$ORIGIN = 可执行文件所在目录）
```

`-fPIC` 不能省：位置无关代码，否则动态库无法被加载到任意地址。

## 七、交叉编译 (Cross Compilation)

### 7.1 什么是交叉编译

> **在 PC（x86）上编译出给 MCU（ARM）用的代码**

之所以需要，是因为 MCU 性能太弱，跑不动编译器。

```
开发机 (x86 Linux)                         目标 ECU (ARM Cortex-M4)
┌────────────────────┐                    ┌──────────────────────┐
│ arm-none-eabi-gcc  │                    │                      │
│ arm-none-eabi-g++  │  ─── .elf ───►     │  Flash → 执行        │
│ arm-none-eabi-ld   │  ─── .bin ───►     │                      │
└────────────────────┘                    └──────────────────────┘
  "我帮你编译"                               "我直接运行"
```

三种编译形态：

| 形态 | 编译器 | 运行平台 | 用途 |
|:--|:--|:--|:--|
| 本地编译 | `gcc` | 同架构 | 主机侧单元测试、工具 |
| 交叉编译 | `arm-none-eabi-gcc` | 不同架构 | 固件 |
| 自举编译 | 自带编译器 | 同架构 | 大型系统（少见） |

### 7.2 完整命令行流程

```bash
# ===== 1. 安装工具链 =====
sudo apt install gcc-arm-none-eabi binutils-arm-none-eabi

# 或从 ARM 官网下载预编译包
wget https://developer.arm.com/-/media/Files/downloads/gnu-rm/...-arm-none-eabi.tar.bz2
tar xjf gcc-arm-none-eabi-*.tar.bz2 -C /opt
export PATH=/opt/gcc-arm-none-eabi/bin:$PATH

# ===== 2. 编译（逐个 .c → .o）=====
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -O2 -c main.c -o main.o
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -O2 -c startup.s -o startup.o

# ===== 3. 链接（含链接脚本）=====
arm-none-eabi-gcc -T link.ld main.o startup.o -o firmware.elf -Wl,-Map=output.map -Wl,--gc-sections

# ===== 4. 转格式 =====
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
arm-none-eabi-objcopy -O ihex   firmware.elf firmware.hex
arm-none-eabi-objcopy -O srec   firmware.elf firmware.s19

# ===== 5. 查看结构 =====
arm-none-eabi-size firmware.elf
arm-none-eabi-objdump -d firmware.elf | head -50
arm-none-eabi-readelf -a firmware.elf
```

### 7.3 手工命令的问题

上面这套命令写死在脚本里，改芯片要改一堆参数。而且：

- 编译参数在编译、链接两处重复（`-mcpu` 等）
- 新增源文件要手工加一行
- 头文件依赖不跟踪，改了 `.h` 不重编

这正是构建系统存在的理由。**CMake 里用 Toolchain File 把「用哪个编译器、什么参数」集中到一个文件**，然后所有编译链接命令由它自动生成 —— 详见 [[knowledge/embedded/02-CMake工程实战-嵌入式固件七能力\|02]] 第三节（cross-compile）。

### 7.4 交叉编译常见问题排查

| 症状 | 原因 | 解决 |
|:--|:--|:--|
| `cannot execute binary file: Exec format error` | 拿 ARM 产物在 x86 上跑 | 换成正确的执行环境 |
| `error trying to exec 'cc1': execvp: No such file` | `PATH` 里缺工具链内部路径 | 用完整的工具链安装目录 |
| `SIGSEGV` 在 target 上 | 链接脚本内存布局错误 | 检查 Flash/RAM 地址 |
| `undefined reference` | 没链接对应的 `.o` 或 `.a`，或链接顺序不对 | 检查目标依赖；用 `--start-group` |
| HardFault 在启动时 | 中断向量表位置不对 | `KEEP(*(.isr_vector))` 必须在 `.text` 段首 |
| 编译通过但跑飞 | 优化级别过高或缺 `volatile` | 先用 `-O0` 定位，检查变量加 `volatile` |
| 浮点运算异常 | FPU 设置与芯片不匹配 | `-mfpu` + `-mfloat-abi` 要和芯片一致 |
| Flash 写不进去 | 固件尺寸超过芯片 Flash | 看 `arm-none-eabi-size` 输出 |
| 链接报 `_sbrk not defined` 之类 | 缺 `nosys.specs` 或自己实现系统调用桩 | 加 `--specs=nosys.specs` |
| 编译时用了主机编译器 | 工具链没在配置阶段生效 | 见 02 的 Toolchain File 用法 |

## 八、产物后处理（bin / hex / map / size）

### 8.1 为什么还需要这一步

链接产出的是 `.elf` —— 带符号表、调试信息、段头的完整容器，**烧录器不认识它**。要转成裸二进制或带地址记录的文本格式。

| 格式 | 命令 | 特点 | 用在哪 |
|:--|:--|:--|:--|
| `.elf` | 链接器直接产出 | 含符号/调试信息 | 调试、存档、size 分析 |
| `.bin` | `objcopy -O binary` | 纯二进制，无地址信息 | 烧录（地址由写入命令指定） |
| `.hex` | `objcopy -O ihex` | Intel HEX，含地址记录 | 多数烧录器、OTA |
| `.s19` | `objcopy -O srec` | Motorola S-record，含地址和校验 | 部分车厂刷写工具 |
| `.map` | `-Wl,-Map=xxx.map` | 符号地址与段布局清单 | 排查溢出、分析内存占用 |

### 8.2 三种格式的本质区别

```
.bin   ← 只有字节流，烧录地址靠外部指定
        [ 0x00 0x01 0x02 ... ]
        ↑ 从哪个地址开始写？烧录命令里告诉它

.hex   ← 每行带地址和校验
        :10010000214601360121470136007EFE09D21901 40
         ↑字节数 ↑地址↑类型        ↑数据            ↑校验和

.s19   ← 类似的记录格式，Motorola 风格
        S00600004844521B
```

`.bin` 最省空间但**必须有配套的地址信息**；`.hex`/`.s19` 自带地址，烧录器能自己解析，适合多段镜像。

### 8.3 把 size 报告当成门禁

```bash
arm-none-eabi-size --format=berkeley firmware.elf
```

```
   text    data     bss     dec     hex filename
  24576    1024    8192   33792    8400 firmware.elf
```

| 段 | 含义 | 实际占用 |
|:--|:--|:--|
| `text` | 代码 + 只读数据 + 向量表 | Flash |
| `data` | 有初值的全局变量 | **Flash + RAM 双份** |
| `bss` | 无初值的全局变量 | 仅 RAM |

**Flash 占用 = text + data，RAM 占用 = data + bss + heap + stack**。CI 里应该直接拿这两个数做门禁，超限就 fail —— 比烧到板上才发现便宜得多。

### 8.4 后处理该挂在哪

| 工具 | 时机 | 说明 |
|:--|:--|:--|
| Make | `all:` 目标之后追加命令 | 每次 `make` 都跑 |
| CMake | `add_custom_command(TARGET xxx POST_BUILD ...)` | 目标构建成功后自动触发 |

两种都要求：**只在交叉编译时执行**。主机侧演练时 `CMAKE_OBJCOPY` 是空的，不加条件会直接报错。

## 九、AUTOSAR 分层架构

### 9.1 分层与依赖方向

AUTOSAR 把一个 ECU 的代码按「抽象层级」切开，**依赖只能向下，不能向上**：

```
┌─────────────────────────────────────────────┐
│  SWC  应用软件组件（业务逻辑）                 │
│       发动机控制、制动控制…                    │
└───────────────────┬─────────────────────────┘
                    │ 只能调 RTE 提供的接口
┌───────────────────▼─────────────────────────┐
│  RTE  运行时环境（由工具从 ARXML 生成）         │
└───────────────────┬─────────────────────────┘
                    │
┌───────────────────▼─────────────────────────┐
│  BSW  基础软件层                              │
│  ┌────────┬────────┬────────┬────────┐      │
│  │  COM   │  Diag  │  NvM   │  OS    │      │
│  │ 通信栈  │ 诊断    │ 存储    │ 操作系统│      │
│  └────────┴────────┴────────┴────────┘      │
└───────────────────┬─────────────────────────┘
                    │
┌───────────────────▼─────────────────────────┐
│  MCAL 微控制器抽象层                          │
│  Adc / Dio / Spi / Can / Fls …               │
└───────────────────┬─────────────────────────┘
                    │
              ┌─────▼─────┐
              │  硬件寄存器  │
              └───────────┘
```

### 9.2 各层职责

| 层 | 全称 | 职责 | 谁写 |
|:--|:--|:--|:--|
| MCAL | Microcontroller Abstraction Layer | 把寄存器操作包成统一 API（`Adc_Read()`） | 芯片厂商 / 向量 |
| BSW | Basic Software | 通信栈、诊断、存储、OS 等通用服务 | 供应商（Vector/ETAS） |
| RTE | Runtime Environment | SWC 与 BSW 之间的通信中介，由 ARXML 生成 | 代码生成器 |
| SWC | Software Component | 真正的业务逻辑 | 应用团队 |

### 9.3 为什么这样分层

| 收益 | 说明 |
|:--|:--|
| **换芯片只改 MCAL** | 上层代码一行不动，只需换一套 MCAL 实现 |
| **换车型只改配置** | 用 ARXML 描述，RTE 代码重新生成，SWC 不动 |
| **可测试** | SWC 依赖 RTE 接口而非寄存器，主机侧可以 mock RTE 跑单测 |
| **可并行开发** | 四个层由不同团队/供应商同时推进 |

### 9.4 映射到构建系统

分层在构建系统里的体现是**一层一个静态库，依赖用 `PUBLIC` 向下传递**：

```
ecu_fw
├── swc_engine ─┐
├── swc_brake  ─┤
│              └▶ rte ─┬▶ com ─▶ mcal
│                      ├▶ os
│                      ├▶ diag
│                      └▶ nvm
```

- 每个模块编成 `add_library(xxx STATIC)`
- 模块头文件目录用 `PUBLIC` 导出，上层自动拿到
- 最终可执行文件链接所有层，静态库循环依赖用 `--start-group`

**完整的 CMakeLists 写法见** [[knowledge/embedded/02-CMake工程实战-嵌入式固件七能力\|02]] 以及其第六节（imported-lib）；本节只负责说清「为什么这样分层」。

### 9.5 官方代码生成的角色

AUTOSAR 项目里大量代码不是手写的：

```
ARXML（系统描述）
    │
    ├──▶ RTE 代码生成器 ──▶ Rte.c / Rte.h
    └──▶ BSW 配置生成器 ──▶ *_Cfg.c / *_Cfg.h
```

这类生成代码接入构建时有两个硬性要求：

1. **生成命令要有显式 `OUTPUT` 和 `DEPENDS`**，否则改了 ARXML 不重新生成
2. **不要用通配符递归收集生成目录**，生成器常留 `.tmp`/备份文件，会被误编进去

具体接法见 02 的相关章节。

## 十、单元测试在构建中的位置

### 10.1 核心思路：双编译

嵌入式单元测试的难点：**测试跑不了在目标板上**。标准做法是**同一份业务代码编两遍**：

```
        ┌── arm-none-eabi-gcc ──▶ firmware.elf   （上板跑）
src/ ──┤
        └── host gcc ──────────▶ test_runner     （CI 里跑）
                                      ↑
                             硬件接口用 mock 替换
```

**能这么做的前提**：业务代码不直接调寄存器，而是通过 HAL 抽象层。这是嵌入式工程分层最实在的收益之一 —— 和第九章 AUTOSAR 分层是同一个道理。

### 10.2 目录结构

```
project/
├── src/
│   ├── palindrome.c        ← 纯逻辑，可主机编译
│   └── reverse.c
├── hal/
│   └── uart.c              ← 真实硬件实现（目标侧）
├── test/
│   ├── mock_uart.c         ← 硬件 mock（主机侧）
│   └── test_palindrome.cpp
└── CMakeLists.txt
```

关键点：`src/` 里不能有 `#include <stm32f4xx.h>` 这类目标相关的头文件。业务逻辑只依赖 HAL 提供的抽象接口。

### 10.3 两侧构建命令

```bash
# 目标侧（固件）
cmake -S . -B build-arm -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake
cmake --build build-arm

# 主机侧（跑测试）
cmake -S . -B build-host -DBUILD_TESTING=ON
cmake --build build-host
ctest --test-dir build-host --output-on-failure
```

两边**必须用不同的构建目录**，且主机侧不加 Toolchain File。

### 10.4 测试指标（嵌入式特有）

| 指标 | 工具 | 门槛建议 |
|:--|:--|:--|
| 行覆盖率 | `gcov` / `lcov` | ≥ 70%（业务逻辑层） |
| 分支覆盖率 | `gcov -b` | ≥ 60% |
| MISRA 合规 | `cppcheck --addon=misra` | 零新增违规 |
| 静态分析 | `clang --analyze` | 零 error |

```bash
# 覆盖率构建
cmake -S . -B build-cov -DBUILD_TESTING=ON \
    -DCMAKE_C_FLAGS="--coverage -O0" \
    -DCMAKE_EXE_LINKER_FLAGS="--coverage"
cmake --build build-cov
ctest --test-dir build-cov
gcovr -r . --html-details coverage.html
```

> **硬件 mock 的价值**：没有它，覆盖率几乎为零 —— 嵌入式代码里大量 `if (reg & MASK)` 在主机上跑不了。写了 mock 之后，业务逻辑能覆盖到 80%+，剩下的硬件抽象层靠 HIL 测试兜底。

## 十一、构建进阶：产物可追溯

### 11.1 版本信息注入

现场拿到一块板子，要能立刻回答「这是哪次 CI 出来的固件」。做法是在构建时把 Git 信息编进去：

```bash
gcc -DFW_VERSION="$(git describe --tags --always --dirty)" \
    -DFW_GIT_HASH="$(git rev-parse --short HEAD)" \
    -DFW_BUILD_TIME="$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
    ...
```

CMake 里用 `configure_file` 生成版本头，见 02 的进阶章节。

### 11.2 编译数据库

给 IDE（CLion / VS Code / Vim）提供准确的编译参数，否则交叉编译时满屏红线：

```bash
# Make 工程
bear -- make

# CMake 工程
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
# 产物：build/compile_commands.json
```

### 11.3 构建工具选择

| 生成器 | 特点 |
|:--|:--|
| Unix Makefiles（默认） | 通用，递归解析慢 |
| **Ninja** | 依赖图紧凑，大工程快 20~50% |
| Ninja Multi-Config | 一个目录支持多配置 |

```bash
cmake -S . -B build -G Ninja
```

### 11.4 产物可复现

```bash
# 同一 commit 构建两次，比对 .bin
sha256sum build1/firmware.bin build2/firmware.bin
```

两次不一致通常因为：

- `__DATE__` / `__TIME__` 宏（把构建时间编进固件）
- 源文件遍历顺序不稳定（通配符在某些文件系统上顺序随机）
- 内嵌了随机 UUID 或时间戳

**能复现的固件**意味着「给定 commit 就能重建出字节一致的产物」，这是车规 OTA 追溯的基本要求。

## 十二、CI/CD 中的构建流水线（嵌入式特化）

### 12.1 典型流水线

```groovy
// Jenkinsfile（嵌入式项目）
pipeline {
    agent { label 'arm-builder' }

    stages {
        stage('Checkout') {
            steps { checkout scm }
        }

        stage('Static Analysis') {
            steps {
                sh 'sonar-scanner -Dsonar.sources=. -Dsonar.language=c'
                sh 'cppcheck --enable=all --std=c11 --suppress=*:test/* src/'
                sh 'misra-checker --config=misra2012.xml src/'
            }
        }

        stage('Build') {
            steps {
                sh 'cmake -S . -B build -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake -DCMAKE_BUILD_TYPE=Release'
                sh 'cmake --build build'
            }
        }

        stage('Unit Test') {
            steps {
                // 主机侧编译跑测试，与目标侧完全独立
                sh 'cmake -S . -B build-test -DBUILD_TESTING=ON'
                sh 'cmake --build build-test'
                sh 'ctest --test-dir build-test --output-on-failure'
            }
        }

        stage('Size Check') {
            steps {
                // 固件超限直接失败，别等烧到板上才发现
                sh './scripts/check_size.sh build/firmware.elf 448K'
            }
        }

        stage('Archive') {
            steps {
                archiveArtifacts artifacts: 'build/*.bin, build/*.hex, build/*.map, build/*.elf'
            }
        }
    }
}
```

### 12.2 嵌入式 CI/CD 的特殊点

| 环节 | 注意事项 |
|:--|:--|
| **构建环境** | 交叉编译工具链需预装或固化进 Docker 镜像；版本必须锁定 |
| **软件许可** | IAR/KEIL 等商业编译器需要 License 服务器，CI 容器要能连上 |
| **静态分析** | MISRA 检查是嵌入式必修课，通常设为质量门禁 |
| **单元测试** | 必须在 x86 主机上编译，硬件接口 mock |
| **大小门禁** | `size` 超限直接 fail，比出问题后再回溯便宜得多 |
| **HIL 测试** | 真正的验证要把固件刷到 ECU 上跑，通常是独立阶段 |
| **版本号注入** | 编译时注入 Git commit / build number，产物可追溯 |
| **产物管理** | `.bin`/`.hex` + `.map` 需长期保存（可追溯、可复现） |

### 12.3 流水线里最容易被忽略的三个门禁

1. **工具链版本检查** —— `arm-none-eabi-gcc --version` 记进日志，否则产物漂移无法归因
2. **ABI 自检** —— `file libxxx.a | grep ARM`，防止 vendor 库混入 x86 版本
3. **产物可复现** —— 见 11.4，同一 commit 两次构建 md5 必须一致
