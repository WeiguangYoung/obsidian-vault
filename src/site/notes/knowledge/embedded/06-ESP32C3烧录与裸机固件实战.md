## 一、这块板是什么

| 项目 | 值 | 来源 |
|:--|:--|:--|
| 芯片 | ESP32-C3 (QFN32) rev **v0.4** | esptool |
| 封装 | **32 pin**（每侧 16） | 实物 |
| Flash | **4 MB**（厂商 `c2` / 型号 `2016`；实测颗粒 MXIC） | esptool / IDF |
| 晶振 | 40 MHz | esptool |
| MAC | `14:63:93:f9:12:80` | esptool |
| 串口桥 | **CH343** `1a86:55d3` → `/dev/ttyACM0` | `lsusb` |
| 接口 | Type-C | 实物 |
| 按键 | BOOT + RST | 实物 |
| 板面丝印 | `ESP32C3` / `V1.0.0` / `LuatOS` | 实物 |
| 原生 JTAG | ❌ 无（Type-C 走 CH343） | 实测 |
| **flash 模式** | **必须 DIO**（QIO 在 C3 镜像头里也被映射成 dio） | 实测 + IDF Kconfig |
| **flash 频率** | 40MHz 保守取值；**80MHz 实测同样正常** | 实测推翻旧结论 |

### 复现命令

```bash
lsusb | grep -iE "1a86|303a|10c4"          # 串口桥型号
ls /dev/tty{ACM,USB}*
python3 esptool.py --port /dev/ttyACM0 chip_id    # 芯片 + MAC
python3 esptool.py --port /dev/ttyACM0 flash_id   # Flash 厂商与容量
```

`chip_id` 在 C3 上会提示「has no Chip ID」并转而读 MAC —— 正常，不是失败。

### 没有原生 USB-JTAG

Type-C 接 CH343，CH343 连 UART0（`GPIO20/21`）。与芯片内置 USB-JTAG（`GPIO18/19`）互斥，所以只能 `printf`，不能断点调试。

> ⚠️ 两条路的设备节点都可能叫 `/dev/ttyACM0`，必须看 VID 区分：`303a:1001` 是乐鑫原生，`1a86:55d3` 是 CH343。

### 端口名对照

| 方案 | 节点 | VID:PID |
|:--|:--|:--|
| 内置 USB-JTAG | `/dev/ttyACM0` | `303a:1001` |
| CH343（本板） | `/dev/ttyACM0` | `1a86:55d3` |
| CH340 | `/dev/ttyUSB0` | `1a86:7523` |
| CP2102 | `/dev/ttyUSB0` | `10c4:ea60` |

## 二、引脚表

⚠️ **`P1`/`P17` 在 USB 接口一端（下），`P16`/`P32` 在另一端（上）。** 容易数反。

左排 P1–P16：

| # | 符号 | # | 符号 |
|:--:|:--|:--:|:--|
| 1 | GND | 9 | IO11 ⚠️ |
| 2 | 5V | 10 | IO07 |
| 3 | BOOT (IO09) | 11 | IO06 |
| 4 | IO08 | 12 | IO10 |
| 5 | IO04 | 13 | IO03 |
| 6 | IO05 | 14 | IO02 |
| 7 | 3.3V | 15 | 3.3V |
| 8 | GND | 16 | GND |

右排 P17–P32：

| # | 符号 | # | 符号 |
|:--:|:--|:--:|:--|
| 17 | 5V | 25 | TX0 ⚠️ |
| 18 | PWR ⚠️ | 26 | GND |
| 19 | GND | 27 | IO19 |
| 20 | 3.3V | 28 | IO18 |
| 21 | EN (RESET) | 29 | IO12 ⚠️ |
| 22 | NC | 30 | IO01 |
| 23 | IO13 ⚠️ | 31 | IO00 |
| 24 | RX0 ⚠️ | 32 | GND |

### 三处必须注意

**PWR (P18) 不是 PWM** —— 芯片 3.3V 供电使能，高有效，可悬空。拉低等于断电。

**三个脚不能当普通 IO**：

| 脚 | 实际功能 | 风险 |
|:--|:--|:--|
| `IO11` (P9) | `VDD_SPI`，Flash 供电 | 输出低会断 Flash 供电 → 死机 |
| `IO12` (P29) | `SPIHD` | 已占用 |
| `IO13` (P23) | `SPIWP` | 已占用 |

**其他约束**：`IO18/19` 用完失去原生 USB；`IO02/08/09` 是 strapping；`IO20/21` 占用即抢走日志口。

### P24/P25 引脚定义

| 位号 | 丝印 |
|:--|:--|
| P24 | `TX0` |
| P25 | `RX0` |

⚠️ 丝印只说明「这根针是 TX0」，**未说明对应 GPIO20 还是 GPIO21**，焊盘到芯片引脚的映射仍需实测。要接串口，稳妥做法是换别的脚走 GPIO Matrix 重映射避开这对针。

## 三、两条路线怎么选

| | ESP-IDF | 纯裸机 |
|:--|:--|:--|
| 上手速度 | 快，`idf.py flash` 一次通 | 慢，要先啃 TRM |
| 学到什么 | 工程组织、组件系统 | **启动流程、链接脚本、寄存器、时钟树** |
| 串口/printf | 开箱可用 | 要自己配 UART 全套寄存器 + 踩 ROM 符号坑 |
| 无线功能 | 完整 WiFi/BLE 栈 | 用不了（协议栈是闭源 blob） |
| 适合场景 | 做产品、赶进度 | 学原理、验证底层理解 |

**结论**：要功能走 IDF，要理解走裸机。本文两条都记录，因为**裸机路线上踩的坑，恰好把 IDF 里被封装掉的东西全暴露了一遍**。

## 四、ESP-IDF 路线

### 4.1 烧录配方

写入工程根目录的 `sdkconfig.defaults`：

```ini
CONFIG_IDF_TARGET="esp32c3"
CONFIG_ESPTOOLPY_FLASHMODE_DIO=y
CONFIG_ESPTOOLPY_FLASHFREQ_40M=y
CONFIG_ESPTOOLPY_FLASHSIZE_4MB=y
```

然后：

```bash
idf.py set-target esp32c3     # 首次
idf.py build
idf.py -p /dev/ttyACM0 flash monitor
```

键名均与乐鑫官方 ESP-AT 包（`ESP32-C3-MINI-1-V2.4.2.0/sdkconfig`）逐项对齐，已核对。

菜单里对应的路径：`Serial flasher config` → `Flash SPI mode` / `Flash SPI speed` / `Flash size`。

### 4.2 flash 参数：DIO 是硬约束，频率不是

**早期结论（已部分推翻）**：曾记录"flash 必须 40MHz DIO，80MHz 会启动死循环"。
实测证明**频率这一半是错的**——真正的元凶是别的。

#### 真凶一：镜像头声明的 flash 容量与实际不符

启动死循环的真实报错：

```
E (26) boot: load partition table error!
E (25) flash_parts: partition 0 invalid magic number 0xffed
```

`0xffed` 是**空 flash 读出的默认值**，说明 bootloader 按镜像头里的容量去算分区表地址，
算出来的位置根本没有数据。同包里的
`micropython-1.19.1-esp32c3-2mflash-firmware.bin` 是 **2MB 配置**（镜像头 `e9 03 02 1f`，
末字节 `0x1f` = speed 80MHz + size code 1 = 2MB），刷到 4MB 板上分区表就在 2MB 之外，
自然读出 `0xffed`。

**这才是当年的真实原因：容量错配，不是频率太高。**

#### 真凶二：PIO 的 flash 参数从来没生效过

`platformio.ini` 里原本写的是 `board_upload.flash_freq = 40m`。这个键**在本版 PlatformIO 里不存在**
（`board_upload` 段只有 `flash_size` / `maximum_ram_size` / `maximum_size` /
`require_upload_port` / `speed`），写了会被静默忽略，不报错也不警告。

镜像头的 `spi_speed` 字段来自 `build.f_flash`，而板级 `esp32-c3-devkitm-1.json` 默认
`f_flash = 80000000L`。所以**配置写着 40m，实际一直烧的是 80MHz**。

验证方法：直接解码镜像头第 4 个字节的低 4 位。

```python
SPEED = {0: '40MHz', 1: '26MHz', 2: '20MHz', 0xF: '80MHz'}
d = open('firmware.bin', 'rb').read(4)
print(SPEED[d[3] & 0x0F])     # 0x0F = 80MHz
```

正确写法是 `board_build.f_flash = 40000000L`。

#### 实测：80MHz + DIO 完全正常

改 `f_flash = 80000000L`、mode 保持 DIO，重新烧录：

```
I (29) boot.esp32c3: SPI Speed      : 80MHz
I (33) boot.esp32c3: SPI Mode       : DIO
I (45) boot: Partition Table:          ← 三行完整读出
I (133) boot: Loaded app from partition at offset 0x10000
I (635) uart1: loopback self-test: PASS
```

单次启动、无 `0xffed`、分区表正常、app 运行、外设自检通过。**80MHz 本身无害。**

#### 顺带发现：C3 上 QIO 在镜像头里永远是 dio

想验证"是不是 QIO 四线模式的问题"，翻 IDF 的 Kconfig 发现：

```
config ESPTOOLPY_FLASHMODE
    default "dio" if ESPTOOLPY_FLASHMODE_QIO
    default "dio" if ESPTOOLPY_FLASHMODE_QOUT
    default "dio" if ESPTOOLPY_FLASHMODE_DIO
    default "dout" if ESPTOOLPY_FLASHMODE_DOUT
```

**ESP32-C3 上 QIO/QOUT 都被映射成 `"dio"`**。这是有意设计：C3 的 SPI 外设上电后
先用 DIO 读镜像头，之后才由 bootloader 切到四线。所以"QIO 导致启动失败"这个假设
在 C3 上无法成立——镜像头根本不写 qio。

#### 那 40MHz 还要不要

要，但理由是**保守**而不是**必需**：

- 这块板 flash 是杂牌（厂商 `c2` / 型号 `2016`），40MHz 留有余量
- 官方 ESP-AT 出厂配置（`download.config`）也是 `--flash_mode dio --flash_freq 40m`
- 高频对启动速度提升有限，失败代价却是变砖

`platformio.ini` 最终保留 `board_build.f_flash = 40000000L`，
但注释里写清了它的来源和那条被推翻的旧结论，避免以后有人照着错因果去排查。

#### 配置到底谁说了算：三层来源

同一个 flash 参数在三个地方出现，改错地方**没有任何提示**：

| 位置 | 作用 | 能否控制镜像头 |
|:--|:--|:--|
| `platformio.ini` 的 `board_build.*` | PIO 板级配置 | **频率能**（`f_flash`） |
| `sdkconfig.defaults` | 只用于**首次生成** `sdkconfig.c3` | 间接 |
| `sdkconfig.c3` | 实际被 IDF 消费，生成后长期存在 | **不能** |

核心认知：**镜像头的 `spi_speed` / `spi_mode` 不是 IDF 编进去的**，
而是 PIO 调 `esptool elf2image` 时按 `build.f_flash` / `build.flash_mode` 现填的。
所以 `sdkconfig` 里把 `CONFIG_ESPTOOLPY_FLASHFREQ_40M=y` 写对了，
镜像头照样可能是 80MHz——这两条链路彼此独立。

三个实测坑：

1. **`board_upload.flash_freq` 不存在**。本版 PIO 的 `upload` 段只有
   `flash_size` / `maximum_ram_size` / `maximum_size` / `require_upload_port` / `speed`。
   写错的键被静默丢弃，不报错、不警告。
2. **`sdkconfig.c3` 一旦生成就长期保留**，`sdkconfig.defaults` 的后续改动不会同步进去。
   实测它还能进入自相矛盾状态：`CONFIG_ESPTOOLPY_FLASHMODE_QIO=y` 与
   `CONFIG_ESPTOOLPY_FLASHMODE="dio"` 并存（后者来自 Kconfig 的 default 映射）。
3. **改 `board_build.flash_mode = qio` 后镜像头仍写 `dio`**。这一条无法单独定位：
   C3 的 Kconfig 把 QIO/QOUT/DIO 全映射成 `"dio"`，所以无论 PIO 是否忽略该键，
   结果都一样。想验证只能换芯片，C3 上这个问题不存在。

重置到干净状态的可靠顺序：

```bash
rm -rf .pio/build/c3           # 清构建缓存（flash_args 在里面）
mv sdkconfig.c3 /tmp/          # 移走持久化 sdkconfig，让 defaults 重新生成
# 改好 platformio.ini 的 board_build.f_flash
pio run -e c3
```

验证只看镜像头，不要看配置：

```python
MODE  = {0:'QIO', 1:'QOUT', 2:'DIO', 3:'DOUT'}
SPEED = {0:'40MHz', 1:'26MHz', 2:'20MHz', 0xF:'80MHz'}
for f in ('bootloader.bin', 'firmware.bin'):
    d = open('.pio/build/c3/' + f, 'rb').read(4)
    print(f, MODE.get(d[2]), SPEED.get(d[3] & 0x0F))
```

> 启动日志里那行 `SPI Speed` 也来自镜像头（bootloader 按 `pfhdr->spi_speed` 打印），
> 所以它可信；但只有真烧上去才看得到，而镜像头在烧录前就能读。
> 先读头、再烧录，能省一轮。

### 4.4 PlatformIO 构建要点

本机 Python 3.8.10，只能锁 `espressif32@6.13.0`（对应 IDF 5.5.3）。更新的 8.x 平台带 IDF 6.1，依赖 `idf-component-manager>=3.1`（需 Python ≥3.10）和 `pydantic 2.12`（需 Python ≥3.9），在 3.8 上装不上。

首次构建需下载约 500 MB 框架，实测 `[SUCCESS] Took 188.10 seconds`。产物：

| 文件 | 大小 | 烧录偏移 |
|:--|:--|:--|
| `bootloader.bin` | 21 K | `0x0` |
| `partitions.bin` | 3.0 K | `0x8000` |
| `firmware.bin` | 171 K | `0x10000` |

### 4.5 MAC 地址

ESP-IDF 读出来和 esptool 一致，无需转换：

```c
#include "esp_mac.h"
uint8_t mac[6];
esp_read_mac(mac, ESP_MAC_WIFI_STA);   // 14:63:93:f9:12:80，正常字节序
```

## 五、裸机路线：从上游模板到可用固件

### 5.1 成品能力

| 功能 | 实现方式 | 状态 |
|:--|:--|:--:|
| UART0 控制台 | 寄存器直配（`CLK_CONF`/`CLKDIV`/`CONF0` + IO_MUX） | ✅ |
| UART1 重映射 | GPIO Matrix（GPIO4/GPIO5） | ✅ 内部回环 + 外部短接 `duplex OK` |
| 芯片信息 | efuse MAC + SPI1 直读 RDID | ✅ |
| 回显 + PING | 主循环轮询 | ✅ |
| 按键中断 | GPIO 中断 + handler | ✅ |
| 交互式 CLI | 11 条命令，表驱动分发 | ✅ |
| CLI 会话状态机 | `cli_state.c` 迁移表，5 状态 | ✅ |
| UART RX 中断 + 环形缓冲 | `ringbuf.c` 无锁 SPSC，256B | ✅ `overflow=0` |

### 5.5 上游模板的四个缺陷

模板本身在 C3 上**没有跑通过**，串口是完全不通的。逐一定位到四个缺陷。

**缺陷 1：`uart_init()` 是空桩**

上游只留了 TODO，`printf` 无处可写：

```c
static inline bool uart_init(uint32_t uart, int baud) {
  (void) uart, (void) baud;
  return false;
}
```

修法见「问题 1」：补 `CLK_CONF` / `CLKDIV` / `CONF0` + IO_MUX 四件事。

**缺陷 2：`link.ld` 里 `printf` 地址是错的**

模板写的是：

```ld
PROVIDE(printf = 0x40000040);
```

但对照 ESP-IDF 的 `esp32c3.rom.ld`，**`0x40000040` 实际是 `ets_printf`**，C3 的 newlib `printf` 在 **`0x400004a4`**。这个地址显然抄自 ESP32（xtensa）版本，RISC-V 的 C3 完全对不上。

逐条核对整个 `link.ld` 的 `PROVIDE` 块，只有 `printf` 一个错，`memset`/`strlen`/`uart_tx_one_char` 等都是对的。

**缺陷 3：`Reset_Handler` 从不开全局中断**

`mstatus.MIE`（bit3）一直没有置位，导致所有中断不被 CPU 响应，SysTick 不计数，`s_ticks` 恒为 0——即使 `printf` 能输出，时间也是死的。

修复只能写内联汇编，因为 `CSR_SETBITS(reg, 0, BIT(3))` 会触发 `-Wconversion`（`~0` 得到 `int -1`）：

```c
asm volatile("csrsi mstatus, 8");
```

**缺陷 4：时钟源假设错误（真正卡住串口的那一环）**

前三个都修完后，串口**依然 0 字节输出**。实测三次（补 UART 前 / 补 UART 后 / 改 printf 地址后）均为空。

真正的根因在「问题 2」：模板按 APB 80MHz 算波特率，而 `clock_init()` 是空函数、PLL 从未建立，实际 APB 不是 80MHz。改用 **XTAL 40MHz** 后立刻通了。

> 📌 **这个失败很有价值**：它证明「配置全对但输出为空」时，问题往往不在你刚改的那一层，而在更底层的时钟假设。
> 当时也得出过一个半对的结论——「别用裸机模板验串口，直接上 IDF」。事实上裸机能通，只是要先解决时钟。

**附：LED 是外接的。**

模板默认 `LED_PIN = 2`，README 原文写「Attach LED to pin 2」，即自己拿一颗 LED 串电阻接到 **GPIO2**。板载 LED 的 GPIO 仍未实测（见第八节）。

## 六、14 个问题清单（按发现顺序）

### 1. `uart_init()` 是空桩，`printf` 无输出

**现象**：编译烧录都成功，串口一片安静。

**原因**：上游 `hal.h` 里 `uart_init()` 直接 `return false`，寄存器一个没配。

**修法**：补 UART 寄存器初始化——`CLK_CONF`（选时钟源 + `sclk_en`/`tx_sclk_en`/`rx_sclk_en`）、
`CLKDIV`、`CONF0`（8N1 + `mem_clk_en`），再切 IO_MUX 到 UART 功能。

> ⚠️ 坑中坑：`CLKDIV` 的 `div_int` 在 `bit11:0`、`div_frag` 在 `bit23:20`，
> **两段不连续**，中间隔着保留位。按连续字段写必错。

### 2. 串口输出乱码，偏差正好 12 倍

**现象**：能收到字节，但全是乱码；速率看起来是预期的 12 倍。

**原因**：时钟源误用 APB 80MHz。本模板 `clock_init()` 是空函数，**PLL 从未建立**，
APB 实际不是 80MHz，按 80MHz 算出的分频必然错。

**修法**：改用 XTAL 40MHz（`sclk_sel=3`）——板上晶振上电即稳，与 PLL 无关。

> 💡 后续上了 PLL（问题 11），但 UART 仍**故意**继续挂 XTAL：
> 波特率不随 CPU 升频变化，调主频时串口不会乱码。这是个非常有用的隔离，
> 建议所有裸机项目都这么布：**调试通道的时钟不要跟着被测对象动。**

### 3. 按键中断一触发就跳空指针

**现象**：按一下键，整机重启。

**原因**：`gpio_set_irq_handler()` 传了 `NULL` handler，中断来了直接跳 0。

**修法**：补真实 handler，并注意参数通过 `void *param` 传递时用 `uintptr_t` 装引脚号。

### 4. `mcycle` 在 C3 上不可用（且会炸机）

**现象**：想用周期计数器反推主频，两次读数完全相同、`c1` 恒为 0。

**原因**：该 CSR 在 C3 上并不递增。

**更糟的尝试**：改用 64 位读法加 `mcycleh` —— **直接触发异常，整机重启**。
当时唯一的"证据"是串口横幅重复出现两次。

**结论**：C3 上放弃用周期计数器测频。

> ⚠️ 当时还顺手写下一个**错误结论**："`clock_sys_freq()` 的 160MHz 是配置值，
> ROM 的 20MHz 是 stale"。后来被问题 11 完全推翻。教训见第七节。

### 5. MAC 字节序

**现象**：读出来和 `esptool` 报的对不上。

**原因**：efuse 里 `RD_MAC_SPI_SYS_1` 低 16 位是 MAC[0..1]、`RD_MAC_SPI_SYS_0` 是 MAC[2..5]，
**都是大端**，直接拼会错位。

**修法**：先用 `esptool dump-mem` 实读校验，再写代码。
这次"先读后写"的做法，后来在问题 11 上救了整轮判断。

### 6. flash 报 2MB，实际 4MB

**现象**：ROM 的 `spi_flash_get_chip_size` 返回 2097152，但 `esptool flash-id` 说是 4MB。

**原因**：裸机启动没走 bootloader 的 flash 参数初始化，ROM 里那个值
还是 SPI 探测前的默认值。IDF 版走完整 bootloader，所以报得对。

**修法**：绕过 ROM，直接操作 SPI1 发 `RDID`(0x9F) 读 24 位。
两条 ROM 路径都试过，都不行：

| 路径 | 结果 |
|:--|:--|
| `esp_flash_read_id` (0x40000300) | `esp_flash_default_chip` 解引用为空——结构体从未初始化 |
| `esp_rom_spiflash_read_user_cmd` (0x40000138) | 固定只读 8 位，只回厂商字节 `0xC2` |

第二条能正确拿到 `0xC2`，说明 SPI1 时钟和 CS 都是好的，只是读位数不够。

**于是踩了两个子坑：**

**(a) `USR_COMMAND_BITLEN` 放错寄存器。** 它在 `USER2(+0x20)` 的 `bit31:28`，
不在 `USER1(+0x1C)`。放错时命令位宽为 0，实际只发 1 位，flash 毫无响应。

**(b) CTRL 里残留 boot ROM 的 DIO 位。** `fastrd_mode`/`fread_dual`/`fread_dio`
等位没清，读数据阶段走两根线，读回交错垃圾 `0x5D5DF5`（三字节全同）。
清掉 `bit7/8/13/14/20/23/24` 后才正常。

**字节序**：W0 是小端打包，低字节 = 线上第一个字节 = 厂商码。
实测 `0x1620C2` → 线序 `C2 20 16`，与 esptool 逐字节一致。
`cap=0x16` 按 SFDP 规则是 `1 << 0x16` = 4194304 = 4MB。

**安全前提**：`.text` 在 IRAM、数据在 DRAM，不经过 flash 取指，
所以手动发 SPI 命令不会把自己锁死。**这条不成立时不要这么干。**

### 7. GPIO Matrix 位域容易配错

**现象**：矩阵寄存器全配了，引脚毫无反应。

**原因**：`IO_MUX` 的 `MCU_SEL` 留 0 会走引脚默认固定功能（如 GPIO21 的 U0TXD），
**矩阵配了也不生效**。

**对齐 IDF `gpio_ll.h` 后的正确位域：**

| 寄存器 | 字段 |
|:--|:--|
| `func_out_sel_cfg` | `out_sel[7:0]`=信号号，`inv_sel[8]`，`oen_sel[9]` |
| `func_in_sel_cfg` | `in_sel[4:0]`=GPIO 号，`sig_in_inv[5]`，`sig_in_sel[6]`=1 启用矩阵 |
| `IO_MUX` | `MCU_SEL[14:12]` 必须置 **1** 才走矩阵 |

### 8. 内部回环 PASS ≠ 引脚映射正确

**现象**：自检打印 PASS，就以为 UART1 通了。

**原因**：`CONF0.loopback=1` 让信号在片内直接回环，**绕过 GPIO Matrix 和物理引脚**，
只能证明 UART 外设本身（时钟、分频、帧格式、FIFO）正常。

**修法**：要验证引脚映射，必须 GPIO4 ↔ GPIO5 外部短接，
看到 `duplex OK (GPIO4 -> GPIO5)` 才算过。

**实测（2026-11-25）**：短接左排 P5(IO04) ↔ P6(IO05) 后，日志出现

```
I (190587) uart1: duplex OK (GPIO4 -> GPIO5): rx 9 bytes
```

`rx 9 bytes` 正好是 `PING 29\r\n` 的 9 个字符，说明 RX 收到的确实是
从 GPIO4 发出去、经外部导线绕回 GPIO5 的那一帧。**引脚映射通过。**

| 验证级别 | 手段 | 证明什么 | 结果 |
|:--|:--|:--|:--:|
| 内部回环 | `uart_set_loop_back(true)` | UART 外设本身（时钟/分频/帧格式/FIFO） | PASS |
| 外部短接 | GPIO4 ↔ GPIO5 导线 | GPIO Matrix 引脚映射 + 物理通路 | PASS |

> 💡 这条可以推广成通则：**自环测试证明的是"自己没问题"，不是"接线没问题"。**

### 9. ROM 的 `strtoul` 在裸机下必崩

**现象**：加了 CLI 后，只要命令带数字参数（`led blink 100`、`hexdump ... 16`）
板子就死机；不带数字的 `led blink`、`uptime 5` 则正常。

**原因在符号来源**：`link.ld` 把 `strtoul` 指向 `0x40000458`，这个地址来自
`esp32c3.rom.newlib.ld`，是 **newlib 版**。newlib 的 `strtoul` 在出错路径会写
`errno`，而 `errno` 展开成 `_impure_ptr->_errno`——裸机下 `_impure_ptr` 是 NULL，
直接空指针跳转。

相比之下 `strcmp`/`strlen`/`memcpy` 来自 `esp32c3.rom.libc.ld`，不碰 errno，
所以一直正常。CLI 是第一个用到数字解析的地方，问题才暴露。

**修法**：自己写 `parse_num()`，不碰 ROM。顺带把非法输入变成明确报错
（`hexdump: bad address 'zzz'`）而不是静默返回 0。

> ⚠️ **可推广的教训**：`PROVIDE` 一个 ROM 地址前，先看它属于哪个 `.ld`。
> `rom.libc.ld` 和 `rom.newlib.ld` 混在同一张符号表里，但后者依赖 libc 全局状态
> （`_impure_ptr`、`errno`），裸机下会炸。

### 10. 自带的 `hexdump` 会堵死主循环

**现象**：`hexdump` 一执行就像死机——命令没反应，但 tick 还在涨。

**原因**：`hal.h` 的 `hexdump()` 走 `PUTCHAR` → ROM `uart_tx_one_char`，
实测约 **190ms/字节**，16 字节要 3 秒。期间主循环停摆、RX FIFO 溢出，
后续输入全部错乱。

**修法**：自写 `hexdump_mem()`，全部走 `uart_printf_to()`；
并且按 32 位字读，避免对 UART/GPIO 这类寄存器做字节访问。

> 💡 "看起来死机、但 tick 还在涨" —— 这个特征值记住：
> 说明 **CPU 没挂，是某段阻塞输出或忙等把主循环卡住了**。

### 11. 主频真相：开机只有 20MHz，不是 160MHz

**现象**：文档里一直写 160MHz，串口也打印 160MHz。

**发现过程**：加了 `hexdump` 后第一件事就是读时钟寄存器，结果：

```
SYSCLK_CONF (0x600C0058) = 0x000A8001
  bit11:10 soc_clk_sel   = 0  -> XTAL
  bit9:0   pre_div_cnt   = 1  -> 分频 2
  bit18:12 clk_xtal_freq = 40 -> 40MHz
=> 40 / 2 = 20 MHz
```

**所以之前的结论完全说反了**：ROM 报的 20MHz 是准的，硬编码的 160MHz 才是错的。

**切到 PLL 160MHz 只需改三个位**（BBPLL 模拟部分 ROM 已配好）：

| 寄存器 | 字段 | 值 |
|:--|:--|:--|
| `CPU_PER_CONF` +0x08 | `bit2 pll_freq_sel` | 1 = 480M PLL |
| `CPU_PER_CONF` +0x08 | `bit1:0 cpuperiod_sel` | 1 = 160M |
| `SYSCLK_CONF` +0x58 | `bit9:0 pre_div_cnt` | 0 = 不分频 |
| `SYSCLK_CONF` +0x58 | `bit11:10 soc_clk_sel` | 1 = PLL |

**为什么敢跳过 BBPLL 内部 I2C 配置**——先读状态再动手：
`RTC_CNTL_OPTIONS0(0x60008000) = 0x1C00A000`，`bit6/bit8/bit10`
（`BB_I2C_FORCE_PD`/`BBPLL_I2C_FORCE_PD`/`BBPLL_FORCE_PD`）全为 0 = 未掉电；
`CPU_PER_CONF` 的 `pll_freq_sel` 已是 1 = 480M。
**ROM 启动时已经把 480M PLL 拉起来了，只是 CPU 没切过去。**

**切频安全的三个前提（缺一不可）**：

1. `.text` 在 IRAM（`0x40380400`），不经 flash 取指 —— 改主频不会打断自己的取指
2. UART 的 `sclk_sel` 是 XTAL，与 PLL 无关 —— 串口不乱码
3. SYSTIMER 时钟源是 XTAL（`SYSTIMER_CLK_SRC_XTAL`）—— tick / `delay` 不失准

**验证方式：A/B 计时，不靠寄存器自证**

```
bench 2000000 iters: XTAL20=703377 us  PLL160=87554 us
bench: XTAL/PLL = 8.03 x
```

8.03 ≈ 8，正好对上 20MHz → 160MHz。

> ⚠️ **测量方法本身也踩了坑**：最初用"固定时间内数循环"，只得 **7.15**。
> 因为每轮循环都要读一次 SYSTIMER（APB 外设），这段是**固定的绝对耗时**，
> 在高频下占比变大，把比值稀释了。
> 改成"固定迭代次数、只测总耗时"才得到 8.03。
>
> **如果当时信了 7.15，就会去查一个根本不存在的硬件问题**（"PLL 只跑到 143MHz？"）。
> 测量方法错了，比不测更危险——它会给出一个看起来很合理的错数字。

### 12. trap 处理器：从「静默跳过」到「打印后停机」

**背景**：这一轮有两次"整机重启"（问题 4 的 `mcycleh`、问题 9 的 `strtoul`），
两次都只能靠猜。原因藏在一行代码里：

```c
} else {  // Exception
  CSR_WRITE(mepc, mepc + 4);   // 静默跳过，然后继续跑
}
```

异常被吃掉，程序带着错误状态继续执行，过一会儿在别处炸——**报障点与故障点分离**，
这是最难查的一类 bug。

**修法**：异常分支改为打印 `mcause` / `mepc` / `mtval` 后停机。

```
cause : 2 (illegal instruction)
mepc  : 0x40381BD6   <- 出错指令地址
mtval : 0x00000000   <- 出错地址/指令
halted.
```

再配一条 CLI 测试命令 `trap`（执行全零指令），随时验证处理器还活着。

#### 但实现上走了两条错路，都很典型

**错路一：手写 naked 汇编压 144 字节帧**

想拿 `x1..x31` 完整现场，手写了汇编入口保存全部通用寄存器。
结果是：抓异常**成功**，但现场恢复有误，把执行流带到了 `0x600C5200`
——那是外设寄存器地址，不是代码。每次启动十几毫秒后就崩。

写的时候还犯了另一个错：在保存 `x5`(t0) **之前**就用 `csrr t0, mscratch`，
把原始 `t0` 覆盖掉，导致现场第一项就是脏的。

> **教训**：手写栈帧的保存顺序、`sp` 还原、ABI 细节太容易错，
> 而且错了以后症状表现为"另一处崩溃"，误导性极强。
> 真需要全寄存器现场，**照抄 IDF 的 `vectors.S`**，不要从零编。

**错路二：`mtvec` 直指 `irq_handler`，整机 0 字节**

改用 `__attribute__((interrupt))` 后，把 `mtvec` 直接指向 `irq_handler`，
结果串口**一个字节都没有**。

查符号才找到根因：

```
irq_handler @ 0x4038068a     <- 末两位 0b10
```

**`mtvec` 的 bit1:0 不是地址的一部分，是 MODE 字段**（0=直接，1=向量）。
`rv32imc` 支持 2 字节压缩指令，函数常只按 2 字节对齐。
把这样一个地址写进 `mtvec`，等于把 MODE 写成了**保留值 2** —— 一开中断就挂，
而且没有任何报错，只表现为"静默"。

补 `aligned(4)` 后地址变成 `0x4038068c`，但整机仍未恢复（另有原因没定位到）。

> **教训**：给 CSR 写地址前，先确认 CSR 的低位有没有被挪作他用。
> `mtvec`、`stvec` 都是这样。判据很简单：拿符号地址算 `addr & 3`。

#### 最终方案：最小改动

保持原来的 `irqtab` 向量表（`aligned(256)`，`mtvec` 指向它，
内部 `j irq_handler` 跳转，**函数对齐就不再有要求**），
只把异常分支从静默跳过改成打印后停机。

**取舍**：只拿到 `mcause`/`mepc`/`mtval`，拿不到 `x1..x31`。
但这三个才是定位崩溃的关键三件套，且不引入任何汇编风险。
真需要全寄存器时再按 IDF 的写法补，那时是"加功能"，不是"修 bug"。

### 13. 短接后回显自激：90 行/秒刷爆日志

**现象**：GPIO4↔GPIO5 短接后，`duplex OK` 从每 2 秒一条暴涨到 **90 条/秒**，
间隔只有 11 ms，每次都是 `rx 128 bytes`。8 小时攒了 28624 行 / 1.9 MB。

**原因**：任务里有一行自动回显——

```c
int n = uart_read_bytes(U1_PORT, buf, sizeof(buf), ...);
if (n > 0) {
    uart_write_bytes(U1_PORT, buf, n);   /* 回显 */
    ...
}
```

短接后形成闭环：

```
收到 128 字节 → 回显发出去 → GPIO4 出 → 导线 → GPIO5 收回 → 再回显
     ↑                                                          │
     └──────────────────────────────────────────────────────────┘
```

PING 只是点火的那一下，之后它自己烧起来了，与发送周期无关。

**修法**：删掉回显，改成「单向发送 + 只观察接收」。

```c
int n = uart_read_bytes(U1_PORT, buf, sizeof(buf) - 1, pdMS_TO_TICKS(50));
if (n > 0) {
    buf[n] = '\0';
    /* 不回显！只判断、只打印 */
    if (strstr((char *)buf, "PING")) { ... } else { ... }
    vTaskDelay(pdMS_TO_TICKS(20));   /* 给回环链路恢复时间 */
}
```

| 指标 | 修复前 | 修复后 |
|:--|:--:|:--:|
| 日志速率 | 90 行/秒 | **1.02 行/秒** |
| 每次字节 | 128（滚雪球） | **9**（`PING N\r\n`） |
| duplex 间隔 | 11 ms | **约 2 秒** |

> ⚠️ **凡是「读到的数据又原样写回去」的代码，遇到物理回环就会自激。**
> 串口回显、CAN 网关转发、网络 echo 服务都一样。
> 做回环自测时，发送与接收必须是两条独立路径。

### 14. `strstr` 没有 NUL 结尾：未定义行为

**背景**：上面那行 `strstr((char *)buf, "PING")` 是隐患，回显的问题暴露后才查出来。

```c
uint8_t buf[128];
int n = uart_read_bytes(U1_PORT, buf, sizeof(buf), ...);  // 可能收满 128 字节
if (strstr((char *)buf, "PING")) { ... }                  // buf 里没有 NUL！
```

`uart_read_bytes` 返回的是**字节数**，不保证缓冲区末尾有 `\0`。
收满 128 字节时，`strstr` 会越过缓冲区边界继续往后扫，
一直读到内存里恰好出现 NUL 为止——**读取了不属于自己的内存**。

之前没炸是运气：后面的内存碰巧有零字节。

**修法**：缓冲区多留 1 字节，读完手动补 NUL。

```c
uint8_t buf[128 + 1];                                        /* +1 留给 NUL */
int n = uart_read_bytes(U1_PORT, buf, sizeof(buf) - 1, ...); /* 少读 1 字节 */
if (n > 0) {
    buf[n] = '\0';    /* 必须！否则 strstr 越界 */
    ...
}
```

**同时改进日志**：原来的 `%.*s` 遇到第一个 `0x00` 就截断，
收到二进制数据时表现为「空数据」，误判成"没收到"。

```c
/* 旧：ESP_LOGI(TAG, "rx %d bytes: [%.*s]", n, n, (char *)buf); */
/* 新： */
char hex[128];
hex_preview(hex, sizeof(hex), buf, n, 24);
ESP_LOGI(TAG, "rx %d bytes: %s", n, hex);
```

`hex_preview` 最多列 24 字节，超出只报剩余数量，且含 NUL 的样本也能完整打印：

```
selftest #12: 8 bytes  -> 00 00 00 00 00 00 00 00
selftest #15: 32 bytes -> A0 A1 A2 ... B6 B7 ... +8
```

> ⚠️ **两条通用教训**：
> 1. **凡是 `read` 返回「字节数」的 API，都不保证 NUL 结尾**——
>    串口、socket、文件读都一样。传给 `str*` 系列前必须自己补。
> 2. **用 `%.*s` 打印二进制数据是错误的**，第一个 `0x00` 就截断。
>    二进制一律走 hex。

### 关于"推翻自己"

这一轮最有价值的不是加了什么功能，而是**推翻了此前写进文档的错误结论**。

问题 4 里那个错误判断（"ROM 的 20MHz 是 stale"）之所以能存活很久，
是因为它自洽：tick 是准的（SYSTIMER 走 XTAL）、功能都正常、
串口也打印 160MHz（因为那是硬编码的字面量）。
**三个"正常"信号，全是同一个错误假设的下游产物，无法互相证伪。**

破局的唯一办法是引入一个**独立**的观测手段：直接读 `SYSCLK_CONF`。
这和问题 2 的解法是同一个思路——不要问"我算得对不对"，
要去问"硬件现在到底是什么状态"。
