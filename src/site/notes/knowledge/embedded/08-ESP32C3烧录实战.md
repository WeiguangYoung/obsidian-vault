# 🔧 ESP32-C3 烧录实战

> ¥12 的 ESP32-C3 核心板。

---

## 一、这块板是什么

| 项目 | 值 | 来源 |
|:--|:--|:--|
| 芯片 | ESP32-C3 (QFN32) rev **v0.4** | esptool |
| 封装 | **32 pin**（每侧 16） | 实物 |
| Flash | **4 MB**（厂商 `c2` / 型号 `2016`） | esptool |
| 晶振 | 40 MHz | esptool |
| MAC | `14:63:93:f9:12:80` | esptool |
| 串口桥 | **CH343** `1a86:55d3` → `/dev/ttyACM0` | `lsusb` |
| 接口 | Type-C | 实物 |
| 按键 | BOOT + RST | 实物 |
| 板面丝印 | `ESP32C3` / `V1.0.0` / `LuatOS` | 实物 |
| 原生 JTAG | ❌ 无（Type-C 走 CH343） | 实测 |
| **flash 频率** | **必须 40MHz DIO** | 实测 + 官方佐证 |

### 复现命令

```bash
lsusb | grep -iE "1a86|303a|10c4"          # 串口桥型号
ls /dev/tty{ACM,USB}*
python3 esptool.py --port /dev/ttyACM0 chip_id    # 芯片 + MAC
python3 esptool.py --port /dev/ttyACM0 flash_id   # Flash 厂商与容量
```

`chip_id` 在 C3 上会提示「has no Chip ID」并转而读 MAC —— 正常，不是失败。

### 没有原生 USB-JTAG

Type-C 接 CH343，CH343 连 UART0（`GPIO20/21`）。与芯片内置 USB-JTAG（`GPIO18/19`）互斥，所以只能 `printf`，不能断点调试。

> 两条路的设备节点都可能叫 `/dev/ttyACM0`，必须看 VID 区分：`303a:1001` 是乐鑫原生，`1a86:55d3` 是 CH343。

## 二、引脚表

⚠️ **`P1`/`P17` 在 USB 接口一端（下），`P16`/`P32` 在另一端（上）。** 容易数反。

左排 P1–P16：

| # | 符号 | # | 符号 |
|:--:|:--|:--:|:--|
| 1 | GND | 9 | IO11 ⚠️ |
| 2 | 5V | 10 | IO07 |
| 3 | BOOT (IO09) | 11 | IO06 |
| 4 | IO08 | 12 | IO10 |
| 5 | IO04 | 13 | IO03 |
| 6 | IO05 | 14 | IO02 |
| 7 | 3.3V | 15 | 3.3V |
| 8 | GND | 16 | GND |

右排 P17–P32：

| # | 符号 | # | 符号 |
|:--:|:--|:--:|:--|
| 17 | 5V | 25 | TX0 ⚠️ |
| 18 | PWR ⚠️ | 26 | GND |
| 19 | GND | 27 | IO19 |
| 20 | 3.3V | 28 | IO18 |
| 21 | EN (RESET) | 29 | IO12 ⚠️ |
| 22 | NC | 30 | IO01 |
| 23 | IO13 ⚠️ | 31 | IO00 |
| 24 | RX0 ⚠️ | 32 | GND |

### 三处必须注意

**PWR (P18) 不是 PWM** —— 芯片 3.3V 供电使能，高有效，可悬空。拉低等于断电。

**三个脚不能当普通 IO**：

| 脚 | 实际功能 | 风险 |
|:--|:--|:--|
| `IO11` (P9) | `VDD_SPI`，Flash 供电 | 输出低会断 Flash 供电 → 死机 |
| `IO12` (P29) | `SPIHD` | 已占用 |
| `IO13` (P23) | `SPIWP` | 已占用 |

**其他约束**：`IO18/19` 用完失去原生 USB；`IO02/08/09` 是 strapping；`IO20/21` 占用即抢走日志口。

### P24/P25 引脚定义

| 位号 | 丝印 |
|:--|:--|
| P24 | `TX0` |
| P25 | `RX0` |

⚠️ 丝印只说明「这根针是 TX0」，**未说明对应 GPIO20 还是 GPIO21**，焊盘到芯片引脚的映射仍需实测。要接串口，稳妥做法是换别的脚走 GPIO Matrix 重映射避开这对针。

## 三、烧录配方（ESP-IDF）

### 关键配置

写入工程根目录的 `sdkconfig.defaults`：

```ini
CONFIG_IDF_TARGET="esp32c3"
CONFIG_ESPTOOLPY_FLASHMODE_DIO=y
CONFIG_ESPTOOLPY_FLASHFREQ_40M=y
CONFIG_ESPTOOLPY_FLASHSIZE_4MB=y
```

然后：

```bash
idf.py set-target esp32c3     # 首次
idf.py build
idf.py -p /dev/ttyACM0 flash monitor
```

键名均与乐鑫官方 ESP-AT 包（`ESP32-C3-MINI-1-V2.4.2.0/sdkconfig`）逐项对齐，已核对。

菜单里对应的路径：`Serial flasher config` → `Flash SPI mode` / `Flash SPI speed` / `Flash size`。

### ⚠️ flash 必须 40MHz DIO

默认 80MHz 会启动死循环：烧录显示 `SUCCESS`，串口却刷

```
E (26) boot: load partition table error!
E (25) flash_parts: partition 0 invalid magic number 0xffed
```

**官方佐证**：乐鑫 ESP-AT 固件包（`ESP32-C3-MINI-1-V2.4.2.0`）的 `download.config` 写着

```
--flash_mode dio --flash_freq 40m --flash_size 4MB
```

它的 `sdkconfig` 也是同一套（`CONFIG_ESPTOOLPY_FLASHMODE_DIO=y` / `CONFIG_ESPTOOLPY_FLASHFREQ_40M=y`）。原厂出货预烧就是 DIO + 40MHz，不必怀疑。

⚠️ 同包里的 `micropython-1.19.1-esp32c3-2mflash-firmware.bin` 是 **2MB / 80MHz** 配置（镜像头 `e9 03 02 1f`），刷到 4MB 板上只能用一半，且会触发上面那个死循环。

### 端口名对照

| 方案 | 节点 | VID:PID |
|:--|:--|:--|
| 内置 USB-JTAG | `/dev/ttyACM0` | `303a:1001` |
| CH343（本板） | `/dev/ttyACM0` | `1a86:55d3` |
| CH340 | `/dev/ttyUSB0` | `1a86:7523` |
| CP2102 | `/dev/ttyUSB0` | `10c4:ea60` |

## 四、裸机版本（不用 ESP-IDF）

同一块板还跑过一版**纯裸机**固件：没有 bootloader、没有分区表，向量表和 `main()` 全在自己手里，镜像直接烧到 `0x0`。

源码来自 [bare-metal-programming-guide](https://github.com/cpq/bare-metal-programming-guide) 的 [`templates/blinky/esp32-c3`](https://github.com/cpq/bare-metal-programming-guide/tree/master/templates/blinky/esp32-c3)。

> ⚠️ **别找错目录**：那个仓库的 `steps/` 和 `my-steps/` 全是 STM32（`-mcpu=cortex-m4`、`st-flash`）；只有 `templates/blinky/` 下按芯片分目录，`esp32-c3` 是唯一的 RISC-V 版本。

工程已并进实战仓的 `bare-metal/`：

| 文件 | 作用 |
|:--|:--|
| `startup.c` | 向量表、`Reset_Handler`、中断分发、`sbrk` |
| `main.c` | 点灯主循环：500ms 翻转 LED，1s 打一次 tick |
| `hal.h` | C3 寄存器定义与 GPIO/UART 封装 |
| `link.ld` | IRAM `0x40380400` / DRAM `0x3fc88000` |

### 编译

```bash
cd bare-metal
make            # firmware.elf + firmware.bin，末尾自动校验镜像
```

工具链直接复用 PlatformIO 已装的 riscv 交叉编译器，**不需要 Docker**（原模板 Makefile 走 `docker run mdashnet/riscv`）：

```bash
GCC=~/.platformio/packages/toolchain-riscv32-esp/bin/riscv32-esp-elf-gcc
ESPTOOL=~/.platformio/packages/tool-esptool/esptool
```

### ⚠️ `-march` 必须带 `_zicsr`

```bash
-march=rv32imc_zicsr -mabi=ilp32
```

新版 GCC（≥12）不再把 Zicsr 隐含在 `rv32i` 里。少了 `_zicsr`，`startup.c` 里所有 `csrr` / `csrw` 全部报错：

```
startup.c:30: Error: unrecognized opcode `csrr a5,mcause', extension `zicsr' required
startup.c:40: Error: unrecognized opcode `csrw mepc,a5', extension `zicsr' required
```

本机是 GCC 15.2.0，模板写作时（GCC 10 左右）不会触发这个问题。

### 烧录

```bash
make flash                          # 默认 /dev/ttyACM0
make flash PORT=/dev/ttyUSB0        # 换串口
make erase                          # 全片擦除
```

等价手工命令：

```bash
esptool --chip esp32c3 elf2image --flash-mode dio --flash-freq 40m --flash-size 4MB \
  -o firmware.bin firmware.elf
esptool --chip esp32c3 --port /dev/ttyACM0 --baud 115200 write-flash 0x0 firmware.bin
```

`--flash-mode dio --flash-freq 40m` 同样不能省，理由见上一节。

### 实测结果

```
Chip type:     ESP32-C3 (QFN32) revision v0.4
Features:      Wi-Fi, BT 5 (LE), Single Core, 160MHz
Uploading stub flasher...
Wrote 1712 bytes at 0x00000000
Hash of data verified.
```

镜像 1712 字节，两个段：

| 段 | 长度 | 加载地址 | 类型 |
|:--:|:--|:--|:--|
| 0 | `0xe0` | `0x3fc88000` | DRAM |
| 1 | `0x580` | `0x40380400` | IRAM |

烧完从板子读回 `0x0` 起始的 4096 字节，前 1712 字节的 SHA-256 与本地 `firmware.bin` 完全一致（`2c0d2c38…5b83`），确认板内跑的就是这份源码。

### 两个已知限制

**1. `uart_init()` 是空桩，串口不会有任何输出。**

`hal.h` 里上游只留了 TODO：

```c
static inline bool uart_init(uint32_t uart, int baud) {
  (void) uart, (void) baud;
  return false;
}
```

所以 `printf("tick: %5lu, CPU %lu MHz\n", ...)` 不会打印到任何地方。要日志得起手补：

- `UART_CLKDIV` 按 `APB_CLK / baud` 算分频
- `UART_CONF0` 配数据位 / 停止位 / 校验
- 经 `IO_MUX` 把 `GPIO20/21` 切到 UART 功能

**2. LED 是外接的。**

模板默认 `LED_PIN = 2`，README 原文写「Attach LED to pin 2」，即自己拿一颗 LED 串电阻接到 **GPIO2**。板载 LED 的 GPIO 仍未实测（见下一节）。

## 五、MAC 地址

ESP-IDF 读出来和 esptool 一致，无需转换：

```c
#include "esp_mac.h"
uint8_t mac[6];
esp_read_mac(mac, ESP_MAC_WIFI_STA);   // 14:63:93:f9:12:80，正常字节序
```

> 只有 Arduino 的 `ESP.getEfuseMac()` 会给出反序值（`80:12:F9:93:63:14`）——它把 efuse 里的 6 字节当小端 uint64 读。用 IDF 就不存在这个问题。

若在 Arduino 下做事，需要手动翻：

```cpp
uint64_t m = ESP.getEfuseMac();
uint8_t b[6];
for (int i = 0; i < 6; i++) b[i] = (m >> (8 * (5 - i))) & 0xFF;
```
