## 第一部分 · 版本与发布规范（原 09）

> 面向 CI/CD & Build Engineer 岗位的**版本管理体系**落地实录。
> 三份目标 JD 里「版本号规范 / 分支策略 / Tag 规范 / Release·Hotfix·灰度·回滚」全是硬要求，
> 但「写一份规范文档」不算落地 —— 本文的主线是**把规范变成流水线里跑得起来的门禁和流程**。
>
> 环境：Jenkins Multibranch + Shared Library `ci-lib`（v0.8.0）+ Harbor + 实验台 `UDS_S32K144_Bootloader`（纯 C）。

---

#### 一、为什么版本管理是「最容易被跳过的硬要求」

大多数人能说清「我们用 Git Flow，版本号 SemVer」，但一问就露馅：

| 常见答法 | 面试官追问 | 暴露的问题 |
|:---|:---|:---|
| 我们打 tag 发布 | tag 打错格式谁拦？打了能反悔吗？ | **没有门禁，规范只靠自觉** |
| 版本号按语义化 | `v1.2.3-rc.1` 和 `1.2.3` 谁大？ | SemVer 优先级规则没吃透 |
| 出了问题做 hotfix | hotfix 从哪拉？合回哪几条分支？ | **流程没有闭环，漏合是常态** |
| 能灰度发布 | 灰度批次怎么划？回滚依据什么指标？ | 只有概念，没有机制 |

**核心认知**：版本管理的产物不是一份文档，而是三类**可执行的约束**：

```
① 格式门禁    —— 版本号/tag 不合法 → 流水线直接失败
② 流程门禁    —— 分支策略决定谁能从哪拉到哪，CI 校验来源分支
③ 可追溯性    —— 每个制品都能反查 commit / 构建号 / 发布批次
```

#### 二、版本号规范（SemVer 2.0 落地细则）

##### 2.1 基本格式

```
MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]
  1  .  2  .  3   -rc.1        +20261101.3
```

| 位 | 何时递增 | 本环境示例 |
|:---|:---|:---|
| **MAJOR** | 不兼容的 API / 协议变更 | UDS 服务号或诊断流程不兼容改造 |
| **MINOR** | 向后兼容的新功能 | 新增 0x31 例程、新增 Flash 驱动 |
| **PATCH** | 向后兼容的缺陷修复 | 修 bootloader 跳转时序 |
| **PRERELEASE** | 预发布：`-alpha.1` `-beta.2` `-rc.1` | 实验室验证版本 |
| **BUILD** | 构建元数据，**不参与优先级比较** | 构建号 / 日期 |

##### 2.2 优先级比较（易错点）

```
1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-alpha.beta < 1.0.0-beta
        < 1.0.0-beta.2 < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0
```

三条硬规则：

1. **有预发布后缀 < 无后缀**（`1.0.0-rc.1 < 1.0.0`）
2. **数字段按数值比，不是字典序**（`beta.11 > beta.2`）
3. **`+build` 完全不参与比较**（`1.0.0+a` == `1.0.0+b`）

> 团队常见坑：把 `1.0.0-rc.10` 当成比 `1.0.0-rc.9` 小（字典序陷阱）。

##### 2.3 0.x.y 阶段怎么管

- `0.MINOR.PATCH` 表示「API 未稳定」，**任何 MINOR 都可能有破坏性变更**
- 一旦对外承诺接口（如 bootloader 与 APP 的刷写协议），立刻升 `1.0.0` 并锁死
- 不建议长期停在 0.x —— **不升 1.0 意味着不敢承诺兼容**

##### 2.4 本环境的实际取版本策略

嵌入式 C 项目和 JVM 项目取版本方式不同：

| 项目类型 | 版本来源 | 说明 |
|:---|:---|:---|
| C / 嵌入式 | `git describe --tags --always --dirty` | 无 tag 时退化为短 SHA，**永远有值** |
| JVM（gradle） | `gradle.properties` 的 `version` | 自动去掉 `-SNAPSHOT` 后缀 |
| 强制指定 | `versionOverride` | 发版时由 Release 流水线显式传 |

版本信息最终注入到两个地方：

1. **构建显示名**：`#42 [main] v1.2.0` —— 在 Jenkins 列表页一眼看到版本
2. **版本头文件**（C 项目）：`Sources/ci_version.h`

```c
#ifndef CI_VERSION_H
#define CI_VERSION_H
#define CI_VERSION      "v1.2.0"
#define CI_BUILD_NUMBER "42"
#define CI_BRANCH       "main"
#define CI_BUILD_DATE   "20261101-043000"
#define CI_COMMIT       "f8b5faaae1d3..."
#endif
```

> **价值**：固件跑起来后，串口/RTT 打印 `CI_VERSION` 就能反查是哪次构建、哪个 commit，
> 不用再靠「烧的是哪个 hex」这种口头确认。这是**可追溯性最便宜的一环**。

#### 三、分支策略（Git Flow vs Trunk-Based）

##### 3.1 两种模型对比

| 维度 | Git Flow | Trunk-Based |
|:---|:---|:---|
| 长期分支 | `main` + `develop` | 只有 `main` |
| 短期分支 | `feature/*` `release/*` `hotfix/*` | `feature/*`（存活 ≤ 2 天） |
| 发布方式 | release 分支冻结 → 打 tag | 直接在 main 打 tag |
| 合入频率 | 低（按特性） | 高（每天多次） |
| 适合场景 | **版本驱动**：车载、嵌入式、交付型 | **持续部署**：SaaS、Web |
| 主要代价 | 分支多、合并冲突多、长期分叉 | 需要强自动化测试 + 特性开关 |

##### 3.2 为什么本环境选 Git Flow（但不照搬）

嵌入式交付型项目（S32K144 bootloader、车规 ECU）的特性：

- 有明确「版本节点」，客户按版本验收，不能随时上 main
- 一次 ta­g 对应一批出货固件，**必须有冻结期**
- 灰度能力弱（OTA 节奏慢），回滚靠重新刷写

所以主干仍是 Git Flow，但砍掉两个低效环节：

| 标准 Git Flow | 本环境取舍 | 理由 |
|:---|:---|:---|
| `develop` 作为长期集成分支 | **保留** | 多特性并行时确实需要缓冲区 |
| `release/*` 分支冻结期长 | **缩短到 1–3 天** | 冻结越久，release 分支与 develop 偏离越大 |
| `hotfix/*` 从 main 拉 | **保留，且必须双合** | 只合 main 不合 develop → 下个版本缺陷复活 |

##### 3.3 分支模型图

```
        ┌── feature/UDS-0x31 ──┐
        │                      ▼
main ───┼──────────────────────●────────────●────────●─────►
        │                    develop      release/  tag v1.2.0
        │                      │          v1.2     │
        │                      └──────────┬────────┘
        │                                 │ (冻结 1-3 天)
        │                                 ▼
        └──────── hotfix/v1.2.1 ◄─── tag v1.2.0
                     │
                     ├──► main   (必须)
                     └──► develop(必须)
```

##### 3.4 分支命名门禁

规范写了没人执行 = 没写。所以在 CI 里加一道**分支命名校验**：

```groovy
// 允许的分支名：main / develop / feature/<slug> / release/<semver> / hotfix/<semver>
def allowed = ~/^(main|develop|feature\/[a-z0-9._-]+|release\/\d+\.\d+(\.\d+)?(-(alpha|beta|rc)\.\d+)?|hotfix\/\d+\.\d+\.\d+)$/
if (!(env.BRANCH_NAME ==~ allowed)) {
    error "分支名不合规：${env.BRANCH_NAME}（规范见版本与发布规范 §3.4）"
}
```

> 这道门禁的价值：把「规范」从文档搬进了流水线，**新人第一次提 PR 就会被拦下并看到规则**。

#### 四、Tag 规范

##### 4.1 Tag 命名

| 类型 | 格式 | 示例 | 说明 |
|:---|:---|:---|:---|
| 正式发布 | `v<MAJOR>.<MINOR>.<PATCH>` | `v1.2.0` | **唯一进入制品的 tag** |
| 预发布 | `v<SEMVER>-<pre>.<n>` | `v1.3.0-rc.1` | 可覆盖（仅实验室） |
| 内部基线 | `baseline-<日期>` | `baseline-20261101` | 不发布，仅供比对 |

**统一 `v` 前缀**：`1.2.0` 和 `v1.2.0` 混用是最常见的版本地狱来源，必须二选一并写进门禁。

##### 4.2 Tag 三条铁律

```
① 正式 tag 一律 annotated，不用 lightweight
   git tag -a v1.2.0 -m "release v1.2.0: 新增 0x31 例程"
   → 保留打 tag 的人、时间、说明；lightweight tag 只有 commit 指针，没有审计信息

② 正式 tag 一旦推送，永不删除、永不移动
   挂 pre-receive hook 或 CI 校验：tag commit 必须等于 main 当前 HEAD

③ tag 与制品强绑定
   镜像 / hex / jar 的元数据里必须能反查 tag → 构建时把 tag 写进制品
```

##### 4.3 Tag 格式门禁

```groovy
stage('Validate Tag') {
    steps {
        script {
            def tag = env.TAG_NAME
            if (!(tag ==~ /^v\d+\.\d+\.\d+(-(alpha|beta|rc)\.\d+)?$/)) {
                error "Tag 格式不合规：${tag}（应为 v1.2.3 或 v1.3.0-rc.1）"
            }
            // annotated 校验
            def type = sh(script: "git cat-file -t ${tag}", returnStdout: true).trim()
            if (type != 'tag') error "Tag ${tag} 是 lightweight tag，正式发布必须用 -a 创建"
        }
    }
}
```

#### 五、发布流程（Release / Hotfix / 灰度 / 回滚）

##### 5.1 Release 流程（完整状态机）

```
① 从 develop 拉 release/vX.Y.Z
② 冻结：只允许 bugfix，禁止新特性
   （CI 校验：release 分支上的 PR 必须带 `fix` label）
③ 全量验证：单测 + 覆盖率 + 双轨门禁（Cppcheck + MISRA）+ 仿真/冒烟
④ 打 tag vX.Y.Z（annotated）→ 触发 Release 流水线
⑤ Release 流水线：构建 → 归档制品 → 推送 Harbor（tag 不可变）→ 生成 release notes
⑥ 合回 main + develop（必须，否则下版本丢修复）
⑦ 删除 release 分支
```

##### 5.2 Hotfix 流程

```
① 从 main 拉 hotfix/vX.Y.Z+1（PATCH +1）
② 只修一个问题，最小改动
③ 验证（缩短版：单测 + 关键冒烟，不做全量仿真）
④ 打 tag vX.Y.Z+1 → Release 流水线
⑤ 合回 main + develop（双合，缺一不可）
```

> **最常见的翻车点**：hotfix 只合了 main，忘了合 develop。下个版本 release 时修复「凭空消失」，
> 只能靠 regressing test 事后发现。把它做成 CI 检查（hotfix 分支合入 main 后自动开 develop 的 PR）能根治。

##### 5.3 灰度发布

嵌入式场景的「灰度」不是流量比例，而是**批次投放**：

| 批次 | 范围 | 放量条件 | 观测窗口 |
|:---|:---|:---|:---|
| 批次 1 | 内部测试机（1–3 台） | 无严重问题 | 24h |
| 批次 2 | 内部车辆 / 小批量试点（~5%） | 0 严重、严重告警率不升 | 3 天 |
| 批次 3 | 全量 | — | — |

放量依据必须是**可量化指标**，不能拍脑袋：

- 启动成功率、CAN 通信错误率、看门狗复位次数
- OTA 升级成功率、升级耗时 P95

> 注入版本号 + 批次号的意义就在这里：出了问题能立刻圈定「哪一批、哪个版本」。

##### 5.4 回滚

| 场景 | 回滚方式 | 前提 |
|:---|:---|:---|
| 镜像问题（云端服务） | 切回上一个不可变 tag（`v1.1.9`） | 镜像 tag 不可变 + 历史镜像未被 GC |
| 固件问题（车端） | 重新刷写上版本 hex / A、B 分区回退 | 保留上一版本制品 + bootloader 支持回退 |
| 配置问题 | 回滚配置（ConfigMap 版本化） | 配置也能版本化 |

**回滚能力的三条前置条件**（缺一不可）：

```
① 上一版本制品还留着 —— 靠 Harbor 保留策略「release tag 永不自动删」
② 版本可精确定位 —— 靠 tag / CI_VERSION 头文件
③ 回滚流程自动化 —— 靠一条 rollback 流水线，而不是人手敲命令
```

##### 5.5 发布节奏建议

| 版本类型 | 节奏 | 冻结期 |
|:---|:---|:---|
| MAJOR | 按里程碑 | 1 周 |
| MINOR | 2–4 周 | 1–3 天 |
| PATCH / Hotfix | 按需，紧急可当天 | 数小时（仅最小验证） |

#### 六、把规范变成流水线（核心实现）

##### 6.1 整体设计

```
Push/PR      → ciPipeline     ：编译 + 单测 + 覆盖率 + 双轨门禁（现有）
Push tag v*  → releasePipeline：tag 校验 + 全量验证 + 制品归档 + Harbor 推送 + release notes
手动触发      → rollbackPipeline：指定目标版本 → 拉回制品 → 回滚部署
```

三条流水线共享同一套 Shared Library，规范和门禁都收敛在库里 —— **改一处，所有仓库生效**。

##### 6.2 `releasePipeline` 步骤骨架

```groovy
/**
 * releasePipeline — 正式发布流水线：tag 校验 → 验证 → 制品 → 归档 → 通知
 *
 * 用法（Jenkinsfile）：
 *   @Library('ci-lib') _
 *   releasePipeline(name: 'UDS_S32K144_Bootloader', stack: 'c-embedded')
 */
def call(Map cfg = [:]) {
    def v   = versioning(versionOverride: env.TAG_NAME)
    def tag = env.TAG_NAME

    // ① Tag 格式 + annotated 校验
    if (!(tag ==~ /^v\d+\.\d+\.\d+(-(alpha|beta|rc)\.\d+)?$/)) {
        error "Tag 格式不合规：${tag}"
    }
    if (sh(script: "git cat-file -t ${tag}", returnStdout: true).trim() != 'tag') {
        error "Tag ${tag} 必须是 annotated tag（git tag -a）"
    }

    // ② Tag 必须指向 main 的 HEAD（防「从错误分支打 tag」）
    def head = sh(script: 'git rev-parse HEAD', returnStdout: true).trim()
    def tagCommit = sh(script: "git rev-list -n 1 ${tag}", returnStdout: true).trim()
    if (head != tagCommit) {
        error "Tag ${tag} 指向 ${tagCommit.take(8)}，与当前构建 ${head.take(8)} 不一致"
    }

    def V = v.version.replaceFirst(/^v/, '')

    // ③ 全量验证（复用现有 ciPipeline 能力）
    //    单测 + 覆盖率 + Cppcheck/MISRA 双轨门禁，任一门禁失败即中断

    // ④ 制品归档（build-info + checksums）
    writeFile file: 'build-info.txt', text: """\
Build version: ${env.TAG_NAME}
Build number:  ${env.BUILD_NUMBER}
Commit:        ${v.commit}
Build date:    ${v.date}
"""
    sh 'find . -name "*.hex" -o -name "*.elf" | xargs -r sha256sum > checksums.sha256'

    // ⑤ 推送 Harbor（镜像类项目；二进制类项目跳过）
    //    acrImage(repo: "${REPO}/${env.JOB_NAME}", tag: "${V}", push: true)

    // ⑥ release notes：从上一个 tag 到本 tag 的 commit 列表
    def prev = sh(script: "git describe --tags --abbrev=0 ${tag}^ 2>/dev/null || echo ''",
                  returnStdout: true).trim()
    def range = prev ? "${prev}..${tag}" : tag
    sh "git log --pretty=format:'- %s (%h)' ${range} > release-notes.md"

    echo "releasePipeline: ${env.TAG_NAME} 发布完成（commit ${v.commit.take(8)}）"
}
```

##### 6.3 关键设计点

| 设计点 | 做法 | 解决的问题 |
|:---|:---|:---|
| **幂等性** | 同一 tag 重跑不产生新版本号 | 重跑不污染版本线 |
| **快速失败** | tag 校验放在最前面，不同步验证 | 省 30+ 分钟冤枉构建 |
| **门禁复用** | 直接调用现有 `codeCheck` / `coverage` | 发布和日常 CI 用同一套标准 |
| **可追溯** | `build-info.txt` + `checksums.sha256` + 版本头文件 | 制品 ↔ commit ↔ 构建 三方反查 |
| **通知回写** | Gitea/GitHub 上生成 Release 页面 | 发布对全员可见，不用口头同步 |

##### 6.4 Harbor 侧配套（制品生命周期）

规范要求「release 永不自动删」—— 这必须落到 Harbor 策略，否则 GC 一次就没了：

| 策略 | 配置 | 目的 |
|:---|:---|:---|
| **Tag 不可变** | 全仓库全 tag 禁覆盖 | 防「同 tag 不同内容」 |
| **保留策略** | `latestPushedK=2` + 清理 untagged（1 天） | 控制空间，但会影响 release tag |
| **例外处理** | release tag 用单独 repo / 单独保留规则 `harbor: true` | **保证回滚有件可用** |

> 血泪提醒：不可变规则被拦时，报错一定是 `configured as immutable`；
> 如果看到 `unauthorized ... push`，那是**登录 token 过期**的假阳性，别被自己骗了。

##### 6.5 实机验证记录（2026-11-04）

> 把 `releasePipeline` 真正接到 Multibranch 仓库上跑一遍，验证门禁是否真的拦得住。

###### 实验环境

| 项 | 值 |
|:---|:---|
| 仓库 | `UDS_S32K144_Bootloader`（Gitea，Multibranch + TagDiscoveryTrait 已启用） |
| 流水线 | Jenkinsfile 310 行，已 `@Library('ci-lib') _` |
| 共享库 | jenkins-shared-library v0.10.0（`vars/releasePipeline.groovy` 210 行） |
| 构建节点 | k3s 动态 Pod（`k8s-linux`，固定 lenovo 节点） |
| Jenkins 宿主 | 2C2G，可用内存约 280Mi |

###### 接入方式

在 Jenkinsfile 的 `stages` 最前面插入：

```groovy
stage('Release') {
    // releasePipeline 内部要跑 git 命令（cat-file / rev-list），必须有 agent
    agent { label 'k8s-linux' }
    when {
        beforeAgent true
        expression { return env.TAG_NAME != null && env.TAG_NAME.startsWith('v') }
    }
    steps {
        releasePipeline(
            name:             'UDS_S32K144_Bootloader',
            artifactGlobs:    ['artifacts/**/*.hex', 'artifacts/**/*.elf', 'artifacts/**/*.map'],
            strictBranch:     'main',
            prereleasePolicy: 'block'
        )
    }
}
```

**第一个坑**：最初的写法没给 `agent`，构建直接报

```
ERROR: Attempted to execute a step that requires a node context 
       while 'agent none' was specified.
```

`releasePipeline` 里有 `sh(script: "git cat-file -t ...")`，而顶层是 `agent none`，必须在 stage 上显式指定 agent。

###### 验证结果一：门禁确实会拦（这是最有价值的一次）

把 tag 打在**非 main 分支**（`release-test`）上，`strictBranch: 'main'` 应当拒绝：

```
门禁① Tag 格式 .......... PASS  (v1.3.0 匹配 semver 正则)
门禁② annotated tag ..... PASS  (git cat-file -t 返回 tag)
门禁③ tag == HEAD ....... PASS  (两者指向 f76a5b2)
门禁④ 正式 tag 在 main .. FAIL  ← 包含该 commit 的远端分支只有 gitea/release-test
```

**门禁④ 正确拦截了「从错误分支打正式 tag」**，这正是发布规范要防的头号事故。

###### 验证结果二：合到 main 后，Jenkins 端到端被环境卡住

把改动合进 main、在 main 的 HEAD 上重打 `v1.3.0`，tag 被 Multibranch 正确发现（生成 `v1.3.0` job），触发构建后：

```
releasePipeline: Tag v1.3.0 格式校验通过（semver=1.3.0 prerelease=false）   ← 门禁① 通过
+ git cat-file -t v1.3.0                                                   ← 门禁② 的 git 命令已执行
k8s-linux-rkrv1 seems to be removed or offline
  (java.io.IOException: cannot find current thread in CpsStepContext[18:sh])
```

连续 4 次构建，**全部卡在同一个位置**：门禁②的 `sh` 步骤把结果回传给 Controller 时，动态 Pod 掉线，CPS 线程断链，整个构建判 FAILURE。

**根因**：

| 项 | 值 |
|:---|:---|
| jenkins-host 总内存 | 1.9G |
| 已用 | 1.68G |
| **可用** | **282Mi** |
| Jenkins 容器 | 660Mi / 1G 限额 |

Jenkins Controller 在内存里维护 CPS 状态机，每挂一个 k8s 动态 agent 就要保存调用栈快照。内存不足时，`sh` 返回的瞬间线程就找不回来。**这不是配置错，也不是代码错，是 2C2G 小机扛不住这套架构。**

###### 验证结果三：本地等价模拟（补齐逻辑验证）

在宿主机上用等价命令逐条跑门禁逻辑：

```bash
TAG=v1.3.0

# 门禁① Tag 格式
echo "$TAG" | grep -qE '^v([0-9]+)\.([0-9]+)\.([0-9]+)(-(alpha|beta|rc)\.[0-9]+)?

四道门禁逻辑**全部验证正确**（门禁④ 在错误分支上如期 FAIL）。

###### 结论

| 验证维度 | 状态 |
|:---|:---|
| `releasePipeline` 门禁逻辑 | ✅ 全部正确（本地逐条验证 + Jenkins 端到端拦截验证） |
| Jenkinsfile 接入方式 | ✅ 已跑通（Release stage + agent 配置） |
| Jenkins 端到端全流程 | ❌ 受 jenkins-host 内存限制，CPS 线程断链 |
| 产物三件套（build-info / checksums / release-notes） | ⬜ 未产出（流程未走到该阶段） |

###### 遗留问题

| # | 问题 | 影响 | 建议解法 |
|:-:|:---|:---|:---|
| 1 | Jenkins Controller 内存不足（可用 282Mi） | 动态 agent 的 `sh` 步骤返回时线程断链 | **升配**（至少 4C/4G）或减少 OpenClaw/其他进程占用 |
| 2 | 无替代常驻 agent | 无法绕开动态 Pod | 加一台常驻 `docker-linux` 或 shell agent 专跑 release |
| 3 | 产物三件套未验证 | 可追溯性链路未闭环 | 解决 #1 后重跑 tag 构建 |
| 4 | 门禁⑤（预发布阻断）未验证 | `-rc` / `-beta` tag 的阻断逻辑未实测 | 推一个 `v1.3.1-rc.1` 验证 |

> **一条经验**：能力和环境要分开记录。门禁逻辑对不对，用本地等价模拟就能证明；能不能跑通，取决于资源。混在一起会让人误以为「代码有问题」，实际是「机器不够」。

## 第二部分 · GitLab CI 流水线（原 10）

> 目标：把已有 Jenkins 流水线（hello-jenkins / S32K144 Bootloader）等价改造到 GitLab CI，跑通全链路，并为「标准化流水线模板沉淀」打底。
> 本文写通用做法与认知，不含真实仓库地址 / Token / 内网 IP（脱敏见文末约定）。

#### 一、为什么补 GitLab CI

| 维度 | Jenkins | GitLab CI |
|:---|:---|:---|
| 流水线定义 | Jenkinsfile（Groovy） | `.gitlab-ci.yml`（YAML） |
| 模板复用 | Shared Library（Groovy 类库） | `include` + `extends` + `!reference` 分层 |
| 并行 / 依赖 | 同 stage 并行；跨 stage 依赖需插件 | `needs:` **原生 DAG**，可跨 stage 任意依赖 |
| 测试报告 | 插件（JUnit / 记录 Issues） | `reports: junit:` **原生** |
| 覆盖率 | 插件解析 | `coverage:` 正则从日志提取 |
| 执行环境 | 常驻 agent / 动态 pod | Runner + executor（docker / shell / **kubernetes**） |
| MR 门禁 | 插件 + PR 回写 | 内置 Pipeline 必须成功才能合并 + `CI_MERGE_REQUEST_*` 变量 |
| 增量基线 | 需 `discoverReferenceBuild` 找参考构建 | `CI_MERGE_REQUEST_DIFF_BASE_SHA` 直接给 |

结论：**YAML 扁平、DAG 原生、MR 变量现成**，是 Jenkins 之外最值得掌握的第二个 CI 平台；多家 JD 把它列为硬要求。

#### 二、整体架构

```
GitLab（jihulab.com，SaaS 托管）
   │  git push / MR
   ▼
Runner Manager Pod（常驻，namespace gitlab-runner）
   │  executor = kubernetes
   ▼
临时 Job Pod（每个 job 一个，用完即销毁）
   ├── build（构建镜像来自私有镜像仓库）
   ├── helper 容器（clone / artifacts）
   └── 共享卷：/builds（内存盘） + /cache（PVC）
```

要点：Runner Manager 只负责「领活 + 开 Pod」，真正干活的是临时 Pod，**不占常驻构建机**。

#### 三、`.gitlab-ci.yml` 设计（9 段式）

对应 Jenkinsfile 的阶段映射：

```
stages: prepare → build → test → analyze → report

prepare → versioning          （git describe 出版本头）
build   → build:linux         （固件编译 + 产物归档）
test    → unit-test / coverage / size-check
analyze → cppcheck / misra
report  → summary
```

##### 3.1 全局骨架

```yaml
stages: [prepare, build, test, analyze, report]

variables:
  ARTIFACT_DIR: "artifacts"
  BUILD_IMAGE_REPO: "<私有仓库地址>/hello-jenkins"
  BUILD_IMAGE_TAG: "v0.4"
  GIT_DEPTH: "0"          # git describe 需要完整历史
  GIT_STRATEGY: "fetch"

default:
  image: "${BUILD_IMAGE_REPO}:${BUILD_IMAGE_TAG}"
  timeout: 90 minutes
  interruptible: true
  before_script:
    - 'echo "Job=${CI_JOB_NAME} Pipeline=${CI_PIPELINE_ID} Source=${CI_PIPELINE_SOURCE}"'

.base-linux:
  tags: [linux-build]
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH'
```

##### 3.2 并行与 DAG

- 同 stage 下的多个 job **天然并行**，不需要像 Jenkins `parallel { }` 那样嵌套
- 用 `needs:` 打破 stage 顺序，让无依赖 job 提前跑：

```yaml
cppcheck:
  stage: analyze
  needs: ["versioning"]        # 不等 build，版本头一出就能跑

misra:
  stage: analyze
  needs: ["build:linux"]       # MISRA 依赖编译产物

summary:
  stage: report
  needs: ["build:linux", "unit-test", "cppcheck"]
```

##### 3.3 产物与报告

```yaml
build:linux:
  stage: build
  needs: ["versioning"]
  script:
    - make -j"$(nproc)"
  artifacts:
    paths: ["${ARTIFACT_DIR}/", "build/*.hex", "build/*.elf", "build/*.map"]
    expire_in: 1 week

unit-test:
  stage: test
  needs: ["build:linux"]
  script:
    - make ut
  artifacts:
    when: always
    reports:
      junit: "${ARTIFACT_DIR}/cunit-*.xml"

coverage:
  stage: test
  needs: ["unit-test"]
  coverage: '/lines.*:\s+(\d+\.\d+)%/'   # 正则抓日志里的覆盖率数字
  artifacts:
    paths: ["${ARTIFACT_DIR}/coverage/"]
```

对照 Jenkins：`archiveArtifacts` → `artifacts.paths`；`junit` 插件 → `reports.junit`（免安装）；`recordIssues` → 需转 Code Climate 格式（下一阶段改造点）。

##### 3.4 MR 门禁

```yaml
# MR 事件与分支事件分开判定
mr-only:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

配套在仓库设置里开启 **「Pipelines must succeed」**，MR 才能合并。等价于 Jenkins 里的 PR 状态回写，但**不用自己写回写逻辑**。

增量质量基线直接用 `CI_MERGE_REQUEST_DIFF_BASE_SHA`，比 Jenkins 侧还要靠 `discoverReferenceBuild` 找参考构建省事。

#### 四、Runner 部署（K8s Executor，纯 YAML 分批 apply）

不引入 Helm，按依赖顺序分 6 个文件：

| 文件 | 内容 | 依赖 |
|:---|:---|:---|
| `01-namespace.yml` | 命名空间 `gitlab-runner` | — |
| `02-rbac.yml` | ServiceAccount / Role / RoleBinding | ns |
| `03-configmap.yml` | `config.template.toml` 模板 | ns |
| `04-pvc.yml` | 构建缓存 PVC | SC |
| `05-secret.yml` | 仅结构参考，**token 用 `kubectl create secret` 创建** | ns |
| `06-deployment.yml` | Runner Manager（官方镜像） | 以上全部 |

##### 4.1 config.toml 模板（关键片段）

```toml
concurrent = 2
check_interval = 3

[[runners\|runners]]
  name = "k3s-runner"
  url = "https://<gitlab 地址>"
  token = "__RUNNER_TOKEN__"        # 由 entrypoint 从 Secret 渲染
  executor = "kubernetes"
  shell = "bash"
  tags = ["linux-build", "k8s-lenovo"]
  run_untagged = false
  environment = ["FF_USE_FASTZIP=true"]

  [runners.kubernetes]
    namespace = "gitlab-runner"
    image = "alpine:3.20"
    privileged = false
    poll_timeout = 600
    cpu_request = "500m"
    cpu_limit = "2"
    memory_request = "512Mi"
    memory_limit = "4Gi"

    [runners.kubernetes.node_selector]
      "kubernetes.io/hostname" = "home-node"    # 键含 / 必须加引号

    [[runners.kubernetes.volumes.empty_dir\|runners.kubernetes.volumes.empty_dir]]    # 构建目录用内存盘
      name = "build-dir"
      mount_path = "/builds"
      medium = "Memory"
      size_limit = "2Gi"

    [[runners.kubernetes.volumes.pvc\|runners.kubernetes.volumes.pvc]]
      name = "runner-cache"
      mount_path = "/cache"

  [runners.cache]
    Type = "local"
    Path = "/cache"
    Shared = true
```

设计取舍：

- **concurrent=2**：目标节点 8C/8G，上面还跑着镜像仓库和监控全家桶，4 并发容易 OOM
- **node_selector 固定节点**：构建镜像 344MB，落在同一节点可利用本地镜像缓存
- **/builds 用 Memory emptyDir**：构建中间文件不落盘，避免把家宽小盘写满
- **token 不进 ConfigMap**：Secret 注入 + entrypoint 渲染模板，配置可安全入库

#### 五、踩坑清单（6 条，按严重度）

##### 坑 1 · Runner 无 tag → job 永久 pending（最关键）

- **现象**：Runner Pod 1/1 Running、日志正常，但流水线所有 job `pending`，`runner=None`
- **排除过程**：确认 Runner 在线 → 确认 job 与项目已关联 → 发现 GitLab 侧 `tag_list=None`，而 yml 写了 `tags: [linux-build]`
- **根因**：新版 GitLab 是「**先创建 runner 拿 token，再连接**」的认证式流程。runner 的 `description` / `tags` 在**创建时就绑定**，`config.toml` 里写的 `tags` 只在本地匹配时用，**不会回写到 GitLab**；共享 Runner 通常只收 untagged job，也帮不上忙
- **修法**：用 API 显式设置标签（拿 PAT 调 `PUT /runners/:id`，body `{"tag_list": "linux-build,k8s-lenovo"}`），或在创建页面就填好标签
- **认知**：**「Pod Running」≠「Runner 可用」**。判活三看：Runner 在线状态、`tag_list`、job 的 `runner` 字段

##### 坑 2 · 旧 pending 流水线不会自动接管

Runner 修好后重启，**已存在的 pending job 仍然不会被执行**（job 与 runner 的绑定在派发时就定了）。必须取消并重新触发流水线。

##### 坑 3 · entrypoint 路径

官方镜像的入口是 `/entrypoint`，写 `/usr/bin/entrypoint` 直接起不来。以镜像实际 `ENTRYPOINT` 为准，别按习惯猜。

##### 坑 4 · TOML 键含 `/` 必须加引号

`[runners.kubernetes.node_selector]` 下的 `kubernetes.io/hostname` 不加引号会被 TOML 解析器截断报错：

```toml
"kubernetes.io/hostname" = "home-node"
```

##### 坑 5 · `empty_dir` / `pvc` 是数组

`[runners.kubernetes.volumes.empty_dir]`（单表）解析不过，必须写成 `[[runners.kubernetes.volumes.empty_dir\|runners.kubernetes.volumes.empty_dir]]`（数组表）。同理 `[[runners.kubernetes.volumes.pvc\|runners.kubernetes.volumes.pvc]]`。

##### 坑 6 · `FF_USE_FASTZIP` 重复定义

Runner 会自动注入 `FF_USE_FASTZIP`，ConfigMap 的 `environment` 里再写一次会触发 k8s 警告（`hides previous definition`）。功能不受影响，但属配置冗余，建议删掉。

#### 六、验收结果

| 项 | 结果 |
|:---|:---|
| Runner | Manager Pod 1/1 Running，`max_builds=2`，注册在线 |
| `.gitlab-ci.yml` | YAML 校验通过，8 个 job |
| 首次全链路 | **8/8 job 成功** |
| 耗时分布 | 多数 job 15~35s；最慢 MISRA 约 133s |
| Job Pod 回收 | 全部正常销毁，只留 Manager |
| 镜像拉取 | 私有仓库镜像可拉（344MB，首次约 78s，之后走节点缓存） |

#### 七、Jenkins → GitLab CI 迁移认知

1. **结构更扁平**：没有 `post { }` 嵌套，`artifacts` / `reports` 直接挂在 job 上
2. **DAG 是最大收益**：`needs:` 让「版本头生成 → 静态检查」这类无编译依赖的活提前并行，Jenkins 要插件或 hack 才能做到
3. **模板分层换思路**：Shared Library 的「Groovy 类库 + 全局变量」→ `include`（引入外部 yml）+ `extends`（继承 job）+ `!reference`（引用片段），可做到「组织级模板仓 + 项目级覆盖」
4. **门禁更省事**：MR 必须通过流水线才能合并是产品内置开关，不用写回写代码；增量基线变量现成
5. **执行器即基础设施**：Runner executor 选 kubernetes，就把「构建机运维」变成了「Pod 调度」——复用集群资源、按需扩缩，和 Jenkins k8s 动态 agent 是同一思路的两种实现
6. **注意差异点**：`recordIssues` 这类在 Jenkins 里插件化的能力，GitLab 侧要转成 Code Climate 格式的 `reports: codequality:`，不是一键迁移

#### 八、Jenkins vs GitLab CI 双平台对比（同一项目实测）

> 对照对象：同一 C 项目（S32K144 Bootloader）两套流水线——`Jenkinsfile`（342 行，k8s 动态 agent + Shared Library）与 `.gitlab-ci.yml`（264 行，K8s Executor Runner）。
> 数据取自两条流水线的真实执行记录，不是纸面推演。

##### 8.1 规模与结构

| 维度 | Jenkinsfile | .gitlab-ci.yml |
|:---|:---|:---|
| 文件行数 | 342 行（Groovy） | 264 行（YAML） |
| 阶段组织 | 嵌套 `parallel { stage { stages { } } }` 三层 | 扁平：`stages` 顶层 + job 平铺 |
| 构建腿 | linux / codecheck / windows 三腿并行 | 单腿（windows 腿未迁移） |
| 复用机制 | Shared Library（Groovy 类库 + vars 全局变量） | `extends` job 模板 + `!reference` 片段 + `include` |
| 可选能力开关 | `environment` 变量 + `when { expression }` | `variables` + `rules: if` |
| 报告发布 | 插件（warnings-ng / junit / html） | 自带 `reports: junit` / `dotenv`，其余落 artifacts |

##### 8.2 能力逐项对照

| 能力 | Jenkins 写法 | GitLab CI 写法 | 谁更省事 |
|:---|:---|:---|:---|
| 执行环境 | `agent { label 'k8s-linux' }` 动态 Pod | `image:` + `tags:` + K8s executor | 平手（思路一致） |
| 跨 stage 依赖 | 只能按 stage 顺序串，或靠 `parallel` 归组 | `needs:` 原生 DAG，任意跨 stage | **GitLab** |
| 并行 | `parallel { stage ... }` 嵌套结构 | 同 stage 平铺即并行 | **GitLab** |
| 产物传递 | `archiveArtifacts` / `stash-unstash` | `artifacts.paths` + `needs` 自动下载 | **GitLab** |
| 变量跨 job 传递 | 全局 `environment` / 文件 + `stash` | `reports: dotenv` 自动注入下游 | **GitLab** |
| 单测报告 | junit 插件（需安装） | `reports: junit`（内置） | **GitLab** |
| 覆盖率数字 | 插件解析或自写正则 | `coverage: '/正则/'` 一行 | **GitLab** |
| 超时/日志轮转 | `options { timeout, buildDiscarder, timestamps }` | `timeout:` / `artifacts.expire_in` | 平手 |
| 模板分层 | Shared Library（Groovy 类库，能力最强） | include + extends + Components | **Jenkins**（Groovy 可写逻辑） |
| 条件跳过 | `when { expression }`（可写 Groovy 表达式） | `rules: if`（CI/CD 变量表达式） | **Jenkins**（灵活度略高） |
| MR 增量基线 | 需 `discoverReferenceBuild` 找参考构建（v0.6→v0.8 才修好） | `CI_MERGE_REQUEST_DIFF_BASE_SHA` 直接给 | **GitLab** |
| 合并门禁 | 自己写 PR 状态回写（插件 + API） | 仓库开关「Pipelines must succeed」 | **GitLab** |
| 失败回写 | 插件调托管平台 API（各家接口不同） | 内置，无需代码 | **GitLab** |
| 自建成本 | Master + 多类型 agent + 插件体系 | 一个 Runner Pod + token | **GitLab** |

##### 8.3 实测耗时（同一份代码、同等任务）

| Job | Jenkins | GitLab CI |
|:---|:---|:---|
| 版本头 | 含在构建腿内 | 14.9s |
| 编译 | 数分钟（受节点缓存影响波动大） | 24.7s（镜像已缓存） |
| 单测 | 数十秒 | 20.2s |
| 覆盖率 | 数十秒 | 21.7s |
| 容量门禁 | 秒级 | 15.1s |
| Cppcheck | 分钟级 | 35.3s |
| MISRA-C | ~8 分钟（单线程 addon） | 122.1s（约 2 分钟） |
| 汇总 | — | 15.5s |

结论：**GitLab CI 单 job 更轻、启动更快**（Pod 按需起、无 Groovy 编排开销）；Jenkins 的多腿并行（linux / codecheck / windows 同时跑）在总墙钟时间上仍有优势，但代价是三套 agent 环境要长期维护。

##### 8.4 踩坑类型对照

| 平台 | 踩过的坑 | 本质 |
|:---|:---|:---|
| Jenkins | JNLP 穿透 NAT、workspaceVolume 僵尸构建、dockerfile agent 缓存漂移、插件 DSL 写法、单引号静默失败、`recordIssues` 通配翻倍 | 环境编排 + Groovy/插件细节 |
| GitLab CI | Runner tag 不回写、pending 不自动接管、TOML 引号与数组表、entrypoint 路径、镜像拉取耗时 | 配置语义 + Runner 认证模型 |

共性认知：**两个平台的坑都集中在「声明与实际生效之间的语义差」**——Jenkins 是插件 DSL 的隐含规则，GitLab 是「UI 侧属性 vs config 文件属性」的双份真相。

##### 8.5 同一问题双平台解法：MR 增量门禁（假绿 → 真拦）

同一业务需求——「新增静态检查问题必须阻断合并，存量问题不能卡住」——两个平台的实现路径完全不同：

| 环节 | Jenkins 解法 | GitLab CI 解法 |
|:---|:---|:---|
| 拿基线 | 自定义参考构建解析（`discoverReferenceBuild` + Multibranch 全名解析） | 仓库内维护基线 XML + 按 `(文件, 行, 规则, 严重度)` 比对 |
| 增量判定 | warnings-ng 的 `new / outstanding / fixed` 三元组 | 自写门禁脚本算 `新增 / 已修复 / 总数` |
| 阻断方式 | `Quality gate` 配置 `enforced=true` | 脚本 `exit 1` + 仓库「Pipelines must succeed」 |
| 结果回写 | 插件调托管平台 API 写 commit status | 内置，无需代码 |
| 可视化 | warnings-ng 报告页 | `reports: codequality:`（Code Climate 格式） |
| 踩过的坑 | v0.6.0「假绿」：参考构建解析失败 → 存量当新增为 0 → 门禁永远通过 | 等价「假绿」：`--error-exitcode=0` → job 永远退出 0 |

**核心教训（跨平台通用）：门禁配置存在 ≠ 门禁生效。** 「发现问题」到「让 job 失败」之间少一环（Jenkins 是基线解析错，GitLab 是退出码恒 0），流水线就稳定假绿。**验证门禁唯一可靠的方式：埋问题，看它是否真的变红。**

###### 8.5.1 实测：改造前的「假绿」

在验证分支新增一个探针文件（埋 `malloc` 未释放、未使用变量、`strcpy` 无边界），开 MR 后：

| 项 | 结果 |
|:---|:---|
| cppcheck job | ✅ success（日志明写 `问题数: 2`） |
| 其余 7 个 job | ✅ success |
| MR 合并状态 | **可合并** |

原因：`--error-exitcode=0` 让 cppcheck 发现问题也返回 0，job 只把报告写成文件、echo 一行数字，**没有任何一步会让 job 失败**。仓库的「Pipelines must succeed」开关形同虚设。

###### 8.5.2 改造方案（落地实现）

**三步走：只产报告 → 独立脚本判门禁 → 结果双通道输出（退出码 + Code Climate）**

```
cppcheck（只扫描、只出 XML）
   ↓
tools/ci_gate.py  ← 比对 lint-baseline/<检查>.xml
   ├─ exit 0/1        → 决定 job 成败（真正的门禁）
   └─ gl-code-quality-report.json → MR 页面可视化
```

门禁脚本 `tools/ci_gate.py`（纯标准库，约 130 行）核心逻辑：

```python
# 解析 XML -> {(file, line, rule, severity, msg): count}
cur  = parse(report)
base = parse(baseline) or {}      # 基线缺失 = 空基线（严格模式）

new   = sum(cnt - base.get(k, 0) for k, cnt in cur.items() if cnt > base.get(k, 0))
fixed = sum(b  - cur.get(k, 0)   for k, b   in base.items() if b   > cur.get(k, 0))

if new > MAX_NEW:            # 默认 0：一条新增都不许
    sys.exit(1)
```

用法（job 里）：

```bash
python3 tools/ci_gate.py \
  --report   ${ARTIFACT_DIR}/codecheck/Cppcheck/cppcheck-report.xml \
  --baseline lint-baseline/Cppcheck.xml \
  --label    Cppcheck \
  --max-new  ${GATE_MAX_NEW_CPPCHECK:-0} \
  --violation-file ${ARTIFACT_DIR}/codecheck/Cppcheck/gl-code-quality-report.json
```

配套改动：
- `artifacts.reports.codequality:` 挂上报告 → MR 页面直接显示新增问题
- 阈值用 CI 变量暴露（`GATE_MAX_NEW_CPPCHECK` / `GATE_MAX_NEW_MISRA`），需要时可在 MR 里临时放宽
- 基线文件放仓库 `lint-baseline/`，只允许在 main 更新

###### 8.5.3 基线策略（存量不卡、新增必拦）

| 项 | 做法 |
|:---|:---|
| 基线来源 | main 分支真实构建的 artifacts 里的报告 XML |
| 基线粒度 | 文件 + 行号 + 规则 ID + 严重度 + 消息，五元组精确匹配 |
| 基线缺失 | 空基线 = 严格模式（全部算新增），首次接入会全红，属预期 |
| 存量治理 | 不靠基线长期冻结，而是修代码或 `--suppress` 逐条减量，减完更新基线 |
| 防止「清零开关」 | 基线只冻结存量；新增永远跑不过 → 禁不起被当成关闭门禁的手段 |

本次实测基线：Cppcheck 1 条（SDK 头文件 `devassert.h` 的 `#include` 噪声）、MISRA 532 条（全部来自 SDK 头文件）。

###### 8.5.4 实测：改造后的三组对照

| 场景 | cppcheck | MISRA | MR 状态 | 说明 |
|:---|:---|:---|:---|:---|
| 埋新增问题、**改造前** | ✅ success | ✅ success | ❌ **可合并** | 假绿 |
| 埋新增问题、**改造后** | ❌ 新增 2 > 0 | ❌ 新增 532 > 0 | ✅ **被阻断** | 门禁生效 |
| 无新增、**改造后**（main） | ✅ success | ✅ success | 可正常合并 | 存量被基线吸收，8/8 job 绿 |

第二组的关键日志：

```
===== Cppcheck 质量门禁 =====
总数: 2  |  新增: 2  |  已修复: 0
[gate] FAIL: 新增问题 2 > 阈值 0
ERROR: Job failed: command terminated with exit code 1
```

第三组（main）：Cppcheck `新增: 0`、MISRA `新增: 0`，两个 job 均 success。

**三个数字合起来才是一次完整的门禁验证：改造前绿 → 埋问题红 → 去掉问题绿。** 只验证其中一两步，很容易把「恰好通过」当成「门禁有效」。

###### 8.5.5 顺带修掉的坑

- **summary job 永远 skipped**：它 `needs: [build:linux, unit-test, cppcheck]`，前置失败时被跳过属正常；但脚本里 `[ -n "${CI_MERGE_REQUEST_IID:-}" ] && echo ...` 作为最后一条命令，非 MR 场景返回 1 会把整个 job 判失败 → 改成 `if ... then ... fi`
- **探针文件必须移除**：验证完立刻删除，否则它会长期挂在新增问题里，等于给自己埋雷

## 第三部分 · ci-lib 作品集（原 12）

> 定位：把「每个仓库都复制粘贴一遍的 Jenkinsfile 样板」收敛成一套可复用、可演进、有门禁的共享库。
> 本文是这件作品的完整说明：解决了什么问题、怎么设计的、踩过什么坑、最后沉淀了什么。

#### 一、要解决的问题

多个仓库（C 固件、Java 服务、Android/NDK 混合）的 Jenkinsfile 长期各写各的，同一个「推镜像」「跑覆盖率」在不同仓库里写法都不一样。改一次阈值要改 N 个仓库，漏改一个就是隐患。

**四条设计原则**：

| 原则 | 含义 |
|:---|:---|
| 仓库侧只声明 | Jenkinsfile 只留 `@Library` + 入口调用 + 配置清单 |
| 差异即配置 | 技术栈/阈值/分支策略走 profile，不进代码 |
| 逻辑唯一源 | 同一段逻辑只写一次，改一处全仓生效 |
| 可快速失败 | 前置校验放在最前面，不浪费 30 分钟才报错 |

#### 二、最终形态：8 个步骤

```
vars/
├── ciInfo.groovy            41   库信息横幅 / 冒烟验证
├── versioning.groovy        65   版本注入（git describe / 文件正则 → displayName + 版本头文件）
├── acrImage.groovy          87   镜像构建推送（VPC 内网回落 + 唯一 tag + buildArgs）
├── coverage.groovy          59   覆盖率包装（生成 → publishHTML → UT → 归档）
├── codeCheck.groovy        222   静态检查 + 双轨门禁 + 趋势
├── publishArtifact.groovy  124   制品发布到 Gitea 通用包
├── standardPipeline.groovy 132   骨架配置解析器 + 技术栈 profile
└── releasePipeline.groovy  210   发布五道门禁 + 三件套
                            ────
                            940 行
```

**配套资源**：

| 文件 | 作用 |
|:---|:---|
| `resources/profiles/c-embedded.groovy` | 嵌入式 C：cppcheck + MISRA、make coverage、`Sources/ci_version.h` |
| `resources/profiles/java-gradle.groovy` | JVM：checkstyle、jacoco、`gradle.properties` 取版本 |

#### 三、六个步骤的 API 速览

##### 3.1 `versioning` — 版本注入

```groovy
def v = versioning(headerFile: 'Sources/ci_version.h')   // C 项目
versioning(versionFile: 'gradle.properties')              // JVM 项目
versioning(versionFile: 'package.json', versionPattern: /"version"\s*:\s*"([^"]+)"/)
```

版本来源优先级：显式 `versionOverride` → 文件正则 → `git describe`。产出 displayName/description + 可选版本头文件。

##### 3.2 `acrImage` — 镜像构建推送

```groovy
acrImage(repo: 'registry.cn-hangzhou.aliyuncs.com/xxx/halo', tag: 'latest')
acrImage(repo: '...', tag: '2.27.0', buildArgs: ['JAR_FILE=...'], tagTemplate: 'v')
```

亮点：**VPC 内网端点可达性探测**——可达就走内网（分钟级），不可达自动回落公网，避免跨地域推送卡 1.5 小时踩满 timeout。

##### 3.3 `codeCheck` — 静态检查 + 双轨门禁

这是全库最复杂的一个（222 行），也是踩坑最多的。

**双轨判定**（按构建上下文自动切换，Jenkinsfile 不用写分支逻辑）：

| 场景 | 判定 | 效果 |
|:---|:---|:---|
| MR 构建（`CHANGE_ID` 存在） | 相对目标分支**新增**问题数 > 0 → 失败 | 不新增告警才放行 |
| 分支构建（main/dev 直推） | 问题**总数** > `maxErrors` → 失败 | 存量基线不恶化 |

```groovy
codeCheck(id: 'cppcheck', name: 'Cppcheck',
          run: 'cppcheck ... --xml --xml-version=2 Sources 2> codecheck/cppcheck-report.xml || true',
          report: 'codecheck/cppcheck-report.xml', parser: 'cppcheck',
          maxErrors: 100)
```

##### 3.4 `coverage` — 覆盖率包装

```groovy
coverage(run: 'make coverage', reportDir: 'build/coverage/html',
         artifacts: 'build/coverage/**')
```

统一用 `publishHTML`（不用 `recordCoverage`），与两个仓库既有约定保持一致。

##### 3.5 `publishArtifact` — 制品发布

```groovy
publishArtifact(package: 'sherpa-onnx-cpp-android', version: '1.13.7',
                files: ['build/libsherpa-onnx-jni.so'], keepDir: true)
```

选 Gitea Generic Registry 的理由：与现有 Gitea 一体、免新组件、任意文件类型、走既有凭据。
`keepDir` 是关键参数——保留子目录，避免多 ABI 同名文件互相覆盖。

##### 3.6 `standardPipeline` — 骨架配置解析器

**这个步骤的定位经过一次重大修正**（v0.4.0）。

最初想让它「生成」声明式骨架，实测发现做不到：

```groovy
// 在库代码里裸写
agent none    → MissingPropertyException: No such property: none
options { }   → NoSuchMethodError: No such DSL method 'options'
```

**原因**：声明式流水线的 `pipeline { agent/options/stages/post }` 必须是 Jenkinsfile 里的**字面量**，库代码里调用不到 DSL。

**改后定位**：库负责「配置解析 + 前置校验 + profile 加载」，返回一个 Map；Jenkinsfile 用这个 Map 填自己的字面量骨架。

```groovy
def SP = standardPipeline(name: 'sherpa-lite', stack: 'cpp-ndk',
                          requiredEnv: ['ACR_CRED'], requiredTools: ['docker'])

pipeline {
    agent none
    options {
        timeout(time: SP.timeoutMinutes, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: "${SP.daysToKeep}"))
    }
    post { always { archiveArtifacts artifacts: SP.archiveGlobs.join(', ') } }
}
```

**收获**：知道了一个工具的边界在哪，比硬凑出一个「看起来能用」的方案更重要。

##### 3.7 `releasePipeline` — 发布五道门禁

| # | 门禁 | 拦截什么 |
|:-:|:---|:---|
| ① | Tag 格式 `^v\d+\.\d+\.\d+(-(alpha\|beta\|rc)\.\d+)?$` | `1.2.0`（缺 v）、`v1.2`（缺 PATCH） |
| ② | annotated tag | `git tag v1.0`（lightweight） |
| ③ | tag commit == HEAD | tag 没打在最新提交上 |
| ④ | 正式 tag 必须在 main | **从错误分支打正式 tag** |
| ⑤ | 预发布默认阻断 | `-rc` / `-beta` 被当成正式版发出去 |

产物三件套：`build-info.txt`（制品↔tag↔commit↔构建）、`checksums.sha256`、`release-notes.md`。

#### 五、最有价值的三个坑

##### 坑 1 · MR 门禁「假绿」——修了两版才修对

这是全库最有教育意义的一段。

**现象**：MR 里明明有新增告警，门禁却永远通过。

**第一版修法（v0.7.0）**：把 `referenceJobName` 塞进 `recordIssues` 参数。
→ **无效**。warnings-ng 13.x 的 `RecordIssuesStep` 字节码里根本没这个参数，会被当成 Unknown parameter **静默丢弃**（只打一条 WARNING）。

**第二版修法（v0.8.0）**：改用 `discoverReferenceBuild(referenceJob: ...)`。
→ 仍然假绿。因为传了裸分支名 `main`，ReferenceFinder 打 `There is no such job`，**回退到当前 job**（`PR-2` 自己的上次构建），delta 恒为 0。

**最终解法**：`referenceJob` 必须传 **Multibranch 子 job 的完整名**（`sherpa-lite/main`），由 `JOB_NAME`/`BRANCH_NAME`/`CHANGE_TARGET` 推导。

**教训**：**门禁配置存在 ≠ 门禁生效**。两次「修好了」都是假象，唯一可靠的验证方式是**埋一个真实问题，看它是否真的变红**。

##### 坑 2 · 声明式骨架无法由库生成

见 3.6 节。库代码里 `agent none`、`options {}` 都调不到，因为它们是 Jenkinsfile 的字面量 DSL。

**教训**：先摸清工具的边界，再设计方案。硬凑出来的「能跑」方案会在下一个仓库上崩。

##### 坑 3 · 注释里的 `**/` 提前闭合注释块

v0.3.1：`coverage.groovy` 的文档注释里写了 `build/**`，其中的 `**/` 被 Groovy 当成注释结束符，导致后面的代码被当成注释，CPS 编译直接失败。

**教训**：Groovy 块注释里写 glob 通配要格外小心。

**【坑】Groovy 块注释被 `**/` 提前闭合**

- 现象：`coverage()` 调用处报 `CpsCompilationErrorsException: unexpected token: *`（指向库文件 `coverage.groovy:18`）；stage 能起容器但脚本编译失败、整条构建红。
- 根因：`coverage.groovy` 的 Javadoc 示例里写了 `junit: "...test-results/**/*.xml"` —— 其中 **`**/`（`*` + `/`）被 Groovy 当成块注释结束符**，导致 `/** ... */` 在示例行提前闭合，后面参数说明文字被当作代码解析。
- 修复：将示例里的 `**/*.xml` 转义为 `**\/*.xml`（`codeCheck.groovy` 当初就正确转义了，所以只有 coverage 中招）。
- **教训**：共享库 `.groovy` 的文档注释里，任何 `*/` 序列（包括 glob 的 `**/`）都会被当作注释结束 —— 写通配例子必须转义。

## 第二部分 · GitLab CI 流水线（原 10）

> 目标：把已有 Jenkins 流水线（hello-jenkins / S32K144 Bootloader）等价改造到 GitLab CI，跑通全链路，并为「标准化流水线模板沉淀」打底。

#### 一、为什么补 GitLab CI

| 维度 | Jenkins | GitLab CI |
|:---|:---|:---|
| 流水线定义 | Jenkinsfile（Groovy） | `.gitlab-ci.yml`（YAML） |
| 模板复用 | Shared Library（Groovy 类库） | `include` + `extends` + `!reference` 分层 |
| 并行 / 依赖 | 同 stage 并行；跨 stage 依赖需插件 | `needs:` **原生 DAG**，可跨 stage 任意依赖 |
| 测试报告 | 插件（JUnit / 记录 Issues） | `reports: junit:` **原生** |
| 覆盖率 | 插件解析 | `coverage:` 正则从日志提取 |
| 执行环境 | 常驻 agent / 动态 pod | Runner + executor（docker / shell / **kubernetes**） |
| MR 门禁 | 插件 + PR 回写 | 内置 Pipeline 必须成功才能合并 + `CI_MERGE_REQUEST_*` 变量 |
| 增量基线 | 需 `discoverReferenceBuild` 找参考构建 | `CI_MERGE_REQUEST_DIFF_BASE_SHA` 直接给 |

结论：**YAML 扁平、DAG 原生、MR 变量现成**，是 Jenkins 之外最值得掌握的第二个 CI 平台；多家 JD 把它列为硬要求。

#### 五、踩坑清单（6 条，按严重度）

##### 坑 1 · Runner 无 tag → job 永久 pending（最关键）

- **现象**：Runner Pod 1/1 Running、日志正常，但流水线所有 job `pending`，`runner=None`
- **排除过程**：确认 Runner 在线 → 确认 job 与项目已关联 → 发现 GitLab 侧 `tag_list=None`，而 yml 写了 `tags: [linux-build]`
- **根因**：新版 GitLab 是「**先创建 runner 拿 token，再连接**」的认证式流程。runner 的 `description` / `tags` 在**创建时就绑定**，`config.toml` 里写的 `tags` 只在本地匹配时用，**不会回写到 GitLab**；共享 Runner 通常只收 untagged job，也帮不上忙
- **修法**：用 API 显式设置标签（拿 PAT 调 `PUT /runners/:id`，body `{"tag_list": "linux-build,k8s-lenovo"}`），或在创建页面就填好标签
- **认知**：**「Pod Running」≠「Runner 可用」**。判活三看：Runner 在线状态、`tag_list`、job 的 `runner` 字段

#### 七、Jenkins → GitLab CI 迁移认知

1. **结构更扁平**：没有 `post { }` 嵌套，`artifacts` / `reports` 直接挂在 job 上
2. **DAG 是最大收益**：`needs:` 让「版本头生成 → 静态检查」这类无编译依赖的活提前并行，Jenkins 要插件或 hack 才能做到
3. **模板分层换思路**：Shared Library 的「Groovy 类库 + 全局变量」→ `include`（引入外部 yml）+ `extends`（继承 job）+ `!reference`（引用片段），可做到「组织级模板仓 + 项目级覆盖」
4. **门禁更省事**：MR 必须通过流水线才能合并是产品内置开关，不用写回写代码；增量基线变量现成
5. **执行器即基础设施**：Runner executor 选 kubernetes，就把「构建机运维」变成了「Pod 调度」——复用集群资源、按需扩缩，和 Jenkins k8s 动态 agent 是同一思路的两种实现
6. **注意差异点**：`recordIssues` 这类在 Jenkins 里插件化的能力，GitLab 侧要转成 Code Climate 格式的 `reports: codequality:`，不是一键迁移

#### 八、Jenkins vs GitLab CI 双平台对比（同一项目实测）

> 对照对象：同一 C 项目（S32K144 Bootloader）两套流水线——`Jenkinsfile`（342 行，k8s 动态 agent + Shared Library）与 `.gitlab-ci.yml`（264 行，K8s Executor Runner）。
> 数据取自两条流水线的真实执行记录，不是纸面推演。

##### 8.1 规模与结构

| 维度 | Jenkinsfile | .gitlab-ci.yml |
|:---|:---|:---|
| 文件行数 | 342 行（Groovy） | 264 行（YAML） |
| 阶段组织 | 嵌套 `parallel { stage { stages { } } }` 三层 | 扁平：`stages` 顶层 + job 平铺 |
| 构建腿 | linux / codecheck / windows 三腿并行 | 单腿（windows 腿未迁移） |
| 复用机制 | Shared Library（Groovy 类库 + vars 全局变量） | `extends` job 模板 + `!reference` 片段 + `include` |
| 可选能力开关 | `environment` 变量 + `when { expression }` | `variables` + `rules: if` |
| 报告发布 | 插件（warnings-ng / junit / html） | 自带 `reports: junit` / `dotenv`，其余落 artifacts |

##### 8.2 能力逐项对照

| 能力 | Jenkins 写法 | GitLab CI 写法 | 谁更省事 |
|:---|:---|:---|:---|
| 执行环境 | `agent { label 'k8s-linux' }` 动态 Pod | `image:` + `tags:` + K8s executor | 平手（思路一致） |
| 跨 stage 依赖 | 只能按 stage 顺序串，或靠 `parallel` 归组 | `needs:` 原生 DAG，任意跨 stage | **GitLab** |
| 并行 | `parallel { stage ... }` 嵌套结构 | 同 stage 平铺即并行 | **GitLab** |
| 产物传递 | `archiveArtifacts` / `stash-unstash` | `artifacts.paths` + `needs` 自动下载 | **GitLab** |
| 变量跨 job 传递 | 全局 `environment` / 文件 + `stash` | `reports: dotenv` 自动注入下游 | **GitLab** |
| 单测报告 | junit 插件（需安装） | `reports: junit`（内置） | **GitLab** |
| 覆盖率数字 | 插件解析或自写正则 | `coverage: '/正则/'` 一行 | **GitLab** |
| 超时/日志轮转 | `options { timeout, buildDiscarder, timestamps }` | `timeout:` / `artifacts.expire_in` | 平手 |
| 模板分层 | Shared Library（Groovy 类库，能力最强） | include + extends + Components | **Jenkins**（Groovy 可写逻辑） |
| 条件跳过 | `when { expression }`（可写 Groovy 表达式） | `rules: if`（CI/CD 变量表达式） | **Jenkins**（灵活度略高） |
| MR 增量基线 | 需 `discoverReferenceBuild` 找参考构建（v0.6→v0.8 才修好） | `CI_MERGE_REQUEST_DIFF_BASE_SHA` 直接给 | **GitLab** |
| 合并门禁 | 自己写 PR 状态回写（插件 + API） | 仓库开关「Pipelines must succeed」 | **GitLab** |
| 失败回写 | 插件调托管平台 API（各家接口不同） | 内置，无需代码 | **GitLab** |
| 自建成本 | Master + 多类型 agent + 插件体系 | 一个 Runner Pod + token | **GitLab** |

##### 8.3 实测耗时（同一份代码、同等任务）

| Job | Jenkins | GitLab CI |
|:---|:---|:---|
| 版本头 | 含在构建腿内 | 14.9s |
| 编译 | 数分钟（受节点缓存影响波动大） | 24.7s（镜像已缓存） |
| 单测 | 数十秒 | 20.2s |
| 覆盖率 | 数十秒 | 21.7s |
| 容量门禁 | 秒级 | 15.1s |
| Cppcheck | 分钟级 | 35.3s |
| MISRA-C | ~8 分钟（单线程 addon） | 122.1s（约 2 分钟） |
| 汇总 | — | 15.5s |

结论：**GitLab CI 单 job 更轻、启动更快**（Pod 按需起、无 Groovy 编排开销）；Jenkins 的多腿并行（linux / codecheck / windows 同时跑）在总墙钟时间上仍有优势，但代价是三套 agent 环境要长期维护。

##### 8.4 踩坑类型对照

| 平台 | 踩过的坑 | 本质 |
|:---|:---|:---|
| Jenkins | JNLP 穿透 NAT、workspaceVolume 僵尸构建、dockerfile agent 缓存漂移、插件 DSL 写法、单引号静默失败、`recordIssues` 通配翻倍 | 环境编排 + Groovy/插件细节 |
| GitLab CI | Runner tag 不回写、pending 不自动接管、TOML 引号与数组表、entrypoint 路径、镜像拉取耗时 | 配置语义 + Runner 认证模型 |

共性认知：**两个平台的坑都集中在「声明与实际生效之间的语义差」**——Jenkins 是插件 DSL 的隐含规则，GitLab 是「UI 侧属性 vs config 文件属性」的双份真相。

##### 8.5 同一问题双平台解法：MR 增量门禁（假绿 → 真拦）

同一业务需求——「新增静态检查问题必须阻断合并，存量问题不能卡住」——两个平台的实现路径完全不同：

| 环节 | Jenkins 解法 | GitLab CI 解法 |
|:---|:---|:---|
| 拿基线 | 自定义参考构建解析（`discoverReferenceBuild` + Multibranch 全名解析） | 仓库内维护基线 XML + 按 `(文件, 行, 规则, 严重度)` 比对 |
| 增量判定 | warnings-ng 的 `new / outstanding / fixed` 三元组 | 自写门禁脚本算 `新增 / 已修复 / 总数` |
| 阻断方式 | `Quality gate` 配置 `enforced=true` | 脚本 `exit 1` + 仓库「Pipelines must succeed」 |
| 结果回写 | 插件调托管平台 API 写 commit status | 内置，无需代码 |
| 可视化 | warnings-ng 报告页 | `reports: codequality:`（Code Climate 格式） |
| 踩过的坑 | v0.6.0「假绿」：参考构建解析失败 → 存量当新增为 0 → 门禁永远通过 | 等价「假绿」：`--error-exitcode=0` → job 永远退出 0 |

**核心教训（跨平台通用）：门禁配置存在 ≠ 门禁生效。** 「发现问题」到「让 job 失败」之间少一环（Jenkins 是基线解析错，GitLab 是退出码恒 0），流水线就稳定假绿。**验证门禁唯一可靠的方式：埋问题，看它是否真的变红。**

## 第三部分 · ci-lib 作品集（原 12）

> 定位：把「每个仓库都复制粘贴一遍的 Jenkinsfile 样板」收敛成一套可复用、可演进、有门禁的共享库。
> 本文是这件作品的完整说明：解决了什么问题、怎么设计的、踩过什么坑、最后沉淀了什么。

#### 一、要解决的问题

多个仓库（C 固件、Java 服务、Android/NDK 混合）的 Jenkinsfile 长期各写各的，同一个「推镜像」「跑覆盖率」在不同仓库里写法都不一样。改一次阈值要改 N 个仓库，漏改一个就是隐患。

**四条设计原则**：

| 原则 | 含义 |
|:---|:---|
| 仓库侧只声明 | Jenkinsfile 只留 `@Library` + 入口调用 + 配置清单 |
| 差异即配置 | 技术栈/阈值/分支策略走 profile，不进代码 |
| 逻辑唯一源 | 同一段逻辑只写一次，改一处全仓生效 |
| 可快速失败 | 前置校验放在最前面，不浪费 30 分钟才报错 |

#### 五、最有价值的三个坑

##### 坑 1 · MR 门禁「假绿」——修了两版才修对

这是全库最有教育意义的一段。

**现象**：MR 里明明有新增告警，门禁却永远通过。

**第一版修法（v0.7.0）**：把 `referenceJobName` 塞进 `recordIssues` 参数。
→ **无效**。warnings-ng 13.x 的 `RecordIssuesStep` 字节码里根本没这个参数，会被当成 Unknown parameter **静默丢弃**（只打一条 WARNING）。

**第二版修法（v0.8.0）**：改用 `discoverReferenceBuild(referenceJob: ...)`。
→ 仍然假绿。因为传了裸分支名 `main`，ReferenceFinder 打 `There is no such job`，**回退到当前 job**（`PR-2` 自己的上次构建），delta 恒为 0。

**最终解法**：`referenceJob` 必须传 **Multibranch 子 job 的完整名**（`sherpa-lite/main`），由 `JOB_NAME`/`BRANCH_NAME`/`CHANGE_TARGET` 推导。

**教训**：**门禁配置存在 ≠ 门禁生效**。两次「修好了」都是假象，唯一可靠的验证方式是**埋一个真实问题，看它是否真的变红**。

##### 坑 2 · 声明式骨架无法由库生成

见 3.6 节。库代码里 `agent none`、`options {}` 都调不到，因为它们是 Jenkinsfile 的字面量 DSL。

**教训**：先摸清工具的边界，再设计方案。硬凑出来的「能跑」方案会在下一个仓库上崩。

##### 坑 3 · 注释里的 `**/` 提前闭合注释块

v0.3.1：`coverage.groovy` 的文档注释里写了 `build/**`，其中的 `**/` 被 Groovy 当成注释结束符，导致后面的代码被当成注释，CPS 编译直接失败。

**教训**：Groovy 块注释里写 glob 通配要格外小心。

#### 第 3 步：`codeCheck` + `coverage` 抽象

| 维度 | hello-jenkins | sherpa-lite | 收敛点 |
|:---|:---|:---|:---|
| codecheck 工具 | cppcheck（C99）+ MISRA（cppcheck addon） | cppcheck（C++17）+ ktlint（Kotlin）+ Android Lint | 都是「跑工具 → 出 XML → 计数 → recordIssues → 归档」 |
| 门禁 | 无（仅出报告） | **有**（问题数 > 阈值 → exit 1 阻断） | `maxErrors` 可选启用 |
| 报告解析器 | `cppCheck` | `cppCheck` / `checkStyle` / `androidLint` | `parser` 参数映射 |
| coverage | `make coverage` → publishHTML | gradle jacoco + UT → publishHTML | 都是「跑生成命令 → publishHTML → 归档」 |
| UT 结果 | xunit CUnit | xunit JUnit | `junit` 可选参数 |

- **`vars/codeCheck.groovy`**：参数 `id`/`name`/`run`/`report`/`parser`/`countPattern`/`maxErrors`/`archive`。
  顺序：**run → recordIssues（先记录，保证门禁失败时趋势仍在）→ 计数门禁 → 归档**。工具调用本身由调用方传入（`run`），库只收敛「样板」。
- **`vars/coverage.groovy`**：参数 `run`/`reportDir`/`reportFiles`/`reportName`/`junit`/`artifacts`/`allowMissing`。
  顺序：**run → publishHTML → 可选 xunit(JUnit) → 归档**。统一用 publishHTML（沿用两仓库既有约定，不用 recordCoverage）。

**【坑】Groovy 块注释被 `**/` 提前闭合**

- 现象：`coverage()` 调用处报 `CpsCompilationErrorsException: unexpected token: *`（指向库文件 `coverage.groovy:18`）；stage 能起容器但脚本编译失败、整条构建红。
- 根因：`coverage.groovy` 的 Javadoc 示例里写了 `junit: "...test-results/**/*.xml"` —— 其中 **`**/`（`*` + `/`）被 Groovy 当成块注释结束符**，导致 `/** ... */` 在示例行提前闭合，后面参数说明文字被当作代码解析。
- 修复：将示例里的 `**/*.xml` 转义为 `**\/*.xml`（`codeCheck.groovy` 当初就正确转义了，所以只有 coverage 中招）。
- **教训**：共享库 `.groovy` 的文档注释里，任何 `*/` 序列（包括 glob 的 `**/`）都会被当作注释结束 —— 写通配例子必须转义。
