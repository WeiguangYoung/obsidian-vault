## 装前修复与清理

> 完整现象 / 根因 / 教训 → 见第二部分「装前事故档案」（docker 版本断裂 / Halo OOM）。

**1. docker CLI 29 vs daemon 24 版本断裂**（`docker ps` 报 client too new）：
```bash
# 临时绕过（老 CLI 兼容上限内）：
DOCKER_API_VERSION=1.43 docker ps
# 正式修复（采用）：重启 daemon 对齐版本
# ⚠️ 重启前预检：业务容器 restart=always / compose 位置 / 内存余量
systemctl restart docker
```

**2. 清理废弃 Halo 容器 + 数据 + 镜像**（共回收约 1.2G）：
```bash
docker rm halo
rm -rf /root/.halo2 /root/halo.tar
docker rmi <halo-image>
```

**3. 新增 2G swap**（此前无 swap，Halo 死于 OOM）：
```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
sysctl -w vm.swappiness=10
```

## k3s 安装（装机流程）

> ⚠️ 国内镜像源已死 + 业务镜像拉不动 → 见 [问题 1]、[问题 2]。

**① 装 server**（2026-09-13 修正：走 `get.k3s.io` + GitHub，别用 `INSTALL_K3S_MIRROR=cn`）：
```bash
curl -sfL https://get.k3s.io | \
  INSTALL_K3S_EXEC='server --disable=traefik --disable=metrics-server --write-kubeconfig-mode=644' sh -
```
- `--disable=traefik / metrics-server`：1.7G 小内存省约 200M，实验集群用不上
- 装完 71 秒节点 Ready ✅

**② 配镜像加速**（k3s 专用文件，不是 containerd config.toml）：
```yaml
# /etc/rancher/k3s/registries.yaml
mirrors:
  docker.io:
    endpoint:
      - https://docker.m.daocloud.io
      - https://docker.1ms.run
  registry.k8s.io:
    endpoint:
      - https://k8s.m.daocloud.io
```
`systemctl restart k3s` 后 1 分钟内 coredns / local-path-provisioner 全部 Running，nginx 冒烟测试 26 秒到 1/1 ✅。

**③ 验证**：
```bash
kubectl get nodes && kubectl get pods -A
kubectl run smoke --image=nginx:alpine --restart=Never
```

```bash

  K3S_URL=https://203.0.113.11:6443 INSTALL_K3S_EXEC='agent' sh /tmp/ki.sh
shred -u /tmp/.nodetok /tmp/ki.sh
```

### 问题 4：k3s-selinux RPM 依赖断裂（AL3 专属，安装直接 fatal）

**现象**：脚本走到 `Finding available k3s-selinux versions` 后 dnf 报错退出：
```
nothing provides container-selinux >= 3:2.191.0-1 needed by k3s-selinux-1.6-1.el9.noarch
```
**根因**：安装脚本对任何红帽系（`/etc/redhat-release` 存在即命中）强装 k3s-selinux 的 **el9 仓库**包，而 AL3（兼容 el8）源里的 container-selinux 版本不够。机器 SELinux 实际是 **Disabled**——装这个包纯属脚本一刀切。
**绕法演进**：先试 `INSTALL_K3S_SELINUX_WARN=true` ❌（只管"策略找不到"警告，管不了 dnf 安装失败本身）→ 正解 **`INSTALL_K3S_SKIP_SELINUX_RPM=true`** ✅（脚本注释里有此开关，跳过 RPM 自动安装）。SELinux Disabled 的机器零影响。

### 问题 5（真正的硬骨头）：cgroup v1 → kubelet 拒绝启动

**现象**：agent 二进制装好、服务起了、containerd/kube-proxy 正常跑，几秒后自杀：
```
failed to validate kubelet configuration, error: kubelet is configured to not run on
a host using cgroup v1. cgroup v1 support is unsupported...
```
**根因**：**K8s 1.31 起 kubelet 彻底放弃 cgroup v1**，集群是 1.36，没有开关可绕。AL3 默认走 v1（Ubuntu 22.04 默认 v2），同一集群两台机 cgroup 版本不同第一次撞上。
**修复**（唯一正路：切 v2，需重启一次）：
```bash
grubby --update-kernel=ALL --args='systemd.unified_cgroup_hierarchy=1'
reboot
# 验证：stat -fc %T /sys/fs/cgroup/ → cgroup2fs
```
重启后 k3s-agent 自启，55 秒节点 Ready。**教训**：跨发行版加节点前，`stat -fc %T /sys/fs/cgroup/` 应列入装前预检清单——这一项在空机时切成本最低，跑了业务再切就要迁容器。

### 观察项：agent 内置 LB 优先学到 server 的 VPC 内网 IP

日志显示 agent 从 server 拿到注册地址 `172.23.174.21:6443`（server 上报的 internal-ip，跨 VPC 不可达），健康检查失败后**自动回落**到 `K3S_URL` 的公网 `203.0.113.11:6443`，当前工作正常。若日后出现注册抖动，根治方案：阿里云控制台建**沪杭 VPC 对等连接**走内网，或接受公网回落现状。

## VPC 对等连接打通实录（沪杭跨 VPC · 2026-09-05）

### 背景：哪些地方被跨 VPC 坑过

两机不同 VPC（server 杭州 172.23.174.21 / agent 上海 172.28.89.44），此前全靠公网互联，先后产生 **5 个连锁问题**：

| # | 症状 | 受害链路 |
|---|---|---|
| 1 | 构建 pod clone codeup 报 `Could not resolve host` | pod → 集群 CoreDNS(10.43.0.10) 的跨 VPC overlay 解析超时（见 Jenkins流水线实战.md §1.1/§1.2） |
| 2 | 修完上游 DNS 又复发 | CoreDNS 被 nodeSelector 固定到 server 后，agent 节点 pod 访问它要穿不通的 overlay → 只能给构建 pod 注入 `dnsPolicy: Default` 变通 |
| 3 | 从 server 拉 agent 节点上 pod 的 logs/exec **全 502** | 6443 API 代理到对端 kubelet(10.250) 走内网不通，只能靠诊断 pod 写 `/dev/termination-log` 绕路取证 |
| 4 | k3s-agent 日志每 ~35s 刷 `remotedialer ... 172.23.174.21 timeout` | agent 内置 LB 优先学 server 内网 IP，不通则回落公网 |
| 5 | 公网暴露面大 | 6443 必须对 0.0.0.0/0 开（agent 公网 IP 会变，不敢收紧） |

### 控制台配置过程（用户操作，2026-09-05 晚）

1. 专有网络控制台 → **VPC 对等连接**：创建杭州 VPC ↔ 上海 VPC 的对等连接（同账号，接收端自动通过；跨账号/跨地域需对端确认，状态必须是"已连接"）
2. **关键：对等连接不会自动传播路由**，必须两边各加一条静态路由：
   - 杭州 VPC 路由表：`172.28.0.0/16 → 对等连接`
   - 上海 VPC 路由表：`172.23.0.0/16 → 对等连接`
   - ⚠️ 要挂在 ECS 所在 vSwitch **关联的那张路由表**上（不是随便一张）
3. 安全组入方向放行对端网段（本机默认策略下组内互访规则不覆盖跨 VPC 流量）

**踩坑实录**：首次测试（路由未配）→ 双向 ping/TCP 全灭，agent 侧抓包 SYN 反复重传、server 侧 **0 个包** → 定性"流量在云平台层被丢，OS 路由表指向 VPC 网关没错"；补路由条目后**秒通**。另注意：路由生效瞬间已建立的 TCP 连接（首轮探测的 6443 FAIL）会残留失败，复测要新开连接。

### 打通后验证清单（四层全过）

| 层 | 测试 | 结果 |
|---|---|---|
| ICMP | 宿主机双向 ping | ✅ 0% 丢包；60s×30 包压测 0 丢包，avg 9~11ms / mdev <0.1ms |
| TCP | 22 / 6443 / 10250 双向 | ✅ 全通 |
| k8s 控制面 | server 上 kubectl logs/exec 打 agent 节点 pod（历史必 502） | ✅ 正常拉取 |
| overlay | 跨节点 pod 互通、agent 节点 pod 走 10.43.0.10 解析公网 5 连 | ✅ 12ms / 5/5 OK |

### 打通后的架构变化

**切了内网的**：agent 机 `K3S_URL` 从公网改内网——
```bash
# agent 机：/etc/systemd/system/k3s-agent.service.env（备份：同目录 bak-pubip-*）
K3S_URL="https://172.23.174.21:6443"   # 原 https://203.0.113.11:6443
systemctl restart k3s-agent
```
前提核查：server 6443 证书 SAN **本来就含内网 IP**（`172.23.174.21`），不含公网 IP——切内网反而更"正"，无需重签证书。回切：还原备份 env 文件 + 重启即回。

**切不了内网的（跨云，公网维持）**：Jenkins master 在**腾讯云**（203.0.113.12），不在阿里云 VPC 内——
- Jenkins Cloud serverUrl `https://203.0.113.11:6443`（建 pod）→ 必须公网
- 构建 agent pod 回连 Jenkins `http://203.0.113.12:8080`（WebSocket）→ 必须公网
- ∴ 6443 公网入口**不能关**（Jenkins 命门），但 agent 已不依赖公网 6443，可把入方向从 0.0.0.0/0 **收紧为 203.0.113.12/32 白名单**（安全欠账消一笔，操作前记得先验证）

**受益点归档**：① 集群内部流量（心跳/日志流/pod 创建/overlay）全走内网，不占公网带宽、延迟更稳 ② DNS 元凶（跨 VPC overlay 不通）根治，历史"玄学解析失败"应绝迹（`dnsPolicy: Default` 变通保留不碍事，等需要集群内 service 名时再摘） ③ remotedialer 超时噪音清零（切换后实测） ④ kubectl 运维体验回归正常（502 时代结束）

### 📌 2026-09-13 更新：VPC 对等连接已"退役"（但暂保留，勿急着删）

> 背景：三节点（杭州 server + 上海 agent + 家宽 home-node）全部改走 WireGuard 平面（`10.88.0.0/24`）后，集群数据面已**不再经过 VPC 对等连接**。上面那些"走内网"的受益点，现在转移由 WG 隧道承接。

**实测证据（2026-09-13）**：

| 检查项 | 结果 |
|---|---|
| server → 上海内网 `172.28.89.44` 活跃连接 | **空**（无流量） |
| server → 上海 WG `10.88.0.3:6443` 活跃连接 | 多条 ESTAB（全走 WG） |
| 三台 flannel VTEP | 全部 `local 10.88.0.x dev wg0` |
| `wg0` 流量统计 | RX 1.69MB / TX 4.32MB（持续承载） |

**各服务依赖现状**：

| 服务 | 路径 | 依赖 VPC 对等连接？ |
|---|---|---|
| k3s 注册 / overlay / logs / exec | **WG 隧道** | ❌ 不依赖（实测已搬走） |
| Gitea | 公网 IP | ❌ |
| Jenkins master（腾讯云）→ 6443 | 公网 IP | ❌ |
| **ACR 镜像推送** | **待核实** | ❓ **唯一未知项** |

**ACR 的关键区分（别混为一谈）**：

```
registry-vpc.cn-hangzhou.aliyuncs.com  ← ACR 产品的 VPC 接入点（解析到 100.100.0.10，
                                          走阿里云 100.100.x 内部路由，不经对等连接）
registry.cn-hangzhou.aliyuncs.com      ← 公网端点
```

- 杭州 server 推 `-vpc` 端点：同 VPC，天然通，**与对等连接无关**
- **上海 agent 推 `-vpc` 端点**：跨 VPC → ⚠️ **才依赖对等连接**
- 若推的是公网端点 → 不依赖（但受限速 ~500KB/s）
- ❓ 构建 pod 主要落上海 agent，**下次跑 Jenkins 构建时看一眼 push 用的端点前缀即可定论**

**处置建议（暂不删，风险 > 收益）**：

1. **成本几乎为零**：阿里云同地域 VPC 对等连接免连接费，删了不省钱
2. **ACR 是唯一可能依赖点**，未查实前不动
3. 真清理时的稳妥顺序：**先删两边路由表的对端网段路由**（可秒级回滚）→ 观察一周 → 再删对等连接

**结论：对等连接处于"退役待命"状态——集群不用了，但保留无成本、无副作用。**

## 资源监控栈部署实录（kube-prometheus-stack · 2026-09-06）

> 背景：方案一度是 Jenkins 主控（腾讯云）compose 起 prometheus+grafana，实测主控 1.5G 已用 + swap 962M，塞不下 → 弃；
> 放 k3s server（杭州）？机上已有 frp/apisix/etcd/cloudreve（内存 46%）→ 定案：**集群内 helm 装 kube-prometheus-stack，有状态组件全钉上海 agent 节点**。

### 裁剪方针与资源预算（两台 2C/1.9G 的机器）

| 组件 | 落位 | limits | 关键参数 |
|---|---|---|---|
| prometheus | 1 × 上海 agent | 1C / 512Mi | retention 3d；scrape/eval 60s（默认 30s 翻倍省开销）；10Gi local-path PVC |
| grafana | 1 × 上海 agent | 300m / 224Mi | NodePort **30300**；2Gi 持久化；admin 密码在 values 里（不落文档） |
| operator | 1 × 上海 agent | 300m / 224Mi | webhook 必须保持开（见问题 14） |
| kube-state-metrics | 1 × 上海 agent | 200m / 192Mi | 排除 10 个 collector 降 watch 开销；探针放宽（见问题 15） |
| node-exporter | DaemonSet 双节点各一 | 极轻（~20M/台） | 不设 nodeSelector，主机层 CPU/内存/磁盘 |
| alertmanager | **不装** | — | 无通知渠道可路由，省 ~40M，需要时再开 |

**关掉的东西**：cadvisor（kubelet ServiceMonitor 已覆盖）、kubeControllerManager/Scheduler/Proxy/Etcd 四个控制面 monitor——k3s 这些组件指标监听 127.0.0.1，ServiceMonitor 跨节点根本抓不到，开着只会满屏 red；控制面健康由 apiserver（可抓）+ node-exporter 兜底。

### 部署命令（chart 离线包，不依赖 helm repo 网络）


### 构建 Pod 跨节点调度与节点本地 Docker 缓存（2026-09-06/07 · 超时 ABORTED 事故）

> 完整流水线视角见 Jenkins流水线实战.md §3.5，本节只记集群侧本质。

**现象**：hello-jenkins 构建 #117/#118 连挂（timeout 掐死 ABORTED），#119 同代码 43min 成功、#120 仅 8.4min——**同一份 Jenkinsfile，耗时差一个数量级**。

**集群侧根因**：Jenkins 的 dockerfile agent 走挂进 pod 的 docker.sock（§3.4 定稿的 hostPath workspace 方案），镜像构建完全发生在**节点本地 dockerd**：`debian:latest` 基础镜像 + apt 工具链层（~681MB）的层缓存在各节点 `/var/lib/docker` 里，**不跟着 pod 走、也不跨节点共享**。双节点集群没给构建 pod 配任何调度亲和性，scheduler 随机落点：落到有缓存的节点分钟级完成，落到没缓存的节点重下重打层，仅 apt 下载就要 ~24min（473kB/s），旧 30min timeout 必爆。日志上的硬证据：失败构建 **零 `Using cache`**，成功构建 Step 2/3 `Using cache`。

**本质**：这不是 k3s 故障，是“有状态构建缓存 × 无状态调度”的架构错配——VPC 对等连接打通后集群内部流量已全走内网，但构建冷缓存的瓶颈在节点出公网拉 apt 镜像的带宽，跟集群网络无关，内网化解决不了它。

**缓解（已做）**：pipeline timeout 30→90min（commit 2346778）——能跑通但冷构建仍白烧 ~35min。

**根治选项**：
1. ~~工具链镜像一次构建推仓库~~ **已落地（2026-09-07 晚）**：Dockerfile 定义的工具链镜像一次 `docker build` 推阿里云 ACR（`example-org/hello-jenkins:v0.1`），Linux 腿 agent 改 `docker { image ... registryCredentialsId 'acr-cred' }` 直接拉。push 侧走 `registry-vpc.cn-hangzhou.aliyuncs.com` 内网端点（杭州机实测 2.94GB 仅 5.25min；公网上传被限速 ~500KB/s，curl 401 探测做可达门禁，跨地域节点自动回落公网）；拉取侧注意：走 dockerd（挂 socket），与 containerd/registries.yaml mirror 无关，私有仓凭证由 Jenkins 凭证随 step 下发，无需节点预登录。另：docker 插件同 tag 本地命中不重拉，升级工具链须递增 tag。完整流水线视角见 Jenkins流水线实战.md §3.6。
2. builder pod 加 nodeSelector 钉单节点 → 缓存稳定命中，代价：构建吞吐绑死一台；且 hostPath workspace 同节点共享，同 job 并发构建互踩问题（Jenkins §3.4 副作用）需同步处理 `disableConcurrentBuilds()`；——选项 1 落地后本项不再必需；
3. 内存注意（仍有效）：上海 agent 机 1.9G 已钉 5 个监控 Pod（~724Mi）+ 构建 pod 主要落点；选项 1 后冷构建变冷 pull（杭州→上海 ACR 公网下载约 4.5min），dockerd 解包 3GB 层仍吃磁盘/内存峰值，available 跌破 200Mi 预案触发线监控继续适用（见上节 Grafana sidecar 裁剪预案）。

### 第 7 步 · 收尾 overlay（三节点全上 WG）· ✅ 已完成

**现状与根因**（第 6 步后）：

```
server flannel.1:  local 172.23.174.21 dev eth0   ← VTEP 是内网地址
home-node flannel.1:  local 10.88.0.2     dev wg0    ← 已是 WG

单向半通：home-node→server pod ✅（VXLAN 封装正确打到 10.88.0.1:8472）
          server→home-node pod ❌（server 回包外层源 IP 是 172.23.174.21，home-node 公网不可达）
```

**物理约束**：flannel 是**单 VTEP**——每个节点只能宣告一个 VTEP 地址。server 需同时服务两条腿（↔上海 agent 走 VPC 内网、↔home-node 走 WG），但只有一个 VTEP 地址。**因此必须让整个 overlay 平面统一到同一套网络**——而 home-node 只能用 WG，所以三台都得走 WG。

### 7.3 ⚠️ 问题 12：server FORWARD 链 policy=DROP，peer 间转发被拦


- **现象**：上海 ↔ server 通（各自 ping server），但**上海 ping 不通 home-node**。
- **根因**：WG 是点对点，两个 peer 互通要 server **转发**；而 k3s/kube-router 把 `FORWARD` 链 policy 设为 **DROP**，WG 包（`-i wg0 -o wg0`）被拦下。
- **修法**（插到 FORWARD 首位）：

```bash
iptables -I FORWARD 1 -i wg0 -o wg0 -j ACCEPT
```

- 验证：`上海 → ping 10.88.0.2`（home-node）3/3 ✅，`home-node → ping 10.88.0.3`（上海）3/3 ✅
- 持久化：建议写入 `/etc/wireguard/wg0.conf` 的 `PostUp` 以便重启保留。

### 7.6 启动依赖加固（重启不自乱）

> 问题：`wg-quick down/up` 会短暂拆掉 wg0，而 k3s 的 flannel/apiserver 都绑在它上面 → 集群网络瞬间失联；若 server 重启时 k3s 先于 wg0 启动，flannel 绑不上 wg0 起不来。

```bash
# server：给 k3s.service 加 wg0 启动依赖（/etc/systemd/system/k3s.service 的 [Unit] 段）
[Unit]
...
Wants=network-online.target
Wants=wg-quick@wg0.service
After=network-online.target wg-quick@wg0.service

systemctl daemon-reload
systemctl list-dependencies k3s    # → 应看到 wg-quick@wg0.service
```

- 同时把 FORWARD 放行规则**持久化**进 `wg0.conf`（避免重启丢失）：

```bash
# /etc/wireguard/wg0.conf（server）
PostUp = iptables -I INPUT -p udp --dport 51820 -j ACCEPT; iptables -I FORWARD 1 -i wg0 -o wg0 -j ACCEPT
PostDown = iptables -D INPUT -p udp --dport 51820 -j ACCEPT; iptables -D FORWARD -i wg0 -o wg0 -j ACCEPT
```

- ⚠️ **运维提醒**：以后改 wg0 配置**别用 `wg-quick down/up`**（会震集群），用 `wg syncconf wg0 <(wg-quick strip wg0)` 在线生效。

### 问题 1：国内 k3s 镜像源已死

| 源 | 状态 |
|---|---|
| `rancher-mirror.rancher.cn` | ❌ DNS→`169.254.254.254`（阿里 CDN 下线占位）→ 脚本静默失败 |

| `get.k3s.io` | ✅ 200 |
| GitHub 直连 | ✅ 1.96 MB/s |
| DaoCloud 镜像 | ✅ 存活 |

**修正**：去掉 `INSTALL_K3S_MIRROR=cn`，直接用 `get.k3s.io` + GitHub；`registries.yaml`（DaoCloud）仍必要。

### 问题 3：token "not authorized"

`{ echo "K3S_URL=..."; cat /tmp/.tokenv; }` 生成的 env 里 token **带引号且内嵌换行** → systemd EnvironmentFile 解析坏 → agent 报 `not authorized`（server 日志 `HTTP/2.0 401` = 网络/TLS 全通，纯认证问题）。
**修法**：取 `node-token` 权威值，写**单行无引号**。

### 问题 6：⚠️ 502 的隐藏层——`egress-selector-mode=agent`（k3s v1.36 默认）

- **现象**：WG 通了、`curl -sk https://10.88.0.2:10250/healthz` → **401**（kubelet 正常应答），但 `kubectl logs/exec` 仍 502。
- **根因**：k3s 默认让 apiserver **不直连 kubelet**，而是走 agent 的 remotedialer 隧道代理；节点已可直连时，这层反而成为累赘。
- **判定法**：**直连 10250 得 401、经 `127.0.0.1:6443` HTTP CONNECT 代理得 502** → 就是这层。
- **解决**：server 加 `--egress-selector-mode=disabled`，日志打 `Tunnel server egress proxy mode: disabled`。

### 问题 7：改 `node-ip` 不刷新 Node 对象

`k3s.io/internal-ip` 注解变了，但 `kubectl get nodes` 的 INTERNAL-IP 仍是旧值 → 必须 `kubectl delete node` + 重启 agent 强制重注册。

### 问题 8：flannel 端点不跟 `node-ip` 走

`flannel.alpha.coreos.com/public-ip` 不会自动更新（仍指家宽私网）。修法：① `kubectl annotate node home-node flannel.alpha.coreos.com/public-ip=10.88.0.2 --overwrite`（仅注解，进程未必重建）；② **`--flannel-iface=wg0`（推荐）** → 重启后 `flannel.1 local 10.88.0.2 dev wg0`，MTU 自动降 1370。

### 问题 9：apt 后台事务拖住 SSH 会话

server 上 apt 可能卡在 `needrestart`，让安装命令长时间不回；`dpkg --configure -a` 可能报 lock。用 `pgrep -x apt-get` 轮询等它跑完即可。

### 问题 10：验证三连教训（`curl -sfL | sh` 的 exit 0 不可信）

`curl -sfL | sh` 的 exit 0 **不可信**（`-sf` + 管道吞掉失败退出码）→ 必须落地验文件存在性（`test -s`）。scp 传 token 中间文件易丢，靠断言兜底。

### 问题 11：国内 WG 端口风险

UDP 51820 可能被云厂商/运营商 QoS，握手不上就换 **UDP 443**（长得像 QUIC）；阿里云**安全组**要放行 UDP 51820（光 ufw/iptables 不够）。

### 问题 12：server `FORWARD` 链 policy=DROP 拦 WG peer 间转发

见第 7.3 节（重复条目，正文以第 7.3 节为准）。要点：WG 全 mesh 需要 server 转发 peer 之间的包，而 k3s/kube-router 把 `FORWARD` 设为 DROP → 必须 `iptables -I FORWARD 1 -i wg0 -o wg0 -j ACCEPT`。

### 问题 13：改 flannel-iface 要认 unit 格式

k3s 的 systemd unit 可能是一行式（`ExecStart=/usr/local/bin/k3s agent`）或多行续行式（`agent \\` 换行）。adopt `sed` 追加参数时要按实际格式写，先用 `sed -n "/ExecStart=/,/^$/p"` 看清楚。

### 问题 14：关 admissionWebhooks → operator 永久 ContainerCreating

**现象**：`admissionWebhooks.enabled=false` 后 operator Pod 卡住，引用一个永远不存在的证书 secret。

**根因**：kube-prometheus-stack 89.x 里即使关掉 webhook，operator 的 Deployment **仍挂载** webhook patch Job 生成的 tls-secret；把 Job 关了 → 没人建 secret → operator 起不来。"关功能"≠"不留产物引用"。

```yaml
prometheusOperator:

    enabled: true
    patch:

        registry: quay.m.daocloud.io
        repository: jetstack/kube-webhook-certgen
        tag: "v1.5.5"
```

**教训**：Helm chart 关功能前，先 grep 模板确认该功能是否被别处引用（这里 secret 由 patch Job 生成，被 operator 挂载依赖）。

### 问题 15：server 卡顿风暴误杀 kube-state-metrics（探针默认值太脆）

**现象**：ksm CrashLoopBackOff（exit 2），日志末行 `Failed to contact API server for /livez: got 0`。

**根因**：部署当晚杭州 server 一波 swap 风暴把 API server 拖到响应缓慢（集群层面 NodeNotReady + http2 connection lost 同窗出现），ksm 默认探针 `timeout=5s / failureThreshold=3` 直接判死。同一场抖动造成 grafana ×16、node-exporter ×13 次重启，网络恢复后全部自愈。

**修法**：values 里放宽 `livenessProbe: timeout 15s / period 20s / failureThreshold 5`。

**教训**：小集群里单节点 IO 卡顿的爆炸半径会被"默认探针"放大成组件集体重启，有状态组件的探针值要在 values 阶段就按弱机放宽。

### 问题 16：kube-state-metrics 探针韧性（问题 15 的长期复现 · 2026-09-27）

**现象**：`kps-kube-state-metrics` 长期 `CrashLoopBackOff`，`restartCount` 已达 **1901 次 / 13 天**，exit code 2。

**根因**（与问题 15 同源，但这次是**持续发作**而非一次性风暴）：该 Pod 钉在 **home-node（家宽节点）**；探针 `liveness: timeout=5s / period=10s / failureThreshold=3`。家宽链路 + 弱机偶发响应慢，`/livez` 超过 5s 没回 → kubelet 判死重启。kubelet 事件原话：`Liveness probe failed: Get "http://10.42.2.24:8080/livez": context deadline exceeded`。

**排除项**（避免误判）：
- RBAC 正常：`kubectl auth can-i list pods --as=system:serviceaccount:monitoring:kps-kube-state-metrics -A` → yes
- 端口正常：手动 port-forward 后 `/livez`(8080) / `/readyz`(8081) 均 200
- 按 deploy 规格手动复跑 Pod → **不复现崩溃** → 推翻"镜像/配置/RBAC"假设，锁定探针

**修法**（正是问题 15 早写好的方案，只是**从没落到这套环境上**）：
```bash
kubectl -n monitoring patch deploy kps-kube-state-metrics --type=strategic -p \
  '{"spec":{"template":{"spec":{"containers":[{"name":"kube-state-metrics",
   "livenessProbe":{"timeoutSeconds":15,"periodSeconds":20,"failureThreshold":5},
   "readinessProbe":{"timeoutSeconds":10,"periodSeconds":20,"failureThreshold":5}}]}}}}'
```
验收：新 Pod `restartCount=0`，ksm target **UP**，Prometheus targets 21/21。

**关键认知**：
1. **这套监控栈是 `helm template + kubectl apply` 管的，无 helm release**（`helm status kps` = *release not found*）→ values 里改了探针**不会自动生效**，必须原生 `kubectl patch deploy`；patch 后也不会被任何 helm 覆盖。
2. "问题 15 已修复"≠"线上已修复"——**修复方案写在文档里、没落到实际环境，等于没修**。文档修法要跟上实际 apply。

### 问题 17：杭州 server 内存耗尽 → 用户态整体卡死（脱管 5 天才发现 · 2026-09-27）

**现象**（最迷惑人的一次故障）：`203.0.113.11` 客观"半死"——

| 层 | 探测 | 结果 |
|---|---|---|
| 内核 | `ping` | ✅ 9.7ms 通 |
| 内核 | TCP 22 三次握手 | ✅ 能建立 |
| 用户态 | 读 SSH banner | ❌ 永远读不到（`Connection timed out during banner exchange`）|
| 用户态 | k3s API `6443` | ❌ 不通 |
| 内核 | NodePort 30080/30090/30300 | ✅ 秒回 200 |

**读法**：**内核活着（ICMP/TCP握手/iptables DNAT 全正常），用户态进程（sshd / k3s / APISIX 容器）整体卡死**。NodePort 还能用是因为它走**内核态 DNAT** 直达 home-node 上的 Pod，不经杭州用户态。

**发现路径**（关键：从监控反查，而非从 SSH）——SSH/6443 死时，用仍存活的 **Grafana(30300) → Prometheus → Alertmanager** 代理链取证：
```promql
up{instance="10.88.0.1:9100"}   # 历史序列：09-22 22:37 UTC → 0（此前一直是 1）
```
→ 结合 memory 里 09-23 06:49 CST 那条被当成"部署期暂态"忽略的 `promtail ... TLS handshake timeout (Count 481)` → **脱管起点 = 北京时间 09-23 06:37**，已 5 天。

**死前最后水位**（09-22 22:08 UTC，Prometheus 留有数据）：
- 内存可用 **453MB / 1787MB（用 ~75%）** ← 吃紧
- 根盘 19.33G/41.88G（56%，**不紧张**）
- load1 0.08（**不是负载**）→ 死因指向**内存耗尽 thrashing**

**根因**：2C/1.9G 小机同时扛 **k3s server + 原生 docker 全家桶**（apisix / etcd / apisix-dashboard / cloudreve / frp）→ 内存耗尽，用户态进程全部失去响应（内核仍在服务中断/转发）。

**救法（唯一路径）**：SSH 进不去、本机无阿里云 AK → **只能去阿里云控制台 VNC 登录 / 重启实例**。重启后：SSH banner 恢复、6443 通、三节点全 Ready、targets 21/21、全部 Pod 自愈（无需人工）。

**关键认知**：
1. **"TCP 能连"骗人**——`/dev/tcp` 探端口能成功只说明内核栈在应答，**不代表服务进程活着**。判活要看**应用层响应**（SSH banner / HTTP 体），不是握手成功。
2. **NodePort 能访问 ≠ 节点健康**——它绕过了宿主机用户态，恰恰是最容易误导的信号。
3. **监控栈钉在 home-node 反而救了这次**：控制面（杭州）死了，监控面（家宽）还活 → 正是靠它反查出 5 天的脱管窗口。**控制面与监控面物理分离，是事故可观测性的关键。**
4. **教训的教训**：09-23 那条 promtail 报错被当"暂态"放过，代价是 5 天无人知。**"看起来像噪声"的持续性报错，要交叉验证是不是真故障。**
5. 已加 `NodeMemoryAvailableLow/Critical` 告警规则（见 `07-Alertmanager告警出口接入实战.md`）堵同类风险。

### 问题 18：node-exporter 探针裸奔 + KSM 探针二次收紧（问题 15/16 的续集 · 2026-10-20）

**现象**（例行巡检发现，非告警触发）：`kps-kube-state-metrics` restarts=**853**、`kps-prometheus-node-exporter-9l7vw`（杭州节点）restarts=**284**。两者当前均 `1/1 Running`（已过发作期），但重启计数高得离谱。

**根因（一条主线，两个病灶）——都是「探针超时 → kubelet 杀容器 → 重启」，非 OOM、非 panic：**

| Pod | 节点 | 最后退出码 | 病灶 |
|---|---|---|---|
| node-exporter `9l7vw` | 杭州 `i-xxxxxxxx0001` | **143（SIGTERM）** | liveness `timeout=1s / period=10s / failureThreshold=3`——杭州内存紧（free 仅 17Mi、load 2.6）→ 探针 1s 内回不来 → kubelet 直接 SIGTERM |
| kube-state-metrics `k8b8m` | home-node | **2** | 最后一次重启停在 10-18 09:18；kubelet 日志同一窗口刷 `Slow SQL … duration=5~12s`（kine/SQLite）+ `http2: client connection lost` + 末行 `Failed to contact API server for /livez: got 0` → `/livez` 连不上 API server 判死 |

**为什么问题 15/16「修过了」还复现：**
- 问题 15/16 只 patch 了 **KSM**，**node-exporter 的 liveness 从没动过**——还是 chart 默认的 `timeout=1s`。今天是它第一次被翻出来（284 次）。**同类默认值要一次全扫，别只修报出来的那一个。**
- KSM 的探针虽已放宽到 `timeout=15s`，但**根因（kine 慢 + 杭州内存紧）没除**，10-18 一次抖动又攒了一波；且 KSM 带 `limits.cpu=200m`，CPU 限本身会拖慢探针。

**修法（2026-10-20 已落地，原生 patch）：**
```bash
# ① node-exporter（DaemonSet）——删 liveness（DS 本不需要）+ 放宽 readiness
kubectl -n monitoring patch ds kps-prometheus-node-exporter --type=json -p '[\
 {"op":"remove","path":"/spec/template/spec/containers/0/livenessProbe"},\
 {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe","value":{"httpGet":{"path":"/","port":"http-metrics","scheme":"HTTP"},"initialDelaySeconds":10,"periodSeconds":15,"timeoutSeconds":5,"failureThreshold":6,"successThreshold":1}}]'

# ② KSM（Deployment）——探针再放宽 + 去掉 CPU limit（保内存 limit 512Mi）
kubectl -n monitoring patch deploy kps-kube-state-metrics --type=json -p '[\
 {"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe","value":{"httpGet":{"path":"/livez","port":"http","scheme":"HTTP"},"initialDelaySeconds":30,"periodSeconds":30,"timeoutSeconds":25,"failureThreshold":6,"successThreshold":1}},\
 {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe","value":{"httpGet":{"path":"/readyz","port":"metrics","scheme":"HTTP"},"initialDelaySeconds":15,"periodSeconds":30,"timeoutSeconds":20,"failureThreshold":6,"successThreshold":1}},\
 {"op":"replace","path":"/spec/template/spec/containers/0/resources","value":{"requests":{"cpu":"50m","memory":"128Mi"},"limits":{"memory":"512Mi"}}}]'
```

**验收**：两边 rollout 均成功；三个 node-exporter（杭州/上海/home-node）+ KSM 全新 Pod `restartCount=0`，事件流只剩 `Created/Started`，之前的 `Liveness probe failed … context deadline exceeded` 刷屏停止。

**关键认知**：
1. **探针放宽是止血，不是治本。** 杭州内存仍紧（free 17Mi）、kine(SQLite) 仍慢。治本 = 给杭州减负/加内存，或换 datastore。
2. **问题 15/16 只修了 KSM，node-exporter 的 1s 探针一直裸奔** —— 「方案写了/只改了一个」≠「全环境已修」。改完一个组件后要横向扫同类默认值。
3. 这套栈仍是 **helm template + kubectl apply 管理（无 helm release）**，patch 不会被任何 helm 覆盖（延续问题 16 认知）。
4. 小机器上 **「默认探针值」是系统性风险** —— 问题 15/16/17/18 同源，都是弱机 + 默认探针被放大成组件集体重启。

### 问题 19：杭州 server「每日 06:40 定时」复发 —— 磁盘 IO 被打满 → 整机 thrash（2026-10-21 / 22 / 23 连发三晨）

**现象**：连续三天同一症状、同一时段复发（**北京时间 06:37~06:57**），与问题 17 同型（内核活、用户态全卡死）：

| 时刻（北京） | 事件 |
|---|---|
| 10-21 06:57 | 首次复发（此前后台平稳） |
| 10-22 06:37 | 第二次（06:37 掉，07:01 闪回 1 分钟又掉） |
| 10-23 06:37 | 第三次（08:08 人工重启恢复） |

- 内核层全活：`ping` 12ms 通、TCP 22/6443/10250 三次握手成功、WG 握手正常
- 用户态全卡：SSH 卡在 **banner 交换**（`Connection timed out during banner exchange`）、`6443` TCP 通但 **TLS 永不返回**（curl `000`）、`10250` 同
- 上海 agent 视角：对 `10.88.0.1:6443` 一堆 `ESTAB` + 不断 `SYN-SENT` 重连 → 连不上控制面
- 告警齐响：`KubeAPIInstanceUnreachable{6443}`、`KubeletInstanceUnreachable×3`、`NodeDiskIOSaturation{杭州}`、`NodeSystemSaturation`、`TargetDown`

**关键**：NodePort（30080/30090/30002）**秒回 200** —— 它走内核态 DNAT 直达 home-node 上的 Pod，不经杭州用户态（与问题 17 认知一致）。

**根因（这次进机实测坐实）——不是磁盘坏，是磁盘 IO 被工作负载打满**：

1. **磁盘本身健康**：`dmesg` **无任何** `I/O error / EXT4-fs error / 坏道 / SMART 告警`；`vda` 40G 用 56%（剩 17G，不紧张）。
2. **但 IO 被榨干**（Prometheus 实测）：`vda` IO util **~90%**、持续读 **~100 MB/s**（写仅 ~285 KB/s）、读 IOPS ~533、**队列深度 ~26**、iowait **70~80%**、`node_procs_blocked` **11**（D 态）、load1 15、MemAvailable 从 625MB 断崖到 344MB。
3. **每日定额触发器（撞在崩溃窗口上）**：
   - `apt-daily-upgrade.timer` **每天 06:35** → unattended-upgrades 升 `ca-certificates/git-man/liblzma5/libnss3/tzdata/xz-utils`，dpkg 写盘 + fsync
   - `man-db.timer` **06:53** → mandb 全量重扫（重随机读）
4. **k3s kine = 单文件 SQLite**：`state.db` 12MB + WAL 11MB；日志实锤 `Slow SQL … INSERT … duration=2.7s / 7.9s`（**写一条要 8 秒**）；崩溃中自身日志刷 `client-side throttling … Waited before sending request delay=2m55s`（连自己 `127.0.0.1:6444` 都要等近 3 分钟）。
5. **同机还压着 APISIX + etcd（bitnami）+ dashboard + Cloudreve + frp**：etcd 是 fsync 大户，全部抢同一块系统盘。
6. **`vm.swappiness=0`**：2G swap 完全不用 → 内存一紧内核宁可 CPU 疯狂回收也不换页 → thrash 加剧（PSI memory waiting 极高）。
7. 附加噪音：snapd 反复 watchdog 超时 / `Failed to start Snap Daemon`；APISIX 容器 restart loop（`nginx: [emerg] bind() to unix:/usr/local/apisix/conf/config_listen.sock failed (98: Address already in use)` 残留 socket）。

**为什么是「每天同一钟点」而不是「随运行时长」**：三次崩溃都落在 06:37~06:57，正是 apt/man-db 定时任务窗口 → 崩溃**由每日定额负载触发**，与 uptime 无关。

**进机路径（本机直连杭州 sshd 卡 banner 时）**：
```bash
# 本机 → 上海(可直连) → WG 内网 → 杭州
ssh root@203.0.113.13        # 上海 agent（可直连）
  ssh root@10.88.0.1          # 杭州 server（走 WG 平面）
```

**修法（2026-10-23 已全部落地，低风险优先）**：

```bash
# ① 每日崩溃触发器：apt 类定时任务挪到凌晨空闲段（drop-in 覆盖，保留启用以维持安全更新）
mkdir -p /etc/systemd/system/apt-daily.timer.d
cat > /etc/systemd/system/apt-daily.timer.d/override.conf <<'EOF'
[Timer]
OnCalendar=
OnCalendar=*-*-* 04:00:00
RandomizedDelaySec=30m
Persistent=false
EOF
# 同法：apt-daily-upgrade.timer → 04:30；man-db.timer → 04:15
systemctl daemon-reload
# 实测已从 06:35 改到 04:11/04:22/04:38（16h 后）

# ② 内核参数：swappiness 0→20 + 收紧 dirty（先找真凶）
#    ⚠️ /etc/sysctl.conf 第 1 行硬编码了 vm.swappiness = 0，会覆盖 /etc/sysctl.d/；
#       且 tuned(active=virtual-guest, dynamic_tuning=1) 也在动态托管 → 必须三处一起改
sed -i 's/^\s*vm\.swappiness\s*=\s*0/vm.swappiness = 20/' /etc/sysctl.conf
cat > /etc/sysctl.d/99-hz-io-tuning.conf <<'EOF'
vm.swappiness = 20
vm.dirty_background_ratio = 5
vm.dirty_ratio = 15
EOF
# tuned 也用同值 profile 固化（dynamic_tuning=0，避免被动态改回）
mkdir -p /etc/tuned/hz-io
cat > /etc/tuned/hz-io/tuned.conf <<'EOF'
[main]
include=virtual-guest
[sysctl]
vm.swappiness=20
vm.dirty_background_ratio=5
vm.dirty_ratio=15
EOF
tuned-adm profile hz-io
sysctl --system

# ③ earlyoom（内存-critical 时提前杀大户，防整机 thrash）
apt-get install -y earlyoom && systemctl enable --now earlyoom
```

**验收**：
- timers：`apt-daily 04:11 / man-db 04:22 / apt-daily-upgrade 04:38`（北京，从 06:3x 挪走）✅
- `sysctl vm.swappiness=20 / dirty_background_ratio=5 / dirty_ratio=15`（三处持久化，重启不回退）✅
- `systemctl is-active earlyoom` = `active` ✅

**待办（治本，未做）**：
- **APISIX + etcd 迁走**（按 `05-APISIX迁移k3s方案`）—— etcd 是 fsync 大户，别跟 k3s server 同机
- 卸无用的 snap（lxd/snapd）；修 APISIX 残留 socket 导致的 restart loop
- 治 k3s kine(SQLite) 慢：备份/优化 datastore，或小机升配（1.7G/2C 扛 k3s + APISIX 全家桶已超载）
- 补告警：**iowait / 磁盘读速率 / 磁盘饱和度**（现有 `NodeMemoryAvailable*` 在本次 320MB 未触发）

**关键认知**：
1. **「磁盘满」和「磁盘 IO 打满」是两回事** —— 本机盘还剩 17G，但 IO util 90% + 队列深度 26 照样把整机拖死。看 `%util / iowait / procs_blocked / await`，不是只看 `df`。
2. **「每天同一钟点复发」要往定时任务上想** —— 三次都卡 06:3x~06:5x，apt/man-db 是头号嫌疑。这类系统定额负载在小磁盘上就是雪崩扳机。
3. **`vm.swappiness=0` 是弱机毒药** —— swap 空着不用，内存一紧就 CPU 疯狂回收 → thrash。**且该值可能被 `/etc/sysctl.conf` 硬编码 + tuned 双重托管**，改之前先 `grep -rn swappiness /etc` 找全源头。
4. **管控面（杭州）单点 + 超载是系统性风险** —— 问题 17（内存）→ 问题 19（IO）同机复发，本质都是「1.7G/2C 小机扛了不该它扛的东西」。减负比调参重要。

## 装前事故档案（装机前的历史遗留，不占 1~15 编号）

> 这两件事发生在装 k3s **之前**，属于"顺手修掉的旧账"，不是 k3s 部署踩的坑，故单独归档。流程见第一部分「装前修复与清理」。

### A1 · docker CLI 29 vs daemon 24 版本断裂

**现象**：
```
docker ps → Error response from daemon: client version 1.52 is too new.
Maximum supported API version is 1.43
```

**根因**（典型 apt 自动升级事故）：
- 运行中的 dockerd 是 **24.0.5**（2024 年启动至今没重启）
- 今年 4 月 `unattended-upgrades` 把 docker.io 包升到了 **29.1.3**，只换了磁盘上的二进制，服务没重启
- → 新 CLI(29, API 1.52) 连老 daemon(24, API 1.43)，超出版本协商窗口

**修法**（评估过三条，采用第三个）：
| 方案 | 影响 |
|---|---|
| 降级 CLI（apt 装回 24.x） | 零中断，但会被下次 apt upgrade 又升上去 |
| 环境变量兜底（`DOCKER_API_VERSION=1.43`） | 治标不治本 |
| **`systemctl restart docker`（采用）** | daemon 升 29 对齐 CLI；⚠️ Live Restore=false，全部容器重启中断约 15 秒 |

**执行前预检（关键动作）**：先查 5 个业务容器 `restart=always`、compose 项目位置、内存余量，确认"重启后会自动回来"才动手。
**结果**：CLI 29.1.3 = Server 29.1.3，全容器自动拉起，Cloudreve HTTP 200 验证通过。

**教训**：
- 长期不重启的机器 + unattended-upgrades = 二进制与进程版本漂移，`/var/run/reboot-required` 和 `docker version` 要定期看
- docker 建议开 live-restore（`/etc/docker/daemon.json` 加 `"live-restore": true`），以后 restart docker 不杀容器（本次未开，留作待办）

### A2 · 废弃 Halo 的 OOM 教训

**现象**：Halo 容器 2025-10-26 被杀（Exit 137 = SIGKILL）；容器内 `OOMKilled=false` 但实为**宿主机级 OOM** 杀进程——1.7G 内存跑 Java 应用必然踩雷。
`restart=no` 且不在任何 compose 里（当年手动 `docker run`），10 个月无人发现无人管。

**修法**：`docker rm halo` + 删 `/root/.halo2`(5.1M) + 删 `/root/halo.tar`(430M) + `docker rmi`(445M)，共回收约 1.2G。
**由此决定先加 swap 再装 k3s**：2G swapfile + fstab 持久化 + `vm.swappiness 0→10`（原值 0 意味着内存满之前宁死不换页，OOM 的直接放大器）。

**教训**：小内存机器跑 JVM 应用必须配 swap；游离的手工容器（不在 compose/编排里）是定时炸弹，定期 `docker ps -a` 盘一遍。

### 为什么没走 Helm（血泪）
- 两台节点均 2C/1.9G。**server 内存不足 → apiserver 频繁 `net/http: TLS handshake timeout`**（kubectl 偶发、**helm 必爆**——helm 多步事务任一 API 调用超时就整体失败）。cloudreve 释放过一轮、Prometheus 停后缓解，但 helm 依旧不稳

| Service×2 | `gitea-http` / `gitea-ssh` | NodePort 3000:**30080** / 22:**30222** |

- 数据实际落盘：**上海节点宿主** `/var/lib/rancher/k3s/storage/pvc-<pv>_gitea_gitea-data/`（含 `git/`、`gitea/`(库+`gitea.db`)、`ssh/`）——local-path 单节点本地盘，不跨节点
- 页面 `http://203.0.113.13:30080`，首次 Web 向导建管理员后再 `kubectl apply` 即可用

### 踩坑
- **NodePort 30080 被占**：default 里 9-04 部署的 `nginx-demo-np` svc 占着 → `kubectl delete svc nginx-demo-np -n default` 释放后 `gitea-http`（nodePort 30080）才建得上
- helm 卸载反复 API 超时失败 → 手工程序化删除：`kubectl delete deploy gitea -n gitea` + `kubectl delete ns gitea`（连带 PVC/svc/rs/cm 全清，helm release 记录随 ns 消失）

## Halo 部署实战（首个业务应用上 k3s · 2026-09-22）

> 背景：Halo 流水线打通并产出运行镜像后（见 `Jenkins流水线实战.md` §11），把 **Halo 作为首个真实业务应用部署到 k3s**，落在**家宽 Lenovo 节点**。
> 交付链路：`git push → Jenkins 构建 → 运行镜像推 ACR → k8s 拉镜像起 Pod → APISIX 域名入口`（APISIX 部分见 `05-APISIX迁移k3s方案.md`）。

### 一、部署 YAML（`/root/halo-ci/k8s-halo-home-node.yaml`）

| Kind | 名称 | 要点 |
|---|---|---|
| Namespace | `halo` | 隔离 |
| PVC | `halo-data` | 10Gi · local-path · RWO（Halo 工作目录 `/root/.halo2`）|
| Deployment | `halo` | 镜像 `registry.cn-hangzhou.aliyuncs.com/example-org/halo:latest` · **nodeSelector 钉 home-node** · `strategy: Recreate` · 副本 1 |
| Service | `halo` | NodePort 8090:**30090** |

**关键配置与理由**：
- **`nodeSelector: {kubernetes.io/hostname: home-node}`** —— 固定调度到 Lenovo（家宽算力机）
- **`strategy: Recreate`** —— local-path 是 **RWO 卷**，滚动更新会卡（两个 Pod 抢同一块盘），必须 Recreate
- **`JVM_OPTS: -Xms256m -Xmx768m -XX:+UseSerialGC`** —— Lenovo 内存已用 ~50%，小规格 + SerialGC 省内存
- **资源**：`requests 200m/512Mi`、`limits 1/1Gi`
- **`startupProbe.failureThreshold: 30`** —— 首启初始化慢（要建库、装默认主题），给足 5 分钟
- **健康检查**：`/actuator/health/readiness` + `/actuator/health/liveness`

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: halo
  namespace: halo
spec:
  replicas: 1
  strategy: { type: Recreate }
  selector: { matchLabels: { app: halo } }
  template:
    metadata: { labels: { app: halo } }
    spec:
      nodeSelector: { kubernetes.io/hostname: home-node }
      containers:
        - name: halo
          image: registry.cn-hangzhou.aliyuncs.com/example-org/halo:latest
          imagePullPolicy: Always
          ports: [{ name: http, containerPort: 8090 }]
          env:
            - { name: JVM_OPTS, value: "-Xms256m -Xmx768m -XX:+UseSerialGC" }
            - { name: HALO_WORK_DIR, value: "/root/.halo2" }
            - { name: TZ, value: "Asia/Shanghai" }
          volumeMounts:
            - { name: halo-data, mountPath: /root/.halo2 }
          resources:
            requests: { cpu: "200m", memory: "512Mi" }
            limits:   { cpu: "1",    memory: "1Gi" }
          startupProbe:
            httpGet: { path: /actuator/health/readiness, port: 8090 }
            failureThreshold: 30
            periodSeconds: 10
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8090 }
          livenessProbe:
            httpGet: { path: /actuator/health/liveness, port: 8090 }
      volumes:
        - name: halo-data
          persistentVolumeClaim: { claimName: halo-data }
```

### 二、私有镜像拉取（k3s 复用 containerd 凭证）

- ACR 是**私有仓**，但 **k3s 三节点 containerd 已在 `/etc/rancher/k3s/registries.yaml` 配好 auth**（username `<ACR_USER>`）→ **无需 imagePullSecret**，Pod 直接拉
- 验证：`k3s crictl pull registry.cn-hangzhou.aliyuncs.com/example-org/halo:latest`

```yaml
# /etc/rancher/k3s/registries.yaml (三节点均配)
configs:
  "registry.cn-hangzhou.aliyuncs.com":
    auth:
      username: "<ACR_USER>"
      password: "***"
```

### 四、关键认知

**1. k3s 的 NodePort 在全部节点生效**
- Pod 跑在 Lenovo（家宽无公网 IP），但**杭州/上海两大公网节点的 30090 都能访问到 Pod**（k3s iptables/ipvs 规则天然效果）→ 家宽节点上的服务**天然借道云节点暴露**
- 实测：`http://203.0.113.11:30090/actuator/health/readiness` → `{"status":"UP"}`

**2. 数据库 = H2 嵌入式（文件模式）**
- Halo 2.x 默认 **H2 嵌入式数据库**（R2DBC 驱动），文件 `/root/.halo2/db/halo-next.mv.db`（`.mv.db` = H2 MVStore 格式）
- **零运维**：不用起 MySQL/PG；随 Pod 走（挂 PVC）
- ⚠️ **嵌入式单写** → 不适合多副本（与 RWO 卷一致）
- 换库：设 `SPRING_R2DBC_URL= r2dbc:pool:postgresql://...` 等环境变量即可切 PG/MySQL

**3. 单副本而非高可用**
- 存储 `local-path` + `RWO` → 同刻只能一 Pod 挂载，多副本会抢盘
- 家宽单机 → 多副本也只在一台，无 HA 意义
- 个人博客单副本足够；要 HA 需换 **RWX 共享存储**（NFS/Longhorn）+ 去 nodeSelector
