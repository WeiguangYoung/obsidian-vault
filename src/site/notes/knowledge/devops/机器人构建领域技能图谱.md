# 机器人 / 具身智能「构建领域」技能图谱

> 机器人赛道的 Build Engineer，跟通用 CI/CD 有约 70% 重叠，剩下 30% 是**行业特有的硬骨头**。
> 本文按「构建领域」视角梳理这 30%，作为求职对照表与补课清单。
> 配套训练计划见 [[knowledge/devops/ROS2具身智能CI实战\|ROS2 + 具身智能 CI 实战]]。

## 为什么机器人构建特殊

通用 CI/CD 面对的是「一门语言 + 一个平台」；机器人项目面对的是：

| 维度 | 通用 CI/CD | 机器人 / 具身智能 |
|:----|:----|:----|
| 语言 | 1~2 种 | C++ / Python 混合，多包仓库 |
| 构建工具 | Maven / Gradle / npm | **colcon + ament**（ROS2）、CMake、Bazel |
| 目标平台 | x86（偶尔 ARM） | **x86 + ARM64（Jetson/RK3588）交叉编译** |
| 测试 | 单元 / 集成 | **仿真回归**（物理世界）+ HIL 真机 |
| 产物 | jar / 镜像 | 镜像 + **deb 包** + 模型文件（ONNX/TensorRT） |
| 门禁 | 测试通过率 | **物理指标**：碰撞数、任务耗时、端到端延迟 |

一句话：**机器人的构建，要同时处理"代码"和"物理世界"。**

## 一、ROS2 构建体系（最核心的行业分水岭）

这是机器人 Build Engineer 与普通 CI 工程师最明显的分界线。

### colcon + ament

- **colcon**：ROS2 的构建工具（colcon = collective construction），逐包并行构建。
- **ament**：构建系统，两种包类型：
  - `ament_cmake`（C/C++ 包）
  - `ament_python`（纯 Python 包）
- **`package.xml`**：依赖声明（`build_depend` / `exec_depend` / `test_depend`）。
- **underlay / overlay**：
  - **underlay** = 装好的 ROS 发行版（如 `/opt/ros/humble`）
  - **overlay** = 你自己的工作空间（`source install/setup.bash` 叠加）
  - 层层叠加，是 ROS 工作空间的核心心智模型。

### 关键构建选项

```bash
colcon build --merge-install            # 所有包装到同一前缀（部署友好）
colcon build --symlink-install          # Python 用软链，改代码免重装（开发友好）
colcon build --packages-select pkg_a    # 只编指定包（增量）
colcon build --parallel-workers 8       # 并行度
```

- **per-package 增量构建**：ROS2 项目动辄数百包，**全量重编是灾难**，增量和缓存是效率命门。
- **ccache**：C/C++ 重编加速的标配，CI 里必须挂缓存。

### 依赖管理

- **rosdep**：跨平台依赖自动解析（`rosdep install --from-paths src --ignore-src -y`）——ROS 世界的 apt/pip 门面。
- **vcstool（vcs）**：批量拉取多仓库（`.repos` 文件）——大型机器人项目的多仓管理标配。

### 质量工具（天然接门禁）

- **ament_lint_auto**：一行批处理 lint。
- **flake8 / pep257 / uncrustify / cpplint / cppcheck**：ROS2 内置规范检查，天然是质量门禁的输入。

### ROS1 遗留

老机器人项目还在用 **catkin**（`catkin_make` / `catkin build`）——面试可能被问 ROS1 vs ROS2 构建差异。

## 二、多架构交叉编译（机器人硬件碎片化的必然）

机器人本体上的算力板五花八门，**交叉编译是刚需**。

### 目标平台

| 平台 | 典型场景 | 难点 |
|:----|:----|:----|
| **x86_64** | 工控机 / 服务器 | 常规 |
| **ARM64 / aarch64** | **Jetson（Orin/Xavier）、RK3588、树莓派** | 交叉工具链 + sysroot |
| ARM32 | 老嵌入式控制器 | 工具链老旧 |

### Jetson 特有问题

- **JetPack / L4T**：NVIDIA 的定制 Ubuntu，**CUDA / cuDNN / TensorRT 版本与 L4T 强绑定**。
- **aarch64 交叉编译**：需要 aarch64 工具链 + **sysroot**（含目标平台的 `.so`、头文件）。
- **本地编译 vs 交叉编译**：Jetson 本机编译慢但省心；交叉编译快但配置复杂，多数团队折中（交叉 + 少量真机验证）。

### CI 里做多架构

- **`docker buildx`**：多平台镜像构建（`--platform linux/amd64,linux/arm64`）。
- **QEMU / binfmt**：在 x86 上模拟 ARM 跑构建 —— **慢，适合轻量任务**，重编译不划算。
- **原生 ARM runner**：快，但需要真机（树莓派 / Jetson 做 runner）——**device farm** 的雏形。
- **CMake toolchain file**：交叉编译配置核心：
  ```cmake
  set(CMAKE_SYSTEM_NAME Linux)
  set(CMAKE_SYSTEM_PROCESSOR aarch64)
  set(CMAKE_C_COMPILER aarch64-linux-gnu-gcc)
  set(CMAKE_SYSROOT /path/to/sysroot)
  ```

### 依赖地狱（最常见的构建断裂点）

目标平台的 **glibc 版本**、`.so` 版本、CUDA 驱动版本 —— 一个不对就链接失败。**sysroot 的完整性决定交叉编译能不能成。**

## 三、仿真进 CI（机器人独有的"回归测试"）

机器人的改动要用**物理行为**验证，不能只靠单元测试。

### 仿真器选择

| 仿真器 | 能否进 CI | 说明 |
|:----|:----|:----|
| **Gazebo**（Classic / Ignition / 新 Gz） | ✅ **纯 CPU 可跑** | **CI 的正解** |
| **Isaac Sim** | ❌ | 需 RTX GPU + ≥8G 显存，托管 runner 跑不了，只能本地进阶 |
| Webots | ✅（软件渲染） | 轻量替代 |

### CI 里的仿真测试模式

- **headless 运行**：无图形界面跑仿真（`gz sim -s` / `xvfb-run`）。
- **场景用例**：启动仿真 → 下发目标 → **断言**（是否到达 / 是否碰撞 / 耗时）。
- **回放与量测**：输出通过率、延迟、碰撞次数、任务完成时间。

### 量化门禁（机器人 CI 的招牌）

门禁必须是**物理指标的硬数字**，不能只说"失败就阻断"：

| 指标 | 建议门禁 |
|:----|:----|
| 用例通过率 | `< 90%` → 阻断 |
| 任务完成时间 | 超基线 `> 20%` → 阻断 |
| 碰撞次数 | `> 0` → 阻断（安全类场景） |
| 端到端延迟 | 超阈值（如 `> 200ms`）→ 阻断 |

> 这是机器人 CI 与 Web CI 最大的理念差异：**门禁锚定在物理世界的行为上。**

## 四、AI / 模型构建流水线（具身智能的增量）

具身智能 = 机器人 + 大模型，构建链里多了一段"模型"。

### 模型转换链

```
PyTorch → ONNX → TensorRT（Jetson）/ TFLite / OpenVINO → 量化 → 部署
```

- **ONNX**：跨框架中间格式，模型构建流水线的枢纽。
- **TensorRT**：Jetson 上的推理加速（精度 vs 速度权衡，INT8 量化）。
- **量化 / 剪枝**：模型压缩，构建阶段常见步骤。

### 评测即构建

- **触发方式**：路径过滤，模型变更才跑（避免每次 push 都跑，慢且浪费）：
  ```yaml
  on:
    push:
      paths: ['models/**', 'eval/**']
  ```
- **指标**：推理延迟、显存/CPU 占用、精度（mAP / 成功率）、错误率。
- **输出**：自动生成 Markdown / JSON 评测报告，**作为门禁与留痕**。

### GPU runner

模型构建 / 评测需要 **GPU agent**，CI 调度要考虑 GPU 资源的排队与隔离（nvidia-docker / device plugin）。

## 五、HIL / 真机冒烟（机器人 CI 最"接地气"的一环）

仿真过了不代表真机行 —— **Hardware-in-the-Loop** 是最后一道闸。

### 链路

```
CI 触发 → 推镜像到目标板 → 目标板自动起节点 → 冒烟测试 → 回传日志/传感器数据
```

### 现实约束（最容易卡住的一步）

- **网络可达性**：CI runner 必须能访问目标板。托管 runner 到不了内网 →
  - 用**自建 runner**（跑在能通目标板的机器上），或
  - 用 **WireGuard / frp 隧道**打通。
- **安全**：SSH 密钥**走 CI Secret，绝不入库**；目标板侧用专用 `ci` 用户 + 最小权限。
- **幂等 + 可重跑**：`docker rm -f` 先清场、固定端口、`timeout 300` 兜底 —— 防止残留进程污染下次构建。

### device farm / board farm

大厂有专门的**硬件 CI 池**（一堆真机/板卡由 CI 排队调度），是机器人公司构建体系的成熟形态。

## 六、机器人制品分发（容易被忽视）

### deb 打包 + bloom release

- **deb 包**：ROS 包的标准发布形式（`dpkg-buildpackage`）。
- **bloom**：生成 debian 打包元数据并发布。
- **ros_buildfarm**：ROS 官方的**分布式构建农场** —— 本身就是一套巨型 CI 系统，值得作为架构案例研究。

### OCI 镜像分发

- `ros:humble` 官方镜像做基础层，**叠加增量层**（预装依赖）推私有 registry（Harbor）。
- 比在每个 CI job 里逐包 apt 更快更稳。

### 版本线

- **rosdistro**：ROS 发行版矩阵（humble / jazzy ...）+ 你的包版本，形成版本发布节奏。

## 对照表：能力矩阵（自查用）

| 类别 | 关键技能 | 通用 DevOps 是否覆盖 | 补课难度 |
|:----|:----|:----:|:----:|
| **ROS2 构建** | colcon / ament / rosdep / overleay / 增量缓存 | ❌ 特有 | 中 |
| **多架构交叉编译** | Jetson / RK3588 / sysroot / buildx / QEMU | 🟡 部分（ARM 跨编可迁移） | 中高 |
| **仿真进 CI** | Gazebo headless / 量化门禁 | ❌ 特有 | 中 |
| **AI 模型流水线** | ONNX / TensorRT / 量化 / GPU runner | 🟡 部分 | 中高 |
| **HIL / 真机** | 隧道触达 / 幂等冒烟 / device farm | 🟡 部分（K8s+WG 可迁移） | 中 |
| **制品分发** | deb / bloom / ros_buildfarm / OCI | 🟡 Harbor 可复用 | 中 |

## 三条最短路径（复用现有资产）

1. **colcon + ament 构建 ROS2 包 → 推 Harbor**：把现成的 Harbor 与 ROS2 串成一条链。
2. **Gazebo headless 仿真回归 + 量化门禁**：机器人 CI 的招牌能力，**纯 CPU 就能做**，不依赖 GPU。
3. **HIL 冒烟：CI → WireGuard 隧道 → 真机**：手上有 Jenkins + k3s + WG + 一台真机，**这是别人没有的现成靶场**。

> 这三条都能直接写进简历，且每条都命中「机器人 / 具身智能 Build Engineer」的核心要求。
