# K8s 网络详解

> 从「四层网络模型」讲起，到 Service → kube-proxy → Ingress → CNI → DNS 的完整链路。
> 附本项目 k3s 双节点实证（含跨 VPC 踩坑）。

---

## 一、K8s 网络模型

K8s 对网络的**根本要求**只有四条：

1. **每个 Pod 有独立 IP**，集群内任意 Pod 之间**可直接通信**（不用 NAT）
2. **所有 Pod 在同一扁平网络**里，无论是否在同一节点
3. **Node 与 Pod 互通**，Pod 与 Node 互通
4. **Pod 看到的自己的 IP = 别人看到的它的 IP**（无端口映射幻觉）

> 这就是所谓的 **"IP-per-Pod" 模型**。它把"容器网络很复杂"这件事**下沉给了 CNI 插件**，让上层（Service、Ingress）能基于简单 IP 做文章。

### 三种 IP 别搞混

| IP 类型 | 作用域 | 谁分配 | 变不变 |
|:--------|:-------|:-------|:-------|
| **Node IP** | 物理机/虚拟机 | 云平台 / DHCP | 相对固定 |
| **Pod IP** | 每个 Pod 一个 | CNI 插件 | **Pod 重建就变** |
| **Cluster IP** | 每个 Service 一个 | K8s API | **固定不变**（Service 生命周期内）|

```
外部用户 ──> Node IP (公网 122.51.10.97:31000)
                │ NodePort
                ▼
         Cluster IP (10.43.x.x:8080)  ← Service 抽象层
                │ kube-proxy 转发
                ▼
         Pod IP (10.42.x.x:80)        ← 真实容器
```

## 二、Pod 之间怎么通（CNI）

### 2.1 CNI 是什么

**CNI（Container Network Interface）** 是一套**网络插件标准**：kubelet 创建 Pod 时调用 CNI 插件，插件负责给 Pod 分配 IP、接好网线、配好路由。

K8s 本身**不实现网络**，只规定接口。选哪个 CNI 决定了网络怎么工作。

### 2.2 主流 CNI 对比

| CNI | 数据面 | 特点 | 适用 |
|:----|:-------|:-----|:-----|
| **Flannel** | VXLAN overlay | 简单、轻量 | 小集群、入门（**k3s 默认内置**）|
| **Calico** | BGP / IPIP | 性能好、网络策略强 | 中大型生产 |
| **Cilium** | eBPF | 高性能、可观测性极强 | 云原生进阶、大集群 |
| **Weave** | VXLAN | 简单，但性能一般 | 已边缘化 |
| **kube-router** | BGP | 轻量，自带 LB/策略 | 特定场景 |

### 2.3 Overlay vs Underlay

- **Overlay（覆盖网络）**：Pod 包被**再包一层**（VXLAN/Geneve），跨节点通信靠隧道。**不依赖底层网络**，但**有封包开销**、MTU 变小。Flannel VXLAN 属此类。
- **Underlay（原生路由）**：Pod 网段直接**被底层网络路由可达**，无隧道开销、性能最好。Calico BGP、云厂商 VPC-CNI 属此类。

```
Overlay（Flannel VXLAN）：
  Pod A ──[VXLAN 封包: 外层 Node IP + 内层 Pod IP]──> Node B ──> Pod B
          ↑ 多一层包头，MTU 从 1500 降到 ~1450

Underlay（Calico BGP）：
  Pod A ──[原生 IP 包，底层网络直接路由]──> Pod B
          ↑ 无封装，性能接近裸机
```

### 2.4 同节点 vs 跨节点通信

- **同节点**：CNI 建一个网桥（`cni0`/`flannel.1`），Pod 网卡 `veth` 一端在 Pod、一端接网桥，纯二层转发。
- **跨节点**：靠 overlay 隧道（VXLAN）或 BGP 路由把包送到对端节点，再交给对端网桥。

```bash
# 观察 CNI 网络设备（在节点上）
ip link show          # 看 flannel.1 / cni0 / veth*
ip route              # 看 Pod 网段路由
kubectl get pods -o wide   # 看 Pod 落在哪个节点、Pod IP 是什么
```

## 三、Service：Pod 的稳定访问入口

Pod IP 会变（重建就换），所以业务**不能直接连 Pod IP**。**Service** 给一组 Pod 提供一个**固定虚拟 IP（Cluster IP）** + **负载均衡**。

### 3.1 四种 Service 类型

| 类型 | 访问范围 | 实现 | 典型用途 |
|:-----|:---------|:-----|:---------|
| **ClusterIP** | **仅集群内** | 虚拟 IP，kube-proxy 转发 | 内部服务互调（默认类型）|
| **NodePort** | 集群外（通过 `节点IP:30000-32767`）| 每个节点开同一端口 | 测试、简单暴露 |
| **LoadBalancer** | 集群外（云 LB 公网 IP）| 云厂商自动创建 LB | 生产公网入口 |
| **ExternalName** | — | DNS CNAME 到外部域名 | 把外部服务"假装"成集群内 Service |

```yaml
# ClusterIP（默认）—— 内部服务
apiVersion: v1
kind: Service
metadata:
  name: backend
spec:
  selector:
    app: backend
  ports:
    - port: 8080            # Service 暴露的端口
      targetPort: 80        # 容器实际监听端口
---
# NodePort —— 对外暴露（本项目 Gitea 用的就是这个）
apiVersion: v1
kind: Service
metadata:
  name: gitea-http
spec:
  type: NodePort
  selector:
    app: gitea
  ports:
    - port: 3000
      targetPort: 3000
      nodePort: 30080       # 外部访问 http://<节点IP>:30080
```

### 3.2 Service 如何找到 Pod

两件事：

1. **标签选择器（selector）**：Service 用 `selector` 匹配一组 Pod，匹配到的 Pod 成为 Endpoints（后端列表）。
2. **Endpoints / EndpointSlice**：K8s 自动维护这份"可用后端 IP 清单"，Pod 增删自动更新。

```bash
kubectl get endpoints backend   # 看 Service 背后挂了哪些 Pod IP
kubectl describe svc backend    # 也能看到 Endpoints
```

> ⚠️ **selector 匹配不上 = Endpoints 为空 = 访问 503**。排障第一步就是查 Endpoints。

### 3.3 kube-proxy：Service 的"隐形实现者"

Service 只是个**虚拟概念**（Cluster IP 没人真正拥有，ping 不通）。真正干活的是**每个节点上的 kube-proxy**，它把发往 Cluster IP 的流量**转成发往某个 Pod IP**。

三种工作模式：

| 模式 | 原理 | 性能 |
|:-----|:-----|:-----|
| **userspace** | kube-proxy 进程在用户态代理 | 最差，已淘汰 |
| **iptables** | 写 iptables 规则做 DNAT | 好，但规则多时线性变慢 |
| **IPVS** | 内核 LVS 负载均衡 | **最好**，大规模首选 |

```
Client Pod ──> Cluster IP:8080
                  │ kube-proxy 规则命中
                  ▼
            随机选一个 Endpoint Pod IP
                  │ DNAT
                  ▼
            Pod IP:80  ← 真实后端
```

```bash
# 看 kube-proxy 用的模式
kubectl -n kube-system get cm kube-proxy -o yaml | grep mode

# 看 Service 转发的 iptables 规则（iptables 模式）
sudo iptables -t nat -L KUBE-SERVICES -n | grep <clusterIP>
```

## 四、Ingress：七层入口

NodePort / LoadBalancer 都是**四层**（TCP/UDP）暴露，端口难看、没有域名和路径路由、不能终止 HTTPS。**Ingress** 补上这一层。

### 4.1 Ingress vs Ingress Controller

- **Ingress**：只是一个**规则对象**（API 资源），描述"哪个域名/路径转发到哪个 Service"。
- **Ingress Controller**：**真正干活的组件**（一个跑在集群里的 Pod），监听 Ingress 规则并配置自己的负载均衡器。

> 光写 Ingress 对象**没用**，必须有 Ingress Controller 在跑。常见：**ingress-nginx**（最流行）、Traefik、HAProxy Ingress、APISIX。

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx          # 用哪个 Controller
  tls:
    - hosts: ["app.example.com"]
      secretName: app-tls          # HTTPS 证书（Secret）
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: backend
                port:
                  number: 8080
          - path: /web
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
```

### 4.2 完整请求链路

```
用户浏览器
   │ https://app.example.com/api
   ▼
Ingress Controller（nginx Pod，挂在 NodePort/LB 上）
   │ 按 host + path 匹配 Ingress 规则，TLS 在此终止
   ▼
Service backend (Cluster IP)
   │ kube-proxy 负载均衡
   ▼
Pod (10.42.x.x:8080)
```

### 4.3 常用注解速查（ingress-nginx）

| 注解 | 作用 |
|:-----|:-----|
| `nginx.ingress.kubernetes.io/rewrite-target` | 路径重写 |
| `nginx.ingress.kubernetes.io/ssl-redirect: "true"` | HTTP 强制跳 HTTPS |
| `nginx.ingress.kubernetes.io/proxy-body-size: "50m"` | 上传体积上限 |
| `nginx.ingress.kubernetes.io/affinity: "cookie"` | 会话保持 |

## 五、DNS：服务发现的基石

Service 有了固定 IP，但 IP 也难记。**CoreDNS** 给每个 Service 一个**域名**，Pod 内直接用域名访问。

### 5.1 域名格式

```
<service>.<namespace>.svc.cluster.local
```

- 完整 FQDN：`backend.default.svc.cluster.local`
- **同 ns 内**：直接 `backend` 就行（自动补全）
- **跨 ns**：`backend.other-ns` 或完整 FQDN

```bash
# Pod 内测试 DNS
kubectl run -it --rm dns-test --image=busybox:1.28 --restart=Never -- nslookup backend
kubectl run -it --rm dns-test --image=busybox:1.28 --restart=Never -- nslookup kubernetes.default
```

### 5.2 Pod 的 DNS 解析链路

Pod 的 `/etc/resolv.conf` 指向 CoreDNS 的 Cluster IP（如 `10.43.0.10:53`），解析顺序：

1. 先按 `search` 域补全（同 ns、svc.cluster.local...）
2. 本地匹配不到 → 转发给上游 DNS（`forward . /etc/resolv.conf`）

```bash
# 看 Pod 的 DNS 配置
kubectl exec <pod> -- cat /etc/resolv.conf

# 看 CoreDNS 配置
kubectl -n kube-system get cm coredns -o yaml
```

### 5.3 常见 DNS 坑

| 现象 | 原因 |
|:-----|:-----|
| Pod 内解析不了 Service 名 | CoreDNS 没起 / Pod 的 `dnsPolicy` 不对 |
| 解析公网域名慢/超时 | 上游 DNS 不可达（**本项目踩过，见第六节**）|
| Headless Service 拿到多 IP | `clusterIP: None` 时 DNS 返回所有 Pod IP（有状态服务常用）|

## 六、k3s 双节点实证（本项目踩坑记录）

### 6.1 k3s 默认网络方案

k3s **内置 Flannel（VXLAN overlay）**，开箱即用，无需额外装 CNI：

- Pod 网段：默认 `10.42.0.0/16`（每节点再分 `/24` 子网）
- Service 网段：默认 `10.43.0.0/16`
- CoreDNS Cluster IP：`10.43.0.10`

```bash
kubectl get nodes -o wide        # 看每个节点的 PodCIDR
kubectl get svc -A               # 看 Cluster IP 段
kubectl -n kube-system get pods  # flannel / coredns 都在跑
```

### 6.2 ⚠️ 跨 VPC overlay 不通（实战大坑）

**现象**：构建 Pod 在集群内 clone 代码报 `Could not resolve host`，Pod → CoreDNS 的 VXLAN 隧道解析超时。

**根因**：两个节点**不在同一 VPC**（杭州 server + 上海 agent），**Flannel VXLAN overlay 跨 VPC 不通**（底层网络不支持节点间 UDP 8472 直通）。

**当时排障与变通**：
- 临时把 Pod 的 `dnsPolicy` 改成 `Default`，让它走**节点自己的 VPC DNS** 解析公网——能绕过但放弃集群内 service 名解析
- 最终根治：开通**沪杭 VPC 对等连接**，overlay 恢复，集群 DNS 完全可用

> 详见 k3s部署实战.md「VPC 对等连接打通实录」。

**教训**：
1. **多节点跨 VPC 部署前，先确认底层网络能承载 CNI overlay**（UDP 8472 / BGP 179 等端口与方向）。
2. 排查顺序：`Pod 内 ping CoreDNS → 节点间 ping → 隧道端口 → 底层路由`，逐层收敛。
3. 云上跨地域/跨 VPC 组 K8s 集群，**网络先行**，别等问题发生了再补。

### 6.3 本项目 Service 实例

Gitea 部署即用了 **NodePort** 暴露：

| Service | 类型 | 端口映射 | 外部访问 |
|:--------|:-----|:---------|:---------|
| gitea-http | NodePort | 3000 → **30080** | `http://101.133.228.245:30080` |
| gitea-ssh | NodePort | 22 → 30222 | `ssh://...:30222` |

> ⚠️ 坑：`30080` 曾被 `default/nginx-demo-np` 占用，删除旧 svc 才释放——**NodePort 重复会创建失败**，`kubectl get svc -A` 先查占用。

## 七、运维速查

```bash
# 网络对象总览
kubectl get svc -A                       # 所有 Service
kubectl get endpoints -A                 # 后端清单（排查 503 第一步）
kubectl get ingress -A                   # Ingress 规则
kubectl get networkpolicy -A             # 网络策略
kubectl get pods -o wide -A              # Pod 落在哪个节点 + Pod IP

# 连通性排查（三板斧）
kubectl run -it --rm net-test --image=nicolaka/netshoot --restart=Never -- bash
  # 容器内可用：ping / nslookup / curl / dig / tcpdump / mtr

# 从 Pod 测 Service
kubectl exec <pod> -- wget -qO- http://backend:8080/health

# 看 kube-proxy 模式与规则
kubectl -n kube-system get cm kube-proxy -o yaml | grep -E "mode|clusterCIDR"
```

**常见故障对照：**

| 现象 | 排查方向 |
|:-----|:---------|
| Service 访问 503 | `kubectl get endpoints` → 空=selector 不匹配 |
| Pod 间不通 | CNI 未就绪 / overlay 隧道断 / NetworkPolicy 拦截 |
| DNS 解析失败 | CoreDNS Pod 状态 / `dnsPolicy` / resolv.conf |
| Ingress 404 | Ingress Controller 没起 / `ingressClassName` 不匹配 / path 写错 |
| NodePort 建不上 | 端口被占用（`kubectl get svc -A` 查）|

## 八、知识地图

```
【Pod 间通信】 IP-per-Pod 模型
        │ 谁来接线？
        ▼
    CNI 插件（Flannel / Calico / Cilium）
        ├─ 同节点：网桥 + veth
        └─ 跨节点：Overlay 隧道（VXLAN）/ BGP 路由

【稳定访问】 Pod IP 会变 → Service
        │ Cluster IP + selector
        ▼
    kube-proxy（iptables / IPVS）做 DNAT 负载均衡
        ├─ ClusterIP（集群内）
        ├─ NodePort（节点端口）
        └─ LoadBalancer（云 LB）

【七层入口】 Ingress 规则 + Ingress Controller（ingress-nginx）
        │ 域名 / 路径 / TLS
        ▼
    转发到 Service

【服务发现】 CoreDNS
        └─ <svc>.<ns>.svc.cluster.local
```
