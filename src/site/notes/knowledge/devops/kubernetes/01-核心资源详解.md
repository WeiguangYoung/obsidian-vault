# K8s 核心资源详解

> 把 K8s 的"家底"过一遍：**能描述什么东西（对象）**、**它们怎么协作（控制器层级）**、**怎么定义与操作（YAML + kubectl）**。
> 面向实操，每种资源给"是什么 + 关键字段 + 最小 YAML + 何时用"。

---

## 一、K8s 的世界观：声明式 + 控制器

K8s 解决的是"**一个容器好跑，一千个容器怎么管**"。核心哲学一句话：

> **声明式 API + 控制器循环（Reconcile）**

你不命令它"启动 3 个副本"，而是**声明期望状态**（我要 3 个副本、镜像是什么），控制器在后台不断比对"实际状态 vs 期望状态"，不一致就动手补齐。

```
你提交 YAML（期望状态）
      │
      ▼
  对象存入 etcd
      │
      ▼
控制器循环（Reconcile）：实际状态 ≠ 期望状态？
      │ 是 → 动手修正（新建/删除/更新 Pod）
      ▼
实际状态 == 期望状态（达成，继续 watch）
```

**自愈的来源**就是这里：Pod 崩了 → 实际副本数 < 期望 → 控制器再拉一个起来。

**一切皆对象（Object）**：K8s 里每个资源都是一条 API 对象记录，统一有 `apiVersion` / `kind` / `metadata` / `spec`（期望）/ `status`（实际）五段结构。

```yaml
apiVersion: apps/v1        # 用哪个 API 版本
kind: Deployment           # 什么类型
metadata:                  # 元信息：名字、标签、命名空间
  name: myapp
spec:                      # 期望状态（你写的）
  replicas: 3
status:                    # 实际状态（K8s 填的，别手写）
```

## 二、资源全景图

```
┌─────────────────────────── 工作负载（Workload）───────────────────────────┐
│  Pod   ← 最小调度单位                                                      │
│   ▲                                                                        │
│   ├── ReplicaSet ←── Deployment（无状态，管副本/滚动更新/回滚）             │
│   ├─────────────── StatefulSet（有状态，稳定标识 + 独立存储）               │
│   ├─────────────── DaemonSet（每节点一个，日志/监控采集）                   │
│   ├─────────────── Job（一次性任务）→ CronJob（定时任务）                   │
│   └─────────────── 裸 Pod（不推荐，无自愈）                                 │
└────────────────────────────────────────────────────────────────────────────┘
┌────── 服务与网络 ──────┐  ┌────── 配置与存储 ──────┐  ┌──── 治理 ────┐
│ Service（稳定入口）     │  │ ConfigMap（普通配置）  │  │ Namespace    │
│ Ingress（七层路由）     │  │ Secret（敏感配置）     │  │ RBAC         │
│ NetworkPolicy（网络策略）│  │ PVC/PV（持久存储）     │  │ ResourceQuota│
│ Endpoints（后端地址）    │  │ StorageClass（存储类） │  │ LimitRange   │
└────────────────────────┘  └────────────────────────┘  └──────────────┘
```

## 三、Pod：最小调度单位

**Pod 是 K8s 里你能创建/调度的最小单元**——一个或多个共享网络命名空间、存储卷的容器集合。

### 3.1 为什么不是直接跑容器

因为存在"**辅助容器**"场景：主容器 + 边车（sidecar）。同一 Pod 内容器**共享 localhost**（端口不能冲突）、共享 volume。典型：

| 模式 | 说明 |
|:-----|:-----|
| **Sidecar** | 日志采集、代理（如 Istio 注入的 envoy）|
| **Ambassador** | 代理对外连接（应用只连 localhost）|
| **Adapter** | 把应用输出转成统一格式（监控暴露）|

### 3.2 最小 Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
  labels: { app: nginx }
spec:
  containers:
    - name: nginx
      image: nginx:alpine
      ports:
        - containerPort: 80
      resources:
        requests: { cpu: 100m, memory: 128Mi }
        limits:   { cpu: 500m, memory: 256Mi }
```

### 3.3 多容器 Pod（sidecar 示例）

```yaml
spec:
  containers:
    - name: app
      image: myapp:v1
      volumeMounts:
        - { name: logs, mountPath: /var/log/app }
    - name: log-shipper          # 边车：读同一卷，发日志
      image: fluent-bit:latest
      volumeMounts:
        - { name: logs, mountPath: /var/log/app }
  volumes:
    - name: logs
      emptyDir: {}               # Pod 生命周期内的临时卷
```

> ⚠️ **生产不要裸跑 Pod**——没有自愈、没有滚动更新。用 Deployment/StatefulSet/DaemonSet 管。
> 裸 Pod 只用于调试：`kubectl run -it --rm debug --image=busybox --restart=Never -- sh`

## 四、工作负载控制器：谁管 Pod

### 4.1 Deployment：无状态应用（最常用）

管副本数、滚动更新、回滚。**层级：Deployment → ReplicaSet → Pod**。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  selector:
    matchLabels: { app: myapp }      # 认领带此标签的 Pod
  strategy:
    type: RollingUpdate              # 滚动更新（默认）
    rollingUpdate:
      maxSurge: 1                    # 更新时最多多出 1 个
      maxUnavailable: 0              # 更新时最少保证 0 个不可用（不中断）
  template:                          # Pod 模板
    metadata:
      labels: { app: myapp }
    spec:
      containers:
        - name: app
          image: myapp:v1.2.3
          ports: [{ containerPort: 3000 }]
          readinessProbe:            # 就绪才接流量（滚动更新关键）
            httpGet: { path: /ready, port: 3000 }
          livenessProbe:
            httpGet: { path: /healthz, port: 3000 }
```

**滚动更新原理**：改镜像 → 生成新 ReplicaSet → 逐步（按 maxSurge/maxUnavailable）把 Pod 从旧 RS 换到新 RS → 旧 RS 保留（`revisionHistoryLimit` 个）以便回滚。

```bash
kubectl rollout status deploy/myapp      # 看滚动进度
kubectl rollout history deploy/myapp     # 看历史版本
kubectl rollout undo deploy/myapp        # 回滚上一版
kubectl rollout undo deploy/myapp --to-revision=2
kubectl scale deploy/myapp --replicas=5  # 手动扩缩
```

**何时用**：无状态 Web 服务、API —— 绝大多数场景。

### 4.2 StatefulSet：有状态应用

给 Pod **稳定网络标识 + 独立存储**，适合数据库、消息队列、有状态集群。

| 特性 | Deployment | StatefulSet |
|:-----|:-----------|:------------|
| Pod 名字 | 随机（myapp-7d4b-x9k2）| **有序固定**（db-0 / db-1 / db-2）|
| 网络标识 | 无稳定 DNS | **稳定 DNS**（db-0.svc.ns）|
| 存储 | 共享/无 | **每 Pod 独立 PVC**（volumeClaimTemplates）|
| 启停顺序 | 并行 | **按序号顺序**（0→1→2 启，2→1→0 停）|
| 用途 | 无状态 | 有状态（主从/集群）|

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db-headless          # 必须配一个 headless Service
  replicas: 3
  selector:
    matchLabels: { app: db }
  template:
    metadata:
      labels: { app: db }
    spec:
      containers:
        - name: db
          image: postgres:16
          volumeMounts:
            - { name: data, mountPath: /var/lib/postgresql/data }
  volumeClaimTemplates:              # 每个 Pod 自动创建一块独立 PVC
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: local-path
        resources:
          requests: { storage: 10Gi }
```

> **典型用法**：Prometheus、Elasticsearch、Kafka、MySQL 主从这类"每个副本要有自己独立身份和数据"的组件，都用 StatefulSet —— 稳定存储是历史数据不丢的关键。

### 4.3 DaemonSet：每个节点一个

保证**每个（或指定）节点上跑一个 Pod**——日志采集、监控 Agent、网络插件。

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
spec:
  selector:
    matchLabels: { app: node-exporter }
  template:
    metadata:
      labels: { app: node-exporter }
    spec:
      hostNetwork: true              # 直接用宿主网络（采集宿主指标）
      hostPID: true
      tolerations:                   # 容忍所有污点，才能落到每个节点
        - operator: Exists
      containers:
        - name: node-exporter
          image: prom/node-exporter:v1.8.2
          ports: [{ containerPort: 9100, name: metrics }]
```

> **典型用法**：node-exporter（节点指标）、Promtail/Fluent Bit（日志采集）、CNI 插件、kube-proxy —— 凡是"每个节点都要一份"的 Agent，都用 DaemonSet。
> ⚠️ **hostNetwork 会占用宿主端口** → 同节点不能跑两个 hostNetwork 的 node-exporter。

### 4.4 Job 与 CronJob：一次性 / 定时任务

```yaml
# Job：跑一次就结束（批处理、数据迁移）
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
spec:
  backoffLimit: 3                    # 失败重试 3 次
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: myapp:migrate
          command: ["./migrate.sh"]
---
# CronJob：按 cron 定时（备份、报表）
apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup
spec:
  schedule: "0 3 * * *"              # 每天 3 点
  concurrencyPolicy: Forbid          # 上次没跑完就别起新的
  successfulJobsHistoryLimit: 3
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: postgres:16
              command: ["pg_dump", "-f", "/backup/db.sql"]
```

> **典型用法**：数据库迁移（db-migrate）、bucket 初始化、证书/凭证生成 —— 这类"跑完就结束"的初始化动作，都用 Job；定时备份、报表则用 CronJob。

## 五、Service：稳定入口

Pod 的 IP 是临时的（重建就变），所以需要 **Service** 给一组 Pod 一个**稳定虚拟 IP（ClusterIP）**，并自动负载均衡。

### 5.1 四种类型

| 类型 | 可达范围 | 用途 |
|:-----|:---------|:-----|
| **ClusterIP** | 仅集群内 | 内部服务互调（默认）|
| **NodePort** | 集群外（节点IP:端口）| 简单暴露（30000-32767）|
| **LoadBalancer** | 云负载均衡 | 云上对外服务 |
| **ExternalName** | DNS 别名 | 把外部域名映射进集群 |

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  type: NodePort                     # 对外暴露
  selector: { app: myapp }           # 靠标签找后端 Pod
  ports:
    - name: http
      port: 80                       # Service 端口
      targetPort: 3000               # 容器端口
      nodePort: 30080                # 节点端口（30000-32767）
```

> **选型提示**：对外暴露用 **NodePort / LoadBalancer**，仅集群内互调用 **ClusterIP**（默认）。NodePort 每个节点都开端口，**公网暴露务必配安全组限源**。

### 5.2 Headless Service（无头服务）

`clusterIP: None` —— 不要虚拟 IP，直接返回后端 Pod 的 DNS 列表。**StatefulSet 的稳定 DNS 靠它**。

```yaml
spec:
  clusterIP: None
  selector: { app: db }
# 结果：db-0.db-headless.ns.svc.cluster.local → 直接解析到 db-0 的 Pod IP
```

> **典型用法**：Prometheus 抓 node-exporter 时就是靠 headless Service 直接发现每个 Pod 的 IP，而不用经过负载均衡（采集端要的是"每个实例"而非"任一实例"）。

### 5.3 三条端口链要分清

```
用户 → [Service.port] → [targetPort] → 容器
外网 → [nodePort]（NodePort 类型时）
```
**坑**：改了容器端口却忘了同步 `targetPort`，Service 就转发到空端口。

## 六、Ingress：七层路由

Service 是四层（TCP/UDP），**Ingress 是七层（HTTP/HTTPS）**——按域名/路径路由到不同 Service。

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx            # 指定 Ingress Controller
  tls:
    - hosts: [app.example.com]
      secretName: tls-secret
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-svc
                port: { number: 80 }
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-svc
                port: { number: 80 }
```

**关键点**：Ingress 只是"路由规则声明"，**必须有 Ingress Controller 落地**（Nginx / Traefik / APISIX）。

> **本项目实例**：杭州节点上跑的 **APISIX** 就是这个角色 —— `apisix_apisix_1`（80→9080）做网关/路由，`apisix_apisix-dashboard_1`（9000）是它的管理面板，`apisix_etcd_1`（12379）存配置。相当于"集群外的 Ingress Controller"。

## 七、配置与密钥

### 7.1 ConfigMap：普通配置

把配置从镜像里剥离（改配置不用重打镜像）。

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_MODE: "production"             # 键值
  nginx.conf: |                      # 整个文件
    server {
      listen 80;
      location / { return 200 "ok"; }
    }
```

**三种挂载方式**：

```yaml
spec:
  containers:
    - name: app
      image: myapp
      envFrom:                                    # ① 全部作为环境变量
        - configMapRef: { name: app-config }
      env:                                        # ② 单个作为环境变量
        - name: MODE
          valueFrom:
            configMapKeyRef: { name: app-config, key: APP_MODE }
      volumeMounts:                               # ③ 作为文件挂载
        - { name: cfg, mountPath: /etc/nginx/conf.d }
  volumes:
    - name: cfg
      configMap: { name: app-config }
```

### 7.2 Secret：敏感配置

和 ConfigMap 类似，但用于密码/Token/证书。**注意：默认只是 base64 编码，不是加密！**

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  password: cGFzc3dvcmQxMjM=          # base64
stringData:                            # 也可以直接写明文，K8s 帮你编码
  username: admin
```

```bash
# 生成（避免明文进 shell history 用 --from-file）
kubectl create secret generic db-secret \
  --from-literal=username=admin \
  --from-literal=password='S3cr3t!'
```

**安全加固**（生产必做）：
- 开启 **etcd 静态加密**（EncryptionConfiguration）
- 用 **RBAC** 限制谁能读 Secret
- 外部密钥管理：Sealed Secrets / External Secrets / Vault

> **典型用法**：数据库密码、API Token、TLS 证书放 Secret；普通配置（日志级别、超时）放 ConfigMap。**认证信息一律进 Secret，不写进 ConfigMap 或镜像。**

### 7.3 imagePullSecrets：拉私有镜像

```yaml
spec:
  imagePullSecrets:
    - name: acr-cred              # 引用一个 docker-registry 类型 Secret
  containers:
    - name: app
      image: registry.example.com/team/myapp:v1
```

```bash
kubectl create secret docker-registry reg-cred \
  --docker-server=registry.example.com \
  --docker-username='<用户名>' \
  --docker-password='<密码>'
```

> **两条路径**：私有镜像仓库的认证，一是**节点层面**（如各发行版的 registry 配置文件，全节点生效），二是 **Pod 层面**（imagePullSecrets，按工作负载生效）。生产建议敏感凭证走外部密钥管理，别明文进仓库。

## 八、存储：PV / PVC / StorageClass

**三层关系**：用户声明 **PVC**（我要一块盘）→ 系统找/建 **PV**（实际盘）→ **StorageClass** 定义"怎么自动建盘"。

```
PVC（用户声明：我要 10Gi）           ← 只管要，不管从哪来
   │ 绑定
   ▼
PV（实际存储卷：本地盘 / 云盘 / NFS）
   ▲ 供给
   │
StorageClass（供给模板：local-path / alicloud-disk / nfs-client）
```

### 8.1 静态 vs 动态供给

| 方式 | 流程 | 场景 |
|:-----|:-----|:-----|
| **静态** | 管理员先建 PV → PVC 匹配绑定 | 手工管理、少量 |
| **动态** | PVC 引用 StorageClass → 自动创建 PV | 云原生主流 |

```yaml
# ① StorageClass（一次定义）
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-path
provisioner: rancher.io/local-path
reclaimPolicy: Delete                 # PVC 删了 PV 也删（Delete/Retain）
volumeBindingMode: WaitForFirstConsumer   # 等 Pod 调度后才建卷（本地盘必须）
---
# ② PVC（每次申请）
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: prometheus-data
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: local-path
  resources:
    requests: { storage: 10Gi }
---
# ③ Pod 挂载
spec:
  volumes:
    - name: data
      persistentVolumeClaim: { claimName: prometheus-data }
```

### 8.2 访问模式（AccessModes）

| 模式 | 缩写 | 说明 |
|:-----|:-----|:-----|
| ReadWriteOnce | RWO | 单节点读写（云盘/本地盘）|
| ReadOnlyMany | ROX | 多节点只读 |
| ReadWriteMany | RWX | 多节点读写（NFS/CephFS）|
| ReadWriteOncePod | RWOP | 单 Pod 读写（最严）|

> ⚠️ **local-path 的坑**：PV 就是节点本地盘的一块目录，**不跟随 Pod 跨节点迁移** —— 换节点 = 数据不跟随。所以有状态服务（Prometheus 等）一旦用了 local-path，就等于**被钉死在那个节点**，这是选存储类时要先想清楚的。

## 九、命名空间与治理

### 9.1 Namespace：逻辑隔离

```bash
kubectl create ns monitoring
kubectl get pods -n monitoring
kubectl config set-context --current --namespace=monitoring   # 切默认 ns
```

**作用**：资源分组、权限隔离（RBAC 按 ns 授权）、配额隔离。**默认 ns**：`default` / `kube-system`（系统组件）/ `kube-public`。

> **本项目实例**：`default` / `gitea` / `jenkins` / `monitoring` / `kube-system` 五个 ns 各司其职。

### 9.2 ResourceQuota / LimitRange：配额与默认值

```yaml
# ResourceQuota：整个 ns 的资源上限
apiVersion: v1
kind: ResourceQuota
metadata: { name: mem-cpu-quota, namespace: team-a }
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.cpu: "20"
    limits.memory: 40Gi
    pods: "50"
---
# LimitRange：给没写 requests/limits 的 Pod 兜底默认值
apiVersion: v1
kind: LimitRange
metadata: { name: default-limits, namespace: team-a }
spec:
  limits:
    - type: Container
      default:            { cpu: 500m, memory: 256Mi }   # 默认 limits
      defaultRequest:     { cpu: 100m, memory: 128Mi }   # 默认 requests
```

> ⚠️ **小机必备**：2C/1.9G 的节点上，用 LimitRange 兜底 + ResourceQuota 防某队把集群吃空。

### 9.3 RBAC：谁能对什么做什么

**三要素**：**Subject（谁）** + **Role（能做什么）** + **Binding（绑定）**。

```
ServiceAccount / User / Group
        │ 通过
        ▼
Role / ClusterRole（一组权限规则）
        │ 绑定
        ▼
RoleBinding / ClusterRoleBinding
```

| 对象 | 作用范围 |
|:-----|:---------|
| Role / RoleBinding | **命名空间级** |
| ClusterRole / ClusterRoleBinding | **集群级**（所有 ns + 非资源 URL）|

```yaml
# ClusterRole：允许读 pods/nodes（Prometheus 服务发现用）
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: prometheus-monitoring }
rules:
  - apiGroups: [""]
    resources: ["nodes", "services", "endpoints", "pods"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata: { name: prometheus-monitoring }
roleRef:
  kind: ClusterRole
  name: prometheus-monitoring
  apiGroup: rbac.authorization.k8s.io
subjects:
  - kind: ServiceAccount
    name: default
    namespace: monitoring
```

```bash
# 排查权限：这个 SA 能不能做某事
kubectl auth can-i list pods --as=system:serviceaccount:monitoring:default
kubectl auth can-i '*' '*' --all-namespaces
```

> **本项目实例**：手搓 Prometheus 因缺 RBAC 报 `pods is forbidden` 抓不到 target；KPS 由 operator 自动建 RBAC 解决。**教训：ServiceAccount 不配 RBAC = 什么都读不到。**

## 十、标签、选择器与注解

**标签（Label）** 是 K8s 里"关联一切"的胶水 —— Service 找 Pod、Deployment 认领 Pod、nodeSelector 挑节点，全靠它。

```yaml
metadata:
  labels:                    # 用于选择（可被 selector 匹配）
    app: myapp
    env: prod
    version: v1
  annotations:               # 用于附加信息（不参与选择）
    description: "主应用"
    prometheus.io/scrape: "true"
```

```bash
kubectl get pods -l app=myapp,env=prod          # 等值选择
kubectl get pods -l 'env in (prod,staging)'     # 集合选择
kubectl label pod mypod tier=backend            # 打标签
kubectl annotate pod mypod note="debug"         # 加注解
```

| 概念 | 参与选择 | 用途 |
|:-----|:---------|:-----|
| **Label** | ✅ | 关联对象、选择器匹配 |
| **Annotation** | ❌ | 记录元信息、给控制器/工具读（Ingress 配置、Prometheus 抓取开关）|

## 十一、一键速查表

| 资源 | 一句话 | 何时用 |
|:-----|:-------|:-------|
| Pod | 最小调度单位（1+ 容器）| 调试；生产用下面的控制器 |
| Deployment | 无状态 + 副本 + 滚动更新 | Web/API |
| StatefulSet | 有状态 + 稳定标识 + 独立存储 | DB/MQ/集群 |
| DaemonSet | 每节点一个 | 监控/日志采集 |
| Job | 跑一次 | 迁移/初始化 |
| CronJob | 定时跑 | 备份/报表 |
| Service | 稳定入口 + 负载均衡 | 服务互调/暴露 |
| Ingress | 七层 HTTP 路由 | 域名/路径分流 |
| ConfigMap | 普通配置 | 剥离配置 |
| Secret | 敏感配置 | 密码/证书 |
| PVC/PV | 持久存储 | 数据落盘 |
| Namespace | 逻辑隔离 | 分组/配额 |
| RBAC | 权限控制 | 最小权限 |
| ServiceAccount | Pod 身份 | 访问 API |
| PDB / PriorityClass | 可用性 / 优先级 | 生产保障 |
| Label / Annotation | 关联 / 元信息 | 一切选择的胶水 |
