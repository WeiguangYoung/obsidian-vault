# K8s 安全详解

> K8s 安全的四条主线：**谁能操作集群（认证/授权）→ 工作负载能做什么（Pod 安全）→ 谁能访问谁（网络策略）→ 密钥与镜像可信（Secret/镜像安全）**。
> 面向实操，每块讲清「威胁是什么、机制怎么工作、怎么落地」。

---

## 一、安全模型总览：4C 模型

K8s 安全不是单点，而是**层层纵深（Defense in Depth）**，业界常说的 **4C**：

```
Cloud（云/基础设施）      ← 网络隔离、安全组、主机加固
   └── Cluster（集群）     ← RBAC、准入控制、审计日志
        └── Container（容器） ← 镜像安全、最小权限、只读根文件系统
             └── Code（代码）  ← 依赖漏洞、密钥管理
```

**关键理念**：**内层依赖外层**。代码再安全，集群被攻破也白搭；集群再稳，镜像里带木马也没用。本节聚焦 **Cluster 和 Container 两层**。

**核心原则（记住这两条，后面所有机制都是它的推论）**：

| 原则 | 含义 |
|:-----|:-----|
| **最小权限（Least Privilege）** | 只给完成工作**必需**的权限，多一点都不给 |
| **零信任（Zero Trust）** | 默认拒绝，显式放行；不因为"在集群内"就信任 |

## 二、认证与授权：谁能操作集群

K8s 的一次 API 请求要过三关：**认证（Authentication）→ 授权（Authorization）→ 准入控制（Admission）**。

```
请求到达 apiserver
   │
   ▼
① 认证 Authentication —— "你是谁？"
     · 客户端证书（kubectl 的 client cert）
     · Bearer Token（ServiceAccount / OIDC）
   │
   ▼
② 授权 Authorization —— "你能做这个吗？"
     · RBAC（主流）
     · ABAC / Node / Webhook（少用）
   │
   ▼
③ 准入控制 Admission —— "这个请求本身合规吗？"
     · 内置：NamespaceLifecycle、ResourceQuota…
     · 动态：ValidatingWebhook / MutatingWebhook（Kyverno/OPA、PSA）
   │
   ▼
写入 etcd
```

### 2.1 认证：三种身份

| 身份类型 | 说明 | 用途 |
|:---------|:-----|:-----|
| **User（用户）** | 由外部系统（证书/OIDC）确认，K8s 不存用户对象 | 人（运维、开发）|
| **Group（组）** | 用户所属组，RBAC 里按组授权 | 团队批量授权 |
| **ServiceAccount（服务账号）** | **K8s 原生对象**，给 Pod 内进程用 | 工作负载访问 API |

> **重要**：ServiceAccount 是**命名空间级**资源，是"**给程序用的账号**"。Pod 里默认会挂一个 SA token（`/var/run/secrets/kubernetes.io/serviceaccount/token`），Pod 拿它就能调 apiserver —— **所以给 SA 授权要极其克制**。

```bash
# 关掉 Pod 自动挂载 SA token（不需要访问 API 的工作负载就该关）
spec:
  automountServiceAccountToken: false
```

### 2.2 RBAC：授权的核心

**三要素：谁（Subject）+ 能做什么（Role）+ 绑定（Binding）**。

```
Subject（User / Group / ServiceAccount）
     │ 通过
     ▼
Role / ClusterRole（一组 rules：apiGroups + resources + verbs）
     │ 绑定
     ▼
RoleBinding / ClusterRoleBinding
```

| 对象 | 作用范围 | 用途 |
|:-----|:---------|:-----|
| **Role** | 单个命名空间 | ns 内权限（如"能读写本 ns 的 Pod"）|
| **ClusterRole** | 全集群 | 跨 ns 资源（nodes/ns/pv）、或定义后供 RoleBinding 复用 |
| **RoleBinding** | 绑定 Role 或 ClusterRole 到**某 ns 内**主体 | ns 级授权 |
| **ClusterRoleBinding** | 绑定 ClusterRole 到**全集群**主体 | 集群级授权 |

```yaml
# 示例：给一个 SA 只读某 ns 的 Pod（最小权限）
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
  - apiGroups: [""]            # "" = core API group
    resources: ["pods"]
    verbs: ["get", "list", "watch"]    # 只读，不给 create/delete
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
  - kind: ServiceAccount
    name: my-app
    namespace: dev
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

```bash
# 排查权限（最常用两条）
kubectl auth can-i list pods --as=system:serviceaccount:monitoring:default
kubectl auth can-i '*' '*' --all-namespaces          # 危险信号：不该有人能全通
```

**RBAC 避坑:**

| 坑 | 说明 |
|:---|:-----|
| `verbs: ["*"]` + `resources: ["*"]` | 等于集群管理员，**绝对禁止**给应用 |
| ClusterRoleBinding 给 default SA | 默认 SA 被大量 Pod 共用，一授权全员受益 |
| `secrets` 读权限 | 拿到就能读所有密钥，等同提权（`get secret` ≈ `get token`）|
| 忘了 RoleBinding 的 ns | Role 是 ns 级的，跨 ns 不生效 |

> **典型场景**：Prometheus 需要读集群资源做服务发现，得给它一个**只读** ClusterRole（nodes/pods/services/endpoints）。**漏配 RBAC 就会报 `pods is forbidden`** —— 这正是授权的必要性：ServiceAccount 不配 RBAC＝什么都读不到。

### 2.3 准入控制：请求的最后一道闸

授权通过 ≠ 一定放行。**准入控制器**能在对象落库前**校验（Validating）或修改（Mutating）**它。

| 类型 | 作用 | 例子 |
|:-----|:-----|:-----|
| **Validating** | 不通过就拒绝 | 禁止 hostNetwork、强制加 labels |
| **Mutating** | 修改对象 | 自动注入 sidecar、补默认 resources |

**两种主流落地方式:**

| 方案 | 特点 | 工具 |
|:-----|:-----|:-----|
| **Pod Security Admission（PSA）** | K8s 内置（1.25+ GA），按 ns 打标签 | 不用装 |
| **策略引擎** | 功能强，可写任意规则 | **Kyverno**（YAML 友好）/ OPA Gatekeeper（Rego）|

```bash
# PSA：给命名空间打标签，强制安全等级
kubectl label ns dev pod-security.kubernetes.io/enforce=restricted
```

```yaml
# Kyverno 示例：禁止创建带 hostNetwork 的 Pod
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: disallow-host-network }
spec:
  validationFailureAction: Enforce
  rules:
    - name: host-network
      match:
        any:
          - resources: { kinds: [Pod] }
      validate:
        message: "hostNetwork 不允许"
        pattern:
          spec: { hostNetwork: "false" }
```

## 三、Pod 安全：工作负载能做什么

K8s 用 **Pod Security Standards（PSS）** 定义三档安全等级，再通过 **Pod Security Admission（PSA）** 在 ns 级别强制执行。

### 3.1 三档安全等级（PSS）

| 等级 | 说明 | 适用 |
|:-----|:-----|:-----|
| **Privileged** | 无限制（等于没有约束）| 系统组件、需要特权的 Agent |
| **Baseline** | 阻止已知提权（禁 hostNetwork/hostPID、禁 privileged）| 大多数业务 |
| **Restricted** | 最严：必须非 root、必须丢弃所有 capability、只读根文件系统 | 高安全业务 |

```bash
# ns 级强制（enforce=拒绝 / audit=记录 / warn=警告）
kubectl label ns prod \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted
```

### 3.2 securityContext：容器级安全

这是**最需要手动配的一块**——很多"必须 root 才能跑"其实是没配 securityContext。

```yaml
spec:
  securityContext:              # Pod 级：对所有容器生效
    runAsNonRoot: true          # 禁止以 root 运行
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000               # 卷的属组
    seccompProfile:             # 系统调用过滤（收窄内核攻击面）
      type: RuntimeDefault
  containers:
    - name: app
      image: myapp:v1
      securityContext:          # 容器级：覆盖 Pod 级
        allowPrivilegeEscalation: false    # 禁止提权（setuid 等）
        readOnlyRootFilesystem: true       # 根文件系统只读
        privileged: false
        capabilities:
          drop: ["ALL"]                     # 丢弃所有 Linux capability
          add: ["NET_BIND_SERVICE"]         # 只加必需的（如绑 80 端口）
        runAsNonRoot: true
```

**几个关键项为什么重要:**

| 配置 | 防住的攻击 |
|:-----|:-----------|
| `runAsNonRoot: true` | 容器内 root 逃逸到宿主的风险 |
| `allowPrivilegeEscalation: false` | setuid 程序提权 |
| `readOnlyRootFilesystem: true` | 攻击者写入恶意文件持久化 |
| `capabilities.drop: ["ALL"]` | 用不需要的内核能力（如 CAP_SYS_ADMIN）搞事 |
| `seccompProfile: RuntimeDefault` | 减少可用系统调用面 |

> ⚠️ **只读根文件系统的代价**:应用可能要写临时文件 → 需要额外挂 `emptyDir` 到 `/tmp`。
> ⚠️ **有些镜像天生要 root**（如 nginx 默认绑 80）→ 换非 root 镜像版本，或只加 `NET_BIND_SERVICE`。

### 3.3 Pod 安全相关字段速查

| 字段 | 风险 | 安全建议 |
|:-----|:-----|:---------|
| `hostNetwork: true` | 用宿主网络，可嗅探/占端口 | 尽量不用（除 node-exporter 类）|
| `hostPID: true` | 能看到宿主所有进程 | 同理，非必需不用 |
| `hostPath` 卷 | 挂宿主目录，可能读敏感文件 | 限制路径，用只读挂载 |
| `privileged: true` | 等同于宿主 root | **几乎永远不该用** |
| `automountServiceAccountToken` | 自动挂 SA token | 不需要 API 就设 `false` |

> **典型场景**：node-exporter / Promtail 这类 DaemonSet 必须用 `hostNetwork: true`（要采宿主指标/日志），属于**合理例外** —— 但要配 RBAC 最小化 + 单独 ns 隔离。这就是「安全例外要显式声明并记录原因」的实践。

## 四、网络安全：谁能访问谁

### 4.1 默认全通 → NetworkPolicy 收紧

**K8s 默认：Pod 之间网络全通**（同 ns、跨 ns 都能互访）。这是"零信任"最该补的一课。

**NetworkPolicy** 是"Pod 级防火墙"——**声明谁能进/出**。

```yaml
# 示例：只允许 frontend 访问 backend 的 8080，其他全拒
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-allow-frontend
  namespace: prod
spec:
  podSelector:
    matchLabels: { app: backend }      # 这个策略作用于 backend Pod
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: frontend }   # 只允许 frontend
      ports:
        - protocol: TCP
          port: 8080
---
# 默认拒绝所有入站（该 ns 的兜底策略，最实用的一招）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}                      # 空 = 选中所有 Pod
  policyTypes: [Ingress]               # 不写 ingress 规则 = 全拒
```

| 要点 | 说明 |
|:-----|:-----|
| **需要 CNI 支持** | Calico / Cilium 支持；**Flannel 不支持**（策略会被忽略！）|
| **默认拒绝思想** | 先建 `default-deny`，再逐条放行 |
| **入站/出站都要管** | `policyTypes: [Ingress, Egress]` |
| **空 podSelector** | `{}` 表示选中 ns 内所有 Pod |

> ⚠️ **踩坑提醒**：k3s 默认 CNI 是 **Flannel —— 不支持 NetworkPolicy**。要上网络策略得换/叠加 Calico，或启用变体后端 + 额外组件。**上策略前先确认 CNI 支不支持，否则策略会被静默忽略。**

### 4.2 服务暴露面的收紧

| 暴露方式 | 风险 | 收紧建议 |
|:---------|:-----|:---------|
| NodePort | 每节点开端口，全公网可达 | 云安全组限源 IP；能 ClusterIP 就别 NodePort |
| LoadBalancer | 直接对外 | 配 WAF / 只开必要端口 |
| Ingress | 七层入口，可能配错 | 强制 TLS、限 path、加认证 |
| **hostNetwork** | 直接占宿主端口 | 非必需不用 |

> **典型场景**：Grafana 用 NodePort 暴露 → 云安全组**必须限源**（只放行自己的 IP / 内网段），别裸奔公网；Prometheus 保持 ClusterIP 不对外。原则是**宁可多一层网关，不直接暴露**。

## 五、配置与密钥安全

### 5.1 Secret 的本质：默认不加密

**这是最大的认知误区**：Secret 默认只做 **base64 编码**，**不是加密**！

```bash
# 任何人都能解出来
echo "cGFzc3dvcmQxMjM=" | base64 -d      # → password123
```

**它能拿到的方式:**
- `kubectl get secret -o yaml`（有 RBAC 权限就能读）
- etcd 里明文（除非开静态加密）
- Pod 里挂载的文件（能进 Pod 就能读）

### 5.2 加固手段

| 手段 | 做法 |
|:-----|:-----|
| **etcd 静态加密** | EncryptionConfiguration（AES-GCM），落盘加密 |
| **RBAC 收紧** | 严格控制谁能 `get secrets`（这是提权跳板）|
| **关闭自动挂载** | `automountServiceAccountToken: false` |
| **外部密钥管理** | Sealed Secrets / External Secrets Operator / Vault |
| **审计** | 开 Audit Log，记录 secret 读取 |

```yaml
# etcd 静态加密（各发行版均可配 encryption-config）
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources: ["secrets"]
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: <base64 32字节密钥>
      - identity: {}          # 兜底：未加密的老数据仍可读
```

### 5.3 镜像与供应链安全

| 环节 | 风险 | 手段 |
|:-----|:-----|:-----|
| 镜像来源 | 拉到来路不明的镜像 | 只用可信仓库（自建 Harbor / 云厂商 ACR）|
| 镜像内容 | 带漏洞/恶意软件 | **镜像扫描**（Trivy / Clair / 仓库自带扫描）|
| 完整性 | 镜像被篡改 | **镜像签名**（Cosign / Notary）|
| 拉取凭证 | 凭证泄露 | imagePullSecrets + 最小权限仓库账号 |

```bash
# Trivy 扫镜像漏洞（CI 里常用）
trivy image myapp:v1 --severity HIGH,CRITICAL

# 签名验证（准入控制里配 Cosign 校验，没签名不让跑）
cosign verify --key cosign.pub registry.example.com/myapp:v1
```

> **典型做法**：镜像统一走**私有仓库**（Harbor / 云厂商 ACR），凭证走 registry 配置 + imagePullSecrets；仓库开启自动漏洞扫描 —— 这就是「可信来源 + 扫描」的落地。

## 六、运行时安全与审计

### 6.1 运行时威胁检测

Pod 跑起来之后，还要防"**已经被攻破**"的情况：

| 工具 | 作用 |
|:-----|:-----|
| **Falco** | 基于 eBPF/内核事件，检测异常行为（起 shell、读 /etc/shadow、异常外联）|
| **Cilium Tetragon** | eBPF 运行时安全，可阻断 |
| **Audit Log** | apiserver 层面记录"谁做了什么"|

```yaml
# Falco 规则示例：容器里起 shell 告警
- rule: Terminal shell in container
  desc: 容器内出现交互式 shell（常见入侵特征）
  condition: >
    spawned_process and container and
    proc.name in (bash, sh, zsh) and proc.tty != 0
  output: "Shell spawned in container (user=%user.name container=%container.id)"
  priority: WARNING
```

### 6.2 审计日志

apiserver 的 Audit Log 记录**每一次 API 调用**（谁、什么时间、对什么资源、什么操作、结果）。

```yaml
# 审计策略（关键：记录 secret 访问、exec 进容器、RBAC 变更）
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  - level: RequestResponse          # 记录请求+响应体（最详细）
    resources:
      - group: ""
        resources: ["secrets"]
  - level: Metadata                 # 只记元数据
    omitStages: ["RequestReceived"]
    verbs: ["get", "list", "watch"]
```

> **必查的三个高危操作**：读 Secret、`kubectl exec` 进容器、改 RBAC —— 这三样是横向移动/提权的典型路径。

## 七、安全落地清单

按代价从低到高、收益从高到低排序（**零成本的先做**）：

| 项 | 建议 | 成本 |
|:---|:-----|:-----|
| **RBAC** | 应用权限最小化；定期 `kubectl auth can-i --list` 审；别给 `*` | 零 |
| **SA token** | 不需要访问 API 的 Pod 设 `automountServiceAccountToken: false` | 零 |
| **Secret** | etcd 静态加密；secrets 读权限收紧 | 低 |
| **公网暴露** | NodePort / LB 一律**云安全组限源**；Prometheus 等保持 ClusterIP | 零 |
| **PSA** | 业务 ns 逐步上 `baseline`（先 `warn` 观察）| 低 |
| **镜像** | 统一私有仓库 + 开漏洞扫描；imagePullSecrets 最小权限 | 低 |
| **NetworkPolicy** | 上 `default-deny` + 逐条放行（**先确认 CNI 支持**）| 中（可能要换 CNI）|
| **审计** | 关键 ns 开 Audit Log（记 secret / exec / RBAC 变更）| 中 |
| **运行时检测** | Falco / Tetragon 检测异常行为 | 高（吃资源）|

> **小机现实**：小规格节点跑不起重型安全组件（Falco / Gatekeeper 都要资源）。优先级：**RBAC 最小化 → Secret 加固 → 安全组限源**（零成本）> PSA > NetworkPolicy（需换 CNI）> 运行时检测。

## 八、安全速查表

| 层面 | 机制 | 一句话 |
|:-----|:-----|:-------|
| 认证 | 证书 / Token / OIDC | 你是谁 |
| 授权 | **RBAC** | 你能做什么（最小权限）|
| 准入 | PSA / Kyverno | 请求合规才放行 |
| Pod 安全 | securityContext / PSS | 非 root、丢 capability、只读根 |
| 网络 | **NetworkPolicy** | 默认拒绝，显式放行（需 CNI 支持）|
| 配置 | Secret + 静态加密 | base64 ≠ 加密，务必落盘加密 |
| 镜像 | 扫描 + 签名 | 可信来源，漏洞出不去 |
| 运行时 | Falco / 审计日志 | 检测异常行为 |
| 通用 | 最小权限 + 零信任 | **一切机制的出发点** |
