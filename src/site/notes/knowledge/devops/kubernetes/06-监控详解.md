# Node-exporter + Prometheus + Grafana 部署实战（跨节点公网采集 · 2026-09）

> 完整一套主机监控：三处 **node-exporter** 采集端（裸机 docker-compose + k3s DaemonSet）→ 一台中央 **Prometheus** 从公网抓取 → **Grafana** 展示。
> 覆盖节点：① 裸机 OpenCloudOS（公网 `122.51.10.97`）② k3s 双节点（杭州 server `47.99.57.217`、上海 agent `101.133.228.245`）③ 中央一台自行控制（Prometheus 9090 + Grafana 3000）。
> 方案 A：node-exporter 公网直连（`/metrics` 无鉴权，安全提示在文末，务必看）。

## 二、采集端① 裸机 —— docker compose 部署 node-exporter

本机（OpenCloudOS 9.4 / x86_64，公有 IP `122.51.10.97`），用 docker compose 最省事。

```bash
mkdir -p /opt/node-exporter && cd /opt/node-exporter
```

`docker-compose.yml`：
```yaml
services:
  node-exporter:
    image: prom/node-exporter:v1.8.2
    container_name: node-exporter
    restart: unless-stopped
    network_mode: host                       # 直接用宿主机 9100
    command:
      - --path.procfs=/host/proc
      - --path.sysfs=/host/sys
      - --path.rootfs=/host
      - --collector.filesystem.mount-points-exclude=^/(sys|proc|dev|host|etc)($|/)
    volumes:
      - /proc:/host/proc:ro
      - /sys:/host/sys:ro
      - /:/rootfs:ro,rslave
```

启动并验证：
```bash
docker compose up -d
curl -s localhost:9100/metrics | head -3
```

> ⚠️ `122.51.10.97` 是 Jenkins 同机（docker 8080）。9100 建议安全组只放行中央 Prometheus IP，别全网开 0.0.0.0/0。

## 三、采集端② k3s 双节点 —— DaemonSet 部署

每节点自动 1 个 pod，同样走节点 host 9100。

`node-exporter.yaml`：
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
spec:
  selector:
    matchLabels: { app: node-exporter }
  template:
    metadata:
      labels: { app: node-exporter }
    spec:
      hostNetwork: true
      terminationGracePeriodSeconds: 30
      tolerations:
        - { operator: Exists }
      containers:
        - name: node-exporter
          image: prom/node-exporter:v1.8.2
          args:
            - --path.procfs=/host/proc
            - --path.sysfs=/host/sys
            - --path.rootfs=/host
          ports:
            - { name: metrics, containerPort: 9100, hostPort: 9100 }
          resources:
            requests: { cpu: 10m, memory: 30Mi }
            limits:   { cpu: 200m, memory: 128Mi }
          volumeMounts:
            - { name: proc, mountPath: /host/proc, readOnly: true }
            - { name: sys,  mountPath: /host/sys,  readOnly: true }
            - { name: root, mountPath: /host, readOnly: true, mountPropagation: HostToContainer }
      volumes:
        - { name: proc, hostPath: { path: /proc } }
        - { name: sys,  hostPath: { path: /sys } }
        - { name: root, hostPath: { path: / } }
```

在 k3s server 上部署（注意：这台 server 内存 2G 很紧，先确认负载不高再 apply）：
```bash
ssh root@47.99.57.217
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
kubectl create ns monitoring 2>/dev/null || true
kubectl apply -f node-exporter.yaml
kubectl get pods -n monitoring -o wide      # 两节点各 1 Running
curl -s localhost:9100/metrics | head -3    # 节点本机验证
curl -s 101.133.228.245:9100/metrics | head -3  # 公网验证
```

> node-exporter 资源极省（~30Mi/节点 / 近 0 CPU），2C/1.9G 小机无压力，可放心开。

## 四、中央端(③)：Prometheus + Grafana（docker compose 为主）

假定中央机有 docker + compose。目录 `/opt/monitoring/`：
```text
/opt/monitoring/
├── docker-compose.yml
└── prometheus/
    └── prometheus.yml
```

### 1) `prometheus/prometheus.yml` —— 核心抓取配置
```yaml
global:
  scrape_interval:     30s      # 小机器 30-60s 省资源；默认 15s
  evaluation_interval: 30s

scrape_configs:
  # 裸机 node-exporter
  - job_name: 'node-baremetal'
    static_configs:
      - targets: ['122.51.10.97:9100']
        labels: { source: 'baremetal' }

  # k3s 双节点
  - job_name: 'node-k3s'
    static_configs:
      - targets:
          - '47.99.57.217:9100'
          - '101.133.228.245:9100'
        labels: { source: 'k3s' }

  # Prometheus 自监控（可选）
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']
```

### 2) `docker-compose.yml`
```yaml
services:
  prometheus:
    image: prom/prometheus:v2.53.0
    container_name: prometheus
    restart: unless-stopped
    volumes:
      - ./prometheus:/etc/prometheus
      - prom-data:/prometheus
    ports:
      - "9090:9090"
    command:
      - --config.file=/etc/prometheus/prometheus.yml
      - --storage.tsdb.retention.time=30d
      - --web.enable-lifecycle

  grafana:
    image: grafana/grafana:11.2.0
    container_name: grafana
    restart: unless-stopped
    environment:
      - GF_SECURITY_ADMIN_USER=admin
      - GF_SECURITY_ADMIN_PASSWORD=***   # 更换为强密码
      - GF_USERS_ALLOW_SIGN_UP=false
    volumes:
      - grafana-data:/var/lib/grafana
    ports:
      - "3000:3000"
    depends_on: [prometheus]

volumes:
  prom-data:
  grafana-data:
```

### 3) 启动与验证
```bash
cd /opt/monitoring
docker compose up -d
docker compose ps
curl -s localhost:9090/api/v1/targets | grep -E '"health"|"job"' | head   # targets 应 UP
```
> 若中央机不想用 docker，可用二进制同步配置运行（见文末「二进制替代」）。

## 五、核心监控指标 & PromQL（可视化/告警层）

从 3 个 node-exporter 抓到的是 `node_*` 系列。按"1(裸机) + 2(k3s 两台)独立看"最常用查询如下。

### CPU 使用率
```promql
100 - avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100
```
这台 k3s 曾 `iowait 87%`，单独看磁盘等待很关键：
```promql
100 * avg by(instance)(rate(node_cpu_seconds_total{mode="iowait"}[5m])) /
      sum by(instance)(rate(node_cpu_seconds_total[5m]))
```
负载：`node_load5`

### 内存可用率
```promql
100 * node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
```
swap 剩余比（这台有 swap）：`node_memory_SwapFree_bytes / node_memory_SwapTotal_bytes`

### 磁盘使用率（盘常满，重点）
```promql
100 - 100 * node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}
```

### 网络吞吐（rate 字节/s）
`rate(node_network_receive_bytes_total[5m])` / `rate(node_network_transmit_bytes_total[5m])`

### 磁盘 IO 压力
`rate(node_disk_io_time_seconds_total[5m])` —— 反映盘忙不忙（wa 高时盯这个）

### 运行时长
`time(node_boot_time_seconds)` 差值 = 在线时长

> `by(instance)` 会把裸机 + k3s 两台分开成多线；想只挑某台在 PromQL 加 `instance="101.133.228.245:9100"`。

**建议告警阈值**：内存可用 <10%、磁盘 / >85%、IO wait 持续高、`up{job="node-*"} == 0`（掉线）。

## 六·补、Grafana 视图（View）导览

上面是"手搓面板"的入门路子；真正上生产后，kube-prometheus-stack 会随 chart 自带一整套**预置 dashboard（视图）**，开箱即用。本节按视图分类逐个说明**看什么、什么指标、什么时候盯**。

> 入口：Grafana 左侧 `Dashboards → Browse`，按 folder 分组（`General` / `Kubernetes` / `Prometheus` 等）。预置视图来自 chart 的 `grafana.dashboardProviders` + sidecar 自动发现，随 ConfigMap 挂入。

### 视图速查表

| 视图 | 对应 dashboard | 数据源 | 主要回答 |
|:-----|:--------------|:------|:--------|
| **apiserver** | Kubernetes / API Server | kube-apiserver `/metrics` | 控制面健不健康、请求延迟、限流 |
| **cluster** | Kubernetes / Cluster (Global) | kube-state-metrics 聚合 | 集群总览：节点/Pod/Deploy 数量、容量 |
| **coredns** | CoreDNS | CoreDNS service `/metrics` | DNS 解析量、错误、延迟 |
| **fluentbit** | Fluent Bit | Fluent Bit 自带 `/api/v1/metrics` | 日志采集吞吐、丢弃、重试 |
| **gpuxgpu** | NVIDIA DCGM Exporter / GPU 视图 | DCGM Exporter | GPU 利用率、显存、温度、功耗（见下文说明）|
| **host** | Node Exporter Full（1860）等 | node-exporter | 物理机/虚机资源：CPU/内存/磁盘/网卡 |
| **node** | Kubernetes / Nodes | kubelet + node-exporter | 节点级资源与调度状态、节点就绪 |
| **pod** | Kubernetes / Pods、Compute Resources | cAdvisor | Pod 级 CPU/内存/网络、重启、OOM |
| **prometheus** | Prometheus / Overview | Prometheus 自监控 | 抓取是否成功、TSDB 大小、查询延迟 |
| **pvc** | Kubernetes / Persistent Volumes | kube-state-metrics | PVC 容量、使用率、绑定状态 |

### 1. apiserver（API Server）

**看什么**：控制面性能与稳定性。

- 请求速率 / 每秒请求数（`apiserver_request_total`）
- **请求延迟分位**（`apiserver_request_duration_seconds` P99）—— 慢请求是控制面卡顿第一信号
- **限流**（`apiserver_flowcontrol_rejected_requests_total`）与 429 数
- 在途请求（`apiserver_current_inflight_requests`）、watch 连接数
- etcd 交互延迟（`etcd_request_duration_seconds`）

**什么时候盯**：`kubectl` 变慢、HPA 扩容不及时、Controller 反应迟钝时。k3s 这类小集群 API 单点，是**最先被压垮的一环**（本项目 09-07 就遇到过"冷建单节点压垮杭州 API"）。

> ⚠️ k3s 的 apiserver 默认监听 `127.0.0.1:6444/6443`，Prometheus 抓不到 → 需要 ServiceMonitor 指向 `kubernetes` Service，或确认 chart 的 `kubeApiServer` 组件已开。

### 2. cluster（Cluster / Global）

**看什么**：一屏看全集群家底。

- 节点数（Ready/NotReady）、Pod 总数与容量上限
- Deployment / StatefulSet / DaemonSet 副本数（期望 vs 就绪）
- CPU / 内存 / 存储的 **Request 与 Limit 总量 vs 节点可分配量**
- 命名空间级资源占用排行

**什么时候盯**：日常巡检查容量、上生产前评估"还塞得下多少"。本项目 42 台机器全部独享 + 双污点策略，这个视图能直观印证"0 剩余"的饱和状态。

### 3. coredns（CoreDNS）

**看什么**：集群内服务发现健不健康。

- DNS 查询速率（`coredns_dns_requests_total`）按 type（A/AAAA/SRV）
- **错误响应**（`coredns_dns_responses_total{rcode=~"SERVFAIL|NXDOMAIN"}`）
- 延迟分位（`coredns_dns_request_duration_seconds`）、缓存命中率（`coredns_cache_hits_total` vs `coredns_cache_misses_total`）

**什么时候盯**：Pod 里 `nslookup` 超时、Service 名偶发解析不到、服务间调用偶发 5xx。

指标（Prometheus）回答"忙不忙"，日志回答"出了什么事"。两者在 Grafana 里同一个看板，排障时来回切。**轻量栈推荐 Promtail → Loki → Grafana**，比 ELK 省一个数量级的内存，适合本项目这种小机场景。

### 4. fluentbit（Fluent Bit）

**看什么**：日志采集链路自身是否健康（**注意采日志的组件自己也要监控**）。

- 输入/输出吞吐：`fluentbit_input_records_total`、`fluentbit_output_records_total`
- **丢弃**：`fluentbit_output_dropped_records_total` —— 不为 0 就是日志丢了
- 重试/错误：`fluentbit_output_retries_total`、`fluentbit_output_errors_total`
- 缓冲区占用（`fluentbit_output_proc_bytes`）—— 堆积说明下游（Loki/ES）写入跟不上

**什么时候盯**：日志缺块、Grafana 查不到最新日志、下游存储写满时。

> ⚠️ 本项目轻量栈用的是 **Promtail**（见第七节），Fluent Bit 是 7.1 选型表里的"超小机/边缘"替代项。若换 Fluent Bit，需在它自己的 `prometheus` 输出插件暴露上述指标 + 建对应 dashboard。此视图属于**可选/扩展**。

### 5. gpuxgpu（GPU 视图）

**看什么**：GPU 卡级利用率与健康（AI 训练/推理场景必看）。

- **利用率**：`DCGM_FI_DEV_GPU_UTIL`（卡忙不忙）、SM/Memory 分项
- **显存**：`DCGM_FI_DEV_FB_USED` / `FB_FREE`（vs `FB_TOTAL`）—— 显存泄漏比利用率更致命
- **温度/功耗**：`DCGM_FI_DEV_GPU_TEMP`、`DCGM_FI_DEV_POWER_USAGE`（撞温度墙会降频）
- **ECC/XID 错误**：`DCGM_FI_DEV_ECC_*`、XID 报错 —— 硬件故障最直接的证据
- 若走 **xGPU/GPU 虚拟化**：额外看 vGPU 实例分配数、切分后各实例占用

**什么时候盯**：训练任务变慢、OOM / 显存不足、卡掉线（XID）、多租户抢卡。

> ⚠️ 说明：**kube-prometheus-stack 默认不含 GPU 视图**。"gpuxgpu"需要额外接 **NVIDIA DCGM Exporter**（`nvcr.io/nvidia/k8s/dcgm-exporter`）作为 ServiceMonitor，再导入社区 GPU dashboard（如 Grafana id `12239`）。裸金属 GPU 机器还需装 NVIDIA driver + `nvidia-container-toolkit`。此视图为**扩展项**，有 GPU 节点才需要。

### 6. host（主机 / Node Exporter Full）

**看什么**：物理机 / 云主机整机资源。

- CPU 使用率 / iowait / 负载（`node_load*`）
- 内存可用率、swap（`node_memory_*`）
- 磁盘使用率（`node_filesystem_*`）、磁盘 IO（`node_disk_*`）
- 网卡吞吐 / 丢包（`node_network_*`）

**什么时候盯**：第五节的 PromQL 手动版不够看时，直接导入 **dashboard id `1860`（Node Exporter Full）**，一屏含 100+ 面板，是本项目最实用的主机视图。

### 7. node（Kubernetes / Nodes）

**看什么**：K8s 视角的**节点**（区别于 host 的纯 OS 视角）。

- 节点 Ready / NotReady（`kube_node_status_condition`）
- 节点上 Pod 数 / 容量、可分配 CPU·内存
- 节点级 CPU/内存 Request 与 Limit 占用
- Node 污点 / 不可调度状态

**什么时候盯**：**NotReady 是最该告警的信号**——本项目 09-06 就因 `NodeNotReady + API 连接抖动` 引发了一轮重启风暴（grafana×16 / ksm×17）。节点挂了，上面的 Pod 全部连锁重启。

### 8. pod（Kubernetes / Pods、Compute Resources）

**看什么**：Pod 级细粒度资源与生命周期。

- Pod CPU / 内存使用（cAdvisor `container_*` 系列）vs Request/Limit
- **重启次数**（`kube_pod_container_status_restarts_total`）—— 突增就是有问题
- **OOMKilled**（`kube_pod_container_status_last_terminated_reason`）—— 极限裁剪内存的典型后果
- Pod 状态相位（Running/Pending/Failed）、就绪探针失败
- 网络收发（`container_network_*`）

**什么时候盯**：服务变慢、容器反复重启、Pending 不调度。本项目 Grafana 512Mi OOM 循环（重启 113 次）正是靠 Pod 视图定位的；内存 Limit 压太狠的组件全在这个视图现形。

### 9. prometheus（Prometheus / Overview）

**看什么**：监控系统自监控（**监控也得被监控**）。

- **抓取目标**：UP / DOWN 数（`up`）、scrape 失败、scrape 耗时（`scrape_duration_seconds`）
- TSDB：样本数、`prometheus_tsdb_*`、内存占用、chunk 数
- 查询延迟（`prometheus_engine_query_duration_seconds`）、并发查询数
- 规则评估耗时、告警规则触发情况（`prometheus_rule_*`）

**什么时候盯**：target 掉线、TSDB 膨胀吃内存、Grafana 查询变卡。本项目 Prom limits 512Mi + 10Gi PVC，这个视图能提前预警 "Prometheus 自己 OOM"。

### 10. pvc（Persistent Volumes / PVC）

**看什么**：持久卷容量与状态。

- PVC 绑定状态（`kube_persistentvolumeclaim_status_phase`）—— Pending 就是没绑上
- **容量 / 已用**：`kubelet_volume_stats_used_bytes` / `capacity_bytes` —— 使用率必盯
- 剩余可用空间、inode（小文件多时 inode 先满）
- PV 与 StorageClass 对应关系

**什么时候盯**：Prometheus/Loki 等有状态组件盘写满、Pod 因存储驱逐。本项目 kps 的 Prom 10Gi / Grafana 2Gi 都是 local-path PVC，小盘场景尤其要看这个视图。

## 七、日志采集（Loki + Promtail）

| 方案 | 采集端 | 存储/查询 | 内存开销 | 适合 |
|:-----|:------|:---------|:--------|:-----|
| **Loki + Promtail**（本文）| Promtail（DaemonSet）| Loki（对象/本地盘 + LogQL）| 低（~百 MB 级）| 中小规模、Grafana 一体化 |
| ELK（Filebeat + ES + Kibana）| Filebeat | Elasticsearch | **高**（ES 单节点 GB 起步）| 全文检索重、大规模 |
| Fluent Bit + 任意后端 | Fluent Bit | 可写 Loki/ES/文件 | 极低 | 超小机、嵌入式边缘节点 |

> 部署方案里预留的就是 **Prometheus + Grafana + Loki 同机部署**（Loki 压到 2u 配额），本节即落地它。

### 7.2 架构

```
k3s 双节点容器日志（/var/log/containers/*.log）
   │ 每节点 Promtail（DaemonSet）tail + 打标签
   ▼
中央机 Loki :3100 ──> 本地盘存 chunk（retention 7~30d）
   │ Grafana 加 Loki 数据源
   ▼
Grafana Explore / 看板（与 Prometheus 指标同一入口，可互跳）
```

### 7.3 中央机：Loki + Grafana（docker compose，并入第四节的 compose）

`docker-compose.yml` 追加：
```yaml
  loki:
    image: grafana/loki:3.1.0
    container_name: loki
    restart: unless-stopped
    volumes:
      - loki-data:/loki
    ports:
      - "3100:3100"
    command: -config.file=/etc/loki/config.yml

  # 配套挂载：./loki/config.yml 内容如下
```

`loki/config.yml`（单机 monolithic 模式，最简）：
```yaml
auth_enabled: false
server:
  http_listen_port: 3100
common:
  path_prefix: /loki
  storage:
    filesystem:
      chunks_directory: /loki/chunks
      rules_directory: /loki/rules
  replication_factor: 1
  ring:
    kvstore:
      store: inmemory
schema_config:
  configs:
    - from: 2024-01-01
      store: tsdb
      object_store: filesystem
      schema: v13
      index:
        prefix: index_
        period: 24h
limits_config:
  retention_period: 168h        # 日志留 7 天，按需改
compactor:
  delete_request_store: filesystem
```

> Loki 3.x 单机用 `tsdb + filesystem` 即可，不用拉 MinIO；真要长期留再上对象存储。

Grafana 里 Add data source → **Loki** → URL `http://loki:3100` → Save & Test。

### 7.4 采集端：k3s 用 Promtail DaemonSet

`promtail.yaml`（采集所有容器 stdout/stderr + kubelet 系统日志，自动富化 pod/ns/container 标签）：
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: promtail
  namespace: monitoring
spec:
  selector:
    matchLabels: { app: promtail }
  template:
    metadata:
      labels: { app: promtail }
    spec:
      tolerations:
        - { operator: Exists }
      containers:
        - name: promtail
          image: grafana/promtail:3.1.0
          args: ["-config.file=/etc/promtail/config.yml"]
          resources:
            requests: { cpu: 10m, memory: 32Mi }
            limits:   { cpu: 100m, memory: 128Mi }
          volumeMounts:
            - { name: varlog, mountPath: /var/log }
            - { name: positions, mountPath: /run/promtail }
            - { name: config, mountPath: /etc/promtail }
      volumes:
        - { name: varlog, hostPath: { path: /var/log } }
        - { name: positions, emptyDir: {} }
        - name: config
          configMap:
            name: promtail-config
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: promtail-config
  namespace: monitoring
data:
  config.yml: |
    server:
      http_listen_port: 9080
    positions:
      filename: /run/promtail/positions.yaml
    clients:
      - url: http://<中央机IP>:3100/loki/api/v1/push   # 公网推，安全组限定来源
    scrape_configs:
      - job_name: kubernetes-pods
        kubernetes_sd_configs:
          - role: pod
        relabel_configs:
          - source_labels: [__meta_kubernetes_pod_node_name]
            action: replace
            target_label: instance
          - target_label: __path
            replacement: /var/log/pods/*$1/*.log
            source_labels: [__meta_kubernetes_pod_uid, __meta_kubernetes_pod_container_name]
            separator: /
          - source_labels: [__meta_kubernetes_namespace]
            target_label: namespace
          - source_labels: [__meta_kubernetes_pod_name]
            target_label: pod
          - source_labels: [__meta_kubernetes_pod_container_name]
            target_label: container
```

```bash
kubectl apply -f promtail.yaml
# 验证：Grafana Explore → 数据源选 Loki → 选择器 {namespace!=""} → 应刷出日志
```

### 7.5 裸机（组①）：systemd journal + 文件

```yaml
# /opt/monitoring/promtail/config.yml（docker 跑 promtail/grafana/promtail:3.1.0，挂 /var/log 与 /run/promtail）
scrape_configs:
  - job_name: syslog
    static_configs:
      - targets: [localhost]
        labels: { job: syslog, host: baremetal-122 }
    syslog:
      listen: 0.0.0.0:1514
      format: rfc3161
  - job_name: files
    static_configs:
      - targets: [localhost]
        labels: { job: varlogs, host: baremetal-122 }
    journal:
      path: /var/log/journal     # 读 systemd journal（jenkins/docker 日志都在）
      max_age: 12h
```

> 或者直接更简单：只加一个 `static_configs` tail `/var/log/jenkins/*.log` 之类的关键文件，按需选。

### 7.6 LogQL 速查（和 PromQL 一样先记三板斧）

```logql
# 1) 按标签过滤：某命名空间某 pod
{namespace="gitea", pod=~"gitea.*"}

# 2) 关键词 + 行解析：找报错
{job="varlogs"} |~ "(?i)error|oom|failed" | line_format "{{.message}}"

# 3) 统计速率（可配告警）：每分钟错误行数
sum(rate({namespace="monitoring"} |~ "(?i)error" [5m]))

# 4) 提取字段（logfmt / JSON）
{job="kubernetes-pods"} | json | container="node-exporter" | __error__=""
```

**建议告警（Loki ruler 或 Grafana Alerting）**：`count_over_time({namespace!=""} |~ "OOMKilled" [5m]) > 0`、`sum(rate(...error...[5m]))` 超阈值。

### 7.7 小机避坑

| 坑 | 现象 | 对策 |
|:---|:-----|:-----|
| Promtail 采集无限流 | 某容器刷日志把带宽/磁盘打爆 | scrape_configs 加 `pipeline_stages` 采样/丢弃；Loki 端限 `ingestion_rate_mb` |
| positions 丢了重采 | 节点重启日志重复灌 | positions 落 `emptyDir` 不行，重启就重 → 换 `hostPath: /var/lib/promtail` 持久化 |
| 公网 push 被扫 | :3100 是写接口，被人灌垃圾 | **安全组只放行两节点出口 IP**；更进一步加 basic auth（nginx 反代）|
| 磁盘写满 | Loki chunk 无限长 | `retention_period` + compactor 开启（上面 config 已配）；磁盘 >85% 告警 |
| 2G 节点跑不动 | OOM | Promtail limits 128Mi 已够；若还紧张换 **Fluent Bit**（内存减半）|

## 八、二进制替代（中央机不想 docker 时）

- **Prometheus**：下 tarball，`./prometheus --config.file=prometheus.yml &`（建议 systemd）。
- **Grafana**：yum/apt 装 grafana，管理员密码用 `GF_SECURITY_ADMIN_PASSWORD` env（systemd 里 `Environment=`）。
- 配置与第四、五、六节完全一致，仅无 compose 的 volume/restart 自动管理。

## 九、安全（公网暴露必读）

- 三地 `:9100` node-exporter **无鉴权**，公网能读节点名/OS/cpu/磁盘等元数据 + 易被扫。**建议各采集机云安全组 9100 只放行中央机公网 IP**，别开全网。
- **Grafana :3000** 公网入口：强密码 + `GF_USERS_ALLOW_SIGN_UP=false`（本方案已含）。
- **Prometheus :9090** 一般不对外，含全部抓取配置；如要用，安全组限定来源 IP。
- **Loki :3100 是写入端口**，公网裸奔会被灌垃圾日志；安全组限定采集端出口 IP（同 9100 的收紧思路）。
- 裸机那台还有 Jenkins，9100 更应收紧。
