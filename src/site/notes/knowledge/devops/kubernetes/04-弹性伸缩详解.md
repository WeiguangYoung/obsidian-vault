# K8s 调度与弹性伸缩详解

> 分两大块：**上半场「调度」**——Pod 该落到哪个节点（requests/limits、QoS、亲和性、污点容忍、优先级抢占、探针）；
> **下半场「伸缩」**——三层伸缩：**Pod 数（HPA）→ Pod 规格（VPA）→ 节点数（Cluster Autoscaler）**，外加事件驱动（KEDA）与落地判断。

---

## 一、调度基础：Pod 落到哪个节点

**调度（Scheduling）** 是 kube-scheduler 给每个新建 Pod 选节点的过程，分两步：

```
待调度 Pod
   │
   ▼
① 过滤 Filter —— 剔除所有不满足条件的节点
     · 资源不够（requests 之和 > 可分配）
     · 节点选择器 / 亲和性不符
     · 污点没被容忍（Taint 未 Tolerate）
   │
   ▼
② 打分 Score —— 给剩下的节点打分，选最高分绑定
     · 资源更均衡、亲和性更满足的节点得分高
   │
   ▼
绑定（Bind）→ Pod 被调度到该节点
```

> 一句话：**过滤决定「能不能上」，打分决定「上哪个」。** 这台不满意（被过滤）就换下一台。

### 1.1 requests 与 limits：调度与上限

这两个参数容易混，但作用完全不同：

- **requests** 是「**保证量**」——调度器按它找节点。一个节点上所有 Pod 的 requests 总和不能超过节点可分配容量，所以 requests 决定了 Pod **能不能**被调度上去。
- **limits** 是「**上限**」——运行时不能超。**超 CPU 会被限流（throttle）**（进程变慢但不死）；**超内存会被 Kill（OOMKilled）**（内存无法「限流」，只能杀）。

| 参数 | 作用阶段 | 超了会怎样 | 影响谁 |
|:-----|:---------|:-----------|:-------|
| requests | 调度期 | 调度不上去（Pending）| 调度器 |
| limits | 运行期 | CPU 限流 / 内存 OOMKilled | 内核 cgroup |

> ⚠️ **实践教训**：某 Grafana 曾因 limits 512Mi 太小反复 OOMKilled 重启上百次 → **limits 要按真实峰值给**，别一律压死；内存超限只会被 Kill（不像 CPU 能限流）。

### 1.2 QoS 与驱逐

Pod 被莫名赶走？这跟 **QoS（服务质量等级）** 有关。K8s 按 requests/limits 给 Pod 分三级，节点资源紧张时**按等级从低到高驱逐**：

| QoS 等级 | 条件 | 驱逐优先级 |
|:---------|:-----|:-----------|
| **Guaranteed** | 每个容器 requests == limits | 最低（最后逐）|
| **Burstable** | 设置了但两者不等 | 中 |
| **BestEffort** | 完全没设置 | 最高（最先逐）|

**驱逐（Eviction）触发条件**：节点内存/磁盘到 `eviction-hard` 阈值（如 memory.available<100Mi）→ kubelet 按 QoS 优先级杀 Pod，腾出资源。

> 生产关键服务：要么设 Guaranteed，要么给足 requests，别让它在资源紧张时第一个被牺牲。

### 1.3 探针：判断 Pod「活着」和「能干活」

三种探针**失败后果不同**，用错会带来麻烦：

| 探针 | 判断 | 失败后果 |
|:-----|:-----|:---------|
| **livenessProbe** | 进程还活着吗 | 重启容器 |
| **readinessProbe** | 准备好接流量了吗 | 从 Service 摘除（**不重启**）|
| **startupProbe** | 启动完成了吗 | 完成前不执行 liveness |

关键区别：**liveness 失败会重启**，只该判断「进程是不是死了」。拿它判断「依赖的数据库连不上」会导致 Pod 反复重启雪崩——这种情况应该用 readiness（摘流量，等依赖恢复再接）。

```yaml
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 10
  periodSeconds: 10
  failureThreshold: 3          # 连续 3 次失败才重启（别设 1，容易误杀）
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 3
startupProbe:                   # 启动慢的应用（如 Java）必备
  httpGet: { path: /healthz, port: 8080 }
  failureThreshold: 30
  periodSeconds: 10             # 最长容忍 300s 启动
```

> ⚠️ **实践教训**：CoreDNS 曾因 `Readiness probe failed`（健康端口超时）反复重启 → **探针超时值给太小、内存限制太紧都会引发周期性自杀**，排障时先看 `describe pod` 的探针失败记录。

## 二、节点选择：标签与亲和性

调度器怎么知道「这个 Pod 想去哪」？靠四层递进的选择机制：

| 机制 | 粒度 | 表达式能力 | 场景 |
|:-----|:-----|:-----------|:-----|
| **nodeName** | 直接指定 | 无（硬绑定）| 调试、临时 |
| **nodeSelector** | 标签等值匹配 | 只能 `key=value` | 简单固定（如钉 GPU 节点）|
| **nodeAffinity** | 标签表达式 | In/NotIn/Exists/Gt/Lt + 软硬 | 复杂节点选择 |
| **podAffinity/AntiAffinity** | Pod 间关系 | 与已有 Pod 同/异节点 | 高可用、数据本地性 |

### 2.1 nodeSelector：最简单的钉节点

```yaml
spec:
  nodeSelector:
    kubernetes.io/hostname: gpu-node-1   # 只调度到该节点
```

> **典型场景**：把有状态/重负载组件**钉到资源最宽裕的节点**，避免落到小规格节点撑爆 —— 用 `nodeSelector: kubernetes.io/hostname=<节点名>` 最简单直接。

### 2.2 nodeAffinity：带表达式的节点亲和

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:    # 硬约束：必须满足
        nodeSelectorTerms:
          - matchExpressions:
              - key: kubernetes.io/os
                operator: In
                values: [linux]
      preferredDuringSchedulingIgnoredDuringExecution:   # 软约束：尽量满足
        - weight: 100
          preference:
            matchExpressions:
              - key: disktype
                operator: In
                values: [ssd]
```

- **required**（硬）：不满足就不调度（Pod Pending）
- **preferred**（软）：尽量满足，不满足也能调度（可配 weight 权重）
- **「IgnoredDuringExecution」**：调度后节点标签变了，**不会**驱逐已运行的 Pod（对比污点能做到，见 2.3）

### 2.3 污点与容忍（Taints / Tolerations）

**这是「调度」范畴里最实用的一对概念**——节点给 Pod 设「门槛」（污点），Pod 声明「我能忍」（容忍），两个都满足才能上去。

```
节点打污点（Taint）    →  排斥不能容忍它的 Pod
   │
   ▼
Pod 声明容忍（Toleration）→  才允许调度到带该污点的节点
```

**污点的三种效果（effect）**：

| effect | 含义 | 对已运行 Pod |
|:-------|:-----|:-------------|
| **NoSchedule** | 新 Pod 不能调度（除非容忍）| 已运行的不动 |
| **PreferNoSchedule** | 尽量不调度（软）| 已运行的不动 |
| **NoExecute** | 不能调度 **+ 驱逐** 不容忍的已运行 Pod | **会驱逐！** |

```bash
# 给节点打污点：专用于某类负载 / 隔离节点
kubectl taint nodes node-1 dedicated=node-1:NoSchedule

# 查污点
kubectl describe node node-1 | grep -i taint

# 移除污点（末尾加 -）
kubectl taint nodes node-1 dedicated-
```

```yaml
# Pod 声明容忍
spec:
  tolerations:
    - key: dedicated
      operator: Equal          # Equal / Exists
      value: gpu-node-1
      effect: NoSchedule
    - key: node-role.kubernetes.io/control-plane
      operator: Exists         # 容忍所有控制面污点（DaemonSet 常用）
      effect: NoSchedule
```

> **典型策略**：给节点打**组合污点**（如 `workload` + `dedicated` 两个），只有显式容忍的工作负载能上去，实现「独享节点」；配合 PriorityClass 分档（关键/普通/可牺牲）做优先级保障。
> **DaemonSet 的容忍**：node-exporter / Promtail 这类 DaemonSet 需要 `operator: Exists` 容忍所有污点，才能在每个节点都跑起来。

### 2.4 Pod 亲和与反亲和（Affinity / Anti-Affinity）

控制 **Pod 之间**的落点关系：**亲和**（想在一起）/ **反亲和**（想分开）。

```yaml
spec:
  affinity:
    podAntiAffinity:                            # 反亲和：别落同一个节点
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels: { app: myapp }
          topologyKey: kubernetes.io/hostname   # 按「主机」维度分散
```

| 类型 | 作用 | 场景 |
|:-----|:-----|:-----|
| **podAffinity** | 和指定 Pod 落同节点 | 缓存/应用同节点（降延迟）|
| **podAntiAffinity** | 和指定 Pod 落不同节点 | 同一服务多副本分散（高可用）|
| **topologySpreadConstraints** | 按拓扑域均匀分布 | 比反亲和更灵活的多副本分散 |

```yaml
# 拓扑分布：让副本均匀分布在各节点（推荐替代反亲和做高可用）
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname
      whenUnsatisfiable: DoNotSchedule
      labelSelector:
        matchLabels: { app: myapp }
```

> **最佳实践**：高可用组件配 `topologySpreadConstraints` + `podAntiAffinity` + `PDB` 三件套，保证副本分散到不同节点、且驱逐时不一次性全挂。

### 2.5 优先级与抢占（PriorityClass / Preemption）

资源不够时，**高优先级的 Pod 能「插队」挤掉低优先级的**。

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000                 # 数字越大优先级越高
 globalDefault: false
preemptionPolicy: PreemptLowerPriority   # 允许抢占
---
# Pod 引用
spec:
  priorityClassName: high-priority
```

| 值区间 | 典型用途 |
|:-------|:---------|
| 2000000000+ | 系统关键（kube-system）|
| 1000000 | 核心业务 |
| 1~999999 | 普通业务 |
| 0 或未设 | 默认优先级 |

> **典型分档**：PriorityClass 三档（p0 关键组件 / p1 普通业务 / p2 可牺牲任务），资源紧张时先牺牲 p2。

### 2.6 调度机制对照表

| 机制 | 方向 | 硬/软 | 能否驱逐已运行 |
|:-----|:-----|:------|:---------------|
| nodeSelector | Pod→节点标签 | 硬 | 否 |
| nodeAffinity required | Pod→节点标签 | 硬 | 否（IgnoredDuringExecution）|
| nodeAffinity preferred | Pod→节点标签 | 软 | 否 |
| **Taint NoSchedule** | 节点→排斥 Pod | 硬 | 否 |
| **Taint NoExecute** | 节点→排斥 Pod | 硬 | **是（会驱逐）** |
| podAffinity | Pod→Pod | 硬/软 | 否 |
| podAntiAffinity | Pod→Pod | 硬/软 | 否 |
| topologySpread | 拓扑域均匀 | 硬/软 | 否 |
| PriorityClass | 抢占排序 | — | 会触发抢占 |

## 三、为什么要弹性伸缩

### 固定容量是"两头亏"

- **按峰值配资源**：平时大量资源闲置，烧钱。
- **按均值配资源**：流量一涨就雪崩，体验差、甚至宕机。

**弹性伸缩（Autoscaling）** 就是让资源**跟着负载走**：负载涨就加，负载落就减。它同时解决三件事：

| 目标 | 说明 |
|:-----|:-----|
| **保稳定** | 高峰自动扩容，扛住流量 |
| **降成本** | 低谷自动缩容，省资源 |
| **少人工** | 不用人盯着半夜手动加机器 |

### K8s 的三层伸缩

```
第 3 层：节点数     Cluster Autoscaler / Karpenter   ← 机器不够了加机器
第 2 层：Pod 规格   VPA（Vertical Pod Autoscaler）    ← 给单个 Pod 调大/调小 CPU/内存
第 1 层：Pod 数量   HPA（Horizontal Pod Autoscaler）  ← 增减 Pod 副本数（最常用）
        ────────────────────────────────────────
        补充：KEDA（事件驱动，按队列长度等扩缩）
```

> **顺口溜**：HPA 管"几个"，VPA 管"多大"，CA 管"几台"。
> 三者可叠加使用，但 **HPA + VPA 同时改 CPU 会打架**（见第四节）。

## 四、前置：metrics-server

HPA/VPA 需要**指标数据**，K8s 本身不采集资源用量，必须装 **metrics-server**。

### 4.1 它是什么

从每个节点 kubelet 的 cAdvisor 拉取 CPU/内存用量，聚合成 `metrics.k8s.io` API，供 HPA/VPA/kubectl top 使用。

### 4.2 安装

```bash
# 部分发行版（如 k3s）自带 metrics-server，先确认
kubectl -n kube-system get deploy metrics-server

# 标准 K8s 集群用官方 manifest
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```

### 4.3 验证

```bash
kubectl top nodes          # 节点资源用量
kubectl top pods -A        # Pod 资源用量
kubectl get apiservice v1beta1.metrics.k8s.io   # 应为 Available
```

> ⚠️ 自建集群常见坑：metrics-server 默认要**校验 kubelet 证书**，自签证书会报 `x509` 错误 →
> 加启动参数 `--kubelet-insecure-tls`（仅测试环境）。

## 五、HPA：Pod 水平伸缩（最常用）

HPA 根据指标**自动增减 Deployment/StatefulSet 的副本数**。

### 5.1 核心原理

```
每 15s（默认）循环一次：
  当前指标值  vs  目标值
       │
       ▼
  期望副本数 = ceil( 当前副本数 × (当前指标 / 目标指标) )
       │
       ▼
  在 minReplicas ~ maxReplicas 之间夹逼，遵守伸缩冷却窗口
```

### 5.2 基于 CPU 的 HPA（最经典）

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70      # 平均 CPU 利用率超过 70% 就扩容
  behavior:                            # 伸缩行为控制（v2 新增，非常重要）
    scaleUp:
      stabilizationWindowSeconds: 0    # 扩容立即生效
      policies:
        - type: Percent
          value: 100                   # 一次最多翻倍
          periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300  # 缩容前观察 5 分钟（防抖动）
      policies:
        - type: Pods
          value: 1                     # 每次最多减 1 个
          periodSeconds: 60
```

> ⚠️ **前提**：目标 Deployment 的容器**必须设置 `resources.requests.cpu`**。
> HPA 的"利用率"是相对 **requests** 算的（不是 limit、不是节点总量）——没设 requests，HPA 会报错不工作。

### 5.3 基于内存的 HPA

```yaml
  metrics:
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
```

> ⚠️ **内存不像 CPU 能回收**：Pod 内存涨上去不会自己降，所以内存 HPA 缩容很迟钝，**容易只扩不缩**。一般内存只用来**触发扩容**，缩容靠 CPU/QPS。

### 5.4 多指标 HPA

可以同时配 CPU + QPS，HPA 会**取所有指标算出的最大副本数**（哪个要求多听哪个，**保证不欠**）。

```yaml
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Pods                   # 自定义指标（需 Prometheus Adapter）
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "100"
```

### 5.5 HPA 的三种指标来源

| 指标类型 | 来源 | 示例 | 额外组件 |
|:---------|:-----|:-----|:---------|
| **Resource** | metrics-server | CPU / 内存 | metrics-server |
| **Pods / Object** | 自定义指标（Custom Metrics）| QPS、连接数 | Prometheus Adapter |
| **External** | 外部指标 | 消息队列长度、云监控 | Prometheus Adapter / KEDA |

## 六、VPA：Pod 垂直伸缩

VPA 不改副本数，而是**调整 Pod 的 requests/limits**（给 Pod"长个儿或缩个儿"）。

### 6.1 三种更新模式

| 模式 | 行为 |
|:-----|:-----|
| `Off` | 只**给建议值**，不实际改（安全，先观察）|
| `Initial` | 只在 Pod **创建时**按建议设置，运行中不改 |
| `Auto` | 自动**驱逐重建** Pod 来应用新规格（会重启！）|

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  updatePolicy:
    updateMode: "Off"        # 先用 Off 观察建议值，别急着 Auto
  resourcePolicy:
    containerPolicies:
      - containerName: web
        minAllowed:
          cpu: 100m
          memory: 128Mi
        maxAllowed:
          cpu: 2
          memory: 2Gi
        controlledResources: ["cpu", "memory"]
```

```bash
# 看 VPA 给出的建议值（Off 模式也能看）
kubectl describe vpa web-vpa
# 输出里有 Target / Lower Bound / Upper Bound —— 这就是它建议的合理区间
```

### 6.2 ⚠️ HPA + VPA 不能同时管 CPU

两个都基于 CPU 决策时会**互相打架**（HPA 加副本，VPA 调规格，指标来回震荡）。正确做法：

- **HPA 管副本（CPU/QPS） + VPA 只管内存**（`controlledResources: ["memory"]`）
- 或 **VPA 用 Off 模式**，仅作为"该给多少 requests"的参考，人工/CI 采纳

### 6.3 典型用途

- **不知道 requests 该设多少** → VPA Off 跑几天，看建议值再改 Deployment
- **长期负载缓慢增长**的服务 → VPA Initial
- **不适合**：频繁重启有代价的有状态服务、内存敏感的数据库

## 七、Cluster Autoscaler：节点伸缩

HPA 加到 maxReplicas 也扛不住时，需要**加机器**——这就是 **Cluster Autoscaler（CA）**。

### 7.1 工作原理

```
每 10s 检查：
  ┌─ 有 Pod 因资源不足 Pending？ → 扩容节点
  └─ 有节点长期空闲（利用率 < 50% 且 Pod 都可安置到别处）？ → 缩容节点
```

### 7.2 关键前提

- **节点池/ASG 必须支持动态增减**（云厂商：ESS 伸缩组 / EKS Node Group / GKE Node Pool）
- Pod 要能被驱逐缩容：需设 **PDB（PodDisruptionBudget）** 保护，以及合理的 requests

### 7.3 阿里云 ACK 场景

ACK 用 **cluster-autoscaler** 组件，绑定 **ESS 伸缩组**：

```yaml
# ACK 节点池开启弹性伸缩后，CA 自动管理
# 关键：给不需要被缩容的节点打标签
kubectl annotate node <node> cluster-autoscaler.kubernetes.io/scale-down-disabled=true
```

```bash
# 看 CA 状态（ACK 内置组件在 kube-system）
kubectl -n kube-system logs deploy/cluster-autoscaler | tail -50
kubectl -n kube-system get pods | grep autoscaler
```

### 7.4 三层联动

```
流量涨 → HPA 加 Pod（副本 2→10）
        → 节点资源不够，Pod Pending
        → Cluster Autoscaler 加节点
        → Pod 被调度上去，业务扛住

流量落 → HPA 减 Pod（副本 10→2）
        → 节点空闲
        → Cluster Autoscaler 回收节点
        → 成本降下来
```

> **关键**：**HPA 是"加多少 Pod"，CA 是"加多少机器"**，两者配合才是完整的云上弹性。

## 八、KEDA：事件驱动伸缩

HPA 主要看 CPU/内存，但很多场景**负载不在 CPU 上**——消息队列积压、定时任务、外部事件。**KEDA**（Kubernetes Event-driven Autoscaling）补齐这块。

### 8.1 它能做什么

- 按 **队列长度**（RabbitMQ / Kafka / Redis / MQ）伸缩
- 按 **Cron 时间**伸缩（白天多副本、夜里 0 副本）
- 支持 **缩到 0**（HPA 最低是 1，KEDA 可以 0 → 省资源）
- 内置几十种 Scaler（MySQL、Prometheus、云监控……）

### 8.2 示例：按 RabbitMQ 队列长度伸缩

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: consumer-scaler
spec:
  scaleTargetRef:
    name: consumer
  minReplicaCount: 0          # 没消息时缩到 0
  maxReplicaCount: 30
  triggers:
    - type: rabbitmq
      metadata:
        protocol: amqp
        queueName: orders
        mode: QueueLength
        value: "50"           # 每 50 条消息对应 1 个副本
      authenticationRef:
        name: rabbitmq-auth
```

### 8.3 示例：Cron 伸缩（办公时段扩容）

```yaml
  triggers:
    - type: cron
      metadata:
        timezone: Asia/Shanghai
        start: "0 8 * * *"     # 早 8 点扩到 5 副本
        end: "0 20 * * *"      # 晚 8 点缩回 1
        desiredReplicas: "5"
```

### 8.4 安装

```bash
helm repo add kedacore https://kedacore.github.io/charts
helm install keda kedacore/keda -n keda --create-namespace
```

> KEDA 底层**复用 HPA**（它会自动创建 HPA 对象），只是指标来源更丰富、能缩到 0。

## 九、小集群 / 轻量发行版落地判断

### 9.1 轻量发行版（k3s 类）自带能力盘点

| 组件 | k3s 是否自带 | 说明 |
|:-----|:------------|:-----|
| metrics-server | ✅ 自带 | `kubectl top` 直接能用 |
| HPA | ✅ API 内置 | 直接写 HPA 对象即可 |
| VPA | ❌ 需装 | `kubectl apply` 官方 manifest |
| Cluster Autoscaler | ❌ 不适用 | k3s 是固定节点，无云伸缩组（除非接 Karpenter）|
| KEDA | ❌ 需装 | Helm 一条命令 |

### 9.2 固定小集群的适用性判断

**固定节点 + 小内存**（如 2 节点、单节点 2G）的集群：

- **Cluster Autoscaler 用不上**（没有弹性节点池，加机器是手动买）。
- **HPA 可用但要谨慎**：节点资源本就吃紧，HPA 扩出来的 Pod 可能 Pending 挤爆节点 → 适合**配合 requests 精细设置 + maxReplicas 保守**。
- **KEDA 缩到 0 很有价值**：Gitea / 定时任务类服务夜里缩到 0，能明显省内存。
- **实用顺序**：先 metrics-server（已有）→ HPA（CPU）→ 观察 → 再考虑 KEDA。

### 9.3 一个可直接用的 HPA 示例

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-web
spec:
  replicas: 2
  selector:
    matchLabels: { app: demo-web }
  template:
    metadata:
      labels: { app: demo-web }
    spec:
      containers:
        - name: web
          image: nginx:alpine
          resources:
            requests:            # ⚠️ HPA 必需
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: demo-web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: demo-web
  minReplicas: 1
  maxReplicas: 4                 # 保守上限，别撑爆 2G 节点
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

```bash
# 压测触发扩容（另开一个 Pod 打流量）
kubectl run -it --rm load --image=busybox --restart=Never -- \
  sh -c "while true; do wget -q -O- http://demo-web; done"

# 观察副本数变化
kubectl get hpa demo-web-hpa -w
kubectl get pods -l app=demo-web -w
```

## 十、调优与避坑

### 10.1 常见坑对照表

| 坑 | 现象 | 解法 |
|:---|:-----|:-----|
| **没设 requests** | HPA 报 `<unknown>/70%`，不扩缩 | 容器加 `resources.requests.cpu` |
| **指标抖动** | 副本数来回跳 | `behavior.scaleDown.stabilizationWindowSeconds` 设 300s+ |
| **扩了但起不来** | 新 Pod Pending | 节点资源不足 → 上 CA / 调 requests / 提 maxReplicas 前提是加机器 |
| **内存 HPA 只扩不缩** | 副本一直高位 | 内存改用 VPA，或 HPA 只看 CPU/QPS |
| **HPA + VPA 打架** | 指标震荡 | VPA 只管内存，或 VPA 用 Off |
| **缩容太猛** | 流量回弹就打满 | scaleDown 策略限制每次减 1 个 |
| **扩容太慢** | 峰值早就过了才扩完 | 提前用 KEDA Cron 预热；`scaleUp` 策略放宽 |

### 10.2 调优要点

1. **requests 要贴近真实用量**——太小导致 HPA 过早扩容，太大导致利用率永远低、不扩容。
2. **扩容快、缩容慢**：`scaleUp` 激进（如翻倍），`scaleDown` 保守（观察 5~10 分钟）。
3. **保护有状态服务**：给 StatefulSet / 数据库配 **PDB**，避免 CA 缩容时误驱逐。
4. **配合 PDB + 优雅退出**：缩容时 Pod 要能优雅处理完在途请求（`terminationGracePeriodSeconds` + preStop）。

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 1
  selector:
    matchLabels: { app: web }
```

### 10.3 观测什么

```bash
kubectl get hpa -A                      # 当前/目标指标 + 副本数
kubectl describe hpa <name>             # 伸缩事件、决策原因
kubectl get events --field-selector reason=ScalingReplicaSet
kubectl top pods -A                     # 实际用量
```

> 生产建议：把 HPA 的 `kube_horizontalpodautoscaler_*` 指标接入 Prometheus，配 Grafana 看板 + 告警。

## 十一、选型决策表

| 需求 | 用什么 |
|:-----|:-------|
| Web 服务按 QPS/CPU 增减副本 | **HPA** |
| 不知道 requests 该设多少 | **VPA（Off 观察）** |
| 云上节点池自动增减机器 | **Cluster Autoscaler / Karpenter** |
| 按消息队列长度伸缩 / 能缩到 0 | **KEDA** |
| 定时（白天扩容夜里缩容）| **KEDA Cron**（或定时改 HPA）|
| 数据库、有状态集群 | 谨慎：PDB + VPA 建议 + 手动为主 |

## 十二、知识地图

```
【第 1 层：Pod 数量】
  HPA ── 指标来自 ──> metrics-server（CPU/内存）
                  └─> Prometheus Adapter（自定义/外部指标）
                       └─> KEDA（队列/事件/Cron，可缩到 0）

【第 2 层：Pod 规格】
  VPA ── Off（只建议）/ Initial / Auto（驱逐重建）
       └─ ⚠️ 别和 HPA 同管 CPU

【第 3 层：节点数量】
  Cluster Autoscaler ── 云伸缩组（ESS / Node Group）
                     └─> Karpenter（更快的按需节点）

【联动】
  流量↑ → HPA 加 Pod → 资源不够 → CA 加节点
  流量↓ → HPA 减 Pod → 节点空闲 → CA 回收节点（省钱）
```
