# K8s 存储详解

> 从「容器里数据为什么会丢」讲起，到 K8s 存储的完整体系：Volume → PV/PVC → StorageClass → CSI。
> 附 k3s / 阿里云场景的落地对照。

---

## 一、为什么需要 K8s 存储

### 容器文件系统是"用完即弃"的

容器的可写层（UnionFS 顶层）生命周期 = 容器生命周期。容器一删，写进去的数据**跟着消失**；Pod 重建（崩溃重启、滚动更新、被调度到别的节点）也会换一个全新容器，数据全没。

这就是**无状态**容器能随便漂移的原因，也是**有状态**服务（数据库、对象存储、消息队列）不能只靠容器文件系统的原因。

### K8s 存储要解决的三件事

| 问题 | 对应机制 |
|:-----|:---------|
| 数据要**活得比容器久** | Volume（卷） |
| 存储资源要**和业务解耦**（业务不关心底层是 NFS 还是云盘） | PV / PVC 抽象 |
| 存储要能**按需动态供应**（不用管理员手工建盘） | StorageClass |
| 集群要接入**任意存储后端**（云盘、NFS、Ceph、本地盘） | CSI 驱动 |

---

## 二、Volume 入门（Pod 级）

Volume 是 Pod 里**多个容器共享的目录**，生命周期跟随 Pod（不是容器）。容器重启，Volume 里的数据还在；Pod 被删除，Volume 才消失。

### 2.1 临时卷

| 类型 | 用途 | 特点 |
|:-----|:-----|:-----|
| `emptyDir` | 同 Pod 内容器间共享数据、缓存 | **Pod 删除即清空**（默认落节点磁盘，可 `medium: Memory` 落内存）|
| `configMap` / `secret` | 挂配置文件、密钥 | 只读挂载，内容来自 ConfigMap/Secret 对象 |
| `hostPath` | 挂节点本地路径（如 docker.sock、日志目录）| ⚠️ **与节点强绑定**，Pod 漂到别的节点数据就没了，慎用 |

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: shared-volume-demo
spec:
  containers:
    - name: writer
      image: busybox
      command: ["sh", "-c", "while true; do date >> /data/out.txt; sleep 5; done"]
      volumeMounts:
        - name: data
          mountPath: /data
    - name: reader
      image: busybox
      command: ["sh", "-c", "tail -f /data/out.txt"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      emptyDir: {}          # 两个容器共享；Pod 一删就没
```

### 2.2 持久卷（PV/PVC）

真正要**跨 Pod 生命周期持久化**，用 PV + PVC：

```
业务 Pod ──引用──> PVC（我要 10Gi 读写盘）
                    │ 绑定
                    ▼
                  PV（实际的一块盘：云盘 / NFS / 本地盘）
```

- **PV（PersistentVolume）**：集群级别的存储资源，由管理员创建（静态）或 StorageClass 自动创建（动态）。
- **PVC（PersistentVolumeClaim）**：用户的**存储申请单**——"我要 10Gi、ReadWriteOnce"。K8s 负责把它和一个满足条件的 PV 绑定。
- 业务 Pod 只认 PVC，**不关心底层**是阿里云盘还是 NFS——这就是解耦。

```yaml
# 1) 存储申请单
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data
spec:
  accessModes: ["ReadWriteOnce"]     # 单节点读写（云盘典型）
  resources:
    requests:
      storage: 10Gi
  storageClassName: local-path       # 指定用哪个 StorageClass
---
# 2) 业务挂载
apiVersion: v1
kind: Pod
metadata:
  name: mysql
spec:
  containers:
    - name: mysql
      image: mysql:8.0
      env:
        - name: MYSQL_ROOT_PASSWORD
          value: "changeme"
      volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: mysql-data         # 引用 PVC，不是 PV
```

### 2.3 访问模式（AccessMode）

| 模式 | 缩写 | 含义 |
|:-----|:-----|:-----|
| ReadWriteOnce | RWO | 只能被**单个节点**读写（云盘最常见）|
| ReadOnlyMany | ROX | 多节点只读（NFS）|
| ReadWriteMany | RWX | 多节点读写（NFS / CephFS / NAS）|
| ReadWriteOncePod | RWOP | 只能被**单个 Pod** 读写（K8s 1.22+，最强限制）|

> ⚠️ 常见坑：**云盘默认只支持 RWO**，想让多个 Pod 同时写同一份数据，必须换 NAS/NFS（RWX）或让应用自己做分片。

## 三、StorageClass：动态供应

手工建 PV 太累。**StorageClass（SC）** 定义"用哪套存储、怎么建盘"，PVC 引用 SC 后，K8s 会**按需自动创建 PV**（这叫 Dynamic Provisioning）。

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: alicloud-disk-essd
provisioner: diskplugin.csi.alibabacloud.com    # 由哪个 CSI 驱动来建盘
parameters:
  type: cloud_essd
  zone: cn-hangzhou-h
reclaimPolicy: Delete          # PVC 删除后，PV/云盘是否跟着删
volumeBindingMode: WaitForFirstConsumer   # 等到 Pod 调度到某节点再建盘（关键！）
allowVolumeExpansion: true     # 允许后期扩容
```

**两个关键字段：**

- **`reclaimPolicy`**
  - `Delete`：删 PVC 时连盘一起删（省资源，但数据没了——**慎用于数据库**）
  - `Retain`：删 PVC 时保留盘，需人工清理（保命）
- **`volumeBindingMode`**
  - `Immediate`：PVC 一创建就建盘（可能建到 Pod 去不了的可用区）
  - `WaitForFirstConsumer`：**等 Pod 调度后**再在对应节点/可用区建盘（多可用区集群**必须**用它，否则 Pod 调度不上去）

**默认 StorageClass**：给某个 SC 打注解 `storageclass.kubernetes.io/is-default-class: "true"`，PVC 不写 `storageClassName` 时就走它。

## 四、CSI：存储接入标准

**CSI（Container Storage Interface）** 是 K8s 统一的存储插件标准。有了它，任何存储厂商只要实现 CSI 驱动，就能接入 K8s，不用改 K8s 核心代码。

一次挂载的完整链路：

```
PVC 创建 → SC 的 provisioner 被调用
        → CSI 驱动向存储后端申请一块盘（云 API / NFS 导出）
        → 生成 PV 对象，绑定 PVC
        → Pod 调度到节点 → kubelet 调 CSI Node 服务
        → 把盘 attach + mount 进容器
```

| 存储后端 | CSI 驱动 | 典型场景 |
|:---------|:---------|:---------|
| 阿里云云盘 | `diskplugin.csi.alibabacloud.com` | RWO，数据库 |
| 阿里云 NAS | `nasplugin.csi.alibabacloud.com` | RWX，共享文件 |
| 阿里云 OSS | `ossplugin.csi.alibabacloud.com` | 对象存储挂载 |
| NFS | `nfs.csi.k8s.io` / 内建 | 自建共享存储 |
| Ceph RBD / CephFS | `rbd.csi.ceph.com` | 自建分布式块/文件 |
| 本地盘 | `rancher.io/local-path`（k3s 内置）| 单机测试、轻量场景 |

## 五、k3s 场景落地（本项目实证）

k3s 默认自带 **local-path-provisioner**，开箱即用：

- 默认 StorageClass 名：`local-path`，注解已是 default
- provisioner：`rancher.io/local-path`
- 数据落点：**调度到哪个节点，就落在该节点的 `/var/lib/rancher/k3s/storage/pvc-xxx_<ns>_<pvc名>/`**

```bash
# 看当前有哪些 StorageClass
kubectl get storageclass

# 建个 PVC 验证自动供应
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: demo-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
EOF

kubectl get pvc demo-pvc        # 应显示 Bound
kubectl get pv                  # 自动生成了一个 pv
```

> **本项目实证**：Gitea 的 SQLite 数据就落在上海节点的
> `/var/lib/rancher/k3s/storage/pvc-<pv名>_gitea_gitea-data/`（内含 `git/`、`gitea.db`、`ssh/`）。
> 详见 k3s部署实战.md。

### local-path 的坑

1. **不是真持久**：Pod 被调度到**另一个节点**时，原节点的数据**不会跟着走** → 数据"消失"。生产要跨节点持久，必须用 NFS/云盘这类网络存储。
2. **单副本**：节点挂了数据就没了，无冗余。
3. **RWX 不支持**：多 Pod 同时写同一 PVC 会翻车。
4. **`reclaimPolicy=Delete`**：因为 PVC 删除后目录会被清理，误删 PVC = 数据没了。

> 结论：local-path 适合**单机验证 / 轻量单体应用**（如 Gitea）；数据库和跨节点共享场景请上云盘 / NAS。

## 六、有状态服务典型模式

### 6.1 StatefulSet + volumeClaimTemplates

无状态用 Deployment，**有状态用 StatefulSet**——它保证：

- **稳定的网络标识**：Pod 名固定为 `<sts名>-0/1/2`（不是随机后缀）
- **稳定的存储**：每个副本有自己**独立的 PVC**，Pod 重建后**绑回同一块盘**
- **有序启停**：0→1→2 顺序启动，逆序终止

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: mysql:8.0
          volumeMounts:
            - name: data
              mountPath: /var/lib/mysql
  volumeClaimTemplates:          # 每个副本自动生成一个 PVC
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: alicloud-disk-essd
        resources:
          requests:
            storage: 20Gi
```

生成的 PVC 名为 `data-mysql-0`、`data-mysql-1`、`data-mysql-2`，**删 Pod 不删 PVC**，数据留存。

### 6.2 数据库 vs 共享文件的选择

| 场景 | 存储类型 | 访问模式 |
|:-----|:---------|:---------|
| MySQL / PostgreSQL / Redis 单机 | 云盘 / local-path | RWO |
| 多副本有状态集群 | 每副本独立云盘 | RWO（各自一块）|
| 多 Pod 共享读写（日志、上传目录）| NAS / NFS / CephFS | RWX |
| 只读配置、密钥 | ConfigMap / Secret | 只读 |

## 七、运维速查

```bash
# 查看存储资源
kubectl get sc                        # StorageClass 列表
kubectl get pv                        # 集群所有 PV
kubectl get pvc -A                    # 所有 ns 的 PVC
kubectl get pvc -n <ns> -o wide       # 看绑定到哪个 PV / SC

# 排查 PVC 一直 Pending
kubectl describe pvc <name> -n <ns>   # 看 Events（供应失败原因）

# 扩容（需 SC 开启 allowVolumeExpansion）
kubectl patch pvc <name> -n <ns> -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'

# 看 PV 详情（含真实后端路径/盘 ID）
kubectl get pv <pv名> -o yaml
```

**常见故障对照：**

| 现象 | 可能原因 |
|:-----|:---------|
| PVC 一直 `Pending` | 没有匹配的 SC / provisioner 没跑 / 可用区不匹配 / 配额不足 |
| Pod 卡 `ContainerCreating` | 盘 attach/mount 失败，看 `describe pod` 的 Events |
| Pod 换了节点后数据没了 | 用了 local-path / hostPath（节点本地），应换网络存储 |
| 多 Pod 写同一 PVC 报错 | 访问模式是 RWO，实际需要 RWX |

## 八、知识地图

```
容器可写层（用完即弃）
        │ 需要持久化
        ▼
   Volume（Pod 级，随 Pod 生死）
   ├─ emptyDir / configMap / secret / hostPath（临时）
   └─ persistentVolumeClaim ──┐
                              │ 引用
        ┌─────────────────────┘
        ▼
     PVC（申请单：要多大、什么模式）
        │ 绑定（静态匹配 / 动态供应）
        ▼
     PV（真实的存储资源）
        │ 由谁创建？
        ▼
   StorageClass（模板 + provisioner）
        │ 调用
        ▼
   CSI 驱动 ──> 云盘 / NAS / NFS / Ceph / 本地盘
```
