# K8s 监控详解（Prometheus + Grafana + Loki）

> **定位**：讲清 K8s 可观测性的**指标 + 日志**两条线 —— Prometheus 采集/存储/查询、Grafana 可视化、Loki 日志聚合的原理与部署。
> 面向通用集群，每块讲清「是什么 + 原理 + 怎么配 + 常见坑」。
>
> **一句话架构**：每节点 Agent（node-exporter / Promtail）本地采集 → 中心端（Prometheus / Loki）存储 → Grafana 统一查询可视化。

---

## 一、架构总览

```
```
┌──────────────────── K8s 集群（指标 + 日志两条线）────────────────────┐
│                                                                      │
│  采集端（DaemonSet，每个节点各 1 Pod）                                │
│    ├ node-exporter  ── hostNetwork :9100 ── 宿主 CPU/内存/磁盘/网络/IO │
│    └ promtail       ── tail /var/log/pods ── 容器 stdout/stderr       │
│                                    │                                 │
│                                    ▼ 集群内 push/pull（无需公网）      │
│  Namespace monitoring                                                │
│    ├ Prometheus :9090   ← 指标存储（PVC · retention 可配）             │
│    ├ Loki       :3100   ← 日志存储（PVC · retention 可配）             │
│    └ Grafana    :3000   ← 统一可视化（NodePort / Ingress 暴露）        │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

| 角色 | 部署方式 | 采集/存储 |
|---|---|---|
| node-exporter | DaemonSet（hostNetwork） | 宿主 CPU/内存/磁盘/网络/IO |
| promtail | DaemonSet | 容器日志 tail + 打标签 |
| Prometheus | StatefulSet + PVC | 抓 node-exporter/kubelet/ksm 等，retention 可配 |
| Loki | StatefulSet + PVC | 日志聚合，retention 可配 |
| Grafana | Deployment + PVC | 看板 + 数据源（Prometheus / Loki）|

**采集路径选型（两种）**：

| 维度 | 公网采集（旧式） | 集群内采集（推荐） |
|---|---|---|
| 采集路径 | 公网 :9100（无鉴权裸奔） | 集群内 Pod 网络 |
| 安全性 | 需安全组逐台收紧 | **零公网端口**，仅 Grafana 出入口 |
| 迁移性 | 配置散在中央机 | k8s 原生，跟着集群走 |

## 二、采集端：node-exporter DaemonSet

`node-exporter` 是 Prometheus 官方的**宿主指标采集器**，采 CPU/内存/磁盘/网络/IO。在 K8s 里用 **DaemonSet** 保证**每个节点各 1 个 Pod**，用 `hostNetwork` 直接采宿主。

`node-exporter.yaml`：
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: monitoring
---
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
  labels: { app: node-exporter }
spec:
  selector:
    matchLabels: { app: node-exporter }
  template:
    metadata:
      labels: { app: node-exporter }
    spec:
      hostNetwork: true
      hostPID: true
      terminationGracePeriodSeconds: 30
      tolerations:
        - { operator: Exists }          # 容忍所有污点，每节点都有
      containers:
        - name: node-exporter
          image: prom/node-exporter:v1.8.2
          args:
            - --path.procfs=/host/proc
            - --path.sysfs=/host/sys
            - --path.rootfs=/host
            - --collector.filesystem.mount-points-exclude=^/(sys|proc|dev|host|etc)($|/)
          ports:
            - { name: metrics, containerPort: 9100, hostPort: 9100 }
          resources:
            requests: { cpu: 10m, memory: 30Mi }
            limits:   { cpu: 200m, memory: 128Mi }
          volumeMounts:
            - { name: proc, mountPath: /host/proc, readOnly: true }
            - { name: sys,  mountPath: /host/sys,  readOnly: true }
            - { name: root, mountPath: /host, readOnly: true, mountPropagation: HostToContainer }
      volumes:
        - { name: proc, hostPath: { path: /proc } }
        - { name: sys,  hostPath: { path: /sys } }
        - { name: root, hostPath: { path: / } }
```

部署：
```bash
kubectl apply -f node-exporter.yaml
kubectl get pods -n monitoring -o wide    # 每个节点各 1 Running
```

> node-exporter 资源极省（~30Mi/节点 / 近 0 CPU），小规格节点也无压力。
> **注意**：`hostNetwork: true` 让 Pod 直接用宿主 9100，因此**同节点不能有两个 node-exporter**；该端口在集群内可达即可，**不需要公网暴露**。

## 三、采集端（可选）：集群外的裸机

> 有些机器（如 Jenkins / 构建机）**不在 K8s 集群内**。要采它们，要么走公网 :9100，要么让其以"被监控端主动 push"的方式上报。

`/opt/node-exporter/docker-compose.yml`：
```yaml
services:
  node-exporter:
    image: prom/node-exporter:v1.8.2
    container_name: node-exporter
    restart: unless-stopped
    network_mode: host
    command:
      - --path.procfs=/host/proc
      - --path.sysfs=/host/sys
      - --path.rootfs=/host
      - --collector.filesystem.mount-points-exclude=^/(sys|proc|dev|host|etc)($|/)
    volumes:
      - /proc:/host/proc:ro
      - /sys:/host/sys:ro
      - /:/rootfs:ro,rslave
```

```bash
docker compose up -d && curl -s localhost:9100/metrics | head -3
```

> ⚠️ 采集集群外机器，若走公网 :9100 必须**安全组限源**（只放行采集端出口 IP ；动态 IP 场景不现实）。**推荐**改用"被监控端主动 push"（pushgateway / remote write 代理），或把这台机器也接入集群。

## 四、完整方案：kube-prometheus-stack（Helm）

> **定位**：kube-prometheus-stack（KPS）是社区标准的「全家桶」Chart，把 **Prometheus Operator + Prometheus + Grafana + kube-state-metrics + node-exporter + 预置 dashboard + 告警规则** 一次装齐。本节讲怎么装、怎么裁剪、有哪些坑。

### 4.0 组件与落位

| 组件 | 副本 | 建议 limits | 说明 |
|---|---|---|---|
| prometheus (StatefulSet) | 1 | 1C / 1.5Gi | 指标存储，retention 可配，PVC |
| prometheus-operator | 1 | 300m / 384Mi | 管 CRD 与热加载，含 config-reloader |
| kube-state-metrics | 1 | 200m / 384Mi | K8s 对象指标（node/pod/pvc 视图的源）|
| grafana (+2 sidecar) | 1 | 500m / 512Mi | 可视化，预置 dashboard 靠 sidecar 自动加载 |
| node-exporter | DaemonSet | ~30Mi/台 | 每节点 1 个，采宿主指标 |
| alertmanager | 可选 | ~40Mi | 有通知渠道才装 |
| 控制面 monitor (etcd/scheduler/controller/proxy) | 可选 | — | **k3s 类只监听 127.0.0.1，跨节点抓不到 → 关掉** |

> **落位原则**：所有有状态/重负载组件用 `nodeSelector` **钉到资源最宽的节点**，别让小规格节点撑爆。多节点时也可用 `nodeAffinity` / 污点容忍精确控制。

### 4.1 获取 chart（离线包）

若集群所在网络**访问不了 GitHub**（`helm repo add prometheus-community` 卡死、`curl index.yaml` timeout），用**离线包**方式：

1. **在能通 GitHub 的机器（gateway）下载** `index.yaml` 与 chart tgz：
   ```bash
   curl -sSL -o kps-index.yaml https://prometheus-community.github.io/helm-charts/index.yaml
   # 取 chart 名 kube-prometheus-stack 的最新版本
   curl -sSL -o kps.tgz \
     https://github.com/prometheus-community/helm-charts/releases/download/kube-prometheus-stack-<版本>/kube-prometheus-stack-<版本>.tgz
   ```
2. **scp 到目标集群的任一可执行节点**。
3. 部署**不走 helm install**，改用 `helm template` 渲染 → **分批 `kubectl apply`**（见 4.3）。

> ⚠️ 有些网络环境 GitHub Pages 被阻、但 **GitHub Releases 域名可通**——chart 包能下、index 也能下（只是慢，要留足超时）。curl 大文件务必 `--retry 3`；实在下不动就换国内镜像源或从能通网的机器中转。

### 4.2 values.yaml（关键裁剪）

```yaml
fullnameOverride: kps
defaultRules:
  rules: { alertmanager: false, etcd: false, kubeControllerManager: false,
           kubeSchedulerAlerting: false, kubeSchedulerRecording: false, kubeProxy: false }
prometheus:
  prometheusSpec:
    nodeSelector: { kubernetes.io/hostname: <落点节点> }
    retention: 15d
    resources: { requests: { cpu: 100m, memory: 512Mi }, limits: { cpu: "1", memory: 1536Mi } }
    storageSpec:
      volumeClaimTemplate:
        spec: { storageClassName: local-path, accessModes: [ReadWriteOnce],
                resources: { requests: { storage: 10Gi } } }
prometheusOperator:
  nodeSelector: { kubernetes.io/hostname: <落点节点> }
  admissionWebhooks: { patch: { nodeSelector: { kubernetes.io/hostname: <落点节点> } } }
nodeExporter:
  enabled: false            # 复用已部署的 DaemonSet，避免 hostNetwork:9100 冲突
kube-state-metrics:
  nodeSelector: { kubernetes.io/hostname: <落点节点> }
grafana:
  enabled: true
  image:
    tag: 11.2.0             # ⚠️ 见 4.4 坑③：chart 默认 13.2.1-distroless 拉不动，用本地已有版本顶替
  nodeSelector: { kubernetes.io/hostname: <落点节点> }
  persistence: { enabled: true, storageClassName: <存储类>, size: 2Gi }
  service: { type: NodePort, nodePort: 30080 }
  adminUser: admin
  adminPassword: <强密码>
  sidecar: { dashboards: { enabled: true, searchNamespace: ALL }, datasources: { enabled: true } }
alertmanager: { enabled: false }
kubeEtcd: { enabled: false }
kubeControllerManager: { enabled: false }
kubeScheduler: { enabled: false }
kubeProxy: { enabled: false }
# apiserver / kubelet / coreDns 保留 true
```

### 4.3 分批 apply（控制 API 压力）

**背景**：两台云节点仅 2C/1.9G，server 内存紧 → apiserver 会 `TLS handshake timeout`；helm 多步事务极易失败。故**不用 `helm install`**，改为渲染后分批：

```bash
export KUBECONFIG=<集群 kubeconfig>
cd <chart 所在目录>
helm template kps ./kube-prometheus-stack-<版本>.tgz -n monitoring -f values.yaml > /tmp/kps-all.yaml

# 批0：CRD（helm template 不含，需单独拿）
helm show crds ./kps.tgz > /tmp/kps-crds.yaml   # 通常是 10 个 CRD
kubectl apply --server-side -f /tmp/kps-crds.yaml

# 拆批（按 kind 归类后逐批 apply，每批间 sleep 12~20s）
#   批1 RBAC(17) → 批2 config/secret/pvc/svc(30) → 批3 webhook/job(4) → 批4 workload(40)
```

> 拆分脚本：读 helm 渲染结果按 `---` 切文档，再按 `kind` 归入 rbac / config / workload / other 四个桶。**关键：CRD 必须最先（server-side apply），workload 最后。**

### 4.4 本轮踩的坑（落地实录）

#### 坑①：helm repo 加不进 / index 拉不动（网络被阻）
见 4.1。结论：**走离线包 + 分批 apply**，别指望集群网络直连 GitHub。

#### 坑②：Prometheus 抓不到任何 target（`pods is forbidden`）
**症状**：Prometheus 起来但 targets 只有自己。
**根因**：KPS 的 ServiceMonitor/PodMonitor 依赖 Prometheus 的 RBAC（operator 会自动建 ClusterRole + Binding），**手写栈**则需自建。
> 手写栈：需自建 ClusterRole 授权 SA 读 nodes/pods/services/endpoints + `/metrics`，再 `rollout restart`。

#### 坑③：Grafana 主镜像拉不动（docker.io 出口抖动）
**症状**：grafana Pod `PodInitializing` 卡 5min+，`describe` 显示主容器卡在 `Pulling docker.io/grafana/grafana:13.2.1-distroless`（sidecar/busybox 都拉好了）。
**根因**：chart 默认要 **13.2.1-distroless**，而节点拉 docker.io 慢/断；本地只有旧版本。
**解法（本次采用）**：values 里 `grafana.image.tag: 11.2.0` **用本地已有镜像顶替** —— 三台节点本地都有，秒起，19 个 dashboard 功能完整。
**备选**：从网络好的机器 `docker pull <国内镜像源>/grafana/grafana:13.2.1-distroless` → `docker tag` 私有仓库 → `docker push` → 节点从私有仓库拉（镜像中转链路见 4.5）。

#### 坑④：kubelet 出现 6 个 down target（重复发现）
**症状**：23 个 target 里 6 个 down，全是 `172.28.x / 172.23.x:10250`。
**根因**：kubelet ServiceMonitor 用 `node` 角色发现，把 `Node.status.addresses` 的**所有地址**（含节点物理内网 IP）都当 target；Prometheus 在 overlay 网络里够不到某些地址（真实指标在能达的那组已 up）。
**处理**：给 kubelet ServiceMonitor 的每个 endpoint 加一条 relabel，只保留可采集的网段：
```yaml
relabelings:
  - { action: keep, sourceLabels: [__address__], regex: "<可采集的网段正则>" }
```
应用后 target 只保留可达地址，**全 up、0 down**。

#### 坑⑤：复用旧 node-exporter 导致 host 视图全空（⚠️ 本轮最坑）
**症状**：全量 KPS 装好后，`host`（Node Exporter Full）视图打开**无数据**；Prometheus 的 `job` 标签里**只有 kubelet，没有 node-exporter**。
**根因**：为了“不重复”，values 里设了 `nodeExporter.enabled=false` **复用 §二 手搓的 DaemonSet**。但那个旧 DaemonSet **没有 ServiceMonitor**，而 KPS 的 Prometheus **只抓带 ServiceMonitor 的目标** → node-exporter 从未被纳入采集。
**错误尝试**：手写 Service + ServiceMonitor 接回来（`app: node-exporter` selector）—— 数据能回，但**脱离了 chart 管理**（后续 upgrade 不管它、版本/label 易不一致）。
**正确做法**：`nodeExporter.enabled: true`，**用 chart 自带的 DaemonSet**，自带 ServiceAccount/Service/ServiceMonitor/RBAC，每节点 1 Pod。
```yaml
nodeExporter:
  enabled: true
  # 不设 nodeSelector（DaemonSet 默认容忍全节点，三台都跑）
  resources: { requests: { cpu: 10m, memory: 30Mi }, limits: { cpu: 200m, memory: 128Mi } }
```
> **教训**：`values` 里 `xxx.enabled=false` 复用手预置组件时，必须确认新体系（KPS/operator）能发现它 —— KPS 依赖 **ServiceMonitor 声明**，不是“Pod 在跑就算”。**能启用 chart 自带的就启用，别复用。**

### 4.5 镜像中转（跨网络搬镜像）

节点拉 docker.io 反复失败时的统一解法 —— **用一台网络好的机器做「中转站」**（可以是镜像仓库，也可以直接是另一个节点）：

```bash
# 网络好的机器：拉 → tag → push 到私有仓库/镜像站
REG=registry.example.com/<命名空间>
docker pull <国内镜像源>/<img>:<tag>
docker tag  <国内镜像源>/<img>:<tag>  $REG/<img>:<tag>
docker push $REG/<img>:<tag>
```

- **云厂商 ACR 有公网端点 + VPC 内网端点**，走内网端点更快且免流量费
- 节点侧凭证写在容器运行时的 registry 配置里（如 k3s 的 `/etc/rancher/k3s/registries.yaml` `configs` 段），全节点统一
- ⚠️ **`ctr images push` 到 multi-arch 仓库常报 `blob unknown to registry`**（index 层本地不全，`ctr pull` 默认只拉本平台）→ **改用 `docker pull/tag/push`**（docker 与 containerd 是两套存储）
- 实测国内镜像源 4-5 MiB/s，几百 MB 镜像分钟级

## 五、核心监控指标 & PromQL（可视化/告警层）

从 node-exporter 抓到的是 `node_*` 系列。按 `by(instance)` 可把各节点分开看，最常用查询如下。

### CPU 使用率
```promql
100 - avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100
```
**iowait** 高说明磁盘是瓶颈，单独看很关键：
```promql
100 * avg by(instance)(rate(node_cpu_seconds_total{mode="iowait"}[5m])) /
      sum by(instance)(rate(node_cpu_seconds_total[5m]))
```
负载：`node_load5`

### 内存可用率
```promql
100 * node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
```
swap 剩余比：`node_memory_SwapFree_bytes / node_memory_SwapTotal_bytes`

### 磁盘使用率（盘常满，重点）
```promql
100 - 100 * node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}
```

### 网络吞吐（rate 字节/s）
`rate(node_network_receive_bytes_total[5m])` / `rate(node_network_transmit_bytes_total[5m])`

### 磁盘 IO 压力
`rate(node_disk_io_time_seconds_total[5m])` —— 反映盘忙不忙（wa 高时盯这个）

### 运行时长
`time(node_boot_time_seconds)` 差值 = 在线时长

> `by(instance)` 会把每个采集目标分成一条线；想只挑某台，在 PromQL 里加 `instance="<目标>:9100"` 过滤。

**建议告警阈值**：内存可用 <10%、磁盘 / >85%、IO wait 持续高、`up{job="node-*"} == 0`（掉线）。

### 6.1 落地实录（2026-09-14 实际部署，含排障）

**访问入口**：`http://<节点IP>:30080`（NodePort）→ `/login`，账密 `admin` / 见 Grafana admin Secret。

**依赖清单**（`/tmp/monitoring/`）：

| 文件 | 内容 |
|---|---|
| `node-exporter.yaml` | Namespace + node-exporter DaemonSet |
| `prometheus.yaml` | PVC + ConfigMap + Deployment + Service |
| `grafana.yaml` | PVC + Secret(grafana-admin) + Deployment + NodePort Service |
| `rbac.yaml` | ClusterRole + ClusterRoleBinding（Prometheus 服务发现用） |
| `grafana-dash-provider.yaml` | Grafana 看板 provisioning provider |

#### 坑①：Prometheus 抓不到 node-exporter（`pods is forbidden`）

**症状**：Prometheus targets 只有它自己，3 个 node-exporter 全丢。日志刷：
```
Failed to watch *v1.Pod: pods is forbidden: User "system:serviceaccount:monitoring:default"
  cannot list resource "pods" in API group "" at the cluster scope
```
**根因**：Prometheus 的 `kubernetes_sd_configs`（role: pod 自动发现）需要 **cluster 级 list/watch pods** 权限，但 Deployment 用的是 `default` SA，**没配任何 RBAC**。

**修复**：`rbac.yaml`（授权 `default` SA 读 nodes/nodes-metrics/services/endpoints/pods + `/metrics`）：
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: prometheus-monitoring }
rules:
  - apiGroups: [""]
    resources: ["nodes","nodes/metrics","nodes/proxy","services","endpoints","pods"]
    verbs: ["get","list","watch"]
  - apiGroups: ["networking.k8s.io"]
    resources: ["ingresses"]
    verbs: ["get","list","watch"]
  - nonResourceURLs: ["/metrics"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata: { name: prometheus-monitoring }
roleRef: { kind: ClusterRole, name: prometheus-monitoring, apiGroup: rbac.authorization.k8s.io }
subjects: [{ kind: ServiceAccount, name: default, namespace: monitoring }]
```
`kubectl apply -f rbac.yaml && kubectl -n monitoring rollout restart deploy/prometheus` → 3 个 target 全 UP。

#### 坑②：拉镜像卡死（节点拉 docker.io 反复失败）

**症状**：prometheus/grafana 长时间 `ContainerCreating`，节点上 `ctr images ls` 对应镜像数为 0；kubelet 日志 `pull ... lookup <镜像站>: Try again`（DNS 抖动）。小镜像（如 node-exporter）却能拉成功。

**根因**：节点到 Docker Hub / 国内镜像站的链路间歇性不稳定（网络抖动）。

**处置（多路尝试后的有效解）**：
1. `ctr images push` 到 ACR ❌ —— `blob unknown to registry`（multi-arch index 层本地不全，containerd 老问题，`ctr images pull` 默认只拉本平台层）。
2. `docker pull docker.1ms.run/<img>` → `docker tag` ACR 地址 → `docker push` ✅ **可行**（凭证走 `docker login`，同仓库层可复用 `Mounted from ...`）。
3. **最终最简单的解：先把镜像源钉成单源 `docker.1ms.run` 再让 kubelet 重试** —— 大镜像（272MB 级）轮询重试终能拉下。

> **镜像中转统一方案**：用云厂商容器镜像服务（如 ACR）作中转，它有**公网端点 + VPC 内网端点**（走内网更快且免流量费），凭证写在容器运行时的 registry 配置里（如 k3s 的 `/etc/rancher/k3s/registries.yaml` `configs` 段），全节点统一。

#### 坑③：Grafana 打开报 "failed to load its application files"

**症状**：浏览器打开 Grafana 显示静态资源加载失败页（提示检查 reverse proxy / root_url / serve_from_subpath）。

**排查**：在网关侧实测（非浏览器）：
```
HTTP 200  /login
HTTP 200  /public/build/runtime.*.js (13KB)
```
→ **服务端完全正常**，问题在浏览器缓存（之前 Grafana 没起来时访问过，缓存了坏状态）。**开无痕 / 强制刷新 `Ctrl+Shift+R` 即好**。
教训：NodePort 下静态资源走相对路径，URL 用带明确路径的 `/login` 打开即可，别用裸 `:端口`。

#### 坑④：dashboard 1860 导入失败

- 走 `POST /api/dashboards/import` 一直 400 `bad request data` / `required value Dashboard must not be empty`。
- 根因：`kubectl exec -i ... cat > file` **管道传大会截断**（32768/24576 字节处被切 → JSON 不完整）。改用 `base64 -d` 中转仍受限。
- **正解：ConfigMap + provisioning**（不碰 API，也不怕管道限制）：
  1. `kubectl -n monitoring create configmap dash1860-file --from-file=node-exporter-full.json=<裸dashboard.json>`（**裸 JSON**，不能带 `{"dashboard":...,"overwrite":...}` 外层包装，否则 provisioning 报 `Dashboard title cannot be empty`）。
  2. `grafana-dash-provider.yaml`：provider 指向 `/var/lib/grafana/dashboards`。
  3. `kubectl -n monitoring patch deploy grafana` 挂两个 volume：`dash-provider`→`/etc/grafana/provisioning/dashboards`，`dash-files`→`/var/lib/grafana/dashboards`。
  4. 重启 grafana pod → `api/search` 能看到 `Node Exporter Full`。
- 另外要**手动加数据源**（`POST /api/datasources`，`url: http://prometheus.monitoring.svc:9090`，`isDefault: true`）——本方案没用 sidecar 自动发现。

**幂等清单**（可重复执行）：
```bash
kubectl apply -f /tmp/monitoring/{node-exporter,prometheus,grafana,rbac,grafana-dash-provider}.yaml
kubectl -n monitoring create configmap dash1860-file --from-file=node-exporter-full.json=/tmp/dash-bare.json --dry-run=client -o yaml | kubectl apply -f -
```

## 六·补、Grafana 视图（View）导览

> 入口：Grafana 左侧 `Dashboards → Browse`，按 folder 分组（`General` / `Kubernetes` / `Prometheus` 等）。预置视图来自 chart 的 `grafana.dashboardProviders` + sidecar 自动发现，随 ConfigMap 挂入。

|:-----|:--------------|:------|:--------|

### 1. apiserver（API Server）

**看什么**：控制面性能与稳定性。

- 请求速率 / 每秒请求数（`apiserver_request_total`）
- **请求延迟分位**（`apiserver_request_duration_seconds` P99）—— 慢请求是控制面卡顿第一信号
- **限流**（`apiserver_flowcontrol_rejected_requests_total`）与 429 数
- 在途请求（`apiserver_current_inflight_requests`）、watch 连接数
- etcd 交互延迟（`etcd_request_duration_seconds`）

**什么时候盯**：`kubectl` 变慢、HPA 扩容不及时、Controller 反应迟钝时。小集群 API 常是单点，是**最先被压垮的一环**。

> ⚠️ k3s 的 apiserver 默认监听 `127.0.0.1:6444/6443`，Prometheus 抓不到 → 需要 ServiceMonitor 指向 `kubernetes` Service，或确认 chart 的 `kubeApiServer` 组件已开。

### 2. cluster（Cluster / Global）

**看什么**：一屏看全集群家底。

- 节点数（Ready/NotReady）、Pod 总数与容量上限
- Deployment / StatefulSet / DaemonSet 副本数（期望 vs 就绪）
- CPU / 内存 / 存储的 **Request 与 Limit 总量 vs 节点可分配量**
- 命名空间级资源占用排行

**什么时候盯**：日常巡检查容量、上生产前评估"还塞得下多少"。节点被污点独享/独占时，这个视图能直观印证容量饱和状态。

### 3. coredns（CoreDNS）

**看什么**：集群内服务发现健不健康。

- DNS 查询速率（`coredns_dns_requests_total`）按 type（A/AAAA/SRV）
- **错误响应**（`coredns_dns_responses_total{rcode=~"SERVFAIL|NXDOMAIN"}`）
- 延迟分位（`coredns_dns_request_duration_seconds`）、缓存命中率（`coredns_cache_hits_total` vs `coredns_cache_misses_total`）

**什么时候盯**：Pod 里 `nslookup` 超时、Service 名偶发解析不到、服务间调用偶发 5xx。

指标（Prometheus）回答"忙不忙"，日志回答"出了什么事"。两者在 Grafana 里同一个看板，排障时来回切。**轻量栈推荐 Promtail → Loki → Grafana**，比 ELK 省一个数量级的内存，适合小机场景。

### 4. fluentbit（Fluent Bit）

**看什么**：日志采集链路自身是否健康（**注意采日志的组件自己也要监控**）。

- 输入/输出吞吐：`fluentbit_input_records_total`、`fluentbit_output_records_total`
- **丢弃**：`fluentbit_output_dropped_records_total` —— 不为 0 就是日志丢了
- 重试/错误：`fluentbit_output_retries_total`、`fluentbit_output_errors_total`
- 缓冲区占用（`fluentbit_output_proc_bytes`）—— 堆积说明下游（Loki/ES）写入跟不上

**什么时候盯**：日志缺块、Grafana 查不到最新日志、下游存储写满时。

> ⚠️ 轻量栈通常用 **Promtail**（见第七节），Fluent Bit 是 7.1 选型表里的"超小机/边缘"替代项。若换 Fluent Bit，需在它自己的 `prometheus` 输出插件暴露上述指标 + 建对应 dashboard。此视图属于**可选/扩展**。

### 5. gpuxgpu（GPU 视图）

**看什么**：GPU 卡级利用率与健康（AI 训练/推理场景必看）。

- **利用率**：`DCGM_FI_DEV_GPU_UTIL`（卡忙不忙）、SM/Memory 分项
- **显存**：`DCGM_FI_DEV_FB_USED` / `FB_FREE`（vs `FB_TOTAL`）—— 显存泄漏比利用率更致命
- **温度/功耗**：`DCGM_FI_DEV_GPU_TEMP`、`DCGM_FI_DEV_POWER_USAGE`（撞温度墙会降频）
- **ECC/XID 错误**：`DCGM_FI_DEV_ECC_*`、XID 报错 —— 硬件故障最直接的证据
- 若走 **xGPU/GPU 虚拟化**：额外看 vGPU 实例分配数、切分后各实例占用

**什么时候盯**：训练任务变慢、OOM / 显存不足、卡掉线（XID）、多租户抢卡。

> ⚠️ 说明：**kube-prometheus-stack 默认不含 GPU 视图**。"gpuxgpu"需要额外接 **NVIDIA DCGM Exporter**（`nvcr.io/nvidia/k8s/dcgm-exporter`）作为 ServiceMonitor，再导入社区 GPU dashboard（如 Grafana id `12239`）。裸金属 GPU 机器还需装 NVIDIA driver + `nvidia-container-toolkit`。此视图为**扩展项**，有 GPU 节点才需要。

### 6. host（主机 / Node Exporter Full）

**看什么**：物理机 / 云主机整机资源。

- CPU 使用率 / iowait / 负载（`node_load*`）
- 内存可用率、swap（`node_memory_*`）
- 磁盘使用率（`node_filesystem_*`）、磁盘 IO（`node_disk_*`）
- 网卡吞吐 / 丢包（`node_network_*`）

**什么时候盯**：第五节的 PromQL 手动版不够看时，直接导入 **dashboard id `1860`（Node Exporter Full）**，一屏含 100+ 面板，是最实用的主机视图。

### 7. node（Kubernetes / Nodes）

**看什么**：K8s 视角的**节点**（区别于 host 的纯 OS 视角）。

- 节点 Ready / NotReady（`kube_node_status_condition`）
- 节点上 Pod 数 / 容量、可分配 CPU·内存
- 节点级 CPU/内存 Request 与 Limit 占用
- Node 污点 / 不可调度状态

**什么时候盯**：**NotReady 是最该告警的信号**——曾因 `NodeNotReady + API 连接抖动` 引发一轮重启风暴（监控组件纷纷重启）。节点挂了，上面的 Pod 全部连锁重启。

### 8. pod（Kubernetes / Pods、Compute Resources）

**看什么**：Pod 级细粒度资源与生命周期。

- Pod CPU / 内存使用（cAdvisor `container_*` 系列）vs Request/Limit
- **重启次数**（`kube_pod_container_status_restarts_total`）—— 突增就是有问题
- **OOMKilled**（`kube_pod_container_status_last_terminated_reason`）—— 极限裁剪内存的典型后果
- Pod 状态相位（Running/Pending/Failed）、就绪探针失败
- 网络收发（`container_network_*`）

**什么时候盯**：服务变慢、容器反复重启、Pending 不调度。Grafana 512Mi OOM 循环（重启上百次）正是靠 Pod 视图定位的；内存 Limit 压太狠的组件全在这个视图现形。

### 9. prometheus（Prometheus / Overview）

**看什么**：监控系统自监控（**监控也得被监控**）。

- **抓取目标**：UP / DOWN 数（`up`）、scrape 失败、scrape 耗时（`scrape_duration_seconds`）
- TSDB：样本数、`prometheus_tsdb_*`、内存占用、chunk 数
- 查询延迟（`prometheus_engine_query_duration_seconds`）、并发查询数
- 规则评估耗时、告警规则触发情况（`prometheus_rule_*`）

**什么时候盯**：target 掉线、TSDB 膨胀吃内存、Grafana 查询变卡。给 Prometheus 设的 limits + PVC 容量是否够，这个视图能提前预警 "Prometheus 自己 OOM"。

### 10. pvc（Persistent Volumes / PVC）

**看什么**：持久卷容量与状态。

- PVC 绑定状态（`kube_persistentvolumeclaim_status_phase`）—— Pending 就是没绑上
- **容量 / 已用**：`kubelet_volume_stats_used_bytes` / `capacity_bytes` —— 使用率必盯
- 剩余可用空间、inode（小文件多时 inode 先满）
- PV 与 StorageClass 对应关系

**什么时候盯**：Prometheus/Loki 等有状态组件盘写满、Pod 因存储驱逐。小盘场景尤其要看这个视图。

## 七、日志采集（Loki + Promtail）

> **定位**：指标回答「忙不忙」，日志回答「出了什么事」。本节讲清**为什么这样采集、原理是什么、怎么部署、怎么用**，脱离特定集群也能迁移。
> （方案完整，按需启用即可。）

### 7.1 为什么需要日志栈

Prometheus 指标告诉你"CPU 飙了"，但**回答不了"为什么"**。日志才能给到堆栈、异常、上下文。K8s 下日志的难点在于：

| 难点 | 说明 |
|:-----|:-----|
| **日志分散** | Pod 分布在多节点，业务容器 stdout 落在**各自节点的**磁盘上 |
| **Pod 会漂移** | Pod 重建/迁移，日志跟着走，盯着单机文件没用 |
| **生命周期短** | 容器一删，日志全丢；得集中起来才行 |
| **需要关联** | 一条日志要能对上"哪个集群/ns/pod/container"才好查 |

**采集架构的核心思路**：每节点一个 Agent（DaemonSet）本地 tail 日志文件 → 打上 K8s 元数据标签 → 推送到集中的日志后端 → Grafana 统一查询。

### 7.2 技术选型：Loki vs ELK vs Fluent Bit

| 方案 | 采集端 | 存储/查询 | 内存开销 | 适合 |
|:-----|:------|:---------|:--------|:-----|
| **Loki + Promtail**（本文）| Promtail（DaemonSet）| Loki（对象/本地盘 + LogQL）| 低（~百 MB 级）| 中小规模、Grafana 一体化 |
| **ELK**（Filebeat + ES + Kibana）| Filebeat | Elasticsearch | **高**（ES 单节点 GB 起步）| 全文检索重、大规模 |
| **Fluent Bit + 任意后端** | Fluent Bit | 可写 Loki/ES/文件 | 极低 | 超小机、嵌入式边缘节点 |

**为什么选 Loki**：它**不做全文索引**，只索引标签（labels）。代价是「按内容模糊搜」比 ES 慢，收益是**存储与内存低一个数量级**，且与 Prometheus 标签体系一致、和 Grafana 天然一家。对「小机 + 已知要查什么」的场景，性价比最高。

### 7.3 工作原理

#### 7.3.1 采集端怎么工作

```
节点上的容器 stdout/stderr
   │ kubelet 把它们写成文件
   ▼
/var/log/pods/<ns>_<pod>_<uid>/<container>/*.log   （软链：/var/log/containers/*.log）
   │  Promtail（DaemonSet，每节点一个）tail 这些文件
   │  · 用 K8s API 反查：这个文件属于哪个 pod/ns/container
   │  · 给每一行打上 label（job/namespace/pod/container/node）
   │  · 记住读了到哪（positions 文件，重启不重读）
   ▼
HTTP push → Loki /loki/api/v1/push
```

**三个关键点**：

| 机制 | 作用 | 对应配置 |
|:-----|:-----|:---------|
| **positions** | 记录每个文件读到第几行，重启接着读不重不漏 | `positions.filename` |
| **kubernetes_sd_configs** | 自动发现 Pod，动态获取日志路径与元数据 | `scrape_configs` |
| **relabel_configs** | 把 K8s 元数据映射为 Loki 标签 | `relabel_configs` |

#### 7.3.2 查询端怎么工作（Loki 的"标签"哲学）

Loki 的日志流由**标签组合**唯一定义（叫 **stream**）。同一个 stream 的日志聚在同一个 chunk 里。

> 类比：Loki 像 **Prometheus 的日志版**——Prometheus 存"带标签的时序数值"，Loki 存"带标签的日志行"，都用 LogQL/PromQL 一样的标签选择器。

**这决定了它的使用方式**：**先靠标签把范围缩到很小，再做内容过滤**。

```logql
# ✅ 好：先用标签定位，再 grep 内容
{namespace="gitea"} |= "error"

# ❌ 差：不带标签、全库扫内容（慢且吃资源）
{ } |~ "error"
```

### 7.4 如何部署（Loki + Promtail）

#### 7.4.1 后端 Loki

`docker-compose.yml` 追加（或 k8s 里起 deployment，落到指定节点）：
```yaml
  loki:
    image: grafana/loki:3.1.0
    container_name: loki
    restart: unless-stopped
    volumes:
      - loki-data:/loki
    ports:
      - "3100:3100"
    command: -config.file=/etc/loki/config.yml
```

`loki/config.yml`（单机 monolithic 模式，最简）：
```yaml
auth_enabled: false
server:
  http_listen_port: 3100
common:
  path_prefix: /loki
  storage:
    filesystem:
      chunks_directory: /loki/chunks
      rules_directory: /loki/rules
  replication_factor: 1
  ring:
    kvstore:
      store: inmemory
schema_config:
  configs:
    - from: 2024-01-01
      store: tsdb
      object_store: filesystem
      schema: v13
      index:
        prefix: index_
        period: 24h
limits_config:
  retention_period: 168h        # 日志留 7 天，按需改
compactor:
  delete_request_store: filesystem
```

> Loki 3.x 单机用 `tsdb + filesystem` 即可，不用拉 MinIO；真要长期留再上对象存储。
> **部署三件套**：`auth_enabled: false`（集群内不鉴权）+ `filesystem` 存储 + `compactor` 开 `retention_period`（否则磁盘无限涨）。

#### 7.4.2 采集端 Promtail（DaemonSet）

`promtail.yaml`（采集所有容器 stdout/stderr + kubelet 系统日志，自动富化 pod/ns/container 标签）：
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: promtail
  namespace: monitoring
spec:
  selector:
    matchLabels: { app: promtail }
  template:
    metadata:
      labels: { app: promtail }
    spec:
      tolerations:
        - { operator: Exists }        # 容忍所有污点，每节点都跑
      containers:
        - name: promtail
          image: grafana/promtail:3.1.0
          args: ["-config.file=/etc/promtail/config.yml"]
          resources:
            requests: { cpu: 10m, memory: 32Mi }
            limits:   { cpu: 100m, memory: 128Mi }
          volumeMounts:
            - { name: varlog, mountPath: /var/log }
            - { name: positions, mountPath: /run/promtail }

#### 7.4.3 裸机（组①）：systemd journal + 文件

### 7.5 怎么用：LogQL 速查

LogQL 和 PromQL 一样先记**三板斧**：

```logql
# ① 标签选择器（必带，决定扫描范围）
{namespace="gitea", pod=~"gitea.*"}

# ② 行过滤器（内容匹配）
{job="varlogs"} |= "error"              # 包含
d={job="varlogs"} != "debug"             # 不包含
d={job="varlogs"} |~ "(?i)error|oom|failed"   # 正则
d={job="varlogs"} !~ "healthz"            # 正则排除

# ③ 统计速率（可配告警）：每分钟错误行数
sum(rate({namespace="monitoring"} |~ "(?i)error" [5m]))

# ④ 提取字段（logfmt / JSON）
{job="kubernetes-pods"} | json | container="node-exporter" | __error__=""
```

**建议告警**（Loki ruler 或 Grafana Alerting）：`count_over_time({namespace!=""} |~ "OOMKilled" [5m]) > 0`、`sum(rate(...error...[5m]))` 超阈值。

### 7.6 小机避坑

| 坑 | 现象 | 对策 |
|:---|:-----|:-----|
| Promtail 采集无限流 | 某容器刷日志把带宽/磁盘打爆 | scrape_configs 加 `pipeline_stages` 采样/丢弃；Loki 端限 `ingestion_rate_mb` |
| positions 丢了重采 | 节点重启日志重复灌 | positions 落 `emptyDir` 不行，重启就重 → 换 `hostPath: /var/lib/promtail` 持久化 |
| 公网 push 被扫 | :3100 是写接口，被人灌垃圾 | **安全组只放行两节点出口 IP**；更进一步加 basic auth（nginx 反代）|
| 磁盘写满 | Loki chunk 无限长 | `retention_period` + compactor 开启（上面 config 已配）；磁盘 >85% 告警 |
| 标签基数爆炸 | 查不动、内存爆 | **别把易变值（如 request_id）当标签**；标签只放离散有限集（ns/pod/container）|
| 2G 节点跑不动 | OOM | Promtail limits 128Mi 已够；若还紧张换 **Fluent Bit**（内存减半）|

## 八、变更与迁移

**改抓取配置**：KPS 体系下编辑 ServiceMonitor/PodMonitor（或 values 里的 `defaultRules`/`additionalScrapeConfigs`），operator 会自动 reload；手搓栈才需要 `kubectl rollout restart deploy/prometheus`。

**改 values 后重部署（KPS 分批 apply 体系）**：
```bash
export KUBECONFIG=<集群 kubeconfig>
cd <chart 所在目录>
helm template kps ./kube-prometheus-stack-<版本>.tgz -n monitoring -f values.yaml > /tmp/kps-all.yaml
# 按 kind 拆批后重新 apply（CRD 可跳过）
```

**把监控从一个节点迁到另一个节点**（若原节点不稳定）：
```bash
# 1. 改 values 里各组件 nodeSelector 为目标节点
# 2. PVC 是 local-path（单节点本地盘），换节点=数据不跟随，需重建（历史指标丢失）
#    KPS 的 Prometheus PVC 名：prometheus-kps-prometheus-db-prometheus-kps-prometheus-0
kubectl -n monitoring delete statefulset prometheus-kps-prometheus
# 重渲染 + 分批 apply
```

**扩容**：落点节点磁盘/内存宽裕时，Prometheus retention 可放宽到 30~90d，改 values 的 `prometheus.prometheusSpec.retention` + PVC 容量重 apply。

**清理旧栈残留**（手搓栈 → KPS 迁移时）：
```bash
kubectl -n monitoring delete deploy prometheus grafana svc prometheus grafana \
  cm prometheus-config grafana-dash-provider dash1860-file \
  secret grafana-admin pvc prometheus-data grafana-data
kubectl delete clusterrole prometheus-monitoring; kubectl delete clusterrolebinding prometheus-monitoring
# node-exporter DaemonSet 保留（KPS 复用）
```

## 九、安全（公网暴露必读）

- **node-exporter :9100 不再公网暴露** —— 本方案`hostNetwork` 但只在集群内可达（云主机安全组不放行 9100 即可），旧方案的安全组收紧步骤**取消**。
- **Grafana**：NodePort 暴露时，务必强密码 + `GF_USERS_ALLOW_SIGN_UP=false`。**尽量仅内网可达**；外网访问走 SSH 隧道或前置 Ingress + 认证，别裸奔公网。
- **Prometheus :9090** ClusterIP 不对外（本方案已如此）。
- **Loki :3100 若启用**：集群内写入即可，别暴露公网。
- **集群外裸机**：若走 §三 采它，:9100 必须安全组限源（动态 IP 不现实 → 建议改 push 模式或接入集群）。
