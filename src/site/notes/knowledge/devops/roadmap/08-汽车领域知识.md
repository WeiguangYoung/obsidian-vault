# 八、汽车领域知识（车载协议综述）

> 面向汽车软件/嵌入式方向的领域知识概览：诊断、架构、通信协议与 OTA 升级。

## 8.1 车载通信协议全景

一辆现代汽车里有几十上百个 ECU（电子控制单元），它们之间靠各种总线/网络通信。这些协议不是任意选的，而是**按速率和用途分层**——贵的高速骨干连核心部件，便宜的低速总线连车身小件：

| 协议 | 速率 | 拓扑 | 典型用途 |
|:----|:------|:------|:------|
| **LIN** | ≤ 20 kbps | 单主多从（1 主 + ≤15 从） | 车门、车窗、雨刮、座椅等低速车身件 |
| **CAN** | 125 kbps ~ 1 Mbps | 多主总线（带仲裁） | 动力、车身、底盘，最主流 |
| **CAN FD** | 最高 8 Mbps（数据段） | 同 CAN | 大数据量、刷写、域控 |
| **FlexRay** | 10 Mbps | 时间触发 + 事件触发 | 线控底盘、主动悬架（逐步被以太网替代） |
| **MOST** | 150 Mbps | 环形 | 车载多媒体（老方案） |
| **车载以太网** | 100 Mbps ~ 10 Gbps | 交换式 | 智驾、域控、SOME/IP、DoIP |

**架构演进的趋势**值得留意：早先是"每个功能一个 ECU"，后来变成"按域集中"（动力域、座舱域、智驾域各一个域控制器），现在正走向"**中央计算 + 区域控制器（Zonal）**"——一个中央大脑 + 若干区域网关，构成"**以太网做骨干、CAN/LIN 做边缘**"的分层网络。

## 8.2 CAN / CAN FD

CAN 之所以能成为车载总线的主流，靠的是三个关键设计：

- **多主总线**：所有节点共享一条差分线（CAN_H / CAN_L），谁想发就发，不像传统主从那样要等指挥。差分信号还带来很强的抗干扰能力（车内电磁环境恶劣）。
- **消息导向**：报文靠 **CAN ID 广播**，没有"源地址/目的地址"的概念——谁需要谁收。ID 越小优先级越高。
- **可靠性机制**：CRC 校验、位填充、错误帧、自动重发，确保恶劣环境下数据可靠。

### 位仲裁：CAN 的精华设计

多主总线最怕"撞车"——两个节点同时发怎么办？CAN 的答案非常优雅：**非破坏性位仲裁**。

```
节点 A 发 ID=0x100，节点 B 发 ID=0x200，同时开始发送：
ID 逐位比较，显性位(0) 覆盖 隐性位(1)
A(0x100) 在第一个差异位胜出 → B 自动退让，下轮重发
→ 无损仲裁（winner 的数据不被破坏）
```

关键在于"**位仲裁的同时也在传数据**"：谁的 ID 数值小（二进制里显性位更多），谁就能在整个 ID 段"压过"对手，而且**胜者完全感知不到发生过冲突**，数据一字不差地发出去。这就是"非破坏性"的含义——冲突不丢包、不重传。

### 帧类型

| 类型 | 作用 |
|:----|:------|
| **数据帧** | 传输数据（标准帧 11 位 ID / 扩展帧 29 位 ID） |
| **远程帧** | 请求某 ID 的数据 |
| **错误帧** | 检测到错误时主动通知全总线 |
| **过载帧** | 接收方忙，请求延迟 |

### CAN ID 与信号

- 报文按 ID 标识，载荷最多 **8 字节**（CAN FD 最多 64 字节）
- 一条报文里的多个信号，按 **起始位 + 长度 + 字节序（Intel/Motorola）** 排布，这些定义由 **DBC 文件** 描述——所以做诊断/测试时，DBC 是必备的"翻译字典"。

### 排障与开发工具

```bash
# Linux SocketCAN
cansend can0 123#DEADBEEF    # 发一帧
candump can0                 # 抓包
```

```python
import can
bus = can.interface.Bus(channel='can0', bustype='socketcan')
msg = can.Message(arbitration_id=0x123, data=[0xDE, 0xAD], is_extended_id=False)
bus.send(msg)
```

## 8.3 LIN

LIN 是 CAN 的"廉价补充"。它**单主多从**（一个 Master 调度，若干从节点被动响应），只用**单根信号线**（加电源和地），速率很低（≤20 kbps）。Master 按一张**调度表**轮流询问各从节点，整个总线是有序、可预测的。

它的定位很清楚：**对带宽和实时性都不敏感的简单执行器**——车窗、雨刮、座椅调节、车灯、一些传感器。这些地方用 CAN 属于浪费，LIN 够用且便宜。

## 8.4 UDS（统一诊断服务）

> 详见 [[knowledge/embedded/UDS协议入门指南\|UDS 协议入门指南]]。此处为综述。

UDS（ISO 14229）是汽车统一的"诊断语言"——读故障码、读数据、刷写固件，全靠它。核心概念：

| 概念 | 说明 |
|:----|:------|
| **SID** | 服务标识（0x10 会话控制、0x22 读数据、0x2E 写数据、0x34/0x36/0x37 刷写） |
| **DID** | 数据标识符，配合 0x22/0x2E 读写 |
| **DTC** | 诊断故障码，故障记录 |
| **Session** | 诊断会话（默认 / 编程 / 扩展） |
| **寻址** | 物理寻址（点到点）/ 功能寻址（广播） |

### 传输层承载：报文怎么跑在总线上

UDS 本身只是"应用层协议"，它需要底层帮忙传字节。两种常见承载：

| 承载 | 说明 |
|:----|:------|
| **ISO-TP (ISO 15765-2)** | 基于 CAN 的分段传输 |
| **DoIP (ISO 13400)** | 基于以太网的诊断，用于大数据刷写 |

**为什么需要 ISO-TP？** 因为 CAN 单帧最多 8 字节，而 UDS 报文（尤其是刷写数据）动辄几百上千字节——必须**分段**。ISO-TP 用四种帧协作完成分段与重组：

| 帧类型 | 作用 |
|:----|:------|
| **SF** 单帧 | ≤7 字节，一帧发完 |
| **FF** 首帧 | 声明总长度，启动分段 |
| **CF** 连续帧 | 携带后续数据（带序号，防乱序） |
| **FC** 流控帧 | 接收方反馈继续/等待/溢出（流控） |

而 **DoIP 走以太网**，单包能装的数据多得多，所以更适合刷写这种大数据量场景。

### 典型刷写流程

刷写一个 ECU 的固件，UDS 流程大致是：

```
进入扩展会话 → 安全访问（27）→ 写指纹 → 擦除 Flash（31）→
请求下载（34）→ 传输数据（36）→ 退出传输（37）→ 校验依赖（31）→ 复位（11）
```

注意其中的**安全访问（0x27）**——刷写前必须过安全校验（通常是 seed-key 挑战应答），防止未授权刷写；以及最后的**校验依赖**——确认所有数据块都写对了才让 ECU 复位。

## 8.5 AUTOSAR

AUTOSAR（**AUT**omotive **O**pen **S**ystem **AR**chitecture）是汽车软件的**标准化架构**，目标是**软硬件解耦、模块复用**——让同一套应用软件能跑在不同 MCU 上，也让不同供应商的模块能组合在一起。

它分两个平台，对应两类截然不同的场景：

| 维度 | Classic Platform (CP) | Adaptive Platform (AP) |
|:----|:------|:------|
| **定位** | 深度嵌入式、实时、资源受限 | 高性能计算（智驾、域控） |
| **OS** | OSEK/VDX，静态配置 | POSIX（PSE51），支持动态 |
| **通信** | RTE + COM（CAN/LIN/FlexRay 信号） | SOA + SOME/IP（服务化） |
| **语言** | C（MISRA-C） | C++14/17 |
| **典型载体** | MCU（车身、动力） | SoC（智驾、座舱） |

简单说：**CP 是传统 MCU 世界的经典架构，AP 是高性能 SoC 世界的新架构**（面向服务、支持动态部署）。

### CP 的分层架构

```
┌─────────────────────────────┐
│        应用层 (SWC)          │  软件组件
├─────────────────────────────┤
│     RTE（运行时环境）         │  组件间通信
├─────────────────────────────┤
│  基础软件 BSW                 │
│  ┌────────┬────────┬───────┐ │
│  │ 服务层  │ ECU抽象│ 微控器 │ │  DCM/DEM/COM/NvM
│  │(Services)│(ECU Abstraction)│(MCAL)│ │
│  └────────┴────────┴───────┘ │
├─────────────────────────────┤
│        微控制器 (MCU)         │
└─────────────────────────────┘
```

分层的含义：上层应用（SWC）只管业务逻辑，不关心底层是哪个芯片；中间 **RTE** 负责组件间通信；底层 **BSW** 才是跟硬件打交道的部分（服务层如 DCM/DEM、ECU 抽象层、微控制器抽象层 MCAL）。

### UDS 在 AUTOSAR 中的归属

做诊断时绕不开这两个 BSW 组件：

- **DCM**（Diagnostic Communication Manager）：**负责处理 UDS 诊断服务**的组件
- **DEM**（Diagnostic Event Manager）：**管理 DTC 与故障事件**

诊断配置通常用 **ODX / ARXML** 这类标准格式描述。

> 详见 [[knowledge/embedded/UDS协议入门指南\|UDS 协议入门指南 · AUTOSAR 章节]]。

## 8.6 OTA（空中升级）

OTA（Over-The-Air）就是"**远程给车升级**"。按升级对象分两类：

| 类型 | 目标 | 说明 |
|:----|:------|:------|
| **SOTA** | 软件升级 | 座舱娱乐、T-Box 应用层，体验类 |
| **FOTA** | 固件升级 | ECU 固件、BMS、智驾域，功能类 |

### 典型 FOTA 链路

```
云端发布升级包 → T-Box 下载 → 车端 OTA Master 校验（签名/完整性）
  → 分发到目标 ECU → 各 ECU Bootloader 刷写 → 回滚兜底 → 上报结果
```

**T-Box** 是车上的通信网关（通过蜂窝网连云端），**OTA Master** 是编排者（负责下载、校验、分发、触发各 ECU 刷写）。

### 关键技术点

| 要点 | 说明 |
|:----|:------|
| **差分包** | 只传新旧版本的差异，减小包体（bsdiff/courgette） |
| **断点续传** | 弱网环境下支持续传、分批下载 |
| **双分区（A/B）** | 双系统镜像，升级失败可回滚 |
| **安全** | 签名验签、加密传输、防降级 |
| **一致性** | 多 ECU 协同刷写（依赖关系、原子性） |
| **车规约束** | 刷写时车辆需满足条件（驻车、电量、网络） |

### SOTA vs FOTA 对比

| 维度 | SOTA | FOTA |
|:----|:------|:------|
| **刷写对象** | 应用层/座舱 | ECU 固件/底层 |
| **风险** | 低（可回退） | 高（刷坏可能开不了车） |
| **触发路径** | T-Box → 车机 | T-Box → OTA Master → 各 ECU |
| **安全等级** | 一般 | 高（验签+回滚+条件检查） |

### 与 UDS/Bootloader 的关系

- ECU 侧的刷写**仍然是走 UDS 刷写流程 + Bootloader**
- OTA Master 只负责**编排**：下载 → 校验 → 触发各 ECU 进入编程会话 → 刷写 → 复位验证

换句话说，OTA 是"**无线下载 + 编排**"，而真正的"写 Flash"这件事，还是 UDS 和 Bootloader 在干。

## 8.7 车载以太网与 SOA

随着智驾、座舱对带宽要求暴涨，CAN 那点速率不够用了，**车载以太网**开始成为骨干：

| 技术 | 说明 |
|:----|:------|
| **100BASE-T1 / 1000BASE-T1** | 单对双绞线车载以太网（BroadR-Reach） |
| **SOME/IP** | 面向服务的中间件协议（服务发现 + RPC + 事件） |
| **SOME/IP-SD** | 服务发现（Offer/Find/Subscribe） |
| **DoIP** | 基于 IP 的诊断（ISO 13400），支持大数据刷写 |
| **TSN** | 时间敏感网络，保障确定性时延（AVB/音视频、线控） |

**SOME/IP** 是这里的核心新概念。传统 CAN 是"信号导向"（谁广播一个信号，谁需要谁收），而 SOME/IP 是"**面向服务**"——服务方把自己"提供什么能力"发布出去，使用方按需订阅/调用（SOA，面向服务架构）。这种方式更灵活，适合功能频繁迭代的智驾/座舱域。

## 8.8 汽车软件与 DevOps 的结合点

汽车软件的 CI/CD 和互联网软件差别很大，几个关键差异点：

| 环节 | 关注点 |
|:----|:------|
| **构建** | 交叉编译工具链、CMake/Bazel、AUTOSAR 工程生成 |
| **质量** | MISRA-C、静态分析（Cppcheck/clang-tidy）、单元测试（GTest） |
| **制品** | .elf → .hex/.bin/S19，Bootloader 刷写包 |
| **合规** | ASPICE、ISO 26262 功能安全、ISO 21434 网络安全 |
| **测试** | HIL/SIL、CANoe/CANalyzer 自动化、总线仿真 |
| **交付** | OTA 发布流水线、诊断刷写自动化 |

和普通软件 CI/CD 最大的不同：**产物形态多样**（不是只有一个可执行文件，还有 .hex/.bin/S19 等）、**合规要求硬**（功能安全/网络安全要取证）、**测试依赖硬件**（HIL 硬件在环）。

## 8.9 学习路线建议

```
基础：C/C++ + 嵌入式基础（MCU、外设、中断）
  ↓
总线：CAN/CAN FD → LIN → 车载以太网 / SOME/IP
  ↓
诊断：UDS + ISO-TP → 刷写/Bootloader → DoIP
  ↓
架构：AUTOSAR（CP → AP）→ SOA
  ↓
系统：OTA → 整车 E/E 架构 → 功能安全 / 网络安全
```
