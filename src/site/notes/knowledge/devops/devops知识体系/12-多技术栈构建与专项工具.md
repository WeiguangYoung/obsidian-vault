# 十二、多技术栈构建与专项工具

> 覆盖吉利 JD 中 Repo/Gerrit/KubeSphere/Maven/Gradle/C++ 依赖管理等缺口。

## 12.1 Repo — 多仓库管理

### 是什么

Google 为 Android/AOSP 开发的多 Git 仓库管理工具。在汽车行业，大型嵌入式项目往往拆分为数十甚至上百个 Git 仓库（BSP、Middleware、App 层），Repo 是管理这些仓库的标准方案。

### 核心概念

| 概念 | 说明 |
|:----|:------|
| **manifest** | XML 清单文件，定义所有 Git 仓库的地址、分支、路径 |
| **default.xml** | 默认清单，描述整个项目的仓库组成 |
| **repo sync** | 一键同步所有仓库到指定分支/标签 |
| **repo start** | 在所有相关仓库创建主题分支 |
| **repo upload** | 将变更推送到 Gerrit 进行代码评审 |

### manifest 示例

```xml
<?xml version="1.0" encoding="UTF-8"?>
<manifest>
  <remote name="origin" fetch="ssh://git@gerrit.example.com:29418/" />
  <default revision="main" remote="origin" sync-j="4" />

  <project path="bsp/mcu-a" name="platform/bsp/mcu-a" revision="v2.1.0" />
  <project path="bsp/mcu-b" name="platform/bsp/mcu-b" revision="v2.1.0" />
  <project path="middleware/someip" name="middleware/someip" />
  <project path="apps/cluster" name="apps/cluster" />
  <project path="apps/ivi" name="apps/ivi" />
  <project path="tools/build" name="tools/build" />
</manifest>
```

### 常用命令

```bash
repo init -u ssh://git@gerrit/project/manifest.git -b main  # 初始化
repo sync                                                      # 同步所有仓库
repo start feature-xxx --all                                   # 创建分支
repo status                                                    # 查看变更
repo upload                                                    # 提交到Gerrit评审
repo forall -c 'git clean -fdx'                               # 所有仓库执行命令
```

## 12.2 Gerrit — 代码评审系统

### vs GitLab MR

| 维度 | Gerrit | GitLab MR |
|:----|:------|:----------|
| **评审粒度** | 单个 Commit | 整个分支/MR |
| **工作流** | Commit → Review → Rework（amend）→ +2 → Submit | Push Branch → MR → Review → Merge |
| **权限模型** | 细粒度：+1/+2 分权 | 相对粗粒度 |
| **适用场景** | 大型开源项目（AOSP）、汽车行业 | 通用企业 |
| **学习曲线** | 陡峭 | 平缓 |

### Gerrit CI 集成

```
开发者 git commit → repo upload
    ↓
Gerrit 接收变更
    ↓
Jenkins/GitLab CI 触发验证（基于 refs/changes/xx/yy/zz）
    ↓
CI 结果回写到 Gerrit（Verified +1 / -1）
    ↓
人工 Review（Code-Review +2）
    ↓
Submit → Merge 到目标分支
```

### Jenkins 触发 Gerrit Patch

```groovy
// Jenkins 通过 Gerrit Trigger 插件监听
pipeline {
    agent any
    triggers {
        gerrit(
            project: 'platform/bsp/mcu-a',
            branch: 'refs/heads/main',
            triggerOn: [
                patchsetCreated(approvalCategory: 'Code-Review', approvalValue: '+1')
            ]
        )
    }
    stages {
        stage('Verify') {
            steps {
                sh 'cmake -B build && cmake --build build'
                sh 'ctest --test-dir build --output-on-failure'
            }
        }
    }
}
```

## 12.3 KubeSphere — 容器平台

### 核心能力

| 模块 | 功能 |
|:----|:------|
| **多租户管理** | 企业空间 → 项目 → 资源隔离（比原生 K8s 更友好） |
| **DevOps 流水线** | 内置 Jenkins 引擎，可视化编排 CI/CD |
| **灰度发布** | 蓝绿部署、金丝雀发布、流量镜像 |
| **微服务治理** | 基于 Istio/Spring Cloud 的服务网格 |
| **应用商店** | 基于 Helm 的应用模板市场 |
| **可观测性** | 内置 Prometheus + Grafana + EFK 日志 |

### KubeSphere DevOps 流水线示例

```
拉取代码 → 单元测试 → 代码分析 → 镜像构建 → 推送仓库 → 部署到开发环境 → 部署到生产
```

KubeSphere 将 Jenkins Pipeline 封装为可视化编排，支持：
- 凭证管理（Git 密钥、镜像仓库密码）
- 构建节点池管理
- 流水线模板与参数化构建

### KubeSphere vs 原生 K8s

| 场景 | KubeSphere 优势 |
|:----|:------|
| 团队权限管理 | 企业空间/项目/角色体系，无需手动 RBAC |
| 流水线 | 开箱即用的 DevOps 引擎，降低 Jenkins 维护成本 |
| 日志/监控 | 内置可观测性，无需额外搭建 EFK/Prometheus |
| 应用发布 | 灰度/蓝绿/金丝雀发布一键配置 |

## 12.4 Java 构建体系

### Maven

| 概念 | 说明 |
|:----|:------|
| **pom.xml** | 项目对象模型，定义依赖、插件、构建配置 |
| **坐标 GAV** | GroupId:ArtifactId:Version 唯一标识一个制品 |
| **生命周期** | clean → compile → test → package → verify → install → deploy |
| **依赖管理** | 传递依赖、依赖范围（compile/test/provided）、依赖冲突仲裁 |
| **多模块** | 父子 POM 聚合构建，统一管理版本 |

### Gradle

| 概念 | 说明 |
|:----|:------|
| **build.gradle(.kts)** | Groovy DSL 或 Kotlin DSL 构建脚本 |
| **Task** | 构建的基本单元，比 Maven 阶段更灵活 |
| **依赖配置** | implementation / api / compileOnly / testImplementation |
| **增量构建** | 自动跳过未变更的 Task（比 Maven 快） |
| **Gradle Wrapper** | gradlew 脚本，锁定 Gradle 版本，无需预装 |

### CI/CD 中的 Java 构建

```groovy
// Jenkins Pipeline 示例
stage('Build Java Service') {
    steps {
        // Maven 项目
        sh 'mvn clean package -DskipTests'
        // 或 Gradle 项目
        sh './gradlew clean build -x test'
    }
}
stage('Test') {
    steps {
        sh 'mvn test'                   // Maven
        // sh './gradlew test'          // Gradle
    }
    post {
        always {
            junit '**/target/surefire-reports/*.xml'   // Maven
            // junit '**/build/test-results/**/*.xml'  // Gradle
        }
    }
}
stage('Publish') {
    steps {
        // Maven: 发布到 Nexus
        sh 'mvn deploy -DaltDeploymentRepository=nexus::default::https://nexus.example.com/repository/maven-releases/'
        // Gradle: 使用 maven-publish 插件
        // sh './gradlew publish'
    }
}
```

## 12.5 C++ 依赖管理

### 传统方式 vs 现代方案

| 方式 | 工具 | 问题 |
|:----|:------|:------|
| 传统 | vendor 目录、Git Submodule | 版本漂移、更新困难、二进制不兼容 |
| 现代 | Conan / vcpkg | 声明式依赖、版本锁定、二进制缓存 |

### Conan

```python
# conanfile.py
from conan import ConanFile

class MyProject(ConanFile):
    name = "my-app"
    version = "1.0"
    settings = "os", "compiler", "build_type", "arch"

    def requirements(self):
        self.requires("boost/1.84.0")
        self.requires("protobuf/3.21.12")
        self.requires("gtest/1.14.0")

    def build(self):
        cmake = CMake(self)
        cmake.configure()
        cmake.build()
```

```bash
# CI 中使用
conan install . --profile=arm-none-eabi-gcc --build=missing
cmake --preset conan-release
cmake --build --preset conan-release
```

### vcpkg

- 微软维护，CMake 原生集成
- 经典模式（全局安装）vs Manifest 模式（项目级 `vcpkg.json`）

```json
// vcpkg.json
{
  "name": "my-app",
  "version": "1.0",
  "dependencies": ["boost-asio", "protobuf", "gtest"]
}
```

```bash
# CI 集成（Manifest 模式）
cmake -B build -DCMAKE_TOOLCHAIN_FILE=$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake
cmake --build build
```

### CI/CD 最佳实践

| 实践 | 说明 |
|:----|:------|
| **依赖锁定** | conan.lock / vcpkg baseline commit → 可复现构建 |
| **二进制缓存** | 自建 Conan/Artifactory 远端，避免重复编译 |
| **交叉编译 Profile** | ARM GCC / RISC-V / 多工具链预设 |
| **SBOM 生成** | CycloneDX 格式，满足合规要求 |

## 12.7 研发效能度量

### DORA 四大指标

| 指标 | 定义 | 目标 |
|:----|:------|:------|
| **部署频率 (DF)** | 多久部署一次到生产 | 按需/每天多次 |
| **变更前置时间 (LT)** | 从 Commit 到上生产的时间 | < 1 小时（Elite） |
| **变更失败率 (CFR)** | 导致故障的部署占比 | < 15%（Elite） |
| **恢复时间 (MTTR)** | 从故障到恢复的时间 | < 1 小时（Elite） |

### 数据采集

```
GitLab API → 取 Commit/MR 时间
Jenkins API → 取构建开始/结束时间
K8s API → 取部署时间、Pod 状态
Jira API → 取故障工单信息

→ 汇总到效能看板（Grafana Dashboard）
```
