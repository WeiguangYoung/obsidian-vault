# 车载功能安全 CI 落地清单

> ISO 26262 管**产品安全**（ASIL A~D），ASPICE 管**过程能力**（CL 1~5）。CI 的责任边界是：**用自动化证明「安全相关实现完成、且可追溯」**——它不代替安全分析，也不代替 HIL 台架。
> 一句话主线：**凡是概率性的判定都不能当安全门禁；凡是确定性的判定都必须能在流水线里复现。**

## 三、部分可复用（🔄）——有基础但不够

### 🔄 8. 覆盖率采集与 ASIL 分级门禁

| 项 | 内容 |
|:--|:--|
| 现状 | 有覆盖率采集（行覆盖 / 分支覆盖）|
| 缺口 | **没有按 ASIL 分级判定** |
| 待补 | 模块打 ASIL 标签 → 按标签查阈值 |

**ASIL 覆盖率要求**：

| ASIL | 结构覆盖率 | 门禁值 |
|:--|:--|:--|
| ASIL D | **MC/DC** | 100% |
| ASIL C | MC/DC 或 条件+判定 | ≥ 95% |
| ASIL B | 分支 + 语句 | ≥ 90% |
| ASIL A | 语句 | ≥ 80% |
| QM | 无强制 | — |

**落地脚本思路**：
```bash
# 1. 从配置文件读模块 ASIL 等级
# 2. 从 lcov XML 取实测覆盖率
# 3. 按等级判定

for module in $(cat asil-map.yaml | yq '.modules[]'); do
  asil=$(yq ".modules[] | select(.name==\"$module\") | .asil" asil-map.yaml)
  threshold=$(case $asil in D) echo 100;; C) echo 95;; *) echo 90;; esac)
  actual=$(lcov --summary coverage.info 2>&1 | grep lines | awk '{print $2}' | tr -d %)
  [ "$actual" -lt "$threshold" ] && { echo "FAIL: $module $asil needs $threshold%, got $actual%"; exit 1; }
done
```

### 🔄 9. MC/DC 结构覆盖

| 项 | 内容 |
|:--|:--|
| 现状 | 只有行覆盖 / 分支覆盖 |
| 缺口 | **MC/DC 测不出来** |
| 待补 | 工具选型 + 集成 |

**为什么行覆盖不够**：`if (a && b || c)` 这种复合条件，分支覆盖只测真/假两次，MC/DC 要求每个原子条件都能独立影响结果，需要 n+1 个用例。

**工具选项**：

| 工具 | 平台 | 说明 |
|:--|:--|:--|
| VectorCAST / C++test | 商用 | 完整 MC/DC，车载主流 |
| Tessy | 商用 | 单元测试 + MC/DC |
| Gcov + 自研 | 开源 | 只能到分支，不能到 MC/DC |

**结论**：ASIL C/D 项目，MC/DC 测量基本只能靠商用工具。这一项的开支和采购周期要提前算。

## 四、待落地（⬜）——车载独有

### ⬜ 10. MISRA 规则集

| 项 | 内容 |
|:--|:--|
| 现状 | cppcheck 默认规则，等于没有 MISRA |
| 目标 | MISRA C:2012 + AUTOSAR C++14 合规 |
| 关键 | **存量不清零**——冻结基线 + 新增归零 |

**基线管理机制**：
```
.gitlab/misra-baseline.txt      ← 存量违规清单（含 justification）
     ↓
CI 扫描 → 对比基线 → 只报告新增违规 → 新增 > 0 则失败
```

**规则裁剪纪律**：
- 每条 deviation 必须有 justification（写在哪、为什么、谁批准）
- justification 入库，审核时要能捞出
- 不允许「因为太多所以关掉规则」

### ⬜ 11. 需求双向追溯（车载核心）

| 项 | 内容 |
|:--|:--|
| 现状 | **完全没有** |
| 标准依据 | ASPICE SWE.1~6 |
| 优先级 | **最高**——审核最常见的扣分点 |

**追溯链**：
```
需求 ID ⟷ 架构组件 ⟷ 详细设计 ⟷ 代码 ⟷ 测试用例 ⟷ 测试结果
```

**CI 落地三步**：

| 步骤 | 做法 | 门禁 |
|:--|:--|:--|
| 1. 需求 → 代码 | commit message 必须含 `REQ-\d+` | 缺 ID 拒绝合入 |
| 2. 代码 → 用例 | 测试用例加 `@req REQ-1234` 标签 | 需求无对应用例 → 报警 |
| 3. 用例 → 结果 | CI 输出 JUnit XML，脚本汇总 | 追溯断链 → 失败 |

**追溯矩阵生成脚本**：
```python
# 从 commit / 测试标签 / 测试结果三方汇总
matrix = []
for req in all_requirements:
    commits = find_commits_by_req(req)
    tests   = find_tests_by_req(req)
    results = get_test_results(tests)
    matrix.append({
        "需求": req,
        "实现": commits or "❌ 无",
        "用例": tests or "❌ 无",
        "结果": results or "❌ 未执行",
    })
# 输出 CSV，作为 ASPICE 审核证据
```

> **审核最有力的证据不是文档，是流水线的门禁记录。**「你问怎么保证质量？每次提交都有，每次都能查。」

### ⬜ 12. 禁用 API 检查

| 项 | 内容 |
|:--|:--|
| 依据 | ISO 26262-6（安全相关编码规范）|
| 做法 | 自定义 clang-tidy 规则 / PC-lint 规则 |

**ASIL D 常见禁用项**：

| 禁用项                                  | 原因          | 检查方式                        |
| :----------------------------------- | :---------- | :-------------------------- |
| `malloc` / `free` / `new` / `delete` | 动态内存不可预测    | 符号扫描                        |
| 递归调用                                 | 栈深度不可静态确定   | 调用图分析                       |
| `goto`                               | 控制流复杂化（可裁剪） | AST 检查                      |
| 未初始化变量                               | 未定义行为       | 编译器 `-Werror=uninitialized` |
| `printf` / `sprintf`                 | 无界缓冲        | 符号扫描                        |
| 浮点运算（部分场景）                           | 确定性要求       | 类型检查                        |
| 多重继承 / 虚函数（C++）                      | 运行时开销不可预测   | AST 检查                      |

**clang-tidy 自定义规则示例**（禁 malloc）：
```yaml
# .clang-tidy
Checks: >
  -*,
  bugprone-*,
  cert-*,
  cppcoreguidelines-no-malloc,
  cppcoreguidelines-owning-memory,
WarningsAsErrors: '*'
```

### ⬜ 13. 工具置信度（TCL）

| 项 | 内容 |
|:--|:--|
| 依据 | **ISO 26262-8 Clause 11** |
| 核心问题 | 你用来自动判定的工具，本身可信吗？ |

**工具置信度评估（TCL）**：

```
TCL1（最低）：工具出错只影响成本，不影响安全 → 不需要特别鉴定
TCL2：工具出错可能漏掉错误 → 需要资格确认
TCL3（最高）：工具出错可能引入错误 → 需要严格鉴定
```

**CI 落地要求**：

| 要求 | 做法 |
|:--|:--|
| 版本固化 | 工具版本写死在 CI 镜像里，不用 `latest` |
| 鉴定记录 | `tool-qualification/` 目录存 TCL 评估报告 |
| 结果可复现 | 同一 commit 两次扫描结果一致（回归验证）|
| 变更受控 | 升级工具要走 MR + 审批 + 重新鉴定 |

**`tool-versions.yaml` 示例**：
```yaml
tools:
  cppcheck:
    version: 2.14.1
    tcl: 2
    qualification: tool-qualification/cppcheck-2.14.1.md
  polyspace:
    version: R2024a
    tcl: 3
    qualification: tool-qualification/polyspace-r2024a.md
```

**门禁**：CI 启动时校验实际版本 == `tool-versions.yaml`，不一致直接失败。

### ⬜ 15. 密码算法白名单

| 项 | 内容 |
|:--|:--|
| 依据 | ISO 21434（车载安全通信）|
| 做法 | 扫描密码相关函数调用，非白名单即失败 |

**典型白名单**：

| 允许 | 禁止 |
|:--|:--|
| AES-128/256-GCM | DES / 3DES |
| SHA-256 / SHA-3 | MD5 / SHA-1 |
| RSA-2048+ / ECC P-256+ | RSA-1024 |
| HMAC-SHA256 | 自有算法 |

**检测方式**：
```bash
# 扫描符号引用
grep -rE "MD5_Init|DES_|SHA1_Init|RC4_" src/ && exit 1
```

### ⬜ 17. 栈使用分析

| 项 | 内容 |
|:--|:--|
| 依据 | ISO 26262-6（资源使用验证）|
| 做法 | `-fstack-usage` 生成 `.su` 文件，与预算比对 |

```bash
# 编译时加
CFLAGS += -fstack-usage

# 分析
cat build/**/*.su | awk '{print $2, $1}' | sort -rn | head -20
# 输出：最大栈帧位置 + 大小

# 门禁：单函数栈帧超阈值 或 最坏路径累计栈超 RAM 预算 → 失败
```

**为什么重要**：栈溢出在嵌入式里是静默崩溃，运行时抓不到，只能静态算。

### ⬜ 18. 产物签名

| 项 | 内容 |
|:--|:--|
| 依据 | ISO 21434 |
| 做法 | 构建完对 `.hex`/`.s19` 签名，烧录前验签 |

```bash
# 签名
openssl dgst -sha256 -sign private.pem -out app.sig app.bin

# 烧录前验签
openssl dgst -sha256 -verify public.pem -signature app.sig app.bin
```

**CI 落地**：签名密钥由 CI 凭证管理（Vault / KMS），不落盘、不进仓库。

### ⬜ 19. HIL 台架回归

| 项 | 内容 |
|:--|:--|
| 依据 | ASPICE SWE.5/6 |
| 成本 | **最高**——台架资源有限，跑一次几小时 |

**分级策略**：

| 触发条件 | 跑什么 | 时长 |
|:--|:--|:--|
| 每个 PR | 只跑①~⑥（编译/静态/单测/追溯）| ≤ 15 分钟 |
| 合入 main | 加 HIL 冒烟集 | 30 分钟~1 小时 |
| 发版前 | HIL 全量回归 | 数小时 |
| 夜间 | HIL 全量 + 长稳 | 整夜 |

**绝不能让 HIL 阻塞每个 PR**——否则开发节奏会被拖死，最后大家绕过 CI 直接推。

## 五、门禁分级：哪些可以阻断合入

**核心原则：概率性判定不能当安全门禁。**

| 门禁 | 阻断 | 理由 |
|:--|:--:|:--|
| 编译通过 | ✅ | 确定性 |
| MISRA 新增违规 | ✅ | 确定性 |
| 单测失败 | ✅ | 确定性 |
| 覆盖率不达 ASIL 阈值 | ✅ | 确定性 |
| 追溯矩阵断链 | ✅ | 确定性 |
| 密钥 / 密码算法白名单 | ✅ | 确定性 |
| 工具版本漂移 | ✅ | 确定性 |
| 制品签名校验 | ✅ | 确定性 |
| **LLM 代码评审** | ❌ | **概率性（F1 最高 61%）**|
| **LLM 漏洞解释** | ❌ | 只读建议 |
| **LLM 自动修复** | ❌ | 需过完整 CI 才能开 PR |

## 六、典型车载 CI 流水线

```
┌──────────────────────────────────────────────────┐
│ ① 提交门禁（秒级）                                │
│    commit 含需求 ID · 密钥扫描 · 大文件检查        │
├──────────────────────────────────────────────────┤
│ ② 构建（分钟级）                                  │
│    交叉编译 · -Werror 全开 · -fstack-usage        │
├──────────────────────────────────────────────────┤
│ ③ 静态分析（分钟级）                              │
│    MISRA 门禁 · 禁用 API · 密码算法白名单         │
├──────────────────────────────────────────────────┤
│ ④ 单元测试（分钟级）                              │
│    GTest · 覆盖率按 ASIL 判定 · MC/DC（C/D）      │
├──────────────────────────────────────────────────┤
│ ⑤ 追溯校验（秒级）                                │

```

## 七、常见坑

| 坑 | 表现 | 解法 |
|:--|:--|:--|
| **MISRA 全量清零** | 项目永久停滞 | 冻结基线 + 新增归零 |
| **覆盖率造假** | 为达标写无断言测试 | 断言数量检查 + 变异测试抽检 |
| **追溯靠人工填表** | 审核前突击补，一查就穿帮 | 需求 ID 打进 commit，CI 自动生成 |
| **工具版本随意升级** | 规则变了，历史数据无法对比 | 镜像锁定 + 变更走审批 |
| **HIL 阻塞每个 PR** | 一跑几小时，节奏被拖死 | HIL 只跑夜间 + 发版 |
| **门禁太严没人提 PR** | 开发者绕过 CI 直接推 | 分级：QM 宽、ASIL D 严 |
| **「有静态分析」当「过 MISRA」** | 审核时规则集是空的 | 规则集、基线、deviation 三件套齐全 |
| **MC/DC 想用开源工具测** | 测不出来 | ASIL C/D 认命买商用工具 |

## 八、实施路线

### 阶段一：补齐确定性门禁（1~2 个月）

```
⬜ 10 MISRA 规则集 + 基线管理
⬜ 12 禁用 API 检查
⬜ 16 密钥扫描
🔄 8  覆盖率按 ASIL 分级
⬜ 13 工具版本固化
```

**目标**：让「确定性判定」全部到位，每 PR 都能跑。

### 阶段二：追溯与证据（2~3 个月）

```
⬜ 11 需求双向追溯
⬜ 20 追溯证据归档
⬜ 14 SBOM
⬜ 18 产物签名
```

**目标**：审核时不靠补文档，靠流水线记录。

### 阶段三：深度覆盖（3~6 个月）

```
🔄 9  MC/DC 测量（需采购工具）
⬜ 17 栈使用分析
⬜ 15 密码算法白名单
⬜ 19 HIL 台架集成
```

**目标**：ASIL C/D 项目的完整合规。

## 九、复用度小结

| 类别 | 数量 | 说明 |
|:--|:--:|:--|
| ✅ 已落地 | 7 | 编译、单测、静态框架、增量、归档、架构校验、状态回写 |
| 🔄 部分可复用 | 2 | 覆盖率（缺 ASIL 分级）、MC/DC（缺工具）|
| ⬜ 待落地 | 11 | MISRA 规则、追溯、禁用 API、TCL、SBOM、密码、密钥、栈、签名、HIL、证据归档 |

**结论**：现有流水线骨架可复用约 **45%**（9/20）。真正的工作量在**规则集、追溯、工具置信度**这三块——它们不是「写个脚本」，而是「建一套需要长期维护的过程资产」。

---

## 十、一句话总结

> 车载功能安全的 CI 落地，难点从来不在「流水线怎么写」，而在「**能不能拿出证据**」。编译通过、测试全绿这些互联网 CI 的常规动作只是入场券；MISRA 基线、双向追溯、工具置信度这三样，才是车规的门槛。
